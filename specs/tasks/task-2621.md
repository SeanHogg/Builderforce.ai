# PRD: P1 — Remirror advisory calendar events on patch + timezone-preserving provider writes

**Parent:** #2532  
**Depends on:** #2537 (P0 — create/cancel mirror only)  
**Priority:** P1

---

## Problem & Goal

P0 (#2537) mirrors advisory meetings to Google and Microsoft calendars on create and cancel only. `CalendarProvider` (`api/src/application/calendar/calendarProviders.ts`) exposes `createEvent`, `deleteEvent`, `listUpcoming`, and `freeBusy` — there is no `updateEvent`.

When an advisor edits title, time, location, or join URL, the remote event is left stale. Re-running create produces a duplicate. Microsoft `createEvent` hardcodes `timeZone: 'UTC'`; Google omits `timeZone`. Non-UTC advisors therefore round-trip with an hour shift.

**Goal:** Patch the existing remote event when a mirrored advisory meeting changes, and persist IANA timezone on create and update so wall-clock times survive the round-trip. Two-way sync is explicitly not in this slice.

---

## Target users / ICP roles

- **Advisors** using Google Calendar or Microsoft 365 whose local timezone is not UTC.
- **Clients / invitees** who must see a single, current event (correct title, time, location, join URL).
- **Internal:** platform / calendar integration owners consuming `CalendarProvider`.

End-user UX is unchanged except that remote calendars stay correct after an advisory edit.

---

## Scope

In:

- `updateEvent` on the Google and Microsoft `CalendarProvider` implementations.
- Advisory meeting patch path: if a remote event id already exists, call `updateEvent`; never create a second event for the same meeting.
- Thread IANA timezone through `CalendarEventInput` on **create and update** (fix Microsoft UTC hardcode; stop omitting timezone on Google).
- Tests for patch idempotency and timezone round-trip.

Out of this slice: inbound calendar webhooks, remote-to-advisory writes, attendee sync, recurrence, and any other provider methods.

---

## Functional requirements

### 1. Provider: `updateEvent`

- Add `updateEvent` to `CalendarProvider` and implement it for Google Calendar and Microsoft Graph.
- Input: existing remote event id + the same fields used on create (`CalendarEventInput`: title, start, end, location, join URL, timezone).
- Semantics: patch/replace those fields on the existing event; do not create a new event id.
- Missing / already-deleted remote event: fail in a way the advisory patch path can distinguish from a generic provider error (so it does not silently duplicate). Do not invent a create-on-miss fallback in this P1.
- Auth, calendar selection, and error mapping follow the P0 create/delete patterns.

### 2. Advisory remirror on patch

- On advisory meeting update, if a stored remote event id exists for that provider, call `updateEvent` with the new title, start, end, location, and join URL.
- Do **not** call `createEvent` when a remote id is present.
- Fields that did not change may still be sent; the remote event must end equal to the advisory record.
- Cancel / delete remains P0 `deleteEvent`. Create-without-remote-id remains P0 `createEvent`.
- Remirror is outbound only (advisory → provider).

### 3. Timezone-preserving writes

- `CalendarEventInput` includes an IANA timezone (e.g. `America/Los_Angeles`) sourced from the advisor (or meeting) timezone.
- Google: send that timezone with start/end (do not omit `timeZone`).
- Microsoft: send that timezone; **stop hardcoding** `timeZone: 'UTC'`.
- Instants stored internally stay correct; wall-clock times on the remote event must match the advisor’s zone with no hour shift.
- Applies to both `createEvent` (fix P0 gap) and `updateEvent`.

### 4. Tests

- **Patch idempotency:** updating title/time/location/join URL on a meeting that already has a remote id results in exactly one `updateEvent` and zero `createEvent`; a second identical patch does not create a duplicate remote event.
- **Timezone:** create and update with a non-UTC IANA zone; provider payloads include that zone; reconstructed wall-clock time matches input (no UTC-forced shift). Cover Google and Microsoft.
- Provider unit/contract tests for `updateEvent` success and “remote event missing” failure.

---

## Acceptance criteria

1. `CalendarProvider` defines `updateEvent`; Google and Microsoft implement it; it mutates the existing remote event and does not allocate a new id.
2. Changing an advisory meeting’s title, start/end, location, or join URL patches the existing Google/Microsoft event when a remote id is stored; the provider calendar shows one event with the new values.
3. The same patch path never calls `createEvent` when a remote id is present (no duplicates).
4. Create and update send the advisor’s IANA timezone to both providers. Microsoft no longer writes `timeZone: 'UTC'`. Google no longer omits `timeZone`.
5. A meeting created or updated for a non-UTC advisor displays the same local date/time on the remote calendar as in the product (no hour shift).
6. Automated tests cover patch idempotency (Google + Microsoft) and timezone round-trip (Google + Microsoft, non-UTC IANA zone).
7. Cancel/delete and first-time create behavior from #2537 is unchanged. No two-way sync, webhooks, or remote-authoritative writes ship in this PR.

---

## Out of scope

- Two-way sync, calendar webhooks, or writing provider-side edits back to advisory meetings.
- Create-if-missing / recreate-after-delete fallback when `updateEvent` cannot find the remote event.
- Recurring events, attendee add/remove, reminders, conferencing provider changes beyond join URL, or extra calendars.
- Apple / other providers; `listUpcoming` / `freeBusy` changes.
- Advisor timezone account settings UI (consume existing IANA zone only).
- Replacing P0 create/cancel remirror.

## D-2 — `CalendarEventInput` (revised)

```ts
/** The data needed to create or update a calendar event for a meeting. */
export interface CalendarEventInput {
  title: string;
  description?: string;
  startISO: string;        // ISO-8601 instant (e.g. "2026-09-17T14:00:00.000Z")
  endISO: string;          // ISO-8601 instant
  attendeeEmails?: string[];
  joinUrl?: string;
  location?: string;       // NEW — physical / named location; falls back to joinUrl when absent
  timezone: string;        // NEW — IANA zone, e.g. "America/Los_Angeles"; callers pass "UTC" when unknown
}
```

**Rationale for `timezone: string` (not optional):** The PM lock mandates "missing → send `UTC` explicitly on both providers." Making the field required at the type level enforces that callers choose a zone — they cannot forget. The existing call site (`meetingRoutes.ts` create path) reads `userAvailability.timezone` and passes it; if that value is `null`/`undefined`, the caller passes `'UTC'`. This is a one-line guard at the call site, not a provider concern.

**Rationale for `location?: string`:** P0 sends `joinUrl` as the event location on both providers. This works but conflates the meeting link with a physical/named location. Adding a separate `location` field lets the advisory patch pass `meetings.location` when set. The provider `createEvent`/`updateEvent` bodies use `location ?? joinUrl` — so existing P0 create behavior is unchanged when `location` is not passed.

## D-3 — `CalendarProvider` interface (revised)

```ts
export interface CalendarProvider {
  readonly name: CalendarProviderName;
  createEvent(accessToken: string, calendarId: string, input: CalendarEventInput):
    Promise<{ eventId: string; htmlLink?: string }>;
  updateEvent(accessToken: string, calendarId: string, eventId: string, input: CalendarEventInput):
    Promise<{ htmlLink?: string }>;   // NEW — mutates existing event; returns updated htmlLink
  deleteEvent(accessToken: string, calendarId: string, eventId: string): Promise<void>;
  listUpcoming(accessToken: string, calendarId: string, opts: { accountEmail?: string; limit?: number; timeMinISO: string }):
    Promise<Array<{ id: string; title: string; startISO: string; endISO: string; htmlLink?: string }>>;
  freeBusy(accessToken: string, calendarId: string, opts: { accountEmail?: string; timeMinISO: string; timeMaxISO: string }):
    Promise<Array<{ startISO: string; endISO: string }>>;
}
```

**Return type of `updateEvent`:** Returns `{ htmlLink?: string }`. It does **not** return `eventId` — the id is the input, proving the same event was mutated. The `htmlLink` MAY change after an update (e.g. Google generates a new link on certain field changes), so we return it and allow the advisory path to overwrite `meetings.calendar_html_link` if present.

## D-4 — Distinguishable miss: `CalendarEventNotFoundError`

New in `calendarProviders.ts`, exported:

```ts
export class CalendarEventNotFoundError extends Error {
  constructor(
    public readonly provider: CalendarProviderName,
    public readonly eventId: string,
    public readonly httpStatus: number,
    bodySnippet: string,
  ) {
    super(`Calendar event not found (${provider}): ${eventId} — HTTP ${httpStatus}`);
    this.name = 'CalendarEventNotFoundError';
  }

  /** Type-safe predicate — use instead of instanceof across module boundaries. */
  static is(err: unknown): err is CalendarEventNotFoundError {
    return err instanceof Error && err.name === 'CalendarEventNotFoundError';
  }
}
```

**Detection points:**

- **Google Calendar:** `jsonFetch` receives HTTP 404. Before the generic throw in `jsonFetch`, the `updateEvent` Google implementation checks `res.status === 404` and throws `CalendarEventNotFoundError`.
- **Microsoft Graph:** Same — HTTP 404 on `PATCH /v1.0/me/events/{id}`.

Because `jsonFetch` throws on any non-OK status, the `updateEvent` implementations **bypass `jsonFetch`** for the PATCH call and use raw `fetch` + status check, constructing `CalendarEventNotFoundError` on 404 and falling through to `jsonFetch`-style generic errors on other statuses. Alternatively (and preferred for minimal diff): wrap the `jsonFetch` call in a try/catch, check if the caught error message starts with `"Calendar API 404"`, and re-throw as `CalendarEventNotFoundError`. This avoids duplicating the response-text logic.

**Preferred pattern (no raw-fetch bypass):**

```ts
// Inside Google updateEvent:
try {
  await jsonFetch(url, { method: 'PATCH', ... });
} catch (err) {
  if (err instanceof Error && err.message.startsWith('Calendar API 404')) {
    throw new CalendarEventNotFoundError('google', eventId, 404, err.message);
  }
  throw err; // re-throw generic
}
```

## D-6 — `updateMeetingEvent` in `calendarService.ts`

Placed immediately after `deleteMeetingEvent`, same module, same import surface:

```ts
/**
 * Patch an already-mirrored advisory meeting on the advisor's connected calendar.
 *
 * Contract (R-4): NEVER block the product meeting update. This function is
 * fire-and-forget — it swallows errors after reporting them. The advisory row
 * remains the source of truth.
 *
 * On a distinguishable 404 miss (CalendarEventNotFoundError): the stored
 * calendar_event_id is left as-is (do NOT null it — R-3). On other errors
 * the id is also left alone; retry / warning UX is #2623.
 */
export async function updateMeetingEvent(
  db: Db,
  env: Env,
  tenantId: number,
  userId: number,
  input: CalendarEventInput & { eventId: string; provider: CalendarProviderName },
): Promise<{ htmlLink?: string } | null> {
  const conn = await getConnectionForUser(db, tenantId, userId, input.provider);
  if (!conn) return null;
  const token = await freshAccessToken(db, env, conn);
  if (!token) return null;
  const p = getCalendarProvider(input.provider);
  if (!p) return null;
  try {
    return await p.updateEvent(token, conn.calendarId, input.eventId, input);
  } catch (error) {
    if (CalendarEventNotFoundError.is(error)) {
      // R-3: distinguishable miss — do NOT create, do NOT null the id.
      reportCaughtError(error, {
        source: 'application/calendar/calendarService.ts',
        operation: 'updateMeetingEvent',
        note: 'remote event not found; stored id preserved',
      });
      return null;
    }
    reportCaughtError(error, {
      source: 'application/calendar/calendarService.ts',
      operation: 'updateMeetingEvent',
    });
    return null;
  }
}
```

**Key design decisions:**

- Takes `eventId` and `provider` alongside `CalendarEventInput` — the advisory route already has these from `meetings.calendar_event_id` and `meetings.calendar_provider`.
- Returns `{ htmlLink?: string } | null` — `null` when no connection, no token, or error; `{ htmlLink }` on success so the route can overwrite `meetings.calendar_html_link`.
- On `CalendarEventNotFoundError`: specifically does **not** null the stored id (R-3). The error is reported for observability but swallowed.

## D-7 — Advisory PATCH remirror in `meetingRoutes.ts`

The existing `PATCH /api/meetings/:id` handler writes `title`, `scheduledAt`, `durationMinutes`, `videoEnabled`. The Design adds a **post-update remirror step** after the meeting row is written but before the response is sent.

**Pseudocode (not a diff; the Developer writes the real code):**

```ts
// After the meeting UPDATE succeeds, before responding:

const meeting = updatedRow; // the row just written

// Determine if this is an advisory meeting with an existing mirror
if (
  meeting.kind === 'advisory' &&                    // #2536 will add this kind
  meeting.calendarEventId &&                         // has a remote id
  meeting.calendarProvider                          // knows which provider
) {
  // Gather advisor timezone
  const avail = await attendeeAvailability.getUserAvailability(db, tenantId, meeting.organizerId);
  const timezone = avail?.timezone || 'UTC';

  // Build CalendarEventInput
  const input: CalendarEventInput = {
    title: meeting.title,
    startISO: meeting.scheduledAt.toISOString(),
    endISO: new Date(meeting.scheduledAt.getTime() + meeting.durationMinutes * 60_000).toISOString(),
    joinUrl: `${env.APP_URL}/meetings?join=${meeting.id}`,
    location: meeting.location || undefined,
    timezone,
  };

  // Fire-and-forget: update the remote event
  const result = await updateMeetingEvent(db, env, tenantId, meeting.organizerId, {
    ...input,
    eventId: meeting.calendarEventId,
    provider: meeting.calendarProvider as CalendarProviderName,
  });

  // If htmlLink changed, persist it (non-blocking)
  if (result?.htmlLink) {
    await db.query(
      `UPDATE meetings SET calendar_html_link = $1 WHERE id = $2`,
      [result.htmlLink, meeting.id],
    ).catch(() => { /* non-critical */ });
  }
}
```

**R-6 trigger-field check:** The Design recommends the Developer check whether any trigger field actually changed before calling `updateMeetingEvent`. The simplest correct approach: compare the PATCH body's `title`/`scheduledAt`/`durationMinutes`/`location` against the pre-update meeting row. If none of the trigger fields changed, skip the remirror. This avoids a no-op provider call.

**Dependency on #2536:** `meeting.kind` and the `KINDS` constant including `'advisory'` are expected from #2536 (which adds the `advisory` meeting kind). If #2536 has not landed when the Developer picks this up, they should either stack on #2536's branch or use the column/constant once merged. The Design assumes `meetings.kind` exists with value `'advisory'`.

## D-8 — Timezone sourcing

The source of the advisor's IANA timezone is:

```
userAvailability.timezone ← attendeeAvailability.getUserAvailability(db, tenantId, organizerUserId)
```

This is the same column returned by `GET /api/meetings/availability/me` and stored via `PUT`. Its default is `'UTC'` (set at row-creation time, per existing schema).

**Flow:**

1. Advisory meeting PATCH → read `meeting.organizerId`
2. `getUserAvailability(db, tenantId, organizerId)` → `{ timezone, windows }`
3. `timezone ?? 'UTC'` → `CalendarEventInput.timezone`
4. Providers embed it as `start.timeZone` / `end.timeZone`

**No new column, no settings UI, no migration.** The column already exists and is already populated.
