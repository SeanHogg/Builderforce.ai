# PRD: P1 — Remirror advisory calendar events on patch + timezone-preserving provider writes

**Parent:** #2532  
**Depends on:** #2537 (P0 — create/cancel mirror only)  
**Priority:** P1

---

## Problem & Goal

P0 (#2537) mirrors advisory meetings to Google and Microsoft calendars on create and cancel only. `CalendarProvider` (`api/src/application/calendar/calendarProviders.ts`) exposes `createEvent`, `deleteEvent`, `listUpcoming`, and `freeBusy` — there is no `updateEvent`.

When an advisor edits title, time, location, or join URL, the remote event is left stale. Re-running create produces a duplicate. Microsoft `createEvent` hardcodes `timeZone: 'UTC'`; Google omits `timeZone`. Non-UTC advisors therefore round-trip with an hour shift.

**Goal:** Patch the existing remote event when a mirrored advisory meeting changes, and persist IANA timezone on create and update so wall-clock times survive the round-trip. Two-way sync is explicitly not in this slice.

---

## Target users / ICP roles

- **Advisors** using Google Calendar or Microsoft 365 whose local timezone is not UTC.
- **Clients / invitees** who must see a single, current event (correct title, time, location, join URL).
- **Internal:** platform / calendar integration owners consuming `CalendarProvider`.

End-user UX is unchanged except that remote calendars stay correct after an advisory edit.

---

## Scope

In:

- `updateEvent` on the Google and Microsoft `CalendarProvider` implementations.
- Advisory meeting patch path: if a remote event id already exists, call `updateEvent`; never create a second event for the same meeting.
- Thread IANA timezone through `CalendarEventInput` on **create and update** (fix Microsoft UTC hardcode; stop omitting timezone on Google).
- Tests for patch idempotency and timezone round-trip.

Out of this slice: inbound calendar webhooks, remote-to-advisory writes, attendee sync, recurrence, and any other provider methods.

---

## Functional requirements

### 1. Provider: `updateEvent`

- Add `updateEvent` to `CalendarProvider` and implement it for Google Calendar and Microsoft Graph.
- Input: existing remote event id + the same fields used on create (`CalendarEventInput`: title, start, end, location, join URL, timezone).
- Semantics: patch/replace those fields on the existing event; do not create a new event id.
- Missing / already-deleted remote event: fail in a way the advisory patch path can distinguish from a generic provider error (so it does not silently duplicate). Do not invent a create-on-miss fallback in this P1.
- Auth, calendar selection, and error mapping follow the P0 create/delete patterns.

### 2. Advisory remirror on patch

- On advisory meeting update, if a stored remote event id exists for that provider, call `updateEvent` with the new title, start, end, location, and join URL.
- Do **not** call `createEvent` when a remote id is present.
- Fields that did not change may still be sent; the remote event must end equal to the advisory record.
- Cancel / delete remains P0 `deleteEvent`. Create-without-remote-id remains P0 `createEvent`.
- Remirror is outbound only (advisory → provider).

### 3. Timezone-preserving writes

- `CalendarEventInput` includes an IANA timezone (e.g. `America/Los_Angeles`) sourced from the advisor (or meeting) timezone.
- Google: send that timezone with start/end (do not omit `timeZone`).
- Microsoft: send that timezone; **stop hardcoding** `timeZone: 'UTC'`.
- Instants stored internally stay correct; wall-clock times on the remote event must match the advisor’s zone with no hour shift.
- Applies to both `createEvent` (fix P0 gap) and `updateEvent`.

### 4. Tests

- **Patch idempotency:** updating title/time/location/join URL on a meeting that already has a remote id results in exactly one `updateEvent` and zero `createEvent`; a second identical patch does not create a duplicate remote event.
- **Timezone:** create and update with a non-UTC IANA zone; provider payloads include that zone; reconstructed wall-clock time matches input (no UTC-forced shift). Cover Google and Microsoft.
- Provider unit/contract tests for `updateEvent` success and “remote event missing” failure.

---

## Acceptance criteria

1. `CalendarProvider` defines `updateEvent`; Google and Microsoft implement it; it mutates the existing remote event and does not allocate a new id.
2. Changing an advisory meeting’s title, start/end, location, or join URL patches the existing Google/Microsoft event when a remote id is stored; the provider calendar shows one event with the new values.
3. The same patch path never calls `createEvent` when a remote id is present (no duplicates).
4. Create and update send the advisor’s IANA timezone to both providers. Microsoft no longer writes `timeZone: 'UTC'`. Google no longer omits `timeZone`.
5. A meeting created or updated for a non-UTC advisor displays the same local date/time on the remote calendar as in the product (no hour shift).
6. Automated tests cover patch idempotency (Google + Microsoft) and timezone round-trip (Google + Microsoft, non-UTC IANA zone).
7. Cancel/delete and first-time create behavior from #2537 is unchanged. No two-way sync, webhooks, or remote-authoritative writes ship in this PR.

---

## Out of scope

- Two-way sync, calendar webhooks, or writing provider-side edits back to advisory meetings.
- Create-if-missing / recreate-after-delete fallback when `updateEvent` cannot find the remote event.
- Recurring events, attendee add/remove, reminders, conferencing provider changes beyond join URL, or extra calendars.
- Apple / other providers; `listUpcoming` / `freeBusy` changes.
- Advisor timezone account settings UI (consume existing IANA zone only).
- Replacing P0 create/cancel remirror.

### R-1 — `updateEvent` on `CalendarProvider` (Google + Microsoft)

**Given** `CalendarProvider` in `api/src/application/calendar/calendarProviders.ts`  
**When** this slice ships  
**Then** the interface defines `updateEvent`, and both the Google Calendar and Microsoft Graph implementations implement it.

- **Input:** existing remote event id + the same `CalendarEventInput` fields used on create: title, start, end, location, join URL, IANA timezone (R-5).
- **Semantics:** patch/replace those fields on the **existing** remote event. MUST NOT allocate a new remote event id.
- **Auth / calendar selection / error mapping:** follow P0 create/delete (`calendar_connections`). Do **not** require a new OAuth consent or scope; reuse the P0 connection.
- `listUpcoming` and `freeBusy` are unchanged. Apple / other providers are out of scope.

### R-2 — Advisory remirror on patch; never create when a remote id is stored

**Given** an advisory meeting (`kind = advisory`) that already has a stored remote event id (`meetings.calendar_event_id` + `meetings.calendar_provider`)  
**When** title, start, end, location, or join URL is patched  
**Then** the patch path MUST call `updateEvent` with the new values and MUST NOT call `createEvent`.

- Applies to **every** advisory update in the advisor tenant (in-page tenant edit, public `/book/{token}` follow-on patch if any, agent/system PATCH) — same “every advisory path” rule as #2537 R-5, for update.
- Fields that did not change MAY still be sent; after the call the remote event MUST equal the advisory record for title, start, end, location, and join URL.
- Cancel / delete remains P0 `deleteEvent`. Create **without** a remote id remains P0 `createEvent`.
- Remirror is outbound only (advisory → provider). No inbound / webhook / remote-authoritative writes.

### R-3 — Distinguishable miss; no create-on-miss; do not clear the stored id

**Given** `updateEvent` cannot find the remote event (already deleted / unknown id)  
**When** the advisory patch path handles that failure  
**Then** the failure MUST be distinguishable from a generic provider error.

- This P1 MUST NOT invent a create-on-miss / recreate-after-delete fallback.
- The stored `calendar_event_id` MUST be left as-is (do **not** null it on miss). Clearing it would let a later patch take the P0 create path and duplicate the remote event.
- Retry, warning UX, and reconnect backfill are **#2623**, not this ticket.

### R-4 — Meeting patch is never blocked by calendar

**Given** `updateEvent` fails (expired token, network, distinguishable 404 miss, provider 5xx)  
**When** the advisor (or any advisory path) patches the meeting  
**Then** the product meeting update still succeeds. The advisory row remains source of truth (same contract as #2537 R-7).

Do not invent a user-facing retry/warning in this slice (#2623).

### R-5 — IANA timezone on `CalendarEventInput` for create AND update

**Given** a create or update of a mirrored advisory event  
**When** the provider payload is written  
**Then** `CalendarEventInput` includes an IANA timezone (e.g. `America/Los_Angeles`).

- **Source:** the existing advisor (or meeting) IANA timezone already stored in product. Architect names the field. Do **not** add an advisor timezone settings UI.
- **Whose zone:** the **advisor’s** zone, not the visitor’s browser zone.
- **Missing zone:** if none is set, send `UTC` **explicitly** (today’s Microsoft behavior, applied to both providers so Google also receives a zone).
- **Google:** send that timezone with start/end. Do **not** omit `timeZone`.
- **Microsoft:** send that timezone. **Stop hardcoding** `timeZone: 'UTC'`.
- Instants stored internally stay correct; wall-clock times on the remote event MUST match the advisor’s zone with no hour shift.
- Applies to both `createEvent` (fixes the P0 gap) and `updateEvent`.

### R-6 — Trigger fields

Remirror via `updateEvent` when any of these change on an already-mirrored advisory meeting:

- title
- start (`scheduledAt`)
- end (including a duration change that moves end)
- location
- join URL

A no-op PATCH that does not change those fields is not required to call the provider; if it does, it still MUST NOT `createEvent`. Changing other meeting fields (internal notes, metadata not mapped into the P0 remote event) does not require a remirror.

### R-7 — Unchanged P0 create/cancel; no two-way sync

Cancel/delete and first-time create behavior from #2537 is unchanged. This PR MUST NOT ship:

- two-way sync, calendar webhooks, or writing provider-side edits back to advisory meetings
- attendee add/remove
- recurrence
- extra calendars / conferencing-provider changes beyond join URL
- Apple / other providers
- changes to `listUpcoming` / `freeBusy`

`packages/creation-canvas-contract` canvas calendar helpers are a different surface and out of scope.

### R-8 — Tests

Automated tests MUST cover:

1. **Patch idempotency (Google + Microsoft):** updating title/time/location/join URL on a meeting that already has a remote id results in exactly one `updateEvent` and zero `createEvent` per patch; a second identical patch does not create a duplicate remote event.
2. **Timezone round-trip (Google + Microsoft):** create **and** update with a non-UTC IANA zone (at least `America/Los_Angeles`); provider payloads include that zone; reconstructed wall-clock time matches input (no UTC-forced shift).
3. **Provider contract:** `updateEvent` success (same remote id, mutated fields) and “remote event missing” distinguishable failure.

### R-9 — Sibling carve-out (#2623)

This ticket does **not**:

- backfill mirrors when an advisor connects a calendar after meetings already exist
- delete remote events or clear mapping on disconnect
- persist last-error / retry
- show a calendar-sync warning on the meeting

Those are #2623.
