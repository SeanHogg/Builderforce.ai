# PRD: Authenticated Setup as a Canvas Destination

**Status:** WIP  
**Related:** PRD 21 (Destinations / Canvas objects)  
**Decision:** Authenticated setup is a destination/Canvas object. It is not a new chrome-ful app.

## Problem & Goal

Authenticated setup is currently at risk of being built as a standalone, chrome-ful application: its own shell, navigation, layout chrome, and routing root. That splits first-run and post-auth configuration from the product’s destination model, duplicates chrome, and forces a later migration onto Canvas.

PRD 21 defines destinations as first-class Canvas objects. Authenticated setup must use that model from day one.

**Goal:** Ship authenticated setup as a Canvas destination object that opens inside the existing host chrome, follows Canvas object lifecycle and navigation, and never introduces a second application shell.

## Target users / ICP roles

- **End users** completing first-run or post-auth setup (workspace, identity, integrations, permissions, defaults).
- **Admins / owners** finishing org-level setup after authentication.
- **Downstream product, design, and eng agents** implementing setup; they must treat it as a destination, not an app.

## Scope

In scope:

- Model authenticated setup as a Canvas destination / object per PRD 21.
- Open setup as a destination after successful authentication when setup is incomplete or required.
- Re-enter setup later as the same destination (deep link, resume, admin revisit).
- Use host Canvas chrome only (existing app shell, nav, and object chrome).
- Persist setup state on the destination object (progress, required vs optional steps, completion).
- Route to, focus, background, and close setup like any other destination.
- Handoff from setup completion to the user’s next destination without a shell swap.
- Auth itself remains the auth boundary; setup begins only after a valid session.

## Functional requirements

1. **Object type:** Authenticated setup is a Canvas destination object (same class of object as other PRD 21 destinations), not an application, not a modal-only flow, and not a parallel shell.
2. **Host chrome:** Setup renders in the Canvas host. No unique top nav, sidebar, or app frame. No second router root or layout tree that impersonates an app.
3. **Entry:** After authentication, if setup is required or incomplete, the host opens the setup destination. If setup is complete, the host does not open it by default.
4. **Re-entry:** The setup destination is addressable (destination id / route equivalent). Users with permission can reopen it without a new app.
5. **Lifecycle:** Create, open, focus, persist, complete, dismiss, and destroy follow Canvas object rules. Refresh or session restore returns the user to the same destination and step state.
6. **State:** Setup progress lives on the object (step completion, validation errors, draft inputs). Completion is a property of the destination, visible to the host for gating.
7. **Gating:** Incomplete required setup may block other destinations. Optional steps must not trap the user. Gating is host/destination policy, not a separate app lock screen.
8. **Exit:** On required completion (or allowed skip), the host closes or backgrounds the setup destination and opens the default next destination. No full-app reload or chrome swap.
9. **Permissions:** Who can view or edit setup is destination-level ACL, consistent with other Canvas objects.
10. **Auth boundary:** Unauthenticated users never see setup. Token expiry returns the user to auth, then back to the same setup destination when the session is valid.

## Acceptance criteria

- Setup is registered and opened as a PRD 21 destination/Canvas object.
- No dedicated chrome-ful app, standalone shell, or duplicate nav exists for setup.
- Post-auth, incomplete required setup opens the setup destination inside host chrome.
- Completed setup does not auto-open; the host continues to the normal next destination.
- Deep link / destination id reopens the same setup object and restores step state.
- Refresh mid-setup restores the setup destination, not a blank app or a different shell.
- Completing setup transitions to the next destination without replacing host chrome.
- Setup cannot be launched without a valid authenticated session.
- Required vs optional steps honor gating without introducing a second product surface.
- QA can complete, resume, skip (where allowed), and re-enter setup entirely within Canvas.

## Out of scope

- Redesign of authentication (login, SSO, MFA, session issuance).
- New product chrome, a setup-only application, or a separate design system shell.
- Unauthenticated onboarding or marketing/pre-auth websites.
- Changing the PRD 21 destination/Canvas object model.
- Non-setup destinations, except as the post-completion handoff target.
- Billing, viral invite growth loops, or unrelated first-run experiments not modeled as this destination.
- Mobile-native or third-party app shells.

## Requirements

Authenticated setup is **not a product**. It is a **use of an existing destination** after a valid session. The first consumer is ticket **#2527** (advisor mode on the talent listing). Later authenticated-setup flows reuse this contract by opening an already-registered destination — they do not mint a setup app.

### R-0 Binding (non-negotiable)

Live primitives that already own this space. Downstream design and implementation **extend these**; they do not fork them.

| Concern | Existing primitive | Location |
|---|---|---|
| Destination registry | `NAV_GROUPS`, `FOR_HIRE_NAV_GROUPS`, `FREELANCER_NAV_GROUPS`, `SALES_NAV_GROUPS` | `frontend/src/lib/navGroups.ts` |
| Derived destination list | `listDestinations()` reads NAV_GROUPS only | `frontend/src/lib/destinations/registry.ts` |
| Registry guard | Adding a product destination means adding a group in NAV_GROUPS | `frontend/scripts/check-destinations.mjs` |
| Host chrome | AppShell. Footer-only paths are auth, legal, and the tenant picker — not product destinations | `frontend/src/lib/shellRouting.ts` (`FOOTER_ONLY_PATHS`) |
| Post-auth workspace pick | `/tenants` (footer-only, **not** a destination, **not** a model for setup chrome) | `frontend/src/app/tenants/page.tsx` |
| Account destination | id `settings`, href `/settings` (Account / Workspace / Integrations / API keys as route tabs) | NAV_GROUPS + FREELANCER_NAV_GROUPS |
| Talent listing destination | id `freelancer-profile`, href `/freelancer/profile` | `FOR_HIRE_NAV_GROUPS` |
| Account-type nav | `navGroupsForAccountType(isFreelancer, availableForHire, isSales)` | `frontend/src/lib/navGroups.ts` |
| Canvas object kinds | spec data (`specObjects`). **Do not** add `advisory` or `setup` | PEOPLE_OBJECT_KINDS unchanged (parent #2527) |
| Canvas surfaces | `CanvasSurfaceId`. **Do not** add a setup surface | `frontend/src/lib/canvasSurfaces.ts` |
| Auth boundary | `/login` then session; unauthenticated users never see in-app destinations | `frontend/src/app/login/` |

**Forbidden on this ticket (and on #2527 P0):** a new NAV_GROUPS id for setup/onboarding/advisors; a new `CanvasSurfaceId`; a new `ShellKind`; extending `FOOTER_ONLY_PATHS` with a setup path; `/setup`, `/onboarding`, `/advisors`, `/advisors/setup`; `advisors` as a `MARKETPLACE_LISTING_KINDS` value; `advisory` on PEOPLE_OBJECT_KINDS; cloning `/tenants` as a setup shell.

`category=advisors` remains a talent **filter** on `/marketplace?family=talent` (PRD 26). It is not a destination and not a listing kind.

### R-1 Object type

The authenticated-setup **experience** is the existing talent-listing destination acting on the existing talent/listing object.

- **Destination id:** `freelancer-profile`
- **Route:** `/freelancer/profile`
- **Canvas object:** the existing freelancer profile / talent listing (same class of object as other listing/people objects). Not an application, not a modal-only flow, not a parallel shell, not a new object kind.

Setup fields (#2527) live **on that listing**: advisor toggle, expertise, industries, languages, methods (video / phone / email / in-person), stages (start / grow / exit), session length, price (`0` = volunteer), location, confidentiality default.

Builders who opted in to being hired already receive `FOR_HIRE_NAV_GROUPS` via `navGroupsForAccountType(..., availableForHire=true)`, so the same destination is in their nav. Freelancer accounts already have it in `FREELANCER_NAV_GROUPS`.

### R-2 Host chrome

Setup renders inside AppShell using the nav already returned by `navGroupsForAccountType`.

- No unique top nav, sidebar, or app frame for setup.
- No second router root or layout tree that impersonates an app.
- Do **not** put setup on `FOOTER_ONLY_PATHS` (that would strip chrome and impersonate `/login` or `/tenants`).
- `/tenants` stays the post-auth **workspace** picker. Setup is a **destination** after a tenant (or a tenantless freelancer session) is established.

### R-3 Entry (post-auth)

Existing sequence; do not invent a gate app:

1. Unauthenticated → `/login` (auth redesign is out of scope).
2. Authenticated builder with no tenant → `/tenants` (existing).
3. Valid session **and** incomplete **required** advisor setup → host **opens** `freelancer-profile` (`/freelancer/profile`) inside host chrome.
4. Setup complete → host does **not** open it by default; continue to the account’s normal next destination (builder: last/default from NAV_GROUPS; freelancer: `freelancer-dashboard`).

**Required vs optional (first consumer #2527):** “Required” means the user has turned the advisor toggle **on** and one or more required advisor fields are invalid or empty. Optional advisor fields never trap. A user who has not opted in is **not** in setup and must not be forced onto this destination.

### R-4 Re-entry

The setup destination is already addressable.

- Destination id `freelancer-profile` / route `/freelancer/profile`.
- Deep link reopens the same listing object and restores field / step state persisted on that object.
- The listing owner (destination-level ACL, same as other listing objects) can reopen without a new app.

Do not invent `/setup`, `/onboarding`, `/advisors/setup`, or a query-only pseudo-app (`?setup=1` as a parallel surface).

### R-5 Lifecycle

Create, open, focus, persist, complete, dismiss, and destroy follow the Canvas object / destination rules already used by `/freelancer/profile`.

- Refresh or session restore returns the user to this destination and the listing’s stored field state — not a blank app, not a different shell, not `/tenants` unless the user actually has no tenant.
- Focus / background / close behave like any other destination (rail + AppShell).
- Unpublishing or destroying the listing is listing lifecycle, not a setup-app uninstall.

### R-6 State

Setup progress lives on the **talent listing object**, not in a parallel setup document, not in localStorage-only wizard state, not on a new canvas kind.

Minimum state on the listing:

- Advisor mode toggle (on/off).
- The #2527 field set (expertise, industries, languages, methods, stages, session length, price including `0`, location, confidentiality default).
- Per-field drafts and validation errors.
- Completion, either stored or **derived**: toggle off ⇒ not in setup; toggle on ⇒ complete iff every required field is valid.

Completion is visible to the host for gating (R-7).

### R-7 Gating

- Incomplete **required** setup may keep the user on `freelancer-profile` and may block opening other destinations until required fields are valid **or** the user turns the advisor toggle off.
- Optional steps must not trap.
- Gating is host / destination policy in AppShell / the existing route guard — **not** a separate lock screen, **not** a footer-only setup page.
- Freelancer route guard already uses `FREELANCER_ALLOWED_PREFIXES` (`/freelancer`) + `FREELANCER_ALLOWED_EXACT` (`/settings`, `/security`). Do **not** add a setup prefix.
- Advisor setup must not require a second opt-in nav beyond `availableForHire` / freelancer account type.

### R-8 Exit / handoff

On required completion (or allowed skip / toggle off):

- Host closes or backgrounds `freelancer-profile`.
- Opens the account’s default next destination.
- **No** full-app reload, **no** chrome swap, **no** bounce through `/tenants` unless the user actually has no tenant.

### R-9 Permissions

Who can view or edit setup = who can view or edit the talent listing (destination-level ACL). No setup-specific ACL model and no setup-specific role.

### R-10 Auth boundary

- Unauthenticated users never see setup (existing login gate).
- Token expiry returns the user to `/login`, then back to `/freelancer/profile` (the same destination) when the session is valid.
- Auth itself remains the auth boundary; setup begins only after a valid session.

### R-11 Locales and theme

Setup field copy uses the existing **five** locale catalogs and **both** themes. No setup-only design-system shell (parent #2527).

### R-12 Explicit non-requirements

Must not ship on this ticket:

- New destination id in NAV_GROUPS for “setup”, “onboarding”, or “advisors”.
- New `CanvasSurfaceId` or new `ShellKind`.
- `advisory` on PEOPLE_OBJECT_KINDS.
- `advisors` as a `MARKETPLACE_LISTING_KINDS` value; no `/advisors` route.
- Dedicated chrome-ful app, standalone shell, or duplicate nav.
- Replacing or restyling `/tenants` as setup.
- Unauthenticated onboarding or marketing/pre-auth websites.
- Billing, viral invite growth loops, or unrelated first-run experiments.
- Changing the PRD 21 destination / Canvas object model.
- Mobile-native or third-party app shells.
