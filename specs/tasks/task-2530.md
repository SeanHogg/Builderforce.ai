# PRD: Authenticated Setup as a Canvas Destination

**Status:** WIP  
**Related:** PRD 21 (Destinations / Canvas objects)  
**Decision:** Authenticated setup is a destination/Canvas object. It is not a new chrome-ful app.

## Problem & Goal

Authenticated setup is currently at risk of being built as a standalone, chrome-ful application: its own shell, navigation, layout chrome, and routing root. That splits first-run and post-auth configuration from the product’s destination model, duplicates chrome, and forces a later migration onto Canvas.

PRD 21 defines destinations as first-class Canvas objects. Authenticated setup must use that model from day one.

**Goal:** Ship authenticated setup as a Canvas destination object that opens inside the existing host chrome, follows Canvas object lifecycle and navigation, and never introduces a second application shell.

## Target users / ICP roles

- **End users** completing first-run or post-auth setup (workspace, identity, integrations, permissions, defaults).
- **Admins / owners** finishing org-level setup after authentication.
- **Downstream product, design, and eng agents** implementing setup; they must treat it as a destination, not an app.

## Scope

In scope:

- Model authenticated setup as a Canvas destination / object per PRD 21.
- Open setup as a destination after successful authentication when setup is incomplete or required.
- Re-enter setup later as the same destination (deep link, resume, admin revisit).
- Use host Canvas chrome only (existing app shell, nav, and object chrome).
- Persist setup state on the destination object (progress, required vs optional steps, completion).
- Route to, focus, background, and close setup like any other destination.
- Handoff from setup completion to the user’s next destination without a shell swap.
- Auth itself remains the auth boundary; setup begins only after a valid session.

## Functional requirements

1. **Object type:** Authenticated setup is a Canvas destination object (same class of object as other PRD 21 destinations), not an application, not a modal-only flow, and not a parallel shell.
2. **Host chrome:** Setup renders in the Canvas host. No unique top nav, sidebar, or app frame. No second router root or layout tree that impersonates an app.
3. **Entry:** After authentication, if setup is required or incomplete, the host opens the setup destination. If setup is complete, the host does not open it by default.
4. **Re-entry:** The setup destination is addressable (destination id / route equivalent). Users with permission can reopen it without a new app.
5. **Lifecycle:** Create, open, focus, persist, complete, dismiss, and destroy follow Canvas object rules. Refresh or session restore returns the user to the same destination and step state.
6. **State:** Setup progress lives on the object (step completion, validation errors, draft inputs). Completion is a property of the destination, visible to the host for gating.
7. **Gating:** Incomplete required setup may block other destinations. Optional steps must not trap the user. Gating is host/destination policy, not a separate app lock screen.
8. **Exit:** On required completion (or allowed skip), the host closes or backgrounds the setup destination and opens the default next destination. No full-app reload or chrome swap.
9. **Permissions:** Who can view or edit setup is destination-level ACL, consistent with other Canvas objects.
10. **Auth boundary:** Unauthenticated users never see setup. Token expiry returns the user to auth, then back to the same setup destination when the session is valid.

## Acceptance criteria

- Setup is registered and opened as a PRD 21 destination/Canvas object.
- No dedicated chrome-ful app, standalone shell, or duplicate nav exists for setup.
- Post-auth, incomplete required setup opens the setup destination inside host chrome.
- Completed setup does not auto-open; the host continues to the normal next destination.
- Deep link / destination id reopens the same setup object and restores step state.
- Refresh mid-setup restores the setup destination, not a blank app or a different shell.
- Completing setup transitions to the next destination without replacing host chrome.
- Setup cannot be launched without a valid authenticated session.
- Required vs optional steps honor gating without introducing a second product surface.
- QA can complete, resume, skip (where allowed), and re-enter setup entirely within Canvas.

## Out of scope

- Redesign of authentication (login, SSO, MFA, session issuance).
- New product chrome, a setup-only application, or a separate design system shell.
- Unauthenticated onboarding or marketing/pre-auth websites.
- Changing the PRD 21 destination/Canvas object model.
- Non-setup destinations, except as the post-completion handoff target.
- Billing, viral invite growth loops, or unrelated first-run experiments not modeled as this destination.
- Mobile-native or third-party app shells.
