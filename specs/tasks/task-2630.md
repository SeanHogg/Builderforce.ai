# PRD: Campaign-RUN Intent Recognition (WIP)

## Problem & Goal

Users ask in natural language to start a marketing campaign (e.g. “I want to run a marketing campaign”, “connect my email and run a marketing campaign”). Downstream agents currently under-detect this as an execution request and over-route to campaign listing or browse flows.

**Goal:** Treat **campaign-RUN** as the primary intent. Classify list/browse as secondary so a user who wants to launch (and optionally connect email first) is routed into the run/connect path, not a list of existing campaigns.

## Target users / ICP roles

- Growth / lifecycle marketers launching email (and similar) campaigns
- Founders and operators on self-serve marketing tools
- Downstream routing, orchestration, and tool-calling agents that consume this intent

## Scope

- Natural-language intent recognition on the product’s conversation / command surface
- Primary class: **campaign-RUN** (start / launch / run a marketing campaign; may include connect-email as a prerequisite step)
- Secondary class: **list** (show / list / browse existing campaigns)
- Disambiguation when an utterance could match both; RUN wins
- Hand-off of a structured intent payload to downstream agents (intent, confidence, optional slots such as channel)

## Functional requirements

1. Detect campaign-RUN for explicit launch language: run, start, launch, create-and-run, send a campaign, “I want to run a marketing campaign”.
2. Detect campaign-RUN when connect-email (or equivalent channel connect) is bundled with run: “connect my email and run a marketing campaign”. Connect is a step, not a separate primary intent.
3. Detect list only when the user clearly wants inventory, not execution: list campaigns, show my campaigns, what campaigns do I have.
4. If RUN and list both fit, classify as campaign-RUN.
5. Emit a structured result: `intent` (`campaign_run` | `list` | other), `confidence`, and slots when present (`channel`, `connect_required`).
6. Do not require the user to name a specific campaign to classify RUN; unnamed “run a marketing campaign” is sufficient.
7. Keep classification independent of whether email is already connected; connection state is handled after intent.

## Acceptance criteria

- “I want to run a marketing campaign” → `campaign_run`.
- “Connect my email and run a marketing campaign” → `campaign_run` with connect-email treated as a prerequisite slot/step, not list.
- Near-paraphrases (start/launch/send a marketing campaign; run an email campaign) → `campaign_run`.
- “List my campaigns” / “show existing campaigns” → `list`.
- Ambiguous “campaigns” with run/launch verbs → `campaign_run`, not `list`.
- Downstream agents receive a stable intent name and can branch: RUN → connect (if needed) then launch flow; list → inventory flow.
- False routing of RUN utterances into list is treated as a defect.

## Out of scope

- Executing the campaign, sending email, or performing OAuth/email connect (recognition and routing only)
- Campaign content, audience, or schedule design
- Analytics, reporting, or pause/stop/edit of an in-flight campaign
- Multi-channel campaign types beyond what the utterance implies (no requirement to infer SMS/ads/etc. unless stated)
- Training data pipelines, model choice, or production ML ops
- Auth, billing, and compliance copy for email sending
- UI chrome for the list view or the run wizard beyond intent hand-off

### R-2 — Output contract (`CampaignIntentResult`)

```
{
  intent: 'campaign_run' | 'list' | 'other'
  confidence: number            // inclusive 0..1, finite, never omitted
```

### R-3 — Primary intent: `campaign_run`

Classify `campaign_run` when the utterance’s **goal** is to start, launch, send, run, kick off, or go live with a marketing / email / ads campaign.

Canonical positives — MUST be `campaign_run`, `confidence ≥ 0.8`:

1. `I want to run a marketing campaign` → `connect_requested=false`, no `channel`
2. `connect my email and run a marketing campaign` → `connect_requested=true`, `channel='email'`

Close paraphrases — MUST be `campaign_run`, `confidence ≥ 0.7`: launch / start / send / kick off / go live / fire off + (marketing | email | ads)? campaign. Match **intent**, not exact strings. Tolerate extra words and common typos of those verbs/nouns (`lanuch`, `kik off`, `campagin`). Missed RUN on the two canonicals is a **defect**.

### R-4 — Compound connect + run

If the same turn mentions connecting a channel **and** a run-class verb + campaign, classify `campaign_run`, **not** connect-only and **not** `list`.

- `connect_requested=true`; `channel` = the named channel.
- Connection is a **precondition slot**, not a competing primary intent.
- EMAIL (`canvas_add_inbox`, tenant-only) and SOCIAL connect tools are **downstream of** this label; this ticket does not call them.
- Guest vs tenant (`persistence` local vs server) SHALL NOT change the label. Canonical (2) is `campaign_run` on an anonymous board too. Whether the inbox tool is in the turn’s list is C0/C1, not a reason to relabel `list` or `other`.

### R-5 — Secondary intent: `list`

Classify `list` only when the utterance asks to show / list / browse / “what campaigns do I have” / “my campaigns” as inspection **and** no run-class verb (R-3) is present.

MUST be `list`, never `campaign_run`: `show my campaigns`, `list campaigns`, `list my campaigns`, `what campaigns do I have`.

`marketing.campaigns.list` (executive catalog / portfolio table) remains the **list** path. This classifier’s job is to **keep RUN off that path**. False RUN on pure list/inspect queries is a **defect**.

### R-6 — RUN wins (ranking)

If both list-like and run-like language appear in one turn, `intent` SHALL be `campaign_run`. List is never equal priority to RUN (PRD out-of-scope). There is no `list_and_run` value.

MUST: `list campaigns and then run one` → `campaign_run`. MUST: `show my campaigns and launch a new one` → `campaign_run`.

### R-7 — Connect-only, inspect-only, and non-run verbs are `other`

- Connect-only (`connect my email`, `connect Gmail`, `link my mailbox`) with **no** run/launch/send/kick off/go live language → `other`. SHALL NOT be `campaign_run`. `connect_requested` MAY be `true` with `intent: 'other'`.
- Draft / edit / pause / stop / analytics / report / “how do campaigns work” / “what is a campaign” → `other` unless a clear run-class verb is also present.
- When unsure between `campaign_run` and `other`, choose `other`. When unsure between `campaign_run` and `list`, choose `campaign_run` **only** if a run-class verb is present (R-6); otherwise `list`.

### R-8 — Confidence bands

| Band | Range | When |
|---|---|---|
| high | ≥ 0.8 | Canonical R-3 examples; unambiguous run-verb + campaign |

| low | < 0.7 | Ambiguous; prefer `other` over forcing RUN |

`confidence` is a finite number in `[0, 1]`; never `NaN`, never omitted.

### Design overview

`classifyCampaignIntent` is a **pure, deterministic, rule-based NLU mini-classifier** that operates on a single English utterance string. It produces a `CampaignIntentResult` with exactly three possible intents (`campaign_run`, `list`, `other`), a 0–1 confidence score, and typed slots. The classifier is the **deterministic half** of the CAMPAIGN intent system — the C0 `canvasAiSystemPrompt.ts` CAMPAIGN block is the **model half**; neither replaces the other.

**Invariants the implementation MUST satisfy:**

1. Same input → same output every time (pure function).
2. No I/O: no LLM call, no HTTP, no canvas snapshot, no `localStorage`, no tenant/mailbox state, no `Date.now()`.
3. English only; case-insensitive; punctuation- and whitespace-tolerant.
4. Canonical T1–T14 produce the pinned results (R-13). Miss on T1 or T7–T9 is a defect.

### 3. Classification algorithm (P3, P4, R-3–R-8)

The algorithm is a **layered keyword + pattern rule engine** executed in strict order. No ML, no embeddings, no fuzzy string libraries — just normalized token matching with explicit typo tolerance.

#### 3.1 Normalization

```
raw → trim → lowercase → collapse whitespace → tokenize on /\s+/
```

Punctuation in the raw string does not block classification but is stripped during tokenization: split on `/[^a-z0-9]+/` so `"send a campaign!"` → `["send", "a", "campaign"]`.

#### 3.2 Detection primitives

Each detector is a boolean function over the token list (or over the normalized string for multi-word phrases). The implementation MUST define these as named constants at module scope so they are auditable.

##### 3.2.1 RUN_VERBS

Tokens (or bigrams for multi-word) that signal the user wants to start/execute:

| Canonical | Typo-tolerant matches |
|---|---|
| `run` | `run`, `rnu`, `urn` (edit distance ≤ 1) |
| `launch` | `launch`, `lanuch`, `lauch`, `luanch` (edit distance ≤ 1) |
| `start` | `start`, `strt`, `star` (edit distance ≤ 1) |
| `send` | `send`, `sned`, `snd` (edit distance ≤ 1) |
| `kick off` | bigram near-match for `kick` + `off`; tolerates `kik off`, `kick of` |
| `go live` | bigram `go` + `live`; tolerates `go lve` |
| `fire off` | bigram `fire` + `off` |

**Implementation note:** Edit-distance tolerance applies only to tokens of length ≥ 3. Single-character tokens (`a`, `I`) are never fuzzy-matched. For bigrams, both components must be present with at most one-character edit distance each. This avoids over-matching noise.

##### 3.2.2 CAMPAIGN_NOUNS

Tokens the user is talking about a marketing campaign:

| Canonical | Typo-tolerant matches |
|---|---|
| `campaign` | `campaign`, `campagin`, `campain`, `campagn` (edit distance ≤ 1) |
| `marketing` | `marketing`, `marketng`, `markting` (edit distance ≤ 1) |

"campaign" is sufficient even without "marketing" — the module is marketing/canvas-scoped (P4).

##### 3.2.3 LIST_VERBS

Tokens signaling inspection/inventory:

`list`, `show`, `browse`, `what` (when followed by campaign-like language), `my` (when adjacent to "campaigns"). Also the phrase `what campaigns do I have`.

##### 3.2.4 CONNECT_VERBS

`connect`, `link`, `add` (when adjacent to a channel noun).

##### 3.2.5 NON_RUN_VERBS (negative set)

If one of these is the *only* action verb and no RUN_VERB is present, the result is `other`:

`pause`, `stop`, `edit`, `draft`, `analytics`, `report`, `how`, `what is`

The presence of a NON_RUN_VERB without a RUN_VERB and without a LIST_VERB → `other`.

##### 3.2.6 CHANNEL_MAP

| Utterance tokens | `channel` slot |
|---|---|
| `email`, `gmail`, `outlook`, `microsoft`+`365`, `mailbox`, `inbox` | `'email'` |
| `social`, `instagram`, `tiktok`, `linkedin`, `facebook`, `x`, `twitter` | `'social'` |
| `ads`, `google`+`ads`, `meta`+`ads`, `paid` | `'ads'` |

Channel is set ONLY when the utterance contains one of these tokens. Never invent a channel.

#### 3.3 Decision tree (MUST be implemented in this order)

```
INPUT: tokens[], normalized string

1. has_run_verb  = any token/bigram matches RUN_VERBS
2. has_campaign  = any token matches CAMPAIGN_NOUNS
3. has_list_verb = any token/bigram matches LIST_VERBS
4. has_connect   = any token matches CONNECT_VERBS
5. has_non_run   = any token matches NON_RUN_VERBS (and NO run verb)
6. channel       = first matching CHANNEL_MAP token, or undefined

DECISION:
  IF has_run_verb AND has_campaign:
      intent = 'campaign_run'
      confidence = computeRunConfidence(tokens, normalized)
      connect_requested = has_connect AND channel !== undefined
      channel = channel  // from utterance only
  ELSE IF has_run_verb AND NOT has_campaign:
      // "launch" / "run" / "start" without "campaign" — marketing-scoped
      // P4: "launch a campaign" (without "marketing") is still campaign_run
      // But "launch" alone with no campaign noun at all → other
      intent = 'other'
      confidence = 0.5
  ELSE IF has_list_verb AND has_campaign AND NOT has_run_verb:
      intent = 'list'
      confidence = 0.85  // clear list; adjust down to 0.75 if also has connect noise
      connect_requested = false
      channel = channel  // may still be present for "list my email campaigns"
  ELSE IF has_connect AND NOT has_run_verb AND NOT has_list_verb:
      intent = 'other'
      confidence = 0.8
      connect_requested = (channel === 'email')  // only email connect is a "connect_requested" signal
      channel = channel
  ELSE IF has_non_run AND NOT has_run_verb AND NOT has_list_verb:
      intent = 'other'
      confidence = 0.85
  ELSE:
      intent = 'other'
      confidence = 0.4
```

#### 3.4 Confidence computation

##### `campaign_run` confidence

| Condition | Confidence |
|---|---|
| Exact canonical: "i want to run a marketing campaign" (normalized) | 0.95 |
| Exact canonical: "connect my email and run a marketing campaign" (normalized) | 0.95 |
| RUN_VERB + "marketing campaign" (exact phrase, no typo) | 0.90 |
| RUN_VERB + "campaign" (no typo on either) | 0.85 |
| RUN_VERB (typo-tolerant) + "campaign" (no typo on "campaign") | 0.80 |
| RUN_VERB (no typo) + CAMPAIGN_NOUN (typo-tolerant) | 0.78 |
| Both RUN_VERB and CAMPAIGN_NOUN typo-tolerant | 0.72 |
| RUN_VERB + campaign but extra words obscure the signal | 0.70 |

FLOOR for `campaign_run` is 0.70. Anything below → reclassify as `other`.

##### `list` confidence

| Condition | Confidence |
|---|---|
| "list my campaigns" / "show my campaigns" (exact normalized) | 0.90 |
| "what campaigns do I have" (exact normalized) | 0.88 |
| LIST_VERB + "campaigns" (no typo) | 0.85 |
| LIST_VERB (typo-tolerant) + "campaigns" | 0.78 |
| "my campaigns" (no verb but clear inventory signal) | 0.75 |

FLOOR for `list` is 0.75.

##### `other` confidence

- Connect-only with clear channel: 0.80
- Non-run verb clearly present: 0.85
- Ambiguous / no signal: 0.40–0.60 (caller should treat low-confidence `other` as "no actionable intent")

### 4. Ranking & conflict resolution (P3, R-6)

The decision tree in §3.3 encodes the ranking. Key rules:

1. **RUN > list always.** If both signals are present, `intent` is `campaign_run`. There is no `list_and_run`.
2. **RUN > connect.** If connect + run language co-occur, `intent` is `campaign_run` with `connect_requested=true`.
3. **connect-only → `other`.** "connect my email" without run/launch/send/kick off/go live language is NOT `campaign_run`.
4. **Unsure RUN vs `other` → `other`.** If confidence would fall below 0.70, output `other` instead of forcing RUN.
5. **Unsure RUN vs `list` → RUN** only if a RUN_VERB is present; otherwise `list`.
6. **Guest vs tenant** (persistence local vs server) DOES NOT change the label. T1 and T2 are `campaign_run` on an anonymous board too.

---

### 5. Typo tolerance (P4, R-12)

Typo tolerance is **edit-distance based** with a maximum distance of 1 for tokens of length ≥ 3. Multi-word verbs use component-wise tolerance. The implementation SHOULD use a simple Levenshtein distance function (no external dependency needed — it is ~15 lines of code). DO NOT pull in a fuzzy-match library; the classifier must remain zero-dependency beyond what the contract package already carries.

**Common typos the classifier MUST handle:**

| Typo | Resolves to |
|---|---|
| `lanuch` | `launch` |
| `kik off` | `kick off` |
| `campagin` | `campaign` |
| `campain` | `campaign` |
| `sned` | `send` |
| `rnu` | `run` |
| `mrketing` | `marketing` |
| `marketng` | `marketing` |

**Typos it does NOT need to handle:** garbled text where every word is misspelled; non-English; entirely phonetic spelling ("run a campane"). The classifier is a routing aid, not a spell-checker.
