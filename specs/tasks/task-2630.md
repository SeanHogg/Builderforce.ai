# PRD: Campaign-RUN Intent Recognition (WIP)

## Problem & Goal

Users ask in natural language to start a marketing campaign (e.g. “I want to run a marketing campaign”, “connect my email and run a marketing campaign”). Downstream agents currently under-detect this as an execution request and over-route to campaign listing or browse flows.

**Goal:** Treat **campaign-RUN** as the primary intent. Classify list/browse as secondary so a user who wants to launch (and optionally connect email first) is routed into the run/connect path, not a list of existing campaigns.

## Target users / ICP roles

- Growth / lifecycle marketers launching email (and similar) campaigns
- Founders and operators on self-serve marketing tools
- Downstream routing, orchestration, and tool-calling agents that consume this intent

## Scope

- Natural-language intent recognition on the product’s conversation / command surface
- Primary class: **campaign-RUN** (start / launch / run a marketing campaign; may include connect-email as a prerequisite step)
- Secondary class: **list** (show / list / browse existing campaigns)
- Disambiguation when an utterance could match both; RUN wins
- Hand-off of a structured intent payload to downstream agents (intent, confidence, optional slots such as channel)

## Functional requirements

1. Detect campaign-RUN for explicit launch language: run, start, launch, create-and-run, send a campaign, “I want to run a marketing campaign”.
2. Detect campaign-RUN when connect-email (or equivalent channel connect) is bundled with run: “connect my email and run a marketing campaign”. Connect is a step, not a separate primary intent.
3. Detect list only when the user clearly wants inventory, not execution: list campaigns, show my campaigns, what campaigns do I have.
4. If RUN and list both fit, classify as campaign-RUN.
5. Emit a structured result: `intent` (`campaign_run` | `list` | other), `confidence`, and slots when present (`channel`, `connect_required`).
6. Do not require the user to name a specific campaign to classify RUN; unnamed “run a marketing campaign” is sufficient.
7. Keep classification independent of whether email is already connected; connection state is handled after intent.

## Acceptance criteria

- “I want to run a marketing campaign” → `campaign_run`.
- “Connect my email and run a marketing campaign” → `campaign_run` with connect-email treated as a prerequisite slot/step, not list.
- Near-paraphrases (start/launch/send a marketing campaign; run an email campaign) → `campaign_run`.
- “List my campaigns” / “show existing campaigns” → `list`.
- Ambiguous “campaigns” with run/launch verbs → `campaign_run`, not `list`.
- Downstream agents receive a stable intent name and can branch: RUN → connect (if needed) then launch flow; list → inventory flow.
- False routing of RUN utterances into list is treated as a defect.

## Out of scope

- Executing the campaign, sending email, or performing OAuth/email connect (recognition and routing only)
- Campaign content, audience, or schedule design
- Analytics, reporting, or pause/stop/edit of an in-flight campaign
- Multi-channel campaign types beyond what the utterance implies (no requirement to infer SMS/ads/etc. unless stated)
- Training data pipelines, model choice, or production ML ops
- Auth, billing, and compliance copy for email sending
- UI chrome for the list view or the run wizard beyond intent hand-off

### R-2 Intent enum and priority (load-bearing)

Every classified **user** turn emits exactly one of:

| `intent` | Meaning |
| --- | --- |
| `campaign_run` | User wants to **start / launch / run** a marketing campaign (optionally connect a channel first) |
| `list` | User wants **inventory** of existing campaigns (show / list / browse / “what do I have”) |
| `other` | Neither. Includes connect-only, chat assent, inspect/how-to, pause/edit/analytics, bare create-without-run |

**Priority:** if RUN and list both fit the same turn, **`campaign_run` wins**. Do not argmax competing confidences in a way that can pick `list` when RUN language is present. Priority is on the **intent label**, not on score.

Stable wire names are snake_case as above. Do not emit `campaign-RUN`, `RUN`, `CampaignRun`, or `browse` on the wire.

### R-3 `campaign_run` detection

Classify `campaign_run` when the utterance’s goal is to start, launch, send, run, kick off, or go live with a **marketing / email / (stated-channel) campaign**, including create-**and**-run.

**Canonical (must hit `campaign_run`, high confidence — R-8):**

- “I want to run a marketing campaign”
- “connect my email and run a marketing campaign”

**Near-paraphrases (must hit `campaign_run`):** start / launch / send / kick off / go live with a marketing campaign; run an email campaign; create and run a campaign; “run a campaign” / “launch a campaign” with or without “marketing”.

**Not required:** a named campaign, an audience, a schedule, or a connected mailbox (R-7, R-9).

**Bare create is not RUN:** “create a campaign” / “draft a campaign” / “make a campaign” without run / start / launch / send / kick off / go live → `other` (author/draft). “Create and run” → `campaign_run`.

### R-4 Compound connect + run (connect is a slot, not a competing intent)

If the same turn mentions connecting email (or another stated channel) **and** running/launching a campaign:

- `intent` = `campaign_run` (not connect-only, not `list`)
- `slots.connect_requested` = `true`
- `slots.channel` = the stated channel (`email` for “connect my email…”; omit if no channel is named)

Connect is a **prerequisite step** for the C1 journey after hand-off. This classifier does not connect, does not call `mailbox.list_connections`, and does not inspect live grant state.

**Connect-only** (“connect my email”, “connect mailbox”, no run/launch/send/start language) → `other`, not `campaign_run` and not `list`. This ticket does not own connect-only routing.

### R-5 `list` detection (only when RUN is absent)

Classify `list` only when the user clearly wants inventory **and** R-3 RUN language is absent.

**Must hit `list`:** “list my campaigns”, “list campaigns”, “show my campaigns”, “show existing campaigns”, “what campaigns do I have”, “browse campaigns”.

**Must not promote to `campaign_run`:** those inventory phrases with no run/launch/send/start/kick-off/go-live verb.

If both list-like and run-like language appear in one turn (e.g. “list campaigns and then run one”, “show my campaigns and launch a new one”) → **`campaign_run`** (R-2).

### R-6 Disambiguation matrix (normative)

| Utterance pattern | `intent` | `connect_requested` | `channel` |
| --- | --- | --- | --- |
| “I want to run a marketing campaign” | `campaign_run` | `false` | omitted |
| “Connect my email and run a marketing campaign” | `campaign_run` | `true` | `email` |
| start / launch / send a marketing campaign; run an email campaign | `campaign_run` | `false` unless connect is also asked | `email` only if stated |
| “List my campaigns” / “show existing campaigns” / “what campaigns do I have” | `list` | `false` / omit | omitted |
| Run/launch verbs + “campaigns” (even if “list” also appears) | `campaign_run` | per R-4 | per utterance |
| “Connect my email” (no run/launch/send/start) | `other` | n/a | n/a |
| Chat assent: “yes”, “send it”, “go live”, “looks good”, “do it”, “ok”, “confirm” with no campaign-run noun phrase | `other` | n/a | n/a |
| Pause / stop / edit / analytics / “how do campaigns work” / “what is a campaign” | `other` | n/a | n/a |
| “Show campaign {name}” / inspect one existing campaign | `other` or `list` (Architect may pick `list`; **must not** be `campaign_run`) | n/a | n/a |
| “Send campaign {name/id}” / “run campaign {name}” | `campaign_run` | `false` unless connect asked | per utterance |
| Bare “create a campaign” (no run/launch/send/start) | `other` | n/a | n/a |

Anaphoric assent without campaign-run language is **`other`**. C3 `#2638` owns that assent never sends; this classifier must not relabel “send it” as a new `campaign_run`.

### R-7 Classification is independent of environment

Inputs to the classifier are **the user utterance** (and, if Architect adds it, UI locale). The following **MUST NOT** be consulted at classify time and **MUST NOT** change the intent label:

- Whether a mailbox / sender / ad account is already connected (`mailbox.list_connections` and equivalents)
- Auth / anonymous vs signed-in
- Whether any campaign already exists
- ICP presence (`#2632`)
- Checklist / `sendReadiness` / `maySend` / `humanConfirmed`
- Persistence (`server` vs local) and `agentDraftOnly`

Anonymous users still get a correct intent (they may enter the C1 draft journey; they still cannot send — C1 / C3). Cloud agents classifying the same user text get the same label; they remain draft-only.

Unnamed “run a marketing campaign” is sufficient for `campaign_run`. Requiring a campaign name or id to classify RUN is a defect.

### R-8 Structured payload (stable hand-off)

For every classified user turn, emit:

```
CampaignIntentResult {
  intent: "campaign_run" | "list" | "other"
  confidence: number          // inclusive 0..1
  slots: {
    channel?: string          // only if the utterance names a channel; do not default to email
    connect_requested: boolean // default false; meaningful on campaign_run (R-4)
    campaign_name?: string    // only if the user named one; absence is OK for RUN
  }
  raw_utterance: string       // the classified turn, unmodified
}
```

**BA vs PM naming:** `connect_requested` **replaces** PM FR-5 `connect_required`. Do not emit `connect_required` on the wire.

**Confidence:**

- Canonical two utterances (R-3) → `intent=campaign_run` and `confidence >= 0.8`
- Inventory phrases (R-5) → `intent=list` and `confidence >= 0.8`
- Implementation may be **deterministic rules** (no ML required — training data / model choice are out of scope). Rule hits may emit `1.0`.
- Confidence **must not** override R-2 priority.

**Do not invent:** campaign copy, audience, schedule, budget, SMS/ads/push unless the utterance states that channel. Multi-channel inference beyond the stated channel is out of scope.

**Purity:** same utterance → same result. Classification has no side effects (R-10).

### R-9 Channel slot rules

1. Set `channel` only when the utterance names one (e.g. “email”, “mailbox”, “SMS”). “Marketing campaign” with no channel → **omit** `channel` (do not default).
2. “Connect my email and run…” → `channel = "email"` (or Architect’s existing channel enum value for email — bind in Design; do not invent SMS/ads enums here).
3. Do not infer ads, social, or SMS from “marketing campaign” alone.

### R-10 Hand-off / routing (no side effects)

Downstream agents **must** branch on `intent`:

| `intent` | Routing | Forbidden |
| --- | --- | --- |
| `campaign_run` | Enter C1 guided journey (context → `#2631` checklist → connect-if-needed `#2635` → draft copy). `connect_requested` is a **step hint**, not a connect API call from this ticket. | Calling `marketing.campaigns.list` / `campaign.list` as the primary handler; sending; scheduling; publishing; ads launch; setting `humanConfirmed` |
| `list` | Existing inventory flow (`marketing.campaigns.list` / `campaign.list` — **unchanged**) | Entering the run wizard; creating a campaign |
| `other` | No campaign-run routing and no forced list | Treating as `campaign_run` |

Classification **itself** MUST NOT: send mail, OAuth, `campaign.create`, `campaign.send`, `campaign.schedule`, publish, ads launch, write C1 flags, or mutate Growth/Canvas campaign records.

False routing of a `campaign_run` utterance into list/inventory is a **defect**. False `campaign_run` on a pure list/inspect query is a **defect**. Missed `campaign_run` on the two canonical utterances is a **defect**.

### R-11 Surfaces

In scope: **user-typed** natural language on the product conversation / command / Canvas AI surfaces (the same family C0 already prompts).

Out of classifier scope (do not classify as user intent): tool results, system messages, prompt-catalog table rows, campaign list API payloads, agent-to-agent chatter that is not the operator’s turn.

Cloud agents may **consume** the structured result to draft. They MUST NOT treat `campaign_run` as permission to send (C1 `agentDraftOnly` / C3).

### R-12 Language

English first. Match **intent**, not exact strings. Tolerate extra words and close paraphrases of the R-3 verbs + “campaign” / “marketing campaign” / “email campaign”. Typo-tolerance of common verbs is best-effort, not a gate. Non-English NLU, voice, and batch classification APIs are out of scope.

### R-13 Defects (QA / Validator)

Treat as fail:

1. Canonical “I want to run a marketing campaign” → not `campaign_run`
2. Canonical “connect my email and run a marketing campaign” → `list`, connect-only, or `other`
3. That second canonical → `campaign_run` but `connect_requested !== true` or channel not email
4. “List my campaigns” / “show existing campaigns” → `campaign_run`
5. Mixed run + list in one turn → `list`
6. Classifier calls `mailbox.list_connections` (or equivalent) and changes the label based on grant state
7. Classifier requires a campaign name to emit `campaign_run`
8. Classifier side-effects send / connect / `campaign.create`
9. Wire payload uses `connect_required` instead of `connect_requested`
10. C0 CAMPAIGN prompt re-authored on this ticket
11. `marketing.campaigns.list` overwritten or used as the RUN handler

### R-14 Out of scope (do not pull in)

- Executing the campaign, sending email, OAuth / mailbox connect, ads spend
- Journey checklist (`#2631`), empty-ICP gate (`#2632`), `maySend` (`#2633`), ROI (`#2634` / `#2640`), connect-never-sends (`#2635`), human-confirm (`#2638`)
- Campaign content, audience builder, schedule design, A/B, pause/stop/edit
- Re-authoring C0 CAMPAIGN prompt
- Overwriting `marketing.campaigns.list`
- Training data pipelines, model choice, production ML ops
- Auth, billing, compliance copy for email sending
- UI chrome for the list view or the run wizard beyond intent hand-off
- Multi-turn slot filling beyond R-8
- Dumping `specs/tasks/task-2630.md` or product-repo files from this BA slot
