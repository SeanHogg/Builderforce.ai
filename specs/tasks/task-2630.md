# PRD: Campaign-RUN Intent Recognition (WIP)

## Problem & Goal

Users ask in natural language to start a marketing campaign (e.g. “I want to run a marketing campaign”, “connect my email and run a marketing campaign”). Downstream agents currently under-detect this as an execution request and over-route to campaign listing or browse flows.

**Goal:** Treat **campaign-RUN** as the primary intent. Classify list/browse as secondary so a user who wants to launch (and optionally connect email first) is routed into the run/connect path, not a list of existing campaigns.

## Target users / ICP roles

- Growth / lifecycle marketers launching email (and similar) campaigns
- Founders and operators on self-serve marketing tools
- Downstream routing, orchestration, and tool-calling agents that consume this intent

## Scope

- Natural-language intent recognition on the product’s conversation / command surface
- Primary class: **campaign-RUN** (start / launch / run a marketing campaign; may include connect-email as a prerequisite step)
- Secondary class: **list** (show / list / browse existing campaigns)
- Disambiguation when an utterance could match both; RUN wins
- Hand-off of a structured intent payload to downstream agents (intent, confidence, optional slots such as channel)

## Functional requirements

1. Detect campaign-RUN for explicit launch language: run, start, launch, create-and-run, send a campaign, “I want to run a marketing campaign”.
2. Detect campaign-RUN when connect-email (or equivalent channel connect) is bundled with run: “connect my email and run a marketing campaign”. Connect is a step, not a separate primary intent.
3. Detect list only when the user clearly wants inventory, not execution: list campaigns, show my campaigns, what campaigns do I have.
4. If RUN and list both fit, classify as campaign-RUN.
5. Emit a structured result: `intent` (`campaign_run` | `list` | other), `confidence`, and slots when present (`channel`, `connect_required`).
6. Do not require the user to name a specific campaign to classify RUN; unnamed “run a marketing campaign” is sufficient.
7. Keep classification independent of whether email is already connected; connection state is handled after intent.

## Acceptance criteria

- “I want to run a marketing campaign” → `campaign_run`.
- “Connect my email and run a marketing campaign” → `campaign_run` with connect-email treated as a prerequisite slot/step, not list.
- Near-paraphrases (start/launch/send a marketing campaign; run an email campaign) → `campaign_run`.
- “List my campaigns” / “show existing campaigns” → `list`.
- Ambiguous “campaigns” with run/launch verbs → `campaign_run`, not `list`.
- Downstream agents receive a stable intent name and can branch: RUN → connect (if needed) then launch flow; list → inventory flow.
- False routing of RUN utterances into list is treated as a defect.

## Out of scope

- Executing the campaign, sending email, or performing OAuth/email connect (recognition and routing only)
- Campaign content, audience, or schedule design
- Analytics, reporting, or pause/stop/edit of an in-flight campaign
- Multi-channel campaign types beyond what the utterance implies (no requirement to infer SMS/ads/etc. unless stated)
- Training data pipelines, model choice, or production ML ops
- Auth, billing, and compliance copy for email sending
- UI chrome for the list view or the run wizard beyond intent hand-off
