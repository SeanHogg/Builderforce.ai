# PRD: Campaign-RUN Intent Recognition (WIP)

## Problem & Goal

Users ask in natural language to start a marketing campaign (e.g. “I want to run a marketing campaign”, “connect my email and run a marketing campaign”). Downstream agents currently under-detect this as an execution request and over-route to campaign listing or browse flows.

**Goal:** Treat **campaign-RUN** as the primary intent. Classify list/browse as secondary so a user who wants to launch (and optionally connect email first) is routed into the run/connect path, not a list of existing campaigns.

## Target users / ICP roles

- Growth / lifecycle marketers launching email (and similar) campaigns
- Founders and operators on self-serve marketing tools
- Downstream routing, orchestration, and tool-calling agents that consume this intent

## Scope

- Natural-language intent recognition on the product’s conversation / command surface
- Primary class: **campaign-RUN** (start / launch / run a marketing campaign; may include connect-email as a prerequisite step)
- Secondary class: **list** (show / list / browse existing campaigns)
- Disambiguation when an utterance could match both; RUN wins
- Hand-off of a structured intent payload to downstream agents (intent, confidence, optional slots such as channel)

## Functional requirements

1. Detect campaign-RUN for explicit launch language: run, start, launch, create-and-run, send a campaign, “I want to run a marketing campaign”.
2. Detect campaign-RUN when connect-email (or equivalent channel connect) is bundled with run: “connect my email and run a marketing campaign”. Connect is a step, not a separate primary intent.
3. Detect list only when the user clearly wants inventory, not execution: list campaigns, show my campaigns, what campaigns do I have.
4. If RUN and list both fit, classify as campaign-RUN.
5. Emit a structured result: `intent` (`campaign_run` | `list` | other), `confidence`, and slots when present (`channel`, `connect_required`).
6. Do not require the user to name a specific campaign to classify RUN; unnamed “run a marketing campaign” is sufficient.
7. Keep classification independent of whether email is already connected; connection state is handled after intent.

## Acceptance criteria

- “I want to run a marketing campaign” → `campaign_run`.
- “Connect my email and run a marketing campaign” → `campaign_run` with connect-email treated as a prerequisite slot/step, not list.
- Near-paraphrases (start/launch/send a marketing campaign; run an email campaign) → `campaign_run`.
- “List my campaigns” / “show existing campaigns” → `list`.
- Ambiguous “campaigns” with run/launch verbs → `campaign_run`, not `list`.
- Downstream agents receive a stable intent name and can branch: RUN → connect (if needed) then launch flow; list → inventory flow.
- False routing of RUN utterances into list is treated as a defect.

## Out of scope

- Executing the campaign, sending email, or performing OAuth/email connect (recognition and routing only)
- Campaign content, audience, or schedule design
- Analytics, reporting, or pause/stop/edit of an in-flight campaign
- Multi-channel campaign types beyond what the utterance implies (no requirement to infer SMS/ads/etc. unless stated)
- Training data pipelines, model choice, or production ML ops
- Auth, billing, and compliance copy for email sending
- UI chrome for the list view or the run wizard beyond intent hand-off

### R-2 — Output contract (`CampaignIntentResult`)

```
{
  intent: 'campaign_run' | 'list' | 'other'
  confidence: number            // inclusive 0..1, finite, never omitted
  slots: {
    channel?: 'email' | 'social' | 'ads'
    connect_requested: boolean  // always present; default false
    raw_utterance: string       // trimmed original; not paraphrased
  }
}
```

- `intent` is exactly one of those three strings (snake_case `campaign_run`, not `campaign-RUN`, not `run`).
- Slot name is **`connect_requested`**, never `connect_required` (requested ≠ a send/connect gate).
- `slots.channel` SHALL be set only when the utterance names a channel: email / Gmail / Outlook / Microsoft 365 → `email`; social / Instagram / TikTok / LinkedIn / Facebook / X / Twitter → `social`; ads / Google Ads / Meta ads / paid → `ads`. SHALL NOT invent a channel when none is named.
- SHALL NOT invent campaign content, audience, schedule, offer, brand, or ICP into slots (C1 intake / C3 checklist).
- Downstream agents receive **only** this payload. Classification does not send mail.

### R-3 — Primary intent: `campaign_run`

Classify `campaign_run` when the utterance’s **goal** is to start, launch, send, run, kick off, or go live with a marketing / email / ads campaign.

Canonical positives — MUST be `campaign_run`, `confidence ≥ 0.8`:

1. `I want to run a marketing campaign` → `connect_requested=false`, no `channel`
2. `connect my email and run a marketing campaign` → `connect_requested=true`, `channel='email'`

Close paraphrases — MUST be `campaign_run`, `confidence ≥ 0.7`: launch / start / send / kick off / go live / fire off + (marketing | email | ads)? campaign. Match **intent**, not exact strings. Tolerate extra words and common typos of those verbs/nouns (`lanuch`, `kik off`, `campagin`). Missed RUN on the two canonicals is a **defect**.

### R-4 — Compound connect + run

If the same turn mentions connecting a channel **and** a run-class verb + campaign, classify `campaign_run`, **not** connect-only and **not** `list`.

- `connect_requested=true`; `channel` = the named channel.
- Connection is a **precondition slot**, not a competing primary intent.
- EMAIL (`canvas_add_inbox`, tenant-only) and SOCIAL connect tools are **downstream of** this label; this ticket does not call them.
- Guest vs tenant (`persistence` local vs server) SHALL NOT change the label. Canonical (2) is `campaign_run` on an anonymous board too. Whether the inbox tool is in the turn’s list is C0/C1, not a reason to relabel `list` or `other`.

### R-5 — Secondary intent: `list`

Classify `list` only when the utterance asks to show / list / browse / “what campaigns do I have” / “my campaigns” as inspection **and** no run-class verb (R-3) is present.

MUST be `list`, never `campaign_run`: `show my campaigns`, `list campaigns`, `list my campaigns`, `what campaigns do I have`.

`marketing.campaigns.list` (executive catalog / portfolio table) remains the **list** path. This classifier’s job is to **keep RUN off that path**. False RUN on pure list/inspect queries is a **defect**.

### R-6 — RUN wins (ranking)

If both list-like and run-like language appear in one turn, `intent` SHALL be `campaign_run`. List is never equal priority to RUN (PRD out-of-scope). There is no `list_and_run` value.

MUST: `list campaigns and then run one` → `campaign_run`. MUST: `show my campaigns and launch a new one` → `campaign_run`.

### R-7 — Connect-only, inspect-only, and non-run verbs are `other`

- Connect-only (`connect my email`, `connect Gmail`, `link my mailbox`) with **no** run/launch/send/kick off/go live language → `other`. SHALL NOT be `campaign_run`. `connect_requested` MAY be `true` with `intent: 'other'`.
- Draft / edit / pause / stop / analytics / report / “how do campaigns work” / “what is a campaign” → `other` unless a clear run-class verb is also present.
- When unsure between `campaign_run` and `other`, choose `other`. When unsure between `campaign_run` and `list`, choose `campaign_run` **only** if a run-class verb is present (R-6); otherwise `list`.

### R-8 — Confidence bands

| Band | Range | When |
|---|---|---|
| high | ≥ 0.8 | Canonical R-3 examples; unambiguous run-verb + campaign |
| medium | 0.7–0.79 | Paraphrase with extra words / mild typo, still clearly RUN |
| list | ≥ 0.75 | Clear list/browse with no run verb |
| low | < 0.7 | Ambiguous; prefer `other` over forcing RUN |

`confidence` is a finite number in `[0, 1]`; never `NaN`, never omitted.

### R-9 — Deterministic, model-free

`classifyCampaignIntent` SHALL be a pure function of the utterance string. No LLM call, no I/O, no canvas snapshot, no tenant lookup. Same input → same output. This is what lets QA pin T1–T14 without a model. The C0 CAMPAIGN prompt remains the instruction to the **model** for intake → checklist → copy → confirm. Neither half replaces the other.

### R-10 — Non-goals (this ticket SHALL NOT)

- Call `campaign.send`, `canvas_publish_social_campaign`, ads `launch`, or any mailbox send.
- Implement C3 checklist, C4 ICP, C5 `maySend`, C6 ROI, C7 connect-success, or #2638 `humanConfirmed`.
- Multi-turn slot filling (audience, schedule, copy) beyond R-2.
- Non-English NLU, voice, or batch classification APIs.
- Training-data dumps, model selection, or infra.
- Treat list as equal priority to RUN.
- Author campaign copy or change `cloudAgentToolset.ts` (still `campaign.list` + `campaign.create` only — classification does not grant send).
- Add `emailCampaign` to `C_SUITE_CANVAS_OWNERS.executiveMarketing.objects`.
- Security, billing, or compliance flows for connected inboxes.

### R-11 — Consumers

Orchestration / NLU / campaign-execution agents SHALL consume `CampaignIntentResult` only. They SHALL start the **run path** (C0 sequence / C1 `guidedCampaignRun`) when `intent === 'campaign_run'`, and the **list/inspect path** (`marketing.campaigns.list` or equivalent) only when `intent === 'list'`. Chat, connect, and agents never send as a result of this classification (send remains C5 + human confirm).

### R-12 — Language

English first. Extra words, punctuation, and common verb/noun typos SHALL NOT drop a canonical RUN to `other`. Case-insensitive. No requirement for non-English, voice, or batch APIs.
