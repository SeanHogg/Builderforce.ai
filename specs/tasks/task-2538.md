# PRD 26 — Meeting Notes listing, minutes→tasks, and follow-up

**Priority:** P0 / P1  
**Spec:** §4.2 J2–J5, §8.4–8.5  
**Dogfood principle:** Meeting intelligence is a marketplace agent path, not a private platform-only feature.

## Problem & Goal

Meeting notes, action items, and follow-ups currently live (or would live) on a private, platform-only path. That blocks dogfood, hides the capability from the marketplace, and forces a second minutes contract if standup-style parsers are reused.

**Goal:** Ship Meeting Notes as a public marketplace `agent` listing that wraps `runAgentTurn` with a silent notetaker persona on `kind=advisory` meetings. Keep the existing three-section Markdown minutes contract so `parseMeetingMinutes` does not fork. On meeting end, place open action items idempotently and propose (never silently book) a follow-up slot, emailing both parties. Guests without a tenant get a guest project plus a claim link.

Success looks like: a public booking creates a meeting row; the notetaker runs by default for dogfood advisors; minutes parse with the existing contract; action items land once per title; visitors cannot list other advisors’ meetings.

## Target users / ICP roles

- **Dogfood advisors** — default-on Meeting Notes on advisory meetings; primary ICP for this slice.
- **Marketplace advisors** — same listing; opt-in via marketplace install after dogfood.
- **Visitors (booked clients)** — receive notes-derived tasks on a project they have or create; receive follow-up proposal email.
- **Guests (no tenant)** — work in a guest project with a claim link rather than a silent tenant create.
- **Downstream agents** — consume this PRD as the shared contract for listing, `summarizeMeeting`, `parseMeetingMinutes`, `pullStandupMinutesAct` generalization, availability solver, and authz tests.

## Scope

### P0

- Publish **Meeting Notes** as a marketplace `agent` listing.
- Listing wraps `runAgentTurn` with a **silent notetaker** persona for `kind=advisory`.
- Default-on for dogfood advisors (no extra install step in dogfood).
- On meeting end, continue to run `summarizeMeeting`.
- Preserve the **three-section Markdown** minutes contract so `parseMeetingMinutes` does not fork.

### P1

- Generalise `pullStandupMinutesAct` so **open action items are placed automatically on meeting end**, idempotent by title.
- Create **canvas task objects** and **API tasks** when the visitor has or creates a project.
- **Propose** a follow-up slot from the **same availability solver**; do not silently book.
- Email **both parties** with the proposal.
- Guest workspace: **prefer guest project + claim link** if the visitor has no tenant.

### Authz / listing tests (ship with P0/P1)

- Public book → meeting row.
- Parser still works against the three-section contract.
- Placing items is idempotent.
- Visitor token cannot list other advisors’ meetings.

## Functional requirements

### FR1 — Marketplace listing (P0)

- Meeting Notes is published as a marketplace listing of type `agent`.
- The listing invokes `runAgentTurn` (not a private/internal-only intelligence path).
- Persona is a silent notetaker: it does not speak in the meeting; it only produces minutes.
- Activation is scoped to meetings with `kind=advisory`.
- Dogfood advisors have the listing **default-on**. Non-dogfood advisors obtain it through the marketplace like any other agent listing.

### FR2 — Minutes contract (P0)

- `summarizeMeeting` continues to run on meeting end. Do not replace or dual-write a second summarizer.
- Output remains **three-section Markdown**, compatible with `parseMeetingMinutes`.
- `parseMeetingMinutes` must not be forked or given a Meeting-Notes-only dialect.
- Section semantics stay stable enough that standup and advisory minutes share one parser.

### FR3 — Auto-place open action items (P1)

- Generalise `pullStandupMinutesAct` for advisory meeting end (not standup-only).
- On end, parse minutes and place **open** action items as tasks.
- Idempotency key is **title** (same title on re-run does not create a duplicate).
- Closed / completed items in minutes are not placed.
- When the visitor already has a project, or creates one in this flow, write:
  - canvas task objects, and
  - API tasks  
  for the same placed items (same title idempotency across both).
- If the visitor has no project and does not create one, do not invent a tenant-owned project on their behalf; see FR5.

### FR4 — Follow-up proposal (P1)

- After minutes + item placement, run the **existing availability solver** (do not introduce a second scheduler).
- **Propose** one follow-up slot; **do not** silently book or write a confirmed calendar event.
- Email both parties (advisor and visitor/guest) with the proposed slot and a path to confirm or decline.
- If the solver returns no slot, send no fake time; omit the proposal or send a “no slot found” notice without booking.

### FR5 — Guest workspace (P1)

- If the visitor has no tenant, **prefer a guest project + claim link**.
- Do not silently provision a full tenant as the default.
- Action items and canvas objects for that meeting attach to the guest project when one exists.
- Claim link lets the guest later attach that project to a real tenant without duplicating placed items (title idempotency still applies).

### FR6 — Data and authz

- A public booking creates a **meeting row** visible to the booked advisor and the visitor for that meeting.
- Meeting Notes artifacts (minutes, placed tasks, follow-up proposal) hang off that row.
- A visitor token **must not** list, read, or enumerate other advisors’ meetings.
- Advisor tokens see only their own meetings plus meetings they are booked on.

## Acceptance criteria

### P0

- Meeting Notes appears as a marketplace `agent` listing wrapping `runAgentTurn`.
- Silent notetaker persona is used only for `kind=advisory`.
- Dogfood advisors have Meeting Notes on without a separate install.
- Meeting intelligence is not reachable only via a private platform path.
- `summarizeMeeting` still runs on meeting end.
- Minutes are three-section Markdown; `parseMeetingMinutes` accepts them without a fork.
- **Test:** public book → meeting row exists for that booking.
- **Test:** parser still works on generated minutes.

### P1

- On meeting end, open action items from minutes are placed without a manual pull.
- Re-running end / pull with the same titles does not duplicate tasks (**idempotent by title**).
- Canvas task objects and API tasks are both written when the visitor has or creates a project.
- Follow-up is a **proposal** from the same availability solver; calendar is not booked silently.
- Both parties receive the follow-up email.
- No-tenant visitors get a guest project and a claim link, not a silent tenant.
- **Test:** placing items is idempotent across double end / double pull.
- **Test:** visitor token cannot list other advisors’ meetings.

## Out of scope

- Speaking / co-pilot notetaker personas, or notetaker for non-`advisory` kinds.
- Forking or replacing `parseMeetingMinutes` or changing the three-section Markdown contract.
- Auto-confirming or silently booking follow-ups; multi-slot offers; SMS/push (email only).
- A second availability solver or a new calendar product.
- Silent tenant provisioning for guests; migrating historical private-path notes.
- Cross-advisor meeting sharing, visitor-to-visitor listing, or admin global meeting search.
- Dedup by anything other than title (assignee, due date, embedding).
- Non-dogfood default-on; marketplace billing/packaging for the listing.
- Rewriting canvas or API task models beyond attaching placed items.
