# PRD 26 — Meeting Notes listing, minutes→tasks, follow-up

**Priority:** P0 / P1  
**Spec:** §4.2 J2–J5, §8.4–8.5  
**Dogfood principle:** Meeting intelligence is a first-class marketplace path, not a private platform-only feature.

## Problem & Goal

Advisors already run live advisory meetings and `summarizeMeeting` already emits minutes. That intelligence is trapped on an internal path: it is not a marketplace agent, action items do not land as tasks, and follow-ups are not proposed from the same availability solver. Visitors without a tenant have no durable place for those tasks.

**Goal:** Ship Meeting Notes as a public marketplace `agent` wrapping `runAgentTurn`, keep the existing three-section minutes contract, auto-place open action items on meeting end (idempotent), and propose (never silently book) a follow-up slot emailed to both parties. Guest visitors get a guest project plus a claim link rather than a silent tenant.

## Target users / ICP roles

| Role | Need |
| --- | --- |
| Dogfood advisor | Default-on silent notetaker on `kind=advisory` meetings; minutes and follow-up without extra setup |
| Marketplace advisor | Same agent listed and installable like any other marketplace agent |
| Booked visitor (tenant) | Action items on their project (canvas objects + API tasks); follow-up proposal in email |
| Booked visitor (no tenant) | Guest project for tasks plus a claim link to take ownership later |
| Downstream agents | Shared minutes contract so `parseMeetingMinutes` does not fork |

## Scope

**P0 — Meeting Notes as a marketplace agent**

- Publish Meeting Notes as a marketplace `agent` listing.
- Implementation wraps `runAgentTurn` with a silent notetaker persona, scoped to `kind=advisory`.
- Default-on for dogfood advisors; other advisors install from the marketplace like any listing.
- On meeting end, continue to call existing `summarizeMeeting`. Do not change the three-section Markdown contract that `parseMeetingMinutes` consumes.

**P1 — Minutes → tasks and follow-up**

- Generalise `pullStandupMinutesAct` so open action items from minutes are placed automatically when the meeting ends.
- Placement is idempotent by task title (re-end / re-parse must not duplicate).
- Persist canvas task objects and create API tasks when the visitor has or creates a project.
- Propose a follow-up slot from the same availability solver used for booking. Do not auto-book.
- Email both parties with the proposal.
- If the visitor has no tenant: create a guest project and include a claim link. Do not invent a tenant.

## Functional requirements

### P0 — Listing and minutes contract

1. **Marketplace listing.** Meeting Notes is published as an `agent` listing (not a hidden platform skill). Metadata, install, and run path match other marketplace agents.
2. **Runtime.** The listing invokes `runAgentTurn`. Persona is a silent notetaker: it does not speak in the live session; it only produces notes/minutes for `kind=advisory`.
3. **Default-on (dogfood).** Dogfood advisors get the agent enabled without a manual install. Non-dogfood advisors opt in via marketplace install.
4. **Meeting row.** A public book creates a meeting row visible to the advisor and the booked visitor under normal authz (see tests).
5. **End-of-meeting summary.** On meeting end, `summarizeMeeting` runs as today.
6. **Markdown contract (frozen).** Minutes remain three-section Markdown so `parseMeetingMinutes` does not fork. Section order and headings stay compatible with the current parser:
   - **Summary** — what was discussed
   - **Decisions** — agreed outcomes
   - **Action items** — open work (title-stable; owners/due dates when present)
7. **No private-only path.** Meeting intelligence is not reachable only through an internal/platform flag. Dogfood uses the same listing + `runAgentTurn` path as marketplace.

### P1 — Place action items

8. **Generalise `pullStandupMinutesAct`.** Same act (or a thin generalisation of it) runs on advisory meeting end, not only standup. Input is the three-section minutes; output is open action items.
9. **Auto-place on end.** When the meeting ends and minutes parse successfully, open action items are placed without a manual “pull” click.
10. **Idempotent by title.** Placement key is the action-item title (normalized). Re-running end/parse/place for the same meeting must not create duplicate canvas or API tasks.
11. **Canvas + API.** Each placed item is a canvas task object. If the visitor has a project, or creates one during this flow, also create the corresponding API task on that project.
12. **Closed items.** Items already marked done in minutes are not placed as open tasks.

### P1 — Follow-up proposal

13. **Solver.** Use the same availability solver as public booking. Propose one slot that works for advisor and visitor constraints already known for this meeting type.
14. **Propose, do not book.** The slot is a proposal only. No calendar hold, no confirmed booking, no silent write to the booking table.
15. **Email both parties.** Advisor and visitor each receive mail that includes the proposed slot and a way to confirm or decline (existing booking/confirm UX; this PRD does not add a new scheduler UI).
16. **No slot.** If the solver returns no slot, skip the proposal, do not fail minutes or task placement, and do not send a misleading “booked” email.

### P1 — Guest workspace

17. **Preference.** If the visitor has no tenant, create a **guest project** under a guest workspace and attach placed tasks there. Include a **claim link** in visitor-facing email so they can claim the project into a real tenant later.
18. **Do not** auto-provision a full tenant, attach guest tasks to another advisor’s workspace as if they were the visitor’s, or leave tasks only on the advisor side with no visitor-owned container.
19. **Visitor with a tenant** uses their existing (or newly created) project; no guest project.

### Authz and isolation

20. A visitor token can read the meeting they booked and tasks placed for them. It **cannot** list other advisors’ meetings or other visitors’ meetings.
21. Advisor tokens see their own meetings and notes only, subject to existing advisor authz.

## Acceptance criteria

- Meeting Notes appears as a marketplace `agent` listing whose run path wraps `runAgentTurn` with the silent notetaker persona for `kind=advisory`.
- Dogfood advisors have the agent default-on; a public book still produces a meeting row.
- After meeting end, minutes are three-section Markdown; `parseMeetingMinutes` succeeds against them without a parser fork or dual contract.
- Open action items from those minutes are placed automatically on end; a second place/end for the same titles does not duplicate canvas or API tasks.
- When the visitor has or creates a project, API tasks exist on that project in addition to canvas task objects.
- A follow-up slot is proposed via the shared availability solver and emailed to both parties; the calendar/booking store does not show a confirmed booking until someone accepts.
- A visitor with no tenant gets a guest project plus a claim link; tasks land on that guest project.
- Visitor token cannot list other advisors’ meetings (negative authz test).
- Automated coverage at minimum: public book → meeting row; parser still works on the frozen three-section contract; placing items is idempotent by title; visitor token cannot list other advisors’ meetings.

## Out of scope

- Changing `summarizeMeeting` section count, headings, or a second minutes schema.
- Spoken/interruptive notetaker behavior in the live session.
- Silently booking or holding the follow-up slot.
- New calendar UI, multi-slot negotiation, or timezone-picker redesign.
- Full tenant provisioning for guests; SSO/IdP for claim.
- Recurring series, multi-visitor attribution beyond title-idempotent place, or assignment to people not on the meeting.
- Using Meeting Notes for non-`advisory` kinds in this slice.
- Platform-only or flag-gated meeting intelligence that bypasses the marketplace listing.
- Redesign of marketplace install/billing; Meeting Notes follows existing agent listing mechanics.
- Editing or deleting historical minutes from this slice (read/parse/place only).
- Cross-advisor meeting search, export, or analytics dashboards.
