# PRD: Generalise `pullStandupMinutesAct` — auto-place open action items

## Problem & Goal

`pullStandupMinutesAct` currently pulls standup minutes in a narrow, minutes-only shape. Open action items are not consistently landed on the canvas or in the project task list, so facilitators re-copy them by hand and duplicates appear when the same minutes are pulled again.

**Goal:** Generalise `pullStandupMinutesAct` so that every open action item from standup minutes is placed automatically at the end of the destination, **idempotent by title**. Placement must cover:

1. **Canvas task objects** on the visitor’s canvas.
2. **API tasks** on the visitor’s project when they already have a project or create one as part of this flow.

Same title already present at the destination must not create a second item. Closed / completed items are not placed.

## Target users / ICP roles

- **Meeting facilitator / standup owner** — pulls minutes after a standup and expects open actions to appear without extra editing.
- **Visitor with a project** — already has (or creates) a project; expects the same open actions as API tasks on that project.
- **Visitor without a project** — still gets canvas task objects; API tasks only after a project exists or is created in this flow.
- Downstream agents implementing canvas placement, project/task APIs, and minutes parsing share this PRD.

## Scope

- Generalise `pullStandupMinutesAct` (same entry point; broader placement behaviour).
- Parse open action items from standup minutes (title is the identity key).
- Append matching items **at the end** of the canvas task sequence.
- Create/link equivalent API tasks when the visitor has a project or creates one during the act.
- Idempotency: skip create if an open item with the same title already exists on that destination (canvas and API independently).
- Re-running the act on the same minutes must not duplicate titles already placed.
- Preserve existing minutes-pull behaviour except where placement of open actions is added or corrected.

## Functional requirements

1. **Open-item extraction**  
   From pulled standup minutes, collect action items whose status is open (not done/cancelled). Use the item **title** (trimmed, case-sensitive as stored) as the idempotency key.

2. **Canvas placement**  
   For each open item with no existing canvas task object of the same title, create a canvas task object and place it at the **end** of the current canvas task order. Do not reorder existing objects. Do not place closed items.

3. **API task placement (project present)**  
   If the visitor already has a project, for each open item with no existing API task of the same title on that project, create an API task. New tasks are ordered at the end of the project’s task list (or equivalent “append” semantics of the tasks API).

4. **API task placement (project created in-flow)**  
   If the visitor creates a project as part of this act (or immediately before placement in the same invocation), run the same API append + title idempotency against the new project.

5. **No project**  
   If the visitor has no project and does not create one, only canvas task objects are placed. The act still succeeds for minutes + canvas placement.

6. **Idempotency**  
   - Canvas: existence check by title among canvas task objects before create.  
   - API: existence check by title among that project’s tasks before create.  
   - A title present on canvas but missing on the API (or vice versa) still creates the missing side only.  
   - Repeated `pullStandupMinutesAct` with unchanged open titles is a no-op for those titles.

7. **End placement**  
   New objects/tasks are always appended after existing ones. Insertion in the middle or reshuffle of prior items is not allowed.

8. **Act contract**  
   Keep the existing `pullStandupMinutesAct` name and caller-facing trigger. Extend its side effects and, if needed, return payload to include counts of created vs skipped-by-title items for canvas and API.

## Acceptance criteria

- Pulling minutes that contain N distinct open action titles creates N canvas task objects when none of those titles exist on the canvas, all appended at the end in minutes order.
- A second pull with the same open titles creates **zero** additional canvas task objects.
- If the visitor has a project, the first pull also creates N API tasks (same titles) at the end of the project task list; the second pull creates zero additional API tasks for those titles.
- If the visitor creates a project during the act, API tasks are created on **that** project with the same append + title idempotency rules.
- If the visitor has no project and creates none, canvas placement still occurs and no API tasks are created.
- An item that is closed in the minutes is never placed on canvas or as an API task.
- If title T exists on the canvas but not on the project, only the API task for T is created (and vice versa).
- Existing canvas order and existing project task order are unchanged except for appends at the end.
- Empty open-action list: minutes pull succeeds; no task objects or API tasks are created.

## Out of scope

- Renaming, merging, or fuzzy-matching titles (no normalisation beyond trim for identity).
- Syncing status, assignee, due date, or description after the initial place (no ongoing two-way sync).
- Deleting canvas or API tasks when they disappear from later minutes.
- Placing closed, cancelled, or completed items.
- Reordering, layout, or grouping of existing canvas objects.
- Multi-project visitors (one visitor project for this act; no project picker UX).
- Notifications, mentions, or third-party task backends.
- Changing how standup minutes themselves are authored or stored, except reading open action items for placement.
