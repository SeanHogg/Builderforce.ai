# PRD: Generalise `pullStandupMinutesAct` — auto-place open action items

## Problem & Goal

**Problem.** `pullStandupMinutesAct` only hydrates standup minutes in a narrow, minutes-centric path. Open action items are not appended to the minutes document, so follow-ups live in a separate list and are easy to miss. Re-running the act can duplicate items with the same title. Canvas task objects and API tasks are not created together when a visitor already has a project or creates one during the flow, so the board and the backend drift.

**Goal.** Generalise `pullStandupMinutesAct` so that:

1. Open action items are placed automatically at the **end** of the standup minutes.
2. Placement is **idempotent by title** (same title → no second item).
3. When the visitor has or creates a project, the act materialises **both** Canvas task objects and API tasks for those items.

Downstream agents should treat this PRD as the shared contract for implementation, tests, and review.

## Target users / ICP roles

- **Visitor** — attendee or facilitator running or viewing a standup; may already own a project or create one in-session.
- **Facilitator / team lead** — expects minutes plus a durable, non-duplicated open-actions tail.
- **Downstream agents** — implement, test, and review against this document only.

## Scope

In scope:

- Generalise `pullStandupMinutesAct` (shared entry point; no parallel pull path).
- Collect **open** action items associated with the standup / visitor context.
- Append those items at the **end** of the minutes payload / document, after existing minutes content.
- Idempotency key: **title** (trimmed, case-sensitive match unless the existing implementation already normalises case — preserve current title equality).
- If the visitor **has** a project, or **creates** one during this act: create or sync **Canvas task objects** and **API tasks** for the placed open items.
- Re-entrancy: a second pull with the same open titles must not append duplicates and must not create duplicate Canvas or API tasks for those titles.
- Preserve existing minutes body, ordering of already-placed items, and current auth / visitor / project resolution behaviour except where this PRD requires change.

## Functional requirements

### FR1 — Generalised pull

`pullStandupMinutesAct` remains the single act that loads standup minutes. It must also resolve open action items and, when a project is present or created, task materialisation. Callers should not need a second act to get the open-actions tail.

### FR2 — Open action items at end

- Source: action items in **open** status for the standup / visitor context used by the act today (do not invent a new status model).
- Placement: append after the last existing minutes block / section. Do not insert into the middle of prior minutes.
- Each placed item exposes at least: title, and existing fields the minutes renderer already needs (assignee, due date, id if present).
- Closed, cancelled, or completed items are not placed.

### FR3 — Idempotent by title

- Before append, treat an item as already present if an item in the minutes tail (or the minutes document’s action-item list) has the **same title**.
- If present: do not append again; do not reorder existing items to “move to end.”
- Empty or whitespace-only titles are skipped (not placed, not used as idempotency keys).
- Multiple distinct open items with different titles all append, in a stable order (existing API / query order; if none, insertion order).

### FR4 — Project present or created

When the visitor **already has** a project, or **creates** a project as part of this act:

- For each open action item that is placed (or already present by title):
  - Ensure a **Canvas task object** exists on the project canvas (create if missing; reuse if a canvas task for that title already exists).
  - Ensure an **API task** exists for the project (create if missing; reuse if an API task for that title already exists on the project).
- Canvas object and API task must refer to the same logical item (shared id or stable link field already used in the product; do not create an unlinked pair).
- If the visitor has **no** project and does **not** create one: still append open items to minutes (FR2–FR3); do **not** create canvas or API tasks.

### FR5 — Create-project path

If the act’s existing create-project branch runs (visitor creates a project):

- Run minutes pull + open-item placement as above.
- After the project exists, run FR4 for all open items in that pull (including ones already in the minutes by title).
- Project creation failure must not leave duplicate minutes items; task creation is skipped if there is no project.

### FR6 — Failures and partial success

- Minutes pull failure: act fails as today; no partial append.
- Open-item fetch failure: minutes still return if they would have without this feature; open tail is omitted; no canvas/API task writes.
- Individual canvas or API task create failure: do not duplicate minutes items; remaining items still attempt create; surface the error in the act’s existing error channel (do not swallow).

## Acceptance criteria

1. Pulling minutes with N open action items and an empty tail appends those N items at the end, in stable order, titles preserved.
2. Pulling again with the same open titles does not append extra items (minutes tail length and titles unchanged).
3. An open item whose title already appears in the minutes is not appended again, even if its backend id differs.
4. Closed / completed items never appear in the auto-placed tail.
5. Whitespace-only titles are omitted.
6. Visitor **with** an existing project: each placed (or title-matched) open item has exactly one Canvas task object and one API task; repeat pull does not create extras.
7. Visitor who **creates** a project during the act: after success, same 1:1 canvas + API task guarantee as (6).
8. Visitor **without** a project and without creating one: minutes include the open-item tail; zero canvas objects and zero API tasks are created.
9. Canvas task and API task for the same title are linked (same logical task), not two unrelated records.
10. Existing minutes body above the tail is unchanged by this feature.
11. Act remains safe to retry (idempotent minutes tail + idempotent tasks by title when a project exists).

## Out of scope

- Renaming, merging, or editing action-item titles; title is the idempotency key only.
- Re-ordering or “move to end” of items already in the minutes.
- Auto-closing items, status transitions, or standup recap copy changes.
- Recurring standups, other meeting types, or a new minutes schema.
- Guest / logged-out visitors beyond current auth behaviour.
- Bulk import, CSV, or third-party task tools (Jira, Linear, etc.).
- UI redesign of the minutes canvas beyond rendering the appended tail and existing task objects.
- Backfill of historical minutes pulled before this change.
- Changing how projects are created except to hook FR4 after a successful create.
