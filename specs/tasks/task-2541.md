# PRD: Generalise `pullStandupMinutesAct` — auto-place open action items

## Problem & Goal

**Problem.** `pullStandupMinutesAct` only hydrates standup minutes in a narrow, minutes-centric path. Open action items are not appended to the minutes document, so follow-ups live in a separate list and are easy to miss. Re-running the act can duplicate items with the same title. Canvas task objects and API tasks are not created together when a visitor already has a project or creates one during the flow, so the board and the backend drift.

**Goal.** Generalise `pullStandupMinutesAct` so that:

1. Open action items are placed automatically at the **end** of the standup minutes.
2. Placement is **idempotent by title** (same title → no second item).
3. When the visitor has or creates a project, the act materialises **both** Canvas task objects and API tasks for those items.

Downstream agents should treat this PRD as the shared contract for implementation, tests, and review.

## Target users / ICP roles

- **Visitor** — attendee or facilitator running or viewing a standup; may already own a project or create one in-session.
- **Facilitator / team lead** — expects minutes plus a durable, non-duplicated open-actions tail.
- **Downstream agents** — implement, test, and review against this document only.

## Scope

In scope:

- Generalise `pullStandupMinutesAct` (shared entry point; no parallel pull path).
- Collect **open** action items associated with the standup / visitor context.
- Append those items at the **end** of the minutes payload / document, after existing minutes content.
- Idempotency key: **title** (trimmed, case-sensitive match unless the existing implementation already normalises case — preserve current title equality).
- If the visitor **has** a project, or **creates** one during this act: create or sync **Canvas task objects** and **API tasks** for the placed open items.
- Re-entrancy: a second pull with the same open titles must not append duplicates and must not create duplicate Canvas or API tasks for those titles.
- Preserve existing minutes body, ordering of already-placed items, and current auth / visitor / project resolution behaviour except where this PRD requires change.

## Functional requirements

### FR1 — Generalised pull

`pullStandupMinutesAct` remains the single act that loads standup minutes. It must also resolve open action items and, when a project is present or created, task materialisation. Callers should not need a second act to get the open-actions tail.

### FR2 — Open action items at end

- Source: action items in **open** status for the standup / visitor context used by the act today (do not invent a new status model).
- Placement: append after the last existing minutes block / section. Do not insert into the middle of prior minutes.
- Each placed item exposes at least: title, and existing fields the minutes renderer already needs (assignee, due date, id if present).
- Closed, cancelled, or completed items are not placed.

### FR3 — Idempotent by title

- Before append, treat an item as already present if an item in the minutes tail (or the minutes document’s action-item list) has the **same title**.
- If present: do not append again; do not reorder existing items to “move to end.”
- Empty or whitespace-only titles are skipped (not placed, not used as idempotency keys).
- Multiple distinct open items with different titles all append, in a stable order (existing API / query order; if none, insertion order).

### FR4 — Project present or created

When the visitor **already has** a project, or **creates** a project as part of this act:

- For each open action item that is placed (or already present by title):
  - Ensure a **Canvas task object** exists on the project canvas (create if missing; reuse if a canvas task for that title already exists).
  - Ensure an **API task** exists for the project (create if missing; reuse if an API task for that title already exists on the project).
- Canvas object and API task must refer to the same logical item (shared id or stable link field already used in the product; do not create an unlinked pair).
- If the visitor has **no** project and does **not** create one: still append open items to minutes (FR2–FR3); do **not** create canvas or API tasks.

### FR5 — Create-project path

If the act’s existing create-project branch runs (visitor creates a project):

- Run minutes pull + open-item placement as above.
- After the project exists, run FR4 for all open items in that pull (including ones already in the minutes by title).
- Project creation failure must not leave duplicate minutes items; task creation is skipped if there is no project.

### FR6 — Failures and partial success

- Minutes pull failure: act fails as today; no partial append.
- Open-item fetch failure: minutes still return if they would have without this feature; open tail is omitted; no canvas/API task writes.
- Individual canvas or API task create failure: do not duplicate minutes items; remaining items still attempt create; surface the error in the act’s existing error channel (do not swallow).

## Acceptance criteria

1. Pulling minutes with N open action items and an empty tail appends those N items at the end, in stable order, titles preserved.
2. Pulling again with the same open titles does not append extra items (minutes tail length and titles unchanged).
3. An open item whose title already appears in the minutes is not appended again, even if its backend id differs.
4. Closed / completed items never appear in the auto-placed tail.
5. Whitespace-only titles are omitted.
6. Visitor **with** an existing project: each placed (or title-matched) open item has exactly one Canvas task object and one API task; repeat pull does not create extras.
7. Visitor who **creates** a project during the act: after success, same 1:1 canvas + API task guarantee as (6).
8. Visitor **without** a project and without creating one: minutes include the open-item tail; zero canvas objects and zero API tasks are created.
9. Canvas task and API task for the same title are linked (same logical task), not two unrelated records.
10. Existing minutes body above the tail is unchanged by this feature.
11. Act remains safe to retry (idempotent minutes tail + idempotent tasks by title when a project exists).

## Out of scope

- Renaming, merging, or editing action-item titles; title is the idempotency key only.
- Re-ordering or “move to end” of items already in the minutes.
- Auto-closing items, status transitions, or standup recap copy changes.
- Recurring standups, other meeting types, or a new minutes schema.
- Guest / logged-out visitors beyond current auth behaviour.
- Bulk import, CSV, or third-party task tools (Jira, Linear, etc.).
- UI redesign of the minutes canvas beyond rendering the appended tail and existing task objects.
- Backfill of historical minutes pulled before this change.
- Changing how projects are created except to hook FR4 after a successful create.

### Actors and destinations

| Actor | Destination A (always) | Destination B (conditional) |
|---|---|---|
| Meeting facilitator / standup owner pulling minutes | That visitor’s **canvas** — task objects of the existing canvas `task` kind | That visitor’s **one** project task list, iff a project already exists or is created in this same invocation |
| Visitor with no project and none created | Canvas only | No API tasks |
| Other attendees / other advisors | Not written | Not written |

One visitor, one canvas, at most one project. No project picker UX. `stepStandupProject` (multi-project walk) is **out of scope**.

Project id, when needed, is `resolveStandupProject` (`chosen` > `scope` > `board` > `none`). An in-flow project create becomes `chosen` for the remainder of the same invocation. Explicit `chosen: null` (“no project”) is a real answer: skip API placement; do not fall back to scope/board.

### Title identity key

- Identity = existing `titleKey`: **trim + case-fold** (`toLowerCase`). No Unicode NFKC, no punctuation strip, no fuzzy match, no merge.
- **Product override of the BA “no case-fold” line:** FR3 already said preserve current title equality if the implementation normalises case. Live code does. A re-summarize that recapitalises an owner must not re-place the task. Case-sensitive matching is **rejected**.
- Stored title string remains `actionItemTitle(item)` (`Owner — task` when owner is present, else the task text). Canvas and API both use that string.
- Empty-after-trim titles are **not** placed and **not** counted as open items.
- Duplicate titles **inside one minutes document**: first occurrence in minutes order wins; later duplicates are treated as already seen (same as a second pull).
- Canvas and API check identity **independently**. Title T on canvas but missing on the project still creates the API task (and vice versa).
- Logical link between canvas object and API task for V1 = **same title identity** on the visitor’s canvas and the visitor’s one project. Do not invent a join table or new canvas kind. If an existing shared id / link field is already used in the product, reuse it; if none, title identity is sufficient for this ticket.

### Open vs closed

An item is **open** when `parseMeetingMinutes` does not mark it `done` (parser already maps done / completed / cancelled and synonyms). Closed items are never placed, never counted in N, and a later pull that marks a previously placed title closed **does not** delete or complete the canvas/API task (no two-way sync — see out of scope).

### R-1 — Act contract

1. Keep the caller-facing name `pullStandupMinutesAct` and the existing minutes-pull trigger (`standup` / `minutes`).
2. Side effects of this ticket are **additive**: pull minutes as today, **then** place open action items.
3. The runner contract stays `CardAct` / `CardActOutcome` (`notice` is mandatory). Do not invent a parallel act protocol. Structured counts required by this ticket:
   - `openTitles`: ordered unique open titles considered;
   - `canvas.created` / `canvas.skippedByTitle` (counts);
   - `api.created` / `api.skippedByTitle` (counts);
   - `api.skippedNoProject` (boolean or count) when Destination B did not run;
   - `api.projectId` when Destination B ran.
   Architect maps these onto `CardActOutcome` (notice interpolation + test-observable `add.nodes` / injected API calls are acceptable). Tests must be able to assert the counts without scraping copy.
4. Failure of one destination must not roll back the other. Minutes pull + canvas placement can succeed while API placement reports an error (and vice versa). Surface per-destination error in the payload / notice; do not throw away successful placements.

### R-2 — Open-item extraction

1. Parse pulled standup minutes with **`parseMeetingMinutes`**. Do not author a second parser.
2. Collect action items whose status is open (closed rule above). Preserve **minutes order**.
3. Deduplicate by title identity (above) **before** placement, so N in the acceptance criteria is the count of distinct open titles.

### R-3 — Canvas placement

1. Destination = the visitor’s current canvas document (the board the act is invoked from).
2. Existence check: among canvas objects of the **existing `task` kind**, compare title identity (`titleKey`). Do not invent a new canvas kind.
3. If no match: create a canvas task object and **append** it (do not reorder, restack, regroup, or change layout of **existing** objects). New-object spatial layout may keep the current beside-the-standup-card offset — “on end” means append-only in object order, **not** a rewrite of the minutes Markdown (R-10) and **not** a restack of the board.
4. If match: skip create (`canvas.skippedByTitle++`). Do not move the existing object to the end.
5. Closed items: no object. Empty open list: no objects, act still succeeds (existing `noticeStandupMinutesNone`).
6. Guest-safe: canvas placement must work for an anonymous / local visitor (local document). It must not require a tenant. **Implication:** the whole-act `accountRequired` gate cannot remain as-is, because `runCardAct` skips `run()` entirely when `persistence !== 'server'`. Split the gate: canvas runs locally; API writes stay project/session-gated.

### R-4 — API task placement (project already present)

1. If `resolveStandupProject` yields a non-null `projectId` **before** any in-flow create, that is Destination B. Inputs: standup card `projectId` as `chosen`, plus the board/scope project the runner already has. Explicit `chosen: null` skips API (R-6).
2. Existence check: among **that project’s** board tasks, compare title identity (task `title`, trimmed + case-fold). Do not match against other projects, marketplace jobs, or canvas titles.
3. If no match: create an API task with that title, appended at the end of the project’s task list (the tasks API’s existing append semantics — no custom rank rewrite).
4. If match: skip create (`api.skippedByTitle++`). Do not reopen, retitle, reassign, or restack the existing task.
5. New API tasks carry only the title required for identity. Do not invent assignee, due date, description, or status sync from the minutes on this ticket.

### R-5 — API task placement (project created in-flow)

1. If the visitor creates a project as part of this act (or immediately before placement in the **same invocation**), Destination B is **that** new project id.
2. Apply R-4 against it. Idempotency still holds if the same invocation somehow places twice.
3. Do **not** mint a guest/claim project here. That is **#2543**. If no project exists and none is created by an already-shipping create-project flow, fall through to R-6. This act does not grow a create-project UI.

### R-6 — No project

1. If project id is null (including explicit `chosen: null`) and no in-flow create happened, skip all API writes. `api.created = 0`, `api.skippedNoProject` set.
2. Canvas placement (R-3) still runs. The act succeeds.

### R-7 — Idempotency (both destinations)

1. Re-running the act on unchanged open titles is a no-op for those titles on each destination that already has them.
2. A second pull after the user **deleted** a previously placed canvas/API item **may** recreate it (existence is live state, not a placement ledger). Do not add a “already placed” store on this ticket.
3. Concurrent double-pull: best-effort. Prefer an existing unique title constraint if one exists; do not add a new unique index solely for this act unless the architect requires it. Duplicate-on-race is a known residual, not a blocker for V1.

### R-8 — Append-only / end placement

1. New canvas task objects are always after existing canvas task objects, in minutes order of the **newly created** titles.
2. New API tasks are always after existing project tasks, in the same minutes order of newly created titles.
3. Insertion in the middle, reshuffle, or restack of existing objects is forbidden. Placing **new** canvas tasks beside the standup card (current layout) is allowed; that is not a restack.

### R-9 — Closed, cancelled, completed

Never placed on canvas or API. A title that is open on pull 1 and closed on pull 2 is not deleted from either destination.

### R-10 — Preserve existing minutes-pull

Authoring, storage, summarisation, and the three-section Markdown contract of standup minutes are unchanged. This ticket only **reads** open action items after the pull. Do not append action items into the minutes Markdown.

### R-11 — Confidentiality and tenancy

1. Do not write another advisor’s or another visitor’s canvas/project.
2. Visitor tokens must not list or place against other advisors’ meetings (parent epic test).
3. Action titles inherit the meeting’s confidentiality: do not publish them to `publicMedia` / `guest` / `share` / `aiContext` as a side effect of placement. Canvas objects on the visitor’s **own** board are the visitor’s document; API tasks are the visitor’s project. Mentoring-restricted threads stay restricted (PRD 26 FR-7) — this act does not copy titles into a public listing.

### R-12 — Errors and empty input

| Input | Canvas | API | Act result |
|---|---|---|---|
| Minutes with N distinct open titles, empty destinations | N created, appended | N created if project; else skippedNoProject | success |
| Same titles, second pull | 0 created, N skippedByTitle | 0 created, N skippedByTitle (if project) | success |
| Empty open-action list | 0 | 0 | success (minutes still pulled) |
| Unparseable minutes | 0, error noted | 0 | minutes-pull error; no partial invented titles |
| API create fails mid-list | already-created canvas kept | already-created API tasks kept; remaining titles reported failed | partial success, not a full rollback |
| Local / guest board, no project | N created (R-3) | skippedNoProject | success |
| No `meetingId` on the standup card | 0 (existing needs-meeting notice) | 0 | success, no invented titles |

- No status, assignee, due, or description sync after initial place.
- No delete when a title disappears from later minutes.
- No reorder / layout / grouping of **existing** canvas objects.
- No multi-project picker; no `stepStandupProject` loop.
- No notifications, mentions, or third-party task backends.
- No follow-up booking (#2542).
- No guest-project mint / claim link (#2543).
- No new canvas object kind, no new listing kind, no `/advisors` page, no SCORE clone.

- Do not mutate standup minutes Markdown to append an “open actions” section.
