# PRD: Empty ICP Is Never a Gate

## Problem & Goal

**Problem.** Downstream workflows treat a missing or empty Ideal Customer Profile (ICP) as incomplete state. That turns ICP into an implicit hard gate: scoring, routing, generation, enrichment, outreach, and agent handoffs stall or fail closed even when every other required input is present.

**Goal.** Empty ICP is a valid, first-class state meaning “unconstrained / unknown,” not “blocked.” No user journey, agent pipeline, or API contract may refuse, hide, or delay work solely because ICP is absent, blank, or unset. When ICP is present it may still *narrow* behavior; when it is empty it must *not stop* behavior.

## Target users / ICP roles

- **Revenue / GTM operators** who run accounts, leads, and campaigns without a fully specified ICP.
- **Product and growth teams** configuring qualification, routing, and content systems.
- **Downstream agents** (scoring, research, copy, outreach, CRM sync) that consume shared task context.
- **Admins / architects** who define ICP schemas but must not make ICP a prerequisite for core flows.

Empty ICP on the *operator* is also not a gate for this work: the rule applies even when no ICP roles are defined yet.

## Scope

In scope:

- Definition of empty ICP (null, `{}`, whitespace-only strings, empty lists, all-optional fields unset).
- Read/write paths that currently require, validate, or short-circuit on ICP.
- UX, API, job, and agent-orchestration behavior when ICP is empty vs. populated.
- Precedence: empty ICP must not override *other* explicit gates (auth, entitlements, required non-ICP inputs, safety policy).
- Telemetry that distinguishes “ICP unused” from “ICP blocked the run.”

## Functional requirements

1. **Empty is valid.** The system MUST accept and persist records, tasks, and runs with no ICP. Empty MUST NOT fail schema validation, form submit, or job enqueue by itself.
2. **No hard stop.** Any flow that today returns 4xx, shows a blocking modal, disables a primary CTA, skips a queue, or aborts an agent because ICP is missing MUST proceed with unconstrained / default-all behavior.
3. **Narrow, don’t block.** If ICP is populated, it MAY filter, score, or tailor output. If ICP is empty, filters MUST be treated as pass-through (no implicit exclude-all).
4. **Shared contract.** All downstream agents MUST read ICP as optional. A missing key is equivalent to “no constraints,” not “wait for human” and not “error.”
5. **Defaults, not refusals.** Copy, research, scoring, and routing MUST use product-wide defaults or all-eligible populations when ICP is empty. They MUST NOT invent a fake ICP or refuse to generate.
6. **Partial ICP.** A partially filled ICP constrains only the fields that are set. Unset fields MUST NOT be treated as failed gates.
7. **Idempotent continue.** Filling ICP later MAY refine subsequent runs; it MUST NOT be required to complete or retry an already-started run that began with empty ICP.
8. **Observability.** Emit a non-error signal (`icp_state: empty | partial | complete`) on every run. Blocking because of ICP MUST be impossible; if a run fails, the cause MUST be something other than empty ICP.
9. **Config cannot re-gate.** Admin flags, required-field toggles, and playbooks MUST NOT be able to mark ICP as a blocking prerequisite for core task execution. Optional *warnings* are allowed; hard gates are not.
10. **Back-compat.** Existing populated-ICP behavior is unchanged. Migration MUST convert prior “ICP required” checks into optional constraints.

## Acceptance criteria

- Submitting, saving, or running with ICP `null`, `{}`, `""`, or `[]` succeeds (2xx / terminal success) when other non-ICP requirements are met.
- Primary CTAs and agent entrypoints remain enabled with empty ICP; no tooltip, modal, or banner blocks the action (informational empty-state copy is OK).
- Scoring / routing with empty ICP returns the unconstrained candidate set, not an empty set and not an error.
- Generation / research / outreach agents produce usable output with empty ICP; they do not wait, no-op, or throw `ICP_REQUIRED`.
- Partial ICP applies only set fields; unset fields do not fail the run.
- Automated tests cover empty, whitespace, `{}`, partial, and full ICP; the empty cases assert success, not skip.
- Logs/metrics never increment a “blocked_on_icp” (or equivalent) counter; such a code path does not exist.
- An admin cannot configure ICP as a required gate for the in-scope flows.
- A run started with empty ICP can complete; adding ICP afterward does not invalidate that run.

## Out of scope

- Designing or changing the ICP schema, taxonomy, or scoring model itself.
- Requiring users to *create* an ICP, ICP onboarding UX, or ICP quality scoring.
- Using ICP as a *soft* relevance ranker (allowed) versus a hard eligibility gate (forbidden) — ranking changes are not required by this PRD.
- Non-ICP blockers: auth, billing, rate limits, PII/safety policy, and genuinely required business fields other than ICP.
- Backfill of historical empty-ICP records beyond making new and in-flight runs ungated.
- Third-party systems outside this product’s write path.
