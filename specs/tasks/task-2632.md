# PRD: Empty ICP Is Never a Gate

**Status:** WIP  
**Owner:** Product Architecture  
**Priority:** P0 — cross-cutting invariant

## Problem & Goal

ICP (Ideal Customer Profile) is used to qualify, route, score, personalize, and sometimes restrict. When ICP is unset, empty, incomplete, or not yet configured, systems often treat “no ICP” as “no match” and fail closed: they block onboarding, hide inventory, stall deals, deny entitlements, or halt workflows.

That behavior is wrong. An empty ICP is missing configuration, not a negative decision. Fail-closed empty-ICP gates create false negatives, setup dead-ends, and lost conversion—especially for new workspaces, first-run users, and teams that have not defined ICP yet.

**Goal:** Empty ICP is never a gate. Absence, emptiness, or incompleteness of ICP must fail open. ICP may only restrict, score-down, or block when it is explicitly defined **and** a negative match is evaluated against that definition. Downstream agents must treat this as a hard invariant, not a preference.

## Target users / ICP roles

ICP roles are documented for design context. They are **not** a prerequisite for shipping, using, or accepting this work. Empty ICP does not block this PRD, implementation, QA, or rollout.

| Role | Why they care |
| --- | --- |
| End user / buyer in-product | Must complete core jobs even if the workspace has no ICP |
| Admin / GTM operator | Must be able to leave ICP blank during setup without locking the product |
| Sales / CS / RevOps | Must progress accounts, deals, and routing when ICP is not configured |
| Growth / onboarding | First-run and empty-state paths must not dead-end on ICP |
| Downstream agents (eng, QA, docs) | Must implement fail-open behavior everywhere ICP is consulted |

If ICP is empty, proceed as if no ICP gate exists.

## Scope

In scope: every product surface, service, job, and agent path that reads ICP to decide whether a user, account, workspace, lead, deal, feature, flow, or resource may proceed.

Includes:

- Workspace and account setup, first-run, and empty states
- Qualification, scoring, routing, and stage progression
- Entitlements, feature flags, paywalls, and pack visibility that consult ICP
- Search, ranking, recommendations, and personalization that consult ICP
- APIs, batch jobs, webhooks, and agent tools that consult ICP
- Validation, required-field, and “complete your profile” gates that consult ICP
- Defaulting, inheritance, and multi-entity ICP (user, account, workspace, org)

## Functional requirements

1. **Fail open on empty.** If ICP is null, missing, `{}`, `[]`, blank strings, or otherwise has no usable definition, do not gate. Allow the action, resource, or transition.
2. **Empty ≠ no-match.** Do not coerce empty ICP into a failed match, zero score that blocks, or implicit “not ICP.” No-match is only valid against a defined ICP.
3. **Defined ICP may gate.** When ICP is explicitly defined and complete enough to evaluate, negative match may score, deprioritize, or block per existing product rules.
4. **Incomplete defined ICP fails open.** If a definition exists but required dimensions are missing such that a match cannot be evaluated, treat as empty ICP (fail open). Do not block on partial config.
5. **No required-ICP checkpoints.** ICP must not be a required field, blocking checklist item, or hard stop in onboarding, checkout, deal create, invite, or publish flows.
6. **Warnings are allowed; blocks are not.** Empty ICP may surface non-blocking hints (“Define ICP to improve ranking”) that are dismissible and never prevent submit, continue, or save.
7. **Inheritance still fail-open.** If child entities inherit ICP and the resolved value is empty, fail open. Do not walk the tree until a block is found.
8. **All consumers honor the invariant.** UI, API, jobs, flags, and agents must use the same emptiness rules. No client-only bypass and no server-only block.
9. **Observability without punishment.** Log empty-ICP fail-open events for ops. Do not use those events to auto-disable features or auto-fail qualification.
10. **Idempotent and reversible.** Defining or clearing ICP must not strand in-flight work. Clearing ICP re-opens any gate that depended on it.

## Acceptance criteria

- Given ICP is unset or empty, when a user starts or continues any in-scope flow, then the flow completes without an ICP error, blocker, or dead-end.
- Given ICP is `null`, `{}`, `[]`, or whitespace-only, when match/score/entitle is evaluated, then the result is pass / allow / unscored-not-blocked—not deny.
- Given ICP is partially defined and cannot be evaluated, when a gate is consulted, then the gate is open.
- Given ICP is fully defined and the entity does not match, when a gate is consulted, then existing negative-match behavior applies (this PRD does not remove defined-ICP gates).
- Given onboarding, deal create, invite, or publish with empty ICP, when the user submits, then the request succeeds and ICP is not in the required-field set.
- Given a non-blocking empty-ICP hint, when the user dismisses or ignores it, then they can still complete the job.
- Given API and UI for the same action with empty ICP, when both are called, then both allow.
- Given ICP is later defined or cleared, when in-flight records are re-evaluated, then they are not stuck behind a stale empty-ICP block.
- Automated tests cover empty, null, partial, and defined-negative ICP for each gate. A gate with no empty-ICP test is not done.
- QA can complete a full happy path on a workspace that has never had ICP configured.

## Out of scope

- Designing or changing the ICP data model, taxonomy, or scoring weights
- Forcing workspaces to create an ICP
- Changing pricing, packaging, or authz that does not consult ICP
- Replacing defined-ICP negative-match rules (only empty/partial ICP is forced fail-open)
- Marketing site, CRM hygiene, or offline ICP workshops
- Backfill of historical “blocked for empty ICP” records (call out separately if needed; do not block this invariant on backfill)

### R-1 — Emptiness (operational)

ICP is **empty** (no usable definition) when any of the following is true. Treat all of them as the same fail-open state.

1. **Unset:** `null`, `undefined`, key omitted from intake / payload / tool args.
2. **Empty container:** `{}`, `[]`.
3. **Blank scalar:** `""`, whitespace-only string.
4. **Unusable identifier:** a string/id that does not resolve to an ICP record (unknown id, dangling ref, placeholder / dummy id).
5. **Unusable record:** a resolved object with no evaluable dimension (no industry / segment / persona / firmographics / other matchable field the product actually uses). A record that is only `{ id }` with no definition is empty.

**Empty ICP means: proceed as if no ICP gate exists.** Do not coerce it to “no-match,” `0` fit that blocks, `ICP_REQUIRED`, a disabled primary CTA, a 4xx, a blocked checklist item, or a refused `campaign.create`.

A helper that answers “is this ICP usable enough to evaluate?” belongs in the **shared contract package** (`packages/creation-canvas-contract`) so UI, C1 `guidedCampaignRun`, `campaign.create`, and cloud-agent draft use **one** spelling (R-11). Architect names the export in Design. This ticket does not change the ICP data model or taxonomy (PM out of scope).

---

### R-2 — Empty ≠ no-match; never invent a dummy ICP

- **No-match** is only valid against a **defined, evaluable** ICP (R-1 false). Empty must not be scored as 0-and-block, “not ICP,” or exclude-all.
- Unscored-not-blocked is the empty result: pass / allow / omit the ICP signal. Do **not** print a confident `0%` ICP fit that then disables send or draft (same fail-closed display bug C1 refused for other scores).
- **Never mint a dummy ICP** (`icp_default`, `unspecified`, workspace-placeholder row, fake id) to satisfy a required-field or to make a matcher run. Absence stays absence.
- Partial set-fields constrain only those fields **for ranking / copy** (C2). Unset fields are not failed gates (R-6).

---

### R-3 — ICP is not a C1 checklist, `maySend`, or `sendReadiness` conjunct

Restates and tightens C1 R-5 for this child:

- `intake.icp` is optional on `GuidedCampaignIntake`.
- ICP is **not** in C1 `CHECKLIST_IDS`. `checklist.ready` / `nextRequired` / `primaryCta` **ignore** ICP emptiness.
- `maySend` conjuncts stay exactly C1 R-4 (`checklist.ready` ∧ `sendReadiness.ready` ∧ `confirm.blocked === false`). ICP is not a fourth conjunct, including when defined.
- `SendBlocker` must **not** gain an `noIcp` / `icpMismatch` / `icpIncomplete` member. `sendReadiness(...)` must **not** grow an `icp` input that can push `ready: false`.
- A workspace that has **never** had an ICP row must still be able to reach C1 `copy` / `confirm` and, when the real send conjuncts hold, `maySend === true`.

### R-4 — `campaign.create` and canvas campaign draft fail-open

The ticket names `campaign.create` as a consumer. Contract:

- Cloud-agent `campaign.create` (draft-only allowlist) **must accept** omitted / null / `{}` / blank ICP and return a draft (non-4xx for the ICP reason). Other existing validation (audience, auth, billing) is unchanged.
- Canvas `canvas_add_object` / campaign-kind draft that C1 copy uses **must not** require `intake.icp` or an `ri_icps` id.
- Mapping C1 intake → `campaign.create` (or equivalent Growth draft) **omits** ICP when empty; it does not substitute a dummy (R-2).
- UI and API for the same draft action both allow (PM AC). No client-only bypass and no server-only ICP block (R-11).

---

### R-5 — C0 CAMPAIGN prompt: ask ≠ gate; do not re-author C0

Current C0 text already fail-opens: missing business / vertical / who-it-is-for → one-sentence ask **and still author**.

- That one-sentence ask is the **allowed hint** (R-9 / PM FR-6). It must remain dismissible by continuing; it must not refuse the turn, skip authoring, or wait-for-human.
- “Who it is for” may be satisfied by **free text or a consent audience**. It does **not** require a `ri_icps` row. Do not teach the model that missing `ri_icps` means “cannot draft.”
- **Do not re-author** `frontend/src/lib/canvasAiSystemPrompt.ts` on this ticket unless Design proves the live prompt **refuses** on empty ICP (regression vs current “still author”). C1 R-12 already forbade a C0 rewrite; this child does not reopen it.
- Do not “fix” the ask by adding ICP to the C1 checklist.

---

### R-6 — Incomplete / partial ICP fails open

If a value exists but a match **cannot be evaluated** (missing required dimensions, unresolved id, schema present with all matchable fields blank), treat as **empty** (R-1). Fail open. Do not block on partial config.

Partial ICP **may** tailor copy on the dimensions that **are** set (C2). It **must not** fail checklist, draft, or send because other dimensions are unset.

---

### R-7 — Defined ICP may personalize; it must not send-gate this journey

When ICP is explicitly defined **and** complete enough to evaluate:

- **Allowed:** C2 ranking / prefill / copy targeting; non-blocking “this is off-ICP” hint; optional display of fit.
- **Forbidden on this journey:** using defined-negative match to set `checklist.ready === false`, `maySend === false`, `sendReadiness.ready === false`, refuse `campaign.create`, or block C1 copy / confirm.
- This PRD does **not** remove defined-ICP behavior in unrelated RI scoring if that product exists; it **does** forbid wiring that behavior into C1 send/draft gates.
- Clearing ICP later must re-open any hint and must not strand in-flight campaigns behind a stale block (R-12).

---

### R-8 — No required-ICP checkpoints; C2 picker is never a start-gate

ICP must not be a required field, blocking checklist item, or hard stop in:

- C1 onboarding-to-campaign / first-run empty workspace
- C1 copy / confirm / send
- `campaign.create` / canvas campaign publish-as-draft
- C2 picker (optional control; empty selection is valid)
- Invite / share of a campaign board (out of C1 but: do not add ICP as required if that path is touched)

C2 may ship after this ticket. **This ticket does not wait on C2** and C2 must not wait on a required ICP. Prefill from brand kit / workspace profile is allowed; if the resolved inherited value is empty, fail open (R-10). Do not walk a parent tree until a block is found.

---

### R-9 — Warnings allowed; blocks not

Empty ICP **may** surface a non-blocking hint, for example:

- C0: one-sentence ask for who it is for
- C2: “Define ICP to improve targeting”
- Copy card: dismissible note

Hints are dismissible / ignorable and **never** prevent submit, continue, save, draft, or send. No blocking modal, no disabled primary CTA whose only reason is empty ICP, no `ICP_REQUIRED` error code.

---

### R-10 — Inheritance / prefill still fail-open

C2 may prefill `intake.icp` from a brand kit or workspace profile when one exists.

- If the child has no ICP and the parent/profile is empty → fail open (no gate).
- If the child has no ICP and the parent has a usable ICP → optional prefill; user may clear it; clearing returns to empty (fail open), not to “required.”
- Do not iterate ancestors looking for a reason to block.

---

### R-11 — One emptiness rule for every campaign-journey consumer

UI (C2 picker), C1 contract (`guidedCampaignRun` / intake), Growth `campaign.create`, canvas campaign draft, and the C0 prompt interpretation **must use R-1**. No client-only skip and no server-only ICP 4xx.

Architect delivers the shared helper + the consumer list. Developer wires C1 (when present) and `campaign.create` to it. A consumer that cannot import the helper must still implement R-1 byte-for-byte (same empty cases).

**Observability without punishment:** logging `icp_state: empty | partial | complete` (or equivalent) on draft/send is allowed. Those events must **not** auto-disable features, auto-fail qualification, increment a `blocked_on_icp` counter that drives a gate, or page as an error. Empty-ICP fail-open is expected first-run behavior, not an incident.

---

### R-12 — Tests, reversibility, ownership, and what this ticket does not do

**Reversibility.** Defining or clearing ICP must not strand in-flight C1 runs or campaign drafts. A run that started with empty ICP can complete without ICP. Adding ICP later may refine **subsequent** copy; it does not invalidate the in-flight run. Clearing ICP removes any defined-ICP hint and must not leave `maySend === false` for an ICP reason.

**Automated tests (a gate with no empty-ICP test is not done).** Cover at least:

| # | Input | Assert |
| --- | --- | --- |
| T1 | ICP `null` / omitted | `campaign.create` draft succeeds (no ICP error); C1 `checklist.ready` / `maySend` ignore ICP |
| T2 | `{}`, `[]`, `""`, whitespace | same as T1 |
| T3 | Unresolved / dummy id | treated as empty (R-1.4); no dummy persisted as a real ICP |
| T4 | Partial record, not evaluable | fail open (R-6) |
| T5 | Defined ICP, negative match | C1 checklist / `maySend` / `sendReadiness` still not gated by ICP (R-7) |
| T6 | `sendReadiness` | `SendBlocker` union unchanged; no `icp` input |
| T7 | C0 path | empty who-it-is-for still authors (if a prompt/contract test exists; do not add a C0 rewrite to make this true) |
| T8 | UI + API same draft action | both allow with empty ICP |

QA: a workspace that has **never** had ICP configured can complete the C1 happy path through copy (and through confirm/send when the **real** send conjuncts hold).
