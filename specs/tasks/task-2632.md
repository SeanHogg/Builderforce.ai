# PRD: Empty ICP Is Never a Gate

**Status:** WIP  
**Owner:** Product Architecture  
**Priority:** P0 — cross-cutting invariant

## Problem & Goal

ICP (Ideal Customer Profile) is used to qualify, route, score, personalize, and sometimes restrict. When ICP is unset, empty, incomplete, or not yet configured, systems often treat “no ICP” as “no match” and fail closed: they block onboarding, hide inventory, stall deals, deny entitlements, or halt workflows.

That behavior is wrong. An empty ICP is missing configuration, not a negative decision. Fail-closed empty-ICP gates create false negatives, setup dead-ends, and lost conversion—especially for new workspaces, first-run users, and teams that have not defined ICP yet.

**Goal:** Empty ICP is never a gate. Absence, emptiness, or incompleteness of ICP must fail open. ICP may only restrict, score-down, or block when it is explicitly defined **and** a negative match is evaluated against that definition. Downstream agents must treat this as a hard invariant, not a preference.

## Target users / ICP roles

ICP roles are documented for design context. They are **not** a prerequisite for shipping, using, or accepting this work. Empty ICP does not block this PRD, implementation, QA, or rollout.

| Role | Why they care |
| --- | --- |
| End user / buyer in-product | Must complete core jobs even if the workspace has no ICP |
| Admin / GTM operator | Must be able to leave ICP blank during setup without locking the product |
| Sales / CS / RevOps | Must progress accounts, deals, and routing when ICP is not configured |
| Growth / onboarding | First-run and empty-state paths must not dead-end on ICP |
| Downstream agents (eng, QA, docs) | Must implement fail-open behavior everywhere ICP is consulted |

If ICP is empty, proceed as if no ICP gate exists.

## Scope

In scope: every product surface, service, job, and agent path that reads ICP to decide whether a user, account, workspace, lead, deal, feature, flow, or resource may proceed.

Includes:

- Workspace and account setup, first-run, and empty states
- Qualification, scoring, routing, and stage progression
- Entitlements, feature flags, paywalls, and pack visibility that consult ICP
- Search, ranking, recommendations, and personalization that consult ICP
- APIs, batch jobs, webhooks, and agent tools that consult ICP
- Validation, required-field, and “complete your profile” gates that consult ICP
- Defaulting, inheritance, and multi-entity ICP (user, account, workspace, org)

## Functional requirements

1. **Fail open on empty.** If ICP is null, missing, `{}`, `[]`, blank strings, or otherwise has no usable definition, do not gate. Allow the action, resource, or transition.
2. **Empty ≠ no-match.** Do not coerce empty ICP into a failed match, zero score that blocks, or implicit “not ICP.” No-match is only valid against a defined ICP.
3. **Defined ICP may gate.** When ICP is explicitly defined and complete enough to evaluate, negative match may score, deprioritize, or block per existing product rules.
4. **Incomplete defined ICP fails open.** If a definition exists but required dimensions are missing such that a match cannot be evaluated, treat as empty ICP (fail open). Do not block on partial config.
5. **No required-ICP checkpoints.** ICP must not be a required field, blocking checklist item, or hard stop in onboarding, checkout, deal create, invite, or publish flows.
6. **Warnings are allowed; blocks are not.** Empty ICP may surface non-blocking hints (“Define ICP to improve ranking”) that are dismissible and never prevent submit, continue, or save.
7. **Inheritance still fail-open.** If child entities inherit ICP and the resolved value is empty, fail open. Do not walk the tree until a block is found.
8. **All consumers honor the invariant.** UI, API, jobs, flags, and agents must use the same emptiness rules. No client-only bypass and no server-only block.
9. **Observability without punishment.** Log empty-ICP fail-open events for ops. Do not use those events to auto-disable features or auto-fail qualification.
10. **Idempotent and reversible.** Defining or clearing ICP must not strand in-flight work. Clearing ICP re-opens any gate that depended on it.

## Acceptance criteria

- Given ICP is unset or empty, when a user starts or continues any in-scope flow, then the flow completes without an ICP error, blocker, or dead-end.
- Given ICP is `null`, `{}`, `[]`, or whitespace-only, when match/score/entitle is evaluated, then the result is pass / allow / unscored-not-blocked—not deny.
- Given ICP is partially defined and cannot be evaluated, when a gate is consulted, then the gate is open.
- Given ICP is fully defined and the entity does not match, when a gate is consulted, then existing negative-match behavior applies (this PRD does not remove defined-ICP gates).
- Given onboarding, deal create, invite, or publish with empty ICP, when the user submits, then the request succeeds and ICP is not in the required-field set.
- Given a non-blocking empty-ICP hint, when the user dismisses or ignores it, then they can still complete the job.
- Given API and UI for the same action with empty ICP, when both are called, then both allow.
- Given ICP is later defined or cleared, when in-flight records are re-evaluated, then they are not stuck behind a stale empty-ICP block.
- Automated tests cover empty, null, partial, and defined-negative ICP for each gate. A gate with no empty-ICP test is not done.
- QA can complete a full happy path on a workspace that has never had ICP configured.

## Out of scope

- Designing or changing the ICP data model, taxonomy, or scoring weights
- Forcing workspaces to create an ICP
- Changing pricing, packaging, or authz that does not consult ICP
- Replacing defined-ICP negative-match rules (only empty/partial ICP is forced fail-open)
- Marketing site, CRM hygiene, or offline ICP workshops
- Backfill of historical “blocked for empty ICP” records (call out separately if needed; do not block this invariant on backfill)
