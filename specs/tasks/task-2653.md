# Product Requirements Document (PRD)

## Problem & Goal

### Problem
The `builderforce/task-2629` branch cannot be checked out by agent runs, resulting in the following issues:
- All repository tools (git, list_files, read_file, write_file, run_command) return "no repository bound to this task."
- Architect exec #31989 and Developer exec #32029 failed with a GitHub 403 error for user ID 15883045.
- C1 code is drafted but cannot be written until the binding issue is resolved.

### Goal
Resolve the repository binding issue to allow successful checkout of the `builderforce/task-2629` branch and enable the execution of C1 code.

- **Repository Administrators**: Users who manage repository access and permissions on GitHub.

## Requirements

## Diagnosis (root cause)

The "no repository bound to this task" message is **MISLEADING**. The repository IS bound — `list_files` and `read_file` both work. The actual fault is a **GitHub API rate limit** (403 "rate limit exceeded for user ID 15883045") that hits the Search API first (30 req/min), while the Tree/Contents APIs survive longer.

**Evidence (collected 2026-09-16 on #2653 run):**
- `list_files("packages/creation-canvas-contract/src")` → succeeds, 47 files listed
- `read_file("packages/creation-canvas-contract/src/marketing.ts")` → succeeds, 371 lines
- `read_file("frontend/src/lib/canvasMarketing.ts")` → succeeds, 112 lines
- `search_code("campaignSendReadiness")` → **403 "rate limit exceeded for user ID 15883045"**

The container executor surfaced the 403 as "no repository bound to this task" which caused architect exec #31989 and developer exec #32029 to misdiagnose as a binding failure and waive/request-changes respectively.

## Requirements

### R-1: Rate Limit Diagnosis
The system shall distinguish between "repository not bound" and "GitHub API rate limit exceeded". The container executor must surface the actual HTTP 403 with the rate-limit message rather than translating it to "no repository bound."

### R-2: Rate Limit Recovery
When a GitHub 403 rate limit is encountered, the executor shall:
- Wait and retry (the limit resets per-minute for Search API)
- Fall back to Tree/Contents APIs (higher limits) for file discovery before failing
- Never surface a rate limit as a binding failure

### R-3: Search API Alternatives
When `search_code` (GitHub Search API, 30 req/min) is rate-limited, the executor shall use `list_files` with glob patterns as a fallback for file discovery. This was proven viable: `list_files` succeeded while `search_code` 403'd in the same run.

### R-4: C1 Deliverable Completion
Once the rate-limit issue is mitigated (wait for reset, or use Tree API fallback), the C1 files for #2629 shall be written:
- `packages/creation-canvas-contract/src/guidedCampaign.ts` — the guided campaign contract
- `packages/creation-canvas-contract/src/guidedCampaign.test.ts` — test vectors
- `packages/creation-canvas-contract/src/index.ts` — barrel re-export (one line)
- `frontend/src/lib/canvasMarketing.ts` — thin adapter (extend existing file)

### R-5: No Binding Change Required
The repository binding (`githubRepoUrl`, `githubRepoOwner`, `githubRepoName` on project 11) shall NOT be modified. These fields are null because they are operator-only (ticket #2600), and the binding already works correctly via tenant-level fallback. The fault is rate-limit, not binding.

### R-6: Operator Documentation
Document that the shared PAT (user ID 15883045) is rate-limited at GitHub's Search API tier (30 req/min authenticated). A project operator may:
- Rotate the PAT to a fresh rate-limit bucket
- Request a higher rate limit from GitHub Support
- Add a second PAT for round-robin usage
