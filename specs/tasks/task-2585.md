# WIP PRD: Location on Profile and Optional Filter

## Problem & Goal

Profiles have no location, so people cannot signal where they are based and discovery cannot be narrowed by place. Results feel less relevant and nearby matches are hard to find.

**Goal:** Let a user add one optional location to their profile, show it on the profile, and let others optionally filter browse/search by that location. Location is never required to create, complete, or find a profile.

## Target users / ICP roles

- Profile owners who want to show a city or region
- People browsing or searching who want an optional place constraint
- Trust & safety / moderation, who need locations to be structured and not free-form spam

## Scope

**In scope**

- One primary location on the profile (city + country; region/state when the place dataset provides it)
- Add, change, and clear location from profile edit
- Show location on the profile when set; omit it when unset
- Optional location filter on primary browse and search surfaces
- Place typeahead against a standard place dataset
- Index/update so profile location is filterable after save

## Functional requirements

1. A profile owner can set, change, or remove a single primary location from profile edit. Location is optional.
2. Location is stored as a structured place: display name, city, region/state when available, country, and stable place id. Free-text-only locations are not accepted.
3. Typeahead suggests places after 2+ characters. Save requires a selected suggestion (valid place id). Unknown or malformed place ids are rejected.
4. Profile view shows the location display name only when a location is set. No location row, placeholder, or “unknown” label when unset.
5. Browse and search expose an optional location filter. Default is no location constraint (same result set as today).
6. Applying a filter returns profiles whose stored place matches the selected place. Matching is by place id; a city filter does not include the entire country. Unset locations never match an active location filter.
7. Clearing the filter, or loading browse/search with no location parameter, returns the unfiltered set. Location combines with existing filters and sorts; it does not replace them.
8. Location changes appear on the profile and in filterable results after save without a full account rewrite.
9. Profile visibility rules still apply. Location is not shown to viewers who cannot see the profile, and filtered results do not leak hidden profiles.

## Acceptance criteria

- User sets a suggested place, sees it on their profile, changes it to another place, then clears it; the profile no longer shows location.
- Profiles with no location remain valid, appear in unfiltered browse/search, and are excluded when a location filter is applied.
- Filter by a city returns only profiles stored with that place id; clearing the filter restores prior unfiltered results.
- Saving without selecting a suggestion fails validation and does not write a location.
- Invalid place ids do not persist and do not 500 browse/search.
- Location filter is visible and optional on main browse/search (desktop and mobile) and does not block using other filters.
- A profile with location hidden by existing visibility rules does not appear in location-filtered results for unauthorized viewers.

## Out of scope

- Multiple locations, location history, or “open to relocate”
- GPS, live location, coordinates, radius / “near me”, or map UI
- Street address, postal code, or precise pinning
- Mandatory location at signup or profile completion
- Location-based notifications, ranking boosts, or feed injection
- Admin bulk backfill
- Custom place-name translations beyond the place dataset
- Distance sort as a separate control (unless already provided by an existing sort)

## Requirements

Location is one optional structured place on the existing talent row (`freelancer_profiles`), shown on the public profile when set, and used as an optional exact-place filter on `/marketplace?category=advisors`. It is **not** a new listing kind, **not** a `/advisors` route, and **not** a second location field.

### D-1 — Place dataset: GeoNames (geonames.org)

The canonical place dataset is **GeoNames** (`geonames.org`), specifically the `cities5000` dump (all cities with population ≥ 15,000). Rationale:

- **Stable, numeric place id.** Every GeoNames entry carries a unique `geonameId` (integer). These ids are persistent across releases — a city renamed or re-parented keeps the same id. This satisfies R-2/R-4 (exact place-id match).
- **Free, no API key.** The data export is CC-BY licensed and downloadable as a single tab-separated file. No runtime API call, no rate limit, no billing.
- **City / region / country from one source.** Each row has `name` (city), `admin1` (region/state), `country` (ISO-3166 country name), and `asciiname` (ASCII display name). Altogether these give us the structured fields P1 requires.
- **Typeahead-capable.** The `cities5000` subset (~50k rows worldwide) is small enough to index in-memory and serve sub-10ms suggestions with a prefix scan after 2+ characters.

**What we ship:** A pre-processed, minified JSON file derived from `cities5000.txt`, checked into the API source tree (e.g. `api/src/infrastructure/data/places.json`). It contains exactly the fields the product needs — no lat/lng, no timezone, no elevation. A companion build script (`scripts/build-places.ts`) regenerates this file from a fresh GeoNames dump so the dataset is auditable and reproducible; the script is for maintainers, not for runtime.

Entry shape in the shipped file:
```ts
interface PlaceEntry {
  id: number;            // geonameId (stable integer)
  displayName: string;   // "Austin, Texas, United States"
  city: string;          // "Austin"
  region: string | null; // "Texas" (admin1; null when the dataset lacks it)
  country: string;       // "United States"
  population: number;    // for typeahead ranking
}
```

**Out of scope for the dataset:** Coordinates, street, postal code, timezone, elevation, feature codes, admin2–admin4, alternate names, and any entry whose feature class is not `P` (populated place). Country-level entries (feature code `PCLI`) are included as selectable places so a seeker can filter by country. Region-level entries from `admin1CodesASCII.txt` are included for regions that function as independent search targets (e.g. US states, Canadian provinces).

### D-2 — DDL: additive columns on `freelancer_profiles`

The existing `freelancer_profiles.location` (`varchar(120)`) is **preserved** as the display column. Three new columns carry the structured place, plus `place_id` as the match key. All are nullable — location is optional.

```sql
ALTER TABLE freelancer_profiles
  ADD COLUMN place_id     INTEGER,                    -- geonameId
  ADD COLUMN place_city   VARCHAR(200),
  ADD COLUMN place_region VARCHAR(200),
  ADD COLUMN place_country VARCHAR(200);
```

**Column contract:**

| Column | Type | Nullable | When set | When unset |
|---|---|---|---|---|
| `location` | `varchar(120)` | YES | Display name from the selected PlaceEntry (e.g. `"Austin, Texas, United States"`). Backward-compatible — legacy rows keep their free-text string here. | `NULL` (explicit clear) |
| `place_id` | `integer` | YES | The `geonameId` from the selected PlaceEntry. Server validates it exists in the shipped `places.json`. | `NULL` |
| `place_city` | `varchar(200)` | YES | `PlaceEntry.city` | `NULL` |
| `place_region` | `varchar(200)` | YES | `PlaceEntry.region` (nullable in the dataset — some cities lack an admin1) | `NULL` |
| `place_country` | `varchar(200)` | YES | `PlaceEntry.country` | `NULL` |

**Index for the filter (D-6):**
```sql
CREATE INDEX CONCURRENTLY idx_freelancer_profiles_place_id
  ON freelancer_profiles (place_id)
  WHERE place_id IS NOT NULL;
```

A partial index — only rows with a structured place are filterable, and the `WHERE` clause keeps it compact. The listing query (D-6) appends `AND fp.place_id = :placeId` when the `place` param is present; the planner uses this index.

**No migration of legacy rows.** The four new columns start `NULL` for every existing row. Legacy free-text in `location` continues to display (P3). It does not match the filter until the owner saves via typeahead.

### D-3 — Typeahead endpoint: `GET /api/places/suggest`

**Route:** `GET /api/places/suggest?q={prefix}`

**Behavior:**
- `q` shorter than 2 characters → `200 { results: [] }` (no network error, no suggestions).
- `q` ≥ 2 characters → prefix match against `displayName` (case-insensitive, ASCII-folded), ranked by `population` descending, top **10** results.
- No `q` param → `400 Bad Request`.
- The response is a JSON array of `PlaceEntry` objects (all five fields). The client renders `displayName` in the dropdown; the submitted value is the whole object, with `id` as the canonical key.
- CORS: same-origin only (this is a profile/marketplace API, not a public geocoding service).
- Cache: `Cache-Control: public, max-age=86400, immutable` — the dataset is static between deploys; a CDN or browser can cache it aggressively.

**Implementation:** Load `places.json` into memory at server start. Build a simple prefix trie or sorted-array + binary-search index. The dataset is ~50k rows; a linear scan with a pre-built lowercased index is well under 1ms. No database round-trip.

**Rate limiting:** Inherit the existing API rate limiter. No additional throttle — this is a typeahead, not a bulk endpoint.

### D-4 — Write path: `PATCH /api/freelancers/me`

The existing `PATCH /api/freelancers/me` handler gains location validation. The request body accepts an optional `location` object:

```ts
// Request body (partial — location is one optional key)
{
  // ... existing fields (headline, bio, method, rate, etc.) ...
  location?: {
    placeId: number;       // geonameId — required when setting a location
    displayName: string;   // from the selected PlaceEntry
    city: string;
    region: string | null;
    country: string;
  } | null;                // explicit null = clear location
}
```

**Validation (server-authoritative):**

1. If `location` is absent from the request body → do not touch any location column (partial PATCH safety — P1).
2. If `location` is `null` → set `location`, `place_id`, `place_city`, `place_region`, `place_country` all to `NULL`. This is the explicit clear.
3. If `location` is an object:
   a. `placeId` must be present and must be a positive integer.
   b. Look up `placeId` in the in-memory `places.json` map. If not found → **400** `PLACE_ID_INVALID` (unknown/malformed id — R-5).
   c. The submitted `displayName`, `city`, `region`, `country` are **cross-checked** against the stored PlaceEntry. If they don't match → **400** `PLACE_DATA_MISMATCH` (the client sent a stale suggestion; re-fetch and try again).
   d. On success: write all five columns from the PlaceEntry. The server uses the **server's** copy of the data (not the client-submitted strings), so the stored values are always consistent with the shipped dataset.
4. #2528 gate: if the profile's method includes `in-person` and the resulting `place_id` is `NULL` after this write → **400** `LOCATION_REQUIRED` (unchanged from #2528; this ticket does not weaken it — P6).

**Note on D-4(c):** Shipping the full PlaceEntry in the request body (not just the id) lets the server detect stale-client bugs without a round-trip. But the server data is authoritative — it writes what `places.json` says, not what the client sent.

### D-5 — Public profile read

`TalentProfileView` already omits the location row when `profile.location` is null. No change to that logic. The API response for `GET /api/freelancers/:id` and the listing endpoints already include `location` as `string | null`. The four new structured columns are **not** exposed on the public read — only `location` (display name) is. The public surface sees no new fields. This keeps the API surface backward-compatible and avoids leaking internal schema.

For the profile-owner's own edit view (`GET /api/freelancers/me`), the response **does** include `placeId`, `placeCity`, `placeRegion`, `placeCountry` so the edit form can pre-populate the typeahead with the current selection. These fields are only in the authenticated own-profile response, never in public reads.

### D-6 — Listing query: `GET /api/freelancers?place={geonameId}`

The existing `GET /api/freelancers` endpoint (used by `/marketplace?category=advisors`) gains one optional query parameter:

| Param | Type | Default | Behavior |
|---|---|---|---|
| `place` | `integer` (geonameId) | absent | When present and a valid positive integer: append `AND fp.place_id = :placeId` to the WHERE clause. When absent, malformed, or unknown: ignore (no filter on this dimension). |

**SQL composition (pseudocode for the existing query builder):**

```ts
if (params.place && Number.isInteger(params.place) && params.place > 0) {
  // place_id is an integer column; bind directly.
  // If the geonameId is not in our places.json, still bind it —
  // it will match zero rows (no 500, no error), which is correct behavior
  // because no profile can hold an id we never shipped.
  where.push('AND fp.place_id = :placeId');
  bindings.placeId = params.place;
}
// If params.place is present but not a positive integer:
// ignore it — 200, no error, other filters still apply (R-5).
```

**Key design decisions:**
- No JOIN — the filter is a direct column equality on the indexed `place_id`.
- No case-folding, no `ILIKE`, no substring — it's an integer equality on a stable id.
- The index `idx_freelancer_profiles_place_id` (partial, where `place_id IS NOT NULL`) serves this query. Rows with `NULL` place_id (unset + legacy) are excluded by the `=` predicate naturally.
- Existing visibility, published-status, and opt-in filters are unchanged — the `place` clause is AND-composed.

**Pagination:** When `place` changes, reset to page 1 (frontend responsibility). The backend accepts `page` as before; the `place` param does not alter pagination semantics.

### D-7 — Frontend: shared PlaceTypeahead component

A single React component serves both the profile edit form and the advisors filter:

```
src/components/places/PlaceTypeahead.tsx
```

**Props:**
```ts
interface PlaceTypeaheadProps {
  value: PlaceEntry | null;       // currently selected place
  onChange: (place: PlaceEntry | null) => void;
  placeholder?: string;
  id?: string;                    // for label `htmlFor`
  disabled?: boolean;
}
```

**Behavior:**
- Renders a combobox (`<input>` + `<ul>` dropdown) following the existing marketplace filter a11y patterns (ARIA `combobox` role, `aria-expanded`, `aria-activedescendant`, keyboard navigation with ↑↓ Enter Escape).
- On 2+ characters typed → `GET /api/places/suggest?q=…`. Debounced at 150ms.
- Dropdown shows up to 10 results with `displayName`. Selecting one calls `onChange(place)`.
- When `value` is set (a PlaceEntry), the input shows `value.displayName`. A clear button (×) resets to null.
- 0–1 characters: no fetch, no dropdown.
- Loading state: a subtle spinner in the input (following existing marketplace patterns).
- Error state: if the suggest call fails, show nothing (graceful degradation — the user can retry by typing more).

**i18n:** Place names are proper nouns and are NOT translated. The input placeholder and the "no results" message ARE translated via the existing i18n catalog (five locales). New keys:

### D-15 — Dataset maintenance

The `scripts/build-places.ts` script:
1. Reads `cities5000.txt` (tab-separated, no header) from a local path or URL.
2. Filters to feature class `P` (populated places) + feature code `PCLI` (countries).
3. Reads `admin1CodesASCII.txt` for region names.
4. For each city row: extract `geonameId`, `name`, `asciiname`, `latitude`, `longitude`, `country`, `admin1`, `population`.
5. Resolve `admin1` code → human-readable region name via the admin1 map.
6. Build `displayName` as `"{asciiname}, {region}, {country}"` when region exists, else `"{asciiname}, {country}"`.
7. For each country row (PCLI): `displayName` = `"{country}"`, `city` = `null`, `region` = `null`.
8. Sort by population descending.
9. Output minified JSON to `api/src/infrastructure/data/places.json`.

The script is run manually when the dataset needs updating (e.g. every 6–12 months). It is NOT part of the CI pipeline or the runtime.
