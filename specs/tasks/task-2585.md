# WIP PRD: Location on Profile and Optional Filter

## Problem & Goal

Profiles have no location, so people cannot signal where they are based and discovery cannot be narrowed by place. Results feel less relevant and nearby matches are hard to find.

**Goal:** Let a user add one optional location to their profile, show it on the profile, and let others optionally filter browse/search by that location. Location is never required to create, complete, or find a profile.

## Target users / ICP roles

- Profile owners who want to show a city or region
- People browsing or searching who want an optional place constraint
- Trust & safety / moderation, who need locations to be structured and not free-form spam

## Scope

**In scope**

- One primary location on the profile (city + country; region/state when the place dataset provides it)
- Add, change, and clear location from profile edit
- Show location on the profile when set; omit it when unset
- Optional location filter on primary browse and search surfaces
- Place typeahead against a standard place dataset
- Index/update so profile location is filterable after save

## Functional requirements

1. A profile owner can set, change, or remove a single primary location from profile edit. Location is optional.
2. Location is stored as a structured place: display name, city, region/state when available, country, and stable place id. Free-text-only locations are not accepted.
3. Typeahead suggests places after 2+ characters. Save requires a selected suggestion (valid place id). Unknown or malformed place ids are rejected.
4. Profile view shows the location display name only when a location is set. No location row, placeholder, or “unknown” label when unset.
5. Browse and search expose an optional location filter. Default is no location constraint (same result set as today).
6. Applying a filter returns profiles whose stored place matches the selected place. Matching is by place id; a city filter does not include the entire country. Unset locations never match an active location filter.
7. Clearing the filter, or loading browse/search with no location parameter, returns the unfiltered set. Location combines with existing filters and sorts; it does not replace them.
8. Location changes appear on the profile and in filterable results after save without a full account rewrite.
9. Profile visibility rules still apply. Location is not shown to viewers who cannot see the profile, and filtered results do not leak hidden profiles.

## Acceptance criteria

- User sets a suggested place, sees it on their profile, changes it to another place, then clears it; the profile no longer shows location.
- Profiles with no location remain valid, appear in unfiltered browse/search, and are excluded when a location filter is applied.
- Filter by a city returns only profiles stored with that place id; clearing the filter restores prior unfiltered results.
- Saving without selecting a suggestion fails validation and does not write a location.
- Invalid place ids do not persist and do not 500 browse/search.
- Location filter is visible and optional on main browse/search (desktop and mobile) and does not block using other filters.
- A profile with location hidden by existing visibility rules does not appear in location-filtered results for unauthorized viewers.

## Out of scope

- Multiple locations, location history, or “open to relocate”
- GPS, live location, coordinates, radius / “near me”, or map UI
- Street address, postal code, or precise pinning
- Mandatory location at signup or profile completion
- Location-based notifications, ranking boosts, or feed injection
- Admin bulk backfill
- Custom place-name translations beyond the place dataset
- Distance sort as a separate control (unless already provided by an existing sort)

## Requirements

Location is one optional structured place on the existing talent row (`freelancer_profiles`), shown on the public profile when set, and used as an optional exact-place filter on `/marketplace?category=advisors`. It is **not** a new listing kind, **not** a `/advisors` route, and **not** a second location field.

### Locked decisions

1. **One location, one row.** Upgrade the existing `freelancer_profiles.location` (display name, still `varchar(120)`). Do not add a second user-facing location, a location-history table, or a parallel career-listing location. `listing.readiness` / hire-me copy continues to read the display string.
2. **Structured place, not free text, on write.** A saved location is a selected place: **place id** (stable, required), **display name** (what the profile shows; written into `location`), **city**, **region/state when the dataset provides it**, **country**. Free-text-only values are rejected. Unknown or malformed place ids are rejected. Coordinates, street, postal code, and radius are not stored and not exposed.
3. **Place id is the match key.** Filter equality is `place_id = selected id`. A city does **not** match its parent region or country. A country selection matches only profiles stored with that country place id, not every city in it. Unset / legacy-without-id rows never match an active location filter.
4. **Optional everywhere except the existing in-person bookable gate.** Location is never required to create, publish, or find a profile, and never required for unfiltered browse. #2528 still owns `LOCATION_REQUIRED` when method includes `in-person` — after this ticket that gate means a **valid structured place**, not a non-empty string. This ticket does not reopen methods, price, or bookable.
5. **Filter surface is advisors category.** MUST ship on `/marketplace?category=advisors` as an optional control, AND-composed with #2580 / #2586, `q`, sort, and pagination. Default (no `place` / location param) = today’s unfiltered advisors set. Other marketplace categories (agent, skill, course, playbook, template, jobs) MUST NOT gain this control or honor leftover place params as visible chrome. If a public talent browse already lists the same `freelancer_profiles` rows, it MAY accept the same place-id query param; it is not a second product.
6. **No `/advisors`, no `advisor` in `MARKETPLACE_LISTING_KINDS`, no `advisory` in `PEOPLE_OBJECT_KINDS`.** Category is the existing query-param filter over opted-in talent (#2527).
7. **No bulk backfill.** Legacy free-text `location` without a place id still **displays** on the profile; it does **not** match filters until the owner re-saves via typeahead. Out of scope: admin backfill, geocoding existing strings, `open_to_relocation`, GPS / “near me” / map UI, ranking boosts, notifications.
8. **Place catalog is Design, not a new geo product.** Architect names one standard place dataset that yields stable city/region/country ids and a typeahead after 2+ characters. Do **not** reuse `api/src/application/web/geocode.ts` (MediaWiki coordinate plotter) as the profile picker, and do not persist lat/lng. Existing `geocoder_cache` is not the profile store.

### R-1 — Surfaces and composition

- **Edit:** replace the free-text location `<input>` on `/freelancer/profile` with a shared place typeahead. Same one-Save profile form as today / #2528. Location stays on the identity/rate row.
- **Public profile:** `TalentProfileView` (and any card that already shows `profile.location`) shows the **display name** only when set. No row, placeholder, or “unknown” when unset. Same visibility rules as the rest of the profile.
- **Filter:** optional location control on `/marketplace?category=advisors` only (desktop + existing mobile filter IA). Same interaction rank as other first-class advisors filters. Does not replace or hide expertise / language / method / stage / Start-Grow-Exit.
- Switching away from `category=advisors` drops the place param from the URL and hides the control (#2580 isolation).

### R-2 — Typeahead and write path

- Suggest after **2+** characters; 0–1 characters yield no list.
- Suggestions come only from the chosen place dataset (city-level first; region/country if the dataset exposes them as places). No user-invented labels.
- **Save requires a selected suggestion** (valid place id). Typing a name and saving without selecting fails validation and writes nothing (`PLACE_ID_INVALID` / equivalent). Clearing is an explicit clear, then save → `location` and place id both null.
- Change = select a different suggestion and save. Partial profile PATCH must not wipe location when the client omits it.
- Server is authoritative. Invalid writes return **400** and persist nothing. Do not 500.

### R-3 — Legacy rows

- Rows with a display string and **no** place id: still show the string on the profile; **excluded** from any active location filter (same as unset).
- Next edit that submits location must pick a suggestion (or clear). Do not re-persist the old free-text as if it were a place.
- No migration job, no silent geocode of old strings.

### R-4 — Optional filter behavior

- Default: no location constraint (same advisors result set as before this ticket).
- Applying a filter: seeker uses the **same typeahead**, selects a place, URL encodes the **place id** (not the display name). Reload / share / back-button restore that selection and set.
- Match: published, visible advisor listings whose stored **place id** equals the param. Hidden / unpublished / visibility-blocked profiles never appear (no leak via the filter).
- Unset and legacy-without-id profiles are omitted while the filter is active; they return when the filter is cleared.
- AND with other advisors filters, `q`, sort. Changing location resets to page 1. Changing page/sort does not clear location.
- Clear control, or loading with no location param, returns the unfiltered advisors set (other filters unchanged).
- Unknown / malformed place param: **200**, ignore that param (do not 500); remaining valid filters still apply (#2580).
- Server-authoritative. Client-only hiding of cards is not sufficient.
- Index / update so a save is filterable on the next listing request without a full account rewrite.

### R-5 — Validation and errors

| Case | Result |
|---|---|
| Select suggestion, save | Persist display name + place id + city / region / country |
| Save typed text, no selection | 400, no write |
| Unknown / malformed place id on write | 400, no write |
| Clear location | Both display and place id null; public omits |
| In-person on and location cleared | #2528 `LOCATION_REQUIRED`; this ticket does not weaken it |
| Filter param missing | Unfiltered (for this dimension) |
| Filter param unknown | 200, param ignored |
| Viewer cannot see profile | Omitted from filtered results |

### R-6 — i18n, a11y, isolation

- New labels go through the existing i18n catalog (five locales). No one-locale hardcoding.
- Typeahead and filter are keyboard-operable, labelled, and follow existing marketplace filter a11y (selected value, clear).
- No SCORE / SBA copy. No ranking, feed injection, or location notifications.
- Do not touch `open_to_relocation`, `timezone`, session price, volunteer badge (#2584), or stage filter (#2586) except AND-composition on the listing query.
