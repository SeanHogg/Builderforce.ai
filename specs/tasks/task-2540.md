# PRD: Meeting-End Summary Markdown Contract

## Problem & Goal

`summarizeMeeting` already runs when a meeting ends. Downstream `parseMeetingMinutes` is built against a fixed three-section Markdown shape. Any drift in headings, section count, order, or body conventions forces a parser fork (new code path, versioned parser, or dual formats).

**Goal:** Keep a single, stable three-section Markdown contract for every meeting-end summary so `parseMeetingMinutes` continues to consume output on the existing path with no fork, no format version flag, and no second parser.

## Target users / ICP roles

- Meeting participants who read minutes after the call
- Facilitators / note owners who act on decisions and tasks
- Downstream agents and services that call `parseMeetingMinutes` (tasking, CRM, search, notifications)
- Product / eng teams shipping on the shared minutes pipeline

## Scope

In scope:

- End-of-meeting invocation of the existing `summarizeMeeting` path only
- Output Markdown whose named sections are only Summary, Decisions, and Action items, in that order
- Compatibility with the current `parseMeetingMinutes` contract (no parser fork, no dual-format detection)
- Empty-section handling that **omits** Decisions / Action items when the transcript supports none (parser binds missing sections to empty arrays). Do not emit `- None` sentinels.

Out of product surface: no new meeting UI, no new summary triggers, no new minute types.

## Functional requirements

1. **Trigger (unchanged):** On meeting end, call `summarizeMeeting`. Do not add a parallel summarizer or a minutes-only code path.
2. **Document shape:** `summarizeMeeting` returns GitHub-flavored Markdown whose *named* sections are only Summary, Decisions, and Action items, in that order. Heading *style* may be ATX or bold; unlabeled leading prose is Summary. No other named sections in the stored `meetings.summary` body.
3. **Section semantics (live contract — do not reverse):**
   - **Summary:** one-paragraph recap (purpose, outcome, unresolved threads).
   - **Decisions:** bullet list, one decision per bullet. If none, **omit the section** (not `- None`).
   - **Action items:** checklist `- [ ] Owner — task` (owner first, em dash). Optional `[x]` means done. If none, **omit the section**. Do **not** switch to `- [ ] task — owner — due` — that grammar would mis-parse under the existing `OWNED` regex and fork the reader.
4. **Heading labels:** Summary / Decisions / Action items (parser also accepts Decision, Action, Actions, and optional colon). Spelling of those names is the contract; heading level is not.
5. **Allowed Markdown inside sections:** Paragraphs and `-` / `*` / `+` / numbered bullets, including `[ ]` / `[x]` checkboxes. No tables, no code fences, no HTML as part of the contract.
6. **Parser compatibility:** `parseMeetingMinutes` remains the only reader. It splits on the three section names (tolerant regex), maps bullets under Decisions and Action items, and treats missing sections as empty arrays. No format discriminator or legacy branch.
7. **Failure mode:** If summarization fails (no transcript, empty model output, LLM error), return `{ error }` and **do not** persist a fabricated minutes document. Empty/null `meetings.summary` already parses to empty `MeetingMinutes`. A three-heading “could not be generated” placeholder is forbidden — it would look like real minutes to `#2541`.

## Requirements

#2540 locks the **existing** minutes contract so `parseMeetingMinutes` stays one implementation. It does not invent a second template.

Grounded in live code (main):

- Producer: `summarizeMeeting` in `api/src/application/meetings/meetingIntelligence.ts` (calls `condenseTranscript` with the minutes `shape`).
- Consumer: `parseMeetingMinutes` in `frontend/src/lib/meetings/meetingMinutes.ts` (shared by the minutes panel and the board act that places checklist items).
- Trigger: meeting-end path in `api/src/presentation/routes/meetingRoutes.ts` already imports and invokes `summarizeMeeting`. Do not add a parallel summarizer.

### R-1 — Single producer on meeting end

**User story:** As a meeting participant, I receive one minutes document when the call ends, from the same path every time.

**Requirement:** On meeting end, the only minutes producer is `summarizeMeeting`. No second summarizer, no minutes-only code path, no `kind`-specific template (standup vs advisory vs adhoc all use this shape). `#2539` (marketplace Meeting Notes listing / `runAgentTurn`) and `#2541` (`pullStandupMinutesAct`) consume this document; they do not author a different one.

**Acceptance:** Meeting end still calls `summarizeMeeting` only. Grep for a second minutes LLM shape or a `parseMeetingMinutes` format switch returns none.

### R-2 — Three named sections, fixed order, no extras

**User story:** As a parser, I always find Summary then Decisions then Action items, and nothing else to special-case.

**Requirement:** Successful minutes Markdown uses at most these three named sections, in this order:

1. Summary
2. Decisions
3. Action items

Labels match the parser's `SECTION` regex (Summary / Decision(s) / Action item(s) / Actions). No Attendees, Transcript, Risks, Parking lot, or other named sections. No document-level H1 title inside the stored `meetings.summary` body (the chat wrapper `📝 **Meeting minutes — {title}**` is added by `postMeetingChatLine`, not by the stored summary).

Heading *style* is not a discriminator: the live parser accepts ATX headings (`#`–`######`), bold (`**Summary**`), optional colon, and unlabeled leading prose as Summary. Tightening to H2-only would not help the parser and is not required.

### R-3 — Section semantics (live prompt)

**Summary:** One-paragraph recap of purpose, outcome, and unresolved threads. Unlabeled prose before the first recognised heading is Summary (models often skip the Summary label). Nested headings that do not match `SECTION` stay in the current section as text.

**Decisions:** Unordered bullet list (`-` / `*` / `+` / numbered). One decision per bullet. If the transcript supports none, **omit the section entirely** — do not emit a `- None` sentinel. `parseMeetingMinutes` maps a missing Decisions section to `decisions: []`. A literal `- None` would become a fake decision and could be placed as a card by `#2541`.

**Action items:** Checklist bullets. Grammar is the live prompt and parser, **owner first**:

```
- [ ] Owner — task
```

- Em dash (`—`) is the prompted separator; the parser also accepts en dash, ` - `, and colon.
- Owner is a short leading run (≤40 chars, no sentence punctuation); remainder is the task.
- Optional `[x]` / `[X]` marks `done: true` so a re-run does not re-place closed work.
- If the line has no owner separator, `owner` is null and the whole line is `task`.
- If the transcript supports none, **omit the section entirely** (`actionItems: []`). Do not emit `- None`.

This is the grammar `actionItemTitle()` already uses (`{owner} — {task}`). Reversing to `- [ ] task — owner — due` would mis-parse under the existing `OWNED` regex (first segment becomes owner) and **would force a parser fork**. Due dates are out of scope for #2540 (see R-7).

### R-4 — Empty and missing input

| Input | `summarizeMeeting` | `parseMeetingMinutes` |
| --- | --- | --- |
| No transcript (`segments.length === 0`) | `{ error: 'No transcript to summarize yet.' }` — do **not** write `meetings.summary` | n/a |
| Model empty / condense error | `{ error }` — do **not** write a fabricated document | n/a |
| `summary` null / blank | n/a | `{ summary: '', decisions: [], actionItems: [] }` |
| Summary only (no Decisions / Action items headings) | valid | those arrays empty |
| Empty meeting that did produce a recap | Summary paragraph; omit empty lists | Summary non-empty; arrays empty |

`condenseTranscript` already instructs: *If the transcript does not support a section, omit it rather than filling it* and *never invent decisions, owners, quotations, commitments or tasks*. #2540 does not reverse that.

### R-5 — Failure is an error, not a fake document

**User story:** As ops, I can tell “minutes were not generated” from “the meeting decided nothing.”

**Requirement:** If summarization fails, return `{ error }` to the route (mapped to 4xx/5xx as today). Do **not** persist a three-heading placeholder, a “minutes could not be generated” Summary, or `- None` bullets. `condenseTranscript` documents this as load-bearing: *Never a fabricated fallback — a summary of a conversation that did not happen is worse than no summary.*

Callers that need a display string use the error, not a synthetic Markdown body. `#2541` must treat missing/`error` summary as “nothing to place,” not parse a placeholder.

### R-6 — One parser, no format discriminator

**User story:** As engineering, I have one reading of minutes. The board and the notes panel cannot disagree.

**Requirement:** `parseMeetingMinutes` remains the only reader. No version field, no “legacy vs H2” branch, no second regex pack. Changing copy inside sections (wording, bullet count) must not require parser changes, as long as:

- section labels still match `SECTION`
- action-item bullets still match `BULLET` + optional `OWNED`
- empty sections stay omitted (or, if a model emits an empty heading with no bullets, the parser already yields an empty array)

Allowed inner Markdown: paragraphs and unordered/checklist bullets. Tables, code fences, HTML, and nested lists are not part of the contract; the parser ignores non-bullet lines outside Summary.

### R-7 — Explicitly not in this ticket

- Marketplace listing / silent notetaker / `kind=advisory` → `#2539`
- Auto-placing open action items / idempotency by title → `#2541` (uses `actionItemTitle`, which depends on R-3)
- Follow-up booking / guest project → `#2542` / `#2543`
- New sections, reordering, localization of heading labels
- Due dates, priority, links, issue IDs on action items (would extend `MinutesActionItem` in the *same* parser later; not a second template)
- Changing when `summarizeMeeting` runs (mid-meeting, manual rerun, scheduled backfill)
- Email / Slack / calendar wrapping of minutes

### R-8 — Compatibility test bar (for QA / developer)

Given minutes Markdown produced by `summarizeMeeting` (or a fixture that matches R-2/R-3):

1. `parseMeetingMinutes` extracts `summary` text, `decisions[]`, and `actionItems[]` with `{ owner, task, done }`.
2. A document with only a Summary paragraph and no other headings yields empty arrays, not a parse error.
3. `- [ ] Ana — Ship the listing` → `{ owner: 'Ana', task: 'Ship the listing', done: false }`.
4. `- [x] Ana — Ship the listing` → `done: true`.
5. A heading `### Action Items` or `**Decisions**` still binds (tolerant `SECTION`); we do not require H2-only.
6. No code path chooses a parser variant based on meeting `kind`, heading level, or a format flag.

Traceability: R-1 → meeting-end + `summarizeMeeting`; R-2/R-3 → `shape` string in `summarizeMeeting` + `SECTION`/`BULLET`/`OWNED`; R-4/R-5 → `condenseTranscript` omit/refuse rules; R-6 → single `parseMeetingMinutes`; R-7 → sibling tickets under epic `#2538`.
