# PRD: Meeting-End Summary Markdown Contract

## Problem & Goal

`summarizeMeeting` already runs when a meeting ends. Downstream `parseMeetingMinutes` is built against a fixed three-section Markdown shape. Any drift in headings, section count, order, or body conventions forces a parser fork (new code path, versioned parser, or dual formats).

**Goal:** Keep a single, stable three-section Markdown contract for every meeting-end summary so `parseMeetingMinutes` continues to consume output on the existing path with no fork, no format version flag, and no second parser.

## Target users / ICP roles

- Meeting participants who read minutes after the call
- Facilitators / note owners who act on decisions and tasks
- Downstream agents and services that call `parseMeetingMinutes` (tasking, CRM, search, notifications)
- Product / eng teams shipping on the shared minutes pipeline

## Scope

In scope:

- Meeting-end invocation of `summarizeMeeting` (already wired; do not replace or duplicate the trigger)
- Output of `summarizeMeeting` as GitHub-flavored Markdown matching the three-section contract below
- Compatibility of that output with the current `parseMeetingMinutes` implementation
- Empty-section and low-signal transcript handling without breaking the contract
- One summary per meeting end; idempotent overwrite of the canonical minutes document if the job is retried

Out of scope is listed separately.

## Functional requirements

### Meeting-end path

1. On meeting end, run `summarizeMeeting` exactly as today. Do not add a parallel summarizer or a second minutes writer.
2. Persist one canonical Markdown minutes document per meeting. Retries replace that document; they must not append a second copy or a variant format.
3. `parseMeetingMinutes` remains the only parser. Callers must not branch on format version, model, or meeting type.

### Three-section Markdown contract

`summarizeMeeting` MUST emit GitHub-flavored Markdown with **exactly three** `##` sections, in this order, with these exact headings:

```markdown
## Summary

## Decisions

## Action Items
```

Rules:

4. No other `##` headings. No `#` title heading. Subsection `###` headings are forbidden (they fork heading-based parse).
5. **Summary:** 1–3 short paragraphs of what happened and why it mattered. No bullet-only Summary. No action verbs framed as tasks here.
6. **Decisions:** Unordered list. Each line is one decided outcome (`- ...`). If none, the body is exactly `- None`.
7. **Action Items:** Unordered list. Each item is one line in this form:
   `- [ ] <task> — <owner> — <due>`
   - `owner` is a display name or `Unassigned`
   - `due` is `YYYY-MM-DD` or `TBD`
   - If none, the body is exactly `- None`
8. Do not wrap the document in a code fence. Do not emit YAML/JSON front matter, HTML, or tables.
9. Transcript quotes, parking-lot notes, and attendee lists stay inside **Summary** prose if needed. They must not become extra sections.
10. Language of the minutes matches the meeting’s dominant spoken language; headings stay English as specified above so the parser does not fork.

### Parser compatibility

11. `parseMeetingMinutes` must succeed on every meeting-end document without code changes.
12. Parsed output maps 1:1: Summary text, Decisions list, Action Items list (checkbox, task, owner, due).
13. `- None` in Decisions or Action Items parses to an empty list, not a real item.
14. Failure to match the contract is a summarizer bug. Fix the generator; do not extend or fork the parser.

## Acceptance criteria

- Given a meeting ends, `summarizeMeeting` runs once on the existing hook and writes the canonical minutes Markdown.
- Every successful summary contains exactly the three headings `## Summary`, `## Decisions`, `## Action Items` in that order and no other `##`/`#` headings.
- `parseMeetingMinutes` on that document returns structured Summary / Decisions / Action Items without errors and without any new parser branch.
- Meetings with no decisions and no tasks still include all three sections; empty lists use `- None` and parse to empty arrays.
- Action item lines match `- [ ] <task> — <owner> — <due>` and round-trip through the parser (checkbox, task, owner, due).
- A retried meeting-end job overwrites the same document and still parses; no second format or duplicate minutes record.
- Repo contains a single `parseMeetingMinutes` implementation; no `parseMeetingMinutesV2`, format enum, or meeting-type switch.
- Contract fixtures (happy path, empty decisions/actions, retry) pass in CI against the current parser.

## Out of scope

- Changing when or how often `summarizeMeeting` is triggered
- Forking, versioning, or rewriting `parseMeetingMinutes`
- Extra sections (Attendees, Transcript, Parking Lot, Risks, Next meeting)
- JSON/YAML minutes, rich cards, or a second persisted format
- Live / mid-meeting partial summaries
- UI for editing minutes, assignment notifications, or calendar due dates
- Model/prompt work that does not protect this contract
- Speaker diarization, recording storage, or access-control changes
