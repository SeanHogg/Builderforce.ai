# PRD: Visitor Advisory Meeting Booking (Chrome-less Confirm + Join)

## Problem & Goal

Visitors who want an advisory session currently have no first-class path from identity capture (name + email) to a correctly attributed meeting. Bookings must land as `kind=advisory`, with the advisor as organizer and the visitor as attendee. Confirmation and join must render without application chrome so the visitor stays in a focused, shareable flow.

**Goal:** Given a visitor’s name and email, create an advisory meeting (advisor = organizer, visitor = attendee) and surface a chrome-less confirmation that includes a join link. Routes under `NO_CHROME_PREFIXES` must render without app chrome.

## Target users / ICP roles

- **Visitor:** external person booking or joining an advisory session; provides name + email; needs a simple confirm + join experience.
- **Advisor:** internal organizer of the advisory meeting; owns the calendar event and host privileges.
- **Downstream agents / implementers:** consume this PRD as the shared spec for booking, attribution, and chrome-less UX.

## Scope

In scope for this WIP:

- Capture visitor **name** and **email**.
- Create a meeting with `kind=advisory`.
- Assign **advisor** as organizer and **visitor** as attendee.
- Confirmation page and join link with **no application chrome**.
- Treat URLs matching `NO_CHROME_PREFIXES` as chrome-less (confirm and join included).

## Functional requirements

1. **Identity capture**
   - Accept visitor **name** and **email** as required inputs.
   - Reject empty name, empty email, or malformed email; do not create a meeting on invalid input.
   - Persist visitor identity on the attendee record (display name + email).

2. **Meeting creation**
   - Create a meeting with `kind` exactly `advisory`.
   - Set the **advisor** as **organizer** (host / calendar owner).
   - Set the **visitor** as **attendee** (not organizer, not co-host).
   - Do not invert, omit, or duplicate these roles.

3. **Confirmation**
   - After successful creation, send the visitor to a confirmation view.
   - Confirmation must be chrome-less (no app shell: no global nav, header, footer, or sidebar).
   - Confirmation must show meeting identity at a glance (advisory session, advisor, time if known) and a primary **join** action.

4. **Join link**
   - Confirmation includes a join link that opens the advisory session.
   - Join route is chrome-less and covered by `NO_CHROME_PREFIXES`.
   - Join link is visitor-safe to open or share; it does not require the app chrome or a logged-in visitor shell.

5. **Chrome-less routing (`NO_CHROME_PREFIXES`)**
   - Confirm and join paths are listed in (or match) `NO_CHROME_PREFIXES`.
   - Any request whose path prefix is in `NO_CHROME_PREFIXES` renders without application chrome.
   - Chrome-less pages remain functional: confirm content, join CTA, and join experience work without the shell.

## Acceptance criteria

- Submitting a valid visitor name + email creates exactly one meeting with `kind=advisory`.
- That meeting’s organizer is the advisor; the visitor is an attendee with the submitted name and email.
- Invalid name/email produces no meeting and a clear validation failure.
- Post-booking confirmation is reachable and has no application chrome.
- Confirmation displays a working join link.
- Join via that link is chrome-less.
- Confirm and join URLs match `NO_CHROME_PREFIXES`; matching prefixes never render app chrome.
- Advisor and visitor roles are not swapped under retries, refreshes, or duplicate submits (idempotent or duplicate-safe behavior: no extra advisory meetings with wrong roles).

## Out of scope

- Visitor account creation, SSO, or magic-link auth beyond name + email on the attendee.
- Advisor discovery, matching, or availability/calendar slot picking.
- Payments, packaging, or advisory-product catalog.
- Email/SMS notifications, calendar invites (ICS), or reminders.
- Reschedule, cancel, no-show, or recording flows.
- Changing `kind` after creation, multi-advisor, or multi-visitor attendees.
- Branded theming beyond “no chrome”; marketing pages; logged-in advisor console UX.
- Mobile native apps; anything not required for name+email → advisory meeting → chrome-less confirm + join.

### R-1 — Identity capture (visitor name + email)

- The public book surface that creates an advisory meeting **requires** two visitor fields: **name** and **email**.
- **Reject** (4xx, no `meetings` insert) when:
  - name is missing or whitespace-only after trim;
  - email is missing, whitespace-only, or malformed (not a single `local@domain` addr-spec; domain must contain a `.`).
- Do not create a meeting, attendee row, reservation, or calendar event on invalid input.
- Persist the **trimmed** name on `meeting_attendees.memberName` and the **normalized** email (trim + lowercase) on `meeting_attendees.email`.
- Visitor account, SSO, and magic-link auth are **out of scope**. Name + email on the attendee row is the whole identity.

Existing ATS `/book/[token]` does **not** collect name/email (the candidate is already on the interview). Advisory booking must add the fields; do not silently reuse the interview client as-is.

### R-2 — Meeting kind is exactly `advisory`

- A successful submit creates **exactly one** `meetings` row whose `kind` column is the literal string `advisory`.
- Do not coerce to `adhoc` (today’s fallback for unknown kinds). If `KINDS` does not yet include `advisory`, that is #2536’s defect — this ticket must not ship a workaround that writes `adhoc` / `direct` / `interview`.
- Do **not** pass `linkTeamChat: true`. Do **not** add `advisory` to `TEAM_CEREMONY_KINDS` (owned by #2536). An advisory meeting must not open the canonical team chat as a side effect.
- Restricted Brain thread / mentoring engagement is **A1** (PRD 26 §7), not this P0 slice. Leave `chatId` null unless a later ticket writes it.

### R-3 — Advisor is the organizer (host)

On the created meeting:

| Field | Value |
|---|---|
| `meetings.createdBy` | Advisor’s user id (`booking_hosts.host_ref` / talent user id). **Never** the visitor. **Never** empty. |
| Attendee #0 | `memberKind: 'human'`, `memberRef: <advisor user id>`, `role: 'host'`, `response: 'accepted'`, display name = advisor’s public listing/display name (not the meetingRoutes default `'Organizer'`). |

The visitor must not be written as `createdBy` and must not receive `role: 'host'`, including when the visitor happens to hold a session in another tenant.

### R-4 — Visitor is an attendee (not organizer, not co-host)

- Exactly one visitor attendee row: `memberKind: 'human'`, `role: 'attendee'` (not `host`), `response: 'invited'` until they join.
- `memberName` / `email` = the submitted identity (R-1).
- `memberRef`: a **stable** value derived from the normalized email (so `meetingRoutes` de-dupe-by-ref and retries do not insert a second visitor row). Do not mint a random UUID per submit.
- Do not invert, omit, or duplicate these two roles (advisor host + visitor attendee).

### R-5 — Write in the advisor’s tenant

- The `meetings` (and any paired `booking_reservations`) row is written in the **service’s tenant** — the advisor’s workspace — matching `reserveForHost` in `bookings.ts`.
- Do not write the meeting in a visitor tenant, a shared “guest” tenant invented here, or the caller’s session tenant. Guest-project / claim-link is #2543, out of scope.

### R-6 — Confirmation view (chrome-less)

After a successful create, the visitor is sent to a confirmation view that:

1. Is reachable from the submit (redirect or in-place booked state).
2. Renders **without application chrome**: no global nav, app header, footer, sidebar, or `RouteMarketing` teaser. `classifyShell` for the confirm pathname must be the no-chrome class consumed by `ConditionalAppShell`.
3. Shows, at a glance:
   - that this is an **advisory** session (not an interview, standup, or generic meeting);
   - the **advisor’s** display name;
   - the scheduled time **if** `scheduledAt` is known (viewer’s timezone, named on the page — same rule as `BookingClient`);
   - a primary **Join** action (R-7).
4. Does **not** list other attendees, raw availability windows, interviewer panels, job titles, or tenant internals. Advisory confirm *does* name the advisor (unlike ATS booking, which hides the panel).

Reuse the existing `/book/[token]` booked state if the advisory token lives there; extend it with the Join CTA. Do not send the visitor to `/meetings`.

### R-7 — Join link on confirmation

- Confirmation includes a working **join href** (anchor or equivalent primary button).
- The href is **visitor-safe to open or share**: credential is a token (same class as `share_links` / ATS `/book/<token>`), **not** a logged-in cookie and **not** the authenticated join URL `` `/meetings?join=<meetingId>` ``.
- That authenticated URL is the **anti-pattern** for this ticket: it is an app-shell route and `POST /meetings/:id/join` refuses a stranger.
- Opening the join href is chrome-less (R-8).
- The **join API** that resolves token→tenant and returns `roomKey` is **#2535**. This ticket **emits** the URL #2535 will honour; it does not implement `POST /meetings/:id/join` for anonymous callers and does not remove `authMiddleware` from the meetings router.

### R-8 — Confirm and join match `NO_CHROME_PREFIXES`

Current list (do not copy-paste into a second source of truth — extend the array in `shellRouting.ts` only if a **new** prefix is required):

`/embed`, `/webcontainer`, `/auth/`, `/book`, `/deal`, `/f/`, `/p/`, `/sign/`, `/invoice/`, `/resume/`, `/data-rooms/shared/`, `/investor/shared/`, `/legal-documents/shared/`, `/references/shared/`, `/lti/`

**Decision:** keep visitor confirm and join **under `/book/…`**. `underPrefix(pathname, '/book')` already covers `/book`, `/book/<token>`, `/book/<token>/confirm`, `/book/<token>/join`.

- Do **not** add `/meetings` to `NO_CHROME_PREFIXES` (that would strip chrome from the operator meetings console).
- If an implementer introduces a prefix other than `/book/…` (e.g. `/join/`), they **must** add it to `NO_CHROME_PREFIXES` with the same trailing-slash / segment rules as `/f/` and `/p/` (`underPrefix`, not `startsWith`), and `classifyShell` tests must cover it.
- Any request whose path matches `NO_CHROME_PREFIXES` continues to render without app chrome. Chrome-less pages remain functional: confirm content, Join CTA, and join experience work without the shell.

### R-9 — Duplicate-safe / idempotent create

Retries, refreshes, and double-submits must **not**:

- insert a second `advisory` meeting for the same booking;
- swap advisor/visitor roles;
- add a second visitor attendee row.

**Idempotency key:** the public booking token **plus** normalized visitor email **plus** `scheduledAt` (ISO) when a slot is present. A repeat submit returns the **existing** meeting (same `id`, same `createdBy`, same two attendee roles) — typically HTTP 200, not a second 201.

ATS `offerInterviewSlots` already revokes the previous `share_links` row on re-offer so two working links cannot exist against one interview. Advisory booking must be equally one-meeting-per-(token, email, slot).

### R-10 — Role stability

R-3 and R-4 hold under retry, refresh, and duplicate submit. Automated checks: after N identical valid posts, `count(meetings where kind='advisory' and this token/slot/email) === 1`, `createdBy === advisorUserId`, visitor attendee `role === 'attendee'` and `email === submitted`.

### R-11 — Validation failure is visible in-flow

Invalid name/email produces **no** meeting and a **clear** validation failure on the book surface (`role="alert"` or equivalent). Do not use the global API-error toast for a validation miss (PRD 26 FR-2.5). Do not create-then-rollback.

### R-12 — Calendar mirror (best-effort, existing path)

When `scheduledAt` is present, the existing organizer calendar sync (`pushMeetingEvent` in the meetings create path) may run **best-effort** for the **advisor** (organizer). Failure must not fail the booking.

- Email/SMS notifications, ICS attachments, and reminders are **out of scope** (ticket PRD).
- Slot picking / busy intervals are **#2533**. If this ticket is exercised without a slot, `scheduledAt` may be null; confirm still renders (time omitted) and the Join CTA still appears.
- Prefer attaching the slot the #2533 page already chose rather than inventing a second availability read.

### R-13 — What this ticket does not build

Re-stated so implementers do not “complete” #2534 by shipping a sibling:

- Public availability / free-slot API (#2533).
- Anonymous `POST /meetings/:id/join` or dropping `authMiddleware` on `createMeetingRoutes` (#2535).
- Adding `'advisory'` to `KINDS` or touching `TEAM_CEREMONY_KINDS` (#2536).
- Authenticated `BookAdvisorPanel` / `reserveForHost` marketplace path (#2527 / #2545).
- `/advisors` destination; `advisor` as a `MARKETPLACE_LISTING_KINDS` value; `category=advisors` as anything other than a talent filter.
- Payments, packaging, catalog, reschedule/cancel/no-show, recording, multi-advisor, multi-visitor, branded theming, mobile native apps.
- Visitor account creation.

### R-14 — Anti-patterns (fail the review)

A change fails this ticket if it:

1. Writes `kind` other than `advisory`.
2. Sets `createdBy` (or host attendee) to the visitor.
3. Sends the visitor to `/meetings?join=<id>` as the confirm or join URL.
4. Relies on app chrome or a logged-in visitor shell for confirm or join.
5. Punches a hole in `authMiddleware` for the whole meetings router.
6. Defaults team-ceremony chat on for advisory.
7. Creates extra meetings or swapped roles on double-submit.
8. Adds a new chrome-less prefix without going through `NO_CHROME_PREFIXES` + `underPrefix` + `classifyShell` tests.
