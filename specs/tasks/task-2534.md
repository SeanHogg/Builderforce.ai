# PRD: Visitor Advisory Meeting Booking (Chrome-less Confirm + Join)

## Problem & Goal

Visitors currently cannot convert a name and email into a correctly typed advisory meeting without extra fields, wrong participant roles, or a chrome-heavy confirmation/join experience.

**Goal:** Given a visitor’s name and email, create a meeting with `kind=advisory`, the advisor as organizer, and the visitor as attendee, then return a chrome-less confirmation and join link whose URLs match `NO_CHROME_PREFIXES`.

## Target users / ICP roles

- **Visitor:** External participant providing name + email; becomes the meeting attendee.
- **Advisor:** Host of the advisory session; becomes the meeting organizer.
- **Downstream agents / booking surface:** Any flow that collects visitor identity and must emit a valid advisory meeting plus chrome-less links.

## Scope

In scope for this WIP:

- Create one meeting from visitor name + email.
- Persist `kind=advisory`.
- Assign advisor as organizer and visitor as attendee.
- Emit confirmation and join URLs that are chrome-less and prefixed per `NO_CHROME_PREFIXES`.
- Minimal success payload: meeting identity, confirmation URL, join URL.

## Functional requirements

1. **Input:** Require visitor `name` and `email`. Resolve the advisor from the current booking context (authenticated advisor, selected advisor, or equivalent existing organizer source). Reject the request if name, email, or advisor cannot be resolved.
2. **Meeting create:** Create a meeting with `kind` exactly `advisory`. Do not default to other kinds.
3. **Roles:** Set the advisor as organizer. Set the visitor as attendee using the submitted name and email. Do not invert roles or add extra required participants.
4. **Confirmation:** After successful create, return a chrome-less confirmation experience (no app shell / nav chrome). Confirmation URL must use a prefix in `NO_CHROME_PREFIXES`.
5. **Join link:** Return a chrome-less join link for the created meeting. Join URL must use a prefix in `NO_CHROME_PREFIXES`.
6. **Idempotency / identity:** Associate the visitor attendee with the submitted email. Do not require a visitor account as a precondition for create.
7. **Errors:** Surface validation failures (missing name/email, unresolved advisor, create failure) without emitting confirmation or join links.

## Acceptance criteria

- Submitting a valid visitor name + email creates exactly one meeting with `kind=advisory`.
- That meeting’s organizer is the advisor; the visitor is an attendee with the submitted name and email.
- The response includes a confirmation URL and a join URL.
- Both URLs are chrome-less (no standard app chrome) and start with a prefix from `NO_CHROME_PREFIXES`.
- Missing name, missing/invalid email, or unresolved advisor does not create a meeting and does not return confirm/join links.
- Confirmation and join pages do not render the normal application chrome.

## Out of scope

- Scheduling UI, slot picking, timezone selection, or calendar availability.
- Payments, intake forms beyond name + email, or CRM enrichment.
- Multi-advisor, multi-visitor, or recurring meetings.
- Changing meeting kind after create; non-`advisory` kinds.
- Email/SMS notification copy, ICS attachments, or reminders.
- Authenticated visitor accounts, SSO, or attendee profile editing.
- Chrome-less behavior for URLs outside `NO_CHROME_PREFIXES`.
- Reschedule, cancel, or no-show flows.
