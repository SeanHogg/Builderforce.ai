# PRD: Reconcile VSIX pin 2026.9.72 vs live package.json 2026.9.79

**Status:** WIP  
**Related:** Parent epic #2555 (step 6), child #2561 (install VSIX via absolute path and confirm pin), packaging #2560  
**Extension:** `builderforce.builderforce-ai`  
**Pinned version (current epic wording):** `2026.9.72`  
**Live checkout version:** `clients/vscode/package.json` and CHANGELOG = `2026.9.79`  
**Constraint:** #2561 must not bump, downgrade, or re-package. Silent install of 79 must not be treated as #2561 pass.

---

## Problem & Goal

### Problem (historical)

Parent #2555 step 6 and #2561 previously required installing and confirming **builderforce.builderforce-ai@2026.9.72** (the pin that replaced PRD 29’s 2026.9.71 after PRD 27 bumped). The bound `seanhogg/builderforce.ai` checkout’s `clients/vscode/package.json` (and CHANGELOG) read **2026.9.79**. No `.vsix` is in the tree.

If #2560 packages whatever is in `package.json`, it emits **2026.9.79**. A leftover 72 assertion would then fail on purpose. Leaving the pin undecided let downstream agents (1) fail #2561, (2) silently install 79 and falsely pass, or (3) bump/downgrade/re-package inside #2561 — all forbidden.

### Goal (product-locked)

**Chosen: (a).** Package / install / confirm **`builderforce.builderforce-ai@2026.9.79`**. Parent #2555 step 6 and #2561 wording name **2026.9.79** (verified this PM run). Path **(b)** (produce a 72 VSIX / keep wording at 72) is **rejected**. No third version.

#2561 is unblocked for version confirmation and **must** assert **79**. Do not rewrite later CHANGELOG entries to fake a 72 pin. Do not call #2561 passed on a 72 install. Header line “Pinned version (current epic wording): 2026.9.72” is **superseded**; the pin is **2026.9.79**.

## Scope

In scope:

- Require a single parent-epic choice: (a) move pin to 79 and update wording, or (b) obtain a 72 VSIX without changelog rewrite of later entries.
- Define how #2560 and #2561 behave after the choice.
- Define pass/fail so a 79 binary cannot satisfy a 72 assertion (and vice versa).
- Leave #2561 forbidden from bumping, downgrading, or re-packaging.

Out of scope is listed below; this PRD does not itself ship a VSIX or edit `package.json`.

## Functional requirements

### FR1 — Decision is explicit and exclusive

Parent epic must record **exactly one** of (a) or (b). Absence of a recorded choice means #2561 does not start version confirmation.

### FR2 — Path (a): pin moves to live 2026.9.79

If (a) is chosen:

- #2555 step 6 and #2561 wording change from `2026.9.72` to `2026.9.79`.
- #2560 may package the bound checkout as-is (`package.json` / CHANGELOG 2026.9.79).
- #2561 installs that VSIX via absolute path and asserts **2026.9.79**.
- No downgrade of `package.json` or CHANGELOG.

### FR3 — Path (b): keep pin 2026.9.72

If (b) is chosen:

- #2555 / #2561 wording stay at **2026.9.72**.
- A VSIX whose marketplace/extension version is **2026.9.72** is produced or otherwise obtained for install.
- Later CHANGELOG entries (including 2026.9.79) are **not** rewritten, deleted, or collapsed to pretend the tree is still 72.
- #2561 still must not bump, downgrade, or re-package; packaging of 72 is not #2561’s job.

### FR4 — #2561 does not change product version artifacts

#2561 may only: take an existing `.vsix` by absolute path, install it, and confirm the installed version equals the pin in the (updated, if (a)) epic wording. It must not:

- edit `clients/vscode/package.json` or CHANGELOG
- bump or downgrade the extension version
- run a packaging step to “make the assertion pass”

### FR5 — #2560 packaging follows the decision, not the silent default

#2560 must not emit a VSIX whose version disagrees with the recorded pin. Packaging “whatever is in package.json” is valid **only** after (a) is chosen (or if the tree is already 72 and (b) applies). Emitting 79 while #2561 still asserts 72 is a known, intentional fail — not a pass.

### FR6 — No silent 79 pass

Installing `builderforce.builderforce-ai@2026.9.79` while #2561 still requires 72 is **fail**, even if the extension loads. Equating “install succeeded” with “pin confirmed” is forbidden.

### FR7 — Version identity is the installed extension version

Confirmation is the installed identifier `builderforce.builderforce-ai@<pin>`, not merely file presence, install UI success, or a matching filename. Pin and live `package.json` are not assumed equal until the decision lands.

### FR8 — Traceability

The recorded choice, the VSIX path used, and the confirmed version string must be visible to later agents on #2555 / #2560 / #2561. No `.vsix` in the git tree is an input fact, not a reason to skip confirmation.
