## Functional requirements

1. **Inventory the diff.** Confirm files touched are limited to converter package manifests and lockfiles (`package.json`, `package-lock.json` / `yarn.lock` / `pnpm-lock.yaml` under `/webdit/converter`). Flag any unexpected source or config edits.
2. **Resolve the exact new versions.** Record landed `vite` (8.2.2) and `vitest` versions, plus any transitive Vite-family packages Dependabot moved (`@vitejs/plugin-*`, `vite-node`, etc.).
3. **Breaking-change review.** Walk Vite 6/7/8 and corresponding Vitest migration notes for items that apply to this app: `server.fs`, CSS, `optimizeDeps`, `preview`, plugin hook changes, default browser targets, `test.environment`, pool/workers, coverage provider, and snapshot defaults.
4. **Peer and plugin compatibility.** Verify every Vite plugin and Vitest-related package used by the converter declares support for Vite 8 / the new Vitest major. Do not merge if a required plugin is Vite-5-only unless it is upgraded in the same PR or a blocking follow-up is opened and this PR is closed.
5. **Runtime floor.** Confirm local and CI Node (and npm/yarn/pnpm) versions meet Vite 8 / Vitest requirements. If CI is below the floor, either bump the CI Node version as part of landing this change or close the PR as blocked.
6. **Install and lockfile integrity.** Clean install from the PR lockfile must succeed with the repo’s package manager; no unexplained duplicate Vite copies or mixed major versions in the converter tree.
7. **Functional verification in `/webdit/converter`.**
   - Install dependencies.
   - Production build succeeds.
   - Dev server starts and serves the converter entry without transform errors (smoke).
   - Vitest suite runs to completion with no new failures; update snapshots only when the change is an intended Vitest default shift and the new snapshots are reviewed.
   - Existing lint/typecheck scripts still pass.
8. **Security impact.** Compare GitHub Dependabot/advisory data for `vite` 5.4.21 vs 8.2.2 and the old vs new `vitest`. Record CVEs closed, CVEs remaining, and any new high/critical issues. Reject merge if the new versions introduce unmitigated high/critical advisories that the previous versions did not have, unless AppSec explicitly accepts the risk.
9. **Required checks and sign-offs.** GitHub required status checks must be green. Obtain the normal code-owner / maintainer review plus security sign-off when advisories are in play. Do not self-merge past failing or skipped required checks.
10. **Disposition.** If validation and sign-offs pass, merge with the repo’s standard merge method (squash unless policy says otherwise) and delete the head branch if that is repo default. If blocked, close #820, comment the blocker, and file or link the follow-up (plugin upgrade, Node bump, or staged 5→6→7→8 path).
11. **Audit trail.** PR comment or merge message must state versions, checks run, security conclusion, and merge/close reason.
