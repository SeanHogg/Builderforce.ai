# PRD: C4 — Campaign-attributed ROI

**Status:** WIP  
**Slice:** C4  
**Depends on:** C1 `campaignRoi()` (returns `unknown` until this engine exists)  
**Explicit non-solution:** workspace `/api/roi/rollup` (failure already named in `canvasRunComparison.ts`)

## Problem & Goal

Post-send tracking can count opens and clicks, but operators cannot answer whether **this campaign run** made money. Workspace-level ROI (`/api/roi/rollup`) mixes unrelated sends, ads, and pipeline and is already rejected as the comparison source.

C1 ships `campaignRoi()` as a typed hole: it returns `unknown` until attribution exists. This slice is the engine that fills that hole.

**Goal:** For a single campaign run, resolve **spend** and/or **attributed pipeline/revenue** from identifiers already present on the send and ads records, and surface those as first-class post-send metrics. Opens and clicks stay visible as secondary counters, not as ROI.

**Non-goals of framing:** do not invent a new CMO warehouse, do not port BurnRateOS CMO tables, do not redefine workspace rollup.

## Target users / ICP roles

- **Campaign operator / AE-marketer hybrid** — launched this run; needs spend vs. pipeline/revenue on the run they just sent, not a workspace total.
- **RevOps / demand-gen lead** — trusts run-level attribution enough to compare two canvas runs without reconciling ads accounts by hand.
- **Downstream agents / UI** — consume `campaignRoi()` once it is no longer `unknown`; they must not call `/api/roi/rollup` for run comparison.

## Scope

In scope for C4:

- Attribution **engine** bound to **one campaign run id**.
- Inputs: existing **send identifiers** and **ads identifiers** already stored on the run / send / ad objects (no new identity graph, no BurnRateOS table port).
- Outputs written into the C1 ROI shape:
  - `spendCents`
  - `attributedRevenueCents`
  - status that lets `campaignRoi()` leave `unknown` when either side cannot be resolved.
- Post-send tracking UI/API for **this run** shows spend and/or pipeline/revenue as primary economic metrics; opens/clicks remain secondary counters.
- Deterministic, re-runnable computation (same identifiers → same cents), suitable for canvas run comparison.

Out of scope is listed below; do not expand this slice into workspace finance, MQL scoring, or a new ads ETL.

## Functional requirements

1. **Run-scoped resolution**  
   Attribution is keyed by campaign run id. It must not read or write workspace `/api/roi/rollup`. `canvasRunComparison.ts` must not gain a rollup dependency.

2. **Fill C1 contract**  
   `campaignRoi(runId)` remains the only consumer-facing accessor. Until identifiers resolve, it stays `unknown`. When the engine can resolve:
   - `spendCents: number` (integer cents, ≥ 0)
   - `attributedRevenueCents: number` (integer cents, ≥ 0)  
   Partial resolution is allowed: spend without revenue, or revenue without spend, with the unresolved field remaining unset/`unknown` rather than coerced to 0 unless the source explicitly reports zero.

3. **Spend from existing ads identifiers**  
   Use ad account / campaign / ad-set / ad ids (or equivalent) already attached to this run. Sum billed or reported spend for the window that belongs to **this run**, convert to cents. Do not create BurnRateOS CMO tables or a parallel spend ledger.

4. **Pipeline/revenue from existing send identifiers**  
   Use send / message / recipient / opportunity-link identifiers already attached to this run. Attribute pipeline or closed revenue that those identifiers already connect to CRM/pipeline records. Attribution grain is the campaign run, not the workspace and not the person lifetime.

5. **Primary vs secondary metrics**  
   Post-send tracking presents spend and/or attributed pipeline/revenue first. Opens, clicks, and other engagement counters remain available but must not be labeled or ranked as ROI.

6. **Idempotency and freshness**  
   Recomputing for the same run overwrites the previous engine result; it does not double-count. Stale identifier maps (send without ads id, ads without send id) yield `unknown` for the missing side, not a guessed number.

7. **Comparison-safe numbers**  
   Two runs compared in canvas comparison use each run’s `spendCents` / `attributedRevenueCents` only. No silent fallback to workspace rollup if either run is `unknown`.

8. **No new source-of-truth tables**  
   Persist only what C1 already expects (ROI fields on the run or the existing ROI record). Do not port or recreate BurnRateOS CMO schemas.

## Acceptance criteria

- Given a campaign run with resolvable ads identifiers and a non-zero ads spend, `campaignRoi(runId)` is not `unknown` and `spendCents` equals the sum of those ads’ spend in cents for that run’s window.
- Given a campaign run with resolvable send identifiers linked to pipeline/revenue, `attributedRevenueCents` equals that attributed amount in cents for **this run only**.
- Given a run missing ads identifiers, spend stays `unknown` (not `0` unless the ads source reports zero). Given a run missing send-side commercial links, revenue stays `unknown`.
- Post-send tracking for the run shows spend and/or pipeline/revenue as the economic line; opens and clicks are still shown and are not used as the ROI figure.
- `campaignRoi()` is the filled path; no production path for this slice calls `/api/roi/rollup` to populate run ROI.
- `canvasRunComparison.ts` compares run-level `spendCents` / `attributedRevenueCents` (or honest `unknown`); it does not treat workspace rollup as a stand-in.
- Re-running the engine for the same run does not duplicate spend or revenue.
- No BurnRateOS CMO tables, migrations, or ports land in this slice.
- Currency is integer cents; no float dollars in the stored ROI fields.

## Out of scope

- Workspace `/api/roi/rollup` as input, cache, or fallback.
- Porting BurnRateOS CMO tables, schemas, or their aggregation jobs.
- Multi-touch / person-lifetime attribution models, incrementality, or holdout stats.
- Changing how opens/clicks are collected; they stay secondary counters only.
- New ads platform ETL, new CRM sync, or new identifier minting — identifiers must already exist on send + ads records.
- Budget pacing, bid changes, or send-time optimization.
- Cross-run rolled “campaign family” ROI, blended CAC, or finance-grade reconciliation.
- Backfill of historical runs that lack send or ads identifiers (those remain `unknown`).
- UI redesign beyond making run-attributed spend/revenue the primary post-send economic display.

## Requirements

C4 is the **attribution engine** that fills C1’s typed hole. C1 (#2636) owns `campaignRoi(runId)` / `guidedCampaignRun().thisRun` and the numeric ROI formula. C4 **only** resolves integer-cent fields from identifiers **already stored** on this run’s send and ads records, then writes those fields where C1 already expects them. C4 does **not** invent a second ROI accessor, a second status enum, or a workspace finance rollup.

**Hard prerequisite:** C1 `campaignRoi()` returning `unknown` until this engine exists. C3 (#2638) is the send gate — not this slice.

**Existing sources this slice is allowed to read (do not replace them):**

| Side | Table / field | Role |
|---|---|---|
| Spend | `ad_campaigns` (`id`, `connectionId`, `platform`, `externalId`, `utmCampaign`, `lastSyncedAt`) | Ads identifiers already on the run |
| Spend | `ad_insights.spendCents` (integer; natural key `tenantId + campaignId + date`) | Billed/reported spend, daily grain |
| Send | `marketing_campaigns` (`id`, `startedAt`, `completedAt`, `opened`, `clicked`) | This run’s email/SMS campaign + window + secondary counters |
| Send | `marketing_campaign_sends` (`campaignId`, `email`, `phone`, `trackToken`, `externalMessageId`) | Per-recipient send identifiers |
| Pipeline | `marketing_leads` (`campaignId`, `email`, `utm`, `convertedContactRef`) | Existing lead ↔ campaign / send / UTM links |
| Pipeline | `deals` (`amountCents`, `currency`, `stage`, `source`, `primaryContactRef`, `accountRef`) | Existing CRM amounts |

There is **no** FK from `marketing_campaigns` → `ad_campaigns`. C4 MUST NOT create one, mint identifiers, or match on campaign **name**. If the run does not already carry the identifier, that side stays `unknown`.

### R-1 — Run-scoped only

Attribution is keyed by **C1’s campaign run id** (the same `thisRun` C1 exposes). The engine MUST NOT read, write, cache, or fall back to workspace `GET /api/roi/rollup`. No production path for this slice may call `/api/roi/rollup` to populate run ROI. `canvasRunComparison.ts` MUST NOT gain a rollup import, call, or silent fallback — that file remains training-run ranking; campaign comparison uses each run’s filled cents or honest `unknown`.

### R-2 — Fill C1 fields; do not replace C1

C4 writes **only** these C1 `thisRun` fields (integer cents `≥ 0`, or unset/`unknown`):

- `spendCents`
- `attributedRevenueCents`
- `attributedPipelineCents`

`campaignRoi(runId)` remains the **only** consumer-facing accessor. C4 does **not** invent a parallel API, a second status enum, or a ratio/difference formula — C1 R-13 already owns `roi.status` (`unknown` until at least one of spend / attributed pipeline / attributed revenue exists; numeric when at least one exists). C4 reports **per-field** resolution (`number` \| `unknown`). Partial fill is required: spend without revenue, revenue without spend, pipeline without either.

### R-3 — Zero vs `unknown` (do not coerce)

A missing identifier map MUST NOT become `0`.

- **Spend `unknown`:** this run carries no ads identifiers; **or** ads identifiers are present but the ads source is unreadable for the window (`ad_campaigns.lastSyncedAt` is null **and** no `ad_insights` rows exist for those campaigns in the window).
- **Spend `0`:** ads identifiers are present **and** the ads source has been read (`lastSyncedAt` set and/or insight rows exist for the window) **and** `SUM(ad_insights.spendCents)` for that window is `0`.
- **Revenue / pipeline `unknown`:** this run carries no send-side commercial links (no send identifiers that already join to `marketing_leads` / `deals` as in R-6).
- **Revenue / pipeline `0`:** commercial links exist **and** the CRM rows those links resolve to have been read **and** the attributed closed-won (resp. open) sum is `0`.

Stale maps (send without ads id, ads without send id) yield `unknown` on the missing side, not a guessed number.

### R-4 — Spend from existing ads identifiers only

Spend is **billed/reported ads spend**, not budget, not ESP/SMS cost, not social-post cost.

1. Read ads identifiers **already attached to this run** (C1 `thisRun` ads ids): local `ad_campaigns.id` and/or (`platform` + `externalId`) and/or `utmCampaign`. Do not scrape the tenant’s other ad campaigns. Do not match `ad_campaigns.name`.
2. Window = this run’s `startedAt` through `completedAt`, or through now if the run is still in flight. Inclusive calendar dates on `ad_insights.date` as already stored (YYYY-MM-DD, ad-account timezone). If the run has ads identifiers but no resolvable window, spend stays `unknown`.
3. `spendCents = SUM(ad_insights.spendCents)` for those campaigns and dates. Use the stored ledger (`ad_insights`); do not live-call the ad network inside this engine. Ads sync remains the existing `/api/ads/sync` path — C4 does not add ETL.
4. `ad_campaigns.dailyBudgetCents` / `totalBudgetCents` MUST NOT be used as spend. Email/SMS send rows have no spend column — do not invent one.

### R-5 — Currency (no FX)

All stored ROI fields are **integer cents**. No float dollars.

Do **not** convert currencies. If every matched `ad_insights` (resp. `deals`) row for this run shares one `currency`, that is the run’s currency for that side. If a sum would mix currencies, that side stays `unknown` — do not add USD cents to EUR cents.

### R-6 — Pipeline / revenue from existing send identifiers only

Grain is **this campaign run**, not the workspace and not the person lifetime. No multi-touch, incrementality, or holdout.

Allowed joins (all must already exist; do not mint):

- `marketing_campaign_sends.campaignId` = this run’s marketing campaign id.
- `marketing_leads.campaignId` = this run’s marketing campaign id.
- `marketing_leads.email` (or phone) equals a send row on this run.
- `marketing_leads.utm` already carrying this run’s ads `utmCampaign` (the immutable tag from `adUtm.ts` / `ad_campaigns.utmCampaign` — not a name match).
- `deals.source` already storing this run’s campaign id or `utmCampaign`.
- `deals.primaryContactRef` = `marketing_leads.convertedContactRef` for a lead already linked above.

A deal (or lead) that is only linked by person, account, or lifetime — without one of the links above to **this run** — MUST NOT be attributed.

**Bucket (architect maps existing `deals.stage` vocabulary; C4 MUST NOT invent new stages):**

- Closed-won `amountCents` → `attributedRevenueCents`.
- Open (not lost / not disqualified) `amountCents` → `attributedPipelineCents`.
- Lost / disqualified → excluded from both.

Do not use `journey_touchpoints.attribution` (multi-touch; out of scope). Do not use measurement/session breakdown as revenue. Do not use opens or clicks as a commercial amount.

### R-7 — Deterministic and idempotent

Same run id + same identifier maps + same `ad_insights` / `deals` / `marketing_leads` rows → same cents. Recomputing **overwrites** C1’s previous `thisRun` ROI fields. It MUST NOT insert extra `ad_insights` or `deals` rows, MUST NOT increment counters, and MUST NOT double-count. The engine is a pure read-then-overwrite of C1 fields.

### R-8 — Persist only what C1 already expects

Write spend / attributed revenue / attributed pipeline onto the run (or the existing ROI record C1 already uses). **No new source-of-truth tables.** No BurnRateOS CMO schemas, migrations, aggregation jobs, or ports. No new ads platform ETL, no new CRM sync, no new identifier minting, no new identity graph.

### R-9 — Post-send tracking: economics first, engagement secondary

For **this run**, post-send tracking presents `spendCents` and/or `attributedRevenueCents` / `attributedPipelineCents` as the **primary economic line** (whichever fields resolved). `marketing_campaigns.opened` / `clicked` (and per-send `openedAt` / `clickedAt`) remain visible as **secondary counters**. They MUST NOT be labeled ROI, MUST NOT be ranked as the ROI figure, and MUST NOT be fed into `campaignRoi()`. Collection of opens/clicks does not change in this slice. UI redesign beyond this ranking is out of scope.

### R-10 — Comparison-safe numbers

Any comparison of two campaign runs uses each run’s `spendCents` / `attributedRevenueCents` / `attributedPipelineCents` only — or honest `unknown` per field. **No silent fallback** to workspace rollup, to the other run’s numbers, to budget, or to opens/clicks when a field is `unknown`. Training-run comparison in `canvasRunComparison.ts` stays scorecard-based and MUST NOT be taught that `/api/roi/rollup` is campaign ROI.

### R-11 — Historical runs and backfill

Runs that lack send or ads identifiers stay `unknown` on the missing side. This slice MUST NOT backfill or invent identifiers for historical runs.

### R-12 — Tenant isolation

Resolution is tenant-scoped (every named table already has `tenantId`). A run in tenant A MUST NOT read ads, sends, leads, or deals from tenant B.

### R-13 — Out of scope (do not implement in C4)

- Workspace `/api/roi/rollup` as input, cache, or fallback.
- BurnRateOS CMO tables / schemas / jobs.
- Multi-touch / person-lifetime attribution, incrementality, holdout.
- Changing how opens/clicks are collected.
- New ads ETL, new CRM sync, new identifier minting.
- Budget pacing, bid changes, send-time optimization.
- Cross-run “campaign family” ROI, blended CAC, finance-grade reconciliation, FX conversion.
- Treating `dailyBudgetCents` / `totalBudgetCents` or ESP cost as spend.
- Using `canvasRunComparison.ts` as the campaign ROI UI.
- C1’s ROI formula / `roi.status` mapping (C1 owns it).
- C3’s confirm-to-send gate.

### R-14 — Acceptance mapping (QA)

| Given | Then |
|---|---|
| Run with resolvable ads identifiers **and** insight rows in the run window with non-zero `spendCents` | `campaignRoi(runId)` is not overall-`unknown` solely for lack of spend; `thisRun.spendCents` equals `SUM(ad_insights.spendCents)` for those campaigns and dates (integer cents) |
| Run with resolvable send-side commercial links to closed-won deals | `thisRun.attributedRevenueCents` equals that attributed closed-won `amountCents` for **this run only** |
| Run with resolvable links to open (not lost) deals | `thisRun.attributedPipelineCents` equals that open `amountCents` for **this run only** |
| Run missing ads identifiers | `spendCents` stays `unknown` (not `0`) |
| Run with ads identifiers, never synced, no insight rows | `spendCents` stays `unknown` (not `0`) |
| Run with ads identifiers, synced, window sum is 0 | `spendCents = 0` |
| Run missing send-side commercial links | `attributedRevenueCents` and `attributedPipelineCents` stay `unknown` |
| Re-run the engine on the same run | Fields overwritten; spend/revenue not duplicated |
| Post-send view of the run | Spend and/or pipeline/revenue is the economic line; opens/clicks shown and not used as ROI |
| Any C4 code path | Does not call `/api/roi/rollup`; does not add a rollup dependency to `canvasRunComparison.ts` |
| Stored ROI fields | Integer cents only; no float dollars; no mixed-currency sum |
| Schema | No BurnRateOS CMO tables, migrations, or ports |
