# PRD: No N+1 API Calls — Progress Computed Server-Side in List Endpoint

**Status:** WIP  
**Owner:** Product Architecture  
**Priority:** High (performance / correctness)

## Problem & Goal

**Problem.** Rendering VSIX Sessions rows and the Brain chat switcher with linked-ticket `%` must not fan out. A client that `GET /api/brain/chats` and then issues one progress/ticket-health/`tasks.get` call per row multiplies latency, saturates the API, and shows a torn snapshot (list at T0, percents at T1). A server list handler that loops the page and loads tickets per chat is the same bug on the other side of the wire.

The list path **already** has a batch fold: `ChatTicketService.attachChatTicketSummaries` / `summarizeChatsTicketHealth` (fail-soft empty map; `ticketCount` + `ticketProgressPct: number | null`). Epic #2436 still adds `progressPct` (#2437) and paints it in the tree/switcher. This ticket exists so that addition **cannot** grow an N+1 — server or client.

**Goal.** One `GET /api/brain/chats` returns each chat on the page with authoritative, server-computed linked-ticket progress (same rollup as the ticket rail). Clients render list `%` from that payload alone: **zero** per-item progress requests. Server query cost vs page size P is O(1) or O(k), not O(P).

This is **not** a context-window / token meter (#2608). It is **not** a new progress formula (#2551 owns ceremony totals). It is **not** the field/DTO/render work (#2437–#2443).

## Functional requirements

1. **Single-request list.** `GET /api/brain/chats` returns, for each item, identity/summary fields **and** linked-ticket progress (`ticketProgressPct` today; `progressPct` per #2437). Clients MUST be able to render list `%` with this response alone.
2. **Authoritative progress.** Same definition as the ticket rail: `rollupChatTicketHealth` via `summarizeChatsTicketHealth` / `attachChatTicketSummaries`. Rounding, clamping, zero-children, complete, not-started match that path. Do **not** invent a second formula. Ceremony/spec/roadmap `total` weighting is #2551.
3. **No N+1 I/O (server).** Must not issue per-item DB queries or HTTP/RPC to assemble progress for the page. One (or a small constant number of) batched queries keyed by the page’s chat ids. No `Promise.all` over the page for health.
4. **Pagination.** Progress is computed only for chats on the current response, not the entire collection.
5. **Authorization.** Unchanged list ACL. Progress reflects only tickets the caller may see. Hidden children do not leak through counts or percents.
6. **Filters and sort.** Existing list query params still apply. This ticket does not add sort-by-progress.
7. **Empty and unknown.** Empty page: `[]` / `{ chats: [] }`, HTTP 200, **no** progress queries. Unknown / no tickets: `ticketProgressPct` null/omitted (existing `number | null`); real `0` is `0`. Clients never follow up per row. Nullability of new `progressPct` is #2437’s debate — see Requirements R-6.
8. **Compatibility.** Additive. Keep `ticketProgressPct`. List does not replace the ticket-rail / detail progress UI.
9. **Error behavior (fail-soft — overrides the generic draft).** Failure to compute progress MUST NOT fail `GET /api/brain/chats`. Health miss → empty map, list still 200 (existing `summarizeChatsTicketHealth` comment). Clients MUST NOT N+1-retry missing progress. (Ada’s original “fail the list so the client cannot N+1 retry” is rejected; the hard rule is “do not N+1 retry,” not “take the list down.”)
10. **Observability.** List endpoint: item count + progress-compute time (or equivalent) so N+1 / slow aggregation is visible.
11. **Clients.** `listBrainChats` / Sessions tree / chat switcher: **zero** per-item progress requests after the list GET. #2441 may re-GET the **list**, not N chat-health URLs.

## Acceptance criteria

- Rendering a list of N chats (N ≥ 1, typical page and max page / `listBrainChats` limit) produces **one** `GET /api/brain/chats` and **zero** per-item progress, ticket-health, or `tasks.get` requests.
- Opening the Brain chat switcher over that list produces **zero** additional per-row progress requests (#2443 binds in memory).
- For a fixture set covering not-started, in-progress, complete, zero-children, and unauthorized-child cases, list progress equals the ticket-rail / `rollupChatTicketHealth` result for the same user and the same chats (shared fields; documented rounding). Formula not re-derived here.
- Database/query traces for a page of size P show O(1) or O(k) queries w.r.t. P (k small constant), not O(P). Empty `chatIds` issues no progress query.
- Pagination: next page / next limit window progress matches those chats’ rail; off-page chats are not loaded for progress.
- A user who cannot access a parent chat does not see it; a user who can access a chat but not some children sees progress computed only from visible children, consistent with the rail.
- Two chats with different rollups have **different** percents on the list payload (no single value stamped on every row).
- Fail-soft: health failure still returns the chat list (200) with progress omitted/empty; the test client does not N+1 retry.
- Contract: list item schema already has or will have progress (`ticketProgressPct` now; `progressPct` via #2437). Client checklist: no list-page fan-out.
- Increasing page size does not multiply outbound HTTP or per-chat DB calls linearly.
- p95 list latency: no agreed numeric budget on this ticket; architect/SRE may set one. The **hard** bar is the O(1)/O(k) I/O bar, not a guessed millisecond cap.

## Requirements

This ticket owns the **no-N+1 constraint** for linked-ticket progress on the Brain **chat list**. It does not add the list field (#2437), the client DTO (#2438), VSIX row render (#2439 / #2442), switcher formatter (#2440), switcher per-row binding (#2443), ticket-health refresh (#2441), or ChatTicketService ceremony/spec/roadmap totals (#2551).

GitHub file reads were rate-limited (403) for part of this BA pass. Requirements are grounded in: epic #2436; sibling PRDs (#2437, #2442, #2443); `search_code` hits on `ChatTicketService.summarizeChatsTicketHealth`, `attachChatTicketSummaries`, and `brainRoutes.ts`; and `listBrainChats` in `clients/vscode/src/bfApi.ts`. Architect verifies internals in Design.

### R-1 — User story

**As a** user of the VSIX Sessions tree or Brain chat switcher, **I want** a single `GET /api/brain/chats` to return each chat together with its linked-ticket progress, **so that** the list can render `%` without a second request per row.

### R-2 — Endpoint in scope (locked)

| Item | Rule |
| --- | --- |
| HTTP | Existing `GET /api/brain/chats` only |
| Handler | Current list path in `api/src/presentation/routes/brainRoutes.ts` (the one that already calls `ChatTicketService.attachChatTicketSummaries`) |
| Not in scope | Project 360, task/OKR list endpoints, `GET` chat-by-id, ticket-rail-by-chat, `tasks.get`, marketplace, advisors |

Detail `GET` may keep using `attachChatTicketSummaries` for **one** id. That is not N+1. N+1 is: list of N chats → N extra progress loads (HTTP or DB).

### R-3 — Metric (locked)

- **What it is:** linked-ticket **rollup** for tickets attached to **that** chat.
- **Server helpers (reuse, do not fork):** `ChatTicketService.summarizeChatsTicketHealth(tenantId, chatIds)` (batch, keyed by the page’s ids) and `attachChatTicketSummaries` (folds `ticketCount` + `ticketProgressPct` onto rows). Rollup function: `rollupChatTicketHealth` — **not** a naïve completed/total mean invented on this ticket.
- **List field #2437 adds:** `progressPct`. **Existing field to keep:** `ticketProgressPct` (and `ticketCount`). Do not rename or drop `ticketProgressPct`.
- **What it is not:** context-window fill, tokens, billing, cost, quality. Context-window is gap #2608.

### R-4 — Server: no per-row I/O (this ticket’s core)

For a returned page of size **P**:

1. Progress MUST be assembled with a **batched, set-based** load keyed by that page’s chat ids (one call to `summarizeChatsTicketHealth` / `attachChatTicketSummaries`, which themselves MUST stay O(1) or O(k) queries w.r.t. P, k a small constant).
2. **Forbidden:** `for (chat of page) { query or RPC for that chat’s tickets/progress }`; `Promise.all(page.map(id => perChatHealth(id)))`; per-row `tasks.get`; per-row HTTP to a progress/ticket-rail URL.
3. `search_code` on `ChatTicketService.ts` shows **no** `Promise.all` today. Adding one over the page is a regression of this ticket.
4. Empty `chatIds` (`[]`): helpers already return an empty map / fold nothing — **zero** extra queries. Preserve that.

#2437 may add `progressPct` onto the same fold. It MUST read the batch summary already computed for the page (`summary?.pct` / `ticketProgressPct` from the map). It MUST NOT issue a second per-id health pass.

### R-5 — Page-scoped compute

Compute progress **only** for chats in the current list response. Do not load the tenant’s entire chat corpus, all tickets, or off-page ids “just in case.” Pagination / limit (e.g. VSIX `listBrainChats(..., limit = 50)`) is unchanged (#2436 out of scope: cursor vs offset).

### R-6 — Empty / unknown / zero

| State | Server | Client (owned by render tickets; listed so N+1 is not used as a fallback) |
| --- | --- | --- |
| Empty page | HTTP 200, `{ chats: [] }` (or existing empty collection). **No** progress queries | Nothing to render |
| Chat with no linked tickets / unknown | `ticketProgressPct` is already `number \| null` on `attachChatTicketSummaries`. Prefer **omit / null** (epic: never coerce with `?? 0`) | Omit metric. **Never** fan-out to “find out” |
| Real rollup `0` | Send `0` | Render `0%` (` · 0%` / `0% · title`) |

**Nullability vs #2437:** #2437 BA text currently says never-null `progressPct: summary?.pct ?? 0`. The epic, `attachChatTicketSummaries`’s `number \| null`, and #2440/#2443 say omit if unknown. **This ticket does not pick.** Either shape is compatible with no-N+1. Do **not** invent a third policy, and do **not** treat missing as a signal to N+1 retry.

### R-7 — Client: zero per-item progress requests

After **one** successful `GET /api/brain/chats`:

- VSIX Sessions (`clients/vscode/src/sessionsTree.ts` via `listBrainChats` in `bfApi.ts`) MUST paint `ticketProgressPct` / `progressPct` from that payload. **Forbidden:** per-row `tasks.get`, per-chat ticket-health GET, or a second chats GET per row.
- Brain-ui switcher (`chatSwitcherLabel` / #2440 / #2443) MUST bind each row to **that row’s** field already on the list record. **Forbidden:** fetching progress when opening the dropdown.
- #2441 (refresh on ticket health changes) MAY re-call the **same list** endpoint (or an existing non-per-row health channel). It MUST NOT refresh by N per-chat progress GETs.

Older servers that omit the field: omit the metric (forward compatible). Do not probe per chat.

### R-8 — Authorization

Unchanged list ACL: a caller who cannot see a chat does not receive it. Progress MUST NOT leak unauthorized child tickets through counts or percents (same visibility as the ticket rail / `rollupChatTicketHealth` for that user). This ticket does not redesign ACL.

### R-9 — Fail-soft (overrides Ada FR9)

`summarizeChatsTicketHealth` is documented **fail-soft**: a health miss returns an empty map so the **chat list still renders**. #2437 says keep fail-soft.

**Decision:** do **not** 500 / fail the whole `GET /api/brain/chats` because progress compute failed. Ada’s generic FR9 (fail the list, or partial-error the page, so the client does not N+1 retry) is **wrong for this product**. The chat list is more important than the percent.

**Hard rule that replaces FR9’s intent:** clients MUST NOT interpret missing / null / failed progress as a reason to issue per-chat progress requests. Missing = omit (or `0` only if #2437 ships always-present `0`). No N+1 retry, no silent fallback estimator.

### R-10 — One snapshot

Identity/summary fields and progress on that response are one server snapshot. Clients MUST NOT stitch list-at-T0 + per-row progress-at-T1 to render the list.

### R-11 — Compatibility

Additive. Keep existing list fields (`ticketCount`, `ticketProgressPct`, titles, timestamps, participants, etc.). Do not break content-type. Do **not** remove the ticket-rail / detail progress path — list does not replace deep ticket UI. Do not change ceremony/spec/roadmap `total` weighting (#2551).

### R-12 — Observability

List handler SHOULD log or metric (a) returned chat count and (b) progress-compute time (or equivalent), so an N+1 or slow aggregation regression is visible. Architect names the metric. No new product analytics warehouse.

### R-13 — Test / proof contract (developer + QA)

These are acceptance probes, not an implementation sketch:

1. Client: rendering a list of N chats (typical page and max page) produces **one** `GET /api/brain/chats` and **zero** per-item progress/ticket-health/task requests.
2. Server: query trace for page size P is O(1) or O(k) vs P, not O(P). Empty page: no progress query.
3. Two chats with different rollups: payload percents **differ** (guards against stamping one value on every row — see #2443).
4. Page 2 (or next limit window): progress matches those chats’ rail/detail rollup; off-page chats are not loaded for progress.
5. Fixture parity (same user, same chats) with the existing rail/rollup for not-started, in-progress, complete, zero-children, unauthorized-child. Formula stays ChatTicketService / #2551; this ticket only requires the **list uses that same batch function**.
6. Increasing page size does not multiply outbound HTTP or per-chat DB calls linearly.
7. Fail-soft: simulated health failure still returns the chat list (200), with progress omitted or empty map — and the test client still does not N+1.
