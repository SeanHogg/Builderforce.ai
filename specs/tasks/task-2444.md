# PRD: No N+1 API Calls — Progress Computed Server-Side in List Endpoint

**Status:** WIP  
**Owner:** Product Architecture  
**Priority:** High (performance / correctness)

## Problem & Goal

**Problem.** VSIX Sessions (`sessionsTree`) and the Brain chat switcher (`chatSwitcherLabel`) must show linked-ticket `%` on every chat row. If they `GET /api/brain/chats` and then fan out one progress / ticket-health / `tasks.get` per row, list open becomes N+1: latency multiplies, the API saturates, list vs. progress snapshots diverge, and cost grows with page size.

**Goal.** `GET /api/brain/chats` is the **only** network hop needed to paint list `%`. Progress is computed server-side in that request via the existing batched `ChatTicketService` path (`summarizeChatsTicketHealth` / `attachChatTicketSummaries` / `rollupChatTicketHealth`), with bounded query cost (no per-row DB or HTTP). Clients bind `%` from the list payload (`ticketProgressPct` today; `progressPct` when #2437 ships) and **never** issue per-item progress calls for the list/switcher.

This ticket is the **N+1 / batching / fail-soft constraint** for epic **#2436**. It does **not** own adding `progressPct`, the DTO field, or the `%` render (see Scope / R-14).

## Functional requirements

1. **Single-request list.** `GET /api/brain/chats` returns, for each item, identity/summary fields **and** linked-ticket progress (`ticketProgressPct` today; `progressPct` per #2437). Clients MUST be able to render list `%` with this response alone.
2. **Authoritative progress.** Same definition as the ticket rail: `rollupChatTicketHealth` via `summarizeChatsTicketHealth` / `attachChatTicketSummaries`. Rounding, clamping, zero-children, complete, not-started match that path. Do **not** invent a second formula. Ceremony/spec/roadmap `total` weighting is #2551.
3. **No N+1 I/O (server).** Must not issue per-item DB queries or HTTP/RPC to assemble progress for the page. One (or a small constant number of) batched queries keyed by the page’s chat ids. No `Promise.all` over the page for health.
4. **Pagination.** Progress is computed only for chats on the current response, not the entire collection.
5. **Authorization.** Unchanged list ACL. Progress reflects only tickets the caller may see. Hidden children do not leak through counts or percents.
6. **Filters and sort.** Existing list query params still apply. This ticket does not add sort-by-progress.
7. **Empty and unknown.** Empty page: `[]` / `{ chats: [] }`, HTTP 200, **no** progress queries. Unknown / no tickets: `ticketProgressPct` null/omitted (existing `number | null`); real `0` is `0`. Clients never follow up per row. Nullability of new `progressPct` is #2437’s debate — see Requirements R-6.
8. **Compatibility.** Additive. Keep `ticketProgressPct`. List does not replace the ticket-rail / detail progress UI.
9. **Error behavior (fail-soft — overrides the generic draft).** Failure to compute progress MUST NOT fail `GET /api/brain/chats`. Health miss → empty map, list still 200 (existing `summarizeChatsTicketHealth` comment). Clients MUST NOT N+1-retry missing progress. (Ada’s original “fail the list so the client cannot N+1 retry” is rejected; the hard rule is “do not N+1 retry,” not “take the list down.”)
10. **Observability.** List endpoint: item count + progress-compute time (or equivalent) so N+1 / slow aggregation is visible.
11. **Clients.** `listBrainChats` / Sessions tree / chat switcher: **zero** per-item progress requests after the list GET. #2441 may re-GET the **list**, not N chat-health URLs.

## Acceptance criteria

- Rendering a list of N chats (N ≥ 1, typical page and max page / `listBrainChats` limit) produces **one** `GET /api/brain/chats` and **zero** per-item progress, ticket-health, or `tasks.get` requests.
- Opening the Brain chat switcher over that list produces **zero** additional per-row progress requests (#2443 binds in memory).
- For a fixture set covering not-started, in-progress, complete, zero-children, and unauthorized-child cases, list progress equals the ticket-rail / `rollupChatTicketHealth` result for the same user and the same chats (shared fields; documented rounding). Formula not re-derived here.
- Database/query traces for a page of size P show O(1) or O(k) queries w.r.t. P (k small constant), not O(P). Empty `chatIds` issues no progress query.
- Pagination: next page / next limit window progress matches those chats’ rail; off-page chats are not loaded for progress.
- A user who cannot access a parent chat does not see it; a user who can access a chat but not some children sees progress computed only from visible children, consistent with the rail.
- Two chats with different rollups have **different** percents on the list payload (no single value stamped on every row).
- Fail-soft: health failure still returns the chat list (200) with progress omitted/empty; the test client does not N+1 retry.
- Contract: list item schema already has or will have progress (`ticketProgressPct` now; `progressPct` via #2437). Client checklist: no list-page fan-out.
- Increasing page size does not multiply outbound HTTP or per-chat DB calls linearly.
- p95 list latency: no agreed numeric budget on this ticket; architect/SRE may set one. The **hard** bar is the O(1)/O(k) I/O bar, not a guessed millisecond cap.

## Requirements

**R-1 — Single list GET paints `%`.** After `GET /api/brain/chats` (VSIX `listBrainChats` or equivalent Brain client), the response body for each returned chat includes linked-ticket progress (`ticketProgressPct: number | null` today; `progressPct` when #2437 lands). Sessions tree and chat switcher MUST render list `%` from that payload alone. **Zero** follow-up requests per chat for progress, ticket-health, or `tasks.get`.

**R-2 — Same formula as the ticket rail.** List progress is `rollupChatTicketHealth` applied by `ChatTicketService.summarizeChatsTicketHealth` / `attachChatTicketSummaries`. Same rounding, clamping, not-started, in-progress, complete, and zero-children behavior as the rail. Do **not** invent a second percent. Ceremony/spec/roadmap `total` weighting stays **#2551**.

**R-3 — Server I/O is O(1) / O(k) in page size P.** `summarizeChatsTicketHealth(chatIds)` MUST load health with a constant (small k) number of set-based queries keyed by the page’s chat ids (IN / join / aggregation). Forbidden: a loop or `Promise.all` that runs one query or RPC **per chat id**. Query traces for page size P show O(1) or O(k) statements, not O(P). Empty `chatIds` MUST return an empty map and issue **no** progress query.

**R-4 — Progress only for the returned page.** Compute health only for chat ids in the current list response. Off-page chats MUST NOT be loaded for progress. Pagination / `listBrainChats` limit is unchanged.

**R-5 — Fail-soft list; no client N+1 retry.** If ticket-health computation throws, `GET /api/brain/chats` still returns HTTP 200 with the chat list. Health miss → empty map (existing `summarizeChatsTicketHealth` warn + empty Map). Clients MUST treat missing/`null` progress as unknown and MUST NOT fan out per-row retries. Ada’s draft “fail the whole list so the client cannot N+1” is **rejected**: the invariant is “do not N+1 retry,” not “take chats down.”

**R-6 — Unknown vs real 0% (keep `ticketProgressPct`).** `ticketProgressPct` stays `number | null`. Omit/`null` = unknown (no tickets / health miss). Real zero = `0` and MUST be distinguishable from unknown (epic #2436: never `?? 0`; `0` shows as ` · 0%`). This ticket does **not** decide whether new `progressPct` is never-null (`?? 0`) or omit-if-unknown — that is **#2437**. Suffix placement (description/meta, not title) is **#2439/#2442**. Keep shipping `ticketProgressPct` even after `progressPct` exists.

**R-7 — Two chats, two percents.** Attachment is per chat id. Distinct rollups MUST appear as distinct values on distinct rows. Forbidden: one percent stamped on every row, or a page-level aggregate in place of per-chat progress.

**R-8 — Authorization, no leak.** Unchanged list ACL: a caller who cannot see a chat does not receive it. Progress counts/percents MUST NOT include tickets/children the caller cannot see. List progress for a given user MUST match the rail for the same user and chats.

**R-9 — Empty page.** Empty list: `[]` / `{ chats: [] }`, HTTP 200, **no** progress queries, **no** client follow-up.

**R-10 — Additive contract.** Existing list fields, filters, sort, pagination, and auth stay. Do not break `ticketCount` / `ticketProgressPct`. Do not replace the ticket-rail UI. Do not require a new breaking content-type.

**R-11 — Clients: no fan-out, including refresh.** `clients/vscode/src/bfApi.ts` (`listBrainChats`), `sessionsTree.ts`, and `packages/brain-ui` chat-switcher path (`chatSwitcherLabel` / LiveActivity consumers) MUST NOT add per-row progress fetches. **#2441** may re-GET **`/api/brain/chats`** (or the existing list helper) when ticket health changes; it MUST NOT N+1 chat-health URLs. Switcher **#2443** binds in memory from the list payload.

**R-12 — Observability.** List path SHOULD record returned chat count and progress-compute duration (or equivalent) so an N+1 or slow aggregation is visible. No new dashboard required on this ticket.

**R-13 — Proof.** Developer/QA MUST show: (a) contract or handler test that list items carry progress without a second endpoint; (b) query/trace or unit proof that P chats do not issue P health queries; (c) empty-`chatIds` issues no progress query; (d) health failure still returns the list; (e) two chats with different rollups differ on the payload. Load-test millisecond budgets are optional; the hard bar is (b).
