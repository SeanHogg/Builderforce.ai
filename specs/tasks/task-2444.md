# PRD: No N+1 API Calls — Progress Computed Server-Side in List Endpoint

**Status:** WIP  
**Owner:** Product Architecture  
**Priority:** High (performance / correctness)

## Problem & Goal

**Problem.** Clients that render a list of parent resources currently fetch the list, then issue one additional request per row to obtain progress. That N+1 pattern multiplies latency, saturates the API, produces inconsistent snapshots (list vs. progress fetched at different times), and scales poorly as list size or concurrency grows.

**Goal.** A single list endpoint returns each resource together with authoritative, server-computed progress so the client never needs a per-item progress call to render the list. Progress is calculated in the same request/transaction as the list, using the same rules as the existing detail/progress path, with bounded query cost (no per-row round trips to the database or downstream services).

## Target users / ICP roles

- End users of list/index screens (learners, operators, PMs, admins) who see progress in tables, cards, or dashboards.
- Frontend clients (web/mobile) that currently fan out progress fetches after `GET` list.
- Backend/API consumers (internal services, BFF) that assemble list UIs or reports.
- Platform/SRE: reduced request volume and p95/p99 on list pages.

## Scope

In scope:

- Extend the existing list/index endpoint for the resource that currently exhibits N+1 progress fetches.
- Compute progress on the server for every item in the returned page (and for empty lists: return an empty collection, not extra calls).
- Return progress in the list payload using the same field names, types, and semantics as the canonical progress representation (detail or dedicated progress resource).
- Preserve existing list filters, sort, pagination, authorization, and field visibility.
- Compute progress with set-based queries (joins/aggregations/batch loads), not one query or remote call per list item.
- Keep list and progress consistent for the duration of that request (one snapshot).
- Document the response shape so clients can delete the per-item progress fan-out.

## Functional requirements

1. **Single-request list.** `GET` list returns, for each item, identity/summary fields **and** progress. Clients must be able to render list progress with this response alone.
2. **Authoritative progress.** Server-side progress uses the same definition as the existing progress source of truth (completed vs. total, percent, status, timestamps, blockers, or equivalent). Rounding, clamping, and edge cases (zero denominator, not started, complete, archived) match the detail path.
3. **No N+1 I/O.** Implementation must not issue per-item DB queries or HTTP/RPC calls to assemble progress for the page. Prefer one (or a small constant number of) batched queries keyed by the page’s IDs.
4. **Pagination.** Progress is computed only for items on the current page, not the entire collection, unless a documented aggregate is explicitly requested.
5. **Authorization.** Progress reflects only data the caller is allowed to see. Hidden or unauthorized child work does not leak through counts or percents. Users who cannot see a parent do not receive it (unchanged list ACL).
6. **Filters and sort.** Existing list query params still apply. If the product already supports sort/filter by progress, those operate on the same server-computed values returned in the payload.
7. **Empty and partial states.** Empty page: `[]` / empty collection, HTTP 200 (unless the existing contract differs). Items with no child work: explicit zero/not-started progress, not omitted fields that force a follow-up call.
8. **Compatibility.** Additive change. Existing list fields remain. Progress may already exist on detail; list must not require a new breaking content-type unless versioning is already in use.
9. **Error behavior.** Failure to compute progress for the page fails the list request (or returns a documented partial-error contract applied to the whole page). Do not return the list without progress and expect the client to N+1 retry.
10. **Observability.** Log/metric the list endpoint with item count and progress-compute time so regressions of N+1 or slow aggregations are visible.

## Acceptance criteria

- Rendering a list of N items (N ≥ 1, including typical page size and max page size) produces **one** list request and **zero** per-item progress requests.
- For a fixture set covering not-started, in-progress, complete, zero-children, and unauthorized-child cases, list progress equals detail/progress for the same user and the same items, byte-for-byte on the shared progress fields (or within documented rounding).
- Database/query traces for a page of size P show O(1) or O(k) queries w.r.t. P (k small constant), not O(P).
- Pagination: page 2 progress matches those items’ detail progress; items not on the page are not loaded for progress.
- A user who cannot access a parent does not see it; a user who can access a parent but not some children sees progress computed only from visible children, consistent with detail.
- Contract tests or OpenAPI/JSON schema include progress on the list item schema; client checklist: remove list-page fan-out.
- p95 list latency on a representative page size does not regress beyond an agreed budget versus the old list-without-progress call (progress compute included).
- Load test or equivalent demonstrates that increasing page size does not multiply outbound calls linearly.

## Out of scope

- Redesign of progress semantics, new progress types, or gamification.
- Real-time/websocket progress push, polling intervals, or client-side optimistic progress.
- Computing progress for resources **not** on the current list page (global rollups, analytics warehouses, admin exports).
- Changing pagination model, cursor vs. offset, or default page size.
- Removing the detail or dedicated progress endpoint (list does not replace deep progress UIs).
- Client visual redesign of the list (only the data contract required to stop N+1).
- Cross-service fan-out that is not required for current list progress (unless it is the current N+1 source; then it must be batched, not redesigned as a new product).
- Backfill/migration of historical progress tables unless required for correct list aggregation.
