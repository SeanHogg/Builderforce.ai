# PRD: Volunteer / Pro-Bono Badge on Talent and Marketplace Cards

## Problem & Goal

Advisors who mark sessions as unpaid (price stored as `0` in P0) are not distinguishable from paid listings on talent and marketplace cards. Seekers cannot tell which advisors offer volunteer / pro-bono sessions without opening a profile or checkout flow.

**Goal:** Show a volunteer / pro-bono badge on talent cards and marketplace cards whenever the advisor’s sessions are unpaid (`P0 = 0`). Hide the badge in all other cases. Downstream agents should implement display-only behavior driven by existing P0 data—no new pricing model.

## Target users / ICP roles

- **Advisor (talent):** Marks sessions unpaid; expects public cards to reflect pro-bono status.
- **Seeker / buyer:** Browses talent and marketplace cards; uses the badge to find unpaid sessions.
- **Marketplace operator / internal QA:** Verifies badge presence matches P0, including paid ↔ unpaid toggles.

## Scope

- Talent cards (list, grid, search, recommendation surfaces that render a talent card).
- Marketplace cards (listing cards for advisor sessions / offerings).
- Badge visibility strictly derived from unpaid state: session price stored as `0` in P0.
- Badge hidden when P0 is missing, null, negative, or any value other than `0`.
- Live update when an advisor changes a session from unpaid to paid (or the reverse) and the card is next rendered or refreshed.
- Accessible name and visual treatment consistent with existing card badge patterns (icon + short label).

## Functional requirements

1. **Source of truth:** Treat a session as unpaid / volunteer / pro-bono if and only if its price in P0 is exactly `0` (numeric zero). Do not infer unpaid status from copy, tags, or discounts.
2. **Show badge:** If the card’s subject session (or the advisor’s featured/default session used by that card) is unpaid per (1), render a volunteer / pro-bono badge on the card.
3. **Hide badge:** If P0 is not `0`, omit the badge entirely (no empty chip, placeholder, or “paid” counterpart).
4. **Surfaces:** Apply the same rule to talent cards and marketplace cards. Do not show the badge on unrelated UI (profile header, checkout, invoices) unless those surfaces already reuse the same card component.
5. **Advisor with mixed inventory:** Badge the individual card/listing whose session has `P0 = 0`. Do not badge every card for that advisor if other sessions have non-zero P0.
6. **Copy:** Badge label is “Pro bono” (or the product’s existing volunteer synonym if one is already in the design system). Tooltip or accessible name: “Unpaid / volunteer session”.
7. **No write path:** This work does not change how advisors set unpaid sessions or how P0 is stored; it only reads P0 for display.
8. **Performance:** Badge evaluation is a cheap field check; no extra network round-trip beyond data already loaded for the card.

## Acceptance criteria

- Given a talent or marketplace card whose session has `P0 = 0`, the volunteer / pro-bono badge is visible on first paint.
- Given a card whose session has `P0 ≠ 0` (including null/absent), the badge is not in the DOM.
- Given an advisor with one unpaid session and one paid session, only the unpaid session’s card shows the badge.
- Given an advisor updates a session from unpaid (`P0 = 0`) to paid (non-zero P0), the badge is gone after refresh / next card render; the reverse update shows the badge.
- Badge is readable at default card sizes, has a non-color-only affordance, and exposes an accessible name equivalent to unpaid / volunteer session.
- Existing paid-card layout, click-through, and ranking are unchanged aside from the badge slot.
- Automated or QA checks cover: `P0 = 0` → visible; `P0 = 1` (or any positive) → hidden; P0 unset → hidden; mixed inventory → per-card.

## Out of scope

- Changing how unpaid sessions are created, priced, or persisted in P0.
- Filtering, sorting, or search facets for pro-bono listings.
- Badges on profiles, booking, checkout, receipts, emails, or admin tools (unless they reuse the same card).
- Compensation, tax, credits, or “free trial” semantics; `P0 = 0` is unpaid volunteer only.
- Localization beyond the existing card i18n pipeline, analytics events, or new advisor settings.
- A paid / “from $X” badge, or badging the advisor globally when only some sessions are unpaid.

## Requirements

This ticket is **display-only**. It does not add a pricing model, listing kind, write path, or filter. Downstream roles (architect, developer, QA, validator) must treat these as the contract. Grounded in P0 #2528 (`freelancer_profiles.session_price_cents`) and A0 talent Book-CTA already on `main`. Do **not** dump a `specs/tasks/task-2584.md` conceptual stand-in — requirements live on **this ticket PRD**.

### Locked decisions

1. **Advisor remains a talent mode.** No `/advisors` route, no `PEOPLE_OBJECT_KINDS` advisory value, no `MARKETPLACE_LISTING_KINDS` `"advisor"`. Badge the existing talent card and the existing marketplace listing card that already render talent / advisor inventory (`/marketplace?family=talent`, and any advisors-category listing that **reuses** the talent card renderer).
2. **Source of truth is P0 session price, not hourly rate.** The unpaid predicate is `session_price_cents === 0` (integer cents on `freelancer_profiles`, already specified by #2528). Do **not** read `hourlyRateCents`, bio copy, tags, discounts, or a new column.
3. **`0` and `null` are different.** `#2528`: `0` = volunteer / complimentary; `null` omits the session-price row. This badge shows **only** for numeric `0`. `null` / absent / undefined → **no badge**.
4. **One price per talent profile.** P0 stores a single `session_price_cents` on the profile. Per-session / per-`booking_services` overrides are out of scope (#2528). Mixed-inventory (PM AC) means **two cards with two bindings** (two profiles, or two listing rows each carrying their own `session_price_cents`) — badge independently. Do **not** roll “this advisor has a $0 somewhere” onto every card for that person.
5. **Read path only.** Advisors already mark unpaid by saving price `0` in P0. This ticket does not change profile edit, persistence, checkout, or payouts.
6. **No discovery facet.** Do not add a pro-bono / unpaid filter, sort, or search chip. That is not #2586 and is out of scope here.

### R-1 — Unpaid predicate (source of truth)

- Treat the card’s bound session as unpaid / volunteer / pro-bono **if and only if** the integer field `session_price_cents` on the card payload is **exactly numeric `0`**.
- The card payload must carry the P0 field already loaded for the talent listing / profile DTO. Architect/developer **thread `session_price_cents` through** if the card DTO does not yet expose it; they must **not** invent a parallel price, a string flag, or a second fetch.
- **Hide** the badge when `session_price_cents` is:
  - `null`, `undefined`, or omitted from the payload
  - any positive integer (`1`, `100`, …)
  - any negative integer (P0 validation should reject these; if a stale row leaks, still hide)
  - non-numeric (`NaN`, `""`, `"free"`, `"0"` as a non-coerced string that is not the JSON number `0`)
- Do **not** infer unpaid status from copy, tags, “free trial”, coupons, or `hourlyRateCents === 0`.

### R-2 — Show the badge

- If R-1 is true, render a volunteer / pro-bono **badge in the existing card badge slot** on first paint of that card.
- Visible label: **`Pro bono`** (product string; wire through the existing card i18n catalog — do not hard-code a one-off English-only node if sibling badges already go through i18n).
- Accessible name and tooltip: **`Unpaid / volunteer session`**.
- Visual: icon **plus** short label, matching existing card badge patterns. Not color-only. Readable at default list and grid card sizes, both themes, existing locales.
- Never present unpaid as **`$0`** or a paid-looking `$0.00` chip. Semantically the same volunteer treatment as #2528’s public profile (“volunteer / complimentary”), but the **card chip copy is `Pro bono`**.

### R-3 — Hide the badge

- If R-1 is false, **omit the badge entirely**: no empty chip, spacer, placeholder, “Paid” counterpart, or `from $X` badge.
- Existing paid-card layout, click-through, ranking, and Book/Hire CTAs are unchanged aside from the occupied badge slot when R-1 is true.

### R-4 — Surfaces (talent cards + marketplace cards)

Apply the same R-1 predicate to every surface that already renders a **talent card** or a **marketplace listing card** for talent / advisor inventory, including:

- Talent list / grid / search / recommendation cards
- Marketplace listing cards on `/marketplace?family=talent` (A0 Book CTA, including price `0`, is already on `main`)
- Advisors-category listing **only if** it reuses the same talent / marketplace card component (P0 #2527: reuse talent profile renderer; primary CTA Book)

**Do not** add the badge to profile header, booking, checkout, invoices, receipts, emails, or admin tools **unless** those surfaces already mount the same card component (in which case the badge comes along for free).

**Do not** create a new advisor card, a new listing kind, or a new people-object kind to hang the badge on.

### R-5 — Mixed inventory (per-card, not per-advisor)

- Badge the **individual card** whose bound `session_price_cents === 0`.
- A second card bound to a non-zero or null price for a different profile/listing **must not** show the badge, even if the same human could theoretically offer both.
- Because P0 is one `session_price_cents` per `freelancer_profiles` row, all cards bound to **that same profile** share the same badge state. That is correct. Do not invent per-service prices here.
- Do **not** badge “the advisor” globally.

### R-6 — Refresh semantics (no extra network)

- Badge evaluation is a cheap field check on data **already loaded** for the card. No extra round-trip, no dedicated unpaid endpoint, no polling, no websocket requirement.
- When an advisor updates P0 from `0` → paid (or the reverse) and the card is **next rendered or refreshed** from updated listing/profile data, the badge appears or disappears accordingly. Live in-place mutation without a data refresh is **not** required.

### R-7 — Prerequisite and data threading

- **Hard data owner:** #2528 (`session_price_cents` on `freelancer_profiles`; `0` = volunteer; `null` omits).
- If #2528 has not yet landed the column or the public listing DTO, this ticket is **blocked on that field existing on the card payload** — report blocked; do not substitute `hourlyRateCents` or a client-only stub.
- A0 on `main` already books talent listings including price `0`. This ticket only **labels** that state on the card.

### R-8 — Accessibility, i18n, themes

- Accessible name equivalent to unpaid / volunteer session (R-2). Screen readers must not depend on color.
- Use the **existing card i18n pipeline** (P0: five locales, both themes). Do not add a new i18n system, analytics events, or advisor settings.
- Both light and dark themes; default list and grid breakpoints.
