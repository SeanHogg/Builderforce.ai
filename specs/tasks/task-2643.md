# PRD: Restore `canvasChange.ts` after placeholder overwrite (P0 merge-gate)

## Problem & Goal

Commit `64f7b74` on `builderforce/task-2601` (developer exec 31923, issue #2601) replaced the live canvas domain module `frontend/src/domains/canvas/domain/canvasChange.ts` with a single line, `placeholder` (`+1/−137`). Merging that branch to `main` would destroy the 138-line production module.

The GitHub API `write_file` path is blocked (403 rate limit), so restore must happen on the operator git checkout: fetch, check out the branch, restore the file from `origin/main` (or revert `64f7b74`), drop the docs dump if present, and commit.

**Goal:** `builderforce/task-2601` must not merge until `canvasChange.ts` is byte-identical to `origin/main`, still exports the live public API, contains no placeholder, and `specs/tasks/task-2601.md` is absent.

## Target users / ICP roles

- Operator restoring the branch (this change is not developer-container-writable).
- Downstream agents sharing this PRD as the single source of truth for the P0 merge-gate.
- Reviewers / merge-gate owners for #2601.

Not an end-user product change. No Canvas UX, no new domain types.

## Scope

In scope:

- `git fetch origin`
- Check out `builderforce/task-2601`
- Restore `frontend/src/domains/canvas/domain/canvasChange.ts` from `origin/main` via `git checkout origin/main -- frontend/src/domains/canvas/domain/canvasChange.ts`, or `git revert 64f7b74`
- Delete `specs/tasks/task-2601.md` if present (P5 / BR-4 — docs dump must not ship)
- Commit that names `64f7b74` and `#2601`
- Verify `git diff origin/main -- frontend/src/domains/canvas/domain/canvasChange.ts` is empty on the branch

Source of the 138-line blob: `origin/main` (identical on `builderforce/task-2554`). If a later commit overwrites the live module again, restore that path from `origin/main`.

## Functional requirements

1. After restore, `frontend/src/domains/canvas/domain/canvasChange.ts` on `builderforce/task-2601` matches `origin/main` with an empty `git diff`.
2. The file is the live module, not a one-line `placeholder`.
3. The file still exports `ProposedCanvasChange`, `canvasChangesCanAutoApply`, `CONNECTED_CANVAS_ACTIONS`, and `canInvokeCreationObjectAction`.
4. Do not invent `CanvasChangeKind`, `applyObjectChange`, or any other new canvas API.
5. Do not write a nested `Builderforce.ai/` prefix on paths or commit artifacts.
6. If `specs/tasks/task-2601.md` exists on the branch, delete it so it does not ship.
7. Commit message must reference `64f7b74` and `#2601`.
8. Do not merge `builderforce/task-2601` until the pass conditions below hold.

## Acceptance criteria

- `git diff origin/main -- frontend/src/domains/canvas/domain/canvasChange.ts` is empty on `builderforce/task-2601`.
- File still exports `ProposedCanvasChange`, `canvasChangesCanAutoApply`, `CONNECTED_CANVAS_ACTIONS`, `canInvokeCreationObjectAction`.
- File is not a placeholder and is not a one-line overwrite.
- `specs/tasks/task-2601.md` is not present.
- Commit names `64f7b74` / `#2601`.
- No invented `CanvasChangeKind` / `applyObjectChange`.
- No nested `Builderforce.ai/` prefix.

## Out of scope

- Merging `builderforce/task-2601` to `main`.
- Rewriting, redesigning, or extending the canvas domain module.
- Inventing types or helpers (`CanvasChangeKind`, `applyObjectChange`, etc.).
- Restoring via GitHub API `write_file` (403; operator git only).
- Shipping `specs/tasks/task-2601.md` or any other docs dump.
- Unrelated files, features, or branches except using `origin/main` (or the identical blob on `builderforce/task-2554`) as the restore source.

### R-1 — Branch Operability
The operator SHALL be able to `git fetch origin`, `git checkout builderforce/task-2601`, and commit to that branch. The GitHub API `write_file` path is 403 rate-limited for the developer container; all restoration SHALL happen on the operator git checkout.

### R-2 — File Restoration to `origin/main`
`frontend/src/domains/canvas/domain/canvasChange.ts` on `builderforce/task-2601` SHALL be byte-identical to `origin/main`. The restore command is:
```
git checkout origin/main -- frontend/src/domains/canvas/domain/canvasChange.ts
```
Alternatively, `git revert 64f7b74` is acceptable if it produces the same blob.

### R-3 — Export Preservation
After restoration, the file SHALL export each of:
- `ProposedCanvasChange`
- `canvasChangesCanAutoApply`
- `CONNECTED_CANVAS_ACTIONS`
- `canInvokeCreationObjectAction`

No export SHALL be removed, renamed, or signature-changed.

### R-4 — Placeholder Elimination
The file SHALL NOT be a one-line `placeholder`, nor SHALL any line of the file contain a placeholder token in lieu of the live 138-line module.

### R-5 — Docs Dump Removal
If `specs/tasks/task-2601.md` exists on `builderforce/task-2601`, the operator SHALL delete it. It SHALL NOT appear in the branch at merge time.

### R-6 — Commit Traceability
The restoration commit message SHALL reference:
- Commit hash `64f7b74` (the destructive overwrite)
- Ticket number `#2601`

Example: `restore: revert 64f7b74 placeholder overwrite of canvasChange.ts (#2601)`

### R-7 — Diff Verification
After commit, `git diff origin/main -- frontend/src/domains/canvas/domain/canvasChange.ts` SHALL produce empty output on `builderforce/task-2601`.

### R-8 — No Invented API
The file SHALL NOT introduce `CanvasChangeKind`, `applyObjectChange`, or any other new canvas domain type, helper, or exported symbol. The 138-line module SHALL be the exact `origin/main` version.

### R-9 — No Nested Prefix
No path or commit artifact SHALL contain a nested `Builderforce.ai/` prefix. All paths SHALL be relative to the repository root.

### R-10 — Non-Merge Guard
The operator SHALL NOT merge `builderforce/task-2601` to `main` as part of this restoration. This ticket (#2643) is a merge-gate; #2601 SHALL NOT land until R-2 through R-9 pass.

### R-11 — Restoration Source
The canonical source for the 138-line blob SHALL be `origin/main`. The identical blob on `builderforce/task-2554` is an acceptable fallback if `origin/main` is unavailable, but `origin/main` is preferred.

### R-12 — Idempotent Recovery
If a subsequent commit on `builderforce/task-2601` overwrites the live module again after this restoration, the operator SHALL apply the same procedure (R-2) to restore the path from `origin/main`.

## Design

## D-0 — Architecture summary

This is a **restore, not a rewrite**. The damaged branch `builderforce/task-2601` contains commit `64f7b74` which replaced the live 138-line canvas domain module with the single line `placeholder`. The restore source is `origin/main`'s blob of `frontend/src/domains/canvas/domain/canvasChange.ts`, which this architect run confirmed on the bound checkout is byte-identical to the known-good live module (138 lines, all four required exports present, no invented symbols). The restore **must** happen on the operator's git checkout — not via the developer container (GitHub API `write_file` returns 403 for user ID 15883045). This design is the architectural blueprint for that operator procedure and the verification gates that confirm it succeeded.

## D-1 — Restore source: `origin/main`

The canonical source for the 138-line blob:

```
git checkout origin/main -- frontend/src/domains/canvas/domain/canvasChange.ts
```

Fallback: the identical blob on `builderforce/task-2554`. If neither is available (remote deleted, branch force-pushed away), escalate — do not reconstruct the module from memory or from a different version.

## D-2 — Operator procedure (execution order)

1. `git fetch origin`
2. `git checkout builderforce/task-2601`
3. `git checkout origin/main -- frontend/src/domains/canvas/domain/canvasChange.ts`
4. `rm -f specs/tasks/task-2601.md` (if present)
5. `git add frontend/src/domains/canvas/domain/canvasChange.ts`
6. If `specs/tasks/task-2601.md` was deleted: `git rm specs/tasks/task-2601.md`
7. `git commit -m "restore: revert 64f7b74 placeholder overwrite of canvasChange.ts (#2601)"`

## D-3 — Verification gates (pass/fail, block merge if any fail)

| Gate | Command / check | Pass criterion |
|------|----------------|----------------|
| G-1 | `git diff origin/main -- frontend/src/domains/canvas/domain/canvasChange.ts` | Empty output |
| G-2 | `grep -c '^placeholder$' frontend/src/domains/canvas/domain/canvasChange.ts` | `0` |
| G-3 | `grep -c 'export type ProposedCanvasChange' frontend/src/domains/canvas/domain/canvasChange.ts` | `1` |
| G-4 | `grep -c 'export function canvasChangesCanAutoApply' frontend/src/domains/canvas/domain/canvasChange.ts` | `1` |
| G-5 | `grep -c 'export const CONNECTED_CANVAS_ACTIONS' frontend/src/domains/canvas/domain/canvasChange.ts` | `1` |
| G-6 | `grep -c 'export function canInvokeCreationObjectAction' frontend/src/domains/canvas/domain/canvasChange.ts` | `1` |
| G-7 | `grep -c 'CanvasChangeKind' frontend/src/domains/canvas/domain/canvasChange.ts` | `0` |
| G-8 | `grep -c 'applyObjectChange' frontend/src/domains/canvas/domain/canvasChange.ts` | `0` |
| G-9 | `test -f specs/tasks/task-2601.md && echo FAIL || echo PASS` | `PASS` |
| G-10 | `git log -1 --format=%s` contains `64f7b74` and `#2601` | Both present |

## D-4 — File invariants (the live module)

This architect run confirmed the live module on `main` (138 lines):

- Exports `ProposedCanvasChange` (discriminated union, 8 variants: `object.add`, `object.update`, `object.delete`, `object.layout`, `object.action`, `connection.add`, `connection.update`, `connection.delete`)
- Exports `canvasChangesCanAutoApply` (pure boolean gate — allows reversible canvas-local authoring, holds destructive/executable/PRD-persisting ops for human review)
- Exports `CONNECTED_CANVAS_ACTIONS` (kind→acts mapping, 30+ kinds, each act backed by a real Canvas-side adapter)
- Exports `canInvokeCreationObjectAction` (boolean check — `inspect`/`edit` unconditional, others gated by `CONNECTED_CANVAS_ACTIONS`)
- Co-located test file: `frontend/src/domains/canvas/domain/canvasChange.test.ts` (100 lines, 14 test cases across 3 `describe` blocks)
- No `CanvasChangeKind`, no `applyObjectChange`, no placeholder tokens, no nested `Builderforce.ai/` prefix anywhere

## D-5 — Idempotency

If a subsequent commit on `builderforce/task-2601` overwrites the live module again AFTER this restoration, re-apply D-2 steps 3–7. The source remains `origin/main` (D-1). Do NOT attempt to merge through the damage — the merge gate (D-3) must pass every time the branch is inspected before merge.

## D-6 — What this design deliberately does NOT do

- Does NOT merge `builderforce/task-2601` to `main` (R-10)
- Does NOT rewrite, extend, or refactor the canvas domain module
- Does NOT introduce new types, helpers, or exported symbols
- Does NOT use GitHub API `write_file` (403; operator git only — R-1)
- Does NOT ship `specs/tasks/task-2601.md` or any other docs dump
- Does NOT touch any other file or branch

## D-7 — Risk: origin/main divergence

If `origin/main`'s `canvasChange.ts` has changed since this design was authored, the operator should still use `origin/main` as the source — it represents the current live truth. If the diff from what this design records is material (exports added/removed, signatures changed), pause and ask whether the branch should be rebased onto the new `main` instead of cherry-picking the old blob. The merge gate (D-3) will still pass as long as G-1 is empty (file matches `origin/main`), which is the only invariant that matters for merge safety.
