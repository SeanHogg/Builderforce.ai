# Product Requirements Document: Five Locales, Both Themes

## Problem & Goal

The product currently ships with a single language and a single visual theme. That blocks adoption for non-English users and for people who need (or prefer) dark UI. This WIP delivers first-class support for five locales and both light and dark themes so every downstream surface—web, docs, emails, and in-product copy—renders correctly, accessibly, and consistently.

Goal: a user can switch language among the five supported locales and switch theme between light and dark (or follow system preference) with no broken layout, missing strings, or contrast failures.

## Target users / ICP roles

- End users in English-, Spanish-, French-, German-, and Japanese-speaking markets
- Product, design, and engineering teams that consume this PRD as the shared source of truth
- Localization, QA, and accessibility reviewers who sign off locale and theme coverage
- Support and GTM teams who need locale-correct help content and screenshots

## Scope

In scope for this WIP:

- Locales: `en-US` (source), `es-ES`, `fr-FR`, `de-DE`, `ja-JP`
- Themes: `light` and `dark`, plus `system` (follows OS / browser `prefers-color-scheme`)
- Locale and theme selection UI, persistence, and URL / cookie / account sync
- String extraction, translation keys, date/number/currency formatting, and plural rules for all five locales
- Semantic color tokens, typography, spacing, and elevation that work in both themes
- First-run detection (browser language + `prefers-color-scheme`) with explicit user override
- Regression coverage on primary flows in every locale × theme combination

## Functional requirements

1. **Locale catalog** — Ship complete, reviewed translations for `en-US`, `es-ES`, `fr-FR`, `de-DE`, and `ja-JP`. Missing keys fall back to `en-US` and are logged.
2. **Locale switcher** — Persistent control (header or settings) lists all five locales in native names. Changing locale updates copy, formatting, and `lang` / `dir` on the document without a full app rebuild.
3. **Formatting** — Dates, times, numbers, percentages, and currency use CLDR data for the active locale. Japanese uses appropriate era/calendar defaults where the OS provides them.
4. **Theme catalog** — Light and dark palettes are defined as semantic tokens (background, surface, text, border, accent, danger, success, warning). No raw hex in feature code.
5. **Theme switcher** — User can choose Light, Dark, or System. Choice persists per device (and per account when signed in). System tracks `prefers-color-scheme` live.
6. **Contrast and motion** — Both themes meet WCAG 2.2 AA for text and UI components. `prefers-reduced-motion` is honored independently of theme.
7. **Persistence and routing** — Locale may be reflected in the URL (e.g. `/es-ES/...`) or a stable cookie; theme is not required in the URL. Signed-in preference wins over anonymous cookie, which wins over first-run detection.
8. **Assets** — Locale-specific images, legal copy, and screenshots exist where meaning is language-dependent. Theme-specific assets (logos, illustrations, OG images) exist for light and dark.
9. **Email and transactional surfaces** — Same five locales and both themes (or a theme-safe single palette) for outbound email where the product already sends mail.
10. **Instrumentation** — Track locale, theme, and switch events so coverage and fallback rates are visible.

## Acceptance criteria

- All five locales are selectable; switching updates UI copy, `html lang`, and formatting on the current page without error.
- A native speaker (or professional LQA) sign-off exists for `es-ES`, `fr-FR`, `de-DE`, and `ja-JP` on the primary user journeys.
- No untranslated key is visible in production for the five locales; fallback-to-English is measurable and ticketed.
- Light, Dark, and System each apply correctly; System updates when the OS theme changes without reload.
- Primary screens (auth, home, settings, checkout or equivalent core flow) pass visual QA in all 5 × 2 locale/theme pairs, including 320px width and 200% zoom.
- Text contrast on default and hover/focus states is ≥ 4.5:1 (normal text) and ≥ 3:1 (large text and UI components) in both themes.
- Japanese line breaking, font fallback, and density do not clip or overflow controls; European locales do not overflow at longest-string lengths.
- Refresh, new tab, and sign-in restore the last chosen locale and theme.
- Automated checks fail the build if a required locale is missing keys for shipped features or if a theme token is undefined.

## Out of scope

- Additional locales (including `pt-BR`, `zh-CN`, and RTL languages such as `ar`)
- Custom or third themes beyond light, dark, and system
- In-context translation editor or CMS for non-engineering translators
- Per-component theme overrides or white-label palettes
- Voice, locale-specific content strategy, or SEO hreflang rollout beyond the five locales listed
- Redesign of information architecture or new product features unrelated to locale and theme
- Native mobile apps except where they already share this web token and string pipeline
