# Product Requirements Document: Five Locales, Both Themes

## Problem & Goal

The product already ships five locales (`en`, `zh`, `es`, `fr`, `de`) and two themes (`light`, `dark`). Parent #2527 (P0 advisor profiles + marketplace category) will add user-visible copy and colour on talent listing, Book/Hire, freelancer/talent advisor fields, and the `advisors` category chip. If those strings are hardcoded English, or those colours are raw hex / `dark:` utilities, the P0 surfaces ship broken for every non-English user and for light-theme users.

Goal: every user-visible string and every colour on those P0 advisor surfaces goes through the existing catalog and token pipeline so a user can switch among the five shipped locales and between light and dark with no missing keys, no contrast failures, and no layout overflow (German length, Chinese wrapping) at 320px / 200% zoom.

This ticket does **not** introduce Japanese, URL-prefixed locales, a persisted System theme, an `/advisors` route, or a fifth marketplace family.

## Functional requirements

1. **Locale catalog (locked)** — The five catalogs are `frontend/src/i18n/messages/{en,zh,es,fr,de}.json`. Missing keys on a non-default catalog are a build failure (`messages.test.ts` key-parity). A failed catalog *fetch* at runtime falls back to `en` and logs a warning (`loadCatalog`); a missing *key* inside a loaded catalog must not ship.
2. **Locale switcher** — Existing `LanguageSwitcher` lists all five locales by endonym (`LOCALE_LABELS`). Changing locale writes `NEXT_LOCALE` (1-year, `path=/`, `samesite=lax`) and updates copy plus `document.documentElement.lang` without a URL change and without `/[locale]/` routing. SSR remains default-locale English; the client swaps after hydration (`LocaleProvider`).
3. **Formatting** — Advisor surfaces format dates, times, numbers, percentages, and currency through `useFormat()` / `getFormat()`. Chinese uses the `zh` CLDR data the runtime already provides; do not special-case a Japanese era calendar.
4. **Theme catalog (locked)** — Light and dark palettes are the existing semantic tokens (background, surface, text, border, accent, danger, success, warning). Feature code references `var(--…)` only.
5. **Theme switcher** — Existing `ThemeToggleButton` / `ThemeSelect` / `useTheme()`. Choice is `light` or `dark`, persisted in `localStorage['bf-theme']`. Unset defaults to dark (inline boot script in `layout.tsx`). This ticket does not add a persisted `system` third value.
6. **Contrast and motion** — Both themes meet WCAG 2.2 AA on the in-scope surfaces. `prefers-reduced-motion` is honored independently of theme; this ticket does not introduce motion that ignores it.
7. **Persistence** — Locale = `NEXT_LOCALE` cookie. Theme = `bf-theme` localStorage. Refresh and new tab restore both. Signed-in account-level locale/theme sync is not in the current product and is not added here. Theme is not in the URL. Locale is not in the URL.
8. **Marketplace copy** — Family labels stay under `marketplace.family.*` driven by `FAMILIES` in `marketplaceFamilies.ts`. The `advisors` category is a talent filter/chip, not a fifth family and not a `MARKETPLACE_LISTING_KINDS` value. Its label key exists in all five catalogs.
9. **Email** — Booking / transactional mail for advisor sessions uses the existing `EMAIL_LOCALES` set (must stay identical to frontend `LOCALES`). Recipient locale resolves via `emailLocaleResolver` (explicit `x-builderforce-locale` header, then cookie, then `Accept-Language`). Email stays on a theme-safe single palette; do not dual-theme outbound mail in this ticket.
10. **Instrumentation** — Do not add a new telemetry pipeline. If locale/theme switch events already exist, do not regress them. Coverage of missing keys is the `messages.test.ts` ratchet, not a production analytics dashboard.

## Acceptance criteria

- All five shipped locales (`en`, `zh`, `es`, `fr`, `de`) remain selectable; switching updates advisor-surface copy, `html lang`, and formatting on the current page without error and without a URL prefix.
- `frontend/src/i18n/messages.test.ts` stays green: catalogs are key-identical; every new advisor key formats rather than echoing its dotted path; every new registry `labelKey` / `titleKey` is asserted against every locale.
- No untranslated key is visible on P0 advisor surfaces in production for the five locales. Runtime catalog-fetch fallback-to-English remains logged (`loadCatalog` warning).
- Light and Dark each apply via `html[data-theme]`; refresh and a new tab restore `bf-theme`. This ticket does not require a live OS-theme follower.
- Primary advisor screens (talent listing with advisors filter, talent/freelancer profile advisor fields, Book CTA, booking confirmation if it ships on #2527) pass visual QA in all 5 × 2 locale/theme pairs, including 320px width and 200% zoom.
- Text contrast on default and hover/focus states is ≥ 4.5:1 (normal text) and ≥ 3:1 (large text and UI components) in both themes on those screens.
- Chinese line breaking, system font fallback, and density do not clip or overflow Book/Hire controls; German (longest European strings) does not overflow at those lengths.
- `EMAIL_LOCALES` and frontend `LOCALES` remain the same five codes. Widening one without the other is a reject.
- Automated checks fail the build if a required locale is missing keys for shipped advisor features or if a theme token used on those surfaces is undefined.
- No `/advisors` route, no `advisor` listing kind, no fifth marketplace family.

- BCP-47 region-tagged catalog files (`en-US.json`, `es-ES.json`, …). Region tags already normalize to the base language.
- `/[locale]/` URL routing. Locale is a cookie (`NEXT_LOCALE`), not a path segment.
- A persisted `system` third theme, per-component theme overrides, or white-label palettes. First-visit `prefers-color-scheme` as a standing mode is not added here; unset `bf-theme` stays dark.
- In-context translation editor or CMS for non-engineering translators.
- Native-speaker LQA as a release gate for this ticket (the automated ratchet is the gate; LQA may follow as a separate process).
- Dual-theme outbound email; account-level locale/theme sync for signed-in users; new instrumentation/dashboards for fallback rates.
- Voice, locale-specific content strategy, or SEO hreflang rollout.
- Redesign of information architecture, a new `/advisors` destination, a new listing family, or `advisor` as a `MARKETPLACE_LISTING_KINDS` / `PEOPLE_OBJECT_KINDS` value (parent #2527 / PRD 26).
- Meeting-notes / silent-notetaker copy (that is #2538). Booking-host bind itself (that is #2532 / A0). This ticket only requires that whatever those surfaces render on P0 goes through catalogs and tokens.
- Native mobile apps except where they already share this web token and string pipeline.
- Platform-wide i18n or theme rewrite. The five locales and both themes already ship; this ticket applies them to P0 advisor surfaces.

## Requirements

Business requirements for ticket #2531, owned by the business-analyst. These bind P0 advisor surfaces (#2527) to the **existing** five-locale / two-theme platform; they do not invent a new i18n or theme system.

### R-1 — Catalog identity (locked)

The product's locale catalog is exactly `{ en, zh, es, fr, de }`.

| Code | Endonym (`LOCALE_LABELS`) | Role |
| --- | --- | --- |
| `en` | English | Source / default (`DEFAULT_LOCALE`) |
| `zh` | 中文 | Fifth shipped locale (not Japanese) |
| `es` | Español | |
| `fr` | Français | |
| `de` | Deutsch | Longest typical European strings — layout worst case |

Sources of truth that **must stay identical**:

- `frontend/src/i18n/config.ts` → `LOCALES`
- `api/src/infrastructure/email/emailLocale.ts` → `EMAIL_LOCALES`

A PR that adds, removes, or renames a locale in one file without the other is rejected. Region-tagged BCP-47 values (`en-US`, `zh-Hans-CN`, `de-AT`, `en-GB`, …) already collapse to the base language via `localeFromAcceptLanguage` / `resolveEmailLocale`; they are not new catalogs.

### R-2 — Copy on P0 advisor surfaces is catalog-backed

Every user-visible string introduced or touched by parent #2527 **must** be a key in all five `frontend/src/i18n/messages/{en,zh,es,fr,de}.json` files in the same PR. No hardcoded English (or any other language) in TSX/TS for:

- Talent listing: advisors-mode heading, empty state, filter/chip label for the `advisors` category.
- Book / Hire CTAs and any adjacent helper text on a talent card or profile when the listing is in advisor mode.
- Freelancer / talent advisor profile fields and their labels, placeholders, validation, and empty states: expertise, industries, languages, methods, stages, session length, price (including the 0 / complimentary case), location, confidentiality default.
- Marketplace `advisors` category chip. This is a talent filter, **not** a fifth family under `FAMILIES` and **not** a `MARKETPLACE_LISTING_KINDS` / `PEOPLE_OBJECT_KINDS` value. Family chrome continues to use `marketplace.family.*` driven by `marketplaceFamilies.ts`.

Key naming follows existing namespaces (`marketplace.*`, `talent.*`, `profile.*`, or a dedicated `advisor.*` prefix if the developer introduces one). Registry entries that expose `labelKey` / `titleKey` / `publishKey` **must** be covered by the catalog-key ratchet in `frontend/src/i18n/messages.test.ts` (AGENTS.md).

### R-3 — Fallback is a failed fetch, not a missing key

- **Missing key in a catalog file:** build failure. `messages.test.ts` requires identical key sets across the five JSON files and requires that interpolation / ICU formatting does not echo the dotted path.
- **Catalog fetch failure at runtime** (`loadCatalog` in `frontend/src/i18n/catalog.ts`): fall back to the statically imported `en` catalog and log a warning. This is the only permitted English fallback.
- No "show the key" or "show English for this one string" behaviour on a loaded catalog.

### R-4 — Locale switcher and persistence (no URL routing)

- The existing `LanguageSwitcher` is the control: five endonyms, writes `NEXT_LOCALE` (`Max-Age=31536000`, `path=/`, `samesite=lax`), calls `router.refresh()`.
- `LocaleProvider` sets `document.documentElement.lang` to the resolved locale. SSR HTML is default-locale English; the client hydrates and swaps. That flash is accepted platform behaviour and is not a defect of this ticket.
- Locale is **not** a path segment. There is no `/[locale]/…` app router and this ticket does not add one. Locale is also not required in query strings.
- Refresh, new tab, and a subsequent visit restore the cookie. Signed-in account-level locale is not in the product today and is not added here; cookie wins for everyone.

### R-5 — Formatting on advisor surfaces

Dates, times, numbers, percentages, currency, and relative time on in-scope surfaces go through `useFormat()` / `getFormat()` (`frontend/src/i18n/format.ts`) so CLDR data for the active locale applies.

Forbidden:

- `toLocaleString()` / `toLocaleDateString()` / `Intl.*` constructed with no locale or with a hardcoded `'en-US'` / `'en'`.
- Hand-rolled date or currency strings.
- A Japanese-era / Imperial calendar special case (Japanese is out of scope).

Currency for session price uses the format helper's currency API with the listing's currency code; a price of 0 must still format (complimentary), not render as a blank or as a raw `0`.

### R-6 — Theme identity (locked)

Themes are `light` and `dark` only.

| Value | Where tokens live | Persistence |
| --- | --- | --- |
| `dark` | `:root` in `frontend/src/app/globals.css` | default when `bf-theme` is unset |
| `light` | `html[data-theme='light']` (BurnRate cool slate; `LIGHT_THEME_BURNRATE.md`) | `localStorage['bf-theme'] = 'light'` |

`frontend/src/lib/theme.ts` is the only writer of `html[data-theme]` and of the `bf-theme-change` window event. Feature code does not set the attribute.

This ticket does **not** add a persisted `system` value. First-visit `prefers-color-scheme` is not consulted as a standing mode; the inline boot script in `layout.tsx` defaults unset to dark. Live OS-theme following is out of scope.

### R-7 — Tokens, not raw colour

On P0 advisor surfaces:

- Colour, type, space, elevation, and focus rings are `var(--…)` from `globals.css` (background, surface, text, muted, border, accent, danger, success, warning, and the existing elevation/shadow tokens).
- No raw hex, rgb, or hsl in feature TSX/CSS for those surfaces.
- No `dark:` Tailwind colour utilities that disagree with the token sheet.
- Interactive states (hover, focus, disabled) use the same token set so contrast (R-8) can be measured once per theme.

### R-8 — Contrast, motion, and density

- WCAG 2.2 AA: contrast ≥ 4.5:1 for normal text and ≥ 3:1 for large text and UI components, on default **and** hover/focus, in **both** themes, on the in-scope screens.
- `prefers-reduced-motion` is honored independently of theme. This ticket does not introduce animation that ignores it.
- Layout must not clip or overflow Book/Hire controls, chips, or profile fields at 320px width or 200% zoom, in all five locales. Explicit worst cases: German compound labels (length) and Chinese wrapping / system font fallback (density and line-breaking).

### R-9 — Email locale parity, theme-safe mail

- Advisor booking / transactional mail uses `EMAIL_LOCALES`. Recipient locale is resolved by the existing `emailLocaleResolver` (explicit `x-builderforce-locale` header, then cookie, then `Accept-Language`).
- Outbound mail stays on a **theme-safe single palette**. Do not dual-theme HTML email in this ticket.
- Strings in those templates follow the same five-locale catalog discipline the email pipeline already uses; do not hardcode English in a new advisor mail template.

### R-10 — Instrumentation is the existing ratchet

- Do not add a new telemetry pipeline, dashboard, or analytics event for locale/theme/fallback in this ticket.
- The build-failing catalog ratchet (`messages.test.ts`) is the coverage signal.
- If locale or theme switch events already exist on `LanguageSwitcher` / `useTheme`, do not regress them.

### R-11 — Non-goals that reject a PR

A change on this ticket is rejected if it:

- Adds `ja-JP` (or any locale outside `{en, zh, es, fr, de}`).
- Adds `/[locale]/` routing or puts theme in the URL.
- Adds a persisted `system` theme.
- Introduces an `/advisors` route, a fifth marketplace family, or `advisor` as a `MARKETPLACE_LISTING_KINDS` / `PEOPLE_OBJECT_KINDS` value.
- Duplicates family chrome under a new `marketplace.family.advisors` key (advisors is a talent category/chip, not a family).
- Touches meeting-notes / silent-notetaker copy (#2538) or the booking-host bind (#2532) beyond requiring that whatever those surfaces render on P0 is catalog- and token-backed.
