# PRD: Visitor join-by-token (meetings)

## Problem & Goal

Unauthenticated visitors must be able to join a meeting via a shareable token without signing in. Today the only obvious shortcut is to exempt the entire meetings router from `authMiddleware`. That would expose tenant-scoped meeting APIs to unauthenticated traffic and diverge from how `interviewScheduling` already resolves `token → tenant`.

**Goal:** Allow a visitor to join a single meeting (and only that meeting) by presenting a valid join token, using the same token→tenant resolution pattern as `interviewScheduling`. Do **not** punch a hole in `authMiddleware` for the whole meetings router.

## Target users / ICP roles

- **Visitor (unauthenticated):** Recruiter-invited candidate, external interviewer, or guest joining via a link. No product account required.
- **Meeting host / organizer (authenticated):** Creates or shares the join token; remains fully behind existing auth.
- **Tenant admin / security:** Expects join access to be token-scoped, tenant-bound, and auditable—not a router-wide auth bypass.

## Scope

- Add a **narrow, token-authenticated join path** for meetings, parallel to `interviewScheduling` token→tenant.
- Resolve tenant (and meeting identity) from the join token **before** tenant-scoped work; do not rely on session cookies or a global meetings-router exemption.
- Authenticated meeting CRUD, listing, and host actions stay behind existing `authMiddleware`.
- Token validation, expiry, single-meeting binding, and tenant isolation for the visitor join flow only.

## Functional requirements

1. **Token→tenant resolution (copy `interviewScheduling`)**
   - Visitor presents a join token (query/path/header—same convention as interview scheduling).
   - Server looks up the token, derives `tenantId` (and meeting id) from the token record, and binds that tenant for the remainder of the request.
   - Invalid, expired, revoked, or unknown tokens fail closed (401/403). No fallback to “unauthenticated tenant-less” meeting APIs.

2. **Do not weaken `authMiddleware` on the meetings router**
   - The meetings router remains protected by `authMiddleware`.
   - Do not add a blanket public exemption, skip-auth flag, or wildcard unauthenticated mount for `/meetings`.
   - Visitor join is a **dedicated route (or small route set)** with its own token middleware, not an exception applied to every meetings handler.

3. **Least privilege for visitors**
   - A valid token authorizes **join (and join-adjacent read) for that meeting only**.
   - Token must not grant: listing other meetings, mutating meeting config, host controls, other tenants, or interview-scheduling resources.
   - Tenant context on the request must equal the token’s tenant; mismatch is rejected.

4. **Parity with interview scheduling token handling**
   - Reuse the same token lookup, hashing/storage, expiry, and tenant-binding approach (shared helper or copied structure—no one-off meetings auth).
   - Token issuance remains an authenticated host/organizer action (existing auth).

5. **Failure and abuse posture**
   - Missing token on the visitor join path: reject.
   - Replay of a revoked/expired token: reject.
   - Do not leak whether a meeting id exists for another tenant.

## Acceptance criteria

- A visitor with a valid, unexpired join token can join the bound meeting without a session.
- The same visitor **cannot** call other meetings-router endpoints that remain behind `authMiddleware`.
- `authMiddleware` is **not** removed, skipped, or globally bypassed on the meetings router.
- Token resolution follows the `interviewScheduling` token→tenant pattern (lookup → tenant bind → scoped handler).
- Wrong tenant, wrong meeting, expired, revoked, or malformed tokens never establish tenant context and never join.
- Authenticated host flows (create/update/list/share token) are unchanged and still require `authMiddleware`.
- Automated tests cover: valid join; expired/revoked/unknown token; no token; token for meeting A cannot join meeting B; meetings router without token still 401s.

## Out of scope

- Public, unauthenticated access to the full meetings API or router.
- Changing `authMiddleware` semantics for other routers.
- Redesigning interview-scheduling tokens (copy the pattern; do not refactor it unless required for a shared helper).
- Account creation, SSO, or converting visitors into full users.
- Token UX (email templates, calendar links) beyond what is required to pass the token into the join path.
- WebRTC/media, recording, or waiting-room product features except as needed to complete token-gated join.
- Multi-meeting or tenant-wide “guest links.”
