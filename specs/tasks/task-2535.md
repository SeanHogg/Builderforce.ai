# PRD: Visitor join-by-token

## Problem & Goal

Authenticated users can already access meetings through the existing meetings API, which is gated by `authMiddleware`. External visitors (no account, no session) must join a specific meeting with a shareable join token.

A naive exemption of the whole meetings router from `authMiddleware` would expose tenant-scoped meeting operations to unauthenticated callers. That is unacceptable.

**Goal:** Let a visitor join one meeting by presenting a join token, resolving token → tenant (and meeting) the same way `interviewScheduling` already does, without punching a hole in `authMiddleware` for the rest of the meetings router.

## Target users / ICP roles

- **Visitor:** Unauthenticated external participant who receives a join link/token and needs to enter a single meeting.
- **Host / organizer:** Authenticated user who creates or shares the join token for a meeting they own or can schedule.
- **Platform / tenant admin:** Relies on tenant isolation remaining intact for all non-join meeting APIs.

## Scope

In scope:

- Visitor join-by-token for meetings, modeled on the existing `interviewScheduling` token → tenant flow.
- A narrowly scoped unauthenticated join path (route, handler, or sub-router) that does **not** bypass `authMiddleware` for the meetings router as a whole.
- Token validation, tenant resolution, and meeting lookup sufficient to admit the visitor into that meeting only.
- Failure modes for missing, expired, revoked, mismatched, or unknown tokens that do not leak tenant or meeting details.

Out of scope items are listed below.

## Functional requirements

1. **Join path isolation**
   - Visitor join must live on a dedicated unauthenticated endpoint (or equivalent isolated handler), not as a blanket skip of `authMiddleware` on the meetings router.
   - All other meetings routes continue to require the existing authenticated middleware chain.

2. **Token → tenant resolution (copy `interviewScheduling`)**
   - Resolve join token → tenant using the same pattern as `interviewScheduling` (lookup, tenant binding, and request context population).
   - After a valid token, subsequent join work runs in that tenant context only.
   - Do not invent a parallel token scheme, a global token table with different semantics, or a meetings-specific auth bypass.

3. **Join semantics**
   - A valid token admits the visitor to **that meeting only**.
   - The join response may include only what the visitor needs to enter the meeting (e.g. meeting identity, join credentials/session material already used for this product’s meeting join).
   - The token must not authorize list/create/update/delete of meetings, participants, recordings, or other tenant resources.

4. **Token validity**
   - Reject missing, malformed, unknown, expired, revoked, already-consumed (if single-use), or meeting-mismatched tokens.
   - Reject tokens that do not bind to a live, joinable meeting in the resolved tenant.

5. **Tenant isolation**
   - Token resolution must not allow cross-tenant meeting access.
   - Error responses must be uniform enough that attackers cannot enumerate tenants or meetings via the join path.

6. **Host-side compatibility**
   - Existing authenticated meeting flows remain unchanged except where they already mint or attach join tokens (if that exists; if not, token issuance is out of scope unless already present via the `interviewScheduling`-equivalent meeting token).

## Acceptance criteria

- Unauthenticated `GET`/`POST` (whichever matches existing join conventions) to the dedicated visitor join path with a valid token joins the bound meeting in the bound tenant.
- The same request with an invalid token returns a generic failure (401/403/404 per existing token-join convention) and does not join.
- The meetings router still applies `authMiddleware` to all non-join meeting routes; unauthenticated calls to those routes fail as they do today.
- Token → tenant resolution reuses the `interviewScheduling` approach (same lookup/binding/context pattern, not a new ad-hoc bypass).
- A valid token for meeting A in tenant T cannot be used to access meeting B, tenant U, or any non-join meetings API.
- No change in behavior for authenticated hosts using the existing meetings API.
- Automated tests cover: valid join, invalid/expired/revoked token, auth still required on the rest of the meetings router, and no cross-tenant access.

## Out of scope

- Exempting or weakening `authMiddleware` on the meetings router.
- New token issuance UI, email/SMS delivery, or public share-link product surface (unless already shipped for meetings).
- Visitor accounts, SSO, or converting a visitor into a tenant member.
- Waiting rooms, lobby policies, recording consent, or in-meeting permissions beyond admission.
- Changing `interviewScheduling` token semantics, except to reuse its token → tenant pattern.
- Analytics, billing, or audit-product work beyond whatever logging the existing token-join path already does.

## Requirements

_Owned by the business-analyst (this run). Grounded in `interviewScheduling.ts` + `candidateBookingRoutes.ts` (token→tenant), `meetingRoutes.ts` (`r.use('*', authMiddleware)` + `POST /:id/join`), and `share_links` (SHA-256, expiry, revocation)._

These requirements are the contract for Architecture, Implementation, QA, and Acceptance. IDs are stable; do not renumber.

### R-1 — Dedicated join router; do not weaken meetings auth

1. Visitor join MUST live on a **dedicated Hono router**, mounted as a **sibling** of `/api/booking` (recommended prefix: `/api/join`). It MUST NOT be a handler on `createMeetingRoutes`.
2. `createMeetingRoutes` MUST keep `r.use('*', authMiddleware)` as its first middleware. No skip-auth flag, public-path allowlist, wildcard unauthenticated mount, or `authMiddleware` removal on `/api/meetings`.
3. A caller **without** a session who hits any existing `/api/meetings/*` path (including `POST /:id/join`, `GET /`, `GET /ice`, `GET /rooms/:key/ws`, list/create/patch/start/end/cancel/transcript/rsvp) MUST still receive **401** from `authMiddleware`.
4. Mounting the join router under the `/api/meetings` prefix is forbidden unless it is a **separate** `app.route` that does not share the authenticated router instance. Prefer `/api/join` so the two cannot be confused.

### R-2 — Token presentation (same convention as interview scheduling)

1. The visitor presents the raw token as a **path parameter** (`/:token`), matching `/api/booking/:token`. Not a header, not a query on the meetings router, not the meeting UUID.
2. Shape-check before any database read: same family as booking’s `TOKEN_RE` (`/^[0-9a-f]{32,128}$/i`). Malformed tokens never reach Postgres.
3. Meeting identity is an **output of token resolution**, not an input. The join URL contains the token, not `?join=<meetingId>`. Authenticated deep-link `/meetings?join=<id>` (and the workforce tab redirect) is unchanged and remains session-gated.

### R-3 — Token storage is `share_links` (copy, do not fork)

1. A join link is a `share_links` row. Do **not** add a meetings-specific token table.
2. Store **only** SHA-256 (`sha256Hex`); return the raw token **once** at issuance. A database read must not be able to mint a working link.
3. Use a distinct `scope` (recommended: `'join'`). Do **not** reuse `'view'` (read-only) or `'book'` (interview booking writes `scheduledAt`). A booking token MUST NOT join a meeting; a join token MUST NOT book an interview or call `/api/booking/*`.
4. Honour existing columns: `expiresAt`, `revokedAt`, `maxUses` / `useCount`, `tenantId`, `objectId`.
5. Default TTL: **14 days** unless the authenticated issuer passes an explicit lifetime (same default as `DEFAULT_LINK_DAYS` in `interviewScheduling`).
6. Join tokens are **multi-use until expiry or revocation** (a refresh must not burn the link). This is the one deliberate difference from booking’s single-use `bookedAt` guard. `maxUses` may be null; if set, exhausted links fail closed like booking.

### R-4 — Token → tenant resolution (the one unscoped query)

1. Copy `resolveToken` in `interviewScheduling.ts`: **one** lookup with **no tenant predicate**. Tenant is an **output**. The token hash is the scope (UNIQUE `token_hash`).
2. Resolve by: `tokenHash` + `scope = 'join'` + `revokedAt IS NULL`, then inner-join to the bound meeting. Drop the row if `expiresAt < now` or `maxUses` is exhausted.
3. Every subsequent read/write MUST use `scopedToTenant(..., tenantIdFromToken, ...)`. Never run meeting APIs in an unauthenticated tenant-less context.
4. Shared helper **or** copied structure is acceptable. Do **not** redesign interview-scheduling tokens. Extracting a small `resolveShareLink(db, token, scope)` is allowed if it is the smaller change; booking behaviour must stay byte-equivalent.

### R-5 — Least privilege (this meeting only)

A valid join token authorizes **only**:

- **Preview** of the bound meeting (see R-6).
- **Join** of the bound meeting (attendee upsert + room key + ICE).
- **Join-adjacent media signaling** for that meeting’s `roomKey` only (see R-7).

It MUST NOT authorize: listing other meetings; creating/updating/cancelling meetings; host start/end/patch; transcript read/write; agent-turn; summarize; RSVP as a tenant user; availability / freebusy / suggest; interview-scheduling resources; other tenants; other meetings in the same tenant; `GET /api/meetings/ice` or `GET /api/meetings/rooms/:key/ws`.

Tenant context on the request MUST equal the token’s tenant; mismatch is rejected (the inner join should make this unreachable).

### R-6 — Preview vs join (two routes, one token)

Parallel to canvas join and `/api/booking`:

| Method | Path (illustrative) | Effect |
|---|---|---|
| `GET` | `/api/join/:token` | Preview. Does **not** increment `useCount`. |
| `POST` | `/api/join/:token` (or `/api/join/:token/join`) | Join: upsert visitor attendee, flip `scheduled` → `live` on first join (same as authenticated join), return `roomKey`, `videoEnabled`, `iceServers`, meeting shell. |

**Preview payload (narrow):** title, status, `scheduledAt`, `durationMinutes`, `videoEnabled`, host display name, `expiresAt`. No other attendees’ emails, no other meetings, no tenant internals, no interviewer/candidate PII.

**Join payload:** same as today’s authenticated `POST /:id/join` **minus** full attendee PII: `roomKey`, `videoEnabled`, `iceServers` (from existing `iceServers()`), meeting shell for the bound row, the visitor’s own attendee row.

**Join body:** optional `name` + `email` (existing `JoinBody`). Email SHOULD be required for an unauthenticated visitor so the attendee row has a stable `memberRef` (see R-8).

### R-7 — Media signaling without opening the meetings router

Authenticated join already returns ICE in the join JSON, but WebRTC signaling today is `GET /api/meetings/rooms/:key/ws` **behind `authMiddleware`**. A visitor who receives `roomKey` + ICE still cannot signal if that path stays 401.

1. Do **not** unprotect `/api/meetings/rooms/:key/ws` or `/api/meetings/ice`.
2. Return ICE on the join response (reuse `iceServers()` / `applyMediaPrivacyMode` as the authenticated path does).
3. Expose a **token-gated** websocket on the join router (e.g. `GET /api/join/:token/ws`) that resolves the token, then `relayToRoom(..., \`media:${meeting.roomKey}\`)`. The room key comes from the token’s meeting, never from the client. A client-supplied room key is ignored/rejected.
4. Recording, waiting-room UX, and TURN product work remain out of scope except as required for this relay.

### R-8 — Visitor identity (no account, no session)

1. Do **not** mint a `users` row or a session (that is the canvas-guest pattern; out of scope here).
2. Upsert `meeting_attendees` with `memberKind = 'human'`, `role = 'attendee'`, `response = 'accepted'`, `joinedAt = now`.
3. `memberRef` MUST NOT be an empty string and MUST NOT collide with a tenant `userId`. Use a stable visitor key derived from the presented email (normalize) or a `visitor:` prefix. Rejoin with the same token + email updates the existing row (`joinedAt`, `leftAt = null`).
4. Ceremony presence write-through (`recordCeremonyPresence`) is **best-effort** and MUST NOT fail the join. If there is no `userId`, skip or record with the visitor `memberRef`; do not invent a tenant user.

### R-9 — Token issuance (authenticated host action)

1. Issuance is an authenticated organizer/manager action on the **existing** meetings router (still behind `authMiddleware`). Suggested: `POST /api/meetings/:id/join-link` (name is Architecture’s).
2. Authorization: same as `loadForMutation` (organizer or manager). Not any attendee.
3. Returns `{ token, expiresAt, joinUrl }` **once**. `joinUrl` is an absolute chrome-less path containing the token (see R-15).
4. Re-issue **revokes** the previous live join link first (same order as `offerInterviewSlots`: revoke then insert, so a failure leaves zero working links, not two). Persist a pointer on the meeting (e.g. `joinShareId`, parallel to `interviews.bookingShareId`).
5. Creating a meeting does **not** have to auto-issue a token. Parent epic #2532 (visitor booking) will call issuance after it creates the advisory meeting. Calendar `joinUrl` today (`/meetings?join=<id>`) stays as the authenticated deep-link; swapping it for the token URL is Token UX and is **out of scope** unless issuance already ran and the host explicitly shares that URL.

### R-10 — Kernel object for `share_links.object_id`

`share_links.object_id` is NOT NULL and FKs to `objects`. Today `POST /api/meetings` does not set an `objectId` on the meeting (unlike interviews, which refuse to share without one).

Architecture MUST pick one:

- **A.** Add `meetings.objectId` (and `joinShareId`) and ensure a kernel object exists at create or at first share; or
- **B.** Mint/register the kernel object at share time and store the pointer.

Do not insert a `share_links` row without a real `objects` row. Do not store the raw token on `meetings`.

### R-11 — Failure and abuse posture (fail closed, one voice)

On the **public join router**, these are indistinguishable (copy booking: **404** + one message, e.g. “This join link is no longer valid.”):

- missing token / empty path
- malformed token (fails `TOKEN_RE`)
- unknown hash
- expired
- revoked
- exhausted `maxUses`

Do **not** use different status codes or bodies that would let a caller sort guessed tokens into “interesting” vs “uninteresting”, and do **not** leak whether a meeting id exists for another tenant.

On a **resolved** token, lifecycle refusals may be specific (the holder already proved the link): cancelled/ended meeting → **409** (same copy as authenticated join: `Meeting has ${status}`).

`authMiddleware` 401 on `/api/meetings/*` without a session is unchanged.

### R-12 — Cross-meeting and cross-tenant isolation

1. A token bound to meeting A MUST NOT join meeting B, even in the same tenant. Because the meeting id is not in the URL, this is structural; if Architecture puts an id in the path anyway, token meeting id MUST match or the request fails closed with the **same** 404 as R-11 (do not reveal “wrong meeting”).
2. Wrong tenant never establishes tenant context.
3. A leaked join token discloses: title, time, duration, host display name, and (after POST) the ability to enter **that** room. It MUST NOT disclose other meetings, attendee emails, or tenant membership.

### R-13 — Meeting lifecycle on visitor join

Copy authenticated `POST /:id/join` for the bound row only:

- 404/closed if the token does not resolve (R-11), not a separate “meeting not found” that leaks ids.
- If resolved and `status` is `cancelled` or `ended` → 409.
- If `scheduled` → set `live` and `startedAt` on first join.
- Walk-in attendee upsert as R-8.
- Do not run host-only mutations.

### R-14 — Authenticated host flows unchanged

Create, list, get, patch, start, end, cancel, RSVP, transcript, agent-turn, summarize, availability, freebusy, suggest, ICE, and authenticated `POST /:id/join` remain behind `authMiddleware` and keep current authorization (`canAccess` / `loadForMutation`). No behaviour change except the new issuance route (R-9).

### R-15 — Frontend: chrome-less join page (minimal)

1. A chrome-less route that takes the token from the path (parallel to `/book/[token]`; recommended `/join/[token]`), listed in `NO_CHROME_PREFIXES`. No operator shell, no marketing nav, no `AuthContext` requirement.
2. Page calls `GET /api/join/:token` then `POST /api/join/:token` with visitor name/email, then reuses the existing media-room client with the returned `roomKey` + `iceServers` + token-gated WS.
3. Email templates, calendar-invite copy, and waiting-room product are **out of scope**. `/workforce?tab=meetings&join=<id>` stays the authenticated bookmark.

### R-16 — Automated tests (acceptance)

Must cover:

1. Valid unexpired join token → preview 200 and join 200 with `roomKey` + `iceServers`; no session cookie.
2. Same visitor **cannot** call `/api/meetings` list/create/`POST /:id/join`/`GET /ice` without a session (401).
3. `authMiddleware` still applied to `createMeetingRoutes` (no skip).
4. Expired, revoked, unknown, malformed, and missing tokens → 404, one message, no tenant context.
5. Token for meeting A cannot join meeting B.
6. Booking-scope (`'book'`) token cannot join; join-scope token cannot book.
7. Re-issue revokes the previous link; old token 404s.
8. Cancelled/ended bound meeting → 409 after a valid token resolves.
9. Issuance without a session → 401; issuance by a non-organizer non-manager attendee → 403.
10. Signaling WS with a valid token reaches only that meeting’s `roomKey`; a guessed `roomKey` is not relayed.

### R-17 — Explicit non-goals (do not implement on this ticket)

- Public unauthenticated access to the full meetings API or router.
- Changing `authMiddleware` semantics for other routers.
- Redesigning interview-scheduling tokens.
- Account creation, SSO, or converting visitors into users/sessions.
- Adding `advisory` to `KINDS` (parent #2532).
- Token email/calendar UX beyond returning `joinUrl` from issuance.
- Waiting-room, recording, or TURN product work beyond R-7.
- Multi-meeting or tenant-wide guest links.
- A docs-only `specs/tasks/task-2535.md` in the product repo (requirements live on this ticket PRD).

Resolved + cancelled/ended → **409** (`Meeting has ${status}`). Token for meeting A cannot join meeting B or tenant U (same 404 if an id is ever put in the path). Preview/join payloads stay narrow (no other attendees’ emails, no tenant internals).

### P4 — Kernel object default B; issuance path locked (R-9, R-10)
