# PRD: Propose Follow-up Slot (No Silent Booking)

## Problem & Goal

After a meeting, teams often need a follow-up but have no shared, trusted next step. Silent auto-booking creates calendar surprise, double-books, and erodes trust. Manual chase (Slack/email ping-pong) is slow and inconsistent.

**Goal:** After a qualifying meeting, use the **same availability solver** already used for original scheduling to **propose one follow-up slot**. Do **not** write the event to either calendar. Email **both parties** with the proposed time, context, and clear accept/decline/reschedule actions.

Success looks like: a single, solver-backed proposal is emailed to both sides; no calendar write occurs until a human accepts.

## Target users / ICP roles

- **Organizer / host** — scheduled the original meeting; owns follow-up.
- **Guest / counterpart** — attendee who must agree before anything is booked.
- **Internal ops / AE / CSM / recruiter** — high meeting volume; need a consistent follow-up path without extra tools.
- **Downstream agents** consuming this PRD — scheduling, email, and calendar integrations must implement the same contract.

## Scope

In scope for this WIP:

- Trigger after a completed (or explicitly marked “needs follow-up”) meeting that was originally scheduled via the product.
- Re-run the **existing availability solver** with the same participant set, timezone rules, working hours, buffers, and duration defaults as the original meeting (duration overridable only if the original meeting recorded a follow-up duration).
- Select **one** proposed slot (solver’s top-ranked feasible slot in the look-ahead window).
- Compose and send **one email thread to both parties** (organizer + guest; To both, not BCC-only).
- Email must include: proposed start/end in each recipient’s timezone, duration, original meeting title/context, that **nothing is booked yet**, and actions: Accept / Suggest another time / Decline.
- Persist proposal state: `proposed`, `accepted`, `declined`, `expired`, `superseded`.
- Idempotency: at most one open proposal per original meeting.
- Audit log: solver inputs/outputs (slot, rank, constraints), email message IDs, no calendar mutation.

## Functional requirements

1. **No silent book**
   - The follow-up path MUST NOT create, update, or tentatively hold calendar events on any provider.
   - Accepting later is a separate booking flow; this feature stops at proposal + email.

2. **Same availability solver**
   - Call the identical solver service/API used for initial scheduling (same version, constraint set, ranking).
   - Participants = original meeting attendees (organizer + guest at minimum).
   - Default duration = original meeting duration unless a follow-up duration was stored.
   - Look-ahead window = product default for new meetings (e.g. next 10 business days), excluding the just-completed slot and any configured buffer after it.
   - If the solver returns zero slots, send a “no times found” email to both parties with a reschedule CTA; still do not book.

3. **Proposal selection**
   - Use the solver’s top-ranked slot only (no multi-option grid in v1).
   - Store slot as UTC plus per-attendee local display times.

4. **Email both parties**
   - Single email to organizer and guest (CC optional additional original attendees if they were on the meeting).
   - Subject and body must state this is a **proposal**, not a confirmation.
   - Include original meeting reference (title, date, id).
   - Include Accept / Decline / Suggest another time links or reply instructions that route back to product state — not mailto-only dead ends.
   - Do not send calendar `.ics` METHOD:REQUEST that would auto-create events. If an attachment is used, it must be informational only and must not invite.

5. **Triggers**
   - Explicit user action “Propose follow-up”, or
   - Automated post-meeting hook when the meeting is marked completed and follow-up is enabled for that meeting type.
   - Never run if a follow-up event already exists or an open proposal is already `proposed`.

6. **State & concurrency**
   - Creating a proposal is idempotent on `original_meeting_id`.
   - If the organizer later books manually, mark the proposal `superseded`.
   - Expire open proposals after the proposed start time has passed or after the product expiry window, whichever is first.

7. **Observability**
   - Log solver request id, ranked slot, email provider ids, and a boolean `calendar_write=false`.
   - Alert if any calendar write API is invoked on this code path.

## Acceptance criteria

- Given a completed original meeting with two parties and solver-available times, when follow-up is requested, the system proposes exactly one slot from the **same solver** and emails **both** parties.
- Calendars of both parties remain unchanged (no event, no hold, no invite) after proposal send.
- Email copy clearly states the slot is proposed and not booked; each recipient sees times in their timezone.
- A second follow-up request for the same meeting does not create a second open proposal or a second email blast.
- If the solver finds no slot, both parties receive a no-availability email and no booking occurs.
- Accepting is not implemented as a side effect of sending the proposal; booking occurs only in a later, explicit accept path.
- Automated tests or traces on the follow-up path show zero calendar create/update calls.
- Audit record exists tying `original_meeting_id` → solver result → email message ids → status `proposed`.

## Out of scope

- Auto-booking, tentative holds, or Smart Invite / `.ics` REQUEST on send.
- Multi-slot suggestion grids, round-robin across a team, or adding new attendees not on the original meeting.
- Changing solver ranking, working hours, or constraint policy for follow-ups.
- In-product accept/decline UI beyond email CTAs (may exist later; not required here).
- Video conference link generation, room booking, or CRM task creation.
- Recurring follow-up series or “same time next week” without the solver.
- SMS, Slack, or in-app notifications as a substitute for emailing both parties.
- Rescheduling the original meeting.

## R1. Trigger (explicit follow-up only)

The follow-up proposal flow **must not** run as a side-effect of creating, ending, transcribing, or summarising a meeting. It runs only when the current task/context **explicitly** requests a follow-up. Recognised triggers (any one is sufficient):

- A user or agent utterance that asks to find / propose / schedule a **follow-up** time (examples: “find a follow-up time”, “propose a follow-up slot”, “book a follow-up” — the last still **proposes**, it does not book).
- A structured tool/act invocation whose name or `kind` is the follow-up-propose act (to be named by Design; e.g. `proposeFollowupSlot`).
- A meeting-notes / minutes downstream step that is **opted in** for follow-up proposal (not default-on for every meeting).

Out of trigger: an unrelated calendar event, a standup, a ceremony session, an interview offer, or a marketplace booking. Those keep their existing paths (`interviewScheduling.ts` offered-slots + book; `bookings.ts` reservations; `ceremonyMeeting.ts` ceremony links).

**Inputs required at trigger:**

| Input | Required | Source |
|---|---|---|
| Original meeting id **or** the two party user-refs + original slot end | Yes (one of) | `meetings` row, or the scheduling context that just ran the solver |
| Tenant id | Yes | auth / meeting row |
| Who requested the follow-up (organizer user-ref) | Yes | current actor |
| Invitee / counterparty user-ref | Yes | original meeting attendees (exactly two parties in this slice) |
| Duration minutes | No | default = original meeting duration; do not invent a new length |
| Window start | No | default = `max(original.endsAt, now)` |

If the original meeting cannot be loaded, or attendees ≠ 2 identifiable parties with emails, the flow **stops** (R8) — it does not guess a second party.

## R2. Solver reuse (no substitute ranking)

The slot **must** come from the existing availability stack already used for internal 1:1s:

1. Load each party’s declared windows via `loadDeclaredAvailability` (`api/src/application/calendar/attendeeAvailability.ts`).
2. Load merged busy intervals via `loadAllBusy` (same module; includes `calendarFreeBusy.ts` external calendars).
3. Call `proposeSlots` from `attendeeAvailability.ts`, which delegates ranking to `availabilitySolver.ts` (`withinWindows`, `isBusy`, duration, buffers, time zones).

**Forbidden substitutes:** hardcoded wall-clock times, “tomorrow at 10:00”, random choice among working hours, a different ranking function, interview `offered_slots` recomputation, marketplace `bookings` availability, or a user-typed datetime.

**Solver inputs that must match the original search** (unless the original context already overrode them):

- Both party calendars / user-refs
- Each party’s time zone and working-hours windows
- Duration (original meeting length)
- Buffer before/after if the original call passed one
- Busy sources (internal meetings + connected Google/Microsoft free-busy)

The window for the *follow-up* search starts at **the original meeting’s `endsAt`**, or **now** if that end is already in the past. It does not re-propose the original slot and does not search *before* the original meeting.

Persist enough to audit: a **solver input hash** (canonical JSON of party refs, duration, window start/end, buffer, tz ids) and, if the solver/call site already has one, a **solver run id**. QA must be able to join proposal → hash/run id (acceptance: “QA can trace proposal → solver run id”).

## R3. Slot selection (exactly one)

- Ask the solver for the next mutually free slots after the window start; **take the first / earliest** ranked slot.
- Persist that one slot only. This slice is not a multi-option picker (out of scope).
- If the solver returns **zero** slots: do not invent a time, do not email a slot, do not write a `proposed` row that implies a time. Outcome is `proposal_failed` with reason `no_availability` (R8).

Start and end are stored in **UTC**. Each party’s display time zone is stored alongside so emails can render local times without re-querying.

## R4. No silent booking (hard invariant)

During propose + email the system **must not**:

- Call `calendarService` create / update / delete
- Call Google/Microsoft calendar insert/patch/delete (including `transparency: 'tentative'`, `status: 'tentative'`, or busy blocks)
- Insert or update a `meetings` row to a booked/scheduled state for the follow-up
- Create a marketplace `bookings` reservation or hold
- Write busy intervals that would make the proposed slot appear taken

Booking is a **separate explicit accept task** (out of scope). Downstream agents may only propose + email. A later accept/book flow (not this PRD) is the only writer of calendar events for the follow-up.

**Testable:** a spy/mock on calendar write functions records **zero** calls for the propose+email path, including the failure and idempotent-replay paths.

## R5. Proposal object (status stays `proposed`)

Persist one auditable proposal record per successful solve. Minimum fields:

| Field | Notes |
|---|---|
| `id` | Stable id |
| `tenant_id` | Scope |
| `original_meeting_id` | Nullable only when the trigger had parties+slot without a meeting row |
| `organizer_ref` / `organizer_email` | Required |
| `invitee_ref` / `invitee_email` | Required |
| `starts_at` / `ends_at` | UTC |
| `organizer_tz` / `invitee_tz` | IANA ids used in the email |
| `duration_minutes` | Copied from solver input |
| `solver_input_hash` | Required |
| `solver_run_id` | If the runtime exposes one; else null + hash is the trace key |
| `status` | **`proposed` only** in this slice. Never `booked`, `accepted`, `held`, or `tentative`. |
| `organizer_message_id` / `invitee_message_id` | Set after send (R6) |
| `created_at` / `updated_at` | Timestamps |
| `idempotency_key` | See R9 |

Status **must not** be advanced to booked by this flow. Accept/decline handling is a later PRD.

**Placement (constraint for Design, not a schema invention here):** do **not** overload `interviews.offered_slots` (hiring) or `bookings` (commerce). Prefer a dedicated follow-up-proposal table in the same bounded context as `meetings` / calendar, or an equally auditable kernel-safe record. Architect owns the final table.

## R6. Email both parties

On a successful proposal (slot chosen + row persisted):

- Send **one email to the organizer** and **one email to the invitee**.
- Reuse `api/src/application/email/sendEmail.ts` (and existing preference / suppression rules). Do not invent a second mailer. Do not substitute Slack, SMS, or in-app-only notify.
- If product email policy already *requires* a single message with both on To/Cc, that is an allowed alternative — but **both addresses must receive the same facts**. Default is two sends so each body can show **that recipient’s local time** first.

Each email **must** include:

1. Who requested the follow-up (organizer display name).
2. Original meeting title (or “your recent meeting”) and original end, when known.
3. Proposed start/end in **the recipient’s time zone**, plus duration.
4. Explicit sentence: **nothing is booked until accepted** (or equivalent: “this time is not on the calendar yet”).
5. Accept and Decline CTAs (R7).

Store the provider message id for each send on the proposal (`organizer_message_id`, `invitee_message_id`) so QA can trace proposal → both message ids.

**Do not send** an email that claims the slot is booked, held, or confirmed.

## R7. CTA (accept is not this slice)

- Emails include **Accept** and **Decline** actions using links or reply tokens **already used by the product** (e.g. `share_links` hashed-token pattern from `interviewScheduling.ts`, or existing email action tokens). Do not mint a parallel unsigned query-string that books on GET.
- **Accept does not book in this slice.** The accept URL may land on a later booking flow or a “we recorded your accept” page; it must not call calendar create.
- Decline may mark the proposal `declined` only if Design chooses to allow that status in a fast-follow; this slice may leave status `proposed` and treat decline as out of scope. Either way, decline must not delete calendar events (there are none).

## R8. Failure behavior

| Condition | Persist | Email | Calendar | Organizer signal |
|---|---|---|---|---|
| Solver throws / provider error | optional `proposal_failed` log, no live proposal | none claiming a slot | none | if organizer email known, one failure notice; else log and stop |
| Solver returns no slots | no `proposed` row with a time | none claiming a slot | none | same as above, reason `no_availability` |
| Missing organizer or invitee email | no live proposal | none | none | email organizer only if *their* address exists; else log and stop |
| Email send fails after persist | keep `proposed` (do not book to “compensate”) | no second invented channel | none | retry send on idempotent replay; do not create an event |

Never send a “booked” confirmation on any failure path.

## R9. Idempotency

Key = `tenant_id` + original meeting id (or party pair) + `solver_input_hash` + trigger kind (`followup_propose`).

Re-running the same follow-up request:

- Does **not** insert a second live `proposed` row.
- Does **not** send a second pair of emails if both message ids are already stored.
- Returns the existing proposal.

If a prior attempt persisted a proposal but email ids are missing (send failed), replay **may** send the missing email(s) once, still without writing calendar.

A **new** original meeting, or a changed duration/window that changes the input hash, is a new proposal.

## R10. Agent contract

Downstream agents (scheduling, email, calendar, meeting-notes) **may only propose + email**. They must not:

- Treat “propose follow-up” as permission to call the book path in `meetingRoutes` / `calendarService` / `googleCalendarSync`.
- Complete the task by creating a hold “so the slot doesn’t disappear”.
- Infer follow-up from an unrelated event.

Booking requires a **separate explicit accept task** (not this PRD).
