# PRD: Propose Follow-up Slot (No Silent Booking)

## Problem & Goal

After a meeting or scheduling flow completes, users often need a follow-up. Today the product either does nothing or can create calendar events without explicit confirmation, which surprises attendees and creates unwanted holds.

**Goal:** After a scheduling context that already used the availability solver, propose one follow-up slot using that same solver, send the proposal to both parties by email, and never create or hold a calendar event until a party accepts.

## Target users / ICP roles

- **Organizer** — host or account owner who initiated the original meeting or scheduling request.
- **Invitee / counterparty** — the other party on the original meeting.
- **Internal operators / downstream agents** — scheduling, email, and calendar agents that must share this PRD and must not invent a silent-book path.

ICP: B2B knowledge workers who schedule 1:1s (sales, recruiting, CS, founder/exec) and expect email-first confirmation rather than auto-holds.

## Scope

In scope for this WIP:

- Reuse the **same availability solver** already used for the original meeting (same constraints, calendars, time zone handling, working hours, buffers, and duration defaults unless the original context already overrode duration).
- Select **one** proposed follow-up slot (not a multi-option picker in this slice).
- **Propose only** — no calendar create, update, hold, or tentative event.
- **Email both parties** with the proposed slot, original meeting context, and a clear call to action to accept or decline.
- Idempotent, auditable proposal records so downstream agents do not double-email or later “complete” the flow by booking.

## Functional requirements

1. **Trigger.** Run only when a follow-up is explicitly requested in the current task/context (e.g., post-meeting follow-up, user asked to “find a follow-up time”). Do not infer follow-up from an unrelated calendar event.
2. **Solver reuse.** Call the existing availability solver with the same party calendars, time zones, constraints, and duration used for the original slot search. Do not substitute a different ranking, random slot, or hardcoded time.
3. **Slot selection.** Return the solver’s next mutually free slot after the original meeting end (or after “now” if the original meeting is already past). If the solver returns none, do not invent a time.
4. **No silent booking.** The system must not create, patch, or delete calendar events; must not place holds, busy blocks, or tentative invites; must not write to either party’s calendar as a side effect of proposing.
5. **Proposal object.** Persist a proposal with: both party identities and emails, proposed start/end (UTC + display TZs), solver run id / input hash, original meeting id if present, status `proposed`, and timestamps. Status must not be `booked`.
6. **Email both parties.** Send one email to the organizer and one to the invitee (or a single email with both on To/Cc if product email policy already requires that). Each email must include: who requested the follow-up, proposed local times for each recipient, duration, and that **nothing is booked until accepted**.
7. **CTA.** Emails include accept and decline actions (links or reply tokens already used by the product). Accept is handled by a later booking flow, not this slice.
8. **Failure behavior.** If solver fails, no slot exists, or either email address is missing, send no “booked” confirmation, create no event, and surface a proposal-failed outcome to the organizer only when an email can be sent; otherwise log and stop.
9. **Idempotency.** The same trigger + original meeting + solver inputs must not send duplicate proposal emails or create duplicate proposal records.
10. **Agent contract.** Downstream agents may only propose + email. Booking requires a separate explicit accept task.

## Acceptance criteria

- Given an original meeting and a follow-up request, the system produces exactly one proposal whose start/end came from the same availability solver, not from a hardcoded or user-typed time.
- No calendar API create/update/delete (including tentative/hold) occurs during propose+email.
- Both parties receive an email containing the proposed slot in their local time and explicit language that the time is **not booked**.
- If the solver returns no availability, no emails claiming a slot are sent and no event is created.
- Re-running the same follow-up request does not send a second pair of emails or a second live proposal.
- Proposal status remains `proposed` until a distinct accept/book flow runs.
- QA can trace proposal → solver run id and both message ids in logs.

## Out of scope

- Auto-booking, calendar holds, or “book unless declined.”
- Multi-slot pickers, reschedule of the original meeting, or changing duration/constraints vs the original solver inputs.
- Video conference link generation, CRM notes, or tasks in external tools.
- Group meetings (>2 parties), round-robin hosts, or finding times across a team pool beyond the original two calendars.
- Accept/decline handling, reminders, or the actual booking write-path (separate PRD).
- SMS, in-app only notify, or Slack as a substitute for email.
- Changing either party’s working hours or calendar permissions.
