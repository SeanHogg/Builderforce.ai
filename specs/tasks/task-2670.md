# PRD: Bind a Readable Repository Checkout for Task #2585's Developer Container

## Problem & Goal

**Problem:** Execution #32142 (task #2585, developer lane, `in_progress`) cannot perform any repository operation. Every repository-dependent tool call fails with a "no repository bound" error:

- `git_sync_latest` → *"no repository checked out — git tools need a bound repo"*
- `git_status` → same
- `list_files` (glob `specs/tasks/task-2585.md`) → *"no repository bound to this task"*
- `run_command` (`pwd && ls -la`) → *"no repository checked out — run_command needs a bound repo"*

Root cause, confirmed on the Project 11 record: `githubRepoUrl`, `githubRepoOwner`, `githubRepoName`, `sourceControlRepoFullName`, `sourceControlRepoUrl`, and `sourceControlIntegrationId` are all `null`. Task 2585's `explicitRepoId` is also `null`. The `projects.update` API only exposes `name` / `description` / `status` / `modality` — there is no field an agent can call to set a repo binding. This requires an operator action (connect the repo in project settings), it is not fixable from within an agent run.

This is the same root defect already tracked in #2600 (scoped to #2554); this ticket tracks the identical defect as it blocks #2585.

**Goal:** Bind Project 11 to its GitHub source repository so that a developer container executing on branch `builderforce/task-2585` has a real, readable checkout — enabling `search_code`, `read_file`, in-place edits, type-check/test runs, and PR creation.

## Why This Can't Be Worked Around

Architect Design D-12 (the design #2585 must implement) requires editing **eleven existing files**, all of which must be read before they're safely modified:

- `api/src/infrastructure/database/schema/commerce.ts` (`freelancerProfiles` Drizzle definition)
- `api/src/presentation/routes/freelancerRoutes.ts` (`PATCH /api/freelancers/me`, `GET /api/freelancers`)
- `frontend/src/lib/freelance/talentProfile.ts` (`FreelancerProfile` type, `TalentFilters`)
- `frontend/src/app/freelancer/profile/page.tsx` (replace free-text location input)
- `frontend/src/app/marketplace/page.tsx` + advisors filter components
- Five `next-intl` locale catalogs

A blind `write_file` against any of these — without first reading current contents — risks silently destroying production code. This is not hypothetical: commit `0267ffd` did exactly this to `canvasChange.ts` under the same defect (see #2600 / #2642). No workaround that fabricates file contents is acceptable here.

## Target Users / ICP Roles

- **Operator / Project Admin** — the human (or privileged internal tool) with access to project settings who can perform the source-control connect action. This is the actor who resolves this ticket.
- **Developer agent (execution runtime)** — the automated agent that consumes the bound repo to implement #2585. Not a human end-user, but the direct consumer of this fix's output.
- **Downstream ticket owners** (#2585, PRD 26 P3, and any future task on Project 11) — blocked until this binding exists.

## Scope

In scope:
- Diagnosing and confirming the missing repository binding on Project 11 (already done; recorded here).
- Performing/enabling the operator-side connect of Project 11 to its GitHub repository via project settings (or equivalent source-control integration flow).
- Verifying all repo-bound fields are populated post-connect.
- Verifying a fresh developer container run on task #2585 can perform the full repo-dependent workflow end-to-end.

Out of scope items are listed below.

## Functional Requirements

1. **FR-1 — Repository connection.** Project 11 must be connected to its intended GitHub repository through the project settings source-control integration flow (operator action), populating:
   - `githubRepoUrl`
   - `githubRepoOwner`
   - `githubRepoName`
   - `sourceControlRepoFullName`
   - `sourceControlRepoUrl`
   - `sourceControlIntegrationId`

2. **FR-2 — Task-level binding resolution.** Task #2585 must resolve a non-null effective repo (either inherited from the now-bound Project 11, or via `explicitRepoId` if task-level override is the chosen mechanism) so the execution runtime has an unambiguous repo to check out.

3. **FR-3 — Branch checkout.** A developer container dispatched against task #2585 must check out (or create, if absent) branch `builderforce/task-2585` from the bound repository's default branch.

4. **FR-4 — Tool functionality restored.** With the binding in place, the following must succeed in a fresh execution against task #2585:
   - `git_sync_latest`
   - `git_status`
   - `list_files` (including `specs/tasks/task-2585.md`)
   - `run_command` (`pwd && ls -la`, plus frontend/api type-check and test commands)
   - `search_code`
   - `read_file` on all eleven D-12 target files
   - `write_file` / in-place edit tooling
   - PR creation from the branch

5. **FR-5 — No silent re-dispatch.** Until this binding is confirmed working end-to-end (per FR-4), the developer slot for #2585 must not be re-dispatched into a container, to avoid repeating the blind-write failure mode seen in #2600/#2642.

6. **FR-6 — Regression check against sibling ticket.** Confirm whether resolving this on Project 11 also requires or informs a parallel fix for #2600 (Project scope for #2554), since both share the identical root defect. Document any shared fix vs. divergence.

## Acceptance Criteria

- [ ] Project 11's `githubRepoUrl`, `githubRepoOwner`, `githubRepoName`, `sourceControlRepoFullName`, `sourceControlRepoUrl`, and `sourceControlIntegrationId` are all non-null and point to the correct repository.
- [ ] Task #2585 resolves a valid bound repository (via project inheritance or `explicitRepoId`).
- [ ] A new developer container execution on task #2585, branch `builderforce/task-2585`, successfully runs `git_sync_latest`, `git_status`, and `list_files` without "no repository bound" errors.
- [ ] The same execution successfully runs `run_command` (`pwd && ls -la`) and shows an actual checked-out working tree.
- [ ] `search_code` and `read_file` succeed against all eleven D-12 target files listed above.
- [ ] The container can perform an in-place edit (`write_file`/patch) on at least one of the eleven files based on its actual current content (not fabricated content).
- [ ] Frontend and API type-check commands run successfully in the container (pass/fail status is irrelevant to this ticket — only that they *execute* against real code).
- [ ] Test suite invocation runs successfully in the container.
- [ ] The container can open a real PR from `builderforce/task-2585` against the correct base branch.
- [ ] This ticket is closed only after the above are verified in a live execution, not merely after the settings change is saved.
- [ ] #2585 developer slot is confirmed un-blocked and safe to (re)dispatch.

## Out of Scope

- Implementing the actual D-12 feature work for #2585 (location-on-profile + optional advisors filter). That remains tracked under #2585 itself and is only unblocked, not delivered, by this ticket.
- Adding a self-service API (e.g., extending `projects.update`) to let agents set repo bindings themselves. Valuable follow-up, but not required to unblock #2585 and not delivered here.
- Fixing #2600 / #2554 directly (tracked separately), though findings here should be cross-referenced there given the shared root cause.
- Remediating any damage from the prior blind-write incident (commit `0267ffd` / #2642) — that is a separate cleanup effort.
- General source-control integration hardening, audit logging, or permissions review beyond what's needed to confirm this specific binding.
