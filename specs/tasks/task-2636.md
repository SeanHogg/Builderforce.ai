# PRD: C2 — ICP picker frontend for `ri_icps`

**Status:** WIP  
**Depends on:** C1 contract (`intake.icp` is optional)  
**Constraint:** ICP is never a send gate. Missing ICP must not block drafting or sending.

---

## Problem & Goal

**Problem.** `ri_icps` exists as an API-only resource. Guided campaign intake has no UI to list, create, or select an ICP. Operators who already keep ICPs in the workspace cannot attach them during intake; operators who do not have one cannot create one in-flow. Brand and workspace profile data that could seed an ICP is unused.

**Goal.** Surface list / create / select of ICPs in guided campaign intake so `intake.icp` can be set when the operator chooses. Prefill from `brandKit` / workspace profile when present. Treat ICP as optional enrichment, not a required field, not a Growth send blocker, and not a draft blocker.

**Success.** Operators can pick or create an ICP in intake; campaigns draft and send with or without an ICP; Growth send paths are unchanged with respect to ICP presence.

---

## Target users / ICP roles

| Role | Why they care |
| --- | --- |
| Campaign operator / marketer | Attaches an existing ICP or creates one during guided intake without leaving the flow. |
| Growth sender | Continues to draft and send regardless of whether an ICP is selected. |
| Workspace admin / brand owner | Brand kit and workspace profile already describe the audience; that data should prefill create, not force a pick. |

No new roles. No permission model change beyond existing `ri_icps` access.

---

## Scope

**In scope**

- Guided campaign intake UI: list existing `ri_icps`, select one, clear selection, create a new ICP in-flow.
- Bind selected ICP to `intake.icp` per C1 (optional field).
- Prefill create form from `brandKit` / workspace profile when those sources have usable fields.
- Empty, loading, error, and “no ICPs yet” states that still allow continue / draft / send.
- Persistence of selection for the current intake session; restore on return to the step if the campaign is still in intake.
- Read-only summary of the selected ICP on later intake steps (name + short description), with change/clear actions.

**Depends on C1**

- `intake.icp` is optional. Frontend must not invent a required contract.
- Do not send a synthetic / placeholder ICP id when none is selected.

---

## Functional requirements

### F1 — Placement

1. ICP picker lives in guided campaign intake as its own optional step or section, after brand/workspace context is available and before send.
2. Step/section is skippable. Primary CTA on the step is “Continue” (or equivalent), not “Select ICP”.
3. Copy states that ICP is optional and does not block draft or send.

### F2 — List and select

1. Load ICPs from `ri_icps` for the current workspace.
2. Show name, short description / summary, and updated-at (or equivalent) for each row.
3. Single-select. Selecting a row sets `intake.icp` to that ICP’s id (C1 shape).
4. Operator can clear selection; `intake.icp` is omitted or null per C1.
5. If the previously selected ICP is missing (deleted or inaccessible), clear selection, show a non-blocking notice, and leave intake valid.

### F3 — Create in-flow

1. “Create ICP” opens an in-flow form (modal or inline), not a separate app area that abandons intake.
2. On success, the new ICP is selected and `intake.icp` is set.
3. Create failure is inline and non-blocking; intake remains valid; operator can retry, pick an existing ICP, or continue without one.
4. Cancel create leaves prior selection (or none) unchanged.

### F4 — Prefill

1. When opening create, prefill from `brandKit` and/or workspace profile if present (e.g. audience, industry, company size, geography, value prop, tone).
2. Prefill is editable. Empty sources yield an empty form; do not block create.
3. Do not auto-create an ICP from brand/profile. Prefill is assistive only.
4. Do not auto-select an ICP just because brand/profile data exists.

### F5 — Never a gate

1. Missing ICP does not disable Continue, Save draft, Generate / draft campaign, or Send (including Growth send).
2. Do not add ICP to Growth send eligibility, quota, or blocker lists.
3. Validation of intake must succeed with `intake.icp` absent.
4. Downstream agents reading this PRD must not treat ICP as required.

### F6 — Resilience

1. `ri_icps` list/create errors: inline error, retry, continue without ICP.
2. Slow list load: skeleton/spinner; Continue remains enabled.
3. Do not retry-loop in a way that stalls intake.

---

## Acceptance criteria

1. **List:** With one or more workspace ICPs, intake shows them and the operator can select exactly one; `intake.icp` matches the selected id.
2. **None selected:** Operator skips the step or clears selection; payload has no required ICP; draft and send succeed.
3. **Create:** Operator creates an ICP in-flow; it appears in the list, is selected, and `intake.icp` is set; intake is not abandoned.
4. **Prefill:** With brandKit / workspace profile fields present, create form is prefilled and editable. With those sources empty, create form is empty and still submittable (subject to existing `ri_icps` create validation only).
5. **No auto-gate:** Brand/profile present does not auto-select or auto-create an ICP and does not require the operator to confirm an ICP to continue.
6. **Deleted selection:** Selected ICP disappears; selection clears; notice shown; Continue / draft / send still work.
7. **API down:** List or create fails; error + retry; Continue / draft / send still work; no ICP attached.
8. **Growth send:** Campaigns with and without `intake.icp` are sendable on Growth; no new ICP-based blocker, tooltip, or disabled Send.
9. **C1 contract:** Client omits or nulls `intake.icp` when unset; never sends a dummy id; when set, shape matches C1.
10. **Copy / UX:** Optional nature is visible (label or helper text); primary path does not imply ICP is required.

---

## Out of scope

- Making ICP required for draft, send, or Growth.
- Backend changes to `ri_icps` or to the C1 `intake.icp` contract (C1 owns the contract).
- ICP as a send-time personalization or compliance gate.
- Multi-select ICPs, ICP versioning UI, sharing ICPs across workspaces.
- Full ICP management app (bulk edit, archive admin, analytics).
- Auto-generating or auto-saving an ICP from brandKit / profile without operator confirm.
- Using ICP presence for packaging, entitlements, or feature flags.
- Changing email/send payload beyond passing through optional `intake.icp`.
- Mobile-specific redesign (follow existing intake patterns).
- A/B experiments or new analytics events beyond existing intake instrumentation (optional follow-up).

### Architecture overview

The ICP picker is a **frontend-only optional section** within the guided campaign intake flow (epic #2547). It consumes the existing workspace `ri_icps` list and create APIs — no backend changes. The selection is written into the C1 intake state (`intake.icp`, optional) and flows through the existing guided-campaign run contract in `packages/creation-canvas-contract/src/guidedCampaign.ts` (C1 home, #2629). No new checklist items, no new `maySend` conjuncts, no Growth send blocker — P8 (never a gate) is invariant.

**Decision: Section, not a standalone step.** The ICP picker is a collapsible or skippable **section** embedded in the intake flow rather than a full numbered step. It may appear:
- As an expandable panel within the Connect/Context step (after brand/workspace context is available), OR
- As a lightweight optional section between Connect and Draft Copy.

The primary Continue CTA is the intake's own Continue — never "Select ICP." The section is always skippable; Continue is never disabled for ICP absence (P8 invariant).

Implemented as a single React component hierarchy: `IcpPickerSection` (container/states) → `IcpList` (list/select/clear) + `CreateIcpModal` (in-flow create form).

### Prefill mapping (P7 / R-8)

When opening CreateIcpModal, map available fields from the intake session's `brandKit` and workspace profile into the form. Each is editable; none are required beyond `ri_icps` existing validation.

| Source | Source field (best-effort) | ICP create form field |
|--------|---------------------------|----------------------|
| `brandKit` | `audience` / `whoWeServe` / `targetAudience` | audience / who-we-serve |
| `brandKit` | `industry` / `vertical` | industry |
| `workspace profile` | `industry` / `vertical` | industry (fallback) |
| `workspace profile` | `companySize` / `size` | companySize |
| `workspace profile` | `geography` / `region` / `country` | geography |
| `brandKit` | `valueProposition` / `offer` / `uniqueSellingPoint` | valueProposition |
| `brandKit` | `tone` / `voice` / `brandVoice` | tone / voice |

**Mapping rules:**
1. Read the intake session's `brandKit` first; fall back to workspace profile for each field independently.
2. Only map fields that actually carry a non-empty value from the source. Do not set empty/undefined placeholders.
3. The operator can edit every prefill. No field is locked because it came from brandKit.
4. Empty sources → empty form → operator fills manually → submits under existing `ri_icps` validation only.
5. **Never auto-create.** The modal must be explicitly opened, filled, and submitted.
6. **Never auto-select.** ICP presence in brandKit/profile never implies a selection.

```
                    │ clear       │ change      │ create (modal)
               ┌────▼────┐  ┌────▼────┐   ┌────▼────────┐
               │  LIST   │  │  LIST   │   │ CREATE_MODAL │
               │(unsel.) │  │(re-pick)│   └────┬────────┘
               └─────────┘  └─────────┘        │ success → SELECTED + new id
                    │                           │ failure → inline error, modal stays
                    │                           │ cancel → SELECTED (unchanged) or LIST
                    │
              ┌─────▼──────────┐
              │ SELECTED_404   │──── detected on re-fetch / session restore
              │ (non-blocking  │
              │  notice shown) │
              └─────┬──────────┘
                    │ auto-clear → LIST or EMPTY
                    │ Continue / draft / send always enabled
```

**Invariant across all states:** Continue, Save draft, Generate / draft campaign, and Send are **never disabled** due to ICP absence, error, or cleared selection (P8). The state machine governs display; it never governs intake progression.

### Resilience and edge cases (P12 / R-13)

| Scenario | Behavior |
|----------|----------|
| List API returns 4xx/5xx | Show `IcpErrorState` with inline message and Retry button. Continue stays enabled. No ICP attached. |
| List API slow (>500ms) | Show `IcpSkeleton` (spinner + placeholder rows). Continue stays enabled. |
| Create API fails | Inline error inside modal. Modal stays open. Operator may retry, close modal, or Continue without ICP. Continue outside modal stays enabled. |
| Selected ICP deleted between selection and later step | On next intake state hydration or list re-fetch, clear selection. Show non-blocking toast/notice: "The selected ICP is no longer available." Continue stays enabled. |
| Session restore with stale id | On mount, verify the persisted id against the fetched list. If missing, clear (R-6/P6). Do not restore a stale id. |
| Guest / anonymous / `agentDraftOnly` | `ri_icps` list returns empty or 403. Surface same as empty/error states. Continue enabled. No sign-in wall. No guest-scoped ICP creation. |
| One in-flight list at a time | Debounce / abort-in-flight before a new fetch. Operator retry is explicit (button), not automatic loop. |
| brandKit / workspace profile absent | Create form opens empty. All fields editable. Submit under existing `ri_icps` validation only. |

### Session persistence (P10 / R-11)

The selection is stored on the **existing** C1 intake state object — no new store. The `IcpPickerSection` reads and writes `intake.icp` through the same C1 adapter (`canvasMarketing.ts` or equivalent) that already manages the guided-campaign run.

- **Write:** On select, create-success, or clear, update `intake.icp` on the intake state via the C1 adapter.
- **Read:** On mount, read `intake.icp` from the intake state. If set, verify the id exists in the fetched list. If missing → clear (R-6). If present → restore selection.
- **Scope:** Per-intake-run. No cross-campaign persistence. No new database table, localStorage key, or cookie.

### Later-step summary (P11 / R-12)

When a selection exists and the operator is on a later intake step (after the ICP section), show `IcpSummary` inline:

```
┌─────────────────────────────────────────────┐
│ ICP: "SMB SaaS Founders"                    │
│ Early-stage B2B SaaS founders, 1-50 employees│
│ [Change]  [Clear]                           │
└─────────────────────────────────────────────┘
```

- **Change** navigates back to / reopens the `IcpList` without abandoning the intake run.
- **Clear** immediately clears `intake.icp` (omit/null) and hides the summary.
- When no ICP is selected, show **nothing** — no placeholder, no "No ICP selected" message. Absence is the normal state.

### Integration points

1. **C1 intake state adapter** (`canvasMarketing.ts` or equivalent). The ICP picker reads and writes `intake.icp` through the same adapter that manages the guided-campaign run state. No new state channel.

2. **`ri_icps` API.** Existing routes for list (GET) and create (POST). The `icpService.ts` thin wrapper calls these; no new routes, no new columns, no new permissions.

3. **brandKit / workspace profile.** Read from the intake session context (already available per placement rule — after brand/workspace context is established). Map candidate fields per the prefill table above.

4. **Growth send path.** No change. `intake.icp` is carried pass-through on the send payload when set; absent otherwise. No new blocker, no new `sendReadiness` item. C3 (#2638) remains the confirm gate.

### Design decisions log

| Decision | Rationale |
|----------|-----------|
| Section, not a standalone step | Skips the visual weight of a numbered step. A section feels lighter and communicates "optional" more naturally. The operator's primary path (Continue) is never interrupted. |
| Modal for create, not inline | Keeps the list context visible. Avoids layout shift. The operator can see the list while deciding whether to create. Cancel is unambiguous — close modal, list unchanged. |
| Single `IcpPickerSection` container with state machine | One owner for fetch, selection, persistence, and error recovery. Child components are presentational. No cross-component state leakage. |
| No `intake.icp` key on intake state when unset (omit, not `null` as default) | C1 specifies "omit or null." Omission is the safer default: absent key cannot be misinterpreted as "selected but null." C2 sends the field only when a selection exists. |
| Prefill reads brandKit first, workspace profile as fallback | brandKit is campaign-scoped and more specific. Workspace profile is a reasonable fallback. Per-field fallback avoids all-or-nothing. |
| Retry is operator-initiated, not automatic | Prevents retry-loop stalls. Operator may choose to continue without ICP if the API is persistently down — that is the correct behavior per P8. |
| No new persistence store | C1 already owns the intake run state. Adding a second store doubles the consistency burden (R-6 stale-id problem, session restore). The C1 adapter is the single source of truth. |
