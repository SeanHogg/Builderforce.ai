# PRD: Add `advisory` meeting kind

## Problem & Goal

Meeting routing currently recognizes a closed set of kinds and does not include `advisory`. Advisory sessions are not team ceremonies; they should be first-class in routing without inheriting ceremony defaults.

**Goal:** Register `advisory` in `KINDS` in `meetingRoutes.ts` so advisory meetings can be created, routed, and handled like other kinds, while **not** turning team-ceremony chat on by default for advisory.

## Target users / ICP roles

- Product and engineering teams creating or joining advisory meetings
- Advisors / coaches running 1:1 or small-group advisory sessions
- Downstream agents implementing and testing meeting routing and chat defaults

## Scope

In scope:

- Add `advisory` to `KINDS` in `meetingRoutes.ts`
- Ensure advisory is a valid meeting kind for routing, validation, and any kind-based dispatch that reads `KINDS`
- Keep team-ceremony chat **off by default** for `advisory` (do not treat advisory as a team ceremony for chat defaults)
- Preserve existing kinds and their current default chat behavior

Out of scope is listed below.

## Functional requirements

1. `KINDS` in `meetingRoutes.ts` includes the string `advisory` alongside existing kinds.
2. Requests and routes that validate meeting kind against `KINDS` accept `advisory` and reject unknown kinds as before.
3. Advisory meetings do **not** get team-ceremony chat enabled by default.
4. Default chat (or equivalent ceremony-chat flag) for advisory is off unless the caller explicitly opts in.
5. Existing kinds are unchanged: membership of `KINDS`, routing, and ceremony-chat defaults for non-advisory kinds stay the same.
6. Advisory is not classified or aliased as a team ceremony for chat-default logic (no “if kind is in KINDS then enable ceremony chat”).

## Acceptance criteria

- `KINDS` contains `advisory`.
- Creating or routing a meeting with `kind: "advisory"` succeeds and does not fail kind validation.
- A newly created advisory meeting does **not** have team-ceremony chat on by default.
- Explicitly enabling chat for an advisory meeting still works if that path already exists for other kinds.
- Regression: existing kinds still route correctly; their ceremony-chat defaults are unchanged.
- No other files or product surfaces are required for this change unless they derive allowed kinds solely from `KINDS` (those should pick up `advisory` automatically).

## Out of scope

- UI, copy, or scheduling flows for advisory meetings beyond kind registration and chat default
- Changing chat defaults for any non-advisory kind
- Turning ceremony chat on for advisory by default, even as a “temporary” or “opt-out” default
- New chat features, permissions, recording, or transcription behavior
- Database migrations, new API resources, or new meeting types beyond the `advisory` kind string
- Analytics, notifications, or calendar integrations specific to advisory
- Treating advisory as a team ceremony for any other default (not only chat)

### Current contract (do not invent a new one)

Create path (`POST /api/meetings`):

```
const kind = body.kind && KINDS.has(body.kind) ? body.kind : 'adhoc';
const linkChat = body.linkTeamChat ?? TEAM_CEREMONY_KINDS.has(kind);
```

- **`KINDS` today:** `standup`, `planning`, `retrospective`, `adhoc`, `direct`, `interview`, `review`.
- **`TEAM_CEREMONY_KINDS` today:** `standup`, `planning`, `retrospective`, `review`.
- Unknown or omitted `kind` is **coerced to `adhoc`**. It is **not** HTTP 400. PM FR-2’s “reject unknown kinds” is **not** current behavior; this ticket must **not** introduce a reject.
- Team-ceremony chat default-on is **only** `TEAM_CEREMONY_KINDS.has(kind)`. `KINDS.has(kind)` must never become the chat-default predicate.
- Callers may pass `linkTeamChat: true | false` to override the default.
- `meetings.kind` is `VARCHAR(16)` with **no CHECK** (`api/migrations/0292_meetings_and_calendar.sql`). `"advisory"` (8 chars) already fits. **No migration.**

Closest analog for advisory: `interview` / `direct` / `adhoc` — valid `KINDS` members that are **not** team ceremonies.

### R-1 — Register the kind

Add the string `'advisory'` to the `KINDS` set in `api/src/presentation/routes/meetingRoutes.ts`. Do not remove, rename, or reorder any existing member as a behavior change.

### R-2 — Do not treat advisory as a team ceremony

Do **not** add `'advisory'` to `TEAM_CEREMONY_KINDS`. Do not replace `TEAM_CEREMONY_KINDS` with `KINDS`. Do not add `if (KINDS.has(kind)) linkChat`. Advisory is classified like `interview` / `direct` / `adhoc`.

### R-3 — Persist `kind = 'advisory'`

`POST /api/meetings` with `kind: "advisory"` must persist `meetings.kind = 'advisory'`. Today that payload is coerced to `adhoc` because the string is missing from `KINDS`. After this change it must not be.

### R-4 — Default team-ceremony chat off

A newly created advisory meeting with `linkTeamChat` omitted must **not** set `meetings.chatId` (no `getOrCreateTeamChat` call). Equivalent: `linkChat` evaluates false.

### R-5 — Explicit opt-in still works

`POST` with `kind: "advisory"` and `linkTeamChat: true` must still attempt to link the team chat on the same path as other kinds.

### R-6 — Unknown kinds unchanged

Payloads with a kind **not** in the updated `KINDS` (e.g. `"workshop"`) continue to coerce to `adhoc`. Do **not** add a 400 “unknown kind” reject on this ticket.

### R-7 — Regression

- `TEAM_CEREMONY_KINDS` membership stays `{standup, planning, retrospective, review}`.
- Ceremony kinds still default `linkTeamChat` on.
- `interview`, `direct`, `adhoc` still default it off.
- Existing create / list / get / join-by-token / book-by-token routing is otherwise unchanged.

### R-8 — Default title

`defaultTitle('advisory')` may keep the existing `default` branch (`'Meeting'`) **or** add `case 'advisory': return 'Advisory Session'`. It **must not** return a ceremony title (`Daily Standup`, `Planning Session`, `Retrospective`, `Review`).

### R-9 — No extra surfaces (out of scope, named so they are not “fixed” here)

This ticket does **not** change:

- `frontend/src/components/meetings/ScheduleMeetingPanel.tsx` — it **duplicates** `KINDS` / `CEREMONY_KINDS` and will **not** pick up `advisory` automatically. Advisory is visitor-booked (parent #2532), not a team-schedule picker option.
- `MeetingKind` in `frontend/src/lib/builderforceApi.ts`
- `api/src/application/ceremony/ceremonyMeeting.ts` / ceremony sessions
- visitor book-by-token / join-by-token (parent #2532)
- schema / migrations
- notifications, analytics, calendar category
- `MARKETPLACE_LISTING_KINDS` or `/advisors`

### R-10 — Tests (developer / QA; BA does not author the suite)

- Create `kind: "advisory"` → 2xx, stored kind `advisory`, `chatId` null/absent.
- Create `kind: "advisory", linkTeamChat: true` → chat link attempted / `chatId` set when team chat resolves.
- Create `kind: "standup"` (no `linkTeamChat`) → still defaults chat on.
- Create `kind: "not-a-kind"` → still stored as `adhoc`.
- Create `kind: "interview"` → still `interview`, chat off.
