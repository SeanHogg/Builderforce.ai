# PRD 26 P3 — Pro-bono badge, location, Start/Grow/Exit filters

**Parent:** Advisor Platform (PRD 26)  
**Depends on:** P0 (price `0` unpaid sessions; stage fields per #2527; location on advisor records) and P1. **Do not start** until P2 (`#filters/chat/Resources`) is in flight **or** the P0+P1 kill condition has passed.  
**Specs:** `specs/builderforce/26-prd-advisor-platform.md`, `specs/builderforce/26-implementation-notes-advisor-platform.md`

## Problem & Goal

Founders scanning talent and marketplace cards cannot tell which advisors offer unpaid sessions, where they work, or which company stage they serve. Those signals already exist in P0 data (price `0`, location, Start/Grow/Exit) but are not surfaced on cards or as first-class listing filters.

**Goal:** Make unpaid (pro-bono) availability, location, and stage intent visible and filterable on `?category=advisors` without new commerce, payout, or affiliation work. Badge is present only when unpaid; otherwise it is absent.

## Target users / ICP roles

- **Founders / seekers** browsing `?category=advisors` who need to filter by stage (Start / Grow / Exit), optionally by location, and spot volunteer sessions at a glance.
- **Advisors** who already mark sessions unpaid (price `0`) and set location and stage in P0; they do not get a new pricing or payout flow in P3.
- **Marketplace / talent card consumers** (same listing surfaces used for other categories).

## Scope

In scope: read-only presentation and filtering of P0 fields.

- Volunteer / pro-bono badge on **talent cards** and **marketplace cards**.
- Location on the **advisor profile** and as an **optional** listing filter.
- Start / Grow / Exit as **first-class** listing filters on `?category=advisors`, matching P0 stage fields (#2527).

Out of this PRD’s build boundary: anything that waits on P2 not being in flight (unless P0+P1 kill has passed).

## Functional requirements

### Pro-bono / volunteer badge

1. An advisor is **unpaid-eligible** when they have marked sessions unpaid with **price stored as `0` in P0**. No other price, coupon, or “free trial” signal counts.
2. When unpaid-eligible, show a **Volunteer / pro-bono** badge on talent cards and marketplace cards for that advisor.
3. When not unpaid-eligible, the badge is **not rendered** (no empty chip, placeholder, or “paid” counterpart).
4. Badge copy and treatment are consistent across talent and marketplace cards. It is a status indicator only; it does not change booking, checkout, or payout.
5. If unpaid status changes in P0 (price no longer `0`, or sessions no longer marked unpaid), cards update on next load/refresh; no separate badge CMS.

### Location

6. Advisor **profile** displays location from the P0-stored location field. If location is missing, omit the location row; do not invent a default.
7. `?category=advisors` listings expose location as an **optional** filter (seeker can use the list with no location selected).
8. Filter matching uses the same location values stored in P0 (no new geo index, map, or radius product in P3 unless already provided by shared listing infra).
9. Location on cards may be shown where the existing card layout already shows secondary metadata; profile remains the source of truth for the full location string.

### Start / Grow / Exit filters

10. On `?category=advisors`, **Start**, **Grow**, and **Exit** are first-class listing filters, not buried in “more filters.”
11. Values match P0 stage fields (#2527). An advisor appears for a stage if that stage is set on their P0 record. Multi-stage advisors appear in each selected stage they match.
12. Stage filters compose with existing listing query params and with the optional location filter. Unselected stage means no stage constraint.
13. Filter UI and URL state follow the same listing filter patterns as the rest of the marketplace (query-param driven, shareable, clearable).
14. Empty result set: standard empty listing treatment; do not hide the stage or location controls.

### Non-goals encoded as requirements

15. **No new payout rail.** Unpaid remains price `0`; P3 does not add settlement, credits, or “volunteer payout.”
16. **No SCORE/SBA affiliation** labeling, badges, or partnership claims.

## Acceptance criteria

- Given an advisor with P0 sessions marked unpaid and price `0`, talent and marketplace cards show the Volunteer / pro-bono badge.
- Given an advisor with no unpaid (price `0`) sessions, those cards do not show the badge in any form.
- Given an advisor with location set in P0, the profile shows that location; given none, location is omitted.
- Given `?category=advisors`, a seeker can apply location as an optional filter and see only matching advisors; clearing location restores the unfiltered-by-location set.
- Given `?category=advisors`, Start, Grow, and Exit are visible as first-class filters and constrain results to P0 stage fields (#2527).
- Combined stage + location filters return the intersection; URL reflects applied filters and round-trips on reload.
- Booking, pricing, and payout behavior are unchanged from P0/P1; price `0` is still the unpaid source of truth.
- No SCORE, SBA, or other affiliation mark ships with this work.
- Work does not start until P2 is in flight or the P0+P1 kill condition has passed.

## Out of scope

- New payout, billing, or credits rail; paid-session pricing UX beyond existing P0 price `0`.
- SCORE, SBA, or any government/nonprofit affiliation.
- New advisor onboarding fields (location and stage are P0; P3 only displays and filters them).
- Map, geocoding product, distance/radius search, or relocating advisors.
- Chat, Resources, or other P2 surfaces except shared listing/filter infrastructure already in flight.
- Changing who can set price `0` or stage; moderation, trust, or verification of “volunteer” claims.
- Badge on surfaces other than talent and marketplace cards (e.g. search SERP chrome, emails, invoices) unless those cards are reused as-is.
- Analytics dashboards, SEO landing pages per stage, or net-new category routes beyond `?category=advisors`.

## Requirements

P3 is **read-only presentation and filtering** of fields P0 already stores on the advisor talent record. It does not introduce commerce, payout, affiliation, geo-search, or a new marketplace family. `?category=advisors` remains a **talent filter** (composition contract): it is not `/advisors`, not a `MARKETPLACE_LISTING_KINDS` value, and not a fifth family.

**Sequencing.** Implementation (code) must not start until P2 (#2579 — expertise/language/method/stage filters, visitor chat, Resources tab) is in flight **or** the P0+P1 kill condition on epic #2522 has passed. This Requirements document may ship while P2 is in spec so architecture can bind to one stage axis.

### Glossary

- **Advisor listing.** Talent `person` rows that P0 marks as advisor-mode, browsed at `/marketplace?category=advisors` (legacy `category` maps onto the Talent family; `resolveFamily` must recognise `advisors` as that filter, not as a new `FamilyId`).
- **Unpaid-eligible.** The advisor has at least one P0 session whose stored price is integer `0`. `null`/absent price is not unpaid. Coupons, trials, “free intro”, and listing `hourlyRateCents` are not this signal.
- **Volunteer / pro-bono badge.** A status chip on cards only. It does not change Book, checkout, or payout.
- **First-class filter.** A control visible on the advisor listing toolbar without opening a drawer or “more filters”.
- **Optional filter.** The list is valid with the control unset; unset means no constraint on that axis.

### R1 — Unpaid-eligible predicate

1. Source of truth is **P0 session price `=== 0`** (the same integer P0 writes when the advisor marks a session unpaid). No other price, coupon, promo, or “free trial” field counts.
2. Eligibility is **any-session**: one unpaid session makes the advisor unpaid-eligible even if other sessions are priced.
3. If P0 later stores no session at price `0`, the advisor is not unpaid-eligible. Cards update on the **next listing/profile load**; P3 does not add a badge CMS, cache invalidation product, or webhook.
4. P3 does **not** add an unpaid / pro-bono **listing filter**. Badge only.

### R2 — Volunteer / pro-bono badge (cards)

1. When unpaid-eligible, render one badge on:
   - **Talent cards** (marketplace Talent grid at `?category=advisors` and any talent card that grid reuses).
   - **Marketplace cards** for the same advisor when that card is the listing tile (same grid today; if a later surface reuses the card component, the badge ships with the component).
2. When **not** unpaid-eligible, **do not render** the badge: no empty chip, placeholder, “Paid” counterpart, or layout hole reserved for it.
3. Copy is consistent on both card types. Canonical English: **Volunteer**. Accessible name / title may read “Volunteer / pro-bono”. Do not use SCORE, SBA, or “nonprofit” wording.
4. The badge is informational. Book CTA, `booking_reservations`, checkout, and payout are unchanged from P0/P1. Price `0` remains the unpaid source of truth at booking time.
5. Grid payloads must carry enough data to decide the badge **without N+1 booking-service fetches per card** (server-computed `unpaidEligible` or equivalent on the freelancer list DTO).

### R3 — Location on profile

1. Advisor profile (existing talent profile renderer P0 reuses — `TalentProfileView` / talent detail) shows the P0 location string when it is non-empty after trim.
2. When location is missing, **omit the location row**. Do not invent “Remote”, “Worldwide”, or a blank placeholder.
3. Profile remains the source of truth for the full location string. Cards may show location only where the existing card already has a secondary-metadata slot; P3 does not redesign the card.

### R4 — Location as an optional listing filter

1. On `?category=advisors` only, expose location as an **optional** filter. Other marketplace categories must not gain this control or be constrained by `location`.
2. Matching uses the **same P0 string values** (exact match after trim; case-insensitive). No geocoding, map, radius, IP “near me”, or new geo index in P3 unless shared listing infra already provides it — and this ticket must not build that infra.
3. Unset / cleared location restores the set that is unfiltered-by-location (other filters still apply).
4. Values offered in the control are the distinct P0 location strings present on **currently advisor-eligible** published listings (or a simple text input if P0 has no enum). Do not ship a world gazetteer.

### R5 — Start / Grow / Exit as first-class listing filters

1. On `?category=advisors` only, **Start**, **Grow**, and **Exit** are first-class toolbar chips/toggles — not buried in “more filters”.
2. Values are P0 `start` | `grow` | `exit`. An advisor appears for a selected stage **iff that stage is set on their P0 record**.
3. Multi-stage advisors appear for **each** selected stage they match (OR across selected stages).
4. Unselected (no stage chip on) means **no stage constraint**.
5. Same P0 stage field P2 filters on. P3 must not introduce `BUSINESS_STAGES` or a parallel `stagesServed` column.

### R6 — Filter composition, URL, empty set

1. Stage and location **intersect** (AND). They also compose with P2 advisor filters (expertise, language, method) and existing talent query params (`q`, paging, sort) without breaking non-advisor categories.
2. Filter UI and URL follow existing marketplace listing patterns: **query-param driven, shareable, clearable, round-trip on reload**.
3. Canonical query params (advisor listings only; ignored elsewhere):
   - `stage` — repeatable and/or comma-separated `start` \| `grow` \| `exit`. Invalid tokens ignored.
   - `location` — single string, URL-encoded P0 value.
4. Empty result set uses the **standard empty listing treatment**. Stage and location controls stay visible. Do not hide filters because the intersection is empty.
5. Clearing a control removes its param from the URL (no `stage=` empty residue required).

### R7 — Surfaces and category isolation

1. In scope: advisor talent cards, marketplace listing cards for those advisors, advisor profile location row, advisor listing toolbar at `?category=advisors`.
2. Out of card scope unless the same component is reused as-is: search SERP chrome, emails, invoices, gigs-only tiles, agent/asset/company families.
3. `?category=advisors` must continue to resolve through Talent family + advisor filter. Do not add `advisors` to `MARKETPLACE_LISTING_KINDS` or `FamilyId`. Today `LEGACY_CATEGORY` in `marketplaceFamilies.ts` has no `advisors` row — P0/P2/P3 share the obligation to map it; P3 must not invent a fifth family to do so.
4. Logged-out browse remains required (P0). Filters and badge work without auth.

### R8 — i18n, theme, accessibility

1. Badge label, Start/Grow/Exit chip labels, location filter label, and empty-state copy are catalog keys (P0: five locales, light and dark). No hardcoded English in the toolbar/card beyond existing talent patterns.
2. Badge and chips are operable by keyboard and exposed to assistive tech (chip = toggle button with pressed state; badge = status, not a button).
3. Do not rely on colour alone for unpaid-eligible.

### R9 — Non-goals (encoded)

1. **No new payout rail.** Unpaid stays price `0`. No settlement, credits, volunteer stipend, or “pro-bono payout”.
2. **No SCORE / SBA / government / nonprofit affiliation** labeling, badges, or partnership claims.
3. No new advisor onboarding fields (location and stage are P0 writes; P3 only displays and filters).
4. No map, geocoding product, distance search, or relocating advisors.
5. No change to who may set price `0` or stages; no moderation/verification of volunteer claims.
6. No analytics dashboards, SEO landing pages per stage, or net-new category routes.
7. No unpaid listing filter in P3.
8. Chat, Resources, and other P2 surfaces are out of P3 except shared listing/filter infrastructure already in flight.
