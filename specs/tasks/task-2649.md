# Product Requirements Document (PRD)

## Problem & Goal

### Problem
The `executions.submittedBy` column in the Postgres database is defined as `varchar(36)`, but certain dispatchers write strings longer than 36 characters, causing the container executor to fail with the error: `value too long for type character varying(36)`.

### Goal
Resolve the database write error by ensuring that the `executions.submittedBy` column can accommodate longer strings, and prevent similar issues in other related columns.

## Target Users / ICP Roles
- **Developers**: Users who dispatch runs and encounter the error.
- **Database Administrators**: Responsible for schema changes and ensuring database integrity.
- **QA Engineers**: Responsible for testing the fix and ensuring regression tests are in place.

## Scope

### In-Scope
- **Database Schema Changes**:
  - Increase the length of the `executions.submittedBy` column from `varchar(36)` to `varchar(64)` or `text`.
  - Review and adjust other columns (`cloud_agent_ref`, `agent_definition_version_id`, `segment_id`) if they are also affected.
- **Regression Testing**:
  - Implement a regression test to dispatch a run via `system:coordinator:producer:<role>` and assert that the execution row persists without errors.
- **Documentation**:
  - Update relevant documentation to reflect the schema changes and the reasons behind them.

### Out-of-Scope
- **Refactoring Dispatcher Logic**: Changing the logic that generates the `submittedBy` string is not part of this task.
- **Handling Other Data Types**: This task does not address issues with other data types or columns not related to the execution write path.
- **Performance Optimization**: While schema changes are being made, performance optimization is not the focus of this task.

## Functional Requirements

1. **Database Schema Update**:
   - Modify the `executions.submittedBy` column to `varchar(64)` or `text` to accommodate longer strings.
   - Ensure that the change does not affect existing data integrity and that all existing data is preserved.

2. **Validation of Other Columns**:
   - Review `cloud_agent_ref`, `agent_definition_version_id`, and `segment_id` to determine if they are also affected by similar issues.
   - Adjust the length of these columns if necessary.

3. **Regression Testing**:
   - Implement a test that dispatches a run using `system:coordinator:producer:<role>`.
   - Assert that the execution row is persisted without errors.
   - Ensure that the test covers both existing and new lengths of the `submittedBy` string.

4. **Documentation**:
   - Update the database schema documentation to reflect the changes made.
   - Include a note explaining the reason for the change and any potential impacts.

## Acceptance Criteria

- The `executions.submittedBy` column can accommodate strings up to 64 characters or is set to `text` without length restrictions.
- No data is lost or corrupted during the schema change.
- The regression test passes, demonstrating that dispatching a run with a longer `submittedBy` string does not cause the container executor to fail.
- Other affected columns, if any, have been appropriately adjusted.
- Documentation is updated to reflect the changes and includes a clear explanation of the reasons behind them.

## Out of Scope

- Changing the logic that generates the `submittedBy` string.
- Addressing issues with other data types or unrelated database columns.
- Performance optimization of the database or application.
- Handling any potential side effects of the schema change beyond ensuring data integrity and application functionality.

### R-1: Widen `executions.submitted_by` — DONE (migration 0368)

Migration `0368_widen_execution_submitted_by.sql` widens `executions.submitted_by` from `varchar(36)` to `varchar(128)`. The Drizzle schema in `api/src/infrastructure/database/schema/agents.ts` declares it as `varchar('submitted_by', { length: 128 })` with a JSDoc comment linking to `composeDispatcherLabel()` as the sole composer. A Postgres `varchar` widen is a metadata-only operation — no table rewrite, no lock beyond a brief `ACCESS EXCLUSIVE`.

**Status:** Complete. The migration exists, the schema and migration agree on 128, and the column comment documents the contract. No further widening is needed.

### R-2: Validate the lifecycle outbox column — PARITY CONFIRMED

`execution_lifecycle_outbox.submitted_by` mirrors `executions.submitted_by` — the outbox is populated by a database trigger in the same transaction as the executions INSERT, so the same overflow would fail the same way. The schema declares it as `varchar('submitted_by', { length: 128 })` — parity with the main table.

**Status:** No gap. Same length, same migration path.

### R-3: Composer that keeps labels within the column — DONE

`api/src/application/runtime/dispatcherLabel.ts` exports `composeDispatcherLabel(base, kind, detail?)` and the constant `MAX_SUBMITTED_BY_CHARS = 128`. It guarantees the output never exceeds 128 characters by sacrificing the base (general context) before the suffix (the specific dispatch identifier). Both call sites that compose labels — `laneRequirementGate.ts` (reviewer dispatch) and `laneEntryTrigger.ts` (producer dispatch) — import and use this composer. No call site builds a label by raw template anymore.

**Status:** Complete. Unit tests in `dispatcherLabel.test.ts` cover the exact overflow scenarios (architect, product-manager, engineering-manager role keys against a coordinator base; pathological long inputs; absent detail; blank base fallback).

### R-4: Validate sibling columns — NO GAPS FOUND

The ticket named three sibling columns on the execution write path:

| Column | Postgres type | Max useful length | Verdict |
|---|---|---|---|
| `cloud_agent_ref` | `varchar(64)` | `ide_agents.id` is `varchar(64)` — exact match | Safe |
| `agent_definition_version_id` | `uuid` (36 chars) | Fixed-length UUID | Safe |
| `segment_id` | `uuid` (36 chars) | Fixed-length UUID | Safe |

None of these carry composed/concatenated strings; none share the overflow vulnerability.

**Status:** No action required. No other `varchar(36)` columns were identified on the execution INSERT path.

### R-5: Regression test — GAP (for the Developer slot)

The PRD requests a regression test that dispatches a run via `system:coordinator:producer:<role>` (or `system:coordinator:lane-approver:<role>`) and asserts the execution row persists without a Postgres 22001 error. The existing unit tests (`dispatcherLabel.test.ts`) cover the composer in isolation, but no integration-level test exercises the full dispatch→INSERT path end-to-end.

The Developer should write one (or declare it out of scope with a reason — e.g. the container executor's dispatch path is not emulatable in the CI test harness). This is the only actionable gap the BA can identify.

### R-6: Schema parity between migration and Drizzle — TO BE CONFIRMED BY CI

The Drizzle schema declares `varchar(128)` and the migration alters the column to `varchar(128)`. When the CI pipeline runs `drizzle-kit push` or the schema-vs-migration drift check, it should report zero drift for this column. If it does not, the migration may not have been applied to the environment or may have a different ordering number.

**Status:** Deferred to CI. No code change is needed for the BA slot.

## Design

### D-1: Schema widening

Migration `0368_widen_execution_submitted_by.sql` widens `executions.submitted_by` from `varchar(36)` to `varchar(128)`. A Postgres `varchar` widen is a metadata-only operation — no table rewrite, no lock beyond a brief `ACCESS EXCLUSIVE`.

### D-2: Lifecycle outbox parity

Migration `0374_execution_lifecycle_outbox.sql` creates the outbox table with `submitted_by` directly as `varchar(128)` — parity with the main table is structural, not an afterthought.

### D-3: Composer contract

`api/src/application/runtime/dispatcherLabel.ts` exports `composeDispatcherLabel(base, kind, detail?)` with `MAX_SUBMITTED_BY_CHARS = 128`. The composer guarantees the output never exceeds 128 characters by sacrificing the base (general context) before the suffix (the specific dispatch identifier). The suffix is never truncated because it is the diagnostic payload.

### D-4: Call site migration

Both call sites that built labels by raw template have been migrated to use the composer:
- `laneRequirementGate.ts` (reviewer dispatch)
- `laneEntryTrigger.ts` (producer dispatch)

No call site builds a label by raw template anymore.

### D-5: Drift guard

The schema-type-drift guard (`.schema-type-drift-allowlist.txt`) is empty by design — any drift between the Drizzle schema and the migration is a CI failure. R-6 is therefore enforced automatically.

### D-6: Sibling columns safe

|---|---|---|
| `cloud_agent_ref` | `varchar(64)` | Safe — matches `ide_agents.id` |
| `agent_definition_version_id` | `uuid` | Safe — fixed length |
