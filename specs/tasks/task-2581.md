# Product Requirements Document: Visitor Chat on Public Advisor Profiles

**Status:** WIP  
**Owner:** Product Architecture  
**Constraint:** Reuse the existing chat primitive. Do not ship a new messenger product.

## Problem & Goal

Public advisor profiles convert poorly because a ready-to-talk visitor has no in-context way to start a conversation. Today they leave the page for a form, email, or calendar, and the advisor’s existing chat inbox is unused for top-of-funnel.

**Goal:** Let a visitor start a 1:1 conversation with the profile owner from the public advisor profile. The thread must be created, stored, rendered, notified, and continued through the existing chat primitive and advisor inbox. Success is a working public-profile entry point, not a new messaging surface.

## Target users / ICP roles

- **Visitor (prospect):** Unauthenticated or authenticated non-client browsing a public advisor profile and wanting a short, immediate conversation.
- **Advisor (profile owner):** Receives, replies to, and owns the thread in the existing inbox.
- **Authenticated user (existing account, not yet a client of this advisor):** Same entry point; identity is already known.
- **Practice admin (if the advisor belongs to a practice):** Visibility and routing only if the current chat model already supports it. Do not invent new admin messaging.

## Scope

In scope for this WIP:

- Chat entry on the public advisor profile only (web).
- One visitor ↔ one profile-owner thread, using existing conversation, message, presence, and notification models.
- Identity gate before the first outbound message (reuse existing auth/lead capture patterns).
- Routing of the new thread into the advisor’s existing inbox and reply flow.
- Visitor return path to the same thread (session, account, or magic-link already supported by chat).
- Empty, loading, offline, rate-limited, and advisor-unavailable states using existing chat UI patterns.
- Basic abuse controls already available to chat (rate limit, block, report) applied to this entry point.

## Functional requirements

1. **Entry point:** The public advisor profile shows a chat CTA when the profile owner is eligible to receive visitor chat. CTA copy and placement must not imply a separate messenger product.
2. **Eligibility:** Visitor chat is available only when the advisor’s account can already receive chat (active, not suspended, chat enabled). If not eligible, hide the CTA; do not show a dead composer.
3. **Composer:** Opening the CTA mounts the existing chat primitive (same message input, send, attachments policy, and thread chrome as in-product chat), scoped to this advisor. Do not introduce a second composer, inbox, or thread list for visitors.
4. **Identity before first send:**
   - Authenticated visitor: use the current user; do not re-prompt for name/email.
   - Unauthenticated visitor: collect the minimum identity the existing chat/lead pipeline already requires (typically name + email) and create or attach the user/lead record before the first message is persisted.
   - Do not allow fully anonymous persisted messages.
5. **Thread creation:** First successful send creates exactly one 1:1 conversation with the profile owner as the advisor participant, using the existing conversation type/flags for inbound visitor/prospect chat if one already exists; otherwise reuse the standard 1:1 advisor chat type.
6. **Idempotency:** Repeat visits from the same identified visitor to the same advisor resume the existing open thread. Do not spawn duplicate conversations for the same visitor–advisor pair.
7. **Advisor experience:** New visitor messages appear in the existing advisor inbox with enough context to see they originated from the public profile (existing metadata/source field; no new inbox tab). Replies use the current reply, read, and notification paths.
8. **Visitor experience after send:** Visitor stays in the same thread UI on the profile (or the existing chat shell if they are authenticated and already have in-product chat). Subsequent advisor replies are delivered through existing realtime/push/email notifications.
9. **Availability:** If the primitive already supports online/away/offline or office hours, surface that state on the profile CTA and in the thread header. If the advisor is unavailable, still allow leaving a message if the inbox can receive it; otherwise disable send and explain why with existing empty-state patterns.
10. **Permissions and privacy:** Visitors never see other clients’ threads, roster, or presence beyond this advisor. Advisors never expose internal notes or non-chat profile-admin tools through this surface.
11. **Abuse and safety:** Apply existing send rate limits, content limits, block, and report flows. Public-profile origin must not bypass those controls.
12. **Analytics (lightweight):** Emit existing funnel events for CTA view, composer open, identity complete, first message sent, and first advisor reply. Do not add a parallel analytics product.

## Acceptance criteria

- A visitor on an eligible public advisor profile can open chat and send a first message without leaving the profile, using the existing chat UI—not a new messenger.
- Unauthenticated visitors cannot persist a message until identity is captured; authenticated visitors skip that gate.
- The resulting thread is a single 1:1 conversation in the advisor’s existing inbox; the advisor can reply there and the visitor sees the reply in the same thread.
- A second session by the same identified visitor on the same profile resumes the same thread; no duplicate conversations.
- If the advisor cannot receive chat, the CTA is hidden and no composer is mounted.
- Existing rate limits, attachment rules, block/report, and notifications apply unchanged to these threads.
- No new standalone inbox, thread list, chat home, or messaging settings screen ships for visitors or advisors.
- Profile, auth, and chat failures fail closed with existing error/empty states; no uncaught composer that appears to send.

## Out of scope

- A new messenger, visitor inbox, multi-thread list, or chat home.
- Group chat, practice-wide inboxes, routing to a pool of advisors, bots, or AI copilots.
- Video, voice, screenshare, or in-chat booking/payments (unless already part of the primitive and required to send).
- Changing advisor-to-client chat behavior, migration of historical threads, or a new conversation data model.
- Native mobile profile chat unless the public profile already ships in those apps; this WIP is the public web profile.
- Marketing widgets, third-party chat vendors, or embedding chat on non-profile pages.
- Compliance/archival product changes beyond whatever the existing chat primitive already does.
- Unauthenticated, fully anonymous public chat.

### R-1 — Surface (public advisor profile only)

- The only in-scope entry is the **public web** advisor profile `/u/[username]` when that profile is in P0 advisor mode (same advisor-mode predicate as the Book CTA on this page; Architect binds to #2527).
- Do **not** add the CTA to marketplace listing cards, `/advisors`, ATS, meetings, marketing pages, embeds, or non-profile routes.
- Native mobile profile chat is out of scope unless `/u/[username]` already ships in those apps (it does not, per parent).
- No new route, slug, or chat-home URL for visitors.

### R-2 — Eligibility (when the CTA is shown)

Show the chat CTA when **all** of the following are true:

1. The profile is in advisor mode (R-1).
2. The viewer is **not** the profile owner (no chat-with-self).
3. The owner’s account can **already** receive the existing conversation primitive (active, not suspended; `startEmployerConversation({ freelancerUserId: person.id })` would be accepted for that user by current API rules).

Hide the CTA (do **not** mount a dead composer, disabled field, or “unavailable messenger”) when any of the above fail.

**Regression lock:** Non-advisor talent profiles keep today’s MessagesButton / `canHire` visibility. This ticket must not make Message appear for logged-out viewers on non-advisor talent profiles.

Do **not** invent a new “visitor chat enabled” advisor setting. If the account cannot receive chat, hide. If it can, show.

### R-3 — CTA copy and placement

- Copy and placement must **not** imply a separate messenger product. Prefer the existing MessagesButton visual language. Acceptable: “Message”, “Chat”. Forbidden: “Open Messenger”, “Start inbox”, “New messaging app”, third-party widget chrome.
- The Chat CTA is **distinct** from the Book CTA (#2532). Chat does not book, schedule, or take payment.
- On an eligible advisor profile the Chat CTA is **visible to unauthenticated visitors** (the visibility change vs today’s `canHire`).
- Owner self-view: no CTA (R-2).

### R-4 — Primitive (locked)

Opening the CTA **invokes** the existing chat primitive. It does **not** mount a second composer, inbox, or thread list on the public profile.

**Create / resume**

- Call `startEmployerConversation({ freelancerUserId })` with `freelancerUserId` = profile `person.id`.
- From this profile, pass **only** `freelancerUserId`. Do **not** pass `jobId`, `engagementId`, or `proposalId` (those are marketplace hire context). Do **not** seed `title` / `body` (do not auto-send, R-6).
- `auth: 'tenant'` is mandatory. Do not add a cookie-less or guest `POST /api/conversations`.

**Continue**

- After `{ id }` returns, the visitor continues in the **existing** inbox chrome (`MessagesPanel` / `/dashboard/messages?c=<id>` or the current equivalent that panel already uses).
- Advisor replies, read-state, presence-in-thread, attachments policy, and notifications are the current paths. Unchanged.

**Forbidden (fails review)**

- Embedding `MessagesPanel` (or a fork) on `/u/[username]` as a parallel composer.
- A visitor inbox, multi-thread list, chat home, or messaging settings screen.
- Brain-chat, meeting-chat, `linkTeamChat`, or `TEAM_CEREMONY_KINDS`.
- A new conversation type/enum, new inbox tab, or new realtime stack.
- Third-party chat vendors or marketing widgets.

Ada FR-3 (“mounts the existing chat primitive”) is satisfied by **invoking** MessagesButton / `startEmployerConversation` / existing inbox chrome — not by drawing a second thread UI on the profile.

### R-5 — Identity gate (tenant session, not name+email)

**Decision (this ticket, binding):** Unauthenticated visitors are gated by **existing auth** (`signInHref`), not by a name+email lead form. Name+email identity is **#2534 booking**, not chat. The conversation API is `auth: 'tenant'`; guest/anonymous persisted messages are forbidden (parent Decision 4; Ada “do not allow fully anonymous persisted messages” still holds).

| Viewer | On CTA click | Persist message? |
|---|---|---|
| Authenticated, has tenant, not owner | Existing MessagesButton flow: `startEmployerConversation`; no name/email re-prompt | Yes, as current user |
| Authenticated, **no** tenant | Same as logged-out: do not POST conversations | No |
| Logged out | `signInHref` with `next` = the current `/u/[username]` URL (query/hash preserved if already present) | No, until tenant session exists |
| Profile owner | CTA hidden (R-2) | n/a |

- After sign-in / tenant pick, land **back on that advisor profile** (`next`).
- Then enter the primitive: if Hire/Book already resumes an intended action after `next` return, Chat **may** reuse that same pattern for a single `startEmployerConversation` call. If no such pattern exists, a **second click** on the CTA after return is acceptable. Do **not** invent a new post-login action bus, magic-link, or guest cookie for this ticket.
- **Do not auto-send** a message after login (parent R-3).
- **Do not** create guest threads, anonymous `users` rows, synthetic `guest-…@guest.invalid` chat actors, or #2543 guest-project conversations to “have a tenant.”
- **Do not** collect name+email on the Chat CTA (that form belongs to advisory booking).
- Magic-link return is in scope **only** if the existing messaging product already supports it for 1:1 threads. This ticket must not add a chat magic-link.

### R-6 — Thread creation and idempotency

- First successful `startEmployerConversation` for this visitor–advisor pair creates **exactly one** 1:1 conversation: visitor on the employer/tenant side, profile owner as `freelancerUserId`.
- Repeat visits by the **same identified user** to the **same** advisor **resume** that open thread. The API already “opens (or reuses)”. Do not spawn duplicates.
- Use the existing conversation type/flags. If an inbound visitor/prospect source flag already exists on conversations, Architect **may** set it. Otherwise reuse the standard 1:1 employer–freelancer type. **No new inbox tab** (Ada FR-7).
- Idempotency key is the existing one: same tenant-authenticated visitor + same `freelancerUserId`. Do not invent a second key (email, fingerprint, guest token).

### R-7 — Advisor experience

- New visitor messages appear in the **existing** advisor inbox with the current reply, read, and notification paths.
- Public-profile origin may be recorded **only** on an existing metadata/source field. If none exists, origin stays implicit (an employer-side user messaging this talent). Do **not** add an inbox tab, filter, or “Prospects” folder.
- Practice-admin visibility and routing **only** if the current chat model already supports it. Do not invent practice-wide inboxes or pool routing (Ada target-users constraint; parent out of scope).

### R-8 — Visitor experience after send

- The visitor is in the **existing chat shell** (R-4 Continue), not a thread UI embedded on `/u/[username]`.
- Subsequent advisor replies are delivered through existing realtime / push / email notifications. Do not add a visitor-only notification product.
- Return path to the same thread = signed-in session (and the existing inbox deep link). Account-based resume is R-6. No new magic-link.

Ada FR-8’s “or the existing chat shell if they are authenticated” is the **only** allowed continuation. The profile stays an entry point.

### R-9 — Availability (reuse only; do not invent presence)

- If MessagesButton / conversation UI **already** surfaces online / away / offline or office hours, reuse that on the CTA and/or thread header.
- If it does **not**, this ticket **must not** invent presence, office-hours, or “advisor unavailable” product chrome.
- If the owner cannot receive chat, **hide the CTA** (R-2). That is the unavailable state.
- If the inbox can receive while the advisor is away, leaving a message is allowed **because that is the existing send path** — do not add a separate “leave a message” product.
- Do not bind Chat to #2533 free/busy slots.

### R-10 — Permissions and privacy

- Visitors never see other clients’ threads, roster, presence beyond this advisor, or any conversation list on the public profile.
- The profile must not list, preview, or count other people’s threads.
- Advisors never expose internal notes, profile-admin tools, or non-chat settings through this surface.
- Fail closed: a conversation GET/POST that is not this 1:1 pair must not leak another thread.

### R-11 — Abuse and safety

- Existing send rate limits, content limits, attachment rules, block, and report flows apply **unchanged**.
- Public-profile origin must **not** bypass those controls (no separate unauthenticated send path that skips them).
- Do not add new abuse controls in this slice; do not skip existing ones.

### R-12 — Analytics (lightweight, existing pipeline only)

- Do **not** add a parallel analytics product or a new funnel service.
- **SHOULD:** if the profile / messaging stack already emits CTA or conversion events, emit the same class for: CTA view, CTA click, identity complete (sign-in return with tenant), first message sent, first advisor reply — via existing helpers and naming.
- **MUST NOT** block chat on missing analytics. If no helper exists, Architect **may** add events to the current pipeline; shipping chat without them does not fail this ticket.
- Do not require a new dashboard for these events.

### R-13 — Failure closed

- Profile, auth, and chat failures fail closed with **existing** error / empty / toast patterns. No uncaught composer that appears to send.
- `startEmployerConversation` 401 / 403 → sign-in (`signInHref`) or the existing API-error path. Do not mount a fake composer.
- Network / offline / rate-limited: existing `MessagesPanel` empty and error states.
- Advisor ineligible: CTA hidden (R-2), no composer.

### R-14 — What this ticket does not build

Re-stated so implementers do not “complete” #2581 by shipping a sibling or a messenger:

- A new messenger, visitor inbox, multi-thread list, chat home, or messaging settings.
- In-profile parallel composer on `/u/[username]`.
- Guest / anonymous persisted messages; name+email as chat identity (#2534).
- Auto-send after login.
- Group chat, practice-wide inboxes, routing to a pool, bots, AI copilots.
- Video, voice, screenshare, in-chat booking or payments.
- Changing advisor-to-client chat behavior, migrating historical threads, or a new conversation data model.
- Marketing widgets, third-party chat vendors, embedding chat on non-profile pages.
- Compliance / archival product changes beyond the existing primitive.
- Guest project / claim link as the chat tenant (#2543).
- Brain-chat, meeting-chat, or `kind=advisory` team-ceremony chat.
- `/advisors` destination; `advisor` as `MARKETPLACE_LISTING_KINDS`.
- Native mobile profile chat.
- Visitor discovery (#2580).

### R-15 — Anti-patterns (fail the review)

A change fails this ticket if it:

1. Ships a second composer, inbox, thread list, or chat home.
2. Embeds a thread UI on `/u/[username]` instead of invoking the existing inbox.
3. Persists a message without a tenant-authenticated user.
4. Collects name+email (or a lead form) as the Chat identity gate.
5. Auto-sends a message after `signInHref` return.
6. Passes `jobId` / `engagementId` / `proposalId` from the public profile, or seeds `body`.
7. Creates duplicate conversations for the same visitor–advisor pair.
8. Adds an inbox tab / “Prospects” folder.
9. Uses #2543 guest project, Brain-chat, or meeting-chat as the transport.
10. Shows the CTA on a non-advisor profile or to the owner viewing self.
11. Changes non-advisor talent `canHire` Message visibility.
12. Punches a hole in conversation auth (cookie-less `POST /api/conversations`).
