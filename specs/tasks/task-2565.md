# PRD: R4 — vsce package (install is operator)

## Problem & Goal

The extension must be shippable as a standard VS Code VSIX so an operator can install it in a target environment. Today there is no agreed, repeatable packaging path: `vsce package` is not treated as a first-class deliverable, artifacts are informal, and install is mixed into packaging work.

**Goal:** Produce a valid, installable `.vsix` via `vsce package` as the R4 deliverable. Installation is an operator action, not part of this work.

## Target users / ICP roles

- **Extension maintainer / build owner** — runs packaging, owns `package.json` / vsce metadata, and hands off the VSIX.
- **Operator** — installs the VSIX into VS Code / Cursor (or equivalent) on the target machine. Not a consumer of this task’s automation.
- **Downstream agents** — consume this PRD as the shared contract for packaging only; they do not implement install.

## Scope

In scope:

- Make the extension packable with the official `vsce` CLI (`vsce package`).
- Ensure required extension manifest fields, files, and ignore rules so the VSIX is complete and free of secrets/dev-only junk.
- Produce a single `.vsix` artifact (named/versioned from the extension manifest) that an operator can install with `code --install-extension` / UI “Install from VSIX”.
- Document the exact packaging command, working directory, prerequisites (`vsce`, Node), and where the artifact lands.
- Fail packaging clearly if the manifest or bundled files are invalid.

Out of scope is listed below; do not expand R4 into publish, CI release, or install automation.

## Functional requirements

1. **Packaging command:** From the extension root, `vsce package` succeeds with exit code 0 and writes a `.vsix`.
2. **Manifest:** `package.json` has valid `name`, `publisher`, `version`, `engines.vscode`, `main` (if applicable), `activationEvents` / contribution points as required by the extension, and any vsce-required fields so packaging does not warn-as-error on missing identity.
3. **File set:** The VSIX includes runtime code, assets, and declared contributions; it excludes `node_modules` that vsce should not pack (or includes a production-only set if the extension requires it), tests, source maps if not needed, `.git`, secrets, `.env*`, and local operator notes.
4. **Ignore rules:** `.vscodeignore` (and npm ignore behavior) is explicit so the packed payload is minimal and does not leak credentials or workspace-only files.
5. **Versioning:** The VSIX filename and internal version match `package.json` `version`. No manual rename as the source of truth.
6. **Prerequisites:** Packaging assumes Node and `vsce` available locally; R4 does not require a CI pipeline, marketplace PAT, or `vsce publish`.
7. **Handoff:** The artifact path and operator install expectation are stated in-repo (short README or packaging note): operator installs; this task does not run install.
8. **Idempotence:** Re-running `vsce package` on the same tree produces a functionally equivalent VSIX (same version unless the manifest version changed).

## Acceptance criteria

- [ ] `vsce package` run from the extension root exits 0.
- [ ] A `.vsix` exists at the documented output path, with version matching `package.json`.
- [ ] The VSIX can be inspected (`vsce ls` or unzip) and contains the extension entrypoint and required assets; it does not contain secrets, `.git`, or obvious dev-only trees called out in `.vscodeignore`.
- [ ] Manifest identity (`publisher`, `name`, `version`, `engines`) is valid for vsce; packaging does not fail on missing required fields.
- [ ] A maintainer following the documented command can reproduce the artifact without unpublished steps.
- [ ] No script, CI job, or agent in R4 installs the VSIX, launches VS Code to sideload, or calls `code --install-extension` / `cursor --install-extension` as a required step.
- [ ] Operator install remains a manual, post-R4 action; R4 is complete when the VSIX is produced and handed off.

## Out of scope

- Operator (or automated) install, sideload, enable, or reload of the extension.
- `vsce publish`, Open VSX / Marketplace listing, PATs, or signing beyond what `vsce package` already does.
- CI/CD release pipelines, artifact registries, or auto-bumping versions.
- Runtime feature work, bugfixes, or UX changes except those required for a valid pack (manifest/ignore/entrypoint).
- Cross-editor packaging for non-VS Code targets except insofar as the same VSIX is what the operator installs.
- Uninstall, upgrade, or rollback procedures.
