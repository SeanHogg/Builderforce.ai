# PRD: R4 — vsce package (install is operator)

## Problem & Goal

The extension must be shippable as a standard VS Code VSIX so an operator can install it in a target environment. Today there is no agreed, repeatable packaging path: `vsce package` is not treated as a first-class deliverable, artifacts are informal, and install is mixed into packaging work.

**Goal:** Produce a valid, installable `.vsix` via `vsce package` as the R4 deliverable. Installation is an operator action, not part of this work.

## Target users / ICP roles

- **Extension maintainer / build owner** — runs packaging, owns `package.json` / vsce metadata, and hands off the VSIX.
- **Operator** — installs the VSIX into VS Code / Cursor (or equivalent) on the target machine. Not a consumer of this task’s automation.
- **Downstream agents** — consume this PRD as the shared contract for packaging only; they do not implement install.

## Scope

In scope:

- Make the extension packable with the official `vsce` CLI (`vsce package`).
- Ensure required extension manifest fields, files, and ignore rules so the VSIX is complete and free of secrets/dev-only junk.
- Produce a single `.vsix` artifact (named/versioned from the extension manifest) that an operator can install with `code --install-extension` / UI “Install from VSIX”.
- Document the exact packaging command, working directory, prerequisites (`vsce`, Node), and where the artifact lands.
- Fail packaging clearly if the manifest or bundled files are invalid.

Out of scope is listed below; do not expand R4 into publish, CI release, or install automation.

## Functional requirements

1. **Packaging command:** From `clients/vscode` (extension root, **not** repo root), `pnpm run package` succeeds with exit code 0 and writes one `.vsix`. That script is `node vsce-platform.mjs package`, which invokes `@vscode/vsce` as `vsce package --no-dependencies --target <os>-<arch>` (host-derived: `win32` | `darwin` | `linux` | `alpine` × `x64` | `arm64`). Bare `vsce package` / `npx @vscode/vsce package` is **not** the ship path (skips `--no-dependencies`, `--target`, and the overwrite guard).
2. **Manifest:** `clients/vscode/package.json` keeps valid `name` (`builderforce-ai`), `publisher` (`builderforce`), `version` (read at pack time; tree is `2026.9.79`), `engines.vscode` (`^1.95.0`), `main` (`./out/extension.js`), `activationEvents` (`["onStartupFinished"]`), `icon` (`media/icon.png`), `l10n` (`./l10n`). R4 does not invent a new identity and does not bump `version`.
3. **File set:** The VSIX includes runtime code produced by `vscode:prepublish` (`out/extension.js` and needed `out/` runtime — not `out/harness.cjs`), webview production build, `media/icon.png` and contributed `media/`, `l10n/`, and `package.json` / package.nls. It excludes `src/`, `webview/` source, tests/harness, source maps, `.git`, secrets, `.env*`, operator notes, and `node_modules/**` (`--no-dependencies`). Linked workspace packages are bundled by esbuild, not packed as `node_modules`.
4. **Ignore rules:** `clients/vscode/.vscodeignore` is the payload contract. Keep current exclusions; add entries only if inspection finds leakage. Do not pack by deleting `.vscodeignore`.
5. **Versioning:** VSIX filename and internal version match `package.json` `"version"` at pack time. Default output `clients/vscode/{name}-{version}.vsix` (example: `clients/vscode/builderforce-ai-2026.9.79.vsix`). No manual rename. Do **not** freeze 2026.9.72 or 2026.9.75. The `.vsix` is a build artifact — do not commit it.
6. **Prerequisites:** Node + pnpm workspace install; `@vscode/vsce` is a **devDependency** (`^3.2.0`). No global vsce, no Marketplace PAT, no CI pipeline, no `vsce publish`.
7. **Handoff:** Short **Packaging (VSIX)** note under `clients/vscode/README.md` (Development) states cwd, `pnpm run package`, prerequisites, artifact path, overwrite guard, and that **operator installs** after R4. `PUBLISHING.md` stays out of R4.
8. **Overwrite / idempotence:** If the output path already exists, `vsce-platform.mjs` throws unless `--allow-overwrite`. A second run without overwrite **must** fail — that is correct. Do not bump `version` on this ticket to get a green pack. Same tree + same version + overwrite allowed (or prior artifact removed) produces a functionally equivalent VSIX.

## Acceptance criteria

- [ ] `pnpm run package` from `clients/vscode` exits 0 (first pack of this `package.json` version, or a deliberate re-cut via `--allow-overwrite` / prior artifact removed).
- [ ] A `.vsix` exists at `clients/vscode/{name}-{version}.vsix` with version matching `package.json` (currently `2026.9.79` → `builderforce-ai-2026.9.79.vsix`). The binary is **not** committed.
- [ ] The VSIX can be inspected (`pnpm exec vsce ls` from `clients/vscode`, or unzip) and contains `out/extension.js`, `media/icon.png`, `l10n/`, webview build, and `package.json` with matching `version`; it does not contain `src/`, `harness/`, `.git`, `.env*`, or `node_modules/`.
- [ ] Manifest identity (`publisher`, `name`, `version`, `engines`) is valid for vsce; packaging does not fail on missing required fields. Installed id (operator, later) is `builderforce.builderforce-ai@<version>`.
- [ ] A maintainer following the README **Packaging (VSIX)** note can reproduce the artifact without unpublished steps. Bare `vsce package` is documented as **not** the ship path.
- [ ] No script, CI job, or agent in R4 installs the VSIX, launches VS Code to sideload, or calls `code --install-extension` / `cursor --install-extension` as a required step.
- [ ] Operator install remains a manual, post-R4 action; R4 is complete when the VSIX is produced, inspects clean, and the handoff note is in-repo. If the developer container cannot run `vsce` / write the `.vsix`, that is a **blocker to report**, not a license to substitute a conceptual VSIX or to complete R4 by documenting install instead.

## Out of scope

- Operator (or automated) install, sideload, enable, or reload of the extension.
- `vsce publish`, Open VSX / Marketplace listing, PATs, or signing beyond what `vsce package` already does.
- CI/CD release pipelines, artifact registries, or auto-bumping versions.
- Runtime feature work, bugfixes, or UX changes except those required for a valid pack (manifest/ignore/entrypoint).
- Cross-editor packaging for non-VS Code targets except insofar as the same VSIX is what the operator installs.
- Uninstall, upgrade, or rollback procedures.

### REQ-1 — Packaging command (FR-1, AC-1, AC-5)

**Given** Node and workspace deps are installed, **when** a maintainer packages from the extension root, **then** the command exits 0 and writes one `.vsix`.

| Item | Value |
|---|---|
| Working directory | `clients/vscode` (extension root; **not** repo root) |
| Required command | `pnpm run package` |
| What that runs | `node vsce-platform.mjs package` (`scripts.package` in `clients/vscode/package.json`) |
| Underlying CLI | `@vscode/vsce` (`devDependencies`: `^3.2.0`), resolved as `@vscode/vsce/vsce` |
| vsce invocation | `vsce package --no-dependencies --target <os>-<arch>` plus optional forwarded args |
| Target | Host-derived in `vsce-platform.mjs`: `win32` \| `darwin` \| `linux` \| `alpine` × `x64` \| `arm64` (musl Linux → `alpine`) |
| Prepublish | vsce runs `vscode:prepublish`: `node esbuild.mjs --production && tsc -p ./ && pnpm run build:webview` |

**Do not** treat a bare global `vsce package` (or `npx @vscode/vsce package` without the wrapper) as the ship path. Bare vsce skips `--no-dependencies`, skips `--target`, and **silently overwrites** an existing `.vsix` — the failure mode `vsce-platform.mjs` exists to prevent (see REQ-6). Equivalent: `node vsce-platform.mjs package` from `clients/vscode`.

Packaging **fails clearly** (non-zero exit, error on stderr) when the manifest is invalid, prepublish fails, or the overwrite guard trips. R4 does not add a CI job.

### REQ-3 — Packed file set (FR-3, AC-3)

The VSIX **must** contain runtime payload produced by `vscode:prepublish` and declared contributions, including:

- `out/extension.js` (and other `out/` runtime the entrypoint needs — not `out/harness.cjs`)
- webview production build output
- `media/icon.png` and other contributed `media/` assets
- `l10n/`
- `package.json` / package.nls as vsce includes them

The VSIX **must not** contain:

- `src/`, `webview/` source, `esbuild.mjs`, `vsce-platform.mjs`, `tsconfig.json`
- `harness/`, `test-integration/`, `out-integration/`, `vitest.config.ts`, `out/harness.cjs`
- `**/*.ts`, `**/*.map`
- `.git`, `.github/`, `.vscode/`, `.vscode-test/`
- secrets, `.env*`, operator notes, local credentials
- `node_modules/**` (wrapper passes `--no-dependencies`; `.vscodeignore` also excludes it)

Linked workspace packages (`@seanhogg/builderforce-brain-embedded`, `@seanhogg/builderforce-brain-ui`, etc.) are **bundled by esbuild**, not packed as `node_modules`. R4 therefore **depends on R3** having rebuilt `brain-embedded` dist; R4 does not rebuild other packages unless prepublish cannot complete.

### REQ-6 — Once-per-version / overwrite (FR-8)

Raw `vsce package` overwrites silently. The repo **rejects** that: if the output path already exists, `vsce-platform.mjs` throws unless `--allow-overwrite`.

**R4 policy:**

1. First pack of this version → run `pnpm run package`; expect exit 0.
2. Artifact already exists for the **same** version → do **not** bump `version` on this ticket. Either delete the existing file (only if it is known to be a stale/partial cut of the same intended build) or pass `--allow-overwrite` (`pnpm run package -- --allow-overwrite`) and record that it was a deliberate re-cut.
3. Do **not** invent a new version to get a green pack. Version bumps for other packages are **#2564**. A VSIX version bump is out of R4 unless an architect/operator explicitly unblocks it.

FR-8 “idempotent re-run produces a functionally equivalent VSIX” is satisfied by: same manifest version + same tree + overwrite allowed or prior artifact removed. A second run **without** overwrite **must** fail; that failure is correct, not a packaging bug.
