# PRD: `maySend` send gate

## Problem & Goal

Sending is a privileged, irreversible action. Drafting must remain available in more contexts than sending. Today those two capabilities can be conflated, which risks unconfirmed, incomplete, anonymous, or agent-authored content leaving the system.

**Goal:** Compute a single boolean `maySend` that is true **only** when every send precondition holds. Otherwise the surface stays draft-only. Anonymous sessions and cloud agents never send.

`maySend` is the conjunction:

`persistence = server` **AND** `humanConfirmed` **AND** `checklist.ready` **AND** `sendReadiness.ready` **AND** `NOT agentDraftOnly`

If any operand is missing, false, or unknown, `maySend` is false.

## Target users / ICP roles

- Authenticated human operators who confirm and send after server-persisted drafts
- Cloud / remote agents that may draft but must not send
- Anonymous or unauthenticated visitors (draft-only; no send path)

Downstream agents implementing UI, state, and persistence must treat this gate as shared contract, not a per-surface heuristic.

## Scope

- Definition and evaluation of `maySend`
- Mapping of session, actor, and readiness state into the operands above
- Draft-only behavior when `maySend` is false (anonymous, cloud agent, incomplete checklist, unconfirmed, local/non-server persistence, `agentDraftOnly`)
- Fail-closed evaluation (unknown / unset → not sendable)

## Functional requirements

1. **`maySend` evaluation**  
   Expose one derived flag, `maySend`. It is true iff all of the following are true at evaluation time:
   - `persistence = server` (server-backed identity and storage; not local-only, ephemeral, or client-only)
   - `humanConfirmed` is true (an authenticated human has explicitly confirmed this send)
   - `checklist.ready` is true
   - `sendReadiness.ready` is true
   - `agentDraftOnly` is false

2. **Fail closed**  
   Missing, stale, or indeterminate operands yield `maySend = false`. Do not infer confirmation, checklist completion, or server persistence.

3. **Anonymous stays draft-only**  
   Anonymous / unauthenticated sessions never satisfy the send conjunction. `maySend` is always false. Drafting may continue; send controls are unavailable.

4. **Cloud agents stay draft-only**  
   Cloud (remote) agents never send. Treat them as draft-only regardless of checklist or readiness bits. They must not set `humanConfirmed`. Prefer `agentDraftOnly = true` for these actors so the conjunction cannot pass.

5. **Human confirmation is not agent confirmation**  
   Only an authenticated human confirmation sets `humanConfirmed`. Agent-authored or auto-approved drafts do not.

6. **Draft path remains open**  
   When `maySend` is false, create/edit/save draft remains allowed subject to existing draft rules. Send, schedule-send, and equivalent dispatch APIs must refuse.

7. **Re-evaluation**  
   Recompute `maySend` whenever persistence, auth/actor, confirmation, checklist, send readiness, or `agentDraftOnly` changes. Do not cache a true value across those transitions.

8. **Server enforcement**  
   UI hiding is not sufficient. Send endpoints must reject when `maySend` would be false.

## Acceptance criteria

- Given `persistence = server`, `humanConfirmed`, `checklist.ready`, `sendReadiness.ready`, and `agentDraftOnly = false` for an authenticated human, `maySend` is true and send is allowed.
- Given any one of those conditions false or unknown, `maySend` is false and send is rejected.
- Anonymous session: `maySend` is false; user can draft and cannot send.
- Cloud agent session: `maySend` is false; agent can draft and cannot send; `humanConfirmed` remains unset by the agent.
- `persistence != server` (local / ephemeral / client-only): `maySend` is false even if other flags are true.
- `agentDraftOnly = true`: `maySend` is false even if persistence, checklist, and readiness are true.
- Send API called while `maySend` is false returns a refusal; no message is dispatched.
- After a blocking flag flips from true to false, `maySend` becomes false without a refresh workaround.
- No send control is presented as enabled when `maySend` is false.

## Out of scope

- Checklist item content, ordering, or how `checklist.ready` is produced
- Internals of `sendReadiness` beyond honoring `.ready`
- Draft storage format, sync, and conflict resolution
- Notification copy, send analytics, and post-send lifecycle
- Changing auth, billing, or persistence product lines except as inputs to this gate
- Allowlists, impersonation, or “send on behalf of” that bypass human confirmation
- Relaxing draft-only for anonymous users or cloud agents

### R-1 — Five-way conjunction (identical to C1 `#2629` R-6)

`maySend === true` **only if all** of the following hold **at evaluation time**. Otherwise `maySend === false`. There is no sixth conjunct.

| Conjunct | Required value | Missing / unknown |
| --- | --- | --- |
| `persistence` | exactly `"server"` | not `"server"` → false |
| `humanConfirmed` | exactly `true` | omit / false / non-boolean → false |
| `checklist.ready` | exactly `true` | omit / false / non-boolean → false |
| `sendReadiness.ready` | exactly `true` | omit / false / non-boolean → false |
| `agentDraftOnly` | exactly `false` | omit / true / non-boolean → false |

In particular:

- `checklist.ready` alone is not send.
- `sendReadiness.ready` alone is not send.
- Connect success is not send (`#2635`).
- Chat assent is not `humanConfirmed` (`#2638`).
- Empty / missing ICP is **not** a conjunct (`#2632`).
- ROI / opens / clicks / `/api/roi/rollup` are **not** conjuncts (`#2634`).
- RUN vs LIST intent is **not** a conjunct (`#2630`). Classifying RUN MUST NOT set `maySend`.

TypeScript shape (names may be refined by Architect; semantics must not):

```ts
maySend =
  persistence === "server" &&
  humanConfirmed === true &&
  checklist.ready === true &&
  sendReadiness.ready === true &&
  agentDraftOnly === false
```

Use strict equality. Do not coerce `"true"`, `1`, or `"server "` (trailing space) into a pass.

### R-2 — Fail closed (unknown / stale / missing → not sendable)

If **any** operand is missing, stale, indeterminate, non-boolean where a boolean is required, or not exactly the required value, `maySend === false`.

Do **not** infer:

- confirmation from checklist completion, copy complete, chat “yes”, connect OAuth, agent tool success, or auto-approve
- checklist completion from `sendReadiness.ready` (or the reverse)
- server persistence from a signed-in cookie on a `'local'` board, from guest identity, or from a missing persistence field
- `agentDraftOnly === false` from a missing field (missing means **not proven human** → not sendable)

Fail-closed is **asymmetric**: a missing `agentDraftOnly` does **not** mean “not an agent” (that would allow send). Missing → `maySend === false`. The adapter SHOULD pass `agentDraftOnly: true` for cloud / remote agents and `agentDraftOnly: false` for signed-in human operators; until it does, evaluation stays false.

Stale snapshots are not a permit. A previously computed `true` that is reused after any operand change is a defect (R-9).

### R-3 — Persistence operand (canvas `'local' | 'server'`)

`persistence === "server"` means a **signed-in** operator session whose campaign objects persist on the **server**.

| Observed canvas / session state | Persistence operand | `maySend` |
| --- | --- | --- |
| Signed-in tenant board, `persistence === 'server'` | `"server"` | other four conjuncts still required |
| Canvas `'local'` | not `"server"` (treat as `"anonymous"`) | **false** |
| Guest / anonymous / unauthenticated | not `"server"` | **false** |
| Missing / undefined / empty / unknown string | not `"server"` | **false** |
| Ephemeral / client-only / not-yet-saved | not `"server"` | **false** |

`persistence !== "server"` yields `maySend === false` **even if** `humanConfirmed`, `checklist.ready`, `sendReadiness.ready`, and `agentDraftOnly === false` are all true. Tests MUST include that fixture.

Adapter mapping (extends existing `frontend/src/lib/canvasMarketing.ts`; does not duplicate the formula): `'local'` / guest / missing → not `"server"`. Only signed-in **server** persistence can ever yield `maySend === true`.

### R-4 — Anonymous / unauthenticated sessions stay draft-only

Anonymous and unauthenticated sessions **never** satisfy the send conjunction.

1. `maySend` is **always false** for these sessions (persistence is not `"server"`; do not also require a second ad-hoc “isAnonymous” conjunct — persistence mapping is sufficient).
2. Drafting MAY continue (create / edit / save draft subject to existing guest-safe draft rules and C0 `canvas_add_object` only).
3. Send, schedule-send, publish, ads launch, and equivalent dispatch APIs MUST refuse (R-10).
4. Send / schedule / publish / ads-launch **controls** are unavailable or disabled. Sign-in prompt is C3 `#2638` R-9 (this ticket does not own that chrome).
5. After sign-in: **do not auto-send**. Re-evaluate all five conjuncts on the authenticated server session. `humanConfirmed` does **not** carry over from the anonymous session (it was never true there).

C1 MUST NOT introduce `canvas_add_inbox`, send, schedule, publish, or spend tools for anonymous boards.

### R-5 — Cloud / remote agents stay draft-only

Cloud (remote / autonomous) agents **never** send.

1. Adapter MUST pass `agentDraftOnly: true` for these actors. Prefer this so the conjunction **cannot** pass even if other bits are wrongly true.
2. `maySend === false` when `agentDraftOnly === true`, **even if** persistence is `"server"`, checklist is ready, sendReadiness is ready, and a `humanConfirmed` bit is present.
3. Cloud agents MUST NOT set `humanConfirmed` (C3 is the only writer of `true`; agents are not an authenticated human confirmation).
4. Agent-authored or auto-approved drafts do **not** count as human confirmation (R-6).
5. Cloud agents MAY draft, edit, preview, and **propose** send. They MUST NOT call send / schedule / publish / ads-launch tools as the send path.
6. Fixture that MUST yield `maySend === false`: `agentDraftOnly: true` + complete checklist + copy + server persistence + `sendReadiness.ready` + `humanConfirmed: true` (poisoned confirm bit still does not send).

Existing `cloudAgentToolset.ts` allowlist (no `campaign.send`) is **defense in depth**, not a substitute for this conjunct.

### R-6 — `humanConfirmed` is read-only here; C3 is the only writer of `true`

1. This ticket **reads** `humanConfirmed: boolean`. It does **not** render the confirm UI (`#2638`).
2. Default / omitted / false / non-boolean → not confirmed → `maySend === false`.
3. `humanConfirmed === true` **only** when an **authenticated human** has completed the explicit C3 confirm control for **this** run / action / payload (C3 R-6 binds it to `(campaignOrRunId, actionKind, payloadFingerprint)`). This ticket does not own that tuple; it honors the boolean C3 writes.
4. The following MUST NOT set `humanConfirmed = true`: connect OAuth/success (`#2635`), mailbox / social / ads connect, chat messages (“yes”, “send it”, “looks good”, “go live”), `checklist.ready`, `sendReadiness.ready`, copy complete, agent tool success, persistence flipping to server, sign-in, list intent, ROI becoming numeric.
5. Human confirmation is **not** agent confirmation. Only an authenticated human confirm sets the flag.

### R-7 — `checklist.ready` and `sendReadiness.ready` are distinct conjuncts

This ticket does **not** produce either flag.

| Operand | Producer | What it means here |
| --- | --- | --- |
| `checklist.ready` | `#2631` / C1 `#2629` R-3 | Journey items: brand (voice **and** doNotSay), consentAudience, senderAccount for the **chosen channel**, offer, copy. **Not** suppression / unsubscribe / transport. |
| `sendReadiness.ready` | existing Growth / Canvas `sendReadiness()` (passthrough) | Suppression, unsubscribe, transport, audience/consent/forbidden-claim blockers already in `marketing.ts`. C1 **accepts** `{ ready: boolean }` as opaque. |

Rules:

1. Do **not** fold Growth blockers into the journey checklist, or journey items into `sendReadiness`.
2. `checklist.ready === true` with `sendReadiness.ready === false` is valid (draftable, **not** sendable) → `maySend === false`.
3. `sendReadiness.ready === true` with `checklist.ready === false` is valid → `maySend === false`.
4. If `sendReadiness` is omitted, treat `sendReadiness.ready` as not true for `maySend` (R-2). Do not fail the checklist (checklist is `#2631`).
5. Dual-counting audience consent (checklist.consentAudience **and** sendReadiness blockers) is allowed; they remain **separate** conjuncts. Both must be true for `maySend`.
6. `forbiddenClaim` stays a Growth send-gate, orthogonal to checklist.brand (kit completeness).

### R-8 — Draft path remains open when `maySend` is false

When `maySend === false`:

- **Allowed** (subject to existing draft rules): create, edit, save draft, preview, list, connect (connect still never sends — `#2635`), propose send.
- **Forbidden:** send, schedule-send, publish, ads launch, and any equivalent dispatch that would message a live audience or spend.

Draft-only is the default. Send is privileged and irreversible. This ticket MUST NOT close the draft path as a side effect of a closed send gate.

Anonymous and cloud-agent draft remain allowed (R-4, R-5).

### R-9 — Re-evaluation; do not cache a `true`

Recompute `maySend` whenever **any** of these change: `persistence`, auth/actor, `humanConfirmed`, `checklist.ready`, `sendReadiness.ready`, `agentDraftOnly`.

1. Do **not** cache a `true` across those transitions.
2. After a blocking flag flips from true to false, `maySend` becomes false **without** a refresh workaround.
3. C3 `#2638` R-12 rechecks `maySend` on confirm submit. A stale pre-submit `true` MUST NOT send. This ticket’s evaluator must be a pure function of **current** operands so that recheck is possible.
4. UI that shows a send control as enabled MUST re-read current `maySend` (and C3 MUST re-read `confirmEnabled`) at paint and at submit.

### R-10 — Server enforcement (UI hide is not sufficient)

Send endpoints and tool handlers MUST reject when `maySend` **would be** false. No message is dispatched. No ad spend occurs.

Covered actions (existing seams only; Architect binds exact symbols; do not invent a new buyer):

- Growth `campaign.send` (send now)
- Growth `campaign.schedule` (or the existing schedule seam on `draft → schedule → send`)
- Canvas / social **publish** (`social_campaign.publish` or existing Canvas publish seam)
- **Ads launch** (existing Canvas/Growth ads-launch seam **if it exists**)

Non-negotiable:

1. UI disable / hiding is **not** sufficient.
2. Rejection is fail-closed: structured error, **no** partial send, **no** spend, campaign remains in its pre-attempt state.
3. This gate composes with C3: C3 additionally requires a valid, unconsumed, payload-bound confirm before those same handlers run. Either gate failing is enough to refuse.
4. Chat assent, connect callbacks, and agent tools hitting these handlers while `maySend` is false MUST receive the same refusal.

This ticket specifies **when** to refuse (`maySend` would be false). C3 specifies **how** confirm is collected. Do not fork a second send pipeline.

### R-11 — `confirmEnabled` (C3) vs `maySend` (this ticket)

| Flag | Owner | Formula (conceptual) | When it is true | What it permits |
| --- | --- | --- | --- | --- |
| `confirmEnabled` | C3 `#2638`, **C3-local** | signed-in human ∧ not anonymous ∧ not cloud agent ∧ `persistence === "server"` ∧ `agentDraftOnly === false` ∧ `checklist.ready` ∧ `sendReadiness.ready` ∧ C3 required fields for **this** action ∧ payload current | **Before** confirm | Confirm control may be shown/enabled |
| `maySend` | C1 / this ticket | those C1 conjuncts **plus** `humanConfirmed === true` | **After** a valid human confirm, on current state | Send / schedule / publish / ads launch may execute |

- Do **not** put `confirmEnabled` or `mayOfferConfirm` on the C1 public contract (C3 `#2638` R-1 / P0).
- Send / schedule / publish / ads-launch **controls** MUST be disabled when `maySend === false`.
- The C3 **confirm** control is **not** a send control. It MAY be enabled while `maySend === false` solely because `humanConfirmed` is not yet true. That is required for confirm to be reachable.
- After confirm commit, execution still requires a fresh `maySend === true` (C3 R-12 step 4–6).

### R-12 — Non-conjuncts (must not enter the formula)

The following MUST NOT appear as `maySend` operands, as implicit ANDs, or as reasons to infer a conjunct:

| Topic | Owner | Rule |
| --- | --- | --- |
| Empty / missing ICP | `#2632` | Never a gate. Fixture with empty ICP still evaluates `maySend` from the five conjuncts only. |
| Connect success | `#2635` | Never send, never spend, never set `humanConfirmed`. MAY satisfy checklist `senderAccount` (which may then contribute to `checklist.ready`); that is still not send. |
| Chat assent | `#2638` | “yes” / “send it” / “go live” is not confirm and not `maySend`. |
| Campaign ROI | `#2634` | `unknown` vs numeric is irrelevant to send. |
| RUN vs LIST intent | `#2630` | RUN starts the journey; it does not send. |
| Persona completeness / guest identity | forbidden | Guest identity is handled via persistence mapping (R-3), not a sixth flag. |
| Opens / clicks / sent counts / `/api/roi/rollup` | `#2634` | Ignored. |
