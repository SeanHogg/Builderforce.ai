# PRD: `maySend` send gate

## Problem & Goal

Sending is a privileged, irreversible action. Drafting must remain available in more contexts than sending. Today those two capabilities can be conflated, which risks unconfirmed, incomplete, anonymous, or agent-authored content leaving the system.

**Goal:** Compute a single boolean `maySend` that is true **only** when every send precondition holds. Otherwise the surface stays draft-only. Anonymous sessions and cloud agents never send.

`maySend` is the conjunction:

`persistence = server` **AND** `humanConfirmed` **AND** `checklist.ready` **AND** `sendReadiness.ready` **AND** `NOT agentDraftOnly`

If any operand is missing, false, or unknown, `maySend` is false.

## Target users / ICP roles

- Authenticated human operators who confirm and send after server-persisted drafts
- Cloud / remote agents that may draft but must not send
- Anonymous or unauthenticated visitors (draft-only; no send path)

Downstream agents implementing UI, state, and persistence must treat this gate as shared contract, not a per-surface heuristic.

## Scope

- Definition and evaluation of `maySend`
- Mapping of session, actor, and readiness state into the operands above
- Draft-only behavior when `maySend` is false (anonymous, cloud agent, incomplete checklist, unconfirmed, local/non-server persistence, `agentDraftOnly`)
- Fail-closed evaluation (unknown / unset → not sendable)

## Functional requirements

1. **`maySend` evaluation**  
   Expose one derived flag, `maySend`. It is true iff all of the following are true at evaluation time:
   - `persistence = server` (server-backed identity and storage; not local-only, ephemeral, or client-only)
   - `humanConfirmed` is true (an authenticated human has explicitly confirmed this send)
   - `checklist.ready` is true
   - `sendReadiness.ready` is true
   - `agentDraftOnly` is false

2. **Fail closed**  
   Missing, stale, or indeterminate operands yield `maySend = false`. Do not infer confirmation, checklist completion, or server persistence.

3. **Anonymous stays draft-only**  
   Anonymous / unauthenticated sessions never satisfy the send conjunction. `maySend` is always false. Drafting may continue; send controls are unavailable.

4. **Cloud agents stay draft-only**  
   Cloud (remote) agents never send. Treat them as draft-only regardless of checklist or readiness bits. They must not set `humanConfirmed`. Prefer `agentDraftOnly = true` for these actors so the conjunction cannot pass.

5. **Human confirmation is not agent confirmation**  
   Only an authenticated human confirmation sets `humanConfirmed`. Agent-authored or auto-approved drafts do not.

6. **Draft path remains open**  
   When `maySend` is false, create/edit/save draft remains allowed subject to existing draft rules. Send, schedule-send, and equivalent dispatch APIs must refuse.

7. **Re-evaluation**  
   Recompute `maySend` whenever persistence, auth/actor, confirmation, checklist, send readiness, or `agentDraftOnly` changes. Do not cache a true value across those transitions.

8. **Server enforcement**  
   UI hiding is not sufficient. Send endpoints must reject when `maySend` would be false.

## Acceptance criteria

- Given `persistence = server`, `humanConfirmed`, `checklist.ready`, `sendReadiness.ready`, and `agentDraftOnly = false` for an authenticated human, `maySend` is true and send is allowed.
- Given any one of those conditions false or unknown, `maySend` is false and send is rejected.
- Anonymous session: `maySend` is false; user can draft and cannot send.
- Cloud agent session: `maySend` is false; agent can draft and cannot send; `humanConfirmed` remains unset by the agent.
- `persistence != server` (local / ephemeral / client-only): `maySend` is false even if other flags are true.
- `agentDraftOnly = true`: `maySend` is false even if persistence, checklist, and readiness are true.
- Send API called while `maySend` is false returns a refusal; no message is dispatched.
- After a blocking flag flips from true to false, `maySend` becomes false without a refresh workaround.
- No send control is presented as enabled when `maySend` is false.

## Out of scope

- Checklist item content, ordering, or how `checklist.ready` is produced
- Internals of `sendReadiness` beyond honoring `.ready`
- Draft storage format, sync, and conflict resolution
- Notification copy, send analytics, and post-send lifecycle
- Changing auth, billing, or persistence product lines except as inputs to this gate
- Allowlists, impersonation, or “send on behalf of” that bypass human confirmation
- Relaxing draft-only for anonymous users or cloud agents
