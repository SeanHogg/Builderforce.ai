# PRD: Render `%` in `sessionsTree.ts` chat item descriptions

## Problem & Goal

Linked-ticket progress is missing from Sessions-tree conversation **descriptions**. Users scanning **Activity Bar → BuilderForce → Sessions** cannot see remaining work beside the title without opening the chat. Parent #2436 requires chat rows to show “· 85%” (or similar) next to title/time; this ticket is that description surface (`clients/vscode/src/sessionsTree.ts` `TreeItem.description` for `node.row.source.kind === "chat"`).

Separately, `%` in a composed description must not be treated as a l10n/printf format token. A lone `%` can strip, double, encode, truncate, or throw; callers must not pre-escape (`%%`, `%25`).

**Goal:** When a conversation has linked tickets and a finite `ticketProgressPct`, put literal `N%` in `item.description` as the first content segment after any attention prefix, joined with existing project / relative time / participant text using ` · `. Every intended percent sign (progress and `%` already in other segments) is U+0025 in the assigned string and in the tree UI. Empty, missing, and `%`-free descriptions stay as today when the progress gate fails. No change to `label`, tooltip, icons, commands, or session identity. Sibling #2440 (in-panel switcher) and #2437/#2438 (API/type) are out of scope.

## Target users / ICP roles

- End users viewing chat/session history in the sessions tree (percent-complete, URLs, encoded paths, titles containing `%`).
- Downstream agents implementing and verifying the `sessionsTree.ts` change.

## Scope

In scope: the chat item `description` path in `sessionsTree.ts` (assignment, any format/l10n/`printf`-style handling, and the string that the tree view renders).

Out of scope items are listed below.

## Functional requirements

1. A chat item `description` that contains `%` must render those characters literally in the sessions tree.
2. A single `%` (not part of a known format pair) must not drop the rest of the string or throw.
3. Existing format tokens used elsewhere in the tree (if any) must keep working; only chat item `description` is changed to treat `%` as literal text.
4. Doubled or encoded forms (`%%`, `%25`) must not be required of callers and must not show up as extra characters in the UI unless they were in the source description.
5. Empty, missing, and `%`-free descriptions must behave as they do today.
6. No change to chat item `label`, `tooltip`, icons, commands, or session identity.

## Acceptance criteria

- A description of `Progress 50%` shows as `Progress 50%`.
- A description of `100% done` and of a lone `%` shows those characters unchanged.
- A description with several `%` signs (e.g. `a%b%c`) shows every `%`.
- Descriptions without `%` match current rendering.
- No runtime error when `description` includes `%`.
- Change is confined to `sessionsTree.ts` chat item `description` handling (or a helper used only for that string).

## Out of scope

- Labels, tooltips, markdown bodies, and other views.
- Localization/message catalogs outside this description string.
- URL encoding/decoding of session data.
- New description fields, copy, or tree UX.
- Performance, accessibility, or theming work beyond correct `%` display.

## Requirements

This section is the backlog contract for ticket **#2439** (child of #2436). It is grounded in the current VSIX Sessions tree: `clients/vscode/src/sessionsTree.ts` `getTreeItem` for `node.row.source.kind === "chat"`, plus `BfBrainChat` in `clients/vscode/src/bfApi.ts`. Sibling #2440 owns the in-panel switcher (`packages/brain-ui` `chatSwitcherLabel`); this ticket does not.

### User stories

1. As a user scanning **Activity Bar → BuilderForce → Sessions**, I want each conversation row to show linked-ticket progress as `N%` in the faded description beside the title/time, so I can see remaining work without opening the chat.
2. As a user whose project name, title, or progress text contains `%` (e.g. `50%`, `100% done`, a lone `%`, `a%b%c`), I want every `%` to appear as a percent sign — not stripped, not turned into `%%` / `%25`, and not truncating the rest of the row.
3. As a user of chats with **no** linked tickets (or an older API that omits progress), I want the description to look as it does today (time, optional project, optional participant initials, optional attention prefix).

### Current behaviour (baseline)

Chat rows in `getTreeItem` already:

- Set **`item.label`** via `conversationTreeLabel(chat)` (`N% · title` when `ticketCount > 0` and `ticketProgressPct` is a finite number). That label path is **out of scope** for this ticket (see Non-goals).
- Build **`item.description`** as a plain concatenated string, then assign `item.description = description`. Segments today:
  1. Optional **attention prefix** (`attentionDescriptionPrefix`) when the chat is running / awaiting input.
  2. **Project label** when the Sessions list is unfiltered (`!this.filtered`), via `projectLabel(...)`.
  3. **Relative time** (`relativeTime(chat.updatedAt)` → `now` / `Nm` / `Nh` / `Nd`).
  4. Optional **participant initials** (`BD · AH` plus ` +N` when more than three).
- Do **not** pass the composed description through `vscode.l10n.t` as a format template (individual catalog strings elsewhere use `{0}` placeholders).
- Leave description empty when every segment is empty.

`BfBrainChat` already carries `ticketCount?: number` and `ticketProgressPct?: number | null`. Ticket #2438’s `progressPct` rename is **not** consumed here; this ticket reads the fields that exist on the type today.

### Functional requirements

**R1 — When to show progress in description.**  
For a conversation tree item, include a progress segment if and only if:

- `(chat.ticketCount ?? 0) > 0`, and
- `chat.ticketProgressPct` is a finite number (`!= null` and `Number.isFinite`).

Otherwise do not add a progress segment. Missing fields on older servers behave as “no progress” (same degrade as `conversationTreeLabel` / `chatSwitcherLabel`).

**R2 — Format of the progress segment.**  
`N%` where `N = Math.max(0, Math.min(100, Math.round(ticketProgressPct)))`. No space between the digits and `%`. `0%` is valid and **must** show when the gate in R1 passes. Examples: `0%`, `67%`, `100%`.

**R3 — Where it sits in the description.**  
The progress segment is the first **content** segment of `item.description` after any attention prefix (live-state still wins the leftmost slot). Join with the same ` · ` separator the row already uses.

Target shape (omit empty parts):

`[attentionPrefix][N%][ · project][ · time][ · participantBadges]`

Unfiltered example: `85% · Acme · 2m · BD AH`.  
Filtered (project implied by header): `85% · 2m`.  
Attention + progress: `{prefix}85% · 2m`.  
No progress (R1 fails): description unchanged from today.

This is what parent #2436 means by “`· 85%` (or similar) next to title/time”: VS Code draws `TreeItem.description` immediately to the right of the label.

**R4 — Literal `%` in the assigned description.**  
After composition, every intended percent sign is the character U+0025 in the string assigned to `item.description`, and that is what the tree view shows.

- Do **not** pass the composed description (or any substring that already contains user/API `%`) as the **message template** to `vscode.l10n.t`. VS Code l10n/printf treats `%` / `%s` as format tokens: a lone `%` can drop the remainder of the string or throw.
- If a catalog string is used **only** for the progress fragment, placeholders must be `{0}`-style. A catalog that needs a percent sign may use the l10n escape (`%%`) internally; the **resolved** string shown in the UI must contain exactly one `%` per intended percent.
- Callers (`GET /api/brain/chats`, `BfBrainChat`, tests) must **not** pre-double (`%%`) or URL-encode (`%25`) the value. Those forms must not appear in the UI unless they were already in a source segment (e.g. a project named `50%%`).
- Implementation may confine escaping to a helper used **only** for this description assignment. Escaping is an implementation detail; the user-visible result is a single `%` per source `%`.

**R5 — `%` already in other description segments.**  
Project labels (or any future segment) that contain `%` must still render every `%`. Fixing progress must not introduce a formatter that swallows `%` in the rest of the description.

**R6 — Empty / missing / `%`-free.**  
Chats with no progress segment and no other parts still get `item.description` as today (`""` or time-only, etc.). `%`-free descriptions are byte-for-byte unchanged except for the added progress segment when R1 applies.

**R7 — Stability of other chat-item fields.**  
This ticket must not change chat item `label` (including `conversationTreeLabel`), `tooltip`, `iconPath`, `command`, `contextValue`, or `id` (`sessionsLibraryRowId`). Canvas rows and group rows are untouched.

**R8 — Facet duplication.**  
A chat that appears under both Recent and Running (or another facet) is two tree items with different ids. Both must get the same description composition.

**R9 — No extra I/O.**  
Progress is read from the `BfBrainChat` already returned by `listBrainChats`. No extra HTTP call, no client-side ticket aggregation.

### Data contract

| Field | Source | Use |
| --- | --- | --- |
| `ticketCount` | `BfBrainChat` / `GET /api/brain/chats` (#2437) | Gate (R1). Treat missing as 0. |
| `ticketProgressPct` | same | Value (R2). Missing / null / non-finite → omit segment. |
| `progressPct` | proposed name on #2438 | **Do not require.** If #2438 later aliases the field, keep reading `ticketProgressPct` unless Design unifies the name. |

### Non-goals (this ticket)

- `conversationTreeLabel` / `item.label` (already `N% · title` to mirror `chatSwitcherLabel`). **Duplication risk:** after R3, a gated chat may show `85%` on both label and description. Architect decides whether to drop the label prefix; this ticket does not change the label.
- brain-ui switcher / dropdown (#2440).
- API batching (#2437) and the `BfBrainChat` type ticket (#2438).
- Tooltips, markdown bodies, canvas descriptions, group labels, `package.nls*.json` except a fragment key used solely for R4.
- URL encoding of session ids, new description fields, tree UX, performance, accessibility, or theming beyond correct `%` display.

### Acceptance criteria (testable)

1. `ticketCount = 6`, `ticketProgressPct = 67` → description contains visible `67%` (not `67`, `67%%`, or `67%25`), joined with existing time/project/participant text via ` · `.
2. `ticketProgressPct = 50` → `50%`; `100` → `100%`; `0` with `ticketCount ≥ 1` → `0%`.
3. Several percents in the composed string (progress plus a project name containing `%`, or `a%b%c` if that is a source segment) all show.
4. A lone `%` as a source segment does not throw and does not drop the rest of the description.
5. `ticketCount = 0` or non-finite / missing `ticketProgressPct` → description matches current composition (no new `N%` segment).
6. `%`-free descriptions match current rendering aside from the added segment when R1 applies.
7. Canvas row descriptions and chat labels/tooltips/commands/ids are unchanged.
8. Change is confined to chat-item `description` handling in `sessionsTree.ts` (or a helper used only for that string).

### Open item for Design (Architect)

Whether `conversationTreeLabel` should stop prefixing `N% ·` on the **label** so progress lives only in **description** (parent wording: next to title/time). Requirements freeze label behaviour for #2439; Design may move that prefix in or out of scope.
