# PRD: Wire refresh on ticket health changes

## Problem & Goal

**Problem.** In epic #2436, “ticket health” is the chat’s **linked-ticket progress rollup** (`ticketProgressPct` on `GET /api/brain/chats`, header ring via `aggregateTicketHealth`) — not SLA risk, sentiment, inactivity, or a support-queue score. Those products do not exist in seanhogg/builderforce.ai.

That % is painted from the last chat-list payload. It goes stale when a linked ticket’s lane/`progressPct` changes, when tickets are linked or unlinked, or when another session mutates the same work. Two concrete gaps on main today:

1. `SessionsTreeProvider` keeps a 5s `rowCache`. `refresh()` drops it, but nothing calls `refresh()` on ticket-health change (only project change / create / rename / delete / invite / sign-in).
2. Chat-list invalidation that keys only `id|updatedAt` misses a health-only update that does not bump `chat.updatedAt`. `ChatTicketsPanel.onChanged` fires for roster/merge/invite/questions, not consistently for **link/unlink** or ticket-progress mutations.

Users keep working from a chat that still reads `40%` after the linked work is done (or the reverse) until they reload the window.

**Goal.** When linked-ticket health changes, automatically refresh every bound **chat-list** surface that already shows (or will show, via siblings) that % — VSIX Sessions TreeView rows, the brain-ui chat switcher, and the open `ChatTicketsPanel` rings — with no window reload, no extra clicks, and without disrupting composer draft, cursor, scroll, or an open drawer.

## Functional requirements

1. **Detect.** A health change is: linked-ticket `status` / `progressPct` / `done` / `total` change (cancelled/canceled drop out of the rollup); link or unlink (`ticketCount` and/or `ticketProgressPct`); or `ChatTicketsPanel.refreshSignal` after MCP/tool work-item mutation. No new backend event type.
2. **Invalidation key.** The chat-list “did anything change?” signature MUST include `ticketProgressPct` (and `progressPct` if present) and `ticketCount`, not only `id|updatedAt`.
3. **Sessions tree.** On invalidation call `SessionsTreeProvider.refresh()` (drop `rowCache`, fire `onDidChangeTreeData`). Do not paint from a still-hot 5s cache.
4. **Chat switcher.** Refetch or patch the in-panel chat list so `chatSwitcherLabel` sees the new `%`. Do not remount the Brain panel.
5. **Open panel.** Bump `refreshSignal` (or equivalent) so rings reload. Fire `onChanged` after **link and unlink** as well as roster/merge, so the host refreshes the **list**.
6. **Local vs remote.** Local: refresh immediately after the mutation succeeds. Remote: existing chat-list poll/`refresh`/`chats.changed` (today on the order of ~12s). Do not add WebSockets.
7. **Non-destructive.** Do not clear composer draft, cursor, scroll, open drawer, focused chat, or remount the webview.
8. **Idempotency.** Last-write-wins by response order. Same `%` must not flicker a tree rebuild.
9. **Failure.** Keep last good `%` on fetch failure; retry via existing poll; never blank the row. Reconnect resyncs on the next successful list.
10. **Performance.** Must not block typing or composer send. Batch bursts in one tick. No full-catalog refetch when a single in-view chat’s health changes — `listBrainChats` / patch that chat is enough.
11. **Accessibility.** Update the existing TreeItem / `<select>` option / ring text. No live region that announces every poll.
12. **No new visualization.** Placement and copy are #2439/#2442 and #2440. This ticket only makes those strings **update**.

## Acceptance criteria

- After a linked ticket on chat C reaches a done-class status, the Sessions row and chat-switcher option for C show the new integer `%` without a window reload. Local mutation: immediately after success. Remote: within the existing chat-list poll/refresh window.
- Link or unlink on the open chat updates `ticketCount` / `ticketProgressPct` on the Sessions row and switcher. 0→N starts showing `%` (per sibling omit-when-null rules); N→0 drops the `%`.
- Open `ChatTicketsPanel` header ring matches `aggregateTicketHealth` of the reloaded tickets; composer draft, cursor, scroll, and open drawer survive.
- Sessions tree does not serve a stale `rowCache` after health invalidation.
- A `listChats` payload whose only delta is `ticketProgressPct` still triggers the refresh path.
- Failed refetch leaves last good `%`; the row is not blanked.
- Duplicate invalidations with the same `%` do not flicker.
- Automated tests cover: health-field change → list invalidation; `updatedAt`-unchanged progress change still invalidates; `SessionsTreeProvider.refresh()` drops cache; link/unlink notifies the host; open-panel refresh is non-destructive; failed fetch keeps last good; cancelled tickets stay excluded from the rollup (do not regress `aggregateTicketHealth` tests).

## Requirements

_Owned by the business-analyst. Source of truth for architect Design and developer Implementation Notes. Paint/API/DTO are sibling tickets; this child is invalidation + refetch only._

### R-0 Term: “ticket health”

In epic #2436, **ticket health** is the chat’s **linked-ticket progress rollup**:

- Server: `ChatTicketService.rollupChatTicketHealth` / `attachChatTicketSummaries` → `ticketProgressPct` on `GET /api/brain/chats` (and `progressPct` once #2437 lands). Integer 0–100. Cancelled/canceled tickets are excluded (all-cancelled list → 100%; empty list → 0% / omit `%` per sibling paint rules).
- Open-chat header ring: `aggregateTicketHealth` over `TicketLinkVM` (`pct`, same cancelled rule). Keep in lockstep with the server rollup — do not invent a third formula on this ticket.
- **Not** SLA clocks, sentiment, inactivity, assignment gaps, or support-queue health. Those are not in this repo.

### R-1 User stories

- **US-1** As a developer with Sessions open, when a linked ticket on any listed chat changes lane or `progressPct`, I see the new `%` on that row without reloading VS Code.
- **US-2** As a developer with the Brain panel open, when I link/unlink a ticket or an agent run completes linked work, the switcher label and panel rings update in place; composer draft, cursor, scroll, and open drawer stay put.
- **US-3** As a developer with two sessions on the same tenant, a remote health change appears in this session within the existing chat-list poll/refresh window.

### R-2 Detect (no new bus)

Treat as a health change:

1. Linked ticket `status` / `progressPct` / `done` / `total` change (including cancelled dropping out of the denominator).
2. Link or unlink (`ticketCount` and/or `ticketProgressPct`).
3. Host bump of `ChatTicketsPanel.refreshSignal` after MCP/tool work-item mutation.

Do **not** add a dedicated “health-change” event type or a new pub/sub product. Reuse `GET /api/brain/chats` (already recomputes summaries) plus existing host↔webview `chats.changed` / `refresh`.

### R-3 Invalidation key

Whatever signature decides “the chat list changed” (`chatsSig` or equivalent) **must include** `ticketProgressPct` (and `progressPct` if present) and `ticketCount`, not only `id|updatedAt`. A health-only payload that does not bump `updatedAt` must still invalidate.

### R-4 Sessions TreeView

On health invalidation call `SessionsTreeProvider.refresh()` — it already drops `rowCache` (TTL 5_000) and fires `onDidChangeTreeData`. Do not paint from a still-valid cache. Do not refetch the agent pool unless `refresh()` already does. Row identity stays `sessionsLibraryRowId`; only the `%` string changes. **Do not** re-specify `%` placement here (#2439 / #2442: `TreeItem.description` `{relativeTime} · {n}%`, title title-only; stop the current `{n}% · title` prefix in `conversationTreeLabel` — that paint is not this ticket, but refresh must update whichever string is live).

### R-5 Chat switcher

On health invalidation, refetch or patch the in-panel `chatList` so `chatSwitcherLabel({ title, id, ticketCount, ticketProgressPct })` sees the new values for the open chat and other listed chats. Prefer patching affected chat object(s). Do not remount the Brain webview.

### R-6 Open `ChatTicketsPanel`

- If the open chat’s linked tickets changed, bump `refreshSignal` so `load()` re-runs (`listTickets` / agents / members / questions).
- Fire `onChanged` after **link** and **unlink** (today it fires for invite/remove/merge/questions; the link form only `load()`s). Host must treat `onChanged` as “refetch chat list now”, not wait for the poll.
- Header ring continues to use `aggregateTicketHealth` on the reloaded tickets.

### R-7 Local vs remote

- **Local** (this webview: panel link/unlink, MCP/tool ticket move): refresh immediately after the mutation succeeds.
- **Remote** (other window, other user, automation): refresh on the next successful `listChats` / existing poll / `refresh` / `chats.changed`. Do not add WebSockets.

### R-8 Non-destructive

Health refresh must not: clear composer draft, move cursor, reset transcript scroll, close an open panel drawer, change the focused chat, or remount the webview.

### R-9 Idempotency

Last-write-wins by response order (and `updatedAt` + health fields). An older list must not overwrite a newer `%`. Identical `%` must not flicker a tree rebuild.

### R-10 Failure

If follow-up `listChats` / `listTickets` fails: keep last good `%` and rings; retry via existing poll/backoff; never blank the row. After host reconnect / token refresh, the next successful list resyncs in-view chats.

### R-11 Performance

Must not block typing or composer send. Batch bursts in the same tick. No full-catalog refetch when a single in-view chat’s health changes — `listBrainChats` and/or patch that chat. Agent-pool fetch stays “once per refresh when needed”.

### R-12 Accessibility

Update existing TreeItem label/description, native `<select>` option text, and health-ring text. Do not add a live region that announces every poll.

### R-13 Protocol

Reuse existing message types (`chats.changed`, host `refresh`, `refreshSignal`). Any new payload field is additive. Do not add marketplace/advisor kinds. Do not dump `specs/tasks/*.md` as the implementation.

### R-14 Dependencies

- Data source: `ticketProgressPct` already on main `listBrainChats`; `progressPct` from #2437; DTO #2438. Refresh applies to whichever field the list already returns.
- Paint: #2439 / #2442 (tree), #2440 (switcher). This ticket updates those strings; it does not change format.
- Not #2608 (context-window meter).

### R-15 Test contract (for QA / developer)

1. Health-field-only `listChats` delta (`updatedAt` unchanged) → Sessions + switcher invalidate.
2. `SessionsTreeProvider.refresh()` drops `rowCache`.
3. Link and unlink call `onChanged` and the host refetches the chat list.
4. Open-panel `refreshSignal` reloads rings without clearing a stubbed composer draft.
5. Failed refetch keeps last good `%`.
6. Duplicate same-`%` events do not flicker.
7. Cancelled exclusion: do not regress `aggregateTicketHealth` tests (`packages/brain-ui/src/chatTickets/aggregateTicketHealth.ts`).

### R-16 Explicit non-goals

Support-queue SLA dashboards, health-rule admin, email/Slack push, historical timelines, new transport, new `%` visualization, context-window `%`, changing the rollup formula.
