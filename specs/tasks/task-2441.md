# PRD: Wire refresh on ticket health changes

## Problem & Goal

**Problem.** In epic #2436, “ticket health” is the chat’s **linked-ticket progress rollup** (`ticketProgressPct` on `GET /api/brain/chats`, header ring via `aggregateTicketHealth`) — not SLA risk, sentiment, inactivity, or a support-queue score. Those products do not exist in seanhogg/builderforce.ai.

That % is painted from the last chat-list payload. It goes stale when a linked ticket’s lane/`progressPct` changes, when tickets are linked or unlinked, or when another session mutates the same work. Two concrete gaps on main today:

1. `SessionsTreeProvider` keeps a 5s `rowCache`. `refresh()` drops it, but nothing calls `refresh()` on ticket-health change (only project change / create / rename / delete / invite / sign-in).
2. Chat-list invalidation that keys only `id|updatedAt` misses a health-only update that does not bump `chat.updatedAt`. `ChatTicketsPanel.onChanged` fires for roster/merge/invite/questions, not consistently for **link/unlink** or ticket-progress mutations.

Users keep working from a chat that still reads `40%` after the linked work is done (or the reverse) until they reload the window.

**Goal.** When linked-ticket health changes, automatically refresh every bound **chat-list** surface that already shows (or will show, via siblings) that % — VSIX Sessions TreeView rows, the brain-ui chat switcher, and the open `ChatTicketsPanel` rings — with no window reload, no extra clicks, and without disrupting composer draft, cursor, scroll, or an open drawer.

## Scope

In-product ticket surfaces that already render health: list/queue, board/kanban, ticket detail header and sidebar, related-ticket widgets, health filters and counts, and any real-time or polling channel those views already use.

Covers health changes from: SLA clocks, customer replies, agent replies, status/priority/assignee updates, health-rule evaluation, bulk actions, and other users or services mutating the same ticket.

Client must subscribe to health-change events (or equivalent invalidation) and refresh only the affected ticket rows/cards/badges and derived aggregates.

## Functional requirements

1. **Detect health changes** for a ticket as soon as the backend commits a new health value or health-derived reason (including no-op writes that still recompute health).
2. **Publish a health-change event** (ticket id, previous health, new health, reason codes, timestamp) on the existing realtime/invalidation bus. If no bus exists for this entity, reuse the ticket-update channel and include a dedicated health payload.
3. **Subscribe on every mounted ticket surface** that displays health. Unmount must unsubscribe.
4. **Targeted refresh:** update the changed ticket’s health badge, color, tooltip/reason, sort/group position, and any per-ticket health metadata. Do not refetch the entire catalog unless the change also affects the active filter, sort, or grouping.
5. **Aggregate refresh:** recompute visible counts, column headers, filter chips, and dashboard tiles that depend on health for the current view (e.g. “At risk: 12”).
6. **Filter / board consistency:** if the new health no longer matches the current filter or swimlane, remove or relocate the ticket in that view after refresh. If it newly matches, insert it in the correct sort position.
7. **Detail pane:** if the open ticket’s health changes, refresh header badge and health panel in place. Do not reset scroll, composer draft, or unsaved field edits.
8. **Multi-tab / multi-user:** a health change originating from another session, user, or automation must refresh this session the same way as a local change.
9. **Idempotency:** duplicate or out-of-order events must not flicker or regress to older health. Last-write-wins by server timestamp / version.
10. **Failure behavior:** if the event arrives but the follow-up fetch fails, keep the last good health, retry with backoff, and do not blank the row. A reconnect after dropped subscription must resync health for tickets currently in view.
11. **Performance:** refresh path must not block typing or composer send. Batch bursts of health events in the same tick. Avoid full-list re-render when a single ticket changes.
12. **Accessibility:** health text/badge updates must be exposed to assistive tech (live region or equivalent) without announcing every unrelated field.

## Acceptance criteria

- Changing a ticket’s health in one session updates badge, color, and reason on list, board, and open detail in other sessions without reload, within the existing realtime SLA for ticket updates.
- Local mutations that cause health recompute (reply, status, assignee, priority) show the new health on the same view after the mutation succeeds, without a manual refresh.
- Tickets that fall out of the active health filter or swimlane leave that view; tickets that enter appear in the correct sort order.
- Visible health counts and filter chips match the tickets on screen after the refresh.
- An in-progress reply draft, cursor position, and unsaved edits survive a health refresh on the open ticket.
- Duplicate events and older versions do not overwrite newer health.
- After a dropped connection, reconnect restores correct health for in-view tickets without a full page reload.
- No full catalog refetch for a single-ticket health change when the ticket remains in the current result set.
- Automated tests cover: event → row update, filter eviction/insertion, aggregate recount, open-ticket non-destructive update, reconnect resync, and out-of-order event ignore.

## Out of scope

- Changing how health is calculated or adding new health rules/reasons
- New health visualization, colors, or copy (wire existing badges only)
- Email, Slack, or mobile push notifications for health changes
- Historical health timelines, analytics, or reporting exports
- Rewriting the realtime transport or introducing a new pub/sub product
- Offline/queued mutation of health itself
- Bulk “refresh all tickets” control or user-facing debug inspector
- Non-ticket entities (customers, orgs, SLAs as standalone objects) unless they are only inputs to ticket health
- Performance work unrelated to this refresh path
