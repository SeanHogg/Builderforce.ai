## Design

## Design

### Architecture context (why this is not just a `git rm`)

`commit 0267ffd` on `builderforce/task-2554` was a **+2/−0 addition**: a 2-line write_file probe at `Builderforce.ai/frontend/src/domains/canvas/domain/canvasChange.ts` (`// probe … export {}`). It did **not** overwrite the live module at `frontend/src/domains/canvas/domain/canvasChange.ts` (138 lines, intact on `main`, exports `ProposedCanvasChange`, `canvasChangesCanAutoApply`, `CONNECTED_CANVAS_ACTIONS`, `canInvokeCreationObjectAction`).

Critically, `frontend/tsconfig.json` `include` is `**/*.ts` rooted at `frontend/` — a nested probe at `Builderforce.ai/frontend/...` sits **outside** the TypeScript compilation root. A `tsc --noEmit` or `next build` would **not** pick it up. CI would stay green while the foreign path ships in the tree. This is exactly why BR-4 mandates path-level verification (`git show …:Builderforce.ai/…`) rather than trusting a green build.

### Execution plan (operator-only — no code change from the bound container)

The container that serves this run can read `main` but cannot switch branches, execute shell commands, or push. The work is a **pure git remainder** for an operator with SSH/PAT write access to `SeanHogg/Builderforce.ai`.

#### Step 1 — Verify starting state (safety check)

```bash
git fetch origin
git checkout builderforce/task-2554
git log --oneline -5
# Confirm 0267ffd is in the ancestry
git show 0267ffd --stat
```

#### Step 2 — Preferred path (BR-2)

```bash
git revert --no-edit 0267ffd360e524dbd6ae8a93d1e71df8202d4dee
```

Because `0267ffd` only added one file and later commits on `task-2554` (`8ececde`, `b006b5d`) are PRD dumps that do not touch the nested probe, this revert is expected to apply cleanly. The `--no-edit` flag uses the default revert message, which names the reverted commit — satisfying BR-6's reference requirement.

#### Step 3 — Fallback (BR-3, only if revert conflicts)

```bash
git rm -f -- Builderforce.ai/frontend/src/domains/canvas/domain/canvasChange.ts
find Builderforce.ai -type d -empty -delete 2>/dev/null || true
git commit -m "Revert 0267ffd — delete nested probe canvasChange.ts (#2554, #2601)"
```

The `find` prunes the empty `Builderforce.ai/` prefix chain so no empty dirs are committed.

#### Step 4 — Push

```bash
git push origin builderforce/task-2554          # no --force
```

#### Step 5 — Verifiation (BR-4, all must pass before merge)

| # | Command | Must |
|---|---|---|
| 1 | `git show builderforce/task-2554:Builderforce.ai/frontend/src/domains/canvas/domain/canvasChange.ts` | **fail** (path absent) |
| 2 | `git diff origin/main...builderforce/task-2554 -- frontend/src/domains/canvas/domain/canvasChange.ts` | **empty** (live module unchanged) |
| 3 | `git ls-tree --name-only -r builderforce/task-2554 | grep '^Builderforce\.ai/'` | **empty** (no nested tree) |
| 4 | `git ls-tree --name-only -r builderforce/task-2554 | grep 'CANVAS_CHANGE_PROBE\|task-2554-repo-probe'` | **empty** (no probe strings in paths) |

### Merge gate (BR-5)

Do **not** merge `builderforce/task-2554` into `main` until all four BR-4 checks pass. The merge gate is binary: all four pass → merge allowed; any fails → re-run Step 2/3.

### Risk: tsconfig blind spot

The `frontend/tsconfig.json` `include` glob `**/*.ts` is relative to `frontend/`, so a nested `Builderforce.ai/frontend/...` path is invisible to the type-checker. A green CI build after the revert does **not** prove the nested tree is absent — only the `git ls-tree`/`git show` checks in BR-4 do. The operator must run BR-4 manually; automation cannot substitute.
