# PRD: Add `progressPct` to `BfBrainChat`

## Problem & Goal

`BfBrainChat` in `bfApi.ts` does not expose chat progress. Downstream UI and API consumers cannot type-safely represent how far a brain chat has advanced (streaming, generation, or other in-flight work).

**Goal:** Add an optional numeric progress field to `BfBrainChat` so callers can read and pass progress without widening the type locally or using untyped casts.

## Target users / ICP roles

- Frontend engineers rendering brain chat status or progress UI
- API / SDK consumers mapping backend chat payloads into `BfBrainChat`
- Downstream agents implementing or reviewing this type change

## Scope

- File: `bfApi.ts`
- Type: `BfBrainChat`
- Change: add optional field `progressPct?: number`
- Keep existing fields, optionality, and exports unchanged

## Functional requirements

1. `BfBrainChat` includes `progressPct?: number`.
2. The field is optional; existing objects without `progressPct` remain valid.
3. Values are numbers (percent-style progress, typically 0–100). This PRD does not add runtime clamping or validation.
4. Any re-exported or generated alias of `BfBrainChat` in `bfApi.ts` must include the same field if it is the canonical definition.
5. No new endpoints, UI, or serialization logic unless already implied by the existing type surface.

## Acceptance criteria

- `progressPct?: number` is present on `BfBrainChat` in `bfApi.ts`.
- Typecheck passes for:
  - `BfBrainChat` without `progressPct`
  - `BfBrainChat` with `progressPct` set to a number
- Assigning a non-number to `progressPct` is a type error.
- No unrelated edits in `bfApi.ts`.
- Existing `BfBrainChat` usages compile without required updates.

## Out of scope

- UI, copy, or progress-bar implementation
- Backend contract changes, API versioning, or new request/response fields beyond this type
- Runtime validation, rounding, or 0–100 enforcement
- Persistence, analytics, or telemetry for progress
- Changes to other chat types unless they are the same `BfBrainChat` definition

## Requirements

### User stories

- As a frontend engineer rendering Brain chat status, I need `BfBrainChat` to declare an optional numeric `progressPct` so I can read and pass percent-style progress without local type widening or untyped casts.
- As an API / SDK consumer mapping `GET /api/brain/chats` payloads into `BfBrainChat`, I need the field to be optional so existing objects that omit it remain assignable.

### Current type (baseline)

Canonical definition: `export interface BfBrainChat` in `clients/vscode/src/bfApi.ts` (the VS Code tenant-API client). There is **no** generated or re-exported alias of this interface in that file.

Existing fields (must be preserved, including optionality):

| Field | Type | Notes |
| --- | --- | --- |
| `id` | `number` | Required |
| `title` | `string` | Required |
| `projectId` | `number \| null` | Required |
| `origin` | `string?` | Optional |
| `createdAt` | `string?` | Optional |
| `updatedAt` | `string?` | Optional |
| `participants` | `Array<{ ref: string; kind: string }>?` | Optional; absent on older servers |
| `ticketCount` | `number?` | Linked-ticket count from `GET /api/brain/chats` |
| `ticketProgressPct` | `number \| null?` | Linked-ticket rollup 0–100, or `null` when none are linked |

Known call sites that construct or consume `BfBrainChat` (must keep compiling with **no** required updates): `sessionsLibrary.ts` / `sessionsLibrary.test.ts`, `sessionsTree.ts` (`conversationTreeLabel` already reads `ticketProgressPct`, not `progressPct`), `extension.ts` (`chatIdOf`).

Sibling type `BrainChat` in `brain-embedded/src/types.ts` is a **different** definition (also has `ticketCount` / `ticketProgressPct`, not `progressPct`). Out of scope for this ticket.

### Functional requirements

**FR-1. Canonical field.** `BfBrainChat` SHALL include `progressPct?: number`. If a re-export or generated alias of `BfBrainChat` is later added in `bfApi.ts`, it MUST include the same field.

**FR-2. Optionality / backward compatibility.** The field SHALL be optional (`?`). A `BfBrainChat` object that omits `progressPct` SHALL remain a valid value. Existing object literals and `Partial<BfBrainChat>` helpers MUST typecheck without changes.

**FR-3. Type contract.** When present, `progressPct` SHALL be a `number`. Assigning a non-number (string, boolean, object) SHALL be a TypeScript error. This ticket does **not** add runtime clamping, rounding, `NaN` checks, or 0–100 enforcement.

**FR-4. Semantics.** `progressPct` is percent-style progress (typically 0–100) for how far the brain chat has advanced (streaming, generation, or other in-flight work, as named by the PM problem statement). This ticket does **not** bind producers: it does not require `listBrainChats` (or the API) to populate the field. `listBrainChats` already returns the JSON body as `BfBrainChat[]`; declaring the optional field is sufficient for TypeScript to accept a payload that includes it.

**FR-5. Coexistence with `ticketProgressPct`.** `ticketProgressPct?: number | null` already carries the linked-ticket rollup used by `sessionsTree.conversationTreeLabel`. This ticket SHALL NOT rename, remove, narrow, or alias that field. `progressPct` is a **separate** optional `number` (not `number | null`). Callers MUST NOT treat the two as interchangeable: `ticketProgressPct === null` means “no linked tickets”; omitted `progressPct` means “unknown / not supplied.”

**FR-6. Surface freeze.** No new endpoints, UI, copy, serialization, persistence, analytics, or telemetry. No progress-bar implementation. Parent epic #2436 (sidebar `%` rendering, ChatTicketService batching, brain-ui switcher) is **not** this ticket.

**FR-7. Edit scope.** Only `BfBrainChat` in `clients/vscode/src/bfApi.ts` changes. No unrelated edits in that file. Do not change other chat types unless they are the same `BfBrainChat` definition (they are not).

### Non-functional

**NFR-1.** Backward compatible: no new required fields; no breaking change to existing `BfBrainChat` object literals.

**NFR-2.** JSDoc SHALL match neighboring fields (one-line comment stating percent-style 0–100, optional/absent on older servers, distinct from `ticketProgressPct`).

### Acceptance mapping

| Acceptance criterion | Requirement |
| --- | --- |
| `progressPct?: number` present on `BfBrainChat` in `bfApi.ts` | FR-1 |
| Typecheck for `BfBrainChat` without `progressPct` | FR-2 |
| Typecheck for `BfBrainChat` with `progressPct` set to a number | FR-3 |
| Assigning a non-number to `progressPct` is a type error | FR-3 |
| No unrelated edits in `bfApi.ts` | FR-7 |
| Existing `BfBrainChat` usages compile without required updates | FR-2, FR-5 |

### Out of scope (confirmed)

- UI, copy, or progress-bar implementation (including `sessionsTree.ts` / brain-ui switcher)
- Backend contract changes, API versioning, or ChatTicketService batching
- Runtime validation, rounding, or 0–100 enforcement
- Persistence, analytics, or telemetry for progress
- Replacing `ticketProgressPct` with `progressPct`
- Changes to `BrainChat` in `brain-embedded` or frontend chat types

### Open point for Architect (does not block this type change)

Parent epic #2436 asked `GET /api/brain/chats` to include per-chat `progressPct` via ChatTicketService. The list payload already exposes that signal as `ticketProgressPct`, and the VSIX tree already renders it. This child ticket still adds `progressPct?: number` as specified. Architect should record whether later work copies ticket rollup into `progressPct`, keeps the fields independent, or treats `progressPct` as in-flight generation only.
