# PRD: VS Code Client — Type-check, Test, Production Build, Package

## Problem & Goal

The VS Code client (`clients/vscode`) must ship as a reliable, production-ready extension. Downstream agents currently lack a single source of truth for what “done” means for type-checking, tests, the production `esbuild` + `tsc` + webview pipeline, and packaging.

**Goal:** Define the shared contract so any agent can type-check, test, produce a production bundle (extension host + webview), and emit a installable package without ad-hoc steps or missing artifacts.

## Target users / ICP roles

- **Downstream coding agents** executing this task against `clients/vscode`.
- **Extension maintainers** who must verify CI-equivalent local and production outputs.
- **End users (indirect):** VS Code users who install the packaged extension; they never run this pipeline.

## Scope

In scope for `clients/vscode` only:

- Type-check the extension TypeScript (and webview TS if present) with project `tsc` config.
- Run the client’s existing unit/integration tests.
- Production build:
  - Bundle extension host code with **esbuild** (minified, production defines, no source maps unless the repo already requires them for crash reporting).
  - Emit declaration/type outputs or run `tsc` as required by the existing build (no emit vs. emit per `tsconfig`).
  - Build webview assets (HTML/JS/CSS) into the paths the extension loads at runtime.
- Package the extension (typically `.vsix` via `vsce` / `@vscode/vsce` or the repo’s equivalent script).
- Use existing scripts, configs, and output directories; do not invent a parallel toolchain.

## Functional requirements

1. **Type-check**
   - Run the repo’s type-check command for `clients/vscode` (e.g. `tsc --noEmit` / workspace script).
   - Must use the client’s `tsconfig` (including webview `tsconfig` if separate).
   - Must fail on type errors; no `skipLibCheck` changes unless already set.

2. **Test**
   - Run the client’s test script (unit and any VS Code integration/e2e already wired).
   - Tests must run against the same source/layout the build consumes.
   - Fail the task on non-zero test exit.

3. **Production esbuild (extension host)**
   - Entry points, externals (`vscode`), format (`cjs` unless the project is ESM), platform `node`, and outfile/outdir must match existing `esbuild` config or npm scripts.
   - Production mode: minify, drop `DEBUG`/`development` defines if used, tree-shake, no watch.
   - Do not bundle `vscode` or other runtime-provided modules.

4. **tsc in production**
   - Run `tsc` as the project does for production (type-check only, or emit `.d.ts` / JS if that is the current contract).
   - `esbuild` output and `tsc` must not fight over the same emit paths unless the existing pipeline already coordinates them.

5. **Webview production build**
   - Compile/bundle webview TS/JS and CSS into the static directory the extension `webview.html` / `asWebviewUri` paths expect.
   - Production: minify, no HMR/watch, correct CSP-friendly asset URLs (relative or `webview.cspSource` as already implemented).
   - HTML entry must reference built assets, not dev-server URLs.

6. **Package**
   - Produce an installable artifact (`.vsix`) with `vsce package` or the repo script.
   - `package.json` `main`, `browser` (if any), `engines.vscode`, activation events, and contributed views/commands must point at production outputs.
   - Respect `.vscodeignore` so source maps, tests, `node_modules` (except bundled), and webview source are not shipped unless required.
   - Version, publisher, and extension id come from existing `package.json`; do not bump version unless the repo script does.

7. **Reproducibility**
   - Prefer documented npm/pnpm/yarn scripts (`typecheck`, `test`, `build`, `package` or equivalents).
   - Do not commit build artifacts unless the repo already does.
   - Node/npm versions should match the client’s engines / lockfile.

## Acceptance criteria

- Type-check exits 0 with zero TypeScript errors under the client configs.
- Test suite exits 0; no skipped-as-passed failures; no tests deleted to go green.
- Production build exits 0 and writes:
  - Extension host bundle(s) at the path(s) `package.json` `main` (and any secondary entries) reference.
  - Webview JS/CSS/HTML at the runtime-loaded paths.
- Bundles are production: minified where the existing prod config minifies; `vscode` external; no `localhost` webview URLs.
- `vsce package` (or project equivalent) exits 0 and produces a `.vsix`.
- Installing the `.vsix` in a matching VS Code engine version activates without missing-file errors for main or webview assets.
- `.vscodeignore` excludes tests, raw webview src, and unused `node_modules`; packaged size is consistent with a production extension (no accidental full `src/` dump).
- No new toolchain, no unrelated refactors, no change to extension UX unless required to point at prod assets.

## Out of scope

- Publishing to the VS Marketplace or Open VSX.
- Signing, notarization, or store listing metadata beyond what packaging already reads.
- Rewriting the build to webpack/vite/rollup or changing bundler unless the current pipeline is broken.
- Adding new features, commands, views, or webview UI.
- Coverage gates, performance budgets, or new CI workflows unless already required to type-check/test/build/package.
- Other clients (desktop, web, CLI) and shared packages except as dependencies of this client’s build.
- Version bumps, changelog, and git tags.
