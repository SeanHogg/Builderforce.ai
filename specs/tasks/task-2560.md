# PRD: VS Code Client — Type-check, Test, Production Build, Package

## Problem & Goal

The VS Code client (`clients/vscode`) must ship as a reliable, production-ready extension. Downstream agents currently lack a single source of truth for what “done” means for type-checking, tests, the production `esbuild` + `tsc` + webview pipeline, and packaging.

**Goal:** Define the shared contract so any agent can type-check, test, produce a production bundle (extension host + webview), and emit a installable package without ad-hoc steps or missing artifacts.

## Target users / ICP roles

- **Downstream coding agents** executing this task against `clients/vscode`.
- **Extension maintainers** who must verify CI-equivalent local and production outputs.
- **End users (indirect):** VS Code users who install the packaged extension; they never run this pipeline.

## Scope

In scope for `clients/vscode` only:

- Type-check the extension TypeScript (and webview TS if present) with project `tsc` config.
- Run the client’s existing unit/integration tests.
- Production build:
  - Bundle extension host code with **esbuild** (minified, production defines, no source maps unless the repo already requires them for crash reporting).
  - Emit declaration/type outputs or run `tsc` as required by the existing build (no emit vs. emit per `tsconfig`).
  - Build webview assets (HTML/JS/CSS) into the paths the extension loads at runtime.
- Package the extension (typically `.vsix` via `vsce` / `@vscode/vsce` or the repo’s equivalent script).
- Use existing scripts, configs, and output directories; do not invent a parallel toolchain.

## Functional requirements

1. **Type-check**
   - Run the repo’s type-check command for `clients/vscode` (e.g. `tsc --noEmit` / workspace script).
   - Must use the client’s `tsconfig` (including webview `tsconfig` if separate).
   - Must fail on type errors; no `skipLibCheck` changes unless already set.

2. **Test**
   - Run the client’s test script (unit and any VS Code integration/e2e already wired).
   - Tests must run against the same source/layout the build consumes.
   - Fail the task on non-zero test exit.

3. **Production esbuild (extension host)**
   - Entry points, externals (`vscode`), format (`cjs` unless the project is ESM), platform `node`, and outfile/outdir must match existing `esbuild` config or npm scripts.
   - Production mode: minify, drop `DEBUG`/`development` defines if used, tree-shake, no watch.
   - Do not bundle `vscode` or other runtime-provided modules.

4. **tsc in production**
   - Run `tsc` as the project does for production (type-check only, or emit `.d.ts` / JS if that is the current contract).
   - `esbuild` output and `tsc` must not fight over the same emit paths unless the existing pipeline already coordinates them.

5. **Webview production build**
   - Compile/bundle webview TS/JS and CSS into the static directory the extension `webview.html` / `asWebviewUri` paths expect.
   - Production: minify, no HMR/watch, correct CSP-friendly asset URLs (relative or `webview.cspSource` as already implemented).
   - HTML entry must reference built assets, not dev-server URLs.

6. **Package**
   - Produce an installable artifact (`.vsix`) with `vsce package` or the repo script.
   - `package.json` `main`, `browser` (if any), `engines.vscode`, activation events, and contributed views/commands must point at production outputs.
   - Respect `.vscodeignore` so source maps, tests, `node_modules` (except bundled), and webview source are not shipped unless required.
   - Version, publisher, and extension id come from existing `package.json`; do not bump version unless the repo script does.

7. **Reproducibility**
   - Prefer documented npm/pnpm/yarn scripts (`typecheck`, `test`, `build`, `package` or equivalents).
   - Do not commit build artifacts unless the repo already does.
   - Node/npm versions should match the client’s engines / lockfile.

## Acceptance criteria

- Type-check exits 0 with zero TypeScript errors under the client configs.
- Test suite exits 0; no skipped-as-passed failures; no tests deleted to go green.
- Production build exits 0 and writes:
  - Extension host bundle(s) at the path(s) `package.json` `main` (and any secondary entries) reference.
  - Webview JS/CSS/HTML at the runtime-loaded paths.
- Bundles are production: minified where the existing prod config minifies; `vscode` external; no `localhost` webview URLs.
- `vsce package` (or project equivalent) exits 0 and produces a `.vsix`.
- Installing the `.vsix` in a matching VS Code engine version activates without missing-file errors for main or webview assets.
- `.vscodeignore` excludes tests, raw webview src, and unused `node_modules`; packaged size is consistent with a production extension (no accidental full `src/` dump).
- No new toolchain, no unrelated refactors, no change to extension UX unless required to point at prod assets.

## Out of scope

- Publishing to the VS Marketplace or Open VSX.
- Signing, notarization, or store listing metadata beyond what packaging already reads.
- Rewriting the build to webpack/vite/rollup or changing bundler unless the current pipeline is broken.
- Adding new features, commands, views, or webview UI.
- Coverage gates, performance budgets, or new CI workflows unless already required to type-check/test/build/package.
- Other clients (desktop, web, CLI) and shared packages except as dependencies of this client’s build.
- Version bumps, changelog, and git tags.

### R-4 — Type-check

From `clients/vscode/`, run **`pnpm run type-check`** (alias `typecheck`). That script is:

```
tsgo -p ./ && tsgo -p webview/tsconfig.json && tsgo -p harness/tsconfig.json && tsgo -p test-integration/tsconfig.json && tsc -p ./ && tsc -p webview/tsconfig.json && tsc -p harness/tsconfig.json && tsc -p test-integration/tsconfig.json
```

All four projects must exit 0. Root `tsconfig.json` is `"noEmit": true`, `"strict": true`, `"include": ["src/**/*.ts"]` — this is type-check only; it must not emit JS into `out/` (esbuild owns that path). Webview has its own `webview/tsconfig.json`.

Non-zero type-check is a **hard stop**. Do not start tests, production build, or package.

### R-5 — Test

From `clients/vscode/`, run **`pnpm test`** (`vitest run`) against the same source/layout the build consumes.

**Do not run `harness/scenarios.test.ts` in full** — it is a known OOM (PRD 27 **#2563** / **#2562**). Exclude that file (vitest `--exclude` / config already excluding it) rather than deleting tests to go green. Do not treat a skipped-as-passed or zero-files-executed run as success.

`test:integration` (`vscode-test`) is a **separate** script. It is **not** required by this ticket unless it is already part of `pnpm test` (it is not). `pretest` compile+lint, if present, is not a substitute for R-4.

Any non-zero test exit is a **hard stop**. Do not start production build or package. Record cwd, command, exit code, and failing file / test names.

### R-6 — Production esbuild (extension host)

After R-4 and R-5 exit 0, produce the host bundle with **`node esbuild.mjs --production`** (the file is `esbuild.mjs`, listed in `.vscodeignore`; `vscode:prepublish` / `compile` already call it).

Must match the existing bundler contract:

- Entry / outfile: `out/extension.js` (the path `package.json` `main` names)
- Format **cjs**, platform **node**
- **`vscode` external** — do not bundle the VS Code runtime module
- Production: **minify**, tree-shake, **no watch**, **no source maps** (`.vscodeignore` already excludes `**/*.map`; do not add maps for crash reporting unless the repo already requires them)
- No new entry points, no new externals policy

`vscode:prepublish` is exactly `node esbuild.mjs --production && tsc -p ./ && pnpm run build:webview`. Running `pnpm run package` will invoke that script via vsce. An explicit production chain **or** the `vscode:prepublish` that `package` already runs satisfies this requirement; do not add a third bundler.

### R-7 — tsc in the production chain

Run **`tsc -p ./`** as `vscode:prepublish` / `compile` already do. Because root tsconfig is `"noEmit": true`, this is a second type-check in the production chain — it must **not** fight esbuild for `out/extension.js`. Do not change `noEmit` or emit `.d.ts` into `out/` unless the existing pipeline already does (it does not).

### R-8 — Webview production build

Run **`pnpm run build:webview`**. That script is `node ../../scripts/ensure-linked-deps.mjs ../../frontend && vite build --config webview/vite.config.ts`.

Vite contract (`webview/vite.config.ts`) — do not retarget:

- `outDir` → `clients/vscode/media/webview/`
- `base: './'` (relative, CSP-friendly; **no** localhost / HMR / dev-server URLs)
- `emptyOutDir: true`, `sourcemap: false`, `cssCodeSplit: false`
- Hashless names: `index.js`, `index.css`, `chunk-[name].js`, `index.[ext]` so the host can build stable `asWebviewUri`s
- `process.env.NODE_ENV` inlined to `"production"`
- ONNX `.wasm` dropped at `generateBundle` (`dropWasmAssets`) — do not ship ~21 MB wasm

After a successful build, `media/webview/` must contain at least **`index.html`**, **`index.js`**, and **`index.css`**. The host HTML shell (`renderWebviewHtml`) must reference those built assets, not `webview/` source and not a Vite dev server.

A stale **#2556/#2557** `dist` or missing frontend catalogs is a classic false failure because this config compiles `frontend/src/components/creation-canvas/**` and resolves `@seanhogg/builderforce-brain-embedded` / brain-ui through built output. If the webview build fails for missing upstream `dist`, **stop and report** — do not silently rebuild sibling packages (those are #2556–#2559).

### R-9 — Package

After the production chain has run, produce the artifact with **`pnpm run package`** (`node vsce-platform.mjs package`).

The packager:

- Invokes `@vscode/vsce` with **`--no-dependencies --target <os>-<arch>`** (`win32|darwin|linux|alpine` × `x64|arm64`)
- Default outfile: **`builderforce-ai-<version>.vsix`** in `clients/vscode/` (currently `builderforce-ai-2026.9.79.vsix`)
- **Refuses to overwrite** an existing file for that version unless **`--allow-overwrite`** is passed. Do **not** bump version to get around this. If the artifact already exists: report it (sibling may have packaged the same version) **or** re-cut only with `--allow-overwrite` when this verify pass deliberately replaces that exact build
- vsce runs **`vscode:prepublish`** (R-6–R-8) unless skipped; a double production build is acceptable

`.vscodeignore` must stay in force so the VSIX does **not** dump `src/`, `webview/` source, `harness/`, `test-integration/`, `**/*.map`, `**/*.ts`, `node_modules/**`, `esbuild.mjs`, or `vsce-platform.mjs`. Built `out/extension.js`, `media/webview/*`, `l10n/`, and `media/icon.png` **must** be inside the package.

Do **not** run `publish:marketplace` / `publish:openvsx` (out of scope).
