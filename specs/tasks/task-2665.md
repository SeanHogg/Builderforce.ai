# PRD: Advisor Filter Fields for Freelancer/Talent Marketplace

## Problem & Goal

**Problem:** The P2 advisor filtering work (R1/R2, AC-F1) is blocked because its required data model and API contract do not exist yet. Specifically:

1. `FreelancerProfile` (in `frontend/src/lib/freelance/talentProfile.ts`) has no `expertise`, `languages`, `methods`, or `stages` fields — the four attributes advisor filters must query against.
2. `TalentFilters` only supports `q, discipline, skill, minRate, maxRate, sort, page, pageSize` — no filter params exist for the four advisor attributes above.
3. `listFreelancers` calls `GET /api/freelancers` with `auth: 'web'`, but design (D-2.4) requires logged-out browse (R2.7) to hit the public `GET /api/public/freelancers` endpoint.
4. `MarketplaceCategory` (in `MarketplacePageClient.tsx`) has no `advisors` member, so there is no way to gate `category=advisors` visibility per R2.1/D-2.2.

**Goal:** Land the foundational data model, filter contract, category enum, and public-endpoint routing so that P2 advisor filters (#2580) compile against real fields and can return non-zero, correct results. This is a P0 deliverable (#2527) that unblocks #2580.

## Target Users / ICP Roles

- **Logged-out visitors** browsing the public talent marketplace (R2.7) — need advisor data via the public endpoint without auth.
- **Logged-in clients/buyers** filtering for advisors by expertise, language, methodology, or funding stage.
- **Frontend engineers (downstream, #2580)** who consume `FreelancerProfile`, `TalentFilters`, and `MarketplaceCategory` to build the actual filter UI.

## Scope

In scope for this ticket:
- Extend `FreelancerProfile` type/model with `expertise`, `languages`, `methods`, `stages`.
- Extend `TalentFilters` to accept corresponding filter parameters.
- Add `advisors` to `MarketplaceCategory`.
- Route unauthenticated/public browse traffic to `GET /api/public/freelancers`; keep authenticated traffic on `GET /api/freelancers` (or consolidate per D-2.4 — see open question).
- Ensure `listFreelancers` (and any related fetchers) select the correct endpoint based on auth state.
- Seed or confirm backend/API responses actually populate the four new fields so filters match non-zero rows.

Out of scope: see [Out of Scope](#out-of-scope) below.

## Functional Requirements

| ID | Requirement |
|----|-------------|
| FR-1 | `FreelancerProfile` type must include `expertise: string[]`, `languages: string[]`, `methods: string[]`, `stages: string[]` (naming/shape to match API contract; nullable/optional only if API can omit them). |
| FR-2 | `TalentFilters` must accept optional `expertise`, `languages`, `methods`, `stages` parameters, each supporting multi-value selection (array or comma-delimited, matching existing param conventions like `skill`). |
| FR-3 | `MarketplaceCategory` enum/union in `MarketplacePageClient.tsx` must include `'advisors'` as a valid member. |
| FR-4 | `listFreelancers` must call `GET /api/public/freelancers` when the user is unauthenticated (logged-out browse, R2.7), and the existing authenticated endpoint otherwise, per D-2.4. |
| FR-5 | The public endpoint response must be shape-compatible with `FreelancerProfile` (including the four new fields) so no additional mapping/adapter is needed downstream. |
| FR-6 | New filter fields must be passed through to the API request as query params consistent with existing filter param encoding. |
| FR-7 | Existing filters (`q, discipline, skill, minRate, maxRate, sort, page, pageSize`) and their behavior must remain unchanged (no regressions). |

## Acceptance Criteria

- **AC-1:** `FreelancerProfile` compiles with `expertise`, `languages`, `methods`, `stages` fields, and existing consumers of this type still typecheck without modification (or with only additive changes).
- **AC-2:** `TalentFilters` compiles with the four new optional fields; passing them produces the correct query string/params sent to the API.
- **AC-3:** `'advisors'` is a valid `MarketplaceCategory` value; `category=advisors` can be read and branched on in `MarketplacePageClient.tsx` without type errors.
- **AC-4:** When no auth session is present, `listFreelancers` requests `GET /api/public/freelancers`; when authenticated, it requests the existing `GET /api/freelancers`. Verified via test/mocked network call.
- **AC-5:** An integration/unit test filtering by at least one of `expertise`, `languages`, `methods`, or `stages` against seeded/mock data returns **non-zero** matching rows (this is the core regression this ticket fixes — zero-row matches are treated as a failing build).
- **AC-6:** No existing filter (`q`, `discipline`, `skill`, `minRate`, `maxRate`, `sort`, `page`, `pageSize`) tests regress.
- **AC-7:** #2580 can be unblocked — its filter UI code compiles against the updated `FreelancerProfile`/`TalentFilters` types with zero `any`/placeholder casts required.

## Out of Scope

- Building the actual advisor filter UI/UX (dropdowns, chips, etc.) — that is #2580.
- Backend/API implementation of `GET /api/public/freelancers` if it does not yet exist server-side (this PRD assumes the endpoint exists per D-2.4; if it does not, that is a separate P0 backend ticket and must be flagged immediately).
- Full audit or redesign of `MarketplaceCategory` beyond adding the `advisors` member (e.g., not addressing other missing categories unless already tracked elsewhere).
- Performance/caching optimization of the public endpoint.
- Analytics/telemetry for advisor filter usage.
- Data backfill strategy for existing freelancer records missing `expertise`/`languages`/`methods`/`stages` values beyond what's needed to satisfy AC-5.
