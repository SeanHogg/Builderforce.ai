# PRD: Advisors Marketplace Category Filters

**Status:** WIP  
**Surface:** Marketplace listing, `?category=advisors`  
**Constraint:** Category-specific filters must not change behavior for any other marketplace category.

---

## Problem & Goal

**Problem.** Marketplace search for advisors is under-specified. Buyers landing on `?category=advisors` cannot narrow listings by the dimensions that actually decide a match: what the advisor knows, what language they work in, how they deliver, and which company stage they typically serve. Existing marketplace filters are either generic (price, rating, availability) or owned by other categories. Applying advisor dimensions globally would pollute other category UIs and query contracts. Omitting them leaves advisor discovery as a long, unfiltered scroll.

**Goal.** On `category=advisors` only, expose four first-class filters—**expertise**, **language**, **method**, **stage**—that compose with existing marketplace query, sort, and pagination. All other categories keep their current filter sets, URLs, empty states, and result counts. No shared filter schema, facet API, or listing card should change for non-advisor categories.

**Success (directional).** Advisor-category sessions use at least one of the four filters; filtered result sets match listing metadata; non-advisor category traffic, bounce, and conversion are unchanged.

---

## Target users / ICP roles

| Role | Need |
|---|---|
| **Founder / operator (buyer)** | Find an advisor who has done this domain, speaks this language, works this way, at this stage—without reading every profile. |
| **Operator / hiring manager (buyer)** | Share a filtered advisors URL with stakeholders; expect the same set on reload. |
| **Advisor (seller)** | Be discoverable when their expertise, languages, methods, and stages are filled in; not appear under the wrong facets. |
| **Marketplace ops / catalog** | Maintain advisor facet taxonomies without forking the whole marketplace filter stack. |

Primary ICP for this change: buyers on the advisors category. Sellers are affected only via listing metadata and facet coverage.

---

## Scope

**In scope**

- Advisors category listing (`/marketplace` or equivalent with `category=advisors`).
- Four filters: expertise, language, method, stage.
- URL query params that round-trip those filters (shareable, reload-safe, back-button-safe).
- Facet values sourced from advisor listing metadata / taxonomy, not free text on the listing page.
- Composition with existing advisors-applicable controls (search query, sort, price/rate if already present, pagination).
- Empty, zero-result, and “clear filters” states for this category only.
- Isolation: other `category=*` routes, default (no category) marketplace, and any category switcher must not gain, lose, or remap filters.

**Assumptions**

- Advisor listings already (or will, via a separate catalog task) store expertise, language, method, and stage as structured fields.
- Marketplace already keys listings and filters by `category`.
- Multi-select is the default interaction unless a taxonomy is strictly single-value (stage may be single- or multi-select; both must be defined in implementation, not mixed per session).

---

## Functional requirements

### 1. Category gating

- The four filters render **only** when the active category is `advisors` (query `category=advisors` on `/marketplace`). This param is additive; it does not replace `family` / `kind` and does not create a `/advisors` route or a `MARKETPLACE_LISTING_KINDS` value.
- Switching away from advisors removes those controls and **drops** advisor-only params (`expertise`, `language`, `method`, `stage`, `category=advisors`) from the URL. Other-category params are not rewritten except to remove advisor-only keys.
- Switching **to** advisors does not inherit inapplicable filters from the previous family (e.g. asset kind, product condition, job type). Inapplicable params are stripped; applicable shared params (`q`, `sort`) may persist; `page` resets to 1.
- Default marketplace (no category) and every non-advisor / non-talent family keep their current filter chrome and query contract. `category=advisors` pasted onto a non-talent family is ignored for chrome and predicates (keys stripped).

### 2. Filter: expertise

- Multi-select from `EXPERTISE_AREAS` (`@builderforce/creation-canvas-contract` / `startupListing.ts`: `product`, `marketing`, `operations`, `finance`, `legal`, `people`, `technology`, and any further members of that exported array).
- Match: listing `expertise` includes **at least one** selected value (OR within the filter).
- Facet counts reflect the current result set after other applied filters (AND across filter groups).
- Do not ship a parallel GTM / fundraising / “technical architecture” chip set unless those slugs already exist in `EXPERTISE_AREAS`.

### 3. Filter: language

- Multi-select from the #2528 closed ISO 639-1 list: `en, es, fr, de, pt, zh, ja, ko, hi, ar, it, nl, pl, ru, tr, vi, id, th, sv, uk`.
- Codes in data and URL; localized labels in UI.
- Match: listing `languages` offers **at least one** selected language (OR within the filter).
- Do not invent languages outside that list. Unused codes may show count `0` and follow the existing marketplace facet pattern.

### 4. Filter: method

- Multi-select from listing `methods`: `video`, `phone`, `email`, `in-person` only (#2528).
- Match: listing includes **at least one** selected method (OR within the filter).
- Do not ship 1:1 / group / retained / project / workshop / async as method values.

### 5. Filter: stage

- Multi-select from listing `stages`: `start`, `grow`, `exit` only (#2528). OR within the filter. Do not mix single-select in the same UI.
- Match against stored `stages` only — not inferred from buyer profile, and **not** `BUSINESS_STAGES` (pre-seed / seed / series A / …).

### 6. Composition and query

- Cross-filter logic: **AND** between the four groups; **OR** within a multi-select group.
- Combine with existing search `q` (AND): text search still applies to advisor name, bio, and other currently searched fields.
- Combine with existing sort and page size; applying or changing a filter resets to page 1.
- Result count and empty state must match the filtered set.
- Deep link example (normative slugs):
  `?category=advisors&expertise=product,finance&language=en,es&method=video&stage=start`
- Unknown or malformed advisor filter values are ignored (not 500); remaining valid filters still apply.
- Clearing all advisor filters returns the unfiltered advisors category set.

### 7. Listing eligibility

- Only **published** talent listings in the advisors view (`category=advisors` → Talent family) are facetable and returnable. Company `SEEKING_TYPES` `'advisors'` rows are not this population.
- Listings missing a given field do not match a positive filter on that field; they remain visible when that filter is unused.
- Filter application is server-authoritative (or equivalent API). Client-only hiding of cards is not sufficient.
- Fields are consumed from #2528 (`freelancer_profiles`); this ticket does not create them.

### 8. Isolation / non-regression

- Non-advisor category pages must not request advisor facet endpoints as a hard dependency of first paint.
- Shared listing/filter components must branch on category; advisor taxonomies are not merged into global facet enums.
- Analytics, ads, SEO canonicals, and sitemap behavior for other categories unchanged.
- API consumers of non-advisor listing endpoints see no new required params and no changed default result sets.

## Acceptance criteria

1. **Advisors-only chrome.** Given `category=advisors`, the listing UI shows expertise, language, method, and stage. Given any other category or no category, those four controls are absent.

2. **Correct AND/OR.** Selecting two expertises and one language returns listings that have at least one of those expertises **and** that language. Counts and cards agree.

3. **URL round-trip.** Applying filters updates the query string. Opening that URL in a new session restores the same filters, order-independent param values, and the same result set (stable sort).

4. **Category switch.** From advisors with filters applied, switching to another category removes advisor params and does not show advisor filters. Switching back to advisors does not resurrect the previous advisor filters unless they are still in the URL.

5. **Pagination / sort.** Changing any of the four filters resets to page 1 and keeps the current sort. Changing page or sort does not clear advisor filters.

6. **Empty and clear.** A combination with zero listings shows the existing marketplace empty/zero-result pattern (advisors copy is allowed). “Clear filters” removes the four params and restores the full advisors set.

7. **Bad values.** `?category=advisors&expertise=not-a-real-slug` does not error; invalid values are dropped; valid siblings still filter.

8. **Metadata fidelity.** A listing is returned for a filter only if its stored expertise / language / method / stage fields justify the match. No client-side-only filtering that disagrees with the API.

9. **Other categories unchanged.** For each existing non-advisor category: same filter set, same default results for the same URL, same result count for representative queries, no new query params required, no visual regression on filter chrome. Smoke at least one category that already has its own custom filters and one that does not.

10. **Performance envelope.** Facet load and filtered listing response stay within the current marketplace listing SLO for comparable result sizes; no N+1 per facet on the listing request.

11. **A11y.** Filters are keyboard-operable, labelled, and announced consistently with existing marketplace filter controls (including selected-count and clear).

---

## Out of scope

- Creating, editing, or backfilling advisor listing fields (expertise, language, method, stage) in the seller onboarding or profile editor—catalog/taxonomy work is a dependency, not this PRD.
- New marketplace categories, or renaming `advisors`.
- Recommendation / ranking model changes (e.g. “best match” using these fields).
- Buyer-profile auto-application of language or stage.
- Geo, price, rating, availability, or calendar filters (keep as they are if already on advisors; do not add here).
- Free-text tag clouds or user-generated facet values on the listing page.
- Saved searches, alerts, or email digests for these filters.
- Localization of the marketplace chrome beyond using existing i18n patterns for new labels.
- Mobile-specific redesign of the filter drawer (follow existing marketplace filter IA).
- Admin taxonomy CMS, unless required to ship the four closed lists.
- Breaking API changes for non-advisor clients; versioned additive advisor query params only.
- Ads, featured placements, or paid boost interacting with these facets.

### Locked decisions

1. **No new listing kind, no `/advisors` route.** Do not add `advisor` (or `advisors`) to `MARKETPLACE_LISTING_KINDS`. Do not ship a parallel Advisor storefront. Advisors remain talent. This matches PRD 26 FR-1.4, #2528, and epic #2579 (“compose only”).
2. **Honor `?category=advisors` as an additive marketplace query param** on the existing `/marketplace` listing. It is **not** in the repo today (0 matches). It does **not** replace `family` / `kind`. It selects the advisors talent view and is the **only** gate for the four filters.
3. **Do not confuse company `SEEKING_TYPES` `'advisors'`** (`companies.seeking` in `startupListing.ts` — startups looking *for* advisors) with this buyer view. This ticket filters **published talent listings**, not company directory rows.
4. **Vocab is #2528 + contract constants — not the PM examples.** Single source of truth; do not fork parallel enums in the marketplace UI or API.
5. **Stage is multi-select.** #2528 stores `stages` as `string[]` (`start | grow | exit`). OR within the group. Do **not** use `BUSINESS_STAGES` (pre-seed / seed / series A / …). Do not mix single-select and multi-select in one session.
6. **This ticket does not create, edit, or backfill profile fields.** Persistence is #2528 (`freelancer_profiles`: `expertise`, `languages`, `methods`, `stages`). If a column is empty/`[]`, a positive filter on that field does not match; the listing still appears when that filter is unused.
7. **Server-authoritative.** Client-only hiding of cards is not sufficient. Additive optional query params only; non-advisor listing endpoints gain **no** new required params and **no** changed defaults.
8. **Siblings stay out.** Visitor chat = #2581. Resources tab = #2582. Volunteer badge / price `0` = #2584. Location filter = #2585. Industries, session length, session price, confidentiality, geo, rating, availability are **not** filters here.

### Population and chrome gate

- **Population:** published talent listings on `/marketplace` (Talent family: `family=talent`). Default marketplace and every non-talent family are unchanged.
- **Chrome gate:** the four filters render **if and only if** the active query has `category=advisors`.
- If `category=advisors` is set and `family` is omitted, treat the view as Talent (`family=talent` implied for results + chrome). Do not switch the user into Assets.
- If `category=advisors` is pasted onto a **non-talent** family (`family=asset` or any non-talent value), **do not** render the four filters, **do not** apply advisor field predicates, and **do not** fail first paint. Strip the advisor-only keys (see R-9) rather than merging taxonomies.
- Switching **to** `category=advisors` does not inherit inapplicable other-family params (asset kind chips, product condition, job type, etc.). Shared params `q`, `sort` may persist; `page` resets to 1.

### URL contract

Deep-link shape (order of keys and of comma-separated values is insignificant):

```
/marketplace?category=advisors&expertise=product,finance&language=en,es&method=video&stage=start
```

- Values are the slugs above (e.g. `method=in-person`, `stage=grow`). Comma-separated multi-select. Repeat-key vs comma form: pick the existing marketplace convention if one exists; otherwise comma-separated.
- Compose with existing `family`, `kind`, `q`, sort, and page params; do not rename them.
- Unknown or malformed advisor values are **ignored** (not 500); remaining valid advisor filters still apply. Example: `expertise=not-a-real-slug&language=en` → drop the bad expertise, still filter language `en`.
- Opening the URL in a new session restores the same filters and the same result set under the current stable sort.
- Clearing all four advisor params (or “Clear filters”) returns the unfiltered `category=advisors` set.

### Cross-filter logic

- **AND** across the four groups; **AND** with existing `q` (name, bio, and any fields already searched).
- **OR** within a multi-select group.
- Facet counts reflect the current result set **after** the other applied groups (AND across groups).
- Changing any of the four filters resets to page 1 and keeps the current sort. Changing page or sort does not clear advisor filters.
- Result count and empty/zero-result chrome must match the filtered set (existing marketplace empty pattern; advisors copy allowed).

### Isolation / non-regression

- Non-advisor (and no-category) pages must not request advisor facet endpoints as a **hard dependency of first paint**.
- Shared listing/filter components branch on `category=advisors`; advisor taxonomies are not merged into global facet enums.
- Analytics, ads, SEO canonicals, and sitemap behavior for other families/kinds unchanged.
- Smoke at least one family that already has custom filters (e.g. Talent `kind=gig`) and one that does not (e.g. an asset kind). Same filter set, same default results for the same URL, same result count for representative queries.

### User stories

- **US-1** As a founder on `/marketplace?category=advisors`, I see expertise, language, method, and stage, and I do not see them on any other family or on marketplace with no category.
- **US-2** As a hiring manager, I select two expertises and one language and get listings that have at least one of those expertises **and** that language; the count matches the cards.
- **US-3** As a stakeholder, I open a shared filtered URL and see the same filters and the same result set (order-independent params, stable sort).
- **US-4** As a buyer, I switch from advisors (with filters) to another family: advisor chrome and advisor params are gone; going back to advisors does not resurrect filters unless they are still in the URL.
- **US-5** As a buyer, changing a filter jumps to page 1; paging or sorting does not clear filters; zero results show the empty pattern; Clear filters restores the full advisors set.
- **US-6** As an advisor, I am returned for a filter only when my stored `expertise` / `languages` / `methods` / `stages` justify the match. Unpublished listings never appear.
