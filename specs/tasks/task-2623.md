# PRD: Late-connect calendar backfill, disconnect cleanup, retry & advisor warning

**Priority:** P1  
**Parent:** #2532  
**Depends on:** #2537 (P0 advisory calendar mirror)  
**Source of truth:** Product CRUD (advisory meetings). Calendar is a one-way outbound mirror.

## Problem & Goal

P0 (#2537) mirrors advisory meetings to a connected advisor calendar via `pushMeetingEvent`, but three gaps remain:

1. **Late connect has no backfill.** Connecting a calendar after eligible meetings already exist does not enqueue mirrors. Those meetings never appear on the calendar unless they are later mutated.
2. **Disconnect is connection-row only.** Disconnect deletes `calendar_connections` and leaves product-created remote events in place with no documented policy.
3. **Failures are swallowed.** `pushMeetingEvent` errors are not retried and never surface to the advisor. Sync can be silently stale indefinitely.

**Goal:** On connect, enqueue a one-way backfill of that advisor’s upcoming eligible meetings. On disconnect, apply a documented best-effort remote cleanup that never blocks. Mirror pushes use per-advisor retry with backoff and a dead-letter after N failures, then show a non-blocking in-product sync warning. Product CRUD remains authoritative; calendar write failures must not fail meeting create/update/delete.

## Target users / ICP roles

- **Advisor (primary):** Connects/disconnects their own calendar; expects existing upcoming meetings to appear after connect; must see a warning if mirroring has given up—not a blocking error.
- **Internal ops / support (secondary):** Needs a dead-letter they can inspect when an advisor’s mirror is stuck; no new admin UI in this slice.

Clients do not connect calendars in this slice.

## Scope

In scope for this P1:

1. **Connect backfill.** When an advisor successfully connects a calendar, enqueue mirror jobs for that advisor’s upcoming eligible advisory meetings. Default lookback is **1 day** (meetings with start ≥ now − 1 day). Skip rows that already have `calendar_event_id`. Same eligibility and payload rules as #2537.
2. **Disconnect policy (documented + implemented).** Disconnect always succeeds locally. Best-effort delete of **product-created** remote events (those we stored `calendar_event_id` for). Never block or roll back disconnect on remote failure. Leave remote events that we did not create.
3. **Per-advisor retry + dead-letter.** Failed mirror pushes retry with exponential backoff, scoped per advisor (one advisor’s failures do not stall others). After **N = 5** failed attempts on a given meeting-mirror job, move it to a dead-letter and stop retrying automatically.
4. **Advisor-visible sync warning.** After a job is dead-lettered (retries exhausted), show a non-blocking warning in the advisor’s calendar-connection / settings surface. Product CRUD and navigation stay fully usable. Clearing the warning when a later successful sync for that advisor occurs (e.g. reconnect or a subsequent successful push) is required.

Lookback is a server-side default (1 day), not an advisor-facing control in this slice.

## Functional requirements

### 1. Connect backfill

- Trigger: calendar connection reaches a connected/authorized state for an advisor (same success path as #2537 connect).
- Select that advisor’s advisory meetings that are **eligible to mirror** under #2537 rules, with `start_at >= now() - lookback` (default lookback **1 day**), and `calendar_event_id IS NULL`.
- Enqueue one mirror job per selected meeting (or an equivalent per-advisor batch that still processes meetings independently for retry). Do not synchronously push in the connect request path.
- Skip meetings that already have `calendar_event_id` (no overwrite, no duplicate remote create).
- Past meetings older than the lookback window are not backfilled.
- Connect UX remains success-oriented; backfill enqueue failure is logged and must not fail the connection itself. Enqueue failure should use the same retry/warning machinery where a job record can be created; if no job can be created, log and do not strand the connection.

### 2. Disconnect cleanup

**Policy (normative):**

- Disconnect **always** deletes/deactivates the local `calendar_connections` row (and any local tokens) and returns success to the advisor.
- After local disconnect, **best-effort** delete remote events we created: for this advisor, each stored `calendar_event_id` is deleted on the provider. Then clear `calendar_event_id` on those meeting rows (including when remote delete fails or the event is already gone).
- Remote delete failures **must not** block, retry-loop, or roll back disconnect. Failed remote deletes are logged; leftover remote events are accepted.
- Do not delete remote events that were not created by this product (no `calendar_event_id` we own).
- Reconnect after disconnect is a new connect: backfill applies again only to eligible rows still lacking `calendar_event_id`.

### 3. Retry, backoff, dead-letter

- `pushMeetingEvent` (create/update/delete of the mirrored event) must not swallow failures. Persist job state: pending / in_progress / succeeded / failed / dead_lettered.
- Retry **per advisor**: backoff and concurrency are isolated so advisor A’s provider errors do not delay advisor B.
- Backoff: exponential, starting at ~30s, cap ~15m, **max 5 attempts** per job (initial try + retries). Transient provider/network errors are retried; permanent errors (revoked token, 404 on update of missing remote event, payload rejected as invalid) may short-circuit to dead-letter before N if they cannot succeed without a new connect or a product-side change—but revoked/expired auth must still produce the advisor-visible warning.
- After N failures (or short-circuit permanent failure): mark dead-lettered; stop automatic retries.
- Meeting create/update/delete in product **never** waits on calendar success and **never** fails because the mirror failed.
- Delete-mirror jobs (meeting deleted in product while connected) use the same retry/dead-letter path. Disconnect cleanup is explicitly best-effort and **not** required to use the full N-retry loop if that would delay disconnect; it may fire-and-forget remote deletes.

### 4. Advisor-visible warning

- When at least one mirror job for the advisor is dead-lettered (or auth is revoked/expired and pushes cannot proceed), show a non-blocking warning on the calendar connection surface (and equivalent settings entry point used in #2537).
- Copy must convey that calendar sync is delayed or incomplete and that meetings in the product are still correct. Do not block CRUD, scheduling, or disconnect.
- Warning is per advisor, not per meeting, in this slice (one banner/state is enough).
- Clear the warning when there are no dead-lettered jobs for that advisor and the connection is healthy (successful push or successful reconnect + backfill enqueue with no remaining DLQ items).
- No email/push notification in this slice.

### 5. Invariants carried from #2537

- One-way product → advisor calendar only.
- Eligibility, field mapping, and `calendar_event_id` ownership unchanged except as needed to skip already-mirrored rows on backfill and to clear ids on disconnect.
- No new calendar providers.

## Acceptance criteria

1. **Late connect backfill.** Given an advisor with eligible advisory meetings starting in the future and/or within the past 1 day, and no `calendar_event_id` on those rows, after a successful calendar connect those meetings are enqueued for mirror and remote events are created. Meetings older than 1 day are not enqueued. Rows that already have `calendar_event_id` are not enqueued and are not duplicated on the provider.
2. **Connect is not blocked.** Connect succeeds even if backfill enqueue or subsequent pushes fail; failures follow retry/warning, not connect rollback.
3. **Disconnect never blocks.** Disconnect removes the local connection (and tokens) and returns success if the provider is down, deletes fail, or there are many remote events.
4. **Best-effort remote delete.** On disconnect, the system attempts to delete product-created remote events and clears local `calendar_event_id` values. Events we did not create remain. Leftover remote events after failed deletes are acceptable and logged.
5. **Reconnect backfill.** After disconnect + reconnect, eligible meetings without `calendar_event_id` are backfilled; meetings that somehow retained an id are skipped.
6. **Retry isolation.** A failing advisor’s mirror jobs retry with backoff and do not prevent other advisors’ jobs from running.
7. **Dead-letter after N.** A job that fails 5 times (or hits a permanent error) is dead-lettered and is not retried automatically.
8. **CRUD unblocked.** Meeting create/update/delete succeeds and remains correct in product regardless of mirror success, retry, or dead-letter.
9. **Warning visible.** After retries exhaust (or auth is unusable), the advisor sees a non-blocking sync warning on the calendar connection/settings surface. They can continue using meetings and can disconnect.
10. **Warning clears.** After a healthy connection and no remaining dead-lettered jobs for that advisor, the warning is not shown.
11. **No scope creep.** Behavior is advisor calendars only, existing provider(s) from #2537 only, one-way mirror only.

## Out of scope

- Two-way sync (calendar → product), conflict resolution, or treating the calendar as source of truth
- Client (advisee) calendar connect or client-facing mirrors
- New calendar providers or provider-agnostic redesign
- Advisor-configurable lookback / backfill window
- Historical backfill beyond the 1-day lookback
- Recurring-event expansion changes beyond what #2537 already ships
- Email, push, or Slack notifications for sync failure
- Admin/ops UI for the dead-letter (persistence + logs are enough)
- Blocking disconnect on incomplete remote cleanup
- Changing product meeting CRUD semantics or eligibility rules except skip-if-`calendar_event_id` and clear-on-disconnect
- Guaranteeing remote event removal on disconnect (best-effort only)

### R-1 — Connect-success trigger

When a calendar connection reaches a connected/authorized state for an advisor (the same success path as #2537: grant upserted, browser redirected `?calendar=connected`), the system **enqueues** a one-way backfill of that advisor’s upcoming eligible advisory meetings. The trigger is **successful connect**, not a separate advisor action. Clients never connect calendars in this slice.

### R-2 — Backfill selection

Select meetings that are **all** of:

- `createdBy` = the connecting advisor’s `userId`
- `tenant_id` = the connecting grant’s tenant
- eligible under #2537 rules (`kind = 'advisory'`, `scheduled_at IS NOT NULL`, `status ≠ 'cancelled'`, host connected)
- `scheduled_at >= now() - 1 day` (server UTC; see R-4)
- `calendar_event_id IS NULL`

Meetings that are live or ended **remain selectable** if they still satisfy the above (start within the lookback or in the future, not cancelled, no stored id). Null `scheduled_at` rows are never selected.

### R-3 — Lookback is a server default, not a control

Lookback is **1 day**. It is not advisor-facing, not per-connection, not configurable in this slice. Meetings with `scheduled_at < now() - 1 day` are **not** enqueued. There is no historical backfill beyond that window.

### R-4 — Skip already-mirrored rows

If `calendar_event_id` is already set, **do not enqueue**, **do not overwrite**, **do not create a second remote event**. Mixed inventory is per-meeting: one stored id means “already ours”.

### R-5 — Enqueue asynchronously; connect stays success-oriented

Do **not** synchronously `createEvent` inside the OAuth callback / connect request. Enqueue one mirror job per selected meeting (or an equivalent per-advisor batch that still **retries per meeting**). The connect response/redirect remains success (`?calendar=connected`) even if enqueue or later pushes fail.

If enqueue fails: log it. If a job record **can** be created, that job uses the R-10–R-13 retry/warning machinery. If **no** job record can be created, log and **do not** strand or roll back the connection.

### R-6 — Idempotent enqueue

OAuth callback replay, double-submit, or a second connect while jobs are already pending **must not** duplicate remote events. At most one **open** (pending / in_progress / failed-retrying) job may exist per `(advisor userId, meeting id, operation)` where operation ∈ {create, update, delete}. A succeeded create that stored `calendar_event_id` is not re-enqueued as create.

### R-7 — Disconnect always succeeds locally

`DELETE /api/calendar/connections/:id` (or the #2537 equivalent) **always**:

- deletes or deactivates the local `calendar_connections` row **and** its tokens/grant for that advisor + provider
- returns success to the advisor (today: 204)

This holds if the provider is down, remote deletes fail, there are many remote events, or there are none. Disconnect **never** rolls back because cleanup failed. Disconnect **never** blocks on the network.

### R-8 — Capture grant, then destroy it, then best-effort remote delete

Tokens live on `calendar_connections` today. Remote delete after disconnect therefore **cannot** read the row after it is gone.

Normative order:

1. Snapshot the advisor’s product-created mapping rows (`calendar_event_id` + provider + calendar id) **and** whatever grant material is required to attempt provider deletes.
2. Destroy the local connection + tokens (R-7) and return success.
3. **After** local success (must not delay the response): best-effort `deleteEvent` for each snapshotted product-created id.
4. Clear `calendar_event_id`, `calendar_provider`, and `calendar_html_link` on those meeting rows **whether or not** the remote delete succeeded, including 404 / already-gone.

Leftover remote events after failed deletes are **accepted** and **logged**. Failed disconnect deletes **do not** enter the N-retry / dead-letter loop (that loop would re-require a connection the advisor just removed, and would delay or re-surface a warning for a disconnected calendar). Fire-and-forget is required here.

### R-9 — Only delete events we created

Never delete a remote event that has no stored `calendar_event_id` we own. Never enumerate the provider calendar to “clean everything”. Events the advisor created outside this product stay.

### R-10 — Reconnect is a new connect

After disconnect + reconnect, R-1–R-6 apply again. Only eligible rows **still lacking** `calendar_event_id` are backfilled. Rows that somehow retained an id are skipped (R-4). Prior dead-lettered jobs for that advisor are **superseded/cancelled** on successful reconnect so they cannot keep the warning up after a healthy new connect (R-16).

### R-11 — Persist job state; do not swallow `pushMeetingEvent` failures

Every mirror push — **create, update, and delete** of the mirrored event, from live product CRUD while connected **and** from backfill — must persist job state:

`pending` → `in_progress` → `succeeded` | `failed` | `dead_lettered`

- `failed` means “will retry” (attempts remaining).
- `dead_lettered` means “automatic retries stopped”.

Returning `null` / empty-catch without a job record is **not** allowed for a connected advisor. (No-connection remains a no-op: if the host has no calendar, there is no job.)

Meeting create/update/cancel **never** waits on calendar success and **never** fails because the mirror failed. A best-effort first attempt inside the CRUD request is allowed **only if** (a) the HTTP handler does not await provider success as a condition of 2xx, and (b) a failure still records a retryable job.

### R-12 — Per-advisor isolation

Backoff, concurrency, and failure of advisor A **must not** delay advisor B. A shared worker is acceptable if jobs are independently schedulable per advisor (no head-of-line blocking across advisors). Isolation key is the connecting advisor `userId` (the `calendar_connections.userId` / `meetings.createdBy`).

### R-13 — Backoff, N = 5, transient vs permanent

- **Max attempts per job:** 5 (initial try + retries). After 5 failures → `dead_lettered`; stop automatic retries.
- **Backoff:** exponential, first delay **~30 seconds**, cap **~15 minutes**.
- **Transient** (retry until N): network errors, HTTP 429, HTTP 5xx.
- **Permanent** (may short-circuit to `dead_lettered` before N): revoked or expired auth that cannot refresh; HTTP 404 on update/delete of a missing remote event; HTTP 4xx that means the payload is invalid (not 429). Revoked/expired auth **must still** produce the advisor-visible warning (R-15) even when short-circuited.
- **Delete-mirror jobs** (product cancelled a meeting **while still connected**) use this same retry/dead-letter path. **Disconnect cleanup** does not (R-8).

### R-14 — Dead-letter is inspectable without a new UI

Persistence + structured logs are enough for internal ops/support. No admin/ops UI, no email, no Slack, no push in this slice. Logs for leftover remote events on disconnect (R-8) and for jobs entering `dead_lettered` must include advisor user id, meeting id, provider, attempt count, and a truncated error (no raw tokens).

### R-15 — Advisor-visible non-blocking warning

Show a warning when **either**:

- at least one mirror job for that advisor is `dead_lettered`, **or**
- the connection’s auth is unusable (refresh failed / revoked / expired) so pushes cannot proceed.

**Surface:** the same calendar-connection / settings entry point #2537 uses to show connected account + disconnect (today’s API: `GET /api/calendar/providers` must expose enough for the client to render this; e.g. a per-connection or per-advisor `syncWarning` boolean + message). One banner/state **per advisor**, not per meeting.

**Normative copy**

- Heading: `Calendar sync incomplete`
- Body: `Some meetings could not be copied to your connected calendar. Meetings in Builderforce are still correct. You can disconnect and reconnect to try again, or keep using meetings as usual.`
- a11y: `role="status"` (or equivalent live region). Not a modal. Not a `window.alert`.

The warning **must not** block meeting CRUD, scheduling, navigation, or disconnect.

### R-16 — Warning clears

Hide the warning when **all** of:

- there are no `dead_lettered` jobs remaining for that advisor, **and**
- the connection is healthy: a successful mirror push has occurred **or** a successful reconnect + backfill enqueue completed with no remaining DLQ items.

Successful reconnect (R-10) cancels/supersedes that advisor’s prior DLQ so a healthy reconnect can clear the banner without ops intervention.

### R-17 — Host, tenant, providers

- Host = `meetings.createdBy` = connecting `calendar_connections.userId`.
- All job writes and mapping-column writes stay in the **advisor’s tenant**.
- Do not enqueue another tenant’s meetings or another user’s meetings.
- Providers: existing `google` and `microsoft` adapters only. No new providers. No provider-agnostic redesign.

### R-18 — Invariants this slice must not break

- Product CRUD remains authoritative. Calendar write failure never fails meeting create/update/delete.
- One-way product → calendar only. No calendar → product writes, no conflict resolution.
- Eligibility, field mapping, and `calendar_event_id` ownership unchanged from #2537 except skip-if-id (R-4) and clear-on-disconnect (R-8).
- No client calendars, no advisee-facing mirrors, no notifications, no advisor-configurable lookback, no guaranteeing remote event removal on disconnect.

## D-0 — Architecture Overview

This ticket introduces three new concerns into the calendar mirror subsystem:

| Layer | What it adds |
|---|---|
| **Persistence** | `calendar_mirror_jobs` table — one row per `(userId, meetingId, operation)` — with state `pending | in_progress | succeeded | failed | dead_lettered`, attempt counter, and next-retry-at timestamp. |
| **Backfill** | Trigger on successful OAuth callback: after `upsertCalendarGrant`, select eligible advisory meetings and INSERT … ON CONFLICT DO NOTHING mirror jobs. |
| **Disconnect cleanup** | Capture grant + product-created `calendarEventId` rows, destroy the `calendar_connections` row (R-7), return 204, then fire-and-forget remote deletes + clear mapping columns. |
| **Retry worker** | A cron-sweep function (`sweepCalendarMirrors`) that picks up `pending|failed` jobs whose `next_retry_at` has passed, enforces per-advisor concurrency via a lightweight advisory-lock keyed on `userId`, calls `pushMeetingEvent` / `deleteMeetingEvent`, increments attempts, and either succeeds or transitions to `failed` (with next backoff) or `dead_lettered`. |
| **Warning API** | `GET /api/calendar/providers` gains a `sync: { warning, message }` per connection, derived from `EXISTS (SELECT 1 FROM calendar_mirror_jobs WHERE userId = … AND status = 'dead_lettered')` OR unrefreshable grant detection. |

**Invariant (unchanged):** Product CRUD (`POST|PATCH|DELETE /api/meetings`) is authoritative. Calendar write failure must never fail the meeting operation. The mirror job is enqueued and the CRUD handler returns success before the remote event is confirmed.

**Dependency baseline:** All D-sections reference the verified-as-is main from the BA:

- `meetings` table with columns `id`, `tenantId`, `kind`, `scheduledAt`, `status`, `createdBy` (the advisor/host), `calendarProvider`, `calendarEventId`, `calendarHtmlLink`.
- `calendarConnections` table with columns `id`, `tenantId`, `userId`, `provider`, `accountEmail`, `calendarId`, `tokenEnc`, `tokenIv`, `accessToken`/`refreshToken`/`expiresAt`/`scope`.
- `pushMeetingEvent(db, env, tenantId, organizerId, input) → {provider, eventId, htmlLink} | null` (today: returns null on ANY failure — no job row).
- `deleteMeetingEvent(db, env, tenantId, organizerId, provider, eventId)` (today: fire-and-forget, catches + `reportCaughtError`).
- Provider interface: `CalendarProvider` with `createEvent`, `deleteEvent`, `listUpcoming`, `freeBusy`.
- Providers: `google` and `microsoft` only.
- Eligibility from #2537: `kind = 'advisory'`, `scheduledAt IS NOT NULL`, `status ≠ 'cancelled'`, host has a connected calendar in same tenant.

## D-1 — Job Persistence: `calendar_mirror_jobs`

```sql
CREATE TABLE calendar_mirror_jobs (
  id            UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  tenant_id     INTEGER NOT NULL REFERENCES tenants(id) ON DELETE CASCADE,
  user_id       TEXT NOT NULL,          -- advisor who owns the calendar
  meeting_id    UUID NOT NULL REFERENCES meetings(id) ON DELETE CASCADE,
  operation     TEXT NOT NULL CHECK (operation IN ('create', 'update', 'delete')),
  status        TEXT NOT NULL DEFAULT 'pending'
                  CHECK (status IN ('pending', 'in_progress', 'succeeded', 'failed', 'dead_lettered')),
  attempt       INTEGER NOT NULL DEFAULT 0,
  max_attempts  INTEGER NOT NULL DEFAULT 5,
  next_retry_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  last_error    TEXT,                    -- truncated error (no raw tokens)
  created_at    TIMESTAMPTZ NOT NULL DEFAULT now(),
  updated_at    TIMESTAMPTZ NOT NULL DEFAULT now()
);

-- Idempotency: at most one OPEN job per (userId, meetingId, operation).
-- "Open" = status IN ('pending', 'in_progress', 'failed').
-- Succeeded/dead_lettered jobs are not open, so a new one can be created.
CREATE UNIQUE INDEX idx_calendar_mirror_open_job
  ON calendar_mirror_jobs (user_id, meeting_id, operation)
  WHERE status IN ('pending', 'in_progress', 'failed');

-- Sweep index: find jobs ready to retry.
CREATE INDEX idx_calendar_mirror_sweep
  ON calendar_mirror_jobs (status, next_retry_at)
  WHERE status IN ('pending', 'failed');

-- Warning query: find dead-lettered jobs per advisor.
CREATE INDEX idx_calendar_mirror_dead_letter
  ON calendar_mirror_jobs (user_id)
  WHERE status = 'dead_lettered';
```

**Why a dedicated table (not webhook reuse):** The webhook delivery engine (`webhookService.ts`, `WEBHOOK_MAX_ATTEMPTS = 6`, `webhookRetryDelaySec`) is purpose-built for outbound HTTP POST to user-registered URLs with a signature header, retrying until the subscriber returns 2xx. Calendar mirror is a different shape:

- The "deliverable" is a provider API call (`createEvent` / `deleteEvent` on Google/Microsoft), not an HTTP POST to a user-supplied URL.
- Isolation key is `userId` (advisor), not `subscriptionId`.
- Max attempts = 5 (not 6), backoff starts ~30s (not the webhook curve).
- Permanent-error short-circuit logic (revoked token, 404 on delete) has no webhook analog.
- A dead-lettered calendar job still needs to surface as a warning on `GET /providers`, not sit in an opaque webhook delivery log.

**Do not reuse the webhook emitter.** A new sweep `sweepCalendarMirrors` is the right call.

**Schema file placement:** `api/src/infrastructure/database/schema/calendarMirror.ts` (new file), registered in the Drizzle schema barrel.

**Migration number:** To be assigned by the developer following the project's migration convention (likely `0XXX_calendar_mirror_jobs.sql`). The BA's verified-as-is does not report an existing migration number — developer assigns it.

## D-2 — Connect Backfill Trigger

### D-2.1 — Where the trigger lives

`GET /api/calendar/callback/:provider` in `calendarRoutes.ts`. Today the success path is:

```
upsertCalendarGrant(…) → redirect ?calendar=connected
```

The new path:

```
upsertCalendarGrant(…) → enqueueBackfill(…) → redirect ?calendar=connected
```

### D-2.2 — `enqueueBackfill` function

New export from `calendarService.ts`:

```ts
export async function enqueueBackfill(
  db: Db,
  tenantId: number,
  userId: string,
): Promise<number> // returns count of jobs enqueued
```

Implementation:

1. Query eligible meetings (D-2.3 selection).
2. For each eligible meeting, INSERT INTO `calendar_mirror_jobs`:
   - `tenant_id = tenantId`, `user_id = userId`, `meeting_id = meeting.id`, `operation = 'create'`, `status = 'pending'`, `attempt = 0`, `max_attempts = 5`, `next_retry_at = now()`.
   - Use `ON CONFLICT (user_id, meeting_id, operation) WHERE status IN ('pending','in_progress','failed') DO NOTHING` to satisfy R-6 (idempotent enqueue — at most one open job).
3. Return the count of rows actually inserted.

**Error handling:**

- If the SELECT fails: log + reportCaughtError, return 0. The connect redirect still succeeds (R-5).
- If the INSERT batch partially fails: the ON CONFLICT DO NOTHING safe-guards against duplicates; partial insert is acceptable.
- If the whole INSERT fails: log + reportCaughtError. The connection is not rolled back (R-5).

### D-2.3 — Backfill Selection Query

```sql
SELECT m.id, m.scheduled_at
FROM meetings m
JOIN calendar_connections c
  ON c.user_id = m.created_by
 AND c.tenant_id = m.tenant_id
 AND c.provider IS NOT NULL   -- provider is already set on the connection
WHERE m.tenant_id   = $tenantId
  AND m.created_by  = $userId
  AND m.kind        = 'advisory'
  AND m.status     != 'cancelled'
  AND m.scheduled_at IS NOT NULL
  AND m.scheduled_at >= now() - INTERVAL '1 day'
  AND m.calendar_event_id IS NULL
```

**Notes:**

- The JOIN on `calendar_connections` guarantees the host (createdBy) is connected (same tenant + userId). The connection was just upserted in the same request, so this always matches at least the just-connected row.
- `calendar_event_id IS NULL` enforces R-4 (skip already-mirrored).
- `scheduled_at >= now() - 1 day` enforces R-3 (lookback window).
- `kind = 'advisory'` enforces R-2 eligibility (#2537 rule). If #2536 has not landed and `advisory` is not yet in the `meetings.kind` CHECK, the query returns 0 rows — correct behavior, no crash.
- Past-but-still-in-lookback meetings are backfilled (R-2: "start within the lookback or in the future").
- Null `scheduled_at` rows are never selected (no calendar event without a date).

### D-2.4 — Why enqueue, not synchronously push

The connect callback is a browser redirect. A synchronous `createEvent` for N meetings (potentially dozens) would:

- Make the redirect latency proportional to N × (provider API latency).
- Risk a provider timeout that kills the whole callback, leaving the connection in an indeterminate state.
- Violate R-5 (connect stays success-oriented).

Enqueuing is an INSERT … SELECT that runs in a single DB round-trip. The sweep processes jobs asynchronously.

## D-3 — Disconnect Cleanup

### D-3.1 — Flow (capture → destroy → fire-and-forget)

`DELETE /api/calendar/connections/:id` in `calendarRoutes.ts`. Today:

```
DELETE FROM calendar_connections WHERE id = … AND tenant_id = … AND user_id = … → 204
```

New flow:

```
1. Read the connection row (to capture userId, provider, tenantId).
2. SELECT meeting_id, calendar_event_id, calendar_provider, calendar_html_link
   FROM meetings WHERE created_by = … AND tenant_id = … AND calendar_event_id IS NOT NULL.
3. DELETE FROM calendar_connections WHERE id = … (destroy local row + tokens).
4. Return 204 to the advisor.        ← RESPONSE ENDS HERE
5. For each snapshotted row:
   a. Best-effort: deleteEvent(token, calendarId, eventId) using the snapshotted grant.
   b. Regardless of outcome: UPDATE meetings SET calendar_event_id = NULL,
      calendar_provider = NULL, calendar_html_link = NULL WHERE id = …
```

### D-3.2 — Grant snapshot

Step 1 must capture `tokenEnc`, `tokenIv`, `provider`, `calendarId` before the row is deleted. The snapshot is held in-memory for step 5; it is never persisted.

If the grant is unreadable (sealed blob that won't open, or missing both sealed and legacy columns), skip step 5 entirely: log "disconnect with unreadable grant — remote events not deleted" and still clear the mapping columns (step 5b). The disconnect succeeds either way (R-7).

### D-3.3 — Fire-and-forget semantics

Step 5 runs **after** the 204 response. Implementation options (developer chooses):

- **Option A (preferred, simple):** `setTimeout`-style deferred work within the request lifecycle. Acceptable because Cloudflare Workers / edge runtimes keep the isolate alive briefly after the response is sent.
- **Option B:** Enqueue a special "disconnect cleanup" batch that a lightweight worker picks up. Overkill for this slice — the remote deletes are fire-and-forget and must not enter the N-retry/DLQ loop.

Step 5 failures are logged via `reportCaughtError` with `source: "calendar/disconnect-cleanup"`, `userId`, `provider`, and a count of failed vs successful deletes. No DLQ row (R-8: "Failed disconnect deletes do not enter the N-retry / dead-letter loop").

### D-3.4 — Mapping-column clearing (step 5b)

After every remote delete attempt (success, 404, other failure), clear:

```sql
UPDATE meetings SET
  calendar_event_id  = NULL,
  calendar_provider  = NULL,
  calendar_html_link = NULL
WHERE id = $meetingId
```

This runs even when the remote delete was skipped (unreadable grant). The product no longer claims ownership of those remote events. Leftover events on the provider are accepted (R-8).

## D-4 — Retry Sweep: `sweepCalendarMirrors`

### D-4.1 — Invocation

A cron-sweep function, following the pattern of the existing webhook sweep (`webhookService.ts`). It is called periodically (e.g. every 30s via a cron trigger on the worker). The sweep processes at most `CALENDAR_MIRROR_SWEEP_BATCH = 100` jobs per tick.

### D-4.2 — Algorithm

```
1. SELECT * FROM calendar_mirror_jobs
   WHERE status IN ('pending', 'failed')
     AND next_retry_at <= now()
   ORDER BY next_retry_at ASC
   LIMIT CALENDAR_MIRROR_SWEEP_BATCH
   FOR UPDATE SKIP LOCKED

2. Group by user_id (advisor).
   For each group, process jobs sequentially within the group.
   Different groups (advisors) can be processed concurrently (R-12).

3. For each job:
   a. SET status = 'in_progress', attempt = attempt + 1, updated_at = now()
   b. Call pushMeetingEvent (for create/update) or deleteMeetingEvent (for delete)
   c. On success (eventId returned / delete succeeded):
      - For create: UPDATE meetings SET calendar_provider, calendar_event_id,
        calendar_html_link FROM the result
      - SET status = 'succeeded', updated_at = now()
   d. On transient failure (network error, 5xx, 429):
      - If attempt < max_attempts:
          SET status = 'failed', next_retry_at = now() + backoff_delay(attempt),
          last_error = truncated error
      - Else:
          SET status = 'dead_lettered', last_error = truncated error
   e. On permanent failure (revoked token, 404 on update/delete, 400 not-429):
      - SET status = 'dead_lettered', last_error = truncated error
      - (May short-circuit before N per R-13)
```

### D-4.3 — Per-advisor isolation (R-12)

Within a sweep tick, jobs for different advisors are processed concurrently (e.g., `Promise.all` over advisor groups). Within a single advisor's group, jobs are processed sequentially so that:

- A single advisor's provider rate-limit or outage doesn't block other advisors.
- The sequential processing within an advisor avoids thundering-herd on the same OAuth token (which might be refreshed mid-batch).

The grouping key is `user_id` (the `calendar_connections.userId` = `meetings.createdBy`).

If this codebase uses a job queue (BullMQ, etc.), the developer may instead enqueue per-advisor jobs with a `userId`-based rate limiter. The PRD does not prescribe the queue implementation — the isolation guarantee is what matters.

### D-4.4 — Backoff function

```ts
const BACKOFF_BASE_MS = 30_000;   // ~30s
const BACKOFF_CAP_MS  = 900_000;  // ~15m

function backoffDelay(attempt: number): number {
  // attempt is 1-based (attempt 1 = first retry after the initial try)
  const delay = BACKOFF_BASE_MS * Math.pow(2, attempt - 1);
  return Math.min(delay, BACKOFF_CAP_MS);
}
```

Attempt timeline (maxAttempts = 5):

| Attempt | Action | Delay before next |
|---------|--------|-------------------|
| 0 | Initial try (synchronous in CRUD or sweep) | — |
| 1 | First retry | 30s |
| 2 | Second retry | 1m |
| 3 | Third retry | 2m |
| 4 | Fourth retry | 4m |
| 5 | Fifth retry (last) | 8m → dead_lettered |

Total window: ~15m 30s from first failure to dead-letter.

### D-4.5 — Transient vs permanent classification

```ts
function classifyError(error: unknown): 'transient' | 'permanent' {
  // Extract status code from the error thrown by jsonFetch:
  // "Calendar API 429: …" or "Calendar API 503: …"
  const msg = String(error);

  // HTTP 429 — rate limit. Retry with backoff.
  if (/429/.test(msg)) return 'transient';
  // HTTP 5xx — server error. Retry.
  if (/5\d{2}/.test(msg)) return 'transient';
  // Network error (fetch threw without a status). Retry.
  if (!/\d{3}/.test(msg)) return 'transient';

  // HTTP 404 — remote event gone. No point retrying.
  if (/404/.test(msg)) return 'permanent';
  // HTTP 400/401/403 — payload rejected, auth revoked.
  if (/40[013]/.test(msg)) return 'permanent';

  // Default: retry (conservative).
  return 'transient';
}
```

**Auth failure edge case (R-13):** A revoked/expired token that cannot be refreshed is caught by `freshAccessToken` returning `null` inside `pushMeetingEvent`. This is a permanent failure — the job goes to `dead_lettered` immediately (no point retrying without a re-connect). The dead-letter status triggers the R-15 warning.

## D-5 — Meeting CRUD → Always-Enqueue

### D-5.1 — Create (`POST /api/meetings`)

Today: calls `pushMeetingEvent` synchronously, writes `calendarProvider`/`calendarEventId`/`calendarHtmlLink` only on success, returns meeting.

Change: **After** inserting the meeting row (so we have the `meeting.id`):

1. If `kind = 'advisory'` AND host has a connected calendar: INSERT a `calendar_mirror_jobs` row (operation = `'create'`, status = `'pending'`). The sweep picks it up.
2. Optionally, still attempt a synchronous `pushMeetingEvent` inside the request for the happy path — but:
   - The CRUD handler **must not** await provider success as a condition of 2xx.
   - If the synchronous push succeeds, mark the job `succeeded` and write mapping columns.
   - If the synchronous push fails, the job stays `pending`/`failed` and the sweep retries it.
3. The meeting create returns 201 regardless of mirror success.

**Developer choice:** The simplest correct implementation is to ENQUEUE ONLY (no synchronous push) and let the sweep handle the first attempt. This keeps the CRUD handler fast and eliminates the dual-path complexity. If the developer prefers to attempt a synchronous first push for lower latency on the happy path, they must ensure it is best-effort and never blocks the 201.

### D-5.2 — Cancel (`POST /api/meetings/:id/cancel`)

Today: best-effort `deleteMeetingEvent` if `calendarEventId` is set, then marks meeting cancelled.

Change:

1. If `calendarEventId` IS SET: INSERT a `calendar_mirror_jobs` row (operation = `'delete'`). The sweep calls `deleteMeetingEvent`.
2. Optionally attempt a synchronous delete inside the request (same "never blocks 2xx" rule as create).
3. Mark meeting cancelled. Return 2xx.

### D-5.3 — Update (`PATCH /api/meetings/:id`)

Today: does **not** update the remote event (update-mirror belongs to #2537).

When #2537 lands update-mirror: enqueue a `calendar_mirror_jobs` row (operation = `'update'`) using the same always-enqueue pattern. Until then, PATCH does not touch the mirror subsystem.

## D-6 — Reconnect Supersedes DLQ (R-10)

When an advisor reconnects after disconnect (`GET /api/calendar/callback/:provider` → `upsertCalendarGrant`):

```sql
-- Cancel all dead-lettered jobs for this advisor.
UPDATE calendar_mirror_jobs
SET status = 'succeeded',    -- "superseded", not dead_lettered
    last_error = NULL,
    updated_at = now()
WHERE user_id = $userId
  AND status = 'dead_lettered';
```

Then run `enqueueBackfill` (D-2) as normal.

**Rationale:** A successful reconnect means the advisor has a fresh grant. Prior dead-lettered jobs were likely caused by the old (disconnected) grant. Superseding them prevents the R-15 warning from persisting after a healthy reconnect. The jobs are marked `succeeded` (not deleted) so the DLQ audit trail is preserved without triggering the warning.

The `enqueueBackfill` that follows will create new jobs for eligible meetings that still lack `calendarEventId` (R-10).

## D-7 — `GET /api/calendar/providers` Warning (R-15)

### D-7.1 — Response shape change

Today:

```json
{
  "providers": ["google", "microsoft"],
  "connections": [
    { "id": 1, "provider": "google", "accountEmail": "a@b.com", "calendarId": "primary" }
  ]
}
```

New:

```json
{
  "providers": ["google", "microsoft"],
  "connections": [
    {
      "id": 1,
      "provider": "google",
      "accountEmail": "a@b.com",
      "calendarId": "primary",
      "sync": {
        "warning": false
      }
    }
  ]
}
```

When warning is active:

```json
{
  "sync": {
    "warning": true,
    "message": "Calendar sync incomplete"
  }
}
```

### D-7.2 — How `sync.warning` is computed

For each connection returned by the query, compute:

```ts
const deadLetterCount = await db.select({ count: count() })
  .from(calendarMirrorJobs)
  .where(and(
    eq(calendarMirrorJobs.userId, conn.userId),
    eq(calendarMirrorJobs.status, 'dead_lettered')
  ));

const grantHealthy = await freshAccessToken(db, env, conn).then(t => t !== null);

const warning = deadLetterCount > 0 || !grantHealthy;
```

**`message` value:** The literal string `"Calendar sync incomplete"` when `warning === true`. The client is responsible for rendering the full normative copy (heading + body from R-15). The API only provides the boolean + a short message key the client can match on.

**Performance note:** The `freshAccessToken` call in `GET /providers` is already in the hot path today (the `/events` endpoint calls it per connection). The DLQ count uses the partial index `idx_calendar_mirror_dead_letter`, so it is a fast index-only scan. For advisors with no dead-lettered jobs, the overhead is negligible.

### D-7.3 — Client rendering contract

The frontend reads `sync.warning` per connection. When `true`:

- Render the R-15 normative copy: heading `Calendar sync incomplete`, body as specified.
- Use `role="status"` (or equivalent live region).
- Do **not** block meeting CRUD, scheduling, navigation, or disconnect (R-15).

The frontend change is in the calendar settings / connection surface (the same page that consumes `GET /api/calendar/providers` today). This is a single banner per advisor, not per meeting.

## D-8 — Warning Clear (R-16)

The warning hides when `sync.warning` returns `false`. This happens when:

1. **No dead-lettered jobs remain** for that advisor (all have been superseded by reconnect per D-6, or manually cleared — no manual clear UI in this slice, but the data model supports it).
2. **Connection is healthy** — `freshAccessToken` succeeds.

The client re-fetches `GET /api/calendar/providers` to re-evaluate. No push/WebSocket needed — the warning is polled.

**Clear path A (reconnect):** Advisor disconnects → reconnects. D-6 supersedes DLQ. D-2 enqueues backfill. If backfill succeeds and no DLQ remains, `sync.warning` becomes `false`.

**Clear path B (automatic recovery):** A transient provider outage resolves. The sweep successfully pushes the last `failed` job → `succeeded`. No DLQ rows remain. Grant is healthy. `sync.warning` becomes `false` on next poll.

## D-9 — Invariant Enforcement (R-18)

### D-9.1 — Product CRUD is authoritative

The mirror job is always enqueued AFTER the meeting row is committed. The meeting create/update/cancel returns 2xx before the mirror job is processed by the sweep. Calendar write failure:

- Does NOT roll back the meeting row.
- Does NOT set meeting status to an error state.
- Does NOT prevent the advisor from using the meeting.
- Results in a `failed` job that will retry (D-4) or `dead_letter` (D-4.2e).

### D-9.2 — One-way only

`calendar_mirror_jobs` operations are `create`, `update`, `delete` — all product → calendar. There is no `import` operation. The sweep never reads from the provider calendar and writes to meetings (except updating mapping columns after a successful `create`). The provider calendar is never treated as source of truth.

### D-9.3 — Mapping column ownership

`calendarEventId` is only written on successful `createEvent` in the sweep (or synchronous first attempt). It is only cleared on:

- Successful disconnect cleanup (D-3.4).
- A failed delete during disconnect cleanup (still cleared — we no longer claim ownership).

It is NEVER overwritten by a second `create` (R-4: `calendar_event_id IS NULL` gate on backfill; ON CONFLICT DO NOTHING on the idempotency index). It is NEVER set to a value we did not receive from the provider.

## D-12 — Error Classification Reference

For the sweep's `classifyError` (D-4.5) and the sync warning (D-7):

| Scenario | Classification | Job outcome | Warning |
|----------|---------------|-------------|---------|
| Network timeout / DNS failure | transient | Retry up to N | No (until DLQ) |
