# PRD: Late-connect calendar backfill, disconnect cleanup, retry & advisor warning

**Priority:** P1  
**Parent:** #2532  
**Depends on:** #2537 (P0 advisory calendar mirror)  
**Source of truth:** Product CRUD (advisory meetings). Calendar is a one-way outbound mirror.

## Problem & Goal

P0 (#2537) mirrors advisory meetings to a connected advisor calendar via `pushMeetingEvent`, but three gaps remain:

1. **Late connect has no backfill.** Connecting a calendar after eligible meetings already exist does not enqueue mirrors. Those meetings never appear on the calendar unless they are later mutated.
2. **Disconnect is connection-row only.** Disconnect deletes `calendar_connections` and leaves product-created remote events in place with no documented policy.
3. **Failures are swallowed.** `pushMeetingEvent` errors are not retried and never surface to the advisor. Sync can be silently stale indefinitely.

**Goal:** On connect, enqueue a one-way backfill of that advisor’s upcoming eligible meetings. On disconnect, apply a documented best-effort remote cleanup that never blocks. Mirror pushes use per-advisor retry with backoff and a dead-letter after N failures, then show a non-blocking in-product sync warning. Product CRUD remains authoritative; calendar write failures must not fail meeting create/update/delete.

## Target users / ICP roles

- **Advisor (primary):** Connects/disconnects their own calendar; expects existing upcoming meetings to appear after connect; must see a warning if mirroring has given up—not a blocking error.
- **Internal ops / support (secondary):** Needs a dead-letter they can inspect when an advisor’s mirror is stuck; no new admin UI in this slice.

Clients do not connect calendars in this slice.

## Scope

In scope for this P1:

1. **Connect backfill.** When an advisor successfully connects a calendar, enqueue mirror jobs for that advisor’s upcoming eligible advisory meetings. Default lookback is **1 day** (meetings with start ≥ now − 1 day). Skip rows that already have `calendar_event_id`. Same eligibility and payload rules as #2537.
2. **Disconnect policy (documented + implemented).** Disconnect always succeeds locally. Best-effort delete of **product-created** remote events (those we stored `calendar_event_id` for). Never block or roll back disconnect on remote failure. Leave remote events that we did not create.
3. **Per-advisor retry + dead-letter.** Failed mirror pushes retry with exponential backoff, scoped per advisor (one advisor’s failures do not stall others). After **N = 5** failed attempts on a given meeting-mirror job, move it to a dead-letter and stop retrying automatically.
4. **Advisor-visible sync warning.** After a job is dead-lettered (retries exhausted), show a non-blocking warning in the advisor’s calendar-connection / settings surface. Product CRUD and navigation stay fully usable. Clearing the warning when a later successful sync for that advisor occurs (e.g. reconnect or a subsequent successful push) is required.

Lookback is a server-side default (1 day), not an advisor-facing control in this slice.

## Functional requirements

### 1. Connect backfill

- Trigger: calendar connection reaches a connected/authorized state for an advisor (same success path as #2537 connect).
- Select that advisor’s advisory meetings that are **eligible to mirror** under #2537 rules, with `start_at >= now() - lookback` (default lookback **1 day**), and `calendar_event_id IS NULL`.
- Enqueue one mirror job per selected meeting (or an equivalent per-advisor batch that still processes meetings independently for retry). Do not synchronously push in the connect request path.
- Skip meetings that already have `calendar_event_id` (no overwrite, no duplicate remote create).
- Past meetings older than the lookback window are not backfilled.
- Connect UX remains success-oriented; backfill enqueue failure is logged and must not fail the connection itself. Enqueue failure should use the same retry/warning machinery where a job record can be created; if no job can be created, log and do not strand the connection.

### 2. Disconnect cleanup

**Policy (normative):**

- Disconnect **always** deletes/deactivates the local `calendar_connections` row (and any local tokens) and returns success to the advisor.
- After local disconnect, **best-effort** delete remote events we created: for this advisor, each stored `calendar_event_id` is deleted on the provider. Then clear `calendar_event_id` on those meeting rows (including when remote delete fails or the event is already gone).
- Remote delete failures **must not** block, retry-loop, or roll back disconnect. Failed remote deletes are logged; leftover remote events are accepted.
- Do not delete remote events that were not created by this product (no `calendar_event_id` we own).
- Reconnect after disconnect is a new connect: backfill applies again only to eligible rows still lacking `calendar_event_id`.

### 3. Retry, backoff, dead-letter

- `pushMeetingEvent` (create/update/delete of the mirrored event) must not swallow failures. Persist job state: pending / in_progress / succeeded / failed / dead_lettered.
- Retry **per advisor**: backoff and concurrency are isolated so advisor A’s provider errors do not delay advisor B.
- Backoff: exponential, starting at ~30s, cap ~15m, **max 5 attempts** per job (initial try + retries). Transient provider/network errors are retried; permanent errors (revoked token, 404 on update of missing remote event, payload rejected as invalid) may short-circuit to dead-letter before N if they cannot succeed without a new connect or a product-side change—but revoked/expired auth must still produce the advisor-visible warning.
- After N failures (or short-circuit permanent failure): mark dead-lettered; stop automatic retries.
- Meeting create/update/delete in product **never** waits on calendar success and **never** fails because the mirror failed.
- Delete-mirror jobs (meeting deleted in product while connected) use the same retry/dead-letter path. Disconnect cleanup is explicitly best-effort and **not** required to use the full N-retry loop if that would delay disconnect; it may fire-and-forget remote deletes.

### 4. Advisor-visible warning

- When at least one mirror job for the advisor is dead-lettered (or auth is revoked/expired and pushes cannot proceed), show a non-blocking warning on the calendar connection surface (and equivalent settings entry point used in #2537).
- Copy must convey that calendar sync is delayed or incomplete and that meetings in the product are still correct. Do not block CRUD, scheduling, or disconnect.
- Warning is per advisor, not per meeting, in this slice (one banner/state is enough).
- Clear the warning when there are no dead-lettered jobs for that advisor and the connection is healthy (successful push or successful reconnect + backfill enqueue with no remaining DLQ items).
- No email/push notification in this slice.

### 5. Invariants carried from #2537

- One-way product → advisor calendar only.
- Eligibility, field mapping, and `calendar_event_id` ownership unchanged except as needed to skip already-mirrored rows on backfill and to clear ids on disconnect.
- No new calendar providers.

## Acceptance criteria

1. **Late connect backfill.** Given an advisor with eligible advisory meetings starting in the future and/or within the past 1 day, and no `calendar_event_id` on those rows, after a successful calendar connect those meetings are enqueued for mirror and remote events are created. Meetings older than 1 day are not enqueued. Rows that already have `calendar_event_id` are not enqueued and are not duplicated on the provider.
2. **Connect is not blocked.** Connect succeeds even if backfill enqueue or subsequent pushes fail; failures follow retry/warning, not connect rollback.
3. **Disconnect never blocks.** Disconnect removes the local connection (and tokens) and returns success if the provider is down, deletes fail, or there are many remote events.
4. **Best-effort remote delete.** On disconnect, the system attempts to delete product-created remote events and clears local `calendar_event_id` values. Events we did not create remain. Leftover remote events after failed deletes are acceptable and logged.
5. **Reconnect backfill.** After disconnect + reconnect, eligible meetings without `calendar_event_id` are backfilled; meetings that somehow retained an id are skipped.
6. **Retry isolation.** A failing advisor’s mirror jobs retry with backoff and do not prevent other advisors’ jobs from running.
7. **Dead-letter after N.** A job that fails 5 times (or hits a permanent error) is dead-lettered and is not retried automatically.
8. **CRUD unblocked.** Meeting create/update/delete succeeds and remains correct in product regardless of mirror success, retry, or dead-letter.
9. **Warning visible.** After retries exhaust (or auth is unusable), the advisor sees a non-blocking sync warning on the calendar connection/settings surface. They can continue using meetings and can disconnect.
10. **Warning clears.** After a healthy connection and no remaining dead-lettered jobs for that advisor, the warning is not shown.
11. **No scope creep.** Behavior is advisor calendars only, existing provider(s) from #2537 only, one-way mirror only.

## Out of scope

- Two-way sync (calendar → product), conflict resolution, or treating the calendar as source of truth
- Client (advisee) calendar connect or client-facing mirrors
- New calendar providers or provider-agnostic redesign
- Advisor-configurable lookback / backfill window
- Historical backfill beyond the 1-day lookback
- Recurring-event expansion changes beyond what #2537 already ships
- Email, push, or Slack notifications for sync failure
- Admin/ops UI for the dead-letter (persistence + logs are enough)
- Blocking disconnect on incomplete remote cleanup
- Changing product meeting CRUD semantics or eligibility rules except skip-if-`calendar_event_id` and clear-on-disconnect
- Guaranteeing remote event removal on disconnect (best-effort only)

## Requirements

_Owned by the business-analyst (Ada) · 2026-09-17 · grounded in `seanhogg/builderforce.ai` main + parent #2537 PRD._

This slice does **not** change who is source of truth (product CRUD) or which meetings are eligible to mirror (that is #2537). It closes three P0 gaps: late-connect has no enqueue, disconnect is local-row-only, and `pushMeetingEvent` swallows errors with no retry or advisor-visible warning.

### Verified as-is on main (binding constraints, not design)

These are facts the architect/developer must reconcile; they are the reason this ticket exists.

1. **Connect does not backfill.** `GET /api/calendar/callback/:provider` (`api/src/presentation/routes/calendarRoutes.ts`) calls `upsertCalendarGrant` then redirects `?calendar=connected`. No selection of existing meetings, no enqueue.
2. **Disconnect is connection-row only.** `DELETE /api/calendar/connections/:id` deletes the `calendar_connections` row (grant + tokens live on that row) and returns 204. It does not read `meetings.calendar_event_id`, does not call `deleteEvent`, and does not clear mapping columns.
3. **Pushes swallow failures.** `pushMeetingEvent` (`api/src/application/calendar/calendarService.ts`) returns `null` on missing connection, missing provider, unreadable/unrefreshable token, **and** on `createEvent` throw (`catch { return null }`). No job row, no retry, no advisor signal. `deleteMeetingEvent` is fire-and-forget (`catch` + `reportCaughtError`).
4. **Live create is in-request and kind-agnostic.** `POST /api/meetings` mirrors any scheduled meeting (any `KINDS` value) synchronously via `pushMeetingEvent`, then writes `calendar_provider` / `calendar_event_id` / `calendar_html_link` only on success. `POST /:id/cancel` best-effort deletes if those columns are set. `PATCH /:id` does **not** update the remote event (update-mirror is #2537; this ticket’s retry machine must apply to it once #2537 writes it).
5. **Ownership token already exists.** `meetings.calendar_event_id` (plus `calendar_provider`, `calendar_html_link`) is how the product records “we created this remote event”. Host is `meetings.createdBy`. Connection is per `(userId, provider)` in the advisor’s tenant; providers are `google` | `microsoft` only.
6. **No calendar job / DLQ / warning today.** There is no `dead_letter` (or equivalent) for calendar. `GET /api/calendar/providers` returns `{ providers, connections: [{ id, provider, accountEmail, calendarId }] }` with no sync-health field. Closest retry analog in-repo is outbound webhooks (`WEBHOOK_MAX_ATTEMPTS = 6`, capped exponential backoff, cron sweep) — **do not reuse that emitter**; calendar mirror is a different job with N = 5 and ~30s/15m backoff as specified below.
7. **`kind = advisory` is not on main yet.** `meetingRoutes.ts` `KINDS` is `standup|planning|retrospective|adhoc|direct|interview|review` (`#2536` adds `advisory`). This ticket assumes #2536 + #2537 have landed eligibility; it does not register the kind.

### Dependency contract (#2537 — do not re-specify)

Carry forward unchanged except where this ticket names a delta:

- One-way product → advisor calendar. Calendar is never source of truth.
- Eligible iff: `meetings.kind = 'advisory'`, `scheduled_at IS NOT NULL`, `status ≠ 'cancelled'`, host (`createdBy`) has a connected calendar in the **same tenant**, payload/field mapping as #2537.
- Store `calendar_event_id` on successful remote create; reuse that id for update/delete; never invent ids for events we did not create.
- Product create/update/cancel HTTP succeeds even if the calendar write fails.
- Existing providers only. No client (advisee) calendars. No two-way sync.

**Deltas this ticket adds:** skip-if-`calendar_event_id` on late-connect backfill; clear mapping columns on disconnect cleanup; persist + retry + dead-letter instead of swallowing; advisor-visible warning.

### R-1 — Connect-success trigger

When a calendar connection reaches a connected/authorized state for an advisor (the same success path as #2537: grant upserted, browser redirected `?calendar=connected`), the system **enqueues** a one-way backfill of that advisor’s upcoming eligible advisory meetings. The trigger is **successful connect**, not a separate advisor action. Clients never connect calendars in this slice.

### R-2 — Backfill selection

Select meetings that are **all** of:

- `createdBy` = the connecting advisor’s `userId`
- `tenant_id` = the connecting grant’s tenant
- eligible under #2537 rules (`kind = 'advisory'`, `scheduled_at IS NOT NULL`, `status ≠ 'cancelled'`, host connected)
- `scheduled_at >= now() - 1 day` (server UTC; see R-4)
- `calendar_event_id IS NULL`

Meetings that are live or ended **remain selectable** if they still satisfy the above (start within the lookback or in the future, not cancelled, no stored id). Null `scheduled_at` rows are never selected.

### R-3 — Lookback is a server default, not a control

Lookback is **1 day**. It is not advisor-facing, not per-connection, not configurable in this slice. Meetings with `scheduled_at < now() - 1 day` are **not** enqueued. There is no historical backfill beyond that window.

### R-4 — Skip already-mirrored rows

If `calendar_event_id` is already set, **do not enqueue**, **do not overwrite**, **do not create a second remote event**. Mixed inventory is per-meeting: one stored id means “already ours”.

### R-5 — Enqueue asynchronously; connect stays success-oriented

Do **not** synchronously `createEvent` inside the OAuth callback / connect request. Enqueue one mirror job per selected meeting (or an equivalent per-advisor batch that still **retries per meeting**). The connect response/redirect remains success (`?calendar=connected`) even if enqueue or later pushes fail.

If enqueue fails: log it. If a job record **can** be created, that job uses the R-10–R-13 retry/warning machinery. If **no** job record can be created, log and **do not** strand or roll back the connection.

### R-6 — Idempotent enqueue

OAuth callback replay, double-submit, or a second connect while jobs are already pending **must not** duplicate remote events. At most one **open** (pending / in_progress / failed-retrying) job may exist per `(advisor userId, meeting id, operation)` where operation ∈ {create, update, delete}. A succeeded create that stored `calendar_event_id` is not re-enqueued as create.

### R-7 — Disconnect always succeeds locally

`DELETE /api/calendar/connections/:id` (or the #2537 equivalent) **always**:

- deletes or deactivates the local `calendar_connections` row **and** its tokens/grant for that advisor + provider
- returns success to the advisor (today: 204)

This holds if the provider is down, remote deletes fail, there are many remote events, or there are none. Disconnect **never** rolls back because cleanup failed. Disconnect **never** blocks on the network.

### R-8 — Capture grant, then destroy it, then best-effort remote delete

Tokens live on `calendar_connections` today. Remote delete after disconnect therefore **cannot** read the row after it is gone.

Normative order:

1. Snapshot the advisor’s product-created mapping rows (`calendar_event_id` + provider + calendar id) **and** whatever grant material is required to attempt provider deletes.
2. Destroy the local connection + tokens (R-7) and return success.
3. **After** local success (must not delay the response): best-effort `deleteEvent` for each snapshotted product-created id.
4. Clear `calendar_event_id`, `calendar_provider`, and `calendar_html_link` on those meeting rows **whether or not** the remote delete succeeded, including 404 / already-gone.

Leftover remote events after failed deletes are **accepted** and **logged**. Failed disconnect deletes **do not** enter the N-retry / dead-letter loop (that loop would re-require a connection the advisor just removed, and would delay or re-surface a warning for a disconnected calendar). Fire-and-forget is required here.

### R-9 — Only delete events we created

Never delete a remote event that has no stored `calendar_event_id` we own. Never enumerate the provider calendar to “clean everything”. Events the advisor created outside this product stay.

### R-10 — Reconnect is a new connect

After disconnect + reconnect, R-1–R-6 apply again. Only eligible rows **still lacking** `calendar_event_id` are backfilled. Rows that somehow retained an id are skipped (R-4). Prior dead-lettered jobs for that advisor are **superseded/cancelled** on successful reconnect so they cannot keep the warning up after a healthy new connect (R-16).

### R-11 — Persist job state; do not swallow `pushMeetingEvent` failures

Every mirror push — **create, update, and delete** of the mirrored event, from live product CRUD while connected **and** from backfill — must persist job state:

`pending` → `in_progress` → `succeeded` | `failed` | `dead_lettered`

- `failed` means “will retry” (attempts remaining).
- `dead_lettered` means “automatic retries stopped”.

Returning `null` / empty-catch without a job record is **not** allowed for a connected advisor. (No-connection remains a no-op: if the host has no calendar, there is no job.)

Meeting create/update/cancel **never** waits on calendar success and **never** fails because the mirror failed. A best-effort first attempt inside the CRUD request is allowed **only if** (a) the HTTP handler does not await provider success as a condition of 2xx, and (b) a failure still records a retryable job.

### R-12 — Per-advisor isolation

Backoff, concurrency, and failure of advisor A **must not** delay advisor B. A shared worker is acceptable if jobs are independently schedulable per advisor (no head-of-line blocking across advisors). Isolation key is the connecting advisor `userId` (the `calendar_connections.userId` / `meetings.createdBy`).

### R-13 — Backoff, N = 5, transient vs permanent

- **Max attempts per job:** 5 (initial try + retries). After 5 failures → `dead_lettered`; stop automatic retries.
- **Backoff:** exponential, first delay **~30 seconds**, cap **~15 minutes**.
- **Transient** (retry until N): network errors, HTTP 429, HTTP 5xx.
- **Permanent** (may short-circuit to `dead_lettered` before N): revoked or expired auth that cannot refresh; HTTP 404 on update/delete of a missing remote event; HTTP 4xx that means the payload is invalid (not 429). Revoked/expired auth **must still** produce the advisor-visible warning (R-15) even when short-circuited.
- **Delete-mirror jobs** (product cancelled a meeting **while still connected**) use this same retry/dead-letter path. **Disconnect cleanup** does not (R-8).

### R-14 — Dead-letter is inspectable without a new UI

Persistence + structured logs are enough for internal ops/support. No admin/ops UI, no email, no Slack, no push in this slice. Logs for leftover remote events on disconnect (R-8) and for jobs entering `dead_lettered` must include advisor user id, meeting id, provider, attempt count, and a truncated error (no raw tokens).

### R-15 — Advisor-visible non-blocking warning

Show a warning when **either**:

- at least one mirror job for that advisor is `dead_lettered`, **or**
- the connection’s auth is unusable (refresh failed / revoked / expired) so pushes cannot proceed.

**Surface:** the same calendar-connection / settings entry point #2537 uses to show connected account + disconnect (today’s API: `GET /api/calendar/providers` must expose enough for the client to render this; e.g. a per-connection or per-advisor `syncWarning` boolean + message). One banner/state **per advisor**, not per meeting.

**Normative copy**

- Heading: `Calendar sync incomplete`
- Body: `Some meetings could not be copied to your connected calendar. Meetings in Builderforce are still correct. You can disconnect and reconnect to try again, or keep using meetings as usual.`
- a11y: `role="status"` (or equivalent live region). Not a modal. Not a `window.alert`.

The warning **must not** block meeting CRUD, scheduling, navigation, or disconnect.

### R-16 — Warning clears

Hide the warning when **all** of:

- there are no `dead_lettered` jobs remaining for that advisor, **and**
- the connection is healthy: a successful mirror push has occurred **or** a successful reconnect + backfill enqueue completed with no remaining DLQ items.

Successful reconnect (R-10) cancels/supersedes that advisor’s prior DLQ so a healthy reconnect can clear the banner without ops intervention.

### R-17 — Host, tenant, providers

- Host = `meetings.createdBy` = connecting `calendar_connections.userId`.
- All job writes and mapping-column writes stay in the **advisor’s tenant**.
- Do not enqueue another tenant’s meetings or another user’s meetings.
- Providers: existing `google` and `microsoft` adapters only. No new providers. No provider-agnostic redesign.

### R-18 — Invariants this slice must not break

- Product CRUD remains authoritative. Calendar write failure never fails meeting create/update/delete.
- One-way product → calendar only. No calendar → product writes, no conflict resolution.
- Eligibility, field mapping, and `calendar_event_id` ownership unchanged from #2537 except skip-if-id (R-4) and clear-on-disconnect (R-8).
- No client calendars, no advisee-facing mirrors, no notifications, no advisor-configurable lookback, no guaranteeing remote event removal on disconnect.
