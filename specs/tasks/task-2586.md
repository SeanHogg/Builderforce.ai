# PRD: Start / Grow / Exit listing filters for Advisors

**Status:** WIP  
**Priority:** P0 (depends on #2527 stage fields)  
**Surface:** `?category=advisors` listing

## Problem & Goal

Advisor listings already store canonical stage values (`Start`, `Grow`, `Exit`) from P0 #2527, but the advisors category listing does not expose those values as filters. Seekers must scan cards or open profiles to learn whether an advisor is relevant to their stage, which hides supply, increases bounce, and under-uses the data we already persist.

**Goal:** Treat Start / Grow / Exit as first-class listing filters on `?category=advisors`, backed by the same stage fields stored in P0 #2527, so seekers can narrow the advisor inventory to the stages they care about without leaving the listing.

## Target users / ICP roles

- **Seekers** browsing advisors (founders and operators deciding who to talk to next).
- **Advisors / listing owners** whose profiles already declare one or more stages; they should not need a second data model for discovery.
- **Internal ops / growth** who need stage-qualified advisor inventory to be queryable from the public listing URL.

## Scope

- Advisors category listing only (`?category=advisors` and equivalent category routing).
- Read-only filter UI + query behavior driven by existing listing stage fields from #2527.
- URL, empty, and multi-select behavior consistent with other first-class listing filters on this surface.
- Analytics events for filter apply / clear so stage demand can be measured.

## Functional requirements

1. **Canonical values.** Filter options are exactly `Start`, `Grow`, and `Exit`, matching the stage enum stored on listings in #2527. Do not introduce aliases, extra stages, or a free-text stage filter.
2. **First-class placement.** On `?category=advisors`, Start / Grow / Exit appear as a dedicated listing filter control (same visual and interaction rank as other primary listing filters), not buried in “more filters,” chips-only, or profile-only UI.
3. **Matching.** A listing is included when **any** of its stored stage values intersects the selected filter set (OR across selected stages). Listings with no stage data are excluded when any stage filter is active.
4. **Multi-select.** Seekers may select one, two, or all three stages. Selecting all three is equivalent to “any staged advisor” and still excludes unstaged listings.
5. **URL as source of truth.** Selected stages are encoded on the listing URL (stable, shareable, back-button friendly) and restore the control on load. Deep links such as `?category=advisors` plus the stage param(s) must produce the same result set as in-UI selection.
6. **Compose with existing listing behavior.** Stage filters compose with current advisors listing sort, search, pagination, and other filters via AND across filter types. Changing stage selection resets to page 1 and refetches the listing.
7. **Empty and zero-result.** If no advisors match, show the standard listing empty state. If #2527 data is missing for a listing, it simply does not match an active stage filter; do not error the page.
8. **Category gating.** The stage filter renders only for advisors. Other categories must not show it or honor leftover stage query params as a visible control.
9. **Labels and counts (if the listing already shows facet counts).** Use the same labels as stored stages. Counts, if present on this listing, must reflect the #2527 fields and current composed query.

## Acceptance criteria

- Given an advisors listing with mixed `Start` / `Grow` / `Exit` / unstaged rows, selecting **Start** shows only listings whose #2527 stage set includes `Start`.
- Selecting **Start** and **Exit** shows listings that include Start, Exit, or both; Grow-only and unstaged listings are hidden.
- Clearing all stage selections returns the unfiltered advisors listing (other filters unchanged).
- Reloading or sharing the filtered URL restores the same selections and result set.
- Stage filter is visible and usable on `?category=advisors` at listing-filter rank; it does not appear on non-advisor category listings.
- Filter interaction does not require a profile page visit and does not write or migrate stage data.
- QA can map each visible result to the listing’s stored #2527 stage field(s) with no client-side-only matching.

## Out of scope

- Changing, adding, or backfilling stage fields (owned by #2527).
- Advisor onboarding / edit-profile UX for stages.
- New stages, custom stages, or seeker-side “I am in Start/Grow/Exit” profiling.
- Ranking, scoring, or sort changes based on stage (filter only).
- Stage filters on non-advisor categories, search global, maps, or saved-search products beyond this listing URL.
- Personalization, recommendations, or paywalling of stage-qualified supply.

## Requirements

This ticket is **compose-only, read-only filtering**. It does not write or migrate stage data (owned by P0 #2527 / #2528), does not add a listing kind, `/advisors` route, `MARKETPLACE_LISTING_KINDS` value, fifth marketplace family, SCORE/SBA affiliation, or a second stage axis.

`?category=advisors` is a **talent filter** (P0 #2529): Talent family + advisor-mode person listings. Bind the existing marketplace listing (`frontend/src/app/marketplace/MarketplacePageClient.tsx`, `CatalogToolbar`) and the existing public talent list (`GET /api/public/freelancers` / `TalentFilters` in `frontend/src/lib/freelance/talentProfile.ts`). Do not add a new list endpoint or search index.

Sibling P3 tickets (#2584 badge, #2585 location) compose with this filter; they do not implement it.

### R2 — First-class placement and category gate

### R3 — Matching (server-authoritative)

1. A listing is included when **any** of its stored P0 `stages` tokens intersects the selected filter set (**OR** across selected stages).
2. **Unstaged listings are excluded** whenever the stage filter is active (one, two, or all three chips on).
3. Selecting **all three** is “any staged advisor”: listings whose `stages` contain at least one of `start`/`grow`/`exit`. It is **not** equivalent to clearing the filter. Clearing all chips (R5) returns the unfiltered-by-stage set, **including unstaged**.
4. Examples (given mixed inventory):
   - `stage=start` → only rows whose `stages` include `start` (may also include grow/exit). Grow-only, exit-only, and unstaged are hidden.
   - `stage=start` + `stage=exit` (or `stage=start,exit`) → rows that include Start, Exit, or both. Grow-only and unstaged are hidden.
   - no `stage` param → unfiltered-by-stage (unstaged included).
5. Matching runs **on the server** as part of the existing public talent list, **only when** `category=advisors`. Client-side AND over the current page is insufficient (breaks counts, pagination, and shared URLs). QA must be able to map each visible card to that listing’s stored `#2527` `stages` field with no client-only matching.
6. If the P0 column is missing for a row (migration not applied, null, `[]`), that row simply does not match an active stage filter. **Do not error the page.**

### R4 — URL as source of truth

1. Query key: **`stage`** (singular), shared with P2’s stage axis — not a new `stages` / `journey` / `fit` key.
2. Values: `start` \| `grow` \| `exit`. Architect picks **one** serialization and uses it everywhere: repeatable `stage=start&stage=exit` **or** comma-separated `stage=start,exit`. Order-independent. Duplicate tokens collapse.
3. Reload, share, and back/forward restore the same selections and result set. Deep links `?category=advisors` plus the stage param(s) produce the same result set as in-UI selection.
4. Changing stage selection **resets `page` to 1** and refetches (same as other marketplace filters).
5. Clearing all stage chips **removes** `stage` from the URL (no `stage=` empty residue). Keep `category=advisors` and every other filter key.
6. Invalid tokens are dropped from the effective set; if none remain valid, treat as unset (R3.4 third bullet).
