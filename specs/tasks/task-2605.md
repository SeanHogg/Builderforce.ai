# PRD: Accurate A0 status in advisor-platform implementation notes

WIP. Shared source of truth for agents editing `specs/builderforce/26-implementation-notes-advisor-platform.md`.

## Problem & Goal

**Problem.** Implementation notes for PRD 26 (`specs/builderforce/26-implementation-notes-advisor-platform.md`, epic #2522 / PR #829) treat the **logged-out public Book kill path** as already decided and landed. They state that public `GET /api/freelancers/:id/booking-services` and `POST /api/freelancers/:id/reservations` already call `listServicesForHost` / `reserveForHost` as if that POST were a public catalogue write that completes visitor booking.

That is the wrong layering. On the bound tree (BA search_code 2026-09-16):

- Application helpers `listServicesForHost` / `reserveForHost` exist in `api/src/application/commerce/bookings.ts`.
- HTTP also exists: `api/src/presentation/routes/freelancerRoutes.ts` exposes GET `/:id/booking-services` and POST `/:id/reservations`, but the POST is behind `authMiddleware` (tenant). `practiceOps.test.ts` asserts that.
- `BookAdvisorPanel` exists (`frontend/src/components/freelance/BookAdvisorPanel.tsx`) as an in-page tenant reserve, not ATS `/book/{token}`.
- `meetingRoutes.ts` exists and is imported from `api/src/index.ts`.

The original gap text (“no freelancer route files / no *Advisor* files / meetingRoutes absent on main”) does **not** match that tree. Relabeling those files as unshipped would create a new false baseline. Downstream agents then implement or demo #2532 against “public POST is the kill path and already shipped,” which contradicts PRD P0 (generalise ATS `/book/{token}`) and the #2522 code-review blocker.

**Goal.** Make the notes match the tree **and** the kill condition: cite application helpers and shipped HTTP with their real auth posture; do not present authed POST `/reservations` or `BookAdvisorPanel` as the logged-out Book path; name completing logged-out Book via ATS `/book/{token}` as #2532. Do not relabel files that exist as “absent from main.” Readers must not infer that a stranger can finish a booking on `main` via POST `/reservations`.
