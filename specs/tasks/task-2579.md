# PRD 26 P2 — Advisor filters, visitor chat, Resources tab

**Status:** WIP  
**Parent:** Epic #2522 / PRD 26 Advisor Platform  
**Depends on:** P0+P1 kill condition must pass (#2527, #2532, #2538). Do not start this slice until that gate is green.  
**Spec:** `specs/builderforce/26-prd-advisor-platform.md`, `specs/builderforce/26-implementation-notes-advisor-platform.md`

## Problem & Goal

Advisors are first-class marketplace inventory, but discovery and the public profile still behave like a generic listing page. Visitors cannot narrow `?category=advisors` by the attributes that actually drive advisor selection (expertise, language, method, stage). They cannot start a conversation from the public profile without a new messaging surface. They cannot see the advisor’s other sellable work next to the profile.

P2 closes that gap using existing primitives only: marketplace filters scoped to the advisors category, visitor chat on the public advisor profile via the current chat primitive, and a Resources tab that lists that advisor’s existing marketplace listings.

**Goal:** A visitor can filter advisors, open a public advisor profile, start a chat, and see that advisor’s agents / skills / courses / playbooks / templates — without a new messenger, CMS, LMS, or category-wide filter regressions.

## Target users / ICP roles

- **Visitor / shopper:** Unauthenticated or authenticated user browsing the marketplace and public advisor profiles. Needs filter, chat, and resource discovery; is not yet a booked client.
- **Advisor (seller):** User with a public advisor profile and zero or more marketplace listings (agent, skill, course, playbook, template). Owns the inventory the Resources tab surfaces; receives visitor chats through the existing chat primitive.
- **Marketplace operator / platform:** Needs category-scoped filters so non-advisor categories keep their current filter set and query behavior.

## Scope

In scope for this slice only:

1. Marketplace filters on `?category=advisors`: expertise, language, method, stage.
2. Visitor chat on the public advisor profile, wired to the existing chat primitive.
3. Advisor profile **Resources** tab showing that advisor’s existing marketplace listings of types agent, skill, course, playbook, and template, including an empty state.

Work is compose-only against current marketplace, profile, and chat surfaces. Filter application must be category-scoped so other marketplace categories are unchanged.

## Functional requirements

### 1. Marketplace advisor filters

- When the marketplace URL includes `category=advisors` (and equivalent category routing), the filter UI exposes **expertise**, **language**, **method**, and **stage**.
- Filters are combinable (AND across dimensions; multi-value within a dimension follows existing marketplace multi-select semantics).
- Selected values persist in the query string using the same query conventions as other marketplace filters; refresh, share, and back/forward restore the same result set.
- Clearing a filter or “clear all” returns the unfiltered advisors category set without dropping `category=advisors`.
- Result counts and empty-results copy follow existing marketplace patterns.
- When `category` is absent or is any non-advisors category, these four controls are not shown and must not be applied. Existing filters, sort, pagination, and listing cards for those categories remain unchanged.
- Advisor cards and ranking/sort for the advisors category continue to use current marketplace listing behavior; this slice does not introduce a new search index or ranking model.

### 2. Visitor chat on the public advisor profile

- The public advisor profile includes a chat entry point visible to visitors (including unauthenticated users, subject to the existing chat primitive’s auth gate).
- Chat uses the **existing chat primitive** only: same threads, composer, notifications, rate limits, and advisor inbox. No new messenger product, no parallel thread store, no new realtime stack.
- Starting chat opens or resumes a thread with that advisor as the counterparty. Profile context (advisor identity) is passed the same way other profile-originated chats already do.
- If the primitive requires sign-in, the existing auth/redirect flow is used; after auth the visitor lands back in the advisor thread.
- Advisors receive and reply in their existing chat inbox. No new advisor-side messaging UI in this slice.
- Chat is not a booking, scheduling, or payment flow.

### 3. Advisor profile Resources tab

- Public advisor profile includes a **Resources** tab.
- The tab lists only marketplace listings **owned by that advisor**, limited to types: **agent**, **skill**, **course**, **playbook**, **template**.
- Listings are existing marketplace records (title, type, status/visibility, deep link into the current listing detail). No new catalog, no CMS/LMS objects, no uploaded-file library.
- Draft, unpublished, or non-marketplace items are not shown. Visibility matches what the marketplace already exposes for that listing.
- Empty state is allowed and required when the advisor has no eligible listings. Empty state is copy + layout only; it does not prompt creation of a new CMS/LMS.
- Tab does not aggregate other advisors’ listings, platform editorial content, or SCORE-branded material.

## Acceptance criteria

**Gate**

- P2 implementation does not start until epic #2522 P0+P1 kill condition passes for #2527, #2532, and #2538.

**Filters**

- Given marketplace `?category=advisors`, the shopper sees expertise, language, method, and stage filters and can apply any combination; the listing grid updates to matching advisors only.
- Given a filtered advisors URL, reload and shared link reproduce the same filters and results.
- Given `?category=` for any other category (or no category), advisor-only filters are absent and that category’s prior filter/query behavior is unchanged (no extra params honored, no broken chips, no empty/wrong grids).
- Clearing advisor filters does not navigate the user out of the advisors category.

**Visitor chat**

- Given a public advisor profile, a visitor can start chat via the existing chat primitive and the advisor sees the thread in the existing inbox.
- No new messenger IA, routes, or data model ship in this slice.
- Unauthenticated visitors follow the existing chat auth gate and return to the advisor thread after sign-in.

**Resources tab**

- Given an advisor with one or more published agent/skill/course/playbook/template listings, the Resources tab shows only those listings and each item links to its current marketplace detail page.
- Given an advisor with none of those listings, the Resources tab renders an empty state and does not error.
- Listings of other types, other owners, or non-marketplace resources do not appear.

**Compose / brand**

- No new CMS or LMS. No SCORE branding on filters, chat, or Resources.

### R1 — Filter vocabularies (bind; do not invent)

P0 (#2527) parentheticals (`stages: start/grow/exit`, SCORE-shaped) are **rejected**. P2 filters the P0 advisor profile fields using platform vocabularies already in `@builderforce/creation-canvas-contract`.

| Filter UI | Query key | P0 profile field | Allowed values | Match rule |
|---|---|---|---|---|
| Expertise | `expertise` | `expertise` | `EXPERTISE_AREAS`: `product`, `marketing`, `operations`, `finance`, `legal`, `people`, `technology`, `business_development`, `fundraising`, `international` | Advisor’s expertise list contains the selected token |
| Language | `language` | `languages` | Same ISO 639-1 option list the P0 profile editor ships. Do not add a language table. | Advisor’s `languages` array contains the code |
| Method | `method` | `methods` | P0 contact methods: `video`, `phone`, `email`, `in_person` | Advisor’s methods list contains the token |
| Stage | `stage` | `stages` | `BUSINESS_STAGES`: `idea`, `mvp`, `early_revenue`, `growth`, `scale` | Advisor’s stages list contains the token |

**Not P2 filters:** `industries` / `STARTUP_SECTORS` (P0 field, unused here), booking service kinds (`one_to_one` / `one_to_many` — Book CTA axis, not a facet), SCORE start/grow/exit, geo/“near me”.

If P0 persists different method/stage tokens than the table, **P0 is wrong against epic § brand rules**; P2 still filters `EXPERTISE_AREAS` + `BUSINESS_STAGES` + ISO 639-1 + `{video,phone,email,in_person}`. Architect maps the stored column names; BA does not add a second enum.

### R2 — Marketplace advisor filters

**R2.1 Visibility.** Render the four controls only when the marketplace URL has `category=advisors` (P0 token), including logged-out browse. Equivalent P0 routing (e.g. `family=talent` plus that category) counts. Place them in the existing `CatalogToolbar` slot, same control pattern as talent `discipline` / `sort` (`<Select>` + `filterControlStyle`).

**R2.2 Combinations.** AND across the four dimensions. Within a dimension, follow **existing** marketplace semantics: today talent facets are single-select, so each P2 control is one value. Do not introduce a new multi-select widget. Invalid/unknown query values are ignored (treated as unset); do not 400 the page.

**R2.3 Query string.** Persist via the same `router.replace` path Marketplace already uses for `discipline` and `sort`.

- Keys: `expertise`, `language`, `method`, `stage`.
- Reload, share, back/forward restore the same filters and result set.
- Changing any of the four resets `page` to 1 (same as other marketplace filters).
- Clear one control: drop that key only.
- Clear all: drop the four keys; **keep** `category=advisors` (and `family` / `kind` if present). Never navigate to `/advisors` and never drop the advisors category.

**R2.4 Category isolation.** When `category` is absent or any value other than `advisors`:

- Do not render the four controls.
- Do not apply those four params to talent, agents, skills, knowledge, companies, or publish grids even if they appear in the URL (ignore; no chips; no empty/wrong grids).
- Existing filters (`discipline`, `sort`), kind switcher, pagination, cards, and ranking stay unchanged.

**R2.5 Data path.** The advisors grid is P0’s advisor-mode talent list (person listings), not a new index and not `MARKETPLACE_LISTING_KINDS`. Prefer passing the four keys into the existing public talent list (`GET /api/public/freelancers` today: `q, page, limit, discipline, sort`) **only when** `category=advisors`. If P0 already added server-side advisor query params, use those names; do not add a second list endpoint. Client-side AND over the current page only is insufficient (breaks counts and share). No new search index or ranking model. Advisors keep current marketplace/talent sort; this slice does not add a sort control.

**R2.6 Counts and empty.** Result count and zero-result copy follow existing marketplace / talent patterns (`CatalogToolbar` `resultCount`, existing empty state). No SCORE or “become a mentor” empty marketing.

**R2.7 Auth.** Filters and results work logged-out (P0 logged-out browse). Do not newly require `auth: 'web'` / tenant JWT to apply filters.

### R3 — Visitor chat (existing primitive only)

**R3.1 Surface.** Public advisor profile `/u/[username]` when the profile is in P0 advisor mode. No new route.

**R3.2 Primitive.** Reuse `MessagesButton` + `startEmployerConversation({ freelancerUserId })` (`auth: 'tenant'`). Counterparty = profile `person.id` (talent userId / A0 `booking_hosts.host_ref`). Opens or resumes the existing thread; advisor replies in the existing inbox (`/dashboard/messages?c=`). Same threads, composer, notifications, rate limits. **No** new messenger IA, thread store, realtime stack, Brain-chat, or meeting-chat.

**R3.3 Visitor-visible CTA.** Unlike today’s Message control (`canHire = isAuthenticated && tenantId && !isOwner`), the advisor-profile chat entry point is **visible to visitors including unauthenticated users**. Owner viewing self: no chat-with-self CTA. Non-advisor talent profiles keep current `canHire` Message visibility (no regression).

**R3.4 Auth gate.** The primitive requires a tenant session. Do not create guest threads.

- Logged out or tenantless: CTA click goes to `signInHref(current profile URL)` (`frontend/src/lib/auth.ts`) so `next` is encoded. After sign-in, land back on that advisor profile.
- After return with a tenant: clicking chat (or a single post-login resume if the profile already does this for Hire) calls `startEmployerConversation` and enters the existing inbox thread. Do not auto-send a message.
- Authenticated tenant visitor who is not the owner: existing MessagesButton flow.

**R3.5 Not chat.** Chat is not booking, scheduling, payment, lead routing, or the Book CTA (#2532). Do not start a reservation from this button.

### R4 — Resources tab

**R4.1 Tab.** Add a **Resources** tab to the public advisor profile `TabBar`. Existing tabs stay: `about`, `listings` (hire-me cards from `listPublicListings`), `activity`, `hired`. Resources is **not** a rename of `listings`.

**R4.2 Inventory.** List only marketplace records **owned by that advisor**, kinds **exactly**:

| Kind | Detail URL (current) |
|---|---|
| `agent` | `/marketplace/agents/{slug}` |
| `skill` | `/marketplace/skills/{slug}` |
| `course` | `/marketplace/course/{id}` (existing knowledge detail) |
| `playbook` | `/marketplace/playbook/{id}` |
| `template` | `/marketplace/template/{id}` |

**Exclude:** `pack`, `person`, `company`, hire-me service cards, drafts, unpublished, other owners, platform editorial, SCORE-branded material.

**R4.3 Ownership.** `CreationListing.sellerRef` (and agent `owner.id`) **equals** profile `person.id`. Never match on display name.

**R4.4 Visibility.** Only listings the public marketplace already exposes logged-out. If it is not reachable on Marketplace without auth, it does not appear here.

**R4.5 Empty state.** Required when the advisor has zero eligible listings: copy + layout only (heading + one line). **No** create/publish/CMS/LMS CTA on the public profile. Failed fetch must not crash the profile; use the page’s existing error pattern.

**R4.6 Data path.** Today `publicListingApi.browse` accepts `q, kind, page, limit` only (no seller). Client-side filtering of an unscoped browse is **not** acceptable (wrong owners, broken pagination). Architect/developer may add a **seller/owner query param to the existing public listings endpoint** — not a new catalog resource, not a new table. Page size follows existing marketplace limits. Each row shows current card fields (title, kind, public status) and deep-links to the current detail page. No resource player, no authoring.
