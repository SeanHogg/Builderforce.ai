# PRD: Guest workspace open — prefer guest project + claim link

**Status:** WIP  
**Decision:** If a visitor opens a guest workspace (or a shared question that resolves to one) and has no tenant, put them in a **guest project** and surface a **claim link**. Do not force tenant creation as a prerequisite to view or participate.

---

## Problem & Goal

Visitors who receive a guest-workspace or shared-question link often have no tenant. Today that path either blocks them, dumps them into a generic signup, or auto-creates a tenant they did not ask for. All three leak conversion, create orphan tenants, and confuse ownership of the work they just opened.

**Goal:** Let a no-tenant visitor open the guest workspace immediately in a **guest project**, keep their work durable, and give them a **claim link** so they (or an org they join later) can attach that project to a real tenant without losing content or identity.

Success looks like: open → work in guest project → optional claim, with no forced tenant and no dead-end.

---

## Target users / ICP roles

- **Anonymous / unauthenticated visitor** following a guest-workspace or shared-question URL.
- **Authenticated user with no tenant** (signed in, not a member of any org).
- **Guest contributor** who will later join or create a tenant and claim the project.
- **Tenant admin / owner** who later accepts a claim and takes the project into their org.
- **Downstream agents** implementing auth, workspace routing, project lifecycle, and share/claim UX.

Not primary: existing tenant members opening a workspace they already belong to (normal tenant routing).

---

## Scope

In scope for this WIP:

- Routing when a visitor opens a guest workspace / shared question and **has no tenant**.
- Creation (or reuse) of a **guest project** bound to that visit/session/user.
- Issuing and displaying a **claim link** for that guest project.
- Persistence of guest-project content across the same visitor identity (cookie, session, or account).
- Claim redemption: attach the guest project to a tenant the user creates or joins, transferring ownership without duplicating the workspace.
- Explicit preference over “create a tenant first” and over “view-only with no project.”

Out of scope is listed below; do not expand into billing, SSO, or multi-tenant merge in this slice.

---

## Functional requirements

### 1. Detect no-tenant visitor

- On guest-workspace or shared-question open, classify the actor as:
  - unauthenticated, or
  - authenticated with **zero** tenant memberships.
- If the actor already has one or more tenants, do **not** use the guest-project path (existing tenant/workspace routing applies).

### 2. Prefer guest project

- For a no-tenant visitor, resolve the open into a **guest project** (create if none exists for this visitor + source workspace/question; reuse if one already does).
- The visitor can view and, where the share allows, participate (comments, answers, edits per existing guest permissions) **without** creating a tenant.
- Guest project is a first-class project with a stable ID, not an ephemeral preview that disappears on refresh.
- Do not auto-provision a tenant, trial org, or personal workspace as a side effect of this open.

### 3. Claim link

- Every guest project gets a **claim link** (unguessable, single-purpose URL or token).
- Surface the claim link in the guest workspace chrome (persistent, copyable). Unauthenticated visitors who later sign in must still be able to retrieve it for projects they own as guest.
- Claiming is optional. The guest project remains usable until claimed, expired, or deleted per existing guest retention rules.
- Claim is allowed only after the actor has a tenant (create or join). Redeeming the link attaches the guest project to that tenant and transfers ownership.
- After a successful claim, subsequent opens of the original guest/share URL follow tenant routing for that project; the guest-project path is not re-entered for the same work.

### 4. Identity and continuity

- If the visitor authenticates mid-session (still no tenant), keep them on the same guest project; do not fork a second project.
- Claim token is bound to the guest project, not to a single browser tab.
- Invalid, expired, or already-redeemed claim links fail closed with a clear state (already claimed / not found), not a new guest project.

### 5. Permissions and isolation

- Guest projects are isolated from all tenants until claimed.
- Share permissions on the source question/workspace still apply inside the guest project (e.g. view-only stays view-only).
- Claiming does not widen permissions beyond what the destination tenant’s policies allow; tenant admins remain the authority after transfer.

---

## Acceptance criteria

1. **No-tenant open:** An unauthenticated user and an authenticated user with no tenants can both open a guest-workspace / shared-question link and land in a guest project without being forced to create a tenant.
2. **No auto-tenant:** Opening does not create a tenant, personal org, or billing account.
3. **Reuse:** The same no-tenant visitor reopening the same source lands in the **same** guest project (same project ID), not a duplicate.
4. **Claim link present:** The guest UI always exposes a working claim link for that project.
5. **Claim succeeds:** After the visitor creates or joins a tenant, redeeming the claim link moves the guest project into that tenant; content, question thread, and membership of the guest session are preserved; the project is no longer in the guest pool.
6. **Claim is idempotent:** Redeeming an already-claimed link does not create a second project; it reports claimed (and routes to the tenant project if the actor has access).
7. **Tenant members unchanged:** A user who already has a tenant and opens the same class of link is **not** sent down the guest-project + claim-link path.
8. **Permission fidelity:** View-only shares remain view-only inside the guest project; claim does not escalate rights.
9. **Fail closed:** Missing workspace, revoked share, or invalid claim token does not provision a guest project or a tenant.

---

## Out of scope

- Forcing or encouraging tenant creation as the primary open path for no-tenant visitors.
- Auto-joining the visitor to the source tenant (true guest, not shadow membership).
- Billing, plan limits, or converting guest projects into paid seats.
- SSO / SCIM / domain capture as a claim mechanism.
- Merging multiple guest projects into one tenant in bulk.
- Changing guest permission models, share-link expiry, or question-threading behavior except as needed to host them in a guest project.
- Mobile-specific clients, public SEO index of guest projects, and admin impersonation of claim links.
- Users who already have a tenant (including which tenant to pick when they have several).
