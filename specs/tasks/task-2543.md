# PRD: Guest workspace open — prefer guest project + claim link if visitor has no tenant

**Status:** WIP  
**Decision:** If a visitor has no tenant, do not force tenant creation. Open (or create) a guest project and surface a claim link so they can attach it to a tenant later.

## Problem & Goal

Visitors often land on a shared/guest workspace without an existing tenant (no org, no billed account). Blocking them behind “create an organization first” drops conversion and breaks the share-link promise.

**Goal:** Let a no-tenant visitor open the guest workspace with minimal friction, persist their work in a **guest project**, and give them a durable **claim link** to attach that project to a tenant when they are ready. Prefer this path over creating a tenant, joining an existing tenant, or treating the session as throwaway.

## Target users / ICP roles

- **Visitor (no tenant):** Unauthenticated or authenticated user with no tenant membership. Primary beneficiary of this path.
- **Sharer / host:** Tenant member who sent the guest/workspace link. Expects the recipient to open work without an account setup gauntlet.
- **Claimer:** Same person (or their org admin) who later creates or joins a tenant and claims the guest project.
- **Org admin (claim-time):** Approves or receives the claimed project into the tenant; not in the open-path UX.

## Scope

In scope for this WIP:

- Detection that the visitor has **no tenant** at guest-workspace open.
- Create or reuse a **guest project** as the container for that visit.
- Persist guest work across the session and subsequent visits via the same identity or claim token.
- Issue and display a **claim link** (copyable, shareable, expirable/rotatable per existing token policy).
- Claim flow: authenticated user with a tenant uses the link to attach the guest project to that tenant.
- Clear, non-blocking UI copy: you are in a guest project; claim it to keep it under an org.
- Idempotency: same visitor + same guest workspace does not spawn duplicate guest projects.
- Auth edge: anonymous visitors may be prompted to sign in/up **without** creating a tenant; identity is enough to bind the guest project.

## Functional requirements

1. **No-tenant gate**  
   On guest workspace open, if the actor has zero tenant memberships, take the guest-project path. Do not redirect to tenant create/join as a hard blocker.

2. **Guest project**  
   - Create a guest project if none exists for this visitor + source workspace (or share).  
   - Reuse the existing guest project on repeat open.  
   - Guest projects are first-class enough to hold the workspace content the visitor is meant to see/edit under guest permissions.  
   - Guest projects are not tenants and do not imply billing, seats, or org identity.

3. **Open behavior**  
   After guest-project resolve, open the guest workspace into that project. Preserve deep-link context (page, object, comment) where it still applies.

4. **Claim link**  
   - Generate a claim link bound to the guest project.  
   - Show it in the guest chrome (banner/modal that can be dismissed but rediscoverable).  
   - Link is useless without later auth + a tenant; it does not grant extra access by itself.  
   - Support copy; respect existing secret-link rotation/expiry if the product already has that.

5. **Claim**  
   - Authenticated user with ≥1 tenant follows the claim link.  
   - If multiple tenants, pick a destination tenant (default: last-used / only tenant).  
   - On success, the guest project becomes a normal project (or equivalent) in that tenant; the visitor’s guest session ends.  
   - If the claimer still has no tenant, allow tenant create **as part of claim**, not as part of open.

6. **Permissions & isolation**  
   - Guest capabilities stay at guest/share ACL, not host-tenant member ACL.  
   - Other host-tenant data remains invisible.  
   - Claiming does not silently add the claimer to the original host tenant.

7. **Failure / conflict**  
   - Invalid/expired claim link: explain and offer to open as guest again if still allowed.  
   - Project already claimed: open in the destination tenant if the user can access it; otherwise standard access-denied.  
   - Visitor later acquires a tenant without claiming: do not auto-claim; keep guest project until explicit claim.

## Acceptance criteria

- A user with **no tenants** who opens a valid guest workspace lands in a guest project **without** being forced to create or join a tenant.  
- A second open by the same visitor reuses the same guest project (no duplicates).  
- Guest chrome always exposes a working claim link for an unclaimed guest project.  
- Claiming with a single tenant attaches the project to that tenant; workspace opens there afterward.  
- Claiming with multiple tenants requires an explicit destination choice before attach.  
- After claim, the old claim link cannot attach again; it either redirects to the claimed project (if authorized) or fails closed.  
- Users who already have a tenant are **not** pushed into this path (existing tenant-member guest-open behavior unchanged).  
- Anonymous users can be asked to authenticate, but authentication alone does not create a tenant.  
- Host-tenant members do not see guest-project internals as org resources until/unless claimed into their tenant.  
- Analytics/events distinguish: `guest_open_no_tenant`, `guest_project_created`, `claim_link_copied`, `guest_project_claimed`.

## Out of scope

- Changing guest ACL, share-link auth, or what guests can edit.  
- Auto-provisioning a tenant (or trial org) on first guest open.  
- Billing, seat consumption, or SSO for guest projects.  
- Merging a guest project into an already-existing project (claim is attach-as-project only).  
- Multi-claim, transfer between tenants after first successful claim, or admin “adopt all guests” tools.  
- Email/SMS claim magic-link campaigns (in-product link only unless a later PRD).  
- Migrating historical anonymous local-only sessions that predate guest projects.  
- Mobile-specific IA beyond using the same open/claim rules.

## Requirements

Authoritative requirements for the no-tenant guest-workspace open path. Downstream architect / developer / QA treat these as the contract. They refine the Product Manager’s functional requirements; they do not reopen out-of-scope items.

| Actor at guest-workspace open | Tenant memberships | Open path |

“Guest workspace open” in this epic means: the visitor is entering the workspace that should hold their work after an advisory/share/meeting landing (the container #2541 needs). It is **not** “join the host’s tenant as a guest collaborator.”

### Guest project vs guest account vs tenant (do not conflate)

| Concept | What it is | What it is not |
|---|---|---|
| **Guest account** | A user identity (`ensureGuestAccountForCanvas` today) | A project; a tenant; enough for API task placement |
| **Guest project** | A first-class **project** that can hold canvas content **and** board/API tasks, not attached to a billed customer tenant until claim | A tenant; an org; a trial; a seat; a canvas-invite membership in the host tenant |
| **Tenant / org** | Billed (or billable) membership container | Created at open; implied by a guest project |

Architect may use a platform-internal holding container that is **invisible as an org**. It **must not** appear in tenant switchers, billing, seats, SSO, or “create your organization” UX. Product language is **guest project**, never “guest organization.”

### Idempotency key (guest project)

Reuse, never duplicate, when **all** of the following match:

1. **Visitor identity** — authenticated `userId` once known. Before auth, a durable **claim token** (cookie or equivalent) is the bind; after auth, that token’s project is bound to the user (merge, do not spawn a second project).
2. **Source workspace** — the share / guest-workspace / meeting-derived workspace the visitor opened (stable source id). Same visitor + same source → same guest project. Same visitor + a **different** source workspace may have a different guest project (do not collapse unrelated shares).

Empty identity + empty token must not mint an un-keyable row that can never be reused.

### R-1 — No-tenant gate

1. On guest-workspace open, count the actor’s **tenant memberships** (active memberships only; invited-but-not-accepted does not count as “has a tenant”).
2. If count = 0: take the guest-project path (R-2–R-5). **Do not** redirect to tenant create, tenant join, billing, or SSO setup as a hard blocker. Those screens may exist elsewhere; they are not on this path.
3. If count ≥ 1: **do not** enter this path. Existing tenant-member guest-open (including canvas-invite seating into a tenant they already belong to, or opening in their current tenant) stays as today.
4. Emit `guest_open_no_tenant` once per open that takes path (2), including reuse of an existing guest project (creation is a separate event).

**Given** an authenticated user with zero tenant memberships opens a valid guest workspace  
**When** the open resolver runs  
**Then** they land in a guest project and are not sent to create/join an organization.

### R-2 — Create or reuse guest project

1. If a guest project already exists for (visitor identity **or** claim token) + source workspace, **reuse it**. Do not insert a second project.
2. If none exists, **create** one, bind it to that identity/token + source, and emit `guest_project_created` (once, on insert only).
3. Repeat open by the same visitor (same identity after auth, or same claim token before auth) against the same source **must** return the same project id.
4. Auth after anonymous open **binds** the in-hand guest project to the new `userId`. If that user already has a guest project for the same source, keep **one** (the pre-existing user-bound project wins; attach any work from the token-bound project or merge per architect — product rule: **no duplicate guest projects for the same user + source**).
5. Do **not** create a tenant, trial org, personal workspace, or billed customer as a side effect of (1)–(4).

**Given** the same no-tenant visitor opens the same guest workspace a second time  
**When** the resolver runs  
**Then** they get the same guest project id; `guest_project_created` is not emitted again.

### R-3 — Guest project capabilities (container for #2541)

A guest project is first-class enough that:

1. It has a stable `projectId` that `#2541` / `resolveStandupProject` can treat as `chosen` (or the equivalent “visitor has a project”).
2. It can hold **canvas task objects** and **API/board tasks** for that visitor (the Destination B #2541 otherwise skips when `projectId` is null).
3. Guest **permissions** on that project stay at guest/share ACL (PM FR 6). Opening a guest project does not grant host-tenant member ACL.
4. It does **not** imply billing, seats, SSO, org name, or tenant membership.
5. Host-tenant members **must not** see this project in their org project lists, billing, or resource inventories until/unless it is **claimed into their tenant** (R-6). Isolation is the default.

This ticket **creates/resolves** the container. It does **not** place minutes action items (that is #2541) and does **not** propose a follow-up slot (that is #2542).

### R-4 — Open behaviour

1. After guest-project resolve, open the guest workspace **into that project**.
2. Preserve deep-link context that still applies (page, object, comment, meeting id). Drop context that required host-tenant ACL; do not 404 the whole open if only a secondary deep-link is unreadable.
3. Session work persists across this visit and later visits via the same identity or the same claim token (R-2).
4. The visitor’s guest session continues until a **successful claim** (R-6). Acquiring a tenant by some other path (invited to an org, created an org in a different flow) **does not** auto-claim (PM FR 7). The guest project remains guest until explicit claim.

**Given** a no-tenant visitor with a deep link to a comment in the shared workspace  
**When** they open and a guest project is resolved  
**Then** they are in that guest project and, where the comment is still in guest-visible content, the comment context is kept.

### R-5 — Claim link (issue and chrome)

1. Every **unclaimed** guest project has exactly one active claim token (rotation replaces it; see 5).
2. The claim **link** is bound to that guest project. It does **not** grant extra access by itself: opening it while unauthenticated or still tenant-less does not attach the project and does not reveal host-tenant data.
3. Guest chrome **always** exposes a working claim link for an unclaimed guest project: banner and/or modal, **dismissible**, **rediscoverable** (settings / “Claim this project” in guest chrome — not a one-shot toast).
4. Copy is supported. Copy emits `claim_link_copied`.
5. Secret handling follows existing product secret-link policy where one exists (canvas invite already hashes tokens at rest, supports expiry). Minimum for V1: token stored **hashed**, raw token shown only at issue/copy, **expiry and rotation** supported. Rotating invalidates the previous URL.
6. Distinct from `/create/join/:token`. Suggested product path shape (architect may rename): `/claim/guest/:token` (or equivalent that cannot collide with canvas invite).
7. UX copy (non-blocking, not a wall): the visitor is in a **guest project**; claim it to keep it under an org. Do not use “create your organization to continue.”

**Given** an unclaimed guest project is open  
**When** the guest chrome renders  
**Then** a copyable claim link is visible or one click away, and dismissing the banner does not destroy the link.

### R-6 — Claim (attach to a tenant)

Claim is the **only** moment this path may create a tenant, and only if the claimer still has none.

1. **Authenticated + exactly one tenant:** attach the guest project to that tenant. No picker. Workspace then opens as a **normal project** in that tenant. Guest session ends. Emit `guest_project_claimed`.
2. **Authenticated + two or more tenants:** require an **explicit** destination choice before attach. Default the picker to last-used tenant (or the only remaining if one is disabled). No silent default-attach. On success, same as (1).
3. **Authenticated + zero tenants:** offer **tenant create as part of claim** (name/org create, then attach). Do **not** send them back through the open-path gate. Cancel leaves the guest project unclaimed.
4. **Unauthenticated claim-link hit:** prompt sign-in/up **without** auto-creating a tenant, then continue (1)–(3).
5. **Success effects:**
   - Project is a normal tenant project (same kind as any other project in that tenant for listing, tasks, canvas).
   - The claim token is **spent**: it cannot attach again.
   - Subsequent use of the old link: if the actor **can access** the claimed project, **redirect** there; otherwise **fail closed** with access-denied (no second attach, no leak of the new tenant’s other data).
6. **Claiming does not** add the claimer to the **original host tenant** and does not copy host-tenant membership, billing, or ACL.
7. **Already claimed** (token spent or project no longer guest): do not attach; apply (5) redirect-or-deny.
8. **Invalid / expired token:** explain; offer to open as guest again **if** the original share/guest-workspace is still allowed for this actor; otherwise fail closed. Do not mint a new guest project from a dead claim token alone.

**Given** a user with one tenant follows a valid unspent claim link  
**When** they confirm  
**Then** the project is in that tenant, the guest chrome is gone, and the same link cannot attach to a second tenant.

**Given** a user with three tenants follows a valid unspent claim link  
**When** the claim UI loads  
**Then** they must pick a destination before attach; last-used is preselected but not submitted.

### R-7 — Permissions and isolation

1. While unclaimed, guest capabilities stay at **guest/share ACL**, not host-tenant member ACL.
2. Other host-tenant data (projects, members, billing, non-shared objects) remains **invisible**.
3. Host-tenant org project lists, search, and analytics **exclude** unclaimed guest projects that are not in that tenant.
4. Claim into tenant T makes the project visible as T’s project to T’s members per T’s normal project ACL — not to the original host tenant unless T **is** that host (unusual; still no silent membership grant).
5. The claim link is not an ACL grant. Possession of the URL without auth + a tenant cannot read host-tenant resources.

### R-8 — Failure, conflict, and non-auto-claim

| Situation | Behaviour |
|---|---|
| Invalid or expired claim link | Explain; offer re-open as guest if the share still allows it; else fail closed |
| Project already claimed; actor can access it | Redirect to the claimed project in its tenant; do not re-attach |
| Project already claimed; actor cannot access it | Access denied; fail closed |
| Visitor later joins/creates a tenant **without** claiming | Guest project stays guest; **no auto-claim** |
| Source share revoked while guest project unclaimed | Guest project remains the visitor’s container for **their** work already persisted; they cannot pull new host-only content. Claim still works for **their** project |
| Duplicate open (race) | Idempotency key (above); at most one guest project per visitor+source. Duplicate-on-race is a residual to close with a uniqueness constraint if the architect requires it; not a V1 product fork |

### R-9 — Auth without a tenant

1. Anonymous visitors **may** be asked to sign in or sign up in order to bind identity to the guest project.
2. That authentication **must not** create a tenant, trial org, or billed account.
3. If today’s register path always mints an org, this open path needs a **no-org** sign-up (or a skip) so identity exists without a tenant. Do not reuse “create organization” as the only register success.
4. After auth, R-2 bind/merge runs; the user is still on the guest-project path until they claim.

**Given** an anonymous visitor is prompted to sign up from guest chrome  
**When** they complete auth  
**Then** they still have zero tenants, still see the same guest project, and still have a claim link.

### R-1 Detect no-tenant visitor

On every in-scope open, classify the actor **before** provisioning:

- **R-1.1** Unauthenticated → no-tenant visitor.
- **R-1.2** Authenticated with zero active `tenant_members` rows that are customer-tenant memberships → no-tenant visitor. (Canvas-collaborator seats on *other people’s* boards do not count as “having a tenant” for this classification if the product already treats them as guests; **having any customer-tenant membership does.**)
- **R-1.3** Authenticated with ≥1 customer tenant → **do not** enter the guest-project path (AC-7).
- **R-1.4** Classification is server-side. Client chrome must not be the only gate.

### R-2 Resolve the source or fail closed

- **R-2.1** Guest-workspace URL must name a resolvable workspace/session. If missing, deleted, or share revoked → **404/410-class failure**, no guest project, no tenant, no claim token (AC-9).
- **R-2.2** Shared-question URL must resolve to a guest workspace **or** fail closed the same way. Resolving MUST NOT create a guest project in order to “have somewhere to put the question” when the source does not exist.
- **R-2.3** Invalid / expired / already-redeemed **guest-project-claim** tokens fail closed with a distinct state (`not_found` | `expired` | `already_claimed`). They MUST NOT mint a new guest project or a tenant (AC-6, AC-9).

### R-3 Prefer guest project (no auto-tenant)

- **R-3.1** For a no-tenant visitor + valid source, resolve to a **guest project**: create if none exists for **(visitor identity × source workspace/question)**; reuse if one does (same project ID) (AC-1, AC-3).
- **R-3.2** The visitor can view and, where the share allows, participate (comments, answers, edits per existing guest permissions) **without** creating a customer tenant (AC-1).
- **R-3.3** Guest project has a stable ID, survives refresh and new tabs for the same visitor identity, and is not an ephemeral preview (AC-3).
- **R-3.4** Open MUST NOT create a customer tenant, trial org, personal workspace, or billing account (AC-2).
- **R-3.5** Open MUST NOT auto-join the visitor to the **source** tenant (true guest, not shadow membership). This is the opposite of today’s canvas-invite seating and is load-bearing.
- **R-3.6** Minutes→tasks and other parent-#2538 P1 writes that need a project use this guest project for no-tenant visitors. They MUST NOT redirect to tenant-create onboarding to “have a project.”

### R-4 Identity and reuse (do not fork)

- **R-4.1** **Reuse key** = visitor identity + source (workspace or resolved question). Same pair → same guest project ID.
- **R-4.2** Visitor identity is, in order: (1) authenticated `userId` when signed in; (2) otherwise a durable visitor credential (existing guest `users` row / session cookie — Architect picks the store). A second project MUST NOT be created because the user opened a second tab.
- **R-4.3** If the visitor authenticates mid-session and is **still** no-tenant, stay on the same guest project; do not mint a second project or a second guest user for the same person (PM FR-4).
- **R-4.4** If the visitor authenticates mid-session and **now has** a customer tenant, do **not** silently claim. Stay on the guest project and keep the claim link available until they redeem (claim is optional and explicit).
- **R-4.5** Do not fork when the same signed-in no-tenant user opens the same source from another device if the identity is the account. Cookie-only visitors are bound to that browser’s durable credential; losing the cookie may lose retrieval of an unauthenticated guest project — that is acceptable; it MUST NOT create a tenant to “save” them.

### R-5 Claim link (issue, surface, retrieve)

- **R-5.1** Every guest project has exactly one active guest-project-claim token (unguessable, single-purpose). Rotating it invalidates the previous URL.
- **R-5.2** Guest workspace chrome **always** exposes a copyable claim link for that project (AC-4). It is persistent (not a one-shot toast).
- **R-5.3** Unauthenticated visitors who later sign in (still no-tenant **or** now with a tenant but unclaimed project) can retrieve the claim link for guest projects they own. Ownership is the visitor identity that created/reused the project, not “whoever holds the URL.”
- **R-5.4** Claiming is **optional**. The guest project remains usable until claimed, expired, or deleted per **existing** guest retention rules. This ticket does not invent a new retention clock; Architect binds token TTL to those rules (canvas guest sessions today are 30 days — a precedent, not a requirement to copy).
- **R-5.5** Copy and UI MUST describe the action as attaching **this project** to **an organization**, not as “join this board” (that copy belongs to canvas invite).

### R-6 Claim redemption

- **R-6.1** Redemption is allowed only when the actor has a customer tenant (they may **create or join** as part of the claim flow). Tenant creation at **claim time** is allowed; tenant creation at **open time** is forbidden.
- **R-6.2** Successful redeem: attach the guest project to that tenant; transfer ownership; preserve content, question thread, canvas objects, API tasks, and guest-session membership of the work (AC-5). No duplicate project.
- **R-6.3** After success, the project is no longer in the guest pool. Subsequent opens of the original guest/share URL follow **tenant routing** for that project; the guest-project path is not re-entered for the same work (AC-5).
- **R-6.4** **Idempotent:** redeeming an already-claimed token does not create a second project. Response is `already_claimed`. If the actor has access to the tenant project, route them there; if not, fail closed with that state (no leak of the tenant’s existence beyond “already claimed”) (AC-6).
- **R-6.5** Claim does not widen permissions beyond the destination tenant’s policies. U4 (tenant admin) is authority after transfer (AC-8).
- **R-6.6** Token is bound to the guest project, not to a browser tab or a single session cookie.

### R-7 Permissions and isolation

- **R-7.1** Guest projects are isolated from all customer tenants until claimed. No tenant member, search, or listing in a customer org may see the guest project.
- **R-7.2** Share permissions on the source question/workspace still apply **inside** the guest project (view-only stays view-only; commenter cannot edit) (AC-8).
- **R-7.3** Mentoring / meeting notes / transcripts that land in the guest project keep existing confidentiality defaults (`restricted`; do not cross `guest` / `share` / `publicMedia` / `aiContext` without an explicit founder act — PRD 26 FR-7). This ticket does not relax confidentiality to make claiming easier.
- **R-7.4** Guest-project membership is not a billable seat and MUST NOT increment `maxSeats`. (Canvas invite already uses `SEAT_KIND.COLLABORATOR` + `maxCreationSessionCollaborators` for a *source* tenant; guest projects have no customer tenant to charge.)

### R-8 Fail closed / security

- **R-8.1** Missing workspace, revoked share, invalid/expired/redeemed claim token → no guest project, no tenant (AC-9).
- **R-8.2** Claim tokens are unguessable (cryptographic; not sequential IDs). Guessing does not 200 with a new project.
- **R-8.3** Enumeration: `already_claimed` vs `not_found` MUST NOT disclose another tenant’s project title, members, or contents to an actor without access.
- **R-8.4** Admin impersonation of claim links is **out of scope** (PM). Do not add an operator override in this slice.

### R-9 Explicit non-goals (reject if a PR implements them)

- Forcing or leading with tenant creation on **open**.
- Auto-joining the visitor to the source tenant.
- Reusing `/create/join/:token` or `claimCanvasInviteLink` as the guest-project claim mechanism.
- Implementing guest project as “auto-create a personal org / trial tenant.”
- Billing, plan limits, paid-seat conversion of guest projects.
- SSO / SCIM / domain capture as claim.
- Bulk merge of multiple guest projects.
- Changing canvas-invite guest permission models, share-link expiry, or question-threading except as needed to **host** them in a guest project.
- Adding `advisor` to `MARKETPLACE_LISTING_KINDS` or a `/advisors` destination (parent epic constraint; this ticket is not A0 booking).
- Mobile-specific clients; public SEO index of guest projects.
