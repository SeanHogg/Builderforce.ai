# PRD: R6 — Operator Live Re-Test

## Problem & Goal

Operators currently cannot re-validate a production path, integration, or customer-facing flow immediately after a change, incident, or failed check without leaving the operator console, coordinating ad-hoc with another team, or running unmanaged scripts against live traffic. That delay hides regressions, lengthens mean time to recovery, and produces inconsistent evidence of whether a fix actually restored the intended behavior.

The goal of R6 is to give an authorized operator a first-class, auditable **live re-test** action: select a defined production check, run it against the live system with explicit safety controls, and receive a pass/fail result plus evidence in the same operator session so they can confirm recovery or escalate with facts.

## Target users / ICP roles

- **On-call / incident operator** — needs a fast, safe way to prove a path works after a deploy, rollback, or mitigation.
- **Operations / SRE lead** — needs repeatable live checks with an audit trail, not one-off scripts.
- **Support / success operator (elevated)** — needs to re-verify a customer-impacting flow after a reported failure, within policy.
- **QA / release operator** — needs to re-run a production smoke check as part of go-live or post-change verification.

Primary ICP: operators who already have production read (and limited write) access and are accountable for restoring or confirming live service health. End customers and unprivileged viewers are not users of this action.

## Scope

In scope for this WIP:

- A single **Live re-test** action on an operator-facing entity (incident, check, service, customer path, or equivalent) that already has a defined production test definition.
- Execution of that test against **live** (production) dependencies, not a sandbox stand-in, with operator identity, timestamp, target, and result recorded.
- Guardrails: permission check, confirmation, concurrency limits, rate limits, and a hard block when the selected check is not marked live-safe.
- Result presentation in the operator UI: status (pass / fail / error), duration, summary, and a link or inline snippet of evidence (logs, response codes, assertion list).
- Audit event emitted for every attempt (started, completed, blocked, cancelled).
- Ability to re-run the same check from the result, subject to the same guards.

## Functional requirements

1. **Entry point** — An authorized operator can start Live re-test from the entity that owns the check (for example an incident, monitor, or service detail). The action is hidden or disabled when the operator lacks permission or the check is not live-eligible.
2. **Check selection** — The operator selects one registered live-safe check (or the default check bound to the entity). The UI shows name, what it hits in production, expected duration, and any side-effect warning.
3. **Confirmation** — Starting the run requires an explicit confirm step that restates: live production target, possible side effects (read-only vs write), and that the run will be audited.
4. **Authorization** — The backend re-checks role, scope (service / account / environment), and live-test entitlement at execution time. Fail closed.
5. **Live-safe catalog** — Only checks flagged `live_safe` can run. Checks that mutate customer state, send external notifications, or are unbounded must not be runnable via this action unless they are separately approved and labeled with side effects.
6. **Execution** — The platform runs the check against production using the operator’s tenant/environment context. Default is **read-only probe** (health, auth handshake, idempotent GET/query). Write/side-effecting checks, if any, must be explicitly labeled and extra-confirmed.
7. **Safety limits** — Enforce per-operator and per-target rate limits, a maximum concurrent live re-test per target, a timeout, and cancellation. Do not fan out to all customers or all shards from this action.
8. **Result** — Persist and display: outcome, started/finished times, operator id, check id/version, target, timeout/cancel reason, and evidence (assertion results and a truncated response or log excerpt). Failures are first-class, not silent.
9. **Audit & timeline** — Append a timeline item on the parent entity and emit an immutable audit record for start, success, failure, block, and cancel.
10. **No silent production writes** — If the check cannot be proven live-safe, the action refuses with a clear reason rather than falling back to an unmanaged call.

## Acceptance criteria

- An operator with the live-re-test permission can start, confirm, and complete a live-safe check from the operator UI and see pass/fail plus evidence without leaving the session.
- An operator without the permission never sees an enabled Live re-test control; API calls return a permission error and write an audit “blocked” event.
- A check not marked live-safe cannot be executed; the operator receives a specific refusal, not a generic error.
- Confirmation is required; a single click on the entry point does not start a live run.
- Concurrent and rate limits reject extra runs against the same target with a clear message; in-flight runs can be cancelled and show `cancelled`.
- A hung check hits the timeout, surfaces `error`/`timeout`, and does not leave an unbounded live request.
- Every attempt (including blocked and cancelled) appears on the entity timeline and in the audit log with operator, check, target, and timestamp.
- Default catalog checks used by R6 are read-only probes; any allowed side-effecting check shows a side-effect warning on confirm and in the audit record.
- Re-running from a result creates a new audited attempt and does not overwrite the previous evidence.
- Live re-test does not change customer-visible state for the default (read-only) checks.

## Out of scope

- Authoring, editing, or versioning of new check definitions (catalog/admin is a separate requirement).
- Full synthetic monitoring, continuous canaries, or replacing existing alerting.
- Load / soak / chaos testing, traffic replay, or multi-target blast-radius runs.
- Automated live re-test on every deploy or alert without an operator action (may be a later requirement).
- Sandbox, staging, or local re-test (this requirement is live-only).
- Customer self-serve “test my account” flows.
- Remediation, rollback, or config change from the re-test result (re-test observes; it does not mutate as a fix).
- Cross-tenant or unrestricted production scans.
- Mobile-specific operator UI unless it already shares the same operator console patterns.
