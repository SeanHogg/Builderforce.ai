# PRD: Per-chat `progressPct` on `GET /api/brain/chats`

## Problem & Goal

**Problem.** Clients listing Brain chats cannot show completion progress without extra per-chat calls. Ticket progress already exists in `ChatTicketService`, but `GET /api/brain/chats` does not expose it, so UIs either omit progress or N+1 against ticket endpoints.

**Goal.** Extend `GET /api/brain/chats` so each chat in the response includes `progressPct`, computed in one batch via `ChatTicketService` for the chats on the current page. Existing list behavior, filters, pagination, and auth stay unchanged.

## Target users / ICP roles

- **End users** of Brain chat list UIs (web/mobile) who need at-a-glance ticket completion.
- **Client engineers** consuming the Brain chats API.
- **Downstream agents** implementing API, service, and contract tests from this PRD.

## Scope

In scope:

- Response shape of `GET /api/brain/chats`: add `progressPct` on each chat item.
- Batch lookup of progress for the chats returned by the current request, using `ChatTicketService` (no per-chat ticket calls from the list handler).
- Deterministic mapping from ticket state → integer percent for chats with and without tickets.
- Backward-compatible JSON (additive field only).
- Unit/integration coverage for batching, empty lists, missing tickets, and mixed progress.

Out of scope is listed below.

## Functional requirements

1. **Additive field.** Every chat object in `GET /api/brain/chats` includes `progressPct` (JSON number, integer 0–100). No other list fields change.
2. **Batch only.** After the handler has the page of chat IDs, it calls `ChatTicketService` once with that ID set (or the service’s existing batch API). Do not call ticket progress per chat in a loop.
3. **Computation.** `progressPct` is the ticket completion percent for that chat as defined by `ChatTicketService` (completed tickets / total tickets for the chat, expressed as an integer percent). If the service already exposes a batch percent, use that; do not reimplement ticket math in the controller.
4. **No tickets.** If a chat has no tickets (or the batch result omits it), `progressPct` is `0`.
5. **Rounding.** Percents are integers in `[0, 100]`. Use the same rounding as `ChatTicketService` (typical: floor of `(completed / total) * 100`, with `100` only when all tickets are complete). Never emit values outside 0–100.
6. **Pagination / filters.** Progress is computed only for chats on the current page after existing filters/sort/limit. Do not load tickets for chats not returned.
7. **Auth / tenancy.** Same authz as today. Progress is only for chats the caller can already list. Ticket data from other tenants or unauthorized chats must not leak into the batch.
8. **Failure mode.** If the batch ticket call fails, the list request fails with the same error class as other Brain list dependency failures (do not return the list with missing/null `progressPct`).
9. **Performance.** One batch call per list request. Batch size equals page size. No extra round-trips proportional to chat count.
10. **Contracts.** OpenAPI / client types for the chats list item include `progressPct: integer` (`minimum: 0`, `maximum: 100`).

## Acceptance criteria

- `GET /api/brain/chats` returns `200` with the previous list payload plus `progressPct` on every item.
- For a page of N chats, `ChatTicketService` batch is invoked exactly once with those N chat IDs (N = 0 → no batch call, or an empty-ID no-op; empty list still returns `[]` with no errors).
- Chat with 0 of 4 tickets complete → `progressPct: 0`.
- Chat with 1 of 4 tickets complete → `progressPct` matches service rounding (e.g. `25`).
- Chat with all tickets complete → `progressPct: 100`.
- Chat with no tickets → `progressPct: 0`.
- Existing query params, pagination metadata, sort, and auth errors are unchanged.
- OpenAPI/schema and automated API tests assert the new field type and range.
- Load of the list handler does not introduce N ticket queries for N chats (asserted in test or query-count check).

## Out of scope

- Changing ticket lifecycle, ticket CRUD, or `ChatTicketService` internals beyond using its batch progress API.
- `progressPct` on other endpoints (`GET /api/brain/chats/:id`, websockets, exports) unless they already share this list DTO.
- Filtering, sorting, or searching the list by `progressPct`.
- Real-time progress push; clients poll or refresh the list as they do today.
- Per-ticket breakdown, remaining count, ETA, or weighted progress in this response.
- UI implementation, copy, or analytics events.
- Breaking changes to the chats list contract or new required request parameters.
