# PRD: Per-chat `progressPct` on `GET /api/brain/chats`

## Problem & Goal

**Problem.** Clients listing Brain chats cannot show completion progress without extra per-chat calls. Ticket progress already exists in `ChatTicketService`, but `GET /api/brain/chats` does not expose it, so UIs either omit progress or N+1 against ticket endpoints.

**Goal.** Extend `GET /api/brain/chats` so each chat in the response includes `progressPct`, computed in one batch via `ChatTicketService` for the chats on the current page. Existing list behavior, filters, pagination, and auth stay unchanged.

## Target users / ICP roles

- **End users** of Brain chat list UIs (web/mobile) who need at-a-glance ticket completion.
- **Client engineers** consuming the Brain chats API.
- **Downstream agents** implementing API, service, and contract tests from this PRD.

## Scope

In scope:

- Response shape of `GET /api/brain/chats`: add `progressPct` on each chat item.
- Batch lookup of progress for the chats returned by the current request, using `ChatTicketService` (no per-chat ticket calls from the list handler).
- Deterministic mapping from ticket state → integer percent for chats with and without tickets.
- Backward-compatible JSON (additive field only).
- Unit/integration coverage for batching, empty lists, missing tickets, and mixed progress.

Out of scope is listed below.

## Functional requirements

1. **Additive field.** Every chat object in `GET /api/brain/chats` `chats[]` includes `progressPct` (JSON number, integer 0–100, never null, never omitted, never a string, never a non-integer). No other existing list fields change (`id`, `title`, `ticketCount`, `ticketProgressPct`, pagination metadata, filters, sort, auth errors).

2. **Batch only.** After the handler has the current page of chat IDs, it calls `ChatTicketService.summarizeChatsTicketHealth` **once** (via existing `attachChatTicketSummaries`) with exactly those IDs. Empty page: no batch call. Do not call `listTicketsForChat` (or any per-chat ticket API) in a loop. Do not add a second ticket query beside `attachChatTicketSummaries`.

3. **Computation.** `progressPct` SHALL equal `rollupChatTicketHealth(ticketsForChat).pct` (lockstep with `aggregateTicketHealth`). **Do not** compute `floor(completedTickets / totalTickets * 100)` — that draft formula is rejected (in-review leaves would only ever show 0% or 100%). Weighted live `progressPct` per linked ticket; cancelled/canceled tickets excluded; all-cancelled → 100; no tickets → 0; `Math.round`; clamp `[0, 100]`. Do not reimplement ticket math in the controller.

4. **No tickets.** If a chat has no tickets (or the batch result omits it), `progressPct` is `0` (not `null`, not omitted). Existing `ticketProgressPct` stays `null` in that case.

5. **Rounding / range.** Percents are integers in `[0, 100]`. Use the same rounding as `rollupChatTicketHealth` (`Math.round` of the weighted rollup). Never emit values outside 0–100. `progressPct === 100` means the rollup is exactly 100.

6. **Pagination / filters.** Progress is computed only for chats on the current page after existing filters/sort/limit. Do not load tickets for chats not returned.

7. **Auth / tenancy.** Same authz as today. Progress is only for chats the caller can already list. Ticket data from other tenants or unauthorized chats must not leak into the batch (existing `ticketHealthBatch` tenant scoping stays).

8. **Failure mode.** Keep fail-soft (draft fail-hard is **rejected**). If the batch ticket call throws, `GET /api/brain/chats` still returns 200 with the chat page; every item still includes `progressPct: 0` (and `ticketCount: 0`, `ticketProgressPct: null`). Do not omit `progressPct`. Do not fail the list request.

9. **Performance.** One batch call per list request. Batch size equals page size. No extra round-trips proportional to chat count.

10. **Contracts.** TypeScript DTO is the contract (no standalone OpenAPI in this repo). API list item: required `progressPct: number` (integer 0–100). Keep `ticketProgressPct?: number | null`. Do not create a new OpenAPI document solely for this field.

## Acceptance criteria

- `GET /api/brain/chats` returns `200` with the previous list payload plus required integer `progressPct` (0–100, never null) on every item. `ticketCount` and `ticketProgressPct` are unchanged.
- For a page of N chats, `ChatTicketService.summarizeChatsTicketHealth` (via `attachChatTicketSummaries`) is invoked exactly once with those N chat IDs (N = 0 → no batch call; empty list still returns `[]` with no errors).
- Chat with no tickets → `progressPct: 0` and `ticketProgressPct: null`.
- Chat whose tickets roll up to 0 → `progressPct: 0`.
- Partial progress matches `rollupChatTicketHealth` (e.g. one of four equal-weight leaves at 100% and three at 0% → `25`).
- All remaining tickets complete → `progressPct: 100`.
- Mixed page (no tickets + partial + complete) → every item has integer `progressPct` in 0–100; batch invoked once with that page’s IDs.
- If the batch ticket call throws: list still returns 200; every item has `progressPct: 0` (fail-soft). Do **not** fail the list request.
- Existing query params, pagination metadata, sort, and auth errors are unchanged.
- TypeScript DTOs for the API list item include required `progressPct`. No new OpenAPI document.
- Load of the list handler does not introduce N ticket queries for N chats (asserted in test).

- `progressPct` on other endpoints (`GET /api/brain/chats/:id`, websockets, exports) unless they already share this list DTO. Detail chat DTO does not carry list health; tickets remain `GET .../tickets`.

- Real-time progress push; clients poll or refresh the list as they do today.

- A new OpenAPI document solely for this field.

## Requirements

**Owner:** Business Analyst (Ada) · ticket #2437 · grounded in `seanhogg/builderforce.ai` (`ChatTicketService`, `BrainService.listChats`, `aggregateTicketHealth`). Downstream architect / developer / QA treat this section as the implementation-ready spec. Draft functional requirements FR-3 and FR-8 are superseded where they conflict (see R3, R7).

### 1. Current behaviour (as-is) — do not invent a second pipeline

`GET /api/brain/chats` already batch-attaches ticket health. The gap is the **field name, nullability, and contract**, not the absence of a batch.

Call chain:

1. `api/src/presentation/routes/brainRoutes.ts` — `GET /api/brain/chats` → `BrainService.listChats`.
2. `api/src/application/brain/BrainService.ts` — `listChats` loads the filtered/sorted page, then `attachChatTicketSummaries(tenantId, rows)`.
3. `attachChatTicketSummaries` takes `ids = chats.map(c => c.id)`. If `ids.length === 0`, it returns immediately (no ticket call). Otherwise it calls `ChatTicketService.summarizeChatsTicketHealth(tenantId, ids)` **once**.
4. `ChatTicketService.summarizeChatsTicketHealth` (`api/src/application/brain/ChatTicketService.ts`):
   - `ticketHealthBatch({ tenantId, chatIds })` — one query over `chat_tickets` for the page, plus batched live health.
   - Groups rows by `chatId`.
   - `rollupChatTicketHealth(tickets)` per chat.
   - Fail-soft: on throw, logs and returns `{}` so the chat list still renders.
5. Each list row is annotated today as:
   - `ticketCount: number` (`0` when the batch omits the chat)
   - `ticketProgressPct: number | null` (`null` when no tickets / omitted)

Existing consumers of nullable `ticketProgressPct`:

- `packages/brain-ui/src/chatTickets/types.ts` — `ChatOptionVM.ticketProgressPct?: number | null` (merge picker / Sessions tree).
- Frontend Brain chat list client in `frontend/src/lib/builderforceApi.ts`.

Per-ticket `progressPct` already exists on `GET /api/brain/chats/:id/tickets` (`TicketLinkVM.progressPct`). That endpoint is **not** this ticket.

Math is already covered by `api/src/application/brain/ceremonyTicketHealth.test.ts` (`ticketHealthBatch`, `rollupChatTicketHealth`). The list handler does **not** yet assert a required integer field named `progressPct`.

### 2. Gap this ticket closes

List items do not currently include a **required integer** named `progressPct` (0–100, never null). Clients that follow this ticket’s contract cannot use the list as specified: they omit the ring, N+1 against `/tickets`, or special-case `ticketProgressPct === null`.

This ticket is **additive**. Emit `progressPct` on every list item. Do **not** rename or remove `ticketCount` / `ticketProgressPct`.

### 3. Requirements

**R1. Additive list field.** Every object in `GET /api/brain/chats` `chats[]` SHALL include `progressPct`.

- JSON type: number.
- Domain: integer in `[0, 100]` inclusive.
- Never `null`, never omitted, never a string, never a non-integer (JSON `25` is fine; `25.5` is not).
- No other existing list fields change (`id`, `title`, `ticketCount`, `ticketProgressPct`, pagination metadata, filters, sort, auth errors).

**R2. Single batch, page-scoped.** After the handler has the current page of chats:

- Invoke `ChatTicketService.summarizeChatsTicketHealth` (via existing `attachChatTicketSummaries`) **at most once**, with exactly those chat IDs.
- Batch size equals page size. Do not load tickets for chats not returned.
- Empty page (`chats: []`): no batch call (existing early-return). HTTP 200, `[]`.
- Do **not** call `listTicketsForChat` (or any per-chat ticket API) in a loop from the list path.
- **Implementation constraint:** extend `attachChatTicketSummaries` to also set `progressPct`. Do not add a second ticket query beside it.

**R3. Computation — existing rollup, not naïve ticket counts.** `progressPct` SHALL equal `rollupChatTicketHealth(ticketsForChat).pct`.

**Do not** compute `floor(completedTickets / totalTickets * 100)`. Draft FR-3’s “completed tickets / total tickets” is **wrong** for this product (a list of in-review leaves would only ever show 0% or 100%).

Authoritative rules — must stay in lockstep with `aggregateTicketHealth` in `packages/brain-ui/src/chatTickets/aggregateTicketHealth.ts` and `rollupChatTicketHealth` in `ChatTicketService.ts`:

1. Each linked ticket contributes its live `progressPct` (0–100), weighted by `total`. If `total` is missing or `≤ 0`, weight is `1` (incomplete spec/roadmap/retro and deleted items still pull the headline).
2. Tickets in lane `cancelled` or `canceled` are excluded from the denominator.
3. If every linked ticket is cancelled → `100` (nothing left owed).
4. If the chat has no linked tickets → `0`.
5. Rounding: `Math.round(weightedPct / totalWeight)`. Result is an integer.
6. Clamp defensively to `[0, 100]` if a bad health row would overflow.
7. `progressPct === 100` means the rollup is exactly 100 (all remaining work complete). A value of 99 is not done.

Do not reimplement ticket math in the controller. Call the service.

**R4. Mapping from existing `ticketProgressPct`.**

| Chat state | `ticketCount` (unchanged) | `ticketProgressPct` (unchanged) | `progressPct` (new) |
|---|---|---|---|
| No linked tickets | `0` | `null` | `0` |
| Batch omitted the chat | `0` | `null` | `0` |
| Has tickets, rollup `pct = P` | `> 0` | `P` | `P` |
| All tickets cancelled | `> 0` | `100` | `100` |

Invariant: if `ticketProgressPct` is a number, then `progressPct === ticketProgressPct`. If `ticketProgressPct` is `null`, then `progressPct === 0`.

**R5. No tickets → 0.** A chat with zero `chat_tickets` rows, or a chat the batch map does not contain, SHALL have `progressPct: 0`. Not `null`. Not omitted.

**R6. Pagination, filters, sort, auth.** Unchanged. Progress is computed only for chats the caller can already list, after existing filters/sort/limit. Ticket rows from other tenants or unauthorized chats MUST NOT enter the batch (existing `ticketHealthBatch` tenant scoping stays).

**R7. Failure mode — keep fail-soft (supersedes draft FR-8).** Keep `summarizeChatsTicketHealth` fail-soft.

If the batch ticket call throws:

- `GET /api/brain/chats` still returns 200 with the chat page.
- Each item still includes `progressPct: 0` (and `ticketCount: 0`, `ticketProgressPct: null`, as today).
- Do not omit `progressPct`. Do not return `null`. Do not fail the list request.

Rationale: `attachChatTicketSummaries` is documented to fail-soft so the chat list still renders when ticket health is unavailable. Fail-hard would make listing chats depend on ticket tables remaining up — a regression for Sessions / the chat picker. Draft FR-8 is superseded by this requirement.

**R8. Performance.** One batch call per list request. No extra round-trips proportional to chat count. Tests MUST assert that for N chats on the page, `summarizeChatsTicketHealth` / `ticketHealthBatch` is invoked once (N = 0 → no invocation).

**R9. Contracts / types.** No standalone OpenAPI file exists in this repo. The contract is the TypeScript DTO:

- API list item (BrainService / route JSON): add required `progressPct: number` (integer 0–100).
- `frontend/src/lib/builderforceApi.ts` Brain chat list type: add `progressPct: number`. Keep `ticketProgressPct?: number | null`.
- `packages/brain-ui/src/chatTickets/types.ts` `ChatOptionVM`: add `progressPct?: number` (0–100). Keep `ticketProgressPct?: number | null` for existing merge-picker callers.

If an OpenAPI/zod schema for this route is added later, it MUST declare `progressPct` as integer, `minimum: 0`, `maximum: 100`, required on each item. Do not create a new OpenAPI document solely for this field.

**R10. Tests (required before Done).** Extend `api/src/application/brain/ceremonyTicketHealth.test.ts` and/or a `BrainService.listChats` / `attachChatTicketSummaries` test. Do not add an unrelated suite.

1. Empty page → `[]`, batch not called, no throw.
2. Chat with no tickets → `progressPct: 0` and `ticketProgressPct: null`.
3. Chat whose tickets roll up to 0 → `progressPct: 0`.
4. Partial progress (e.g. one of four equal-weight leaves at 100% and three at 0% → `25`) → `progressPct` matches `rollupChatTicketHealth`.
5. All remaining tickets complete → `progressPct: 100`.
6. Mixed page (no tickets + partial + complete) → every item has integer `progressPct` in 0–100; batch invoked once with that page’s IDs.
7. Batch throw → list still succeeds; every item has `progressPct: 0`.
8. N chats do not produce N ticket queries.

Existing `ticketHealthBatch` / `rollupChatTicketHealth` tests stay; they already pin the math.

**R11. Out of scope (do not do in this ticket).**

- Changing `rollupChatTicketHealth` / `aggregateTicketHealth` internals or ticket lifecycle/CRUD.
- `progressPct` on `GET /api/brain/chats/:id` (that DTO does not carry list health; tickets are `GET .../tickets`).
- Filtering, sorting, or searching the list by `progressPct`.
- Real-time progress push.
- Per-ticket breakdown, remaining count, ETA, or extra dual fields beyond existing `ticketCount`.
- UI copy, analytics, or a new OpenAPI document.
- Removing or renaming `ticketProgressPct`.
