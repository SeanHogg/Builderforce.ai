# Product Requirements Document (PRD)

## Verify Seller-Scoped Param on Public Listings Endpoint (R4.6)

### Problem & Goal
**Problem:**  
The Resources tab in the application needs to display listings specific to a particular advisor. However, the public marketplace listings endpoint does not currently support filtering listings by a seller or owner, making it impossible to retrieve a specific advisor's listings.

**Goal:**  
Implement a seller/owner-scoped query parameter in the public marketplace listings endpoint to allow filtering listings by a specific seller. This will enable the Resources tab to display the correct listings for a given advisor.

### Target Users / ICP Roles
- **Advisors:** Users who have listings on the marketplace and need to view their own listings via the Resources tab.
- **Marketplace Users:** Users who may benefit from more personalized listing views based on specific advisors.

### Scope
- **In Scope:**
  - Identification and verification of the existing public marketplace listings endpoint in `api/src`.
  - Analysis of the endpoint to determine if a seller-scoping query parameter is already implemented.
  - If the parameter does not exist, implement the `sellerId` (or appropriate alternative) query parameter to allow filtering by seller.
  - Creation of unit tests to ensure the new parameter functions as expected.
  - Documentation of the new parameter in the API documentation.

- **Out of Scope:**
  - Modifications to the frontend Resources tab UI/UX.
  - Changes to the data models or database schema.
  - Implementation of authentication or authorization for the endpoint (the endpoint remains public/unauthenticated).
  - Handling of pagination or other filtering parameters beyond seller scoping.

### Functional Requirements
1. **Endpoint Identification:**
   - Locate the public marketplace listings endpoint in `api/src`.
   - Confirm the current route and method (e.g., GET `/api/listings`).

2. **Parameter Verification:**
   - Check if the endpoint already accepts a query parameter for seller scoping.
   - Candidate parameter names to check: `sellerId`, `ownerUserId`, `userId`, `freelancerId`, `authorId`.
   - If a parameter exists, document its name and usage.

3. **Parameter Implementation (if necessary):**
   - If no seller-scoping parameter exists, implement the `sellerId` query parameter.
   - Ensure the parameter is optional and does not break existing functionality.
   - Validate the `sellerId` parameter to ensure it corresponds to a valid user ID.

4. **Testing:**
   - Write unit tests to verify that the `sellerId` parameter correctly filters listings.
   - Test scenarios should include:
     - Valid `sellerId` provided.
     - Invalid `sellerId` provided.
     - No `sellerId` provided (should return all listings).

5. **Documentation:**
   - Update the API documentation to include the new `sellerId` parameter.
   - Provide clear examples of how to use the parameter.

### Acceptance Criteria
- The public marketplace listings endpoint accepts a `sellerId` query parameter.
- When a valid `sellerId` is provided, the endpoint returns only the listings associated with that seller.
- When an invalid `sellerId` is provided, the endpoint returns an appropriate error message.
- When no `sellerId` is provided, the endpoint continues to return all listings.
- Unit tests exist to verify the functionality of the `sellerId` parameter.
- The API documentation includes details on the `sellerId` parameter and its usage.

### Out of Scope
- Modifications to the frontend Resources tab.
- Changes to the data models or database schema.
- Implementation of authentication or authorization for the endpoint.
- Handling of pagination or other filtering parameters beyond seller scoping.
- Implementation of additional query parameters for filtering listings.
