# PRD: Install VSIX via Absolute Path and Confirm 2026.9.79

## Problem & Goal

The workspace tree now ships extension version **2026.9.79**. Earlier pins targeted **2026.9.71** (PRD 29) then **2026.9.72** (after PRD 27 bumped); #2614 recorded exclusive parent-epic decision **(a)** so install and verification follow the live tree.

**Problem:** Relative-path VSIX installs are fragile across agent working directories, shells, and CI checkouts. Version checks that still expect 2026.9.72 or 2026.9.71 will fail against the current package.

**Goal:** Install the VSIX using an **absolute path** and confirm the installed extension identity and version are **2026.9.79**, so every downstream agent shares one unambiguous install contract.

## Target users / ICP roles

- Downstream coding agents executing this task in a shared workspace
- Local developers and maintainers validating the packaged extension
- CI / release operators installing the VSIX into VS Code / Cursor / compatible hosts

## Scope

- Locate the 2026.9.79 VSIX in the current tree
- Install it with a fully resolved absolute filesystem path (no relative path, no unspecified CWD)
- Confirm the host reports version **2026.9.79** after install
- Treat 2026.9.79 as the source of truth over any prior 2026.9.72 / 2026.9.71 wording

## Functional requirements

1. **Resolve absolute path.** Compute the VSIX file’s absolute path (canonical, OS-native) before invoking the installer. Do not pass a relative path.
2. **Install from that path.** Use the host CLI/API install-from-VSIX flow (e.g. `code --install-extension <absolute-path>` or equivalent Cursor/VS Code command) against that absolute path only.
3. **Target version.** The VSIX on disk and the installed extension must be **2026.9.79**. Do not install or accept 2026.9.72 or 2026.9.71.
4. **Idempotency.** If 2026.9.79 is already installed from the same package, re-install or no-op is acceptable; the post-condition remains 2026.9.79 installed.
5. **Verification.** After install, query the host’s extension list (or equivalent) and assert name/id plus version **2026.9.79**.
6. **Failure visibility.** If the file is missing, the path is not absolute, install fails, or the reported version is not 2026.9.79, fail the task with a clear error (path used, expected vs actual version).

## Acceptance criteria

- The installer is invoked with a path that is absolute (starts with `/` on Unix or a drive/UNC prefix on Windows), not a relative segment.
- The VSIX at that path is the **2026.9.79** artifact from the current tree.
- After install, the editor host lists the extension at version **2026.9.79**.
- Checks that still mention 2026.9.72 or 2026.9.71 are treated as outdated; passing means **2026.9.79**.
- A missing VSIX, non-absolute path, install error, or version mismatch fails the run.

## Out of scope

- Changing extension source, bumping the version again, or re-packaging the VSIX
- Marketplace / gallery publish or download
- Relative-path install as a supported fallback
- Host upgrades, new editor profiles, or multi-host matrix beyond the environment already in use
- Feature work inside the extension; this PRD is install + version confirm only
- Reconciling historical 2026.9.72 / 2026.9.71 docs except to ignore those pins in favor of 2026.9.79
- Path (b) on #2614 (produce a 72 VSIX without changelog rewrite) — rejected

## Requirements

These requirements bind **only** the install + version-confirm step of epic #2555 (PRD 29 verify-and-package, coordinated with PRD 27). Packaging is sibling #2560. Dist rebuilds, typecheck/test, and live UX of composing / parent-line / triage copy are other siblings or the parent epic. This ticket does not change extension source.

### R-1 Artifact identity (depends on #2560)

The only installable is the VSIX sibling #2560 produces under `clients/vscode/`, conventionally `builderforce-ai-2026.9.79.vsix`.

- Do **not** run `vsce package` / `pnpm run package` on this ticket.
- Do **not** bump or downgrade `clients/vscode/package.json`.
- Do **not** rebuild `dist` / webview.

If the file is absent, fail with the path that was resolved and state that #2560 has not produced the artifact. Do not package a substitute.

### R-2 Absolute path (mandatory)

1. Resolve the VSIX to a canonical, OS-native absolute filesystem path **before** invoking the installer.
2. The string passed to `--install-extension` MUST be absolute:
   - Unix: starts with `/`
   - Windows: drive prefix (`C:\\` … or Git-Bash `/c/…`) or UNC (`\\\\server\\share\\…`)
3. Forbidden: relative segments (`./`, `../`, `clients/vscode/…`), unexpanded globs (`builderforce-ai-*.vsix`), any path whose correctness depends on an unspecified CWD.
4. Quote the path so spaces cannot split the argument.

### R-3 Install invocation

Use the editor-host CLI already in this environment (VS Code `code` or Cursor `cursor` — whichever is on PATH and is the active host). Do not add a second host.

```
<host> --install-extension "<absolute-path>" --force
```

`--force` is the idempotency mechanism when 2026.9.79 is already installed. Gallery install (`--install-extension builderforce.builderforce-ai` without a filesystem path) is out of scope.

### R-4 Target version

| Field | Value |
|---|---|
| Extension id | `builderforce.builderforce-ai` |
| Required version | **2026.9.79** |
| Outdated pins (do not install or accept) | 2026.9.72 (retired by #2614 decision (a)), 2026.9.71 (PRD 29 §3.5 / §4) |

Passing means the installed identity is `builderforce.builderforce-ai@2026.9.79`. Installing 2026.9.72 (or 2026.9.71) and calling that a pass is a requirement miss. Pin reconciliation is closed on #2614: exclusive choice is **(a)**.

### R-5 Dual verification (CLI “successfully installed” is not proof)

After R-3, **both** must report 2026.9.79:

1. `<host> --list-extensions --show-versions` contains `builderforce.builderforce-ai@2026.9.79`
2. The host extensions directory lists the matching folder:
   - VS Code: `~/.vscode/extensions` entry matching `builderforce.builderforce-ai-2026.9.79`
   - Cursor (if that is the host): the equivalent `~/.cursor/extensions` folder

A `successfully installed` line from R-3 is **not** sufficient. Relative-path installs have previously printed success while installing nothing (PRD 29 §3.6).

Handoff (not this ticket’s AC): the operator/parent must reload the editor window before any live UX check of composing / parent-line / triage.

### R-6 Failure visibility

Fail the run — do not pass, do not no-op into a wrong version — when any of:

| Condition | Report |
|---|---|
| VSIX missing | resolved path + “file not found” + pointer to #2560 |
| Path not absolute | the exact string passed to the CLI |
| Install CLI non-zero | exit code + stderr |
| Listed version ≠ 2026.9.79 | expected `builderforce.builderforce-ai@2026.9.79` vs the actual `--list-extensions` / extensions-dir line(s) |

### R-7 Idempotency

Re-install of the same 2026.9.79 package with `--force`, or a no-op when that version is already present from that package, is acceptable. Post-condition remains R-5.

### R-8 Out of scope (do not expand this ticket)

- Bumping or downgrading `clients/vscode/package.json` (live tree **2026.9.79**)
- Re-packaging, marketplace / OpenVSX publish, feature work inside the extension
- Multi-host matrix, new editor profiles, host upgrades
- PRD 29 live UX (composing label, `↳ in <epic>`, triage no longer opening with `Likely CONTEXT EXHAUSTION`) — parent #2555
- Typecheck, tests, dist rebuilds, DB migrations — other siblings
- Producing a 2026.9.72 VSIX or rewriting CHANGELOG (path (b) on #2614 — rejected)

### Preconditions

- #2560 has produced `clients/vscode/builderforce-ai-2026.9.79.vsix` (or that basename at the absolute path used).
- A `code` or `cursor` CLI is on PATH in the operator environment.
- #2614 decision (a) is recorded; confirmation asserts **79**, not 72.
