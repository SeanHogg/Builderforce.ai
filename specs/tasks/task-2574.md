# PRD: Live re-test — file and staff two tasks on project 11 (R6)

## Problem & Goal

Work-mode VS Code chat can incorrectly refuse with a manager-role error, even when the operator is acting in a valid work session. Copied chat reports and diagnostics can omit staffing attribution, which blocks verification that an agent was actually staffed. Auth keys may still resolve as `developer` instead of the expected work-mode identity.

**Goal:** On project 11, file two tasks, staff both, and prove R6 end-to-end: work-mode VS Code chat does not return manager-role required; the copied report includes `Staffing:/as <agent>`; a `brain_chat_diagnostics` row exists after Copy; `builtin_chats_diagnostics` returns that row. If the key still resolves as developer, inspect `auth:bfk:v2:`.

## Target users / ICP roles

- **Operator / work-mode user** in VS Code chat (not manager UI).
- **Staffed agent** invoked via `/as <agent>` on a filed task.
- **Downstream verification agents** that consume this PRD and the copied report / diagnostics.

Manager-console-only flows are not the primary path for this re-test.

## Scope

In-scope for project **11** only:

1. File **two** tasks.
2. Staff both tasks (explicit `/as <agent>` staffing).
3. Drive the interaction from **work-mode VS Code chat**.
4. Copy the chat/report after staffing and confirm the copy payload.
5. Confirm diagnostics persistence and queryability:
   - `brain_chat_diagnostics` row written **after Copy**
   - `builtin_chats_diagnostics` returns that row
6. If identity still resolves as `developer`, check `auth:bfk:v2:` and record the resolved role/key prefix (no key material in the report).

## Functional requirements

1. **Task filing:** Create two distinct tasks on project 11 with enough context to staff an agent.
2. **Staffing:** Staff each task as a named agent. Staffing must be visible as `Staffing:/as <agent>` in the copied report (literal prefix plus the agent identifier used).
3. **Work-mode chat:** VS Code work-mode chat must accept the session. It must **not** return a manager-role-required error (or equivalent refusal).
4. **Copy report:** After staffing and chat, Copy must produce a report that includes the Staffing line for each staffed task.
5. **Diagnostics write:** Performing Copy must create a `brain_chat_diagnostics` row (timestamp after the Copy action).
6. **Diagnostics read:** `builtin_chats_diagnostics` must return that same row (matching identifiers / timestamps from the Copy).
7. **Auth fallback:** If the session key still resolves as `developer`, inspect `auth:bfk:v2:` and note whether work-mode identity is present, stale, or missing. Do not treat a developer-resolved key as a pass.

## Acceptance criteria

All of the following must hold on a live run against project 11:

- Two tasks exist on project 11 and both are staffed.
- Work-mode VS Code chat completes the flow with **no** “manager role required” (or equivalent) response.
- Copied report contains `Staffing:/as <agent>` for the staffed agent(s).
- A `brain_chat_diagnostics` row exists with a timestamp **after** Copy.
- `builtin_chats_diagnostics` returns that row.
- Fail the re-test if the auth key still resolves as `developer` unless `auth:bfk:v2:` is checked and the mismatch is documented as the blocking cause.

## Out of scope

- Filing or staffing tasks on any project other than 11.
- Changing product auth, role mapping, or `auth:bfk:v2:` implementation (inspect only).
- Manager-role UI, manager-only chat, or granting manager privileges.
- Unrelated chat diagnostics, historical rows from before this Copy, or non-work-mode clients.
- Exposing, copying, or rotating raw auth keys.
