# PRD: R5 — Operator Applies Migrations 1177/1178

## Problem & Goal

Pending schema/data migrations `1177` and `1178` must be applied in a controlled, auditable way by a human operator. Unapplied or partially applied migrations leave environments inconsistent, block dependent releases, and increase rollback risk.

**Goal:** A designated operator can apply migrations `1177` and `1178` in the correct order, verify they completed, and record the outcome so downstream environments and agents can treat the change as done.

## Target users / ICP roles

- **Primary:** Production operator / SRE on-call executing the runbook
- **Secondary:** Database owner / DBA reviewing pre-checks and post-checks
- **Informed:** Release owner and downstream agents that depend on these migrations being applied

## Scope

- Apply migrations `1177` then `1178` (strict order) in the target environment(s) this release covers
- Pre-flight checks (connectivity, backup/restore point, current schema version, lock/contention risk)
- Execution via the standard migration runner used by this product (no ad-hoc SQL as the happy path)
- Post-apply verification (version table / migration ledger, health checks, sample queries as defined by each migration)
- Operator-visible success/failure, logs, and a recorded completion status for the shared task
- Abort / stop-on-error behavior if either migration fails; no silent continuation to `1178` if `1177` did not succeed

## Functional requirements

1. Operator can identify current applied migration version and confirm `1177` and `1178` are pending before start.
2. Operator can take or confirm a restore point / backup sufficient to recover if apply fails.
3. Operator applies `1177` first; the runner reports success or failure with exit status and logs.
4. Operator applies `1178` only after `1177` is recorded as successfully applied.
5. Each migration is idempotent from the operator’s perspective: re-running an already-applied migration is a no-op or a clear “already applied” result, not a destructive replay.
6. On failure, the system leaves a clear last-applied version, error logs, and does not mark the pair complete.
7. Operator can verify both migrations appear in the migration ledger and that post-checks for `1177` and `1178` pass.
8. Completion is recorded (who, when, environment, versions applied) so other agents on this task treat R5 as done.

## Acceptance criteria

The following **supersede** the original PM draft — in particular, already-applied is **not** a stop. They match Requirements acceptance 1–10. BA **R1–R11** remain the backlog contract. Product-manager (this pass) adopts them unchanged.

1. Pre-flight shows connectivity, a restore point, and `_migrations` state for the two filenames; missing predecessors → stop. Already-applied is **not** a stop (see 6).
2. `1177_coordination_requires_manager.sql` is in `_migrations` before 1178 is started (or 1177 was already present).
3. After the run (or no-op), `_migrations` lists both `1177_coordination_requires_manager.sql` and `1178_brain_chat_diagnostics.sql`.
4. Post-checks in R7 pass (column + table + read-only probes). A live kanban `403 manager role required` is **R6**, not an R5 fail.
5. 1177 failure prevents 1178; either failure is logged and R5 is **not** marked complete.
6. Re-run after success is already-applied / no-op for both, not a rewrite. Both already in `_migrations` **and** R7 green → **R5 complete** (no-op success). Do not refuse.
7. Audit record exists (who, environment, UTC, both IDs, result).
8. Downstream R6/deploy (#2567 / #2574 / #2597) can consume R8 without re-applying.
9. No `specs/tasks/task-2566.md` (or equivalent docs-only stand-in) ships as the deliverable. The copy previously on `builderforce/task-2566` is **deleted** (this pass, commit `1ba6e8976`; gap #2618 tracks the drop).

## Out of scope

- Authoring, editing, or reversing the contents of migrations `1177` / `1178`
- Applying any other migration IDs
- Schema design review, data backfills unrelated to these two files, or application feature work that only *depends* on the new schema
- Automated unattended apply in CI/CD as a substitute for the operator run (unless that is already the standard runner the operator invokes)
- Cross-region / multi-cluster fan-out beyond the environment(s) named in the runbook for this release
- Long-term migration-framework rewrites, new runner features, or operator-platform UX changes not required to apply these two migrations
- Customer-facing product behavior changes except those that automatically take effect once the schema is applied

### User stories

1. As the **production operator**, I need a single ordered procedure (1177 then 1178) against **core** Postgres using the product runner, so the 2026.9.37 worker does not 500 on `coordinationGate` or `chatDiagnosticsStore`.
2. As the **operator**, if both filenames are already in the core ledger, I need a **no-op success** (R5 already done), not a refusal and not a destructive replay.

### Functional requirements

**R1 — Target.** Apply only to **core Postgres** for the environment that will run worker **2026.9.37** (production Neon bound as `NEON_DATABASE_URL`). Not replicas as write targets, not local/dev unless that database *is* that core, not OPERATIONAL/APPS tracks.

**R2 — Artefacts (do not substitute).** Exact files, in order:

1. `api/migrations/1177_coordination_requires_manager.sql`
2. `api/migrations/1178_brain_chat_diagnostics.sql`

No squash, rename, hand-edited SQL, or extra migration IDs. Do not re-author the files.

**R3 — Runner.** Happy path is the standard primary-track runner (`api/scripts/migrate.mjs` / the `pnpm` script that invokes it) with `NEON_DATABASE_URL` set to core. Ad-hoc `psql` is rollback/break-glass only, not the happy path. Architect names the exact command in Design.

**R4 — Pre-flight (before first write).** Operator records:

- Connectivity to core via `NEON_DATABASE_URL`.
- A restore point / backup sufficient to recover a failed apply.
- Current `_migrations` contents for these two filenames (pending, 1177-only, or both).
- Predecessor migrations are present; if the runner would skip or fail because a predecessor is missing, **stop**.

Already-applied is **not** a stop (see R6).

**R5 — Order and abort.**

- Apply 1177 first. Wait until `_migrations` lists `1177_coordination_requires_manager.sql` before starting 1178.
- Apply 1178 only after that ledger write.
- **1177 failure:** do not run 1178; do not mark R5 complete; do not unblock 2026.9.37; leave schema unchanged beyond a failed transaction; surface exit status + logs.
- **1178 failure after 1177 success:** do not mark 1178 applied; leave 1177 in place; keep 2026.9.37 blocked; operator re-runs **from 1178** after fix.

**R6 — Idempotency (corrects the PM AC).** From the operator’s seat:

- 1177 already in `_migrations` → skip 1177 (no destructive replay) and continue to 1178 if needed.
- Both already in `_migrations` **and** post-checks (R7) pass → **R5 complete** (no-op success). Do not refuse, do not rewrite schema.
- Re-run after success → runner reports already applied / no-op for both.

**R7 — Post-checks (all required).** After the runner returns success (or no-op):

1. `_migrations` contains `1177_coordination_requires_manager.sql` and `1178_brain_chat_diagnostics.sql`.
2. `project_manager_configs.coordination_requires_manager` exists, `boolean`, `NOT NULL`, default `false`.
3. Relation `brain_chat_diagnostics` exists (plus the indexes created by 1178).
4. A read-only SQL probe of that column and of `brain_chat_diagnostics` does **not** error. This probe does **not** require worker 2026.9.37.

Do **not** require a live kanban `403` to disappear here (R6).

**R8 — Unblock signal (the only “R5 complete”).** All of:

- R7 probes green on the target core,
- audit record (R9),
- 2026.9.37 worker / API deploy for that environment **may** proceed (this ticket does not perform the deploy).

Downstream agents consume this signal and **must not re-apply**. Paste ledger rows + probe output onto **#2573 and #2566** (or a single comment linked from both).

**R9 — Audit.** Record operator identity, environment (core / Neon), start and end UTC, both filenames, runner exit, pass/fail. Failure must not record R5 complete.

**R10 — Who may apply.** A human operator with core `NEON_DATABASE_URL` (SRE / DBA / Sean on #2573). Cloud agents, BA/developer containers, and this executor **cannot** apply. They must not sign the **developer/operator** slot as complete without pasted ledger proof.

**R11 — No stand-in deliverable.** Forbidden as R5: new/edited SQL, `specs/tasks/task-2566.md` (or `task-2573.md`), runbook-only PRs, and BA/architect prose without R7 proof. Those do not unblock 2026.9.37.
