# PRD: R5 — Operator Applies Migrations 1177/1178

## Problem & Goal

Pending schema/data migrations `1177` and `1178` must be applied in a controlled, auditable way by a human operator. Unapplied or partially applied migrations leave environments inconsistent, block dependent releases, and increase rollback risk.

**Goal:** A designated operator can apply migrations `1177` and `1178` in the correct order, verify they completed, and record the outcome so downstream environments and agents can treat the change as done.

## Target users / ICP roles

- **Primary:** Production operator / SRE on-call executing the runbook
- **Secondary:** Database owner / DBA reviewing pre-checks and post-checks
- **Informed:** Release owner and downstream agents that depend on these migrations being applied

## Scope

- Apply migrations `1177` then `1178` (strict order) in the target environment(s) this release covers
- Pre-flight checks (connectivity, backup/restore point, current schema version, lock/contention risk)
- Execution via the standard migration runner used by this product (no ad-hoc SQL as the happy path)
- Post-apply verification (version table / migration ledger, health checks, sample queries as defined by each migration)
- Operator-visible success/failure, logs, and a recorded completion status for the shared task
- Abort / stop-on-error behavior if either migration fails; no silent continuation to `1178` if `1177` did not succeed

## Functional requirements

1. Operator can identify current applied migration version and confirm `1177` and `1178` are pending before start.
2. Operator can take or confirm a restore point / backup sufficient to recover if apply fails.
3. Operator applies `1177` first; the runner reports success or failure with exit status and logs.
4. Operator applies `1178` only after `1177` is recorded as successfully applied.
5. Each migration is idempotent from the operator’s perspective: re-running an already-applied migration is a no-op or a clear “already applied” result, not a destructive replay.
6. On failure, the system leaves a clear last-applied version, error logs, and does not mark the pair complete.
7. Operator can verify both migrations appear in the migration ledger and that post-checks for `1177` and `1178` pass.
8. Completion is recorded (who, when, environment, versions applied) so other agents on this task treat R5 as done.

## Acceptance criteria

- Pre-check shows `1177` and `1178` pending; operator does not proceed if either is already applied or if a predecessor is missing.
- `1177` applied successfully; ledger shows `1177` applied before `1178` is started.
- `1178` applied successfully after `1177`.
- Post-checks for both migrations pass; application health checks remain green (or match the documented expected post-migration state).
- Failure of `1177` prevents `1178`; failure of either is visible, logged, and does not record R5 as complete.
- Re-run after success reports already applied / no-op for both.
- Audit record exists: operator identity, environment, timestamps, and both migration IDs.
- Downstream agents can consume a single “R5 complete” signal without re-applying.

## Out of scope

- Authoring, editing, or reversing the contents of migrations `1177` / `1178`
- Applying any other migration IDs
- Schema design review, data backfills unrelated to these two files, or application feature work that only *depends* on the new schema
- Automated unattended apply in CI/CD as a substitute for the operator run (unless that is already the standard runner the operator invokes)
- Cross-region / multi-cluster fan-out beyond the environment(s) named in the runbook for this release
- Long-term migration-framework rewrites, new runner features, or operator-platform UX changes not required to apply these two migrations
- Customer-facing product behavior changes except those that automatically take effect once the schema is applied
