# PRD: Apply core Postgres migrations 1177 and 1178 before 2026.9.37 worker deploy

**Status:** WIP  
**Type:** R5 operator action (pre-deploy gate)  
**Owner:** Core platform / operator runbook  
**Depends on:** `1177_coordination_requires_manager.sql`, `1178_brain_chat_diagnostics.sql`  
**Blocks:** 2026.9.37 worker / API deploy

## Problem & Goal

The 2026.9.37 worker expects two new core-Postgres stores to already exist: coordination gate state that requires a manager, and brain-chat diagnostics. Those objects are created only by migrations **1177** and **1178**. If the worker is deployed before both migrations have landed on **core**, gate and diagnostics paths will 500.

**Goal:** Apply `1177_coordination_requires_manager.sql` and `1178_brain_chat_diagnostics.sql` to core Postgres, verify they are recorded as applied, and only then allow the 2026.9.37 worker (and API that depends on it) to deploy.

## Target users / ICP roles

- **R5 operators** executing the pre-deploy migration action.
- **Release / deploy agents** that must treat this as a hard gate before 2026.9.37.
- **Downstream implementers** (migration runner, health checks, rollback) sharing this PRD.

End users are not in scope; this is an internal ops prerequisite.

## Scope

- Run both SQL migrations against **core Postgres only**, in numeric order: 1177 then 1178.
- Confirm schema/objects expected by gate and diagnostics stores exist and that the migration ledger lists 1177 and 1178 as applied.
- Block 2026.9.37 worker (and API deploy that ships that worker) until verification succeeds.
- Document operator steps, failure handling, and the unblock signal for deploy.

Out of this document’s execution: product behavior of coordination-requires-manager or brain-chat diagnostics beyond “stores must not 500 after deploy.”

## Functional requirements

1. **Ordered apply on core**
   - Target database: core Postgres (not replicas as write targets, not non-core clusters).
   - Apply `1177_coordination_requires_manager.sql` first; apply `1178_brain_chat_diagnostics.sql` only after 1177 succeeds and is recorded.
   - Do not skip, reorder, or partially apply.

2. **Idempotency and ledger**
   - If 1177 is already applied, do not re-apply destructively; proceed to 1178.
   - If both are already applied, treat the action as already complete and emit the same success signal.
   - Migration runner must write both versions into the core migration history used by this environment.

3. **Pre-deploy gate**
   - 2026.9.37 worker must not be rolled out until both migrations are applied on the core instance that worker will use.
   - API deploy that includes that worker is likewise blocked.
   - Gate is environment-specific (each core that will receive 2026.9.37).

4. **Failure behavior**
   - On 1177 failure: abort; do not run 1178; do not deploy 2026.9.37; surface error and leave schema unchanged beyond a failed transaction.
   - On 1178 failure after 1177 success: abort deploy; do not mark 1178 applied; leave 1177 in place (forward-only unless an approved rollback of 1178’s partial objects is required).
   - Operator must be able to re-run from the failed step after fix.

5. **Verification**
   - After apply, confirm:
     - Migration history includes 1177 and 1178.
     - Objects/tables/indexes created by each file exist on core.
     - A lightweight read against gate and diagnostics stores does not 500 (no worker 2026.9.37 required for this check if a SQL/psql probe is available).
   - Only then set the deploy-ready flag / handoff for 2026.9.37.

6. **Audit**
   - Record who ran the action, environment, start/end time, migration versions, and pass/fail.
   - Sufficient for R5 operator traceability.

## Acceptance criteria

- [ ] On core Postgres for the target environment, migration 1177 is applied and listed in migration history **before** 1178 is applied.
- [ ] Migration 1178 is applied and listed in migration history.
- [ ] Files used are `1177_coordination_requires_manager.sql` and `1178_brain_chat_diagnostics.sql` (no substitute or squash that omits either).
- [ ] Gate store and diagnostics store schema expected by 2026.9.37 exist; a post-migration probe against those stores does not return 500.
- [ ] 2026.9.37 worker is not deployed (and API deploy is not unblocked) until the above is true for that environment’s core.
- [ ] Re-running the action when both migrations are already applied is a no-op success, not an error and not a schema rewrite.
- [ ] Failed apply of either file leaves deploy blocked and produces an operator-visible error with version and environment.
- [ ] Operator audit log contains environment, versions 1177 and 1178, result, and timestamp.

## Out of scope

- Applying 1177/1178 to non-core databases, analytics replicas, or local/dev DBs unless they are the actual core for that deploy target.
- Authoring or editing the SQL of 1177/1178; changing coordination or diagnostics product behavior.
- Backfill of historical coordination/diagnostics data.
- Deploying 2026.9.37 itself, API feature flags, or worker config beyond the migration gate.
- Rollback of 2026.9.37 after a successful migrate+deploy.
- Multi-region fan-out except as separate per-core repeats of this same action.
- Application-level tests of manager-required coordination or brain-chat diagnostics UX.
