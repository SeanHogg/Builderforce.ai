# PRD: Chat-row context-window usage meter

**Status:** WIP  
**Related:** product insight from analysis of #2442 / epic #2436. Dedicated ticket required; do not implement under #2442 or fold into #2436.

## Problem & Goal

Developers cannot tell from the chat list how full a conversation’s model context window is (`usedTokens / modelContextWindow`). They only learn they have hit the limit after a send fails.

#2442 is unrelated: it shows linked-ticket progress (`ticketProgressPct`) on Sessions TreeView rows as `{relativeTime} · {n}%` in `TreeItem.description`. That is not a context-window meter.

**Goal:** Surface a compact, glanceable context-fill indicator on each chat row so users can see remaining headroom before they send, without mixing it with ticket-complete % or duplicating meters.

## Target users / ICP roles

- Extension users who keep multiple chat sessions open and switch among them in the Sessions tree.
- Users of models with tight or varying context windows who hit send-time failures when a thread is full.
- Power users who prune, branch, or start a new chat when a thread is near capacity.

## Scope

In-scope for this PRD (product definition only):

- A compact context-fill affordance on VSIX Sessions TreeView **chat** rows.
- Display of fill as a short percentage (or equivalent) derived from `usedTokens / modelContextWindow`.
- A tooltip with absolute used and limit token counts.
- Hide/omit the meter when usage cannot be computed.
- An explicit layout rule relative to existing row text (relative time, #2442 ticket progress) so the two `%` signals never double-render without a decided composition.

Out of scope for this document’s *implementation* (see Out of scope). This PRD is the shared spec for a dedicated follow-up ticket.

## Functional requirements

1. **Data**
   - For each chat row, compute fill as `usedTokens / modelContextWindow` when both values are known and `modelContextWindow > 0`.
   - Treat missing, zero, or stale window size, missing used-token count, or a model with no advertised window as **uncomputable**.

2. **Row presentation**
   - When computable, show a compact fill on the chat row, e.g. `· n%` (integer percent, rounded in a single consistent direction documented in the implementing ticket).
   - Keep the control glanceable: no extra TreeItem, no second row, no progress bar unless a later PRD replaces this compact form.
   - Do **not** reuse or overload `ticketProgressPct` / #2442 description text. Ticket complete % and context fill are different quantities.

3. **Layout vs ticket progress**
   - Default: do not show two adjacent `n%` fragments on the same row.
   - If a row already shows #2442 ticket progress in `TreeItem.description`, the implementing design must pick **one** explicit composition (not both ad hoc):
     - context fill only in description, ticket % elsewhere (or vice versa), **or**
     - a single combined description with distinct labels (e.g. time · ticket n% · ctx n%), **or**
     - context fill only in tooltip / accessibility text when description is already occupied.
   - That choice is a required decision in the implementing ticket; this PRD does not default to stacking two unlabeled percentages.

4. **Tooltip**
   - When the meter is shown, tooltip includes used tokens and window limit (e.g. `12,400 / 128,000 tokens` plus the same percent).
   - When hidden as uncomputable, do not show a misleading 0% or empty fraction.

5. **Visibility rules**
   - Hide the meter when uncomputable.
   - Update the meter when token usage or the session’s model (hence window) changes; do not leave a percent from a previous model.
   - Chat rows only; not folders, ticket nodes, or non-conversation tree items.

6. **Accessibility**
   - Screen-reader / `TreeItem` accessibility text must distinguish “context window n% full” from “ticket n% complete” so the two are never announced as the same metric.

## Acceptance criteria

- Given a chat with known `usedTokens` and `modelContextWindow`, the Sessions row shows a compact fill (e.g. `· 37%`) that matches `round(usedTokens / modelContextWindow * 100)` per the chosen rounding rule.
- Hovering that row shows used and limit token counts and the same percent.
- Given missing used tokens, missing/zero window, or unknown model window, the row shows **no** context percent and **no** `0 / 0` (or similar) tooltip.
- Changing the session model recomputes or hides the meter; a stale percent from the previous window is not left on the row.
- A row that already displays #2442 `{relativeTime} · {n}%` ticket progress does not also show an unlabeled second `n%` for context. Layout matches the single explicit composition chosen in the implementing ticket.
- Ticket-complete % (#2436 / #2442) and context-fill % are stored, labeled, and announced as separate fields.
- Non-chat tree items are unchanged.

## Out of scope

- Implementation, coding, or shipping this meter in the #2442 or #2436 work.
- Folding context fill into `ticketProgressPct` or epic #2436 ticket-complete %.
- Token counting accuracy, tokenizer choice, or changing how `usedTokens` is produced (this PRD only displays values the session already has or can obtain).
- Warnings, send blocking, auto-summarize, or compaction when the window is nearly full.
- Settings to toggle the meter, custom thresholds, or color-coding (unless a later PRD adds them).
- Chat editor / input chrome meters (this is the **list row** only).
- Web/non-VSIX surfaces.

### R0 — Identity, surface, and non-mixing

- This ticket owns a **context-window fill meter** on VSIX Sessions TreeView **conversation / chat rows only** (`clients/vscode` Sessions tree; chat `TreeItem`s in `sessionsTree.ts`).
- Fill is `usedTokens / modelContextWindow`. It is **not** linked-ticket complete % (`BfBrainChat.ticketProgressPct`, epic #2436, #2439 / #2442 `{relativeTime} · {n}%` on `TreeItem.description`).
- MUST NOT fold context fill into `ticketProgressPct`, `progressPct`, ChatTicketService ceremony totals (#2551), or any #2436 child.
- MUST NOT implement this meter on the #2442 or #2436 branches.
- Title (`TreeItem.label`) stays title-only (same rule as #2442: no `{n}% · title` prefix).
- Out of this ticket’s UI surface: folders, ticket nodes, non-conversation tree items, brain-ui chat switcher/dropdown (#2440 / #2443), web / non-VSIX, chat editor / input chrome.

### R1 — Computability

Context fill is **computable** iff all of the following hold:

1. `usedTokens` is a known finite number ≥ 0 (zero used is allowed).
2. `modelContextWindow` is a known finite number **> 0**.
3. The window and used count belong to the **current** session model (not a previous model’s leftovers).

**Uncomputable** (meter MUST be omitted) when any of: missing used-token count; missing / zero / negative / non-finite window; model does not advertise a window; used/window pair is stale relative to the current model.

| usedTokens | modelContextWindow | Result |
|---|---|---|
| 0 | > 0, current model | Computable **0%** — **show** it |
| missing | any | Uncomputable — **hide** |
| any | missing, 0, or non-finite | Uncomputable — **hide** |
| known | > 0, previous model | Uncomputable until recomputed — **hide** stale % |

This ticket does **not** change token counting, tokenizer choice, or how used tokens are produced. It displays values the session already has or can obtain.

### R2 — Derived percent

When computable:

- `contextFillPct = clamp(round(usedTokens / modelContextWindow * 100), 0, 100)`
- Rounding: nearest integer, **half-up** (0.5 → 1). This is the single rounding rule; do not mix floor/ceil across tooltip, description, and a11y.
- Overfill (`usedTokens > modelContextWindow`) displays as **100%**, never a value > 100.
- Numeric **0** shows when computable. **null / undefined / uncomputable omits** — never coerce with `?? 0` (that would lie as 0% full).
- Persist and announce as a **separate** field from `ticketProgressPct`. Suggested DTO: raw `usedTokens` + `modelContextWindow` (tooltip) and optional derived `contextFillPct`. Architect names the fields in Design.

### R3 — Row presentation (always labeled)

When computable, the chat row shows a compact **labeled** fragment:

`ctx {n}%`

where `{n}` is `contextFillPct`.

- MUST include the `ctx` label (exact token `ctx`, lowercase) so the fragment cannot be mistaken for #2442 ticket `· {n}%`.
- MUST NOT use a bare unlabeled `· {n}%` for context fill — that collides with #2442 even on rows that have **no** linked ticket.
- No extra TreeItem, no second row, no progress bar.
- Glanceable: one short fragment on the existing chat row.

### R4 — Layout vs #2442 ticket progress (explicit composition)

**Decision:** one combined `TreeItem.description`; never two unlabeled `%` fragments. Keep #2442’s unlabeled ticket fragment unchanged; always label context.

| Ticket % (#2442 `ticketProgressPct`) | Context fill | `TreeItem.description` |
|---|---|---|
| absent / omitted | uncomputable | `{relativeTime}` (unchanged) |
| absent / omitted | computable | `{relativeTime} · ctx {n}%` |
| present (incl. 0) | uncomputable | `{relativeTime} · {ticket}%` (#2442 unchanged) |
| present (incl. 0) | computable | `{relativeTime} · {ticket}% · ctx {n}%` |

- Order, left to right: relative time, then ticket %, then ctx %.
- Do not relabel the ticket fragment in this ticket (`ticket 85%` is a #2442 change, out of scope).
- If the tree would truncate description, **do not** drop the `ctx` label to save space: omit the whole context fragment rather than emit an unlabeled `%`. Tooltip (R5) still carries used/limit when computable.
- Tooltip and a11y are independent of description occupancy: they still distinguish the two metrics when both exist.

### R5 — Tooltip

When the meter is shown (computable):

- Tooltip MUST include used tokens, window limit, and the same `contextFillPct`.
- Format: `Context {used} / {limit} tokens ({n}% full)` with locale grouping separators (e.g. `Context 12,400 / 128,000 tokens (37% full)`).
- MUST be distinguishable from any ticket-progress tooltip copy.

When uncomputable:

- MUST NOT show `0%`, `0 / 0`, an empty fraction, or any implied fill.
- Existing non-context tooltip content (if any) is unchanged.

### R6 — Visibility, refresh, model change

- Hide the meter when uncomputable.
- Recompute when token usage changes (after a send/response that updates used tokens) **or** when the session model (hence window) changes.
- On model change: recompute against the new window or hide. MUST NOT leave a percent computed from the previous window on the row, tooltip, or a11y text.
- Chat rows only; non-chat tree items are unchanged.

### R7 — Accessibility

- Screen-reader / `TreeItem.accessibilityInformation` (or equivalent) MUST announce context fill as **“context window {n}% full”** (optionally “context window {used} of {limit} tokens, {n}% full”).
- Ticket complete remains **“ticket {n}% complete”** (or the existing #2442 a11y string).
- The two MUST never be announced as the same metric or as a single unlabeled percent.
- When uncomputable, do not announce “0% full”.

### R8 — Out of scope (this ticket)

- Implementation on #2442 / #2436; folding into `ticketProgressPct`.
- Token counting accuracy, tokenizer, changing production of used tokens.
- Warnings, send blocking, auto-summarize, or compaction when nearly full.
- Settings to toggle the meter, custom thresholds, or color-coding.
- Chat editor / input chrome meters (list row only).
- Web / non-VSIX / brain-ui dropdown meters (those remain unlabeled follow-ups, not silent scope).
- Relabeling #2442’s ticket `· {n}%` fragment.
