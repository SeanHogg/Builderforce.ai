# Product Requirements Document (PRD)

## Problem & Goal

### Problem
The current implementation of the `CalendarEventInput` type does not include a `location` field, relying instead on the `joinUrl` to represent the meeting location. The proposed design for #2621 introduces a `location` field to `CalendarEventInput`, but it is unclear whether the `meetings.location` column exists in the database. This ambiguity needs to be resolved to ensure the correct mapping of advisory meeting locations to remote calendar events.

### Goal
Determine the existence of the `meetings.location` column and decide on the appropriate course of action for the `CalendarEventInput` type to support meeting locations effectively.

## Target Users / ICP Roles
- **Product Managers**: Need to understand the implications of the `location` field on the product roadmap.
- **Developers**: Responsible for implementing the changes based on the decision.
- **QA Engineers**: Must verify the correct behavior of the `location` field in the application.

## Scope
- Determine the existence of the `meetings.location` column in the database.
- Decide whether to:
  - Pass the `meetings.location` through to `CalendarEventInput` if it exists.
  - Add a nullable `location` column via migration if it does not exist.
  - Remove the `location` field from `CalendarEventInput` if the `meetings.location` column does not exist and maintain the existing behavior using `joinUrl`.
- Update the design and implementation accordingly.

## Functional Requirements

1. **Check for `meetings.location` Column**
   - Verify the existence of the `meetings.location` column in the database schema.
   - If the column exists, ensure it is accessible and can be read by the application.

2. **Update `CalendarEventInput`**
   - If `meetings.location` exists:
     - Pass the `location` value through to the `CalendarEventInput` type.
     - Ensure the mapping from `meetings.location` to `CalendarEventInput.location` is correctly implemented.
   - If `meetings.location` does not exist:
     - Decide whether to add a nullable `location` column via migration.
     - Alternatively, remove the `location` field from `CalendarEventInput` and continue using `joinUrl` as the location.

3. **Update Documentation**
   - Update the relevant design documents (D-14, D-9) to reflect the changes made.
   - Ensure that the API documentation accurately describes the `CalendarEventInput` type, including the `location` field if applicable.

4. **Testing**
   - Implement unit tests to verify the correct behavior of the `location` field based on the decision made.
   - Ensure that existing functionality related to `joinUrl` remains unaffected if the `location` field is not added.

## Acceptance Criteria

1. The existence of the `meetings.location` column is confirmed.
2. The `CalendarEventInput` type is updated appropriately based on the existence of the `meetings.location` column:
   - If the column exists, the `location` field is correctly mapped.
   - If the column does not exist, the decision to add a nullable column or remove the `location` field is implemented.
3. All relevant documentation is updated to reflect the changes.
4. Unit tests are in place to verify the correct behavior of the `location` field.
5. No regression is introduced in the existing functionality related to `joinUrl`.

## Out of Scope

- **Migration of Existing Data**: If a new `location` column is added, migrating existing data is not in scope for this task.
- **UI Changes**: Updating the user interface to display or input the meeting location is not part of this task.
- **Provider Integration**: Handling the `location` field with different calendar providers is not addressed in this task.
- **Error Handling**: Specific error handling related to the `location` field is not in scope unless it affects the core functionality.
