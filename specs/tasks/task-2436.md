# PRD: Chat list progress percentage (VSIX)

## Problem & Goal

Chat lists in the VS Code extension show titles and timestamps but not ticket completion. Users scanning the **Chats** sidebar or the in-chat switcher cannot tell which conversations are done vs still in progress without opening each chat.

**Goal:** Surface a per-chat ticket progress percentage on every chat list row (sidebar tree and in-chat dropdown), computed once on the server and returned with `GET /api/brain/chats`, with list UI refreshing when ticket health changes.

## Target users / ICP roles

- Developers using the Brain VS Code extension who juggle multiple ticket-backed chats
- Anyone triaging or switching chats from the sidebar or chat switcher

## Scope

1. Extend `GET /api/brain/chats` to include per-chat `progressPct`, batched via `ChatTicketService` (no N+1).
2. Add optional `progressPct?: number` to `BfBrainChat` in `bfApi.ts`.
3. Render the percentage in `sessionsTree.ts` on `chat item.description`.
4. Render the same percentage in the brain-ui chat switcher / dropdown.
5. Refresh list/switcher display when ticket health changes.

## Functional requirements

- **List payload:** Each chat in `GET /api/brain/chats` includes `progressPct` when ticket progress is known. Computation is batched server-side through `ChatTicketService`.
- **Client type:** `BfBrainChat` exposes `progressPct?: number`. Clients treat a missing value as “no progress to show.”
- **Sidebar (Chats):** Each chat row shows progress next to title/time, e.g. `· 85%`.
- **Chat switcher:** Dropdown items show the same percentage, same source field.
- **Refresh:** When ticket health updates, sidebar rows and the switcher re-read/re-render `progressPct` without a separate per-chat progress fetch.
- **Performance:** Listing chats must not issue per-chat progress requests.

## Acceptance criteria

- Chat rows in the VSIX sidebar show `· 85%` (or equivalent) next to title/time when `progressPct` is present.
- The chat switcher dropdown shows the same percentage for the same chats.
- Progress is computed server-side on the list endpoint; no N+1 API calls for progress.
- Chats without ticket progress omit the percentage rather than showing a misleading `0%` or placeholder.
- After a ticket health change, both the sidebar list and the switcher reflect the updated percentage.

## Out of scope

- Changing how ticket progress itself is calculated inside `ChatTicketService`
- Progress UI on surfaces other than the Chats sidebar tree and the in-chat switcher/dropdown
- Filtering, sorting, or grouping chats by progress
- Web/non-VSIX chat lists
- Historical progress charts, tooltips with ticket breakdown, or click-through from `%` to ticket details
- New endpoints dedicated to progress; progress rides only on the existing chats list response

### Field contract (resolves #2438 open point)

Epic goal is **ticket completion on chat list rows**, not streaming/generation progress.

Existing list fields stay:

- `ticketCount?: number`
- `ticketProgressPct?: number \| null` — `null` / omitted = no linked tickets

Add:

- `progressPct?: number` — optional **number** (not `number \| null`). Absent = unknown / nothing to show.

**Populate `progressPct` from the same ChatTicketService rollup as `ticketProgressPct`:**

- No linked tickets / no summary → **omit** `progressPct`. Keep `ticketProgressPct: null` (or omit).
- Linked tickets with a known pct, **including 0** → set `progressPct` to that integer 0–100 **and** set `ticketProgressPct` to the same number.
- When both are present they **must match**.

**Forbid** `progressPct: summary?.pct ?? 0` when there is no summary. That is a misleading `0%` and violates epic AC (“chats without ticket progress omit the percentage”). Child #2437 BA “never null / default 0” is **overruled** by this epic AC.

Numeric **0 shows** (` · 0%`) — that is a real incomplete ticket. `null` / `undefined` **omits**. Same rule as project fact `ticket-2440-progresspct-not-encoding`.

UI reads `progressPct` first; if absent, may fall back to `ticketProgressPct` **only when it is a finite number** (not `null`). That keeps #2551’s existing list fields visible if #2437 has not landed yet.

Do **not** treat `progressPct` as in-flight generation. Token/stream progress is out of scope.

### Overlap with bug #2551

#2551 owns ChatTicketService ceremony totals (`total: 1` for incomplete spec/roadmap/retro), `aggregateTicketHealth` treating `total: 0` as weight 1, and attaching `ticketCount` + `ticketProgressPct`. This epic **must not** re-implement that math (epic out of scope: “changing how ticket progress itself is calculated”).

#2551 display sketch was a **title prefix** `67% · title`. This epic’s AC is a **meta suffix** next to title/time: ` · 85%`.

**Bind display here:** keep the chat **title** unchanged. Put ` · {n}%` on the **description / secondary** slot (`TreeItem.description` in `sessionsTree.ts`; equivalent secondary text in the brain-ui switcher). Do not also prefix the title. If #2551 later prefixes the title, drop one of the two — do not show `%` twice.

### Server (#2437, #2444)

1. In the `GET /api/brain/chats` handler, after the page of chats is loaded, call the existing batch (`ChatTicketService.summarizeChatsTicketHealth` / `attachChatTicketSummaries` / `rollupChatTicketHealth` — use the helper already on main, do not add a parallel rollup).
2. One batch per list request, keyed by the chat ids on that page. No per-chat HTTP and no per-chat progress queries.
3. Fail-soft: if the batch throws, still return the chat list; omit `progressPct` (and leave `ticketProgressPct` as today).
4. No new endpoints. Progress rides only on this list response.
5. Test: spy that the batch is invoked **once** per list request, not once per chat.

### Client type (#2438)

Add `progressPct?: number` with a one-line JSDoc: ticket rollup 0–100 from `GET /api/brain/chats`; absent on older servers / chats with no ticket health; distinct from `ticketProgressPct` (`null` = no linked tickets).

Preserve every existing field. `BrainChat` in `brain-embedded` is a different type — only touch it if the list payload is mapped through it; do not invent a second semantic.

### Sidebar (#2439, #2442)

File: `clients/vscode/src/sessionsTree.ts`.

Shared helper (same module or a tiny util used by tree + switcher):

```ts
function formatChatListProgressPct(
  chat: { progressPct?: number; ticketProgressPct?: number | null },
): string {
  const raw =
    typeof chat.progressPct === "number" && Number.isFinite(chat.progressPct)
      ? chat.progressPct
      : typeof chat.ticketProgressPct === "number" && Number.isFinite(chat.ticketProgressPct)
        ? chat.ticketProgressPct
        : undefined;
  if (raw === undefined) return "";
  return ` · ${Math.round(raw)}%`;
}
```

Append the return value to **`item.description`** (existing time/meta). Do not replace `item.label`. Empty string when unknown — never `" · 0%"` from a missing field, never a placeholder.

`conversationTreeLabel` already reads `ticketProgressPct`. Do not duplicate the percentage onto the label in this epic.
