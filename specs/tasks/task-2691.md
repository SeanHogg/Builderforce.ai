# PRD: Guard Against Full-File Overwrite When Repo Read Paths Are Down

## Problem & Goal

**Problem:** When repository read tools (`list_files`, `read_file`, `git_status`, `run_command`) fail with errors like "no repository bound" while `write_file` remains operational, agents can misinterpret a failed read as "file is empty." Combined with stale project memory advice that encourages attempting writes even when reads fail, this leads agents to overwrite existing files with only their new, partial content — destroying pre-existing history.

This exact failure mode occurred on `seanhogg/builderforce.ai`: a failed read of `DONE.md` was misreported as empty, an agent appended 5 lines via `write_file`, and the resulting diff (`additions:5, deletions:34118`) deleted 34,118 lines of accumulated history. The PR was docs-only and green-build, so it was eligible for auto-merge under `prMergePolicy:"on_green"`, and review artifacts (Architect Design) repeated the same false "file is empty" claim, so no human caught it.

**Goal:** Make it structurally impossible (or at minimum, very hard) for a read-path failure to silently become a destructive full-file overwrite, and ensure any resulting large-deletion diff is caught by the merge gate even under auto-merge policies.

## Target Users / Roles

- **Autonomous coding agents** (task executors) that read, edit, and write files in customer repos.
- **Architect/reviewer agents** that produce design docs and review diffs before merge.
- **Merge-gate / CI policy system** that decides on auto-merge eligibility.
- **Human reviewers / team leads** who are the backstop when heuristics flag risk.
- **Project memory / knowledge base maintainers** who curate reusable facts agents rely on.

## Scope

In scope:
- Tool-level safeguards in the read/write/edit file execution layer.
- Agent behavior/prompting changes for choosing `edit_file` vs `write_file`.
- Merge-gate heuristic for large deletion-to-addition ratios.
- Correction of the specific misleading memory fact `repo-tools-write-works-when-reads-fail`.

Out of scope: see "Out of Scope" section below.

## Functional Requirements

### FR1 — Hard-stop on unverifiable overwrite target
When an agent (or the write tool itself) is about to call `write_file` on a path that **already exists** in the repo, and the preceding `read_file`/`list_files`/`git_status` call for that path either:
- returned an error/failure status, or
- returned empty content in a context where the tool cannot positively confirm the file is genuinely empty (e.g., `git_status`/`list_files` also failed or are inconsistent),

then the system must treat this as a **hard stop**: abort the write, surface an explicit error to the agent (e.g., "cannot verify current content of existing file; refusing overwrite"), and require either a successful re-read or explicit human/task-owner override before proceeding.

### FR2 — Existence check independent of read success
`write_file` must, prior to execution, perform (or receive from the calling agent framework) an independent existence check for the target path that does not rely solely on the same failing read path already reported as broken. If existence cannot be determined, default to treating the file as **existing** (fail safe, not fail open).

### FR3 — Prefer `edit_file` for additive tasks
For tasks classified as additive (e.g., appending a completion note, updating a changelog, closing out a checklist item), the agent tooling/prompting must prefer `edit_file` (surgical insert/append) over `write_file` (full replace). `write_file` should be reserved for genuine new-file creation or explicit full-content replacement tasks.

### FR4 — Merge-gate deletion/addition heuristic
The merge gate must compute a deletion-to-addition ratio (or absolute large-deletion threshold) per PR, independent of `docsOnly`/`codeChanged` flags and independent of green-build status. If deletions exceed additions by a configurable large margin (e.g., deletions > N× additions or deletions > absolute threshold X), the PR must be automatically flagged for **mandatory human review**, overriding `allowAutoMerge` for that PR regardless of `prMergePolicy` setting.

### FR5 — Correct the misleading memory fact
The project memory fact `repo-tools-write-works-when-reads-fail` must be edited (not deleted, to preserve the useful part) to explicitly scope its guidance: writing when reads fail is safe **only for new-file creation**, and is unsafe/prohibited for editing or overwriting existing files. The corrected fact must state the FR1 hard-stop behavior as the required action for existing-file targets.

### FR6 — Review artifact accuracy signal
When a read failure occurs during design/review generation (e.g., Architect Design), the generated artifact must not assert factual claims about file contents/size (e.g., "file is empty (0 bytes)") without flagging that the underlying read failed. Reviewers must be able to see a "read failed — content unverified" marker rather than a false empty-file claim.

## Acceptance Criteria

1. **AC1:** Given a target file exists in the repo and the preceding read call for that file failed or ambiguously returned empty due to a tooling error, a subsequent `write_file` call on that path is rejected with an explicit error, and no commit is made.
2. **AC2:** Given the same scenario as AC1, but the task is additive in nature, the system/agent guidance results in an `edit_file` call being attempted instead of `write_file`, and this succeeds once read paths are restored (or is itself blocked with a clear error if reads remain unverified).
3. **AC3:** A test PR with `additions:5, deletions:34118` (or any diff where deletions vastly exceed additions) is automatically flagged for human review by the merge gate, even when `docsOnly:true`, `codeChanged:false`, and build status is green.
4. **AC4:** The memory fact `repo-tools-write-works-when-reads-fail` no longer contains unscoped "always ATTEMPT the write_file" guidance; it explicitly distinguishes new-file creation (safe) from existing-file overwrite (unsafe, blocked).
5. **AC5:** A regenerated Architect Design or review artifact for a scenario where reads fail on an existing file does not assert "file is empty" as fact; it surfaces a read-failure warning instead.
6. **AC6:** No regression: normal write/edit operations on healthy repos (reads succeeding) are unaffected in behavior or latency beyond negligible overhead from the existence check.

## Out of Scope

- Restoring the actual lost content of `DONE.md` on `builderforce/task-2568` — tracked separately on #2568 via the team-lead `changes_requested` verdict (signoff `30b043bd`).
- Root-causing or fixing why `list_files`/`read_file`/`git_status`/`run_command` return "no repository bound" in the first place (the underlying repo-binding infrastructure issue).
- General-purpose diff-review UX redesign beyond the specific deletion/addition heuristic.
- Broader auto-merge policy overhaul beyond adding this one override condition.
- Retroactive audit of other repos/PRs for similar historical data loss (may be a follow-up task, not part of this PRD).
