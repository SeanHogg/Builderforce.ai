# PRD: VSIX chat ticket overall % vs 0% rings, and ticket % in chat dropdown

## Problem & Goal

The VSIX Brain ticket rail header can report a misleading overall, e.g. `6 tickets 100% · 4/4`, while associated spec/roadmap chips sit at `0%` with empty captions. Incomplete ceremony tickets (spec / roadmap / retro) currently emit `total: 0` (`total: done ? 1 : 0`). `aggregateTicketHealth` weights `progressPct` by `total`, so those `0%` tickets drop out of the mean and the done/count fraction.

The chat conversation `<select>` (and Sessions tree) only shows title plus live-run glyphs (`❓` / `●`). Operators cannot see which conversation still needs a return without opening it.

**Goal:** Incomplete spec/roadmap/retro tickets count as weight `1` at `0%` so the header mean and fraction match the chips. Chat list surfaces per-conversation ticket health (`ticketCount` + `ticketProgressPct`) in the dropdown and Sessions tree as `NN% · title`. Keep old-server payloads (`total: 0`) rolling up correctly. Lock the screenshot mix with tests.

## Target users / ICP roles

- **VSIX operator** — Brain ticket rail and chat dropdown while driving linked tickets.
- **Downstream agents** — shared contract for ticket totals, aggregate health, and chat-list fields.

## Scope

- `ChatTicketService` totals for incomplete spec / roadmap / retro (and ceremony equivalents).
- `aggregateTicketHealth` weighting, including `total: 0` as weight `1`.
- Chat list API fields: `ticketCount`, `ticketProgressPct`.
- VSIX conversation `<select>` and Sessions tree label when a chat has linked tickets.
- Unit/integration tests for the screenshot mix (`4×100% + 2×0%` → `~67% · 4/6`) and ceremony/spec/roadmap totals.

## Functional requirements

1. **Incomplete ceremony tickets have weight 1.** Spec, roadmap, and retro (and equivalent ceremony tickets) that are not done emit `total: 1` and `progressPct: 0` (not `total: 0`). Done tickets remain `total: 1`, `progressPct: 100`.
2. **Header overall includes 0% chips.** Ticket rail header mean and `done/count` use every linked ticket. Screenshot mix: four 100% tickets plus two 0% tickets → overall `~67% · 4/6`, not `100% · 4/4`. Chip captions remain consistent with those totals (0% chips are visible and counted).
3. **`aggregateTicketHealth` backward-compatible weights.** A ticket with `total: 0` is treated as weight `1` so older servers that still emit `total: 0` for incomplete ceremony tickets roll into the same mean. Tickets with `total > 0` keep existing weight-by-total behavior.
4. **Chat list ticket health.** Chat list API attaches `ticketCount` and `ticketProgressPct` per conversation that has linked tickets. `ticketProgressPct` is the same aggregate used by the rail header for that chat.
5. **Dropdown and Sessions labels.** VSIX conversation `<select>` and Sessions tree show `NN% · title` when the chat has linked tickets (example: `67% · title`). Chats with no linked tickets keep the existing title + live-run glyph presentation.
6. **Tests.** Tests lock: (a) screenshot mix in `aggregateTicketHealth`; (b) ceremony/spec/roadmap incomplete → `total: 1`; (c) `total: 0` still weighted as `1` in aggregate.

## Acceptance criteria

1. Incomplete spec/roadmap/retro report `total: 1` so 0% chips count in the header (screenshot case: `4×100% + 2×0%` → `~67% · 4/6`, not `100% · 4/4`).
2. `aggregateTicketHealth` treats a ticket with `total: 0` as weight `1` so old servers still roll up correctly.
3. Chat list API attaches `ticketCount` + `ticketProgressPct`; VSIX conversation `<select>` (and Sessions tree) shows e.g. `67% · title` when the chat has linked tickets.
4. Tests lock the screenshot mix in `aggregateTicketHealth` + ceremony/spec/roadmap totals.
