# PRD: Journey Launch Checklist

**Status:** WIP  
**Owner:** Product Architecture  
**Related:** Growth `sendReadiness` (suppression, unsubscribe, transport) — **do not duplicate**

## Problem & Goal

Journeys fail late because brand, consent, sender, offer, and copy are treated as informal notes rather than required launch gates. Growth already owns **send-time** readiness (`sendReadiness`: suppression, unsubscribe, transport). That leaves a gap: **journey-time** completeness for creative, targeting, and channel identity.

**Goal:** A single, machine-readable Journey Checklist that every journey must satisfy before it can leave draft (and that downstream agents can evaluate the same way). Items are: brand (voice + doNotSay), consent audience, sender/account for the chosen channel, offer, copy. Distinct from, and complementary to, Growth `sendReadiness`.

Success looks like: a journey cannot be marked launch-ready until all five items pass; failures are item-specific and actionable; Growth send checks remain the source of truth for suppression / unsubscribe / transport.

## Target users / ICP roles

- **Journey builder** (lifecycle / CRM marketer): configures the path and needs a clear “what’s missing” list, not a send-infra dump.
- **Brand / legal reviewer:** owns voice and doNotSay; must see those as first-class gates, not buried in copy review.
- **Channel ops:** owns sender/account mapping per channel (email from-address/domain, SMS short/long code, push app, etc.).
- **Downstream agents** (implementation, QA, Growth integration): consume the same checklist schema; must never reimplement `sendReadiness`.

## Scope

In scope for this WIP:

1. **Checklist model** attached to a Journey (not a one-off campaign send, not a Growth send job).
2. **Five items only:** brand (voice + doNotSay), consent audience, sender/account for chosen channel, offer, copy.
3. **Per-channel evaluation** where the journey has a chosen channel (sender/account and copy are channel-aware).
4. **Pass / fail / incomplete** states with human-readable reasons and deep links to the owning record.
5. **Launch gate:** journey cannot transition to launch-ready / scheduled / live while any required item is fail or incomplete.
6. **Explicit non-overlap contract** with Growth `sendReadiness`.

Out of scope is listed at the end.

## Functional requirements

### FR-1 — Checklist is a first-class Journey resource

- Every Journey has exactly one checklist instance.
- Checklist is derived from Journey configuration + linked records; it is not a freeform to-do list.
- Schema is stable for agents: `itemId`, `status` (`pass` | `fail` | `incomplete`), `reason`, `ownerType`, `recordId`, `channel` (nullable).

### FR-2 — Brand: voice + doNotSay

- **Pass** when the Journey is linked to a Brand that has:
  - a non-empty **voice** definition (tone, personality, writing constraints used by copy generation/review), and
  - a **doNotSay** list (phrases, claims, competitor names, legal-sensitive language) that is non-empty **or** explicitly marked “none required” by a brand owner.
- **Incomplete** if no Brand is linked.
- **Fail** if Brand is linked but voice is empty, or doNotSay is neither populated nor explicitly waived.
- Voice and doNotSay are evaluated as **two sub-checks under one item** (`brand`). Both must pass for the item to pass.
- Checklist does not invent brand copy; it only verifies presence and link.

### FR-3 — Consent audience

- **Pass** when the Journey has a consent audience: a named audience whose membership is defined by an explicit consent basis appropriate to the Journey’s purpose and channel (e.g. marketing opt-in for promotional email/SMS).
- Audience must be resolvable (exists, not deleted, not a raw unconsented list).
- **Incomplete** if no audience is attached.
- **Fail** if audience is attached but has no consent basis, consent basis is incompatible with the chosen channel, or the audience is marked non-sendable for consent reasons.
- This item is **consent and audience selection**, not suppression, unsubscribe processing, or transport health (those stay in Growth `sendReadiness`).

### FR-4 — Sender / account for chosen channel

- Journey must have a **chosen channel** (email, SMS, push, or whatever the Journey runtime supports).
- **Pass** when that channel has a linked **sender/account** that is active and eligible for that channel (verified sending identity, not a placeholder).
- Multi-step / multi-channel journeys: **each chosen channel** must have its own sender/account; the item fails if any chosen channel is missing one.
- **Incomplete** if channel is unset or sender/account is unset.
- **Fail** if sender/account is linked but inactive, unverified, wrong channel type, or not authorized for this workspace.
- Does **not** include deliverability, IP warmup, bounce rates, or MTA/provider health (`sendReadiness.transport`).

### FR-5 — Offer

- **Pass** when the Journey is linked to an Offer with: identifier, customer-facing value proposition, and any required legal/promo constraints the copy item will need (expiry, eligibility, code).
- **Incomplete** if no Offer is linked and the Journey type requires one (promotional / conversion journeys).
- **Fail** if Offer is linked but missing required fields, expired relative to the Journey’s intended send window, or marked inactive.
- Operational / transactional journey types may mark offer as **not applicable**; that is a pass with `reason = not_applicable`, not a skip of the item.

### FR-6 — Copy

- **Pass** when every message step on a chosen channel has copy that is:
  - present (non-empty body; subject/preview/headline where the channel requires it),
  - bound to the Journey’s Brand (so voice + doNotSay can be applied),
  - bound to the Offer when the offer item is applicable.
- **Incomplete** if any required message slot is empty.
- **Fail** if copy exists but is for the wrong channel, missing required channel fields, or not linked to Brand/Offer when those items are required.
- Copy completeness ≠ brand compliance scoring. This item is **presence and binding**. Optional later: a brand-lint warning that does not block unless product policy says so; default for WIP is **block on missing copy, warn on voice/doNotSay lint**.

### FR-7 — Distinct from Growth `sendReadiness`

- Journey Checklist **must not** evaluate or display: suppression lists, unsubscribe state, RFC-compliant unsubscribe headers, bounce/complaint handling, or transport/provider readiness.
- UI and API copy must name this surface **Journey checklist** (or equivalent), never `sendReadiness`.
- Launch-ready on the Journey side means checklist pass **only**. Actual send still requires Growth `sendReadiness` at send time. Both gates are required; neither implies the other.
- Shared identifiers (journeyId, audienceId, channel, senderId) may be passed to Growth; checklist logic must not call into or fork `sendReadiness` internals.

### FR-8 — Gate behavior

- Default: all five items are **required** unless an item is explicitly `not_applicable` (offer on transactional journeys).
- Status rollup: Journey `checklistStatus = pass` iff every required item is `pass`.
- Transitions to scheduled / live / launch-ready are rejected with the list of failing/incomplete items.
- Edits to Brand, audience, sender, offer, or copy recompute the checklist immediately.

## Acceptance criteria

1. Creating a Journey yields a checklist with five items in `incomplete` (or offer `not_applicable` when the type warrants it).
2. Linking a Brand with voice **and** doNotSay (or an explicit doNotSay waiver) moves `brand` to `pass`; removing voice or doNotSay without waiver moves it to `fail`.
3. Attaching a consent-qualified audience moves `consentAudience` to `pass`; a list with no consent basis is `fail`.
4. Selecting email without a verified from-identity leaves `senderAccount` `incomplete`/`fail`; attaching a valid identity for that channel is `pass`. A second channel without its own sender keeps the item `fail`.
5. Promotional journeys cannot pass `offer` without an active, complete Offer; transactional journeys can pass with `not_applicable`.
6. A message step with empty body keeps `copy` `incomplete`; filling required channel fields and binding Brand (and Offer if applicable) yields `pass`.
7. API/UI never surfaces suppression, unsubscribe, or transport under this checklist. Those remain Growth `sendReadiness` only.
8. Attempting to schedule/launch with any required item not `pass` is rejected; the response lists item ids and reasons.
9. Two agents evaluating the same Journey produce the same checklist statuses from the same records.
10. Passing this checklist does not mark a send job send-ready in Growth; failing `sendReadiness` does not fail this checklist unless a shared record (e.g. deleted audience) independently fails an item here.

## Out of scope

- Growth `sendReadiness`: suppression, unsubscribe, transport, ISP reputation, seed tests, throttling.
- Full brand-compliance or legal auto-redline of copy (beyond presence of voice + doNotSay and optional lint warning).
- Consent capture UX, preference-center design, or lawful-basis engines beyond “audience has a consent basis compatible with channel.”
- Sender onboarding / domain authentication flows (checklist only consumes an already-eligible sender/account).
- Offer merchandising, inventory, or coupon issuance.
- Copy generation, translation, or A/B experiment setup (checklist only requires bound copy slots).
- Journey orchestration runtime, entry criteria, wait steps, or analytics.
- Cross-product campaign calendar, approvals workflow (beyond the mechanical launch gate), or billing.

### R-4 — Stable item schema (agents evaluate this)

Each item is:

- `itemId`: `brand` | `consentAudience` | `senderAccount` | `offer` | `copy`
- `status`: `incomplete` | `fail` | `pass`  
  Maps 1:1 to the PM vocabulary `missing` | `invalid` | `complete`. Parent #2629 may collapse each item to a boolean (`true` iff `pass`). Architect must not invent a fourth state.
- `reason`: stable machine token (R-14) plus optional human-readable detail
- `ownerType`: linked record kind (`brandKit`, `audience`, mailbox/social/ads account, offer/CTA, `emailCampaign` / social/ads copy object)
- `recordId`: id or canvas title-ref; null when unlinked
- `channel`: chosen channel this row applies to, or null for run-level items (`brand`, `offer`; `consentAudience` is run-level but reason may name channel incompatibility)
- `blocking`: **always true for launch-ready** (PM FR-1). Preview / test-send of a **single** step may proceed when **that step’s** sender + copy are `pass`; they do not require the full run `checklist.ready` (PM FR-7, scoped to canvas preview — not a new HTTP surface).

`senderAccount` and `copy` are **channel-aware**. A multi-channel run still has **one** `senderAccount` item and **one** `copy` item; that item is not `pass` if **any** chosen channel is missing its sender or required copy. Do not explode into five parallel checklists.

`checklist.ready === true` iff every required item is `status = pass`.

### R-5 — Brand (`brand`): voice + doNotSay **list presence** (not lint)

Ground in existing `brandKit` / `BrandBinding` (`packages/creation-canvas-contract/src/marketing.ts`: `voice`, `doNotSay` merged from kit + board `battlecard.doNotSay`, `resolveBrandBinding`, `BRAND_BINDING_FIELD`).

**Parent #2629 R-3 / PM lock wins over this ticket’s WIP FR-2 “empty list only if acknowledged”:**

- **Incomplete** (`no_brand`) if no `brandKit` is linked and the board does not resolve to exactly one kit (same three rules as `resolveBrandBinding`: explicit `brandKitRef`, else the only kit, else unbound).
- **Fail** (`voice_empty`) if a kit is linked/resolved but **voice** is empty/whitespace.
- **Fail** (`donotsay_missing`) if the `doNotSay` **field is absent** (`null` / `undefined` — the list was never authored).
- **Pass** (`ok`) when voice is a non-empty string **and** `doNotSay` is a **defined array**. An authored empty array `[]` is valid (“nothing forbidden”). Do **not** require a `doNotSayNoneRequired` waiver flag — that flag does not exist on main and contradicts parent.
- Palette / logo / typography absence does **not** fail this item.
- Checklist **does not invent** brand copy. It does **not** run `forbiddenClaimsIn` (that is send-time; R-10).
- **Launch-gate is stricter than compose:** `marketing.ts` allows half-filled kits so generate still runs. Compose may proceed unbranded; `checklist.ready` must not.

### R-6 — Consent audience (`consentAudience`)

Ground in canvas `audience` (`audienceId` / `audienceName`, `consentBasis`, `AUDIENCE_CONSENT_BASES`, `isAffirmativeConsent`) and Growth audiences. Match order already used by `audienceForCampaign`: `audienceId` first, title second.

- **Incomplete** (`no_audience`) if no audience is attached (no id and no resolvable name).
- **Fail** if attached but: deleted / unresolvable (`audience_unresolvable`); `consentBasis` is `unknown` or missing (`no_consent_basis`); basis is incompatible with the chosen channel and run purpose (`consent_incompatible_with_channel`); or the audience is marked non-sendable **for consent reasons** (`audience_not_sendable_consent`) — not because it is suppressed.
- **Pass** (`ok`) when the audience exists and has an explicit basis appropriate to purpose + channel:
  - Promotional email / SMS: affirmative only (`optIn` or `doubleOptIn`). `imported`, `unknown`, empty → `fail`.
  - Transactional / operational: `contractual` may pass; `legitimateInterest` may pass only when the run type is non-promotional. Architect records the matrix in Design; BA default is **promotional ⇒ affirmative**.
- This item is **selection + consent basis**. It MUST NOT read `suppressedCount`, compute `sendableCount`, or emit `noSuppressionCheck` / `emptyAfterSuppression` (those stay `sendReadiness`).

### R-7 — Sender / account (`senderAccount`) for each chosen channel

Chosen channels are the run’s actual send/publish/launch surfaces, composed from existing primitives — **not** `CHANNEL_PLATFORMS` (that file is agent-host chat: Slack/Discord/…). Typical run channels: `email`, `sms`, `social`, `ads` (and `push` only if the run actually chooses it).

- **Incomplete** if no channel is chosen (`no_channel`), **or** a chosen channel has no linked sender/account (`no_sender`).
- **Fail** if a sender/account is linked but inactive (`sender_inactive`), unverified (`sender_unverified`), placeholder, wrong channel type (`sender_wrong_channel`), or not authorized for this workspace/tenant (`sender_unauthorized`). A second chosen channel without its own sender keeps the **item** `fail` (`channel_missing_sender`) or `incomplete` if that channel’s sender is simply unset.
- **Pass** (`ok`) when **every** chosen channel has an active eligible identity:
  - email → verified sending identity / connected mailbox (Growth Mailboxes / canvas inbox path). Guest boards cannot complete this for email (no tenant OAuth); item stays `incomplete` until a tenant board has a verified identity.
  - sms → active sending number/short-or-long code if SMS is chosen.
  - social → connected social account ready to publish (existing social connect; not a hand-authored fake `socialCampaign` ledger).
  - ads → connected ads account. Linking it does not launch spend (#2635).
- Channel change **clears** the prior sender binding for that step and reopens the item (PM FR-4).
- Does **not** include deliverability, IP warmup, bounce rates, ISP reputation, MTA/provider health, or seed tests.
- Checklist **consumes** an already-eligible sender; it does not onboard domains or collect passwords in chat.
- Connect success MAY flip this item to `pass` when the connected account matches the chosen channel; it MUST NOT send, spend, confirm, or set `maySend` (#2635 / parent R-10).

### R-8 — Offer (`offer`)

There is **no** marketing Offer table on main today. Do **not** reuse employment `offer` (`handover.ts`). Architect maps the offer/CTA to a non-empty string (parent #2629 R-3) and/or a linked canvas record. This slice does **not** require a new merchandising product.

- Promotional / conversion runs: **Incomplete** (`no_offer`) if no offer/CTA is linked **and** the operator has not set an explicit no-offer flag. **Fail** (`offer_incomplete` / `offer_expired` / `offer_inactive`) if a structured offer is linked but missing identifier or customer-facing value proposition, expired relative to the run’s intended send window, or marked inactive — **only when those fields exist on the mapped record**. Parent minimum remains: non-empty offer/CTA string. **Pass** (`ok`) when the string is non-empty (and structured fields, if present, are complete and in-window).
- Explicit no-offer flag **or** transactional / operational run type: item stays on the schema but status is `pass` with `reason = not_applicable`. That is not a skip of the item and not `incomplete`.
- Out of item: coupon issuance, inventory, offer merchandising UI, legal-disclaimer CMS.

### R-9 — Copy (`copy`): presence and binding — **not** a doNotSay fail

Ground in existing authored objects: `emailCampaign` / `emailTemplate` (`subject`, `bodyHtml` / `content`); social via `canvas_create_social_campaign` (never `canvas_add_object` for `socialCampaign`); ads creative fields on the ads path.

- **Incomplete** (`copy_empty`) if any required message slot on a chosen channel is empty.
- **Fail** if copy exists but is for the wrong channel (`copy_wrong_channel`), missing that channel’s required fields (`copy_missing_fields`), or not bound to Brand when `brand` is required (`copy_unbound_brand`), or not bound to Offer when `offer` is applicable (`copy_unbound_offer`).
- **Pass** (`ok`) when every chosen-channel message step has: non-empty body; subject / preview / headline where the channel requires it; `brandKitRef` (or single-kit board resolution) so voice + doNotSay **can** be applied at send-time; offer binding when R-8 is applicable.
- Channel field minimums (BA default; Architect may tighten, not loosen):
  - email: subject + body (`bodyHtml` or `content`)
  - social: non-empty body (network-required media stays a **warn** unless Architect documents it as required presence)
  - ads: headline + body; destination URL if the ads path already requires one
  - sms: non-empty body
- Locale variants, if enabled, each satisfy the same presence rules (PM FR-6 presence half). Locale enablement is not in this ticket’s runtime today; do not invent a localization product.
- **Copy completeness ≠ brand-compliance scoring.** Changing the brand profile re-evaluates **whether copy is still bound** (R-15). It does **not** flip `copy` to `fail` because drafted text contains a doNotSay phrase.

**Override of PM FR-2 / FR-6 / AC “copy containing a doNotSay term sets `copy` to `invalid`”:** a doNotSay **hit** is Growth / canvas `sendReadiness` blocker `forbiddenClaim` via `forbiddenClaimsIn(body, binding)`. Putting the same hit on checklist `copy` would merge the two gates this ticket exists to split. Checklist `brand` = list **presence**; send-time = list **enforcement**. UI MAY warn on a hit; `copy.status` MUST NOT become `fail` solely for that reason.

### R-10 — Distinct from Growth / canvas `sendReadiness` (non-overlap contract)

**As-is on main** (`packages/creation-canvas-contract/src/marketing.ts` `sendReadiness`): blockers are `noAudience` | `unknownConsent` | `noSuppressionCheck` | `emptyAfterSuppression` | `forbiddenClaim`. The function does **not** currently take `unsubscribePresent` or `transportReady`. Adapter: `frontend/src/lib/canvasMarketing.ts` `campaignSendReadiness`.

Product intent (this ticket + parent R-4): checklist never includes suppression, unsubscribe, or transport. Those remain on `sendReadiness`. **As-is `sendReadiness()` also mixes consent (`unknownConsent`) and copy-lint (`forbiddenClaim`).** This ticket does **not** refactor that function. Split is:

| Question | Checklist item | `sendReadiness` (as-is / Growth) |
|---|---|---|
| Brand kit has voice + doNotSay **array**? | `brand` | not evaluated |
| Drafted body contains a doNotSay phrase? | **not** `copy` (warn only) | `forbiddenClaim` |
| Named audience bound with a consent basis? | `consentAudience` | `noAudience` / `unknownConsent` (separate conjunct; dual-count allowed) |
| Suppression asked / sendable remaining? | **never** | `noSuppressionCheck` / `emptyAfterSuppression` |
| Unsubscribe header / page / transport health | **never** | Growth send-time (not args on main today; do not add them here) |

Rules:

- MUST NOT import, call, wrap, or fork `sendReadiness` / `campaignSendReadiness` / `sendableCount` from the checklist evaluator.
- MUST NOT evaluate or display: suppression lists, `suppressedCount`, sendable arithmetic, unsubscribe state or RFC headers, bounce/complaint handling, transport/provider readiness, ISP reputation, throttling, seed tests.
- MAY independently read shared identifiers (`audienceId`, `consentBasis`, `brandKitRef`, channel, sender id) to answer **completeness** questions. Shared inputs are not a shared function.
- UI/API copy names this surface **Journey checklist** (or “Campaign checklist”). Never `sendReadiness`. Checklist UI lists **only** the five items and MAY link to Growth `sendReadiness` as a **separate** section (PM AC).
- `checklist.ready === true` does **not** mark a Growth send job send-ready. `sendReadiness.ready === false` does **not** fail this checklist unless a shared record independently fails an item here (e.g. deleted audience → `consentAudience` fail **and** sendReadiness `noAudience`).
- Both gates are required at send. Neither implies the other. `maySend` conjunction is #2633, not this ticket.
- Do not add unsubscribe/transport parameters to `sendReadiness` as part of this ticket.

### R-11 — Rollup and launch gate

- Default: all five items are **required**. The only `not_applicable` is `offer` on transactional/operational runs or explicit no-offer (R-8), which counts as `pass` for rollup.
- `checklist.ready = true` iff every required item is `status = pass`.
- Any required item `fail` or `incomplete` ⇒ `checklist.ready = false`.
- Attempts to mark the run launch-ready / scheduled / live **must be rejected** with the list of non-pass `{ itemId, status, reason }`. Do not silently coerce. **No partial go-live.**
- HTTP `409` with the checklist body (PM FR-7) applies **only if** an activate HTTP endpoint already exists and Architect maps the reject there. This child MUST NOT invent a new Journey activate REST. Parent C1 refuses via `checklist.ready === false` (and `maySend === false` on #2633).
- This gate is **journey-time**. Actual send/publish/ads launch still requires #2633 (`maySend`) and #2638 (human confirm). Guest and cloud-agent paths stay draft-only even if checklist passes.
- Preview / test-send MAY run for a step whose own `senderAccount` + `copy` are `pass`; they do not require full-run `checklist.ready` (PM FR-7). They still MUST NOT send to a live audience without #2633.
- Edits to brand, audience, sender, offer, or copy **recompute immediately** (same turn / same evaluation). No stale cached pass.

### R-12 — Determinism

Two agents (or the same agent twice) evaluating the same run records MUST produce the same `status` and the same `reason` tokens for every item. No LLM judgement in the evaluator. Lint/warn copy is advisory and MUST NOT change `status`.
