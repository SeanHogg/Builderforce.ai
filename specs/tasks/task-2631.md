# PRD: Journey Checklist (Content & Compliance Readiness)

## Problem & Goal

Journeys can be activated with incomplete brand, consent, sender, offer, or copy configuration. That produces off-brand messages, consent violations, and unsendable steps. Growth already owns `sendReadiness` (suppression, unsubscribe, transport). Journeys need a separate, first-class checklist for creative and compliance completeness so a journey cannot go live until those items are resolved.

**Goal:** Block journey activation until brand (voice + doNotSay), consent audience, channel sender/account, offer, and copy are present and valid for every send step. Surface a single, auditable checklist distinct from Growth `sendReadiness`.

## Target users / ICP roles

- Lifecycle / CRM marketers who author and activate journeys
- Brand / content leads who own voice, doNotSay, and copy
- Compliance / privacy owners who approve consent audiences
- Channel ops who provision sender identities and accounts

## Scope

Applies to all outbound journey send steps (email, SMS, push, WhatsApp, and other configured channels). Checklist state is computed per journey and per send step, persisted with the journey version, and evaluated at draft save, preview, and activate.

In scope:

- Brand: voice profile + doNotSay list bound to the journey (or inherited from workspace default)
- Consent audience: opted-in segment/list matching the journey’s purpose and channel
- Sender/account: verified identity for the chosen channel on each send step
- Offer: selected offer (or explicit “no offer”) with required fields complete
- Copy: channel-specific message body (and subject/preheader where required), passing brand doNotSay checks
- Checklist UI on the journey canvas and activation gate
- Clear separation of IDs, APIs, and UI from Growth `sendReadiness`

## Functional requirements

1. **Checklist model**  
   Each journey version exposes `journeyChecklist` with items: `brand`, `consentAudience`, `senderAccount`, `offer`, `copy`. Each item has `status` (`missing` | `invalid` | `complete`), `blocking` (always true for activation), and a machine-readable `reason`.

2. **Brand (voice + doNotSay)**  
   A journey must reference a brand profile that includes a non-empty voice definition and a doNotSay list (list may be empty only if explicitly acknowledged). Changing the brand profile re-evaluates copy. Copy that matches a doNotSay term marks `copy` as `invalid`.

3. **Consent audience**  
   A journey must bind a consent audience whose channel and legal basis match every send step. Missing audience, expired consent definition, or channel mismatch → `consentAudience` is `missing` or `invalid`.

4. **Sender / account for chosen channel**  
   Every send step must have a sender/account that is verified, active, and valid for that step’s channel. Channel change clears the prior sender and reopens the item.

5. **Offer**  
   Every send step must either attach a complete offer (id, name, value proposition, legal/disclaimer if the offer type requires it) or an explicit no-offer flag. Incomplete offer payloads → `invalid`.

6. **Copy**  
   Every send step must have required copy fields for its channel. Empty required fields → `missing`. doNotSay violations or brand-voice lint failures → `invalid`. Locale variants, if enabled, must each satisfy the same rules.

7. **Activation gate**  
   Activate is disabled while any checklist item is not `complete`. The API returns `409` with the checklist payload if activation is attempted. Preview and test-send may run only for steps whose own items are `complete`; they do not require the full journey to be complete.

8. **Independence from Growth `sendReadiness`**  
   Journey checklist never includes suppression, unsubscribe, or transport. Those remain on Growth `sendReadiness`. Both gates must pass to send; failures are reported in separate objects and UI sections. Shared primitives (channel, sender id) may be referenced but must not merge status.

9. **Versioning and audit**  
   Checklist snapshot is stored on the journey version. Completing or invalidating an item writes an audit event (who, when, item, from/to status).

## Acceptance criteria

- A new journey with no configuration shows all five items `missing`; Activate is disabled.
- Binding a brand profile with voice + doNotSay completes `brand`; omitting either leaves it `missing` or `invalid`.
- Copy containing a doNotSay term sets `copy` to `invalid` with the matched term in `reason`; removing or rewriting the term returns `copy` to `complete` if other copy rules pass.
- Selecting a consent audience that does not cover a send step’s channel leaves `consentAudience` `invalid` and blocks activation.
- A send step without a verified sender/account for its channel leaves `senderAccount` `missing`/`invalid`; assigning a verified sender completes it for that step. All send steps must be complete for the journey-level item to be `complete`.
- A send step with neither an offer nor a no-offer flag leaves `offer` `missing`.
- Activation with any incomplete item is rejected with `409` and the full `journeyChecklist` body; no partial go-live.
- Growth `sendReadiness` can fail while `journeyChecklist` is fully `complete` (and the reverse); the two statuses never overwrite each other.
- Cloning a journey copies checklist bindings but recomputes status; the clone does not inherit a stale `complete` snapshot.
- Checklist UI lists only the five journey items and links to Growth `sendReadiness` as a separate section.

## Out of scope

- Suppression lists, unsubscribe headers/pages, bounce/complaint handling, and transport/provider health (`sendReadiness`)
- Journey graph logic, wait steps, branching, and frequency caps
- Offer catalog authoring, pricing, or inventory
- Brand profile CMS beyond voice + doNotSay binding
- Consent capture UX, preference-center redesign, or legal-basis workflow
- AI copy generation (lint against doNotSay only)
- Multi-brand workspaces beyond selecting one brand profile per journey
- Analytics, holdouts, and incrementality
