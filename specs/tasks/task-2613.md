# PRD: Generalise `pullStandupMinutesAct` — open action items on meeting end

**Epic:** #2538 (P1)  
**Related (explicitly not this ticket):** #2539 Meeting Notes marketplace agent · #2542 Follow-up booking proposal · #2543 Guest-without-tenant  
**Status:** WIP

## Problem & Goal

`pullStandupMinutesAct` only handles standup-shaped minutes. On meeting end, `summarizeMeeting` already emits a stable three-section Markdown document (summary, decisions, action items), but open action items are not automatically materialised as tasks. Operators re-run the same path and get duplicates; guests with a project still have to copy items by hand.

**Goal:** Reuse the existing minutes parser (do not fork `parseMeetingMinutes`) and generalise `pullStandupMinutesAct` so that, on meeting end, every **open** action item from that Markdown lands once—idempotent by title—as canvas task objects, plus API tasks when the visitor has or creates a project.

## Target users / ICP roles

- **Meeting host / facilitator** — expects open actions to exist in the room the moment the call ends, without a second “extract tasks” step.
- **Project-owning visitor** — has or creates a project in-session; needs the same items as durable API tasks, not only canvas chips.
- **Downstream agents** sharing this PRD — implement against this contract; do not invent a second minutes grammar or a marketplace-notes path.

Not in this ticket: anonymous guest with no tenant (#2543).

## Scope

In scope:

- Trigger: **meeting end** (same lifecycle point that already finalises `summarizeMeeting` output).
- Input: the three-section Markdown produced by `summarizeMeeting`.
- Extraction: open action items only, via existing `parseMeetingMinutes` (no fork, no parallel parser).
- Placement: canvas task objects always (when a meeting canvas exists).
- Placement: API tasks **when** the visitor already has a project **or** creates one in this flow.
- Idempotency key: **title** (normalised consistently with current task uniqueness). Re-entry must not create a second canvas object or API task for the same title.
- Generalise `pullStandupMinutesAct` in place so standup and non-standup meetings share one act.

Out of scope is listed below; do not expand this P1 into notes-agent, booking, or guest-without-tenant behaviour.

## Functional requirements

1. **Single act.** Extend `pullStandupMinutesAct` rather than adding a sibling act. Standup behaviour remains a special case of the same pipeline, not a separate code path for parsing.
2. **Source of truth.** Read open action items only from `summarizeMeeting` three-section Markdown. Closed / completed items in that document are ignored.
3. **Parser reuse.** Call `parseMeetingMinutes` as-is. Do not fork, copy, or reimplement section splitting, checkbox / owner / due-date extraction, or title normalisation.
4. **Meeting-end hook.** Invoke the generalised act automatically when the meeting ends and minutes Markdown is available. Missing or empty action-item section is a no-op (success, zero writes).
5. **Canvas writes.** For each open item, upsert a canvas task object on the meeting canvas. Create if no canvas task with the same title exists; if one exists, leave it (no duplicate, no destructive overwrite of user edits unless title-keyed upsert is already the product rule—then update in place, still one object per title).
6. **API tasks (project present).** If the visitor has a project, also upsert an API task per open item, keyed by title. Same idempotency as canvas.
7. **API tasks (project created in-flow).** If the visitor creates a project as part of this meeting-end / capture flow, write API tasks to that project after creation, still idempotent by title. Do not block canvas writes on project creation.
8. **No project.** Canvas tasks still land. Do not create API tasks. Do not invent a tenant or guest-account (that is #2543).
9. **Idempotency.** Safe to run twice on the same meeting end (retry, reconnect, double webhook). Title match is the only uniqueness key for this P1. Empty or whitespace-only titles are skipped, not written.
10. **Failure isolation.** Parser or per-item write failures must not roll back already-written distinct titles; log and continue. Meeting end itself must not fail solely because task placement failed.

## Acceptance criteria

- Given `summarizeMeeting` Markdown with N distinct open action titles, when the meeting ends, the canvas shows exactly N task objects for those titles (plus any pre-existing tasks with different titles).
- Given the same Markdown processed a second time, canvas task count for those titles stays N; API task count for those titles stays N when a project exists.
- Given an item marked closed/done in the action-items section, no canvas or API task is created for it.
- Given two open items with the same title, at most one canvas task and (if project) one API task exist for that title.
- `parseMeetingMinutes` is the only minutes parser used; no forked module or duplicated grammar ships in this change.
- Visitor **with** a project: canvas objects and API tasks both exist for each open title.
- Visitor who **creates** a project in this flow: API tasks appear on that project after creation; canvas objects are not delayed on API success.
- Visitor **without** a project: canvas objects exist; zero API tasks are created.
- Empty action-items section: act succeeds, writes nothing.
- Standup meetings that previously used `pullStandupMinutesAct` still get open items placed; no regression to standup-only title handling beyond the shared parser.

## Out of scope

- Meeting Notes marketplace agent (#2539) — no marketplace packaging, prompts, or agent surface.
- Follow-up booking proposal (#2542) — no calendar holds, suggested next meetings, or booking CTAs.
- Guest-without-tenant (#2543) — no tenant provisioning, anonymous persistence, or “create account to keep tasks” diversion.
- Forking or replacing `parseMeetingMinutes`.
- Closed action items, arbitrary Markdown outside the three-section contract, or re-summarisation.
- Assignee / due-date sync beyond what `parseMeetingMinutes` already returns (no new field mapping in this P1).
- Deduplication by anything other than title (description hash, speaker, timestamp).
- Editing, completing, or deleting tasks from the meeting UI as part of this act.
- Notifications, email digests, or third-party task backends (Jira, Linear, etc.).

## Requirements

**Contract for implementers.** These R-n are the acceptance contract for #2613. Do not invent a second minutes grammar, a marketplace-notes path, a booking CTA, or a guest-tenant provisioner.

### R-1 Single named act

Extend `pullStandupMinutesAct` in place. Standup is a special case of the same pipeline, not a separate parse path. Do not add a sibling act (`pullMeetingMinutesAct`, `extractMeetingTasksAct`, or any other name).

Discovery (2026-09-16, product repo `seanhogg/builderforce.ai` @ `main`): the symbol `pullStandupMinutesAct` is **not present** in the tree today. `parseMeetingMinutes` comments that a board act turns the checklist into cards, but that act is not shipped. Implementers **introduce** the act under the name `pullStandupMinutesAct` as the single pipeline. Absence of the symbol is not licence to fork a second minutes-to-task path or to retarget this work onto #2541.

The act applies to every `meetings.kind` that can carry `summarizeMeeting` Markdown (including `standup`, `planning`, `retrospective`, `adhoc`, `direct`, `interview`, `review`).

### R-2 Source of truth

Read open action items only from the three-section Markdown `summarizeMeeting` stores on `meetings.summary` (Summary / Decisions / Action items). That document is the #2540 contract. Closed / completed checklist items (`done === true`, checkbox `- [x]` / `- [X]`) are ignored. Do not re-summarise. Do not read transcript, chat, or canvas notes as a second source.

### R-3 Parser reuse

Call `parseMeetingMinutes` in `frontend/src/lib/meetings/meetingMinutes.ts` as-is. Do not fork, copy, or reimplement section splitting, checkbox / owner / due-date extraction, or title formation.

- Open item: `item.done === false`.
- Title: `actionItemTitle(item)` (`Owner — task` when owner is present, otherwise `task`), then `.trim()`.
- Empty `task` is already dropped by the parser; still skip any title that is empty or whitespace-only after trim.
- Do not add assignee or due-date mapping beyond what the parser already returns (out of scope for this P1).

If the API-side act cannot import the frontend module, **share the existing module** (move to a packages contract or import the same file) — do not duplicate the grammar. Sharing the module is not a fork.

### R-4 Meeting-end hook

Invoke the act automatically when the meeting has ended **and** minutes Markdown is available.

- Primary lifecycle: `POST /api/meetings/:id/end` in `api/src/presentation/routes/meetingRoutes.ts`, which already best-effort-calls `summarizeMeeting` when `meetings.summary` is empty. Run the act **after** that attempt, on whatever Markdown is then on the row (pre-existing or freshly generated).
- Missing summary, empty Markdown, or empty action-items section (parser returns `actionItems: []`): **no-op success**, zero writes.
- `endCeremonyMeeting` (`api/src/application/ceremony/ceremonyMeeting.ts`) today only sets `status='ended'` and does **not** call `summarizeMeeting`. This ticket does **not** add a second summarizer on that path. If that path later materialises `meetings.summary` (or already has one), the act runs; if it does not, the act is a no-op. Do not expand into ceremony attendance.
- Meeting end itself must not fail solely because task placement failed (same best-effort pattern as summarize on that route).

### R-5 Canvas writes

For each distinct open title, upsert a canvas object of kind `'task'` (already in `CREATION_OBJECT_KINDS` / `packages/creation-canvas-contract/src/objectKinds.ts`) on the **meeting canvas**, when a meeting canvas exists.

- Create if no canvas task with the same title exists.
- If one exists, leave it (no duplicate). Do not destructively overwrite user edits unless title-keyed upsert is already the product rule on that surface — then update in place, still one object per title.
- If no meeting canvas exists, skip canvas writes (success) and still attempt API writes when R-6 / R-7 apply.
- Canvas writes are **not** gated on project creation or API-task success.

### R-6 API tasks when a project is already present

If the meeting already has a `projectId` (or the visitor already has a project in session that this meeting is bound to), also upsert one API task per distinct open title on that project. Same title key as canvas (R-9). Do not create API tasks for closed items or empty titles.

### R-7 API tasks when a project is created in this flow

If the visitor creates a project as part of this meeting-end / capture flow, write API tasks to **that** `projectId` after creation, still idempotent by title. This ticket does **not** invent a new project-creation wizard; it consumes a `projectId` produced in the same flow. Do **not** block canvas writes (R-5) on project creation or on API success.

### R-8 No project / no tenant

Canvas tasks still land (R-5). Do not create API tasks. Do not invent a tenant, guest account, or “create account to keep tasks” diversion — that is #2543.

### R-9 Idempotency

Safe to run twice on the same meeting end (retry, reconnect, double webhook).

- Uniqueness key for this P1 is **title only**: `actionItemTitle(item).trim()`.
- Empty or whitespace-only titles are skipped, not written.
- Two open items in the same Markdown that produce the same title after trim collapse to **at most one** canvas task and (if project) **at most one** API task.
- Re-entry matches an existing canvas `task` object / API task whose title equals that string using the **same equality the current create path already uses** on that surface. Do not add a second key (description hash, speaker, timestamp, meeting id as a uniqueness substitute).
- Do not invent Unicode NFKC / case-fold rules unless that equality already exists on the create path.

### R-10 Failure isolation

Parser or per-item write failures must not roll back already-written distinct titles; log and continue. A parser throw/failure writes nothing and still leaves meeting end successful. Meeting end must not fail solely because task placement failed.

### R-11 Sibling tickets — do not dump, do not dual-ship

- **#2540** owns `summarizeMeeting` output and `parseMeetingMinutes`. This ticket consumes them; it does not change the three-section grammar.
- **#2539** Meeting Notes marketplace agent — no marketplace packaging, prompts, or agent surface.
- **#2542** Follow-up booking proposal — compose-only; no calendar holds, suggested next meetings, or booking CTAs. #2542 R-11 told that ticket not to change `pullStandupMinutesAct`; **this ticket (#2613) owns that generalization**.
- **#2543** Guest-without-tenant — no tenant provisioning.
- **#2541** is the original epic sibling with the same goal and a narrower PM draft (“end of the destination”); its BA Requirements were still unauthored at the time of this contract. **Do not** close, retarget, or implement #2541 from this ticket. **Do not** ship two acts. Implementers of #2613 ship the single `pullStandupMinutesAct` defined here. Coordinators must not merge two PRs that each introduce a minutes-to-task act.
- **#2538** is the parent epic, not a dump target.

### R-12 Standup regression

Standup meetings that previously would have used `pullStandupMinutesAct` still get open items placed through this same pipeline. No standup-only title handling beyond the shared parser. Empty action-items on a standup is still a no-op success (R-4).

### Explicit non-goals (must not ship in this change)

- Notifications, email digests, or third-party task backends (Jira, Linear, etc.).
- Editing, completing, or deleting tasks from the meeting UI as part of this act.
- Closed action items, arbitrary Markdown outside the three-section contract, or re-summarisation.
- Deduplication by anything other than title.
- `specs/tasks/task-2613.md` must not ship.
