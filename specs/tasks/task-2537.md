# WIP PRD: Mirror to advisor's connected calendar when present

## Problem & Goal

Advisors already live in an external calendar (Google Calendar, Microsoft Outlook/365). Meetings created or changed in-product that never appear there are missed, double-booked, or manually re-entered.

**Goal:** When an advisor has a connected calendar, every in-product meeting that involves that advisor is mirrored to that calendar and kept in sync for create, update, reschedule, and cancel. When no calendar is connected, in-product scheduling is unchanged and no external write is attempted.

Success looks like: the advisor’s connected calendar is a faithful, timely reflection of their in-product meetings, with no duplicate or orphaned events, and no blocking of scheduling if a calendar is absent or temporarily unavailable.

## Target users / ICP roles

- **Advisor** — owns the connected calendar; primary beneficiary of mirroring.
- **Client / advisee** — books or is assigned meetings with the advisor; does not need calendar-connect for this feature.
- **Ops / admin** — may create or reassign meetings on an advisor’s behalf.
- **Not in scope for this feature:** client calendar connect, team/shared calendars as write targets, or calendar-as-source-of-truth reverse sync.

## Scope

In scope:

- Detect whether the advisor has a currently connected, authorized calendar.
- Mirror in-product meetings the advisor is assigned to (create / update / reschedule / cancel) to that calendar when connected.
- Map core meeting fields: title, start/end (timezone-aware), location or join URL, description/notes, attendees when the provider allows.
- Idempotent writes: one in-product meeting ↔ one remote event; retries must not duplicate.
- Store a durable remote event identifier on the in-product meeting for later update/delete.
- On disconnect or revoked access: stop new writes; leave existing remote events as-is unless an explicit cleanup path is later specified.
- Degrade gracefully: calendar API failure must not fail the in-product meeting mutation; queue retry with backoff and surface advisor-visible sync status.
- Honor provider auth (OAuth tokens, refresh, scopes for event write).

Out of scope is listed in its own section below.

## Functional requirements

1. **Presence gate.** Before any external write, resolve the advisor’s calendar connection. If missing, expired without refresh, or revoked, skip mirroring and leave the in-product record as source of truth.
2. **Create.** On meeting create (or advisor assignment to an existing meeting), if a calendar is present, create a corresponding event on the advisor’s connected calendar and persist the remote event id.
3. **Update / reschedule.** On time, duration, title, location/join URL, description, or attendee changes, patch the remote event when a remote id exists and the connection is still present.
4. **Cancel / unassign.** On meeting cancel, delete, or advisor removal, delete (or cancel, per provider) the remote event when a remote id exists and the connection is still present. Clear the stored remote id after a successful delete.
5. **Reassignment.** If the meeting moves from advisor A to advisor B: delete A’s remote event if A is connected; create on B’s calendar if B is connected.
6. **Idempotency & dedupe.** Writes keyed by in-product meeting id + advisor id. Replay of the same mutation must not create a second remote event.
7. **Field mapping.** Use a single, documented mapping. Do not overwrite remote-only fields the product does not own. Default visibility/privacy follows product meeting confidentiality (busy vs. details) if the provider supports it.
8. **Timezone.** Persist and send timezone-aware instants; never assume the server’s local zone.
9. **Retry & status.** Transient provider errors enqueue retries with exponential backoff and a bounded max. Expose sync states on the meeting or advisor connection: `synced`, `pending`, `error`, `skipped_no_calendar`.
10. **Auth hygiene.** Use the advisor’s stored tokens only. Do not write to any calendar except the connected advisor calendar for that advisor. Refresh tokens as needed; on unrecoverable auth failure mark the connection broken and stop writes until reconnected.
11. **No reverse sync in this slice.** Remote-only creates/edits/deletes are not imported back into the product.

## Acceptance criteria

- Given an advisor with a valid connected calendar, when a meeting is created for them, a matching event appears on that calendar within the sync SLA (near-real-time; retries complete without duplicate events).
- Given the same meeting is rescheduled or its title/location/join URL/description changes, the existing remote event is updated in place (same remote id), not recreated.
- Given the meeting is canceled or the advisor is unassigned, the remote event is removed or canceled and the stored remote id is cleared.
- Given an advisor with no connected calendar, meeting create/update/cancel succeeds fully in-product and no calendar API calls are made.
- Given a meeting is reassigned from advisor A (connected) to advisor B (connected), A’s remote event is removed and B’s calendar receives a new event.
- Given a meeting is reassigned to an advisor with no calendar, A’s remote event is removed if applicable and no write is attempted for B.
- Given a duplicate delivery of the same create, only one remote event exists.
- Given the calendar provider returns a transient error, the in-product mutation still succeeds and sync status is `pending` then `synced` or `error` after retries.
- Given tokens are revoked mid-flight, writes stop, connection is marked broken, and the user can reconnect without orphaning the in-product meeting.
- Timezones on the remote event match the meeting’s timezone; all-day vs. timed is preserved when the product supports all-day.
- No client calendar is written. No write occurs to a calendar that is not the assigned advisor’s connected account.

## Out of scope

- Two-way sync, importing advisor-calendar events into the product, or treating the external calendar as source of truth.
- Mirroring to the client’s calendar, conference-room resources, or a firm-wide/shared calendar.
- Free/busy read, conflict detection against the external calendar, or booking-slot generation from calendar availability (may exist as a separate feature).
- Recurring-series edge cases beyond what the product already models; if the product has no recurrences, do not invent them on the remote side.
- Historical backfill of meetings created before the advisor connected a calendar (optional follow-on).
- Deleting remote events on calendar disconnect.
- Custom reminders, conferencing-provider auto-generation beyond passing through an existing join URL, or attachments.
- Multi-advisor meetings writing to more than each assigned advisor’s own connected calendar (if multi-advisor is unsupported in-product, do not add it here).
- UI for picking a specific calendar among multiple calendars in the provider account, unless a default calendar is already part of the existing connect flow.
- Compliance/legal hold, eDiscovery export, or provider-specific features (Focus time, Out of office, Google Tasks).
