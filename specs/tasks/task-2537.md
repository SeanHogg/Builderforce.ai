# PRD: Mirror to Advisor's Connected Calendar When Present

**Status:** WIP  
**Feature:** Mirror platform events to an advisor’s connected external calendar when a connection exists  
**Priority:** P1

## Problem & Goal

Advisors schedule and manage client work inside the product, but they live in Google Calendar, Outlook, or similar. When a platform event is created, updated, or cancelled, it often never appears on the advisor’s real calendar unless they copy it by hand. That causes missed meetings, double-booking, and extra admin.

**Goal:** When an advisor has a connected calendar, automatically mirror eligible platform events onto that calendar (create / update / cancel). When no calendar is connected, the product flow must still succeed and must not require a calendar. Mirroring is best-effort relative to the source of truth in the product.

## Target users / ICP roles

- **Advisor** — primary beneficiary; owns the connected calendar and needs events visible in their day-to-day calendar app.
- **Client / advisee** — books or participates in events that should land on the advisor’s calendar; does not need to know about mirroring.
- **Ops / admin** — may create or reassign events on behalf of advisors; needs mirroring to follow the assigned advisor.
- **Internal platform / integrations** — calendar connection, token refresh, and sync workers.

## Scope

In scope for this WIP:

- One-way mirror: **product event → advisor’s connected calendar** (not full two-way sync).
- Trigger on create, update, cancel/delete of eligible events assigned to an advisor.
- Honor “when present”: if the advisor has no connected calendar, skip mirroring and complete the product operation.
- Support already-connected Google Calendar and Microsoft 365 / Outlook calendars (existing OAuth connections).
- Map core event fields, keep a stable external event id, and keep product as source of truth.
- Idempotent writes; retries with backoff; non-blocking failure (product mutation succeeds even if mirror fails).
- Re-mirror or clean up when the assigned advisor changes, when a calendar is connected after events already exist, and when a calendar is disconnected.

## Functional requirements

### Eligibility

1. An event is eligible if it is an advisor-facing scheduled item (meeting, appointment, or blocked working session) with a start time, end time, and assigned advisor.
2. All-day and timed events are both eligible. Internal-only notes, audit logs, and client-private records that the advisor should not put on an external calendar are not eligible.
3. Mirroring is per assigned advisor. If an event has no assigned advisor, do not mirror.

### Connected calendar detection

4. “Connected calendar present” means the assigned advisor has a valid, non-revoked calendar integration with a writable target calendar selected (or a documented default, e.g. primary).
5. If no connection, expired/revoked tokens that cannot be refreshed, or no writable calendar, treat as **not present** and skip mirroring without failing the user-facing action.
6. Calendar presence is evaluated at mirror time, not only at event creation.

### Create / update / cancel

7. **Create:** After the product event is persisted, upsert a corresponding event on the advisor’s connected calendar.
8. **Update:** When title, description/notes (sanitized), start, end, timezone, location/conference link, or attendee-visible status changes, patch the remote event. Do not create duplicates.
9. **Cancel / delete:** When the product event is cancelled or deleted, delete or cancel the remote event if it exists. Missing remote events are not errors.
10. **Reassignment:** If the assigned advisor changes, remove (or cancel) the remote event from the previous advisor’s calendar if still connected, and create it on the new advisor’s calendar if connected.
11. **Late connect:** When an advisor connects a calendar, enqueue mirroring of that advisor’s upcoming eligible events (not historical events older than a defined lookback, default 1 day in the past).
12. **Disconnect / revoke:** Stop new mirrors. Best-effort delete previously mirrored events that the product created, or leave them with a documented policy; do not block disconnect.

### Field mapping and privacy

13. Remote event title and times must match the product event. Timezone must be preserved; do not silently convert to UTC in the advisor’s UI.
14. Description may include meeting purpose, join link, and client display name **only if** the advisor’s org settings allow client identifiers on external calendars. Default: include join link and generic title; omit sensitive account/financial detail.
15. Do not write secrets, internal IDs in the title, or data the client marked private.
16. Conference/join URL from the product, if any, is copied onto the remote event.
17. The product stores `external_calendar_id`, `external_event_id`, provider, and last successful sync timestamp on the event (or a mirror mapping table).

### Reliability and conflict behavior

18. Product CRUD is the source of truth. Calendar API failure must not roll back the product event. Surface a non-blocking warning to the advisor when a mirror fails persistently.
19. Writes are idempotent on `(event_id, advisor_id, provider, calendar_id)`.
20. Concurrent updates: last product write wins; use etag/if-match where the provider supports it; on 409/412, re-fetch and retry once.
21. If the remote event was deleted or edited by the advisor, the next product update recreates or overwrites the mirrored fields. Do not attempt to merge arbitrary advisor-side edits in this WIP.
22. Respect provider rate limits; queue per-advisor; retry with exponential backoff and a dead-letter after N failures.
23. Do not invite the client as a calendar attendee from the advisor’s personal calendar unless that is already an explicit product behavior. Default: advisor-only event (no extra invites that spam the client).

### Permissions and audit

24. Only use the advisor’s own OAuth grants. Never write to another user’s calendar.
25. Log mirror attempts (success/skip/fail) with event id, advisor id, provider, and reason. No payload secrets in logs.

## Acceptance criteria

1. Given an advisor with a valid connected writable calendar, creating an eligible event results in a matching event on that calendar within the sync SLA (target: &lt; 60 seconds under normal load).
2. Given no connected calendar (or revoked/unwritable), creating/updating/cancelling the same event succeeds in the product with no error requiring calendar setup; no remote write is attempted beyond a cheap presence check.
3. Updating time, title, location, or join link on the product event updates the existing remote event; a second remote event is not created.
4. Cancelling or deleting the product event removes or cancels the remote event when a mapping exists; repeating the cancel is a no-op.
5. Reassigning the event from Advisor A to Advisor B removes/cancels A’s remote copy if A is connected and creates B’s remote copy if B is connected.
6. Connecting a calendar backfills upcoming eligible events for that advisor and does not duplicate events that already have a mapping.
7. Disconnecting a calendar stops further mirrors; subsequent product actions still succeed.
8. Client-sensitive fields configured as excluded never appear in the remote description/title.
9. Calendar API 5xx / rate limit / transient auth-refresh failure leaves the product event intact, records a failed mirror, and retries; after exhausting retries the advisor can see a non-blocking sync warning.
10. Token refresh succeeds for a still-valid connection and mirroring continues without the advisor re-OAuthing.
11. All-day events and timed events in non-UTC timezones round-trip without date or hour shift on Google and Microsoft calendars.
12. Automated tests cover: connected create/update/cancel, skip-when-absent, reassignment, late connect backfill, idempotent retry, and mapping persistence.

## Out of scope

- Two-way sync (importing advisor-created calendar events into the product, or treating the external calendar as source of truth).
- Free/busy availability reads, booking-slot generation, or conflict blocking based on the external calendar (separate feature).
- New calendar providers beyond already-supported Google and Microsoft 365/Outlook.
- Mirroring to a client’s calendar, team shared mailboxes, or an org-wide resource calendar.
- Recurrence expansion edge cases beyond what the product already stores (no new RRULE engine).
- Full merge of advisor-side edits, attachments, or guest-list management on the provider event.
- Historical backfill of past events beyond the small lookback used for late connect.
- SMS/email notification redesign, video-meeting provider changes, or calendar-connect onboarding UX beyond a failure/warning state.
- Compliance-specific redaction packs per jurisdiction (use the single org setting in this WIP).
