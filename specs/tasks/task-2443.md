# PRD: Chat Switcher Dropdown — Per-Chat Percentage

## Problem & Goal

**Problem:** The chat switcher dropdown renders the same percentage on every row. The value is not bound to the chat it sits next to, so users cannot tell conversations apart by linked-ticket progress and may act on a stale or duplicated number.

**Goal:** Each row in the chat switcher shows that chat’s own current linked-ticket progress percentage (`ticketProgressPct` on the client chat record; `progressPct` from `GET /api/brain/chats` per #2437). The value stays correct when chats are opened, switched, updated, or removed, and when the dropdown is reopened.

This is **not** a context-window / token-usage meter. That metric is a separate gap (called out on #2442). Do not retarget this ticket to billing, cost, quality, or token fill.

## Scope

- Chat switcher trigger and dropdown list
- Per-row percentage for each listed chat
- Data binding, refresh, and empty/unavailable states for that metric
- Desktop and the product’s existing responsive/web layouts for this control

## Functional requirements

1. Every chat row in the dropdown displays the percentage that belongs to **that** chat, not the active chat, a shared default, a previously selected chat, or a closure over a single list-level value.
2. The percentage is that chat’s **linked-ticket rollup** (`ticketProgressPct` / list `progressPct`). It is **not** context-window fill, token usage, billing, cost, or quality. Format through the existing `chatSwitcherLabel` helper (`{n}% · {title}` when a number is present). Numeric `0` is a real value and MUST render as `0%`. `null` / `undefined` omits the metric — never inherit another chat’s number, and never coerce with a client-side `?? 0`.
3. Opening the dropdown always reads current per-chat values from each row’s own record; it does not freeze a snapshot from first render or from the last selected chat.
4. After the chat list is refreshed (switch, rename, delete, new chat, or the ticket-health refresh owned by #2441), visible rows update to the latest per-chat percentages without a full page reload. Message send/receive alone does **not** change this metric.
5. If a chat has no computable percentage yet, the row omits the metric and never shows another chat’s number.
6. Percentage text does not overflow, truncate into another row’s label, or replace the chat title; title and metric remain distinct (`chatSwitcherLabel` concatenates them in one string with ` · `).
7. Keyboard, pointer, and screen-reader behavior of the switcher is unchanged except that each row’s accessible name/description includes that chat’s own percentage when a value is shown.
8. Performance: opening the dropdown and rendering a typical list (tens of chats) does not introduce a noticeable stall versus today’s switcher. No extra per-row network calls (owned by #2444).

## Acceptance criteria

- Given two or more chats with different linked-ticket progress values, when the user opens the switcher, each row’s percentage matches that chat’s current `ticketProgressPct` / `progressPct` and at least two rows differ when the underlying values differ.
- Given chats A and B, when the user is in A and opens the switcher, B’s row still shows B’s percentage (not A’s).
- Given a chat whose linked-ticket progress changes (ticket health refresh per #2441), when the user reopens or keeps the dropdown open per existing UI behavior, that row shows the updated percentage and other rows are unchanged.
- Given a newly created chat with no tickets / no computable progress yet, its row omits the metric and does not inherit another chat’s percentage.
- Given a deleted chat, it disappears from the list and does not leave its percentage on another row.
- Given a single chat in the list, the one row shows that chat’s percentage correctly (or omits it if unknown).
- Given `ticketProgressPct === 0`, the row renders `0%` (zero is a real rollup, not “unknown”).
- Visual and a11y checks: no duplicated/stale percent string across rows; no overlap with titles; row accessible names reflect the correct per-chat value.
- Regression: selecting a chat from the dropdown still activates that chat; order, unread/active treatment, and existing switcher actions are unchanged.

## Requirements

This ticket owns **per-row data binding** in the Brain chat switcher dropdown. Sibling tickets own the formatter, the list API, the DTO, refresh, and the VSIX tree. Do not expand this ticket into those.

### Metric (locked)

- **What it is:** linked-ticket rollup progress for the tickets attached to **that** chat.
- **Client field:** `ticketProgressPct` on the chat record already consumed by `chatSwitcherLabel` (`packages/brain-ui/src/chatTickets/chatSwitcherLabel.ts`).
- **List field:** `progressPct` on `GET /api/brain/chats` (owned by #2437). The dropdown binds each row to **that row’s** field after the client maps list → `ticketProgressPct` (#2438).
- **What it is not:** context-window fill, token usage, billing, cost, or quality. Ada’s first draft of this PRD named “usage”; that is wrong. #2442 already called out a separate context-window gap. Do not retarget #2443.

### Binding rule (this ticket’s core)

1. For each dropdown row, the percent is computed from **that row’s chat object only**: `chatSwitcherLabel(chat)` / `chat.ticketProgressPct`. It is illegal to pass the active chat’s percent, a component-level `progressPct`, a `useMemo` closed over the selected id, or the first list item into every row.
2. Two chats with different `ticketProgressPct` values MUST render different prefixes. If they do not, the bug is still open — even if the formatter is correct in isolation.
3. Switching the active chat MUST NOT rewrite other rows’ percentages.
4. Deleting a chat removes that row and MUST NOT leave its percent on a neighbor.
5. A new chat with no computable progress omits the metric; it MUST NOT inherit a sibling’s number.

### Empty / zero / unavailable

Align with #2440 and the epic; do **not** invent a third policy:

| Value | Render |
| --- | --- |
| `ticketProgressPct` is a number, including `0` | `{n}% · {title}` (zero is a real rollup) |
| `null` / `undefined` / field absent | title only — omit the metric |
| Client default | **never** `?? 0` on the dropdown path |

**Nullability vs #2437:** #2437’s BA text currently says the API field is never-null and may use `summary?.pct ?? 0`. The epic and #2440 say omit if unknown. This ticket does not resolve that API debate. The **dropdown** treats missing as omit and `0` as `0%`. If #2437 ships always-present `0`, chats with no tickets will show `0%` here; do not add a second client-side coerce.

### Formatter (do not re-author)

`chatSwitcherLabel` already exists and is covered by `chatSwitcherLabel.test.ts`. #2440 owns any remaining formatter work (`n% · title`, numeric 0 shows, null omits). #2443 consumes it per row. Do not fork a second formatter in `BrainPanel` / the VS Code webview.

### Refresh

- Dropdown open reads **current** per-chat records (no stale snapshot from first mount or last selection).
- List mutations this control already handles (switch, rename, delete, new chat) re-bind from the updated list.
- Ticket-health changes after the list was fetched are #2441. Message send/receive does **not** move this metric.

### Surfaces in scope

- Product Brain chat switcher trigger + dropdown list (web `BrainPanel` and any shared `@builderforce/brain-ui` switcher that lists chats with `chatSwitcherLabel`).
- Existing desktop / responsive web layouts for **this** control.

### Surfaces out of scope (pointers)

- VSIX Sessions TreeView conversation rows: #2439 / #2442 (`TreeItem.description`, title stays title-only).
- `GET /api/brain/chats` batch `progressPct`: #2437.
- `BfBrainChat.progressPct?`: #2438.
- Ticket-health refresh: #2441.
- No N+1 on the list: #2444.

### Accessibility

Unchanged switcher keyboard / pointer behavior. When a percent is shown, that row’s accessible name/description includes **that** chat’s value (the `chatSwitcherLabel` string is sufficient if it is the accessible name). Do not announce a shared percent on every row.

### Performance

Tens of chats, no extra per-row fetch. Binding is an O(n) map over records already in memory.

### Likely defect (for architect / developer — not a BA implementation)

`chatSwitcherLabel` is correct **if** each chat object carries its own `ticketProgressPct`. The duplicated-percent symptom is therefore one of:

1. **Shared value in the UI** — the dropdown maps `chats` but labels with `activeChat.ticketProgressPct` or a single hook value; or
2. **Shared value on the list** — `GET /api/brain/chats` stamps one `progressPct` onto every item (#2437 must fix the payload; #2443 still must not collapse distinct payload values).

Architect owns which of those is true in Design. Developer binds the row to the row. QA asserts two chats with different percents render two different prefixes, including “user is in A, B’s row still shows B.”

### Acceptance mapping

| Criterion | Requirement |
| --- | --- |
| Two chats, different percents, both visible and different | Binding rule 2 |
| In A, B’s row shows B | Binding rule 1, 3 |
| Progress change updates that row only | Refresh + #2441 |
| New chat does not inherit | Binding rule 5 |
| Deleted chat does not leak percent | Binding rule 4 |
| Single-chat list is correct | Binding rule 1 |
| `0` renders `0%` | Empty / zero table |
| Unknown omits | Empty / zero table |
| Select still activates; order / unread / actions unchanged | Regression — no switcher redesign |
