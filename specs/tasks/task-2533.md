# PRD: Public Availability Read

## Problem & Goal

External bookers and integrators need a safe way to discover when a host is free without a login and without leaking calendar internals. Today, any public or share-link read that returns stored busy windows, past intervals, or attendee lists exposes private schedule data and third-party identities.

**Goal:** Ship a tokenised / slug-scoped public availability read that returns **only future free slots**. The response must never include raw calendar windows, busy intervals as stored, past time, or other attendees.

## Target users / ICP roles

- **Host / calendar owner** — publishes a public slug or share token so others can see bookable time.
- **External booker** — anonymous or lightly identified visitor choosing a slot.
- **Integrator** — third-party app that polls availability via the public read, not the private calendar API.
- **Platform / scheduling product** — owns slot computation, token/slug scoping, and privacy guarantees.

## Scope

In scope for this WIP:

- Unauthenticated (or token-only) **read** of availability for a single host or resource, addressed by **public slug** or **share token**.
- Server-side computation of **future free slots** from the host’s calendars, working hours, buffers, and existing bookings.
- Response shape limited to bookable slots (start/end in a declared timezone, optional duration / slot id).
- Enforcement that the read is **scoped** to the slug/token’s subject; no cross-host or org-wide dump.
- Privacy: omit attendees, event titles, locations, conference links, and raw busy/free windows.
- Time bounds: only slots whose start is strictly in the future relative to request time (with a small clock-skew allowance defined in acceptance).
- Rate limiting, token/slug validation, and revocation of share tokens.

## Functional requirements

1. **Addressing**
   - Resolve the subject exclusively from a public slug **or** a share token. Invalid, expired, revoked, or unknown identifiers return the same not-found response (no existence oracle beyond that).
   - The token/slug may encode host, event type, duration, and optional timezone preference; it must not grant access to any other host or to private calendar APIs.

2. **Slot computation**
   - Compute free slots from working hours, booking rules (duration, buffers, min notice, max horizon), and existing holds/bookings.
   - Return only **future** slots. Drop any slot with `start <= now` (after skew).
   - Do not return raw busy windows, free/busy blocks, iCal VEVENT payloads, or “gaps between meetings.”
   - Collapse and snap to the event type’s duration (or the duration encoded on the token/slug). Overlapping or adjacent free time must appear as discrete bookable slots, not as a continuous window.

3. **Privacy**
   - Never include other attendees (names, emails, ids), organizer identity beyond what the slug already implies, event titles, descriptions, locations, or conference URLs.
   - Never echo calendar provider ids, recurring-event masters, or exception lists.
   - Error and empty states must not leak whether a conflict was a meeting vs. blocked time vs. outside hours.

4. **Response**
   - Success: list of future free slots (start, end, timezone; optional slot id / duration). Empty list is a valid success when the host has no future free time in the queried range.
   - Support an optional bounded query range (`from` / `to`) that cannot extend into the past and cannot exceed the product’s max booking horizon.
   - Pagination or a hard cap on slot count if the range would otherwise explode.

5. **Safety**
   - Read-only. This endpoint must not create, hold, or cancel bookings.
   - Apply per-slug/token and per-IP rate limits.
   - Share tokens are revocable; revocation takes effect on subsequent reads.

## Acceptance criteria

- Given a valid slug or share token, the client receives only future free slots for that subject and no other fields that describe calendar events or people.
- Given the same underlying calendar, two clients cannot reconstruct raw busy windows or attendee lists from the public response (no busy arrays, no event objects, no attendee keys).
- Slots with `start <= now` (plus documented skew, e.g. 30s) are absent from every response.
- Past `from` values are clamped or rejected; they never cause past slots to appear.
- Invalid, expired, or revoked token/slug → identical not-found; no differential errors that distinguish “revoked” vs “never existed” to unauthenticated callers.
- A slug/token for host A never returns slots (or errors) that imply host B’s calendar.
- Empty availability in-range → `200` with an empty slot list, not an error.
- Response payloads contain no attendee, title, location, or provider-event identifiers (contract test / schema allowlist).
- Rate-limit exceeded → standard rate-limit error without calendar data.
- Revoking a share token causes subsequent reads with that token to fail closed.

## Out of scope

- Authenticated / owner calendar read, free/busy for conferencing add-ins, or any API that returns raw windows.
- Booking, holds, reschedule, cancel, or waitlist writes.
- Multi-host / round-robin / collective availability in a single public response.
- Exposing other attendees even in anonymized or hashed form.
- Historical availability, analytics, or “when were they free last week.”
- Changing working hours, event types, or privacy settings (those remain owner-only).
- Calendar provider webhooks, sync, or OAuth connect flows.
- UI for the public booking page beyond the data contract this read feeds.

- Internal free/busy (`computeFreeBusy` in `calendarFreeBusy.ts`) returns `{ start, end, busy: [{ start, end }] }`. That shape is **forbidden** on any unauthenticated or token-only response. It may be used *inside* the solver only.
- Host bind for talent/advisors is `booking_hosts.host_ref` (user id), not `freelancer_profiles.booking_service_id`, not a new listing kind `advisor`, and not `/advisors`.
- Docs-only `specs/tasks/task-2533.md` is **not** this deliverable.

Assumptions (signed; architect may tighten, not loosen privacy):

| ID | Assumption | Default |
| --- | --- | --- |
| A-1 | Clock-skew allowance on “future” | **30 seconds** |
| A-2 | Default max booking horizon if the service has none | **14 days** from request time |
| A-3 | Hard cap on `to` (even if the service allows more) | **60 days** from request time |
| A-4 | Hard cap on slots returned | **200**, earliest first; `truncated: true` if more exist |
| A-5 | Rate limit | **30 req / 60s / IP** and **60 req / 60s / slug-or-token**; first trip wins |
| A-6 | Slot instants | UTC ISO-8601 with `Z`; `timezone` is the host IANA zone for display |
| A-7 | Duration | Bound on the slug/token’s event type / booking service; **no** query override |

### R-1 Addressing — slug or share token only

1. The unauthenticated read resolves **exactly one subject** from **either**:
   - a **public slug** already used by the booking catalogue (one booking service / event type bound to one host), **or**
   - a **share token** (opaque, high-entropy, non-enumerable).
2. The identifier must not be a host UUID, talent `userId`, `booking_hosts.id`, freelancer profile id, Google calendar id, or tenant id. Those keys are existence oracles and cross-host probes.
3. The token/slug may encode host, event type, duration, and optional timezone *preference*. It must not grant access to any other host, any private calendar API, org-wide dumps, or authenticated owner routes.
4. Share tokens are **revocable**. Revocation is effective on the next read (no caching that serves slots after revoke).
5. Invalid, expired, revoked, malformed, or unknown identifiers return the **same** not-found response (same status, same body, same timing budget). Unauthenticated callers must not distinguish “never existed” vs “revoked” vs “expired” vs “wrong host”.
6. A slug/token for host A never returns slots, truncated flags, errors, or headers that imply host B’s calendar.

**AC:** Given identifier I bound to host A, the response (success or error) contains no slots and no error text that could only be true of host B. Given a revoked token and a never-issued token, unauthenticated responses are indistinguishable.

### R-2 Slot computation — future free slots only

1. The server computes bookable slots from the subject’s working hours, booking rules (duration, buffers, minimum notice, max horizon), and existing **holds + confirmed reservations + busy time from connected calendars**.
2. Return **only future free slots**. Drop any slot with `start <= now + 30s` (A-1). Minimum-notice rules additionally drop slots with `start < now + minNotice`.
3. Collapse and snap to the event type’s duration (or the duration encoded on the token/slug). Overlapping or adjacent free time appears as **discrete** slots of that duration, not as a continuous free window and not as “gaps between meetings.”
4. Do **not** return: raw busy windows, free/busy blocks, iCal VEVENT payloads, Google `busy[]`, “gaps,” exception lists, or recurring-event masters.
5. Pending holds count as busy for computation and are never listed as events.
6. If the host has multiple connected calendars, the solver **unions** busy time internally; the public response is still only slots.

**AC:** Given the same underlying calendar, two clients cannot reconstruct raw busy windows from the public response (no busy arrays, no event objects, no attendee keys, no gap math that reveals meeting length). Slots with `start <= now + 30s` are absent from every response.

### R-3 Privacy allowlist (schema contract)

Success body **may** contain only:

| Field | Meaning |
| --- | --- |
| `timezone` | Host IANA timezone (display). |
| `durationMinutes` | Slot length bound to the slug/token. |
| `slots` | Array of `{ start, end }` UTC instants; optional opaque `id`. |
| `truncated` | Boolean; present only when the slot cap (A-4) was hit. |

Optional opaque `id` — if present — is a computed fingerprint of `(subject, start, end, duration)`, **never** a provider event id, iCal UID, or database serial that enumerates other rows.

Success and error bodies **must not** contain (contract test / schema denylist): `attendees`, `organizer`, `title`, `summary`, `description`, `location`, `hangoutLink`, `conference`, `htmlLink`, `busy`, `events`, `items`, `email`, `emails`, `attendee`, `iCalUID`, `recurringEventId`, `provider`, `calendarId`, `eventId`, `hangout`, `meetUrl`, `video`, `participants`, host personal email, visitor identity, or any third-party calendar object.

Empty availability in-range is **`200` with `slots: []`**, not an error, and must not say *why* (meeting vs blocked vs outside hours vs buffer vs min notice). All of those collapse to “no slot.”

Host display name / price / service title belong on the **existing catalogue** read, not on this availability payload.

**AC:** A schema allowlist test fails the build if a denylist key appears on 200/4xx/429 bodies for this read.

### R-4 Query range

1. Optional `from` / `to` (ISO-8601 instants). If omitted, `from = now + skew` and `to = now + default horizon` (A-2), still capped by A-3 and the service’s max horizon (the tighter bound wins).
2. Past `from` is **clamped** to `now + skew`; it is not a 4xx and it **never** causes past slots to appear.
3. `to` beyond the max horizon is clamped; it is not an oracle for “this host allows 90 days.”
4. After clamp, if `to <= from`, return `200` with `slots: []`.
5. Invalid (unparseable) `from`/`to` → `400` with a generic validation error and **no** calendar fields. Do not 400 merely because `from` was in the past.
6. Visitor `timezone` query, if accepted at all, is **display-only**. It must not change which instants are free (working-hours grid stays in the host zone).

**AC:** A request with `from` last week returns only future slots. A request with `to` next year does not exceed A-3 / service horizon.

### R-5 Pagination / explosion guard

If the computed set would exceed **200** slots (A-4), return the **earliest** 200 and `truncated: true`. v1 does **not** require a next-page cursor (cursors enlarge the probe surface). Clients that need a later window pass a later `from`.

**AC:** A wide-open range on a fully free calendar never returns more than 200 slots.

### R-6 Safety — read-only

1. This endpoint **must not** create, hold, confirm, reschedule, or cancel bookings. GET (or equivalent read) only. No implicit hold on fetch.
2. It must not write calendar events, attendees, or conference links.
3. Unauthenticated **403** is forbidden for this read (403 vs 404 is an existence oracle). Use **404** for identifier failure and **429** for rate limit.
4. Rate-limit exceeded → standard 429 (optional `Retry-After`) with **no** slots and no calendar fields (A-5).
5. Request logs for this path must not persist attendee lists, event titles, or provider payloads pulled during computation.

**AC:** Repeating the read does not reduce remaining free slots. A 429 body matches the denylist in R-3.

### R-7 Subject isolation and tenancy

1. Token/slug resolution loads the host’s tenant **internally** (same idea as interview-scheduling token→tenant used by #2535). Tenant id is not returned.
2. Slot computation runs in that tenant’s booking + calendar data only.
3. `acrossTenants` public catalogue remains catalogue-only; this read must not become an org-wide or cross-tenant slot dump.
4. Do not add `advisor` to `MARKETPLACE_LISTING_KINDS` and do not add `/advisors` to satisfy this ticket.

**AC:** Two hosts in different tenants with similar slugs cannot see each other’s slots. Guessing sequential ids yields only the R-1 not-found.

### R-8 Catalogue vs availability (do not overload)

1. Existing public service list/get (slug catalogue, freelancer booking-services) stay as they are: service metadata, not availability.
2. This ticket adds a **dedicated** public availability read. Do not hang `slots` or `busy` off the catalogue payload (that would bypass the allowlist and leak into every service card).
3. The public booking page (#2534) may call catalogue + this read; this ticket ships only the read.

### R-9 Error catalogue (unauthenticated)

| Situation | Status | Body |
| --- | --- | --- |
| Unknown / expired / revoked / malformed slug or token | 404 | Identical not-found; no calendar fields |
| Unparseable `from`/`to` | 400 | Generic validation; no calendar fields |
| In-range but no free slots (including clamped empty range) | 200 | `{ slots: [] }` |
| Rate limit | 429 | Standard rate-limit error; no calendar fields |
| Method not GET | 405 | No calendar fields |
| Writes attempted on this resource | 405 or 404 | No booking created |

Never return 409 on this read. Never return provider errors (Google 403, sync lag) as distinct public codes; treat them as empty slots or the same 404, whichever does not leak connectivity.
