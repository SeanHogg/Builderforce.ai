### D-1 — Change A: Run visibility architecture

Three subsystems, already written, verified not re-authored:

#### D-1.1 — Composing tool-call stream (P0 / FR-1)

- **Source:** The brain execution engine emits tool-call events during a run's composing phase.
- **Transport:** Events flow through the existing WebSocket/signal channel already used for run status.
- **UI surface:** `brain-ui` (and by extension the VS Code webview) renders a **live composing label** that reflects the most recent tool-call name — e.g. "Composing: read_file" — driven by the stream, not by a polling timer.
- **State machine:**
  - `idle` → no active run or run is paused.
  - `composing` → run is executing, tool-call stream is active, label updates in real time.
  - `error` → composing failed; label shows error state, not stale composing.
- **Anti-patterns to verify against:** stale idle label after run starts; generic "Working…" instead of specific tool name; label stuck on last tool after composing ends.

#### D-1.2 — Idle watchdog (P1 / FR-2)

- **Purpose:** Distinguish true idle (no run, run queued but not started, run paused) from in-flight composing where the tool-call stream is simply quiet.
- **Mechanism:** A heartbeat-based watchdog in `brain-embedded` (or `brain-ui`) that:
  1. Resets on every tool-call event received.
  2. If no event arrives within a configurable timeout (suggested: 30 seconds), transitions from `composing` to `stale-composing`, then fires a diagnostic signal.
  3. True idle is a different state (no active run at all).
- **UI consequence:** The operator sees "Idle" only when no run is active. During composing, even a quiet stream shows "Composing (waiting…)" — never "Idle".
- **Anti-patterns to verify against:** watchdog fires during active composing; watchdog never fires when run is genuinely hung; watchdog fires on runs that are merely waiting on a slow tool.

#### D-1.3 — Triage context-pressure (P2 / FR-3)

- **Purpose:** Prevent the triage/chat view from opening with a CONTEXT EXHAUSTION banner when pressure-handling is active.
- **Mechanism:** The context-pressure monitor (already in `api` or `brain-embedded`) absorbs pressure events rather than propagating them to the UI as a blocking banner. The pressure state is still observable via diagnostics, but it does NOT block triage open.
- **UI contract:** `triage:open` must succeed without a modal/blocking "CONTEXT EXHAUSTION" banner when pressure absorption is in place.
- **Anti-patterns to verify against:** triage blocked by CONTEXT EXHAUSTION banner; pressure silently ignored (no diagnostic signal anywhere); pressure absorption breaks other pressure-related UI (e.g., run pause-on-pressure).

### D-2 — Change B: Ticket-parent architecture (P3 / FR-4)

- **Source:** The ticket data already includes a `parentTaskId` field on the ticket model. The parent's title (epic name) is resolved via the existing ticket API.
- **Resolution path:** `api` → ticket service → `parentTaskId` → fetch parent ticket → extract `title`.
- **UI surface:** The ticket rail in `brain-ui` / VS Code webview renders a parent line below the ticket title, display format: `Epic: {parentTitle}`.
- **Edge cases to verify against:**
  - Ticket has no parent: line is absent (not "Epic: (none)" or "Epic: undefined").
  - Parent exists but has no title (null/empty): line reads "Epic: (untitled)" — NOT an empty string or crash.
  - Parent is not an epic (nested task): still displays — the field is "parent", not "epic parent".
  - Parent fetch fails (network/404): line is absent; error logged to diagnostics; rail does not crash.
