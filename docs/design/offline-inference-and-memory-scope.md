# Shared offline inference and memory scope

Reviewed 2026-10-18 against local source in `builderforce-inference`, `builderforce-memory`, and `Builderforce.ai`. Supplements [the architecture review](vsix-offline-first-architecture-review.md). Static code review only; no GPU benchmarks, browser execution, or package test runs. All requirements apply to Web, Rovr, and VSIX.

## Decision

Reuse **builderforce-inference for inference engines** and **builderforce-memory for local knowledge, retrieval, cognition, and memory learning primitives**. Do not implement competing engines, fact reconciliation, or retrieval in each modality. Use the existing shared TypeScript inference planner/adapter layer to select and drive engines. Memory and inference remain distinct responsibilities integrated through narrow ports.

For automatic generative inference, prefer an already-downloaded, workload-compatible **WebLLM model on WebGPU** when the host exposes a usable GPU adapter. Preserve explicit user model pins subject to offline permission. When WebLLM is unavailable or unfit, try compatible local BFI WebGPU/native or other permitted on-device runtimes. Never silently fall back to BuilderForce API while offline. Local memory recall/cache may satisfy an eligible request before generative inference is needed; a memory hit does not require loading an LLM.

GPU presence alone is insufficient: check usable WebGPU access in the execution context, device creation, features, model-specific buffer limits, installed assets, tool capability, effective context, and actual allocation success. Runtime failure may require a smaller compatible model or another local engine. Capability checks must not download assets or contact the account API.

## Existing inference implementation

| Location | Existing responsibility | Scope decision |
|---|---|---|
| `builderforce-inference/crates/bfi-core`, `bfi-models`, `bfi-runtime`, `bfi-gguf` | Native tensor backends, architectures, generation, tokenizer, grammar/tools, fit, GGUF/model storage | Keep canonical BFI engine mechanics here; reuse native fit/model metadata where applicable |
| `builderforce-inference/crates/bfi-server` | Local HTTP inference interfaces and discovery | Retain native BFI/Synapse adapter; keep local inference independent of `bf-cloud` |
| `builderforce-inference/crates/bfi-web` | WASM `BfiEngine`, WebGPU probe, streaming model load, chat, served-context prediction | Reuse as the BFI browser engine; version its capabilities and error contract |
| `Builderforce.ai/packages/bfi-web` | Vendored generated JS/WASM/types with source commit/hashes | Continue generated-artifact workflow; never hand-edit vendored engine output |
| `Builderforce.ai/packages/local-inference` | Runtime/model registry, fit constraints, discovery, workload filtering, ordered attempt planning | Own pure shared eligibility/ranking policy here; remove preference encoded by incidental registry order |
| `Builderforce.ai/brain-embedded/src/pageEngines` | WebLLM and BFI adapters, GPU probing, model cache/download facade, resident engine coordination | Reuse; extract headless infrastructure exports where necessary rather than copy adapters per modality |
| `Builderforce.ai/brain-embedded/src/hostModelStream.ts` | Shared pin/local-first stream composition | Consume one permission-aware plan and expose structured no-local-model failures |
| Per-host composition | Web origin, extension URLs, host-to-webview bridge, local endpoint discovery | Keep thin; no separate ranking or model readiness rules |

BFI WebGPU and WebLLM are separate engines. BFI consumes its supported GGUF architecture/quantizations; WebLLM consumes compatible MLC artifacts. A downloaded GGUF is not automatically a WebLLM model. The inspected BFI browser code documents qwen3/Bonsai Q1_0 support; native architecture support must not be advertised as browser support without implementation/testing.

Concrete inference gaps:

1. **Ranking:** `local-inference/src/runtimes.ts` currently orders Synapse → Ollama → FreeToken → BFI page engine → WebLLM → browser model. `plan.ts` uses registry order, generally tries one local candidate, then adds cloud. Add a policy-driven WebLLM/WebGPU preference after workload eligibility filtering. Thread policy through the shared host stream instead of reordering candidates independently in each host.
2. **GPU limits mismatch:** TypeScript `pageEngines/webgpu.ts` assigns `maxStorageBufferBindingSize` to `maxBufferBytes`; Rust `bfi-web/src/support.rs` exports `maxBufferSize` as `maxBufferBytes` and retains binding size internally. These limits have different meanings. Version the shared support contract with explicit `maxBufferSizeBytes` and `maxStorageBufferBindingSizeBytes`; update fit/context calculations and generated types together. Neither limit measures total free VRAM.
3. **Adapter selection:** Rust support requests high-performance preference, while the inspected TS probe uses the default adapter request. Define common requested preference/reporting and validate that support checks describe the adapter/device actually used; engine libraries may select devices internally. Do not claim a discrete GPU merely because preference was requested.
4. **Model readiness:** Existing model stores/probes and WebLLM cache checks are useful. Verify every required artifact is local: shards, tokenizer/config, model library WASM, application chunks, and worker scripts. A cached-weights flag alone must not cause offline `reload()` to attempt network repair.
5. **Workload safety:** Catalog currently marks only its Hermes WebLLM row tool-capable; several smaller rows are text-only. GPU preference cannot send ticket/audit/file tools to a text-only model. Preserve tool/schema capability and context checks, including strict pins and fallbacks.
6. **Worker/lifecycle:** `createPageEngineSet` supports a WebLLM worker URL, but inspected Web/Rovr/VSIX composition does not supply it. Package a shared worker entry and configure URLs per host. A worker alone does not survive closing its owning page. VSIX page-engine bridge depends on a connected webview; keep-alive execution ownership must be designed or the run must checkpoint/interrupt or choose another allowed local runtime.
7. **Resource ownership:** WebLLM and BFI maintain separate resident engines; Evermind can also allocate GPU memory. Add a narrow shared resource coordinator/lease with cancellation, bounded concurrent inference, model unload, and scheduling for embeddings/training. Keep engine-specific allocation logic in engines. Suspend learning before interactive inference under pressure.
8. **Failure policy:** Missing GPU/assets, device loss, OOM, corrupted cache, context overflow, host suspension, and abort need distinct results. Failover may occur before output/effects commit; do not replay emitted output or completed tool actions. No API fallback without explicit permission.
9. **Distribution:** Rebuild BFI WASM from its source repo and refresh recorded hashes/types through `scripts/vendor-bfi-web.mjs`. Validate packaged VSIX/Rovr/Web assets and CSP/worker startup. Pin model artifact versions/digests and reconcile source documentation that calls bfi-web published with the product's vendored distribution contract.

## Existing memory implementation

`builderforce-memory` should be the shared offline memory foundation. Its source already supplies:

- `MemoryStore`: IndexedDB facts, stable keys, lexical/hybrid semantic recall, import/export, optional TTL/cap, and weight save/load delegation.
- `EvermindCognition`: store-agnostic canonical subject keys, evidence-based augment/confirm/supersede/reject decisions, sanitized recall, and per-instance serialized commits.
- Local semantic/exact cache primitives. Remote `FetchSemanticCacheBackend` is an optional L2 adapter, not a prerequisite for local facts/recall.
- `MambaSession` / `SSMRuntime`: local session execution, local checkpoint buffers, tokenizer inputs, save/load and delta checkpoint support. URL inputs and transformer bridges introduce optional network dependencies.
- `memory-engine`: local SSM/WebGPU mechanics and CPU Evermind components. The MCP package includes a headless CPU text embedder loading a local `.evermind` package/tokenizer, so useful recall need not depend on WebGPU.
- `memory-mcp` local backend: a MemoryStore adapter with optional durable JSON mirroring, shared-file freshness checks, and lexical/semantic recall.

The **current product integration is more remote-dependent than the package**: VSIX `src/cognition.ts` routes fact recall/remember through `bfApi`; `brain-embedded/src/evermindMemory.ts` provides server-backed project hooks for recall, memory-first answers, and cache writes. Replace those infrastructure bindings with shared local-memory application services in every modality. Preserve the server adapter behind synchronization and explicit connected features.

## Memory gaps and work packages

| ID | Finding in inspected code | Required scope |
|---|---|---|
| M01 | Main `MemoryStore` directly owns IndexedDB and has no production Node database adapter seam. Its Node guidance uses injected `fake-indexeddb`. MCP adds durability only when `persistFile` is configured. | Preserve API compatibility while extracting narrow storage/transaction ports; provide durable browser and VSIX Node adapters. Reuse the MCP backend for interoperability where appropriate, but never treat an in-memory IDB shim as durable storage. |
| M02 | IndexedDB write helpers resolve on request success, without awaiting transaction completion/abort. Fact writes do not share a transaction with a sync journal. | Resolve durable save only after transaction commit; commit fact mutation, provenance, tombstone/event, and journal atomically. Define a unit-of-work port rather than adding an unrelated queue beside the store. |
| M03 | `MemoryEntry` is keyed by a string with content/time/tags/importance; identity fields for account/tenant/project/repository/chat and server versions are absent. Default database names are global to the storage origin. | Explicit scope values and physical/logical partitions, enforced by repositories, covering personal and never-connected memory. Tags and caller conventions are not authorization. Preserve scoped ownership in exported/imported snapshots and all cache keys. |
| M04 | Local facts can be overwritten/deleted, but the store has no account sync receipts, durable operation identity, entity base versions, conflict exchange, or deletion tombstones. | Integrate fact operations with the common sync protocol. Preserve evidence and base revision; use canonical cognition rules during reconciliation. Concurrent evidence conflicts remain explicit rather than unconditional last-write-wins. |
| M05 | Cognition mutex/version/cache are per instance; `_writeSeq` is process-local. They cannot serialize multiple tabs, extension windows, MCP processes, or remote replicas. Shared JSON freshness/rename does not provide a cross-process transaction. | Repository compare-and-set/transaction semantics, durable revisions, ownership/locking where needed, and cross-context invalidation. In-process serialization stays useful but cannot be the distributed consistency boundary. |
| M06 | Optional TTL/caps hard-delete facts. MCP default cap is 10,000; mirrored snapshot drops TTL/time/sequence and restores facts through fresh remember calls. | Separate evictable derived caches from durable user knowledge and unsynced operations. Preserve source time/provenance through import. Scope intentional retention/deletion and tombstones; never evict pending knowledge merely to meet a cache cap. |
| M07 | SemanticCache L1 is process memory; remote L2 can perform lookup/store on each use. MemoryStore dense vectors/index are reused in process, not a persisted cross-restart index in that implementation. | Persist scoped answer cache/index where valuable, with knowledge version and embedding/model/tokenizer version. Disable remote L2 offline; batch permitted shared contributions. Rebuild derived indexes safely when their version changes. |
| M08 | Sessions support local buffers but also fetch checkpoints/tokenizer URLs. InferenceRouter can choose a configured transformer bridge; bridges/L2 can reach remote services. | Offline asset resolver and explicit network capabilities for all memory paths. Local WebLLM/BFI bridge for allowed teacher/generation requests; disable remote teacher fallback, remote embeddings, and automatic downloads in disconnected mode. |
| M09 | Local learning/checkpoint primitives exist, including delta support; these are not account-wide concurrent model merge semantics. | Version base checkpoint, architecture, tokenizer, training configuration, and contribution IDs. Sync eligible experiences/examples/evidence and immutable checkpoint manifests. Reconcile/promote centrally under policy; never average weights or apply a delta to an incompatible base implicitly. |
| M10 | The memory package includes its own SSM/transformer router and graph/checkpoint facilities, while Brain already owns the active agent/tool loop and local inference planner. | Keep one application execution owner. Adapt memory hooks/bridges to the shared inference policy; reuse checkpoint primitives where useful without starting a competing agent loop or independent fallback policy. |
| M11 | Safe cached/SSM answers can avoid generation, but a recalled answer is not proof a current external action occurred. Existing Brain hooks explicitly restrict SSM generation on tool-capable runs. | Preserve that guard locally. Scope cache validity by current knowledge/input/tool semantics; never satisfy a requested mutation with a prior cached action result. Report recall/generation/learning capability and provenance honestly. |

These gaps do not mean the package lacks offline support. Local knowledge and lexical recall can operate without an account, teacher, or GPU. Semantic recall requires an available compatible embedder; SSM generation/adaptation additionally requires compatible installed assets and its supported execution backend. Validate those capabilities independently rather than one blanket “memory available” flag.

## Consolidated ownership and dependency direction

| Layer | Owner / changes |
|---|---|
| Domain | `builderforce-memory` owns memory/cognition/retrieval rules; `builderforce-inference` owns BFI model/backend mechanics; existing shared inference package owns pure eligibility/ranking. No host UI/HTTP dependencies in these rules. |
| Application | One shared local memory service composes recall, cognition commits, eligible cache answers, and learning jobs. The shared run service consumes it and the inference port. Journal creation participates in storage transactions; sync remains optional. |
| Infrastructure | Browser/Node stores, local model/embedding engines, WebLLM adapter, BFI WASM/native bridge, checkpoint/blob storage, and permission-guarded sync implement narrow ports. |
| Presentation | One localized settings/model/memory status contract rendered by Web/Rovr/VSIX. Components call use cases; they do not implement ranking, fact reconciliation, download policy, or network retry. |

Do not move tickets, execution history, or audit reports into `MemoryStore` merely because it is persistent. Their owning contexts retain authoritative structured records; memory indexes/retrieves permitted projections and facts. This is DDD separation with shared infrastructure, not duplicate storage rules. Likewise, do not move WebLLM into the Rust engine or reimplement a Rust model-fit formula independently in each UI. Engine-specific formats and estimates remain behind capability ports.

## Delivery and acceptance

1. Establish versioned capability, asset-readiness, inference-permission, memory-scope, and storage-transaction contracts. Add shared contract fixtures across TS/Rust boundaries; explicitly resolve GPU limit semantics.
2. Add the shared WebLLM-first automatic plan and hard offline permission enforcement. Wire packaged worker/assets and lifecycle/resource coordination across all three modalities.
3. Harden/extract memory persistence adapters, durable transaction completion, fact provenance/revisions/tombstones, and atomic journal integration. Preserve existing cognition/recall implementations behind the new storage ports.
4. Replace server-backed per-turn memory bindings with local services, and integrate facts/experiences/checkpoint manifests with common batch sync. Implement cache invalidation and model-version compatibility rules.
5. Validate each modality: downloaded compatible WebLLM model preferred with GPU; no GPU/no assets/unfit tools/device loss produce correct local alternatives or clear setup state; no attempted API calls. Explicit pins obey policy.
6. Validate offline memory: remember/recall/forget and local model restoration survive restart; lexical recall works without GPU; eligible CPU semantic recall works with installed assets; GPU memory competes safely with LLM generation; no network teacher/L2 leak.
7. Inject crashes/transaction aborts and concurrent writes across windows/MCP processes. Prove no acknowledged knowledge loss, cross-scope recall, resurrected deletes, duplicate learning, incompatible checkpoint application, or evicted unsynced facts. Product restart/network-denial tests supplement package unit tests.

Scope excludes a new inference engine, arbitrary WebLLM support for GGUF, automatic model downloads during chat, automatic model-weight merging, or a second agent orchestrator. Implementation requires changes in both source repositories and the product integrations; documentation alone does not establish capability or performance parity.
