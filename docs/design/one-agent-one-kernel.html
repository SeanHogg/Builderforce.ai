The executable plan is PRD 35: One agent, one kernel (docs/specs/35-prd-one-agent-one-kernel.md). It covers workstreams WS0–WS7, file ownership, the contract and the telemetry gates. This page is its design reference (docs/design/one-agent-one-kernel.html).

Agent Execution Duplication Map

Builderforce has four entry points: VS Code, Rovr, the on-prem agent, and Cloud/container. They are meant to be ways in, not separate engines. A turn should run the same way whichever door it came through. Today it doesn't. Underneath the four entry points there are six executions, and each one rebuilds the run policy for itself. This page sets out the end state first: one execution, with entry points that only supply ports. After that it shows today's duplication and the plan from here to there.

The rule

There is one execution. An entry point decides where a run gets its model, files, shell, storage and people. It never decides how the run behaves. If two entry points behave differently on the same task with the same model and the same files, that is a bug in the core, never a feature of an entry point.

Above the entry points, the cloud/web board and governance layer stays exactly as it is: autonomous execution from the board, and approvals by approver type. It is one owner. It decides whether and by whom a run starts and finishes, then dispatches into the one agent. What it requires of a run, such as a sign-off role or approval gates, reaches the agent as RunPolicy data. The agent then enforces it the same way on every entry point.

The contract

This is the whole surface an adapter sees. Everything that varies by entry point is a port or a policy value. A new entry point is one more adapter that fills these in.

// packages/agent-run
export function runAgent(input: {
  task: RunTask;          // prompt, ticket / chat ids, persona, attachments,
                          // dispatch: { source: "board-sweep" | "lane-entry" | "chat" | "manual" | "ceremony", approvalId? }
  policy: RunPolicy;      // DATA: what this run may do
  ports: RunPorts;        // WHERE it gets things
  resume?: RunState;      // a saved step, for step-at-a-time hosts
  maxSteps?: number;      // 1 on the cloud tick; unbounded elsewhere
}): Promise<RunOutcome>;  // finished | paused (question) | yielded (RunState) | failed

export interface RunPolicy {
  toolScope: ToolScope;   // e.g. "ticket" | "chat-reply" | "canvas" (replaces CHAT_SCOPED_AGENT_TOOLS)
  levers: CostLevers;     // A3, C5, C7, D1, D7, D8 ... on or off
  budgets: { steps?: number; tokens?: number };
  role: string;           // policy role: tier ladder, verify phase
  pinnedModel?: string;
  verify: "declared-checks" | "branch-ci" | "none";
  signoff?: { roleKey: string; laneKey?: string }; // finish blocked until this role signs off
  approvalGates: PolicyGate[];  // in-run acts that need an approver (block / ask)
}

export interface RunPorts {
  model: ModelTransport;          // complete(request): gateway, BYO, local inference
  capabilities: CapabilityProvider; // agent-tools contract: files, shell, git, platform, human
  store: RunStore;                // load / save RunState; commit long-term memory
  events: EventSink;              // turn, tool, steer, escalation, verify, finish
  human: HumanChannel;            // ask + approval; returns an answer or "paused"
  steering?: SteeringSource;      // drains user messages between steps
}

One run, any entry point

Every step is the same sequence. A Node, browser or editor host runs steps back to back. The cloud host runs one step per Durable Object tick and saves state in between. Both produce the same result, because RunState carries everything the policy needs: guard tallies, the cascade, the check note, the run brief, finish-gate counters and the model hand-off.

What exists, and what doesn't

Exists

  • packages/agent-run, the only execution
  • Four adapters, each under about 300 lines
  • One tool registry and one selector, scoped by RunPolicy.toolScope
  • One model policy; transports only carry the call
  • One memory model: the brief during the run, consolidation at the end
  • One sandbox implementation (sandboxCore) behind the cloud provider
  • One conformance suite and one import guard

Doesn't exist

  • The Claude Agent SDK runner, SDK_TOOLS, sdk-memory-server, the SDK Task
  • Run policy inside cloudAgentEngine, agentReplyLoop, brain-embedded runLoop, creationCanvasAi or agent-loop.ts
  • Any per-entry-point stall hook, steering queue, compaction wiring, ask tool or finish gate
  • CHAT_SCOPED_AGENT_TOOLS and other tool lists as code
  • A model decider per entry point
  • Container or Actions loops (removed in the current change)

Four entry points, six executions: the problem being removed

Everything a run actually decides sits around the kernel, in each execution's own code: when to compact, how to recover a stall, what steering does, whether a finish is allowed, which tools and model to use, and what to remember. Each execution owns its own copy of those decisions.

What this changes in the plan

  • VS Code is the reference behaviour. It carries about 99% of real execution, so its runs set the baseline the core must match: 4.4% failure, about 43 steps a run, 23% cache hit. The cloud engine has the most complete policy, but only 4 runs back it.
  • Policy comes from the cloud; behaviour is proven against VS Code. The core is assembled from the cloud engine's policy modules. Its conformance traces and its telemetry gates use VS Code runs.
  • Deleting the unused paths carries little traffic risk (container, Actions, @-reply, on-prem: zero runs). Their capabilities are still retained, per the ledger above, because no loss of function is allowed.
  • VS Code migrates behind a comparison. Moving it onto the core is the highest-risk phase, so it ships only when its telemetry stays at or better than the baseline.

Telemetry gaps the core closes

  • run_model_outcomes for VS Code has no tool_calls or tool_errors. Only cloud rows carry them.
  • turn_index and tool_schema_tokens are null on every row, so turn depth and tool-catalog cost can't be measured.
  • usage_snapshots has no rows in 30 days, so compaction is unrecorded everywhere except the memory.trimmedTokens metadata.
  • No row names its entry point: canvas, Rovr and @-reply are indistinguishable from web.
  • The core's EventSink writes one outcome row per run on every entry point, with the entry point, steps, tool calls, tool errors, compactions and verify result. That uniform row is what the comparison gates read.

Two other findings, not specific to one execution. First, 19,608 auto_run_skipped and 282 auto_run_error events from the autonomous trigger. Second, model failovers of 2,093 for 401, 288 for 403 and 329 for 429, which is the noise the one model policy has to absorb.

Plan

Getting from six to one

  1. Parity oracle. Collect each execution's existing behaviour tests. They run unchanged against the core at every step; a failure means the core is missing something, and the fix goes into the core.
  2. Build packages/agent-run from cloudAgentEngine. It has the most complete policy. The extraction is a Worker-safe package with the five ports. cloudAgentEngine becomes the cloud adapter: DO cursor, git API, sandbox and timeline.
  3. @-replies. agentReplyLoop moves onto the core in the same process. Its chat scope becomes data passed to tool selection.
  4. VS Code, Rovr and Web. brain-embedded runLoop moves onto the core. Its local-first routing becomes the model transport. The canvas becomes a capability provider on the same run, not a separate composition.
  5. On-prem. Channels and tickets both run on the core, with node fs and shell as the capability provider. The Claude Agent SDK runner and its tool list, memory server and Task sub-agent are deleted.

Each phase follows the same rule: port what's missing into the core, run the unchanged tests, then delete the old execution. Nothing runs in parallel with it.

Proof of parity

How each merge is verified

The existing behaviour tests are the parity check. They run unchanged against the merged code. A test's import may move from a deleted module to its replacement, but its inputs and expected outputs stay the same. When one fails, the behaviour drifted and the source gets fixed. Every capability moves under the same five steps (PRD 35 §5.1):

  1. Baseline on the old home. Run the capability's tests against today's code and record that they pass. A test that isn't green there is no oracle.
  2. No test? Write one first, against the old home. A characterization test pins today's behaviour (inputs, tool calls, events, outcome). It lands before any porting commit and is then frozen like every other test.
  3. Port, then run the same tests on the new home. Same files, same assertions. The only allowed edit is an import path.
  4. Run them through every entry point that has the capability. One conformance case per shared capability gives the same event trace and outcome on each adapter, and on the cloud at one step per tick.
  5. Delete the old home only after 3 and 4 are green, in the same workstream.

Not allowed in a test file: changing an input, fixture or expected value; deleting or merging tests; .skip, .only, .todo; loosening a matcher (toEqual → toMatchObject, exact → stringContaining); mocking out the behaviour under test. A test that reached into a deleted module's internals moves to the public seam that carries the same behaviour, with the same inputs and expected values. Enforced three ways: the reviewer rejects any non-import hunk in a test diff, the verify agent reports per-file test counts before and after, and check:tests-unchanged fails CI on any changed non-import line or new skip marker.

In the current change, about fifteen test files had their expectations rewritten. Those rewrites are being reverted so the original assertions run against the engine.
