# PRD: Close SOC 2 readiness gaps for CODEOWNERS, SECURITY.md, and control-count copy

Child of Epic 3062. Repository `seanhogg/builderforce.ai`, base branch `main`.

## Problem & Goal

`soc2Scan()` grades CC1 on the presence of CODEOWNERS and the current workspace has no CODEOWNERS file in any GitHub-recognized location. A nested security doc exists at `agent-runtime/docs/SECURITY.md`, and `Builderforce.ai/CONTRIBUTING.md` exists, but there is no repository-root `SECURITY.md`. Our own readiness scan therefore fails CC1 and CC2.

Separately, the English marketing FAQ (`en.json`, near line 28386) says the tracker seeds a 30-control CC1–CC9 baseline. `SOC2_BASELINE` in `governanceRoutes.ts` has 28 rows and does not include CC6.4, CC6.5, CC6.8, or CC8.2. The public claim and the seed disagree.

Goal: make the in-repo readiness artifacts that CC1 and CC2 grade actually present at the repo root, and make the FAQ control count identical to the seeded baseline, without expanding the control catalog in this change.

## Target users / ICP roles

- Maintainers of `seanhogg/builderforce.ai` who need a default review owner for changes on `main`.
- Compliance and security operators who run `soc2Scan()` and report CC1/CC2 readiness.
- Buyers and evaluators who read the English marketing FAQ and must not be told the tracker seeds controls it does not seed.
- Downstream implementation agents on Epic 3062, who share this PRD and must not fork the 28-vs-30 decision.

## Scope

In scope, on `main` of `seanhogg/builderforce.ai`:

- Add a non-empty `CODEOWNERS` file at the repository root so the existing CC1 check can see it.
- Add a repository-root `SECURITY.md` so the existing CC2 check can see it. The nested `agent-runtime/docs/SECURITY.md` does not satisfy this.
- Change the English FAQ claim of a 30-control baseline to 28, matching `SOC2_BASELINE`.
- Leave the 28-row seed unchanged.

## Functional requirements

1. Create `/CODEOWNERS` at the repo root, not only under `Builderforce.ai/`, `agent-runtime/`, or `docs/`.
2. The file must be valid GitHub CODEOWNERS syntax and must include a default `*` rule so ownership is not limited to one subtree.
3. Owner entries must be GitHub users or teams already associated with this repository. Do not invent accounts, team slugs, or email addresses. If no real owner can be read from the repo, stop and report that blocker rather than writing a placeholder owner.
4. Do not treat `Builderforce.ai/CONTRIBUTING.md` or the root `CONTRIBUTING.md` as a substitute for CODEOWNERS.
5. Create `/SECURITY.md` at the repo root. An organization-level policy outside this repo, and `agent-runtime/docs/SECURITY.md` alone, do not meet this requirement.
6. Root `SECURITY.md` must be a usable security policy: what to report, how to report it, and that GitHub private vulnerability reporting on this repository is an accepted channel. Reuse any real contact already published in `agent-runtime/docs/SECURITY.md`. Do not invent an email, URL, or PGP key. The root file may point at the nested doc for runtime-specific detail, but it must stand alone for disclosure instructions.
7. Do not change `soc2Scan()` in this change. Placement at the repo root is what the current grader must be able to find.
8. In the English FAQ string near `en.json` line 28386, replace the 30-control claim with 28 controls. The sentence must still describe a CC1–CC9 baseline only if that remains accurate for the 28 seeded rows; it must not imply that CC6.4, CC6.5, CC6.8, or CC8.2 are seeded.
9. If the same 30-control claim appears elsewhere in that English FAQ file, update those occurrences in the same change. Do not edit `SOC2_BASELINE` row count, IDs, or order.
10. Search other locale files only to find the same 30-control sentence. If an identical claim exists, update the count to 28 in the same change. Do not add new locales or rewrite unrelated FAQ copy.

## Acceptance criteria

- A glob of the workspace finds a repo-root `CODEOWNERS` file, and that file contains a default `*` ownership rule with at least one real existing owner.
- A repo-root `SECURITY.md` exists and states a non-fabricated reporting path, including GitHub private vulnerability reporting for this repository.
- `soc2Scan()` no longer fails CC1 for a missing CODEOWNERS file or CC2 for a missing root security policy, with no change to the scanner required for these two files to count.
- `SOC2_BASELINE` still has exactly 28 rows and still omits CC6.4, CC6.5, CC6.8, and CC8.2.
- The English FAQ no longer claims a 30-control seed. The number it states is 28, matching the seed.
- No new control IDs are introduced in copy, seed data, or docs as part of this change.

## Out of scope

- Adding CC6.4, CC6.5, CC6.8, CC8.2, or any other control to `SOC2_BASELINE`. A later epic may add them only if the FAQ is updated in that same change so the counts still match.
- Changing `soc2Scan()` grading rules, weights, or control IDs.
- Rewriting `agent-runtime/docs/SECURITY.md`, either CONTRIBUTING file, or the rest of the marketing site.
- Org-level GitHub security policy outside this repository, branch protection, rulesets, or actual access changes for the owners named in CODEOWNERS.
- Evidence collection, auditor packages, or implementing the SOC 2 controls themselves.
- Translating FAQ content beyond the control-count sentence, or creating a root security program that replaces product security documentation.
