# PRD: Host-relay delivery of connection credentials

## Problem & Goal

The capability row `connection → browser yes('vault')` claims that a browser worker can use a vault-backed Connected Account. That claim is a false capability. The row must stay; it is not retired this pass.

Injecting vault secrets into process environment is forbidden. That would make the secrets stealable and still unusable, because process egress must not be widened.

The end state, only if a revised contract is re-reviewed and accepts it, is delivery in the same shape as the ai relay: the worker receives a localhost base URL, and the host attaches the vault secret on the way out. Until that contract exists, `connection → browser yes('vault')` remains an acknowledged false yes and this ticket stays open. No substitute delivery is allowed in the meantime.

## Target users / ICP roles

- Host and runtime engineers who would own a future connection relay and its egress attach path
- Security reviewers who must re-review the revised contract before any delivery is accepted
- Agent and browser-worker authors who may only consume a connection through that relay, never through in-process secrets
- Downstream agents that share this PRD as the contract for the task

## Scope

This pass records the false capability, the forbidden paths, and the only acceptable future delivery shape. It does not build the relay.

- Keep `connection → browser yes('vault')`. Do not retire or relabel the row.
- State that the row is an acknowledged false yes until a host relay exists.
- Block implementation on a revised, re-reviewed contract that explicitly accepts relay delivery.
- Specify that accepted delivery is a localhost base URL whose host attaches the vault secret on egress, same shape as the ai relay.
- Require the vault's real Connected Account shape. Do not invent `CONNECTION_<ID>_*` field names.
- Give nothing to a service that does not use the connection.
- Keep the secret out of the worker script, the manifest, and the workspace tree.

## Functional requirements

1. Capability row. `connection → browser yes('vault')` remains. This contract calls it an acknowledged false capability. It is not removed, hidden, or marked true.
2. Contract gate. Delivery is not implemented in this pass. Work stays blocked until a revised contract is re-reviewed and accepts relay delivery. This ticket stays open until that relay exists.
3. No env injection. Vault secrets are not placed in process environment. Process egress is not widened so a worker could carry the secret itself.
4. Future delivery shape. If and only if the revised contract accepts delivery, the worker is given a localhost base URL. The host, not the worker, attaches the vault secret on the way out. The attach shape matches the ai relay. No other delivery shape is in contract.
5. Connected Account shape. Any future attach uses the vault's existing Connected Account fields only. No `CONNECTION_<ID>_*` names and no parallel secret schema are introduced.
6. Unused connections. A service that does not use the connection receives no base URL and no secret attach.
7. Non-persistence. The secret is never written into the worker script, the manifest, or the workspace tree. It is not checked in, echoed into logs as a stored artifact, or copied into the workspace as a stand-in for the relay.
8. No papering over. If the relay does not exist, callers do not receive env vars, files, or inlined secrets instead. The false yes stays acknowledged.

## Acceptance criteria

- The row `connection → browser yes('vault')` is still present and is explicitly an acknowledged false capability, not a retired row and not a true yes.
- The contract states that this ticket remains open until the host relay exists and a revised contract has been re-reviewed and accepts delivery.
- Process-env injection of vault secrets is forbidden, and widening process egress is forbidden.
- The only delivery mechanism named is a localhost base URL with host-side secret attach, same shape as the ai relay, and only after contract acceptance.
- The contract does not invent `CONNECTION_<ID>_*` field names and refers only to the vault's real Connected Account shape.
- A service that does not use the connection is specified to receive nothing.
- The secret is specified as never written into the worker script, the manifest, or the workspace tree.
- This pass does not treat the relay as built and does not authorize implementation before re-review.

## Out of scope

- Retiring, hiding, or flipping `connection → browser yes('vault')` to a true capability
- Implementing the host relay in this pass
- Injecting vault secrets into process environment or widening process egress
- Writing the secret into the worker script, the manifest, or the workspace tree
- Inventing connection field names or a new secret schema
- Issuing a base URL or secret attach to a service that does not use the connection
- Changing the ai relay except as the shape reference for a future connection relay
- Any delivery path other than the host-attached localhost base URL, once a re-reviewed contract accepts it
