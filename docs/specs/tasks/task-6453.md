# PRD: Bounded-parallel knowledge judgement

## Problem & Goal

Knowledge review judges extracted sections and near-duplicate claim pairs one model call at a time. In `builderforce-memory/packages/memory/src/knowledge/judge.ts`, `judgeSections` (around line 193) and `compareClaims` (around line 270) each `await` inside a serial `for` loop. Model calls are the slow phase of a review; on large workspaces that serial wait dominates wall-clock time. The user asked for parallel execution.

Goal: run those two loops through a bounded worker pool so judgement overlaps up to a fixed concurrency, without changing what is judged, how the budget is counted, how abort works, or the resulting claims.

## Target users / ICP roles

- BuilderForce for VS Code users who run Knowledge review on large workspaces and currently wait on serial judgement.
- Implementers of `builderforce-memory` only. This change does not target API, extension, or review-runner owners.

## Scope

- Add an exported concurrency constant and a small index-pulling worker pool in `builderforce-memory/packages/memory/src/knowledge/judge.ts`.
- Rewrite the `judgeSections` section loop and the `compareClaims` pair loop to use that pool.
- Extend the existing judge test file under `builderforce-memory/packages/memory/src/knowledge` (glob `*judge*test*`) with concurrency and budget cases.
- Leave validation, clamping, batch types, budget fields, and `judgementWithTimeout` untouched.

## Functional requirements

1. Export `JUDGE_CONCURRENCY = 6`.
2. Add a helper `runPool<T>(items, concurrency, worker)` that starts `concurrency` workers. Each worker pulls the next index until the list is exhausted. No other scheduling model.
3. `judgeSections` pools over `a.sections`. Each worker, with no `await` between the budget check and the usage increment:
   1. If `a.signal?.aborted`, throw the signal reason, same as today. Do not schedule further work after abort.
   2. If `budgetLeft(a.budget)` is false, increment `a.batch.unjudged` by 1 and skip that section.
   3. Call `call(...)`. It increments `b.used` synchronously before its first await. That synchronous check-then-increment is what keeps the model-call budget from overshooting under concurrency. JavaScript is single-threaded between awaits; do not insert an await between the check and `call`.
   4. If `answer` is missing, increment `unjudged` by 1 and continue.
   5. On success, run the existing validation plus fact, relation, and claims assembly verbatim.
4. All `batch`, `entities`, and `onJudged` mutations stay synchronous, so they remain race-free. Do not introduce locks or shared mutable updates after an await.
5. Apply the same pool to `compareClaims`. The per-run seen-set dedup must run synchronously before a call is scheduled. Keep the existing skip and abort semantics. Workers must not double-schedule a pair that the seen-set already records.
6. Preserve exact counting semantics for `judged`, `unjudged`, and `invalid`, and the existing abort behavior.
7. Claims array contents must be identical to serial execution. Order may differ. The consumer (`review.ts` `newClaims`) is order-insensitive and is not modified.
8. Aside from completion order, behavior stays deterministic.
9. Do not change `JudgedBatch`, `validateExtract`, `validateCompare`, `clampQuote`, `clampClaim`, the budget fields, or `judgementWithTimeout` (that wrapper lives in another repo and already composes with this pool).

## Acceptance criteria

- A fake `JudgementPort` increments an in-flight counter on entry, decrements it on return, and records the max.
- With 10 sections, every section is judged, `batch.judged === 10`, and max in-flight is `<= JUDGE_CONCURRENCY`.
- With 12 sections, all 12 are judged and max in-flight is `<= JUDGE_CONCURRENCY`.
- Budget: `modelCalls = 3` produces exactly 3 port calls, not more.
- `compareClaims`: 8 pairs are all compared, with max in-flight `<= JUDGE_CONCURRENCY`, and seen-set dedup still suppresses duplicate pairs.
- Abort still throws the signal reason and stops scheduling new work.
- Existing judge tests pass. Vitest for `packages/memory` passes. Typecheck is clean.
- Claim contents match a serial run of the same inputs; only order may differ.

## Out of scope

- Any edit under the API repo, including upload validation, `putExtracted`, route responses, or `skippedRefs`.
- Capping or truncating `src:` file refs. Path parsing (`pathOfRef`, `fileRefOf`, `sourcePathOf`) must keep working; long file paths are not fixed here.
- Bounding section-slug length in `docsExtract`.
- The per-file loop in `review.ts`. It stays serial.
- `judgementWithTimeout` and anything in the review-runner repo.
- Reordering guarantees, new batch fields, or changes to validation and clamp helpers.
- Parallelism anywhere except `judgeSections` and `compareClaims`.
