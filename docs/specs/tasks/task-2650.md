# Product Requirements Document (PRD)

## Problem & Goal

### Problem
The `tasks.create` API fails with a `tasks_assigned_user_id_fkey` violation when no assignee (`assignedUserId`, `assignedAgentRef`, or `assignedAgentHostId`) is provided. This issue arises because the system attempts to assign a default user that does not exist in the `users` table, violating the foreign key constraint.

### Goal
Ensure that the `tasks.create` API successfully creates a task without assigning a user when no assignee is provided, even if the project's default assignee is not set.

## Target Users / ICP Roles
- **Developers**: Users who interact with the `tasks.create` API to create tasks programmatically.
- **Project Managers**: Users who manage projects and may or may not set default assignees.

## Scope

### In Scope
- Modify the `tasks.create` API to handle cases where no assignee is provided.
- Resolve the default assignee before inserting a new task.
- Insert `NULL` for the `assignedUserId` if the default assignee does not exist.
- Add regression tests to ensure the fix works as expected.

### Out of Scope
- Changing the behavior of the `tasks.create` API when an assignee is provided.
- Modifying the logic for assigning default users in other parts of the system.
- Handling cases where the default assignee is set to a non-existent user in projects other than the one specified.

## Functional Requirements

1. **Default Assignee Resolution**
   - Before inserting a new task, the system must resolve the default assignee based on the project's `managerRef` and `managerKind`.
   - If the default assignee does not exist in the `users` table, the system must set the `assignedUserId` to `NULL` instead of inserting a dangling ID.

2. **API Behavior**
   - The `tasks.create` API must succeed when no assignee is provided, even if the project's default assignee is not set.
   - The API must not throw a foreign key constraint violation when no assignee is provided.

3. **Error Handling**
   - The API must handle cases where the default assignee is set to a non-existent user gracefully, without exposing raw Postgres errors to the caller.

## Acceptance Criteria

1. **Successful Task Creation**
   - When calling `tasks.create` on a project with `managerRef=null` and no assignee is provided, the task must be created successfully.
   - The `assignedUserId` field in the newly created task must be set to `NULL`.

2. **No Foreign Key Violation**
   - The `tasks.create` API must not throw a `tasks_assigned_user_id_fkey` foreign key constraint violation when no assignee is provided.
   - The API must return a success response with the created task details.

3. **Regression Test**
   - A regression test must be added to ensure that `tasks.create` with no assignee on a project whose `managerRef` is `null` succeeds and leaves `assignedUserId` as `NULL`.

## Out of Scope

- **Other Projects**: The fix is specifically for projects with `managerRef=null`. Projects with a valid `managerRef` will continue to assign the default user as before.
- **Other APIs**: This change is limited to the `tasks.create` API and does not affect other APIs or parts of the system.
- **User Interface**: The user interface for creating tasks is not affected by this change.
- **Default Assignee Logic**: The logic for assigning default users in other contexts remains unchanged.

### R-1 — Resolve default assignee before INSERT

The `tasks.create` handler MUST resolve the default assignee _before_ inserting the row into the `tasks` table. The resolution is:

1. If the caller provided `assignedUserId`, `assignedAgentRef`, or `assignedAgentHostId` — use it directly (existing behaviour; no change).
2. Otherwise, call `getEffectiveManagerPolicy(db, tenantId, projectId, env)` to obtain the project's `managerRef` and `managerKind`.
3. Pass `managerRef` + `managerKind` through `resolveManagerAssignee()` (the same function already used by the coordinator/autonomy machinery).
4. If `resolveManagerAssignee()` returns an `assignedUserId` that does NOT exist in `users`, treat it as NULL.
5. If the entire resolution yields no valid assignee, set `assignedUserId = NULL`.

**Rationale:** `resolveManagerAssignee` converts a manager-ref designation (`u:123`, `c:abc`, `h:xyz`) into the three assignee columns. When `managerRef` is NULL (as it is on project 11), the function should return no valid user id, and the handler must not propagate a dangling sentinel into the INSERT — doing so currently causes the FK violation.

### R-2 — `managerRef = null` → `assignedUserId = NULL`

When a project's effective `managerRef` is NULL and no explicit assignee was passed, `tasks.create` MUST set `assignedUserId` to `NULL` on the inserted row. The task MUST be created successfully — no error, no FK violation, no raw Postgres message surfaced to the caller.

### R-3 — `managerKind = 'system'` fallback

When `managerKind` is `'system'` and `managerRef` is NULL, the resolution chain MUST NOT attempt to resolve an explicit user or agent. The `resolveManagerAssignee` result for a null/system manager is already `SYSTEM_MANAGER_IDENTITY` — the tasks.create handler must recognise this as "no assignee" and insert NULL rather than trying to map it to a `users` row.

### R-4 — No FK violation surfaces to the API caller

The `tasks.create` API MUST NOT throw a `tasks_assigned_user_id_fkey` foreign-key violation under any combination of null/missing assignee fields and null `managerRef`. If the resolution chain produces a non-existent user ID, the handler MUST catch or avoid it rather than propagating it to the INSERT. The error response, if any, must be a structured API error (e.g. 400/422 with a message), never a raw Postgres exception.

### R-5 — Existing explicit-assignee paths unchanged

When the caller provides ANY of `assignedUserId`, `assignedAgentRef`, or `assignedAgentHostId`, the handler MUST NOT alter that value or re-resolve the default. The explicit assignee is inserted as-is (the same behaviour as today), including its FK validation — an explicitly passed non-existent user ID SHOULD still fail with a clear validation error (not a raw FK exception, but that is a separate concern).

### R-6 — Regression test

Add an automated regression test that:

1. Calls `tasks.create` on a project whose `project_manager_configs.managerRef` IS NULL and whose `managerKind` is `'system'`, WITHOUT passing `assignedUserId` / `assignedAgentRef` / `assignedAgentHostId`.
2. Asserts the API returns success (HTTP 200/201).
3. Asserts the created task row has `assignedUserId = NULL`, `assignedAgentRef = NULL`, and `assignedAgentHostId = NULL`.
4. Asserts no FK violation is raised.

### Dependencies & constraints

- `resolveManagerAssignee()` is already defined in `api/src/application/manager/` and is already unit-tested.
- The `users` table FK is `tasks(id) → users(id)` via column `assigned_user_id`.
- The `project_manager_configs` table stores `managerRef` (nullable TEXT) and `managerKind` (TEXT, default `'system'`).
- This change is confined to the `tasks.create` write path. The read path (`tasks.get`, `tasks.list`) is unaffected.
- The `tasks.update` path is out of scope for this PR but may benefit from the same resolution logic in a follow-up.
