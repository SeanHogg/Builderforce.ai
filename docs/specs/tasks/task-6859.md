# W6 PRD: Migrate Admin Panels, Retire Legacy Modules, Empty Guard Allowlists

## Problem & Goal

Waves W2–W5 put the shared `Card|List` `<Collection>` surface, `Page<T>` contract, bulk Delete/Archive/Merge ports, and collection guards in place everywhere except the admin and remaining ops surfaces. Those surfaces still use local tables, `useTableSort` / `SortableTh`, `dataTableStyles`, duplicate select/bulk i18n, and guard allowlist exceptions.

W6 is the last wave of PRD 47. It moves every remaining admin and ops collection onto `<Collection>`, registers the remaining superadmin bulk ports, deletes legacy sort/table modules only after they have zero references, and leaves the collection and bulk-fanout guards at their final allowlist state.

Done means an operator gets one interaction model on every listed surface: selection, select-all, server-side bulk in one request where the entity supports it, paging at 50/100/250, fixed header and footer with only rows or cards scrolling, and column sort via the shared sort hook. Engineering can delete the legacy modules and ship with empty temporary allowlists.

## Target users / ICP roles

- Superadmin operators who deactivate users, archive tenant status, and bulk-revoke suspect accounts.
- Admin, support, security, billing, and sales operators who page, sort, select, and act on the panels listed in Scope.
- Frontend and API engineers closing PRD 47, plus reviewers who must see each §9 done-check reported on its own.

## Scope

Depends on W2–W5 (PRD 47 §5 W6, §6 retirements, §7 guards, §9 done-checks). Read `Builderforce.ai/docs/specs/47-prd-collection-view.md` before implementation. Do not start this wave until those waves are merged.

- Any remaining `ViewToggle` card/table flag usage outside `<Collection>`

`ViewToggle` itself stays for options-mode pickers. Insights lenses keep a local style module if they still need those rules after the global table CSS is removed.

## Functional requirements

1. Each listed surface renders through the shared `<Collection>` component in card or list mode. No local table, card grid, or one-off selection chrome remains on those surfaces.
2. Selection is checkbox-based, includes select-all for the loaded page, and uses the shared collection selection model. Duplicate select-all copy is not reintroduced.
3. Where the entity supports Delete, Archive, or Merge, bulk execution is one server request carrying ids and tenant. The client must not fan out one request per id.
4. Suspect-account bulk revoke calls the admin `suspectAccount` port. User deactivate and tenant status-archive are superadmin ports, registered and used by the surfaces that own those actions.
5. Paging uses `Page<T>` with page sizes 50, 100, and 250. Header and footer stay fixed; only rows or cards scroll. `AuditLogPanel` adopts the existing server page into `Page<T>` rather than adding a parallel pager.
6. Column sorting goes through shared `useCollectionSort`, including `visitors/LeadsView`. Admin code no longer imports `useTableSort` or `SortableTh`.
7. After admin migrations, grep shows zero references, then delete `useTableSort` / `SortableTh`, `dataTableStyles.ts`, and the named global table CSS rules. If an insights lens still needs those styles, move them into a local style module. Do not leave the global rules in place for that case.
8. Remove duplicate `sessionManagement.bulk*`, `observability.selectAll`, and security select i18n keys. Remaining collection strings stay in parity across en, zh, es, fr, and de.
9. `check:collection-surfaces` allowlist contains only the §2 permanent exclusions, each with a reason. `check:bulk-fanout` allowlist is empty. Design-token, design-scale, and raw-storage guards are green with no new exceptions.
10. Add a `release_notes` row with category `new` stating that bulk Delete/Archive/Merge and paging are available on collection surfaces, and publish the accompanying blog post required by the marketing rule.

## Acceptance criteria

1. Every surface named in Scope is on `<Collection>` plus `Page<T>`. `AuditLogPanel` reuses its existing server paging in that shape. `LeadsView` sorts only through `useCollectionSort`.
2. Bulk Delete, Archive, and Merge, and the three named admin actions, each run as one ids-plus-tenant request through a registered port. No per-id fan-out remains. Read-only panels have no new destructive actions.
3. User deactivate, tenant status-archive, and suspectAccount revoke are registered superadmin ports. SuspectAccountsPanel bulk revoke uses the suspectAccount port.
4. Zero-reference grep precedes each deletion. `useTableSort`, `SortableTh`, `dataTableStyles.ts`, and the named `globals.css` table rules are gone. Insights lenses that still need those styles use a local module. `ViewToggle` remains only for options-mode pickers.
5. Duplicate sessionManagement bulk, observability selectAll, and security select i18n keys are gone. en, zh, es, fr, and de are in parity for the strings these surfaces use.
6. `check:collection-surfaces` allowlist is only §2 permanent exclusions, each with a reason. `check:bulk-fanout` allowlist is empty. Design-token, design-scale, and raw-storage guards pass.
7. PRD §9 done-checks 1 through 7 are run and reported individually, not as a single aggregate. Full frontend and API type-check, lint, and test suites pass. The `release_notes` row (category `new`) and the required blog post are present.

## Out of scope

- Re-implementing `<Collection>`, `Page<T>`, or bulk contracts delivered in W2–W5.
- Changing §2 permanent exclusions, or deleting `ViewToggle` itself.
- Adding Delete, Archive, or Merge to read-only health, metrics, cron, error, or audit surfaces that do not already have those actions.
- New admin roles, permission models, or non-superadmin access to user deactivate, tenant status-archive, or suspectAccount revoke.
- Redesign of admin information architecture, sales workflow rules, or billing business logic beyond adopting the shared collection surface.
- Editing unrelated product surfaces that are already on `<Collection>` and already off the temporary allowlists.
