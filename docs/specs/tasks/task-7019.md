# PRD: Route `no_changes` runs through the shared post-run lifecycle

## Problem & Goal

A cloud run that finishes with outcome `no_changes` skips all post-run bookkeeping. `CloudRunnerDO` (around L395) calls `runtimeService.update(id, { status: landedRunStatus({ ok: true, noChanges: true }) /* ExecutionStatus.NO_CHANGES */, result, telemetry? })`. `RuntimeService.update` (`api/src/application/runtime/RuntimeService.ts`, around L462) switches only on `RUNNING`, `COMPLETED`, and `FAILED`. The default throws `ForbiddenError`. `CloudRunnerDO` swallows that as a warning, so the lane move, metrics, next-lane trigger, audit, and telemetry counts never happen.

`NO_CHANGES` is already a terminal status (`TERMINAL_EXECUTION_STATUSES`) but has no domain transition and is not treated as a landed completion inside the shared fan-out.

Goal: land `NO_CHANGES` through the same persist-and-fan-out path as `COMPLETED`, with an explicit all-zero `RunTally` when telemetry is absent, without copying post-run logic and without changing `COMPLETED` or `FAILED` behaviour.

## Target users / ICP roles

- Ticket owners and lane operators who expect a successful no-diff cloud run to advance the ticket and unblock the next lane.
- Metrics, audit, and telemetry consumers who need a terminal run recorded with explicit zero counts rather than a swallowed failure and null or omitted tallies.
- Runtime and execution engineers who must keep one shared landed lifecycle (`applyLandedLifecycle`) so container, cloud, and Actions finalize paths cannot drift.

## Scope

In-repo work is limited to `Builderforce.ai` (repo `seanhogg/builderforce.ai`, base `main`). Touch only what this fix requires under `Builderforce.ai/api/src`:

- `api/src/domain/execution/Execution.ts`
- `api/src/application/runtime/RuntimeService.ts`
- `api/src/application/runtime/executionLandedEffects.ts`
- `api/src/application/runtime/executionLanding.ts` (read `persistTransition` and `RunTally`; change only if that is the chosen single place for zero tallies)
- `api/src/application/runtime/noChangesLifecycle.test.ts` (new) and/or `api/src/application/runtime/executionLandedEffects.test.ts`
- Any other `api/src` writer found by the grep below that lands `NO_CHANGES` while bypassing `RuntimeService.update`, and only enough to route it through the shared path

Verification is the targeted vitest files plus the `api` `type-check` script only.

## Functional requirements

1. **Domain transition.** In `Execution.ts`, add `markNoChanges(result: string)` mirroring `markCompleted`: call `assertNotTerminal('complete')`, then transition to `ExecutionStatus.NO_CHANGES` with `result` and `completedAt`. Do not add `NO_CHANGES` to `TERMINAL_EXECUTION_STATUSES`; it is already there.

2. **Shared landed outcome.** In `executionLandedEffects.ts`, extend `LandedOutcome['status']` to include `ExecutionStatus.NO_CHANGES`. Inside `applyLandedLifecycle`, treat `NO_CHANGES` exactly like `COMPLETED` for: terminal flag, managed-callback `'completed'` mapping, lane advance block, `onRunFinalized` `'completed'`, next-lane `onLaneEntry` trigger, milestone phase `'completed'`, and `movedTicket`. Normalize once (for example `const completed = outcome.status === ExecutionStatus.COMPLETED || outcome.status === ExecutionStatus.NO_CHANGES`) and use that flag. Do not duplicate those blocks.

3. **Audit.** In `recordLandedAudit`, check `AuditEventType` for a dedicated no-changes event. If one exists, use it. If none exists, audit `NO_CHANGES` as `EXECUTION_COMPLETED` with metadata `noChanges: true`.

4. **Single update path.** In `RuntimeService.update()`, add `case ExecutionStatus.NO_CHANGES` that calls `execution.markNoChanges(dto.result ?? '')`. That case must then flow through the same `persistTransition`, `applyLandedLifecycle`, `stampProducedFromLaneMove`, and `recordLandedAudit` code as `COMPLETED`. Extend the `COMPLETED`-only `stampProducedFromLaneMove` condition to include `NO_CHANGES`. No copied fan-out.

5. **Explicit zero counts.** Read `persistTransition` in `executionLanding.ts` and the `RunTally` type it persists. When the landed status is `NO_CHANGES` and `dto.telemetry` is absent, persist an explicit all-zero `RunTally`: every numeric field set to `0`, never `null` and never omitted. Do this inside `persistTransition` or at the single `update()` call site so every `no_changes` writer gets it. If telemetry is present, persist that telemetry; do not overwrite a provided tally with zeros.

6. **Other writers.** Grep `api/src` for direct landings (`.land(` and `ExecutionStatus.NO_CHANGES`), including any container or GitHub Actions finalize op. If a writer bypasses `RuntimeService.update`, route it through that shared path, or apply the same zero-count plus fan-out treatment by calling `applyLandedLifecycle`. Never add a second copy of post-run logic.

7. **Regression test.** Add `api/src/application/runtime/noChangesLifecycle.test.ts`, or extend `executionLandedEffects.test.ts` using its existing fake-deps harness, in the file’s existing vitest style. Assert that `update()` with status `NO_CHANGES`:
   - lands the row terminal with the given result
   - advances the ticket lane (`tasks.update` called with the next lane)
   - calls `ports.onTaskStatusSync` (metrics) with `terminal: true`
   - fires `ports.onLaneEntry` for the next lane
   - writes an audit event
   - persists explicit zero telemetry counts, not null
   Also assert a `COMPLETED` run’s behaviour is unchanged.

## Acceptance criteria

- A `NO_CHANGES` update no longer throws `ForbiddenError` and is not swallowed as a warning that skips bookkeeping.
- The execution row is terminal `NO_CHANGES` with `result` and `completedAt`.
- Lane move, metrics sync (`terminal: true`), next-lane `onLaneEntry`, milestone `'completed'`, managed-callback `'completed'`, `onRunFinalized` `'completed'`, and audit all run via `applyLandedLifecycle` / `recordLandedAudit`.
- Absent telemetry on a `NO_CHANGES` landing is stored as an all-zero `RunTally`, not null and not omitted.
- `COMPLETED` and `FAILED` update behaviour is unchanged, including existing `executionLandedEffects` and `mk09DispatchGuards` coverage.
- `npx vitest run src/application/runtime/noChangesLifecycle.test.ts src/application/runtime/executionLandedEffects.test.ts src/application/runtime/mk09DispatchGuards.test.ts` from `Builderforce.ai/api` passes, plus any existing `RuntimeService` test file if one is present.
- `package.json` script `type-check` in `Builderforce.ai/api` passes. Failures in those targeted checks are fixed. The full test suite is not run.
- Commit only the files changed for this fix with `git_commit` (`repo=Builderforce.ai`, `allowBaseBranch: true`, explicit paths) after `git_diff --cached` shows nothing foreign. If the index holds foreign changes, use a temp-index commit onto `origin/main`. Then `git_push` with `allowBaseBranch: true`. No `Co-Authored-By` trailer. If CI on `main` is `in_progress`, wait before pushing. Report the commit hash and push result.

## Out of scope

- A second post-run fan-out, a `CloudRunnerDO`-local bookkeeping path, or duplicating lane, metrics, audit, or next-lane logic outside `applyLandedLifecycle`.
- `packages/agent-run` (there is no `no_changes` work there) and any file outside the fix set.
- Do not edit `api/src/application/llm/byoCooldown.ts`, `proxyFunding.ts`, `docs/specs/app-manifest-ai-resource.md`, `packages/knowledge-graph-view/**`, `ROADMAP.md`, or `DONE.md`.

- Full-suite test runs, unrelated refactors, and new product surface for no-changes UX.
