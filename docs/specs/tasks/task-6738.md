# PRD: Phase 1 — Local CPU Inference Engine

## Problem & Goal

Builderforce runs in browser WebContainers and today has no first-class path for on-device text generation. Remote inference breaks offline use, adds latency and cost, and couples the product to a network after a model has already been provisioned.

Phase 1 delivers a browser-compatible, CPU-first local inference runtime that generates tokens in a worker, stores and caches model assets locally, and stays fully offline after provisioning. WebGPU may be used when present, but the CPU path must work without it. A runtime abstraction must hide backend differences so later phases can swap engines without rewriting callers.

Success for this phase is a representative ~1B-parameter Q4 model running locally at the documented performance bar, without blocking the main thread and without remote inference calls after provisioning. Existing WebContainer tests must continue to pass.

## Target users / ICP roles

- **End user in the Builderforce web app:** runs short prompts against a provisioned local model, including offline, without UI freezes.
- **Product / agent runtime:** calls a stable inference API and does not choose WASM backends, quant formats, or cache layout.
- **Phase 1 implementer (subagent):** builds and benchmarks the runtime inside `seanhogg/builderforce.ai` (base `main`) and proves acceptance before Phase 2.
- **Downstream phases:** consume the abstraction, cache contract, and measured baselines; they do not re-litigate backend selection.

## Scope

In scope for Phase 1, inside the bound repo:

- CPU-first execution, using WebAssembly SIMD when the browser exposes it, with a correct non-SIMD fallback.
- Inference isolated in a Web Worker (or equivalent worker) so token generation never blocks the main thread.
- Quantized weights in the 1B–4B class, with an explicit evaluation of Q4, Q5, and Q8 on compatible model/config pairs. Ship path prioritizes a representative 1B Q4 model.
- Local model asset storage and caching so that, after provisioning, inference needs no network.
- A backend-agnostic runtime interface (load, generate, cancel, status, capability probe) with at least one CPU backend wired through it.
- Comparative evaluation of Transformers.js / ONNX Runtime Web, Wllama / llama.cpp WASM, and WebLLM only where WebGPU is available. Backends are not assumed to share formats or execution characteristics; only compatible models and configs are benchmarked against each other.
- WebGPU remains optional. If WebGPU is missing, blocked, or fails, the CPU-only path still loads and generates.
- Documentation of the reference machine, quant/config used, tokens/sec, and short-prompt time-to-first-token (TTFT) so the performance bar can be revalidated.
- Validation that existing WebContainer tests still pass, before any Phase 2 work.

## Functional requirements

1. **Runtime abstraction.** Callers depend on one interface for capability detection, model load from local assets, streaming or incremental generation, cancellation, and error reporting. Backend-specific types, file formats, and thread models stay behind the adapter.
2. **CPU-first execution.** The default path runs on CPU via WASM. SIMD is enabled when `wasm` SIMD (or the backend’s equivalent) is available and disabled cleanly otherwise. Absence of WebGPU must not prevent load or generation.
3. **Worker isolation.** Model load and token generation run off the main thread. The UI thread may receive progress and token callbacks only; it must not run the forward pass. A long generation must leave input, rendering, and navigation responsive.
4. **Quantized model support.** The engine accepts quantized weights for models in the 1B–4B range. Q4, Q5, and Q8 are evaluated on backends that actually support that quant and architecture. Results are recorded per backend and config; a faster number from an incompatible pair is not treated as a win.
5. **Representative ship config.** At least one representative ~1B Q4 model is vendored or provisioned as the acceptance model and runs end-to-end on the CPU path.
6. **Local asset storage and cache.** Weights, tokenizer, and any runtime config are stored in a durable browser store (for example Origin Private File System or Cache Storage, as the implementation chooses) under a versioned cache key. A cache hit skips re-download. Cache misses during provisioning may use the network; after a successful provision, generation must not.
7. **Offline after provisioning.** Once the acceptance model is cached, subsequent loads and generations issue no remote inference API calls and no weight fetches. Failures to read cache surface a local error, not a silent cloud fallback.
8. **Backend evaluation, not a shared-format assumption.** Evaluate Transformers.js / ONNX Runtime Web and Wllama / llama.cpp WASM on CPU. Evaluate WebLLM only as an optional WebGPU backend. Record model id, quant, context, backend version, SIMD on/off, and hardware. Do not rank backends on mismatched formats.
9. **Optional WebGPU.** If WebGPU is available and a WebLLM (or equivalent) adapter is included, it may be selected by capability probe. Selection failure falls back to the CPU backend without user-visible hard failure.
10. **Observability for the bar.** The runtime exposes or logs load time, TTFT for a defined short prompt, and decode tokens/sec on the reference machine so acceptance can be checked without guesswork.
11. **Non-regression.** Existing WebContainer tests remain green. New tests cover worker offload, cache hit without network, CPU path without WebGPU, and the acceptance generation.

## Acceptance criteria

- A representative 1B Q4 model loads from local assets and generates tokens on the CPU path in a browser environment compatible with Builderforce WebContainers.
- Sustained decode rate is at least 5 tokens/sec on the documented reference machine, after baseline hardware validation. The machine, browser, backend, model id, quant, and context length are written down with the measurement. If the reference machine cannot meet 5 tokens/sec, the gap is reported with measurements; the CPU path still functions, and Phase 2 does not start until the bar is met or explicitly rebaselined.
- Short-prompt TTFT is under 5 seconds measured after the model is already loaded (generation start to first token), on that same reference setup.
- Inference does not block the main thread: a concurrent main-thread timer or input handler continues to run during generation; the forward pass executes in a worker.
- After provisioning, a generation session performs no remote inference calls and no model-weight network fetches (verified by network inspection or test double).
- WebGPU disabled or unavailable: the same 1B Q4 CPU path still completes a short generation.
- SIMD-unavailable fallback still completes a short generation (performance bar applies to the SIMD-capable reference machine).
- Q4, Q5, and Q8 are evaluated and recorded for each backend that supports them; unsupported combinations are marked unsupported, not failed benchmarks.
- Existing WebContainer tests pass on `main` plus this change.
- A subagent implements the phase; acceptance evidence is checked and recorded before Phase 2 begins.

## Out of scope

- Phase 2 and later product features (multi-model UX, fine-tuning, tool calling, RAG, agent planning).
- Remote or hybrid inference, API-key cloud fallback, and any post-provision network path for tokens or weights.
- Training, continued pretraining, or on-device fine-tuning.
- Models outside the 1B–4B priority band, except as non-blocking evaluation notes.
- Assuming one model file runs unchanged across Transformers.js, ONNX Runtime Web, llama.cpp WASM, and WebLLM.
- Making WebGPU, WebLLM, or a specific GPU mandatory.
- Native desktop or mobile runtimes, server-side GPU inference, and changes to SOC2 evidence beyond what the feature itself requires.
- Rewriting unrelated WebContainer, frontend, or API behavior except as needed to mount the runtime and keep current tests passing.
