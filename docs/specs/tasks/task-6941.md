# PRD 49: Methodology personas and the `.builderforce/` workspace layout

## Problem & Goal

Builderforce agents, the webcontainer runtime, and the VS Code extension do not yet share one workspace contract for methodology personas, path layout, model policy, the ONNX q4 catalog, or gzip packs. Without that contract, path checks get copied into the VSIX, a second persona registry appears, tools each carry their own gzip copy, and a root manifest writer drifts from the launcher manifest.

Ship PRD 49 so `.builderforce/` layout, persona selection, and pack/model policy are owned in one place and enforced by automated §9 done-checks. `builderforce-webcontainers` (WS-A) ships first and owns path validation; the VSIX consumes that validation and does not copy it. Personas never bypass PRD 45 gates or PRD 48 ship policy.

End-state design is `Builderforce.ai/docs/specs/49-prd-end-state.md`. Epic source is `Builderforce.ai/docs/specs/make.md`, section PRD 49. Both must be reviewed before any code. Implementation follows that design; this PRD does not authorize a parallel layout, registry, or pack format.

Bound repo: `seanhogg/builderforce.ai`, base `main`.

## Target users / ICP roles

- Builders running Builderforce in the VS Code extension and in webcontainers, who need a stable `.builderforce/` workspace and a single set of methodology personas.
- Methodology authors who add or select personas without standing up a second registry or skipping ship gates.
- Runtime and extension engineers who must share one path validator, one manifest, one model policy, one ONNX q4 catalog, and one gzip-pack pipeline.
- Downstream agents on this epic, who implement only the workstream they own and must not re-implement another workstream’s contract.

## Scope

In scope, in ship order:

1. **WS-A** — manifest and launcher options in `builderforce-webcontainers`, including the path validation the VSIX will consume.
2. **WS-B** — `workspacePaths` for the `.builderforce/` layout defined by the end-state design.
3. **WS-C** — methodology personas on the existing persona registry only.
4. **WS-D** — model policy.
5. **WS-E** — ONNX q4 catalog.
6. **WS-F** — gzip packs as one shared pack pipeline.
7. Release notes, blog post, move of this epic into `DONE.md`, and removal from `ROADMAP.md`.

Every §9 done-check in the end-state design is an automated test. Later workstreams depend on earlier ones; do not start VSIX path checks, persona wiring, model policy, catalog, or packs against a copied or provisional validator.

## Functional requirements

### Shared rules

- Review `49-prd-end-state.md` and make.md section PRD 49 before writing code. Field names, directory layout, persona ids, model ids, catalog entries, and pack contents come from that design, not from a local reinterpretation.
- One persona registry. Do not add a second registry, a shadow list, or a tool-local persona table.
- One path validator, owned by `builderforce-webcontainers`. The VSIX calls that API. Do not duplicate the validation function, its allow/deny rules, or its tests inside the extension.
- One manifest writer, owned by the WS-A launcher/manifest path. Do not add a root manifest writer, a repo-root script that emits the manifest, or a second writer in the extension.
- One gzip-pack producer (WS-F). Do not copy gzip bytes or pack-build logic per tool.
- Methodology personas are subject to PRD 45 gates and PRD 48 ship policy on every path that selects, launches, or ships work as that persona. A persona flag, profile, or launcher option must not skip, weaken, or short-circuit those checks.
- Tests assert the §9 done-checks directly. A narrative checklist in docs is not acceptance.

### WS-A — manifest and launcher options

- Land first in `builderforce-webcontainers`.
- Expose launcher options and the workspace manifest required by the end-state design.
- Export path validation as the single API later consumers call. Validation covers the `.builderforce/` paths WS-B will name, and rejects paths outside that contract.
- Manifest write stays inside this package’s launcher/manifest module. No writer is added at the repository root.

### WS-B — workspacePaths

- Implement `workspacePaths` only after WS-A validation exists, and resolve paths through that validator.
- The path set is exactly the `.builderforce/` layout in the end-state design. Do not invent sibling roots or alias the same file under a second path.
- Callers, including the VSIX, obtain paths from this module. They do not hard-code a parallel layout.

### WS-C — methodology personas

- Register methodology personas only in the existing persona registry.
- Persona launch and selection go through WS-A launcher options and WS-B paths.
- Persona execution still passes PRD 45 gates and PRD 48 ship policy. Tests must fail if a persona path omits either check.

### WS-D — model policy

- Apply model policy from the end-state design to persona and launcher model choice.
- Policy is a single module consumed by runtime and extension. Do not fork policy per tool or per persona file.
- Policy cannot be disabled by persona selection.

### WS-E — ONNX q4 catalog

- Publish the ONNX q4 catalog defined by the end-state design.
- Catalog entries are the only q4 model ids model policy and launcher options may select for this epic.
- Do not embed a second catalog in the VSIX or in individual tools.

### WS-F — gzip packs

- Build gzip packs once, from the shared catalog and workspace layout, as specified in the end-state design.
- Tools consume the shared pack artifact. They do not each gzip their own copy of the same payload.

### VSIX

- Depends on published WS-A path validation and on `workspacePaths`.
- Does not vendor, transpile-copy, or reimplement validation, the persona registry, model policy, the ONNX catalog, gzip packing, or manifest writing.

### Release hygiene

- After §9 tests pass: release notes, blog post, move the PRD 49 item into `DONE.md`, and remove it from `ROADMAP.md`.
- Docs describe the shipped contract. They do not introduce a second layout or registry.

## Acceptance criteria

- `49-prd-end-state.md` and make.md section PRD 49 were the design inputs; the diff does not contradict them.
- WS-A is merged before any VSIX change that needs path validation. The extension’s dependency graph calls `builderforce-webcontainers` validation; a search of the VSIX shows no copied validator.
- `workspacePaths` matches the end-state `.builderforce/` layout and every path is checked by the WS-A validator.
- Persona lookup hits only the existing registry. Tests fail if a second registry module or data file is introduced.
- A persona launch fixture still fails closed when a PRD 45 gate fails, and still obeys PRD 48 ship policy. No persona option skips either.
- Model policy is the only policy path for persona/launcher model choice, and it only allows ids from the WS-E ONNX q4 catalog.
- Gzip pack tests show one producer and no per-tool gzip copy of the same payload.
- No root manifest writer exists. Manifest bytes are produced only by the WS-A writer.
- Every §9 done-check has an automated test, and the suite fails if any §9 check is missing or failing.
- Release notes and the blog post match the shipped behavior. `DONE.md` contains the PRD 49 entry. `ROADMAP.md` no longer lists it.

## Out of scope

- A second persona registry, persona shadow list, or per-tool persona table.
- Copying path validation, model policy, catalog, or pack logic into the VSIX or into individual tools.
- A repository-root manifest writer.
- Per-tool gzip copies of a shared pack.
- Any persona bypass, override, or fast path around PRD 45 gates or PRD 48 ship policy.
- New workspace roots outside the end-state `.builderforce/` layout.
- ONNX variants other than the q4 catalog specified for this epic.
- Changes to PRD 45 or PRD 48 semantics beyond calling them unchanged.
- Redesign of unrelated packages under `agent-runtime/`, `actions/`, or `.claude/` except where a workstream above requires a call into the shared contract.
