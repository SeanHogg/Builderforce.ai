# PRD: Export `bootRovrServiceWorker`

## Problem & Goal

The Rovr Chrome service worker at `Builderforce.ai/clients/chrome/src/background/serviceWorker.ts` has no exports. Its policy, outbox, and `flushAll` initialization currently occurs through module side effects, preventing test scenarios from explicitly booting and restarting the worker.

Expose a named `bootRovrServiceWorker` export that provides a deterministic service-worker boot entry point while preserving the existing production startup behavior. The entry point must support validating that Rovr:

- Makes no platform request while the network is denied.
- Persists work durably while offline.
- Retains that work across a service-worker restart.
- Replays the queued work in a batch after connectivity returns.

## Target Users / ICP Roles

- **Extension QA and integration engineers:** Validate offline, persistence, restart, and replay behavior without modifying production source for each scenario.
- **Rovr service-worker maintainers:** Use one initialization path for production startup and automated tests.
- **Agent-runtime developers:** Invoke a stable, named boot API when exercising Rovr scenarios.

## Scope

### In Scope

- Add the named export `bootRovrServiceWorker` from `Builderforce.ai/clients/chrome/src/background/serviceWorker.ts`.
- Refactor or wrap the current policy, outbox, and `flushAll` initialization behind the boot path.
- Preserve normal Chrome service-worker startup and event handling.
- Support deterministic boot, restart, and replay scenarios in the existing Chrome test environment.
- Add or update automated coverage for the exported boot entry point and the offline-to-replay lifecycle.

### Out of Scope

- Adding `bootRovrPanel` or changing `Builderforce.ai/clients/chrome/src/host/panelServices.ts`.
- Redesigning policy evaluation, outbox storage, retry scheduling, or flush behavior.
- Changing platform APIs, transport formats, or storage schemas.
- Introducing a separate panel-specific acceptance surface.
- Relaxing the requirement that denied-network operation produces no platform call.

## Functional Requirements

1. **Named boot API**
   - `serviceWorker.ts` must export `bootRovrServiceWorker` using the exact requested name.
   - A scenario must be able to import and invoke it without editing the service-worker source.

2. **Production-equivalent initialization**
   - The boot path must initialize the same policy, outboxes, `flushAll` behavior, and required Chrome listeners or alarms used by the production worker.
   - Normal extension startup must continue to initialize the worker automatically.
   - Automatic startup and an explicit boot call in the same worker lifetime must not create duplicate listeners, timers, outboxes, or flush executions.

3. **Deterministic completion**
   - Initialization performed by `bootRovrServiceWorker` must complete before a scenario makes assertions.
   - Asynchronous initialization must be represented by an awaitable return value.
   - Initialization failures must not be silently reported as a successful boot.

4. **Offline safety**
   - Booting or processing work while the network is denied must not cause a platform request.
   - Work that cannot be delivered must be committed to the existing durable outbox rather than held only in memory.

5. **Restart behavior**
   - A fresh service-worker boot after restart must reuse persisted outbox data.
   - Restarting while the network remains denied must not replay retained work or generate a platform call.

6. **Replay behavior**
   - When connectivity is restored and flushing occurs, retained work must be replayed in a batch through the existing platform path.
   - Successfully replayed work must be removed or acknowledged according to the existing outbox semantics so it is not delivered again.

7. **Surface separation**
   - The acceptance entry point must be the service-worker export, not a new panel API.
   - The boot path must not depend on panel-only bindings such as `chrome.tabs` or `chrome.runtime` interactions owned by `createPanelServices`.

## Acceptance Criteria

1. **Export is available**
   - The following import resolves successfully:
     ```ts
     import { bootRovrServiceWorker } from "./background/serviceWorker";
     ```
   - No source edits are required to use the boot entry point in a scenario.

2. **Denied network causes no platform call**
   - Given the platform network is denied, when the worker boots and processes a writable operation, then the platform-call mock records zero requests.

3. **Operation is persisted**
   - Given the network is denied, when one durable write is processed, then the operation is present in the existing persistent outbox storage.

4. **Data survives restart**
   - Given the operation was persisted, when the service worker is restarted and booted again, then the operation remains present.

5. **Restart remains offline-safe**
   - Given the network is still denied after restart, when the worker boots and flush opportunities occur, then the platform-call count remains zero.

6. **Queued work is replayed**
   - Given persisted work and restored network access, when the existing flush path runs, then the queued operation is included in a replay batch and reaches the platform exactly once.

7. **Production startup is preserved**
   - Given a normal Chrome extension service-worker startup, when the module loads, then policy, outbox, flush, listener, and alarm behavior initialize once and remain operational.

8. **Regression checks pass**
   - Relevant unit or integration tests, TypeScript validation, and the repository’s standard lint checks pass.

## Out of Scope

- A generic Chrome-independent panel or service-worker runtime.
- New APIs under `panelServices.ts`.
- Changes to the meaning of a durable write, outbox acknowledgment, or platform batching.
- New offline-policy rules beyond those already implemented by Rovr.
- Manual recovery tooling for orphaned outbox records.
- UI changes or user-facing settings.
