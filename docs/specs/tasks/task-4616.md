# VSIX offline continuity when the platform API is down

## Current-state findings (what the code does today)

| Area | Finding | Where |
|---|---|---|
| Connectivity signal | `apiConnectivity` (`createOnlineSignal(true)`) is set by `trackReachability`: a request that gets **no answer** sets it false, any answer sets it true. It cannot distinguish "unreachable" from "Neon out of capacity" unless the API answers with an error body. | `src/outboxStorage.ts` |
| Write outbox | Durable outboxes (`createDurableOutbox`) persist to `workspaceState`, are tenant-scoped, pause while `apiConnectivity` is false and replay when any call gets through. This is the **only** queue to use. | `src/outboxStorage.ts` |
| Rail reads | `createLocalRailAdapter.listTickets` already reads from the host's local store (`local.chatRail` → `read`), then refreshes in the background. A refresh failure is swallowed, so the local copy stands. `refreshSoon` is skipped when `host.connected()` is false. | `webview/src/chat/localRailAdapter.ts` |
| Rail picker | `useTicketRail` swallows `listTickets` failures to `[]` for the `#` typeahead. | `webview/src/chat/useTicketRail.ts` |
| Degraded banner | "The board could not be drawn. The conversation is still here." is the `canvas.degraded` label, rendered by `CanvasBoundary` with the chat as `fallback`. `BoardWithChat` already renders `BoardAuthNotice` + chat when the board is not `ready`. The CSS comment states the notice is "a ROW ABOVE the chat, not an overlay". | `webview/src/WorkspaceApp.tsx`, `src/canvasHostActions.ts`, `webview/src/index.css` |
| Banner wording | The label names neither "platform unreachable" nor "out of database capacity". It is a board-render message reused for network failure. | `src/canvasHostActions.ts`, `l10n/bundle.l10n*.json` |
| Local-model gate | `rootGate` already lets a local route through (`localRoute` / `localPick`) without an account; `VsCodeChatSurface` shows an inline banner offering "Use a local model" when no route exists. | `webview/src/WorkspaceApp.tsx`, `signedOutGate.ts` |

**Consequence:** the rail cache largely exists already, because the rail reads the host's local copy. The remaining gaps are (1) proving and hardening that the rail never empties on a failed refresh, (2) no automatic local-model selection driven by `apiConnectivity`, (3) a degraded message that is explicit and does not reuse the board-render copy, and (4) no stale / last-known indicator. Developers must **verify before rebuilding** — do not add a second cache next to the host's local rail store.

## Business requirements

**BR-1 Non-fatal degraded state.** An unreachable platform or exhausted database never signs the user out, wipes the transcript, empties the rail, or disables local editing.

**BR-2 Last-known rail.** The ticket rail always shows the last successfully loaded tickets while the platform is down, marked as last-known. With no prior load: empty rail plus the explicit error; no invented tickets.

**BR-3 Local model fallback.** While `apiConnectivity` is false, chat runs on a local model without a platform round-trip. When connectivity returns, the user's prior platform model choice is restored if still valid.

**BR-4 Explicit, non-blocking message.** One banner names the failure and sits in the layout flow (a row), never over the transcript or rail.

**BR-5 Replay.** Offline edits go through the existing outbox only; on reconnect they flush in order, then the rail refreshes from the server.

## Functional requirements (testable)

### Slice (a) — rail survives API failure
- FR-A1 A failed `refresh` (network error, 5xx, Neon-capacity error) leaves the previously stored `RailSnapshot` untouched in `RailStore`; `listTickets` returns it.
- FR-A2 The host's `local.chatRail` `read` is the cache. Confirm it persists across extension reload; if it does not, persist the last successful snapshot per `ChatRef` in the existing local store — not in a new Memento key family.
- FR-A3 The rail exposes a "last known" flag (derived from: `apiConnectivity` false OR last refresh failed) and renders an indicator without hiding or disabling any ticket.
- FR-A4 Selecting a cached ticket paints its already-loaded transcript without requiring a successful list or ticket fetch.
- FR-A5 `useTicketRail`'s `[]` fallback for the `#` typeahead must not replace cached local tickets; it merges server results over local ones and only the server part may be empty.

### Slice (b) — local model auto-select
- FR-B1 Subscribe to `apiConnectivity`. On transition to false, select a local route: prefer Synapse when installed and running, else another installed local runtime the extension already supports. Record the user's prior platform selection first.
- FR-B2 While false, no platform model route (gateway `/llm/*`) is called for chat; the send path chooses the local route.
- FR-B3 No local model available: composer stays enabled; send fails with a specific non-fatal message ("A local model is required while the platform is unreachable") and makes **no** API call.
- FR-B4 On transition to true, restore the recorded platform selection if still valid; otherwise leave the current model. The model indicator always shows which model is active.
- FR-B5 Auto-selection must not override a model the user chose manually **during** the outage.

### Slice (c) — banner does not hide work
- FR-C1 Replace reuse of `canvas.degraded` for network failure with a new label (e.g. `platform.degraded`) in `src/canvasHostActions.ts`, `l10n/bundle.l10n.json` and every `bundle.l10n.<lang>.json`.
- FR-C2 Message text. When the client can tell: "BuilderForce platform is unreachable" vs "The platform database is out of capacity". When it cannot: one message covering both ("BuilderForce can't reach the platform or its database is out of capacity"). Do not state a cause that was not observed. Distinguish only on an actual API response (e.g. 5xx body naming capacity); a no-answer is always "unreachable".
- FR-C3 The banner is a layout row above the chat/rail (the `bf-degraded-shell` pattern), not an overlay; it is dismissible, and dismissing changes no data.
- FR-C4 `CanvasBoundary` keeps `fallback={chat}`; the rail and transcript are never unmounted by the degraded state.

### Change tracking and replay
- FR-D1 No new queue. Edits made offline use existing `createDurableOutbox` queues.
- FR-D2 Queued items survive reload (already true via `workspaceState`) and remain until acknowledged.
- FR-D3 On `apiConnectivity` true: flush in original order, then refresh the rail from the server (`refreshSoon` must bypass its 30 s throttle for this reconnect refresh).
- FR-D4 A failed flush leaves the remainder queued, surfaces a non-fatal sync error, and keeps the cached rail.
- FR-D5 The permission gate (`outboxSendPermission`) remains in force: connectivity returning must not send when permission is denied.

## Edge cases to cover
- Connectivity flaps (true→false→true within the throttle window); no selection thrash, no lost restore target.
- Signed out and offline: the rail reads a local chat (`ChatRef` string) and must not require a token.
- Tenant switched while offline: the cached rail is per chat/tenant scope and must not leak across tenants; outbox entries remain parked for their own tenant.
- Neon error that returns an HTTP answer: `apiConnectivity` is true, so the outbox keeps sending and fails. The failure must be surfaced as degraded without flipping connectivity, and the local fallback decision must key off a "platform unusable" signal, not only `apiConnectivity`. **Open question for the architect** (see below).
- `trackReachability` wraps only some requests; confirm every API call path sets the signal.

## Assumptions
1. `local.chatRail` read is persisted by the host's local store and survives reload (to be verified, FR-A2).
2. Synapse and other local runtimes are detectable by existing host code; no new runtime support is added.
3. The 30 s refresh throttle is a constant (`REFRESH_EVERY_MS`) and may be bypassed on reconnect.

## Open questions (route to architect, not blocking BA sign-off)
1. Should "Neon exhausted" (HTTP 5xx with an answer) also trigger local-model fallback, given `apiConnectivity` stays true? The ticket says "when `apiConnectivity` is false"; the PRD treats Neon exhaustion as degraded. Recommendation: introduce a derived "platform usable" signal (unreachable OR N consecutive 5xx) and gate FR-B1 on it, keeping `apiConnectivity` semantics unchanged for the outbox.
2. Where does the "last known" flag come from: the host (`RailSnapshot` field) or the webview (connectivity + refresh outcome)? Recommendation: webview-derived, so no protocol change in `chatRail/railProtocol`.

## Out of scope
Fixing Neon or API availability; new local runtimes or installers; a second outbox, new sync protocol or conflict UI; auth/billing offline; web/mobile parity; offline ticket creation beyond what the outbox already queues; model-picker redesign beyond auto-select and the stale indicator.
