# Task 4616 — VSIX offline: local models + change tracking when API/Neon is down

Role: Architect · Lane: ready · Scope: `clients/vscode` (extension host + webview). No hosted-API or Neon changes.

## 1. Findings (what the code does today)

Read for this design: `clients/vscode/webview/src/chat/useTicketRail.ts`, `clients/vscode/webview/src/chat/localRailAdapter.ts`.

- The ticket rail is already **local-first**. `createLocalRailAdapter` answers `listTickets`/`listRuns`/links from the host's local copy via `request('local.chatRail', { action: 'read' })`, stores the result in a per-chat `RailStore`, and only *asks the host to refresh in the background* (`refreshSoon`, at most once per `REFRESH_EVERY_MS` = 30 s, and only when `host.connected()`). A refresh failure is swallowed (`.catch(() => { /* the local copy stands */ })`).
- Consequence: the local rail copy is the cache for slice (a). The gap is therefore **not a new cache layer**. It is (1) the host's `read` must never depend on the platform, (2) the rail must be marked stale when the last refresh failed or the platform is down, and (3) the places that still call the *platform* adapter directly must degrade instead of throwing. The one confirmed such place in the files read is the composer `#` typeahead in `useTicketRail.ts`: when `connected` it calls `ticketAdapter.listTickets(serverChatId)` (local-backed) and `.catch(() => [])`, so that path is already non-fatal; the remaining platform-only calls (merge, invite, run, `questionsFor`) come from `createChatTicketsPlatform` (`remote`) and are the ones that can surface "The board could not be drawn".
- `connected` is read through `webviewCapability('connected')` / `useCapability('connected')`. This is the single existing gate; it is the signal the PRD calls `apiConnectivity`. It is a **policy/capability** signal (platform allowed), not a **reachability** probe.

Not verified in this pass (rate-limited code search and token budget): the exact source of the "board could not be drawn" string, the `apiConnectivity` producer, the model-routing/Synapse selection code, and the outbox/pending-changes store. The implementer must locate these first (see §6) and must not assume the names below beyond what is stated.

## 2. Key decision: separate *policy* from *reachability*

`connected` today means "the platform may be used". An outage is a different axis: the platform is permitted but unreachable. Conflating them would either (a) make a transient blip look like a policy flip and drop the user's platform model choice, or (b) leave the UI claiming connectivity during an outage.

Introduce one small, pure state in the host, exposed to the webview as a capability alongside `connected`:

```
type PlatformHealth =
  | { state: 'ok' }
  | { state: 'unreachable'; since: number }          // network / 5xx / timeout
  | { state: 'capacity'; since: number }             // API reports DB capacity exhausted, when distinguishable
```

- Derived only from real request outcomes already made by the host (no new polling endpoint required; an optional low-frequency probe while `unreachable` is allowed so recovery is detected without a user action).
- `capacity` is set **only** when the response positively identifies it (a distinguishable status/body from the API). Otherwise use `unreachable` with one message that covers both causes. The client never invents a cause (PRD requirement).
- Hysteresis: 2 consecutive failures to enter degraded, 1 success to leave. Prevents banner flapping.
- Degraded never touches auth, local conversation state, or the outbox.

`apiConnectivity === false` in the PRD maps to `PlatformHealth.state !== 'ok'` **or** `connected === false` (policy denied). Both route chat to local models; only `unreachable|capacity` shows the degraded banner (policy-denied already has its own signed-out/denied presentation).

## 3. Slices

### (a) Last-known rail survives list failure
- Keep the host's local rail copy as the single cache. On a failed background refresh, do **not** clear it; record `staleSince` on the snapshot.
- Extend `RailSnapshot` (in `src/chatRail/railProtocol`) with an optional `stale?: { since: number; reason: 'unreachable' | 'capacity' }`. Optional field, so older frames remain valid.
- `ticketVm`/`useRailSnapshot` pass it through; the panel shows a "last known" indicator **without hiding tickets or blocking selection**.
- First-ever load with no local copy: snapshot has empty `tickets` and `stale` set; the UI shows the degraded banner and an empty rail. No fabricated tickets.
- A cached ticket's conversation is rendered from the already-loaded local transcript (chat persistence is local via `BrainPersistenceAdapter`); selection must not require a platform fetch.
- On recovery: after outbox flush (see §5) run one `refresh` per visible chat; success replaces the snapshot and clears `stale`.

### (b) Local model auto-select when platform is down
- Put the decision in **one pure function** (testable, no I/O): 

```
resolveOfflineModel({ health, connected, installedLocal, userPlatformChoice, lastForced })
  -> { modelId: string | null, forced: boolean, restore?: string }
```
- Order: Synapse if installed and running → another installed local runtime the extension already supports → `null`.
- `forced: true` while degraded; the model picker shows a visible "offline fallback" indicator.
- On recovery return `restore = userPlatformChoice` if still valid; otherwise clear forced state and let normal selection run. Never leave the user on the fallback silently.
- **Enforcement point:** the existing gateway-inference gate in model routing (memory: "modelRouting gateway-inference gate" is composed). The offline rule must be enforced there (host side), not only in the picker, so no code path can send a platform model request while degraded. Picker auto-select is UX; the gate is the guarantee.
- `modelId === null`: composer stays enabled; send is rejected locally with a specific non-fatal message ("A local model is required while the platform is unavailable"). Must not fall through to the API.

### (c) Degraded banner is non-blocking
- Replace the full-surface "board could not be drawn" state with a banner component rendered **beside**, not instead of, the thread and rail (a sibling in the layout, never a conditional that swaps them out).
- Copy comes from the host's l10n bundle (`package.nls.json` + the `ct.*` / chat labels pattern used by `chatTicketsLabelsFromBundle`) — no hard-coded English. Three messages: unreachable, out of database capacity, undetermined (covers both).
- Dismiss is view-state only. It must not touch the rail store, transcript, or outbox.

## 4. Ownership / boundaries
- Webview: banner, stale indicator, picker indicator. Presentational + hooks only (`useTicketRail`, a new `usePlatformHealth`).
- Host: health state machine, offline model resolution + gate enforcement, rail `stale` stamping, outbox replay trigger.
- Shared contract: `railProtocol` (`stale?`), capability list (`platformHealth`).
- Do not add a second queue, a sync protocol, or any server change.

## 5. Change tracking and replay
- Reuse the existing write-outbox + pending-changes path unchanged. Verify (do not assume) that every offline-capable write already goes through it; any write found that bypasses it is a bug to fix by routing it through the outbox, not by adding storage.
- Recovery sequence, in order: health → `ok`; flush outbox in original order; acknowledged items cleared; then refresh rails.
- Flush failure: remaining items stay queued, a non-fatal sync error is surfaced, the rail cache is retained.
- Must survive extension reload (already a property of the outbox store; add a test that asserts it for this flow).
- Interaction with open gap tickets: G12 (#5846 revoke stops outbox), G14 (#5848 atomic domain write + enqueue), G15 (#5849 server batch sync), G24 (#5858 single coordinator + lease). This work must not start a competing flush; it only *triggers* the existing coordinator on recovery. If the coordinator is not yet composed (G24 open), call the existing outbox flush entry point and leave a TODO-free note in the PR.

## 8. Risks
- **Conflating policy and reachability** (mitigated by §2).
- **Picker-only enforcement** would still allow a platform call from a non-UI path; hence the gate requirement in §3(b).
- **Banner flapping** on flaky networks; hysteresis in §2.
- **Concurrent offline-first work** (epic #5747 gaps) touches the same files (outbox, coordinator, policy). Rebase carefully; do not reimplement G12/G14/G15/G24.
- **Open question for the implementer:** whether the API can positively signal DB-capacity exhaustion. If not, ship the single combined message and omit the `capacity` state rather than guessing.
