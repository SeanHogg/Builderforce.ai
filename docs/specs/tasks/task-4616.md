# PRD: VSIX offline continuity when the platform API is down

## Problem & Goal

When builderforce.ai or its API is unreachable, including Neon compute exhaustion, the VSIX extension fails closed. The board shows “The board could not be drawn. The conversation is still here.” Listing tickets empties the rail, and chat still depends on the platform API, so the user cannot keep working.

Goal: the extension remains usable with no platform connectivity. The user keeps the last-known ticket rail and conversation, chats through a local model, and has local edits queued. A clear, non-fatal error states that the platform is unreachable or out of database capacity. When the API returns, queued writes flush and the rail refreshes from the server.

## Target users / ICP roles

- Builder using the BuilderForce.AI VS Code extension as the day-to-day ticket and chat surface.
- Same user during an outage or Neon capacity exhaustion who must continue a conversation and local edits without waiting on the hosted API.
- Not in scope as a primary persona: platform operators fixing Neon, or web-app-only users.

## Scope

Epic outcome: offline continuity for the VSIX against builderforce.ai.

First slices, in order:

1. Cache the last successful chat-ticket list and render it when `listTickets` fails, instead of clearing the rail.
2. When `apiConnectivity` is false, auto-select an available local model (Synapse or another installed local runtime) so chat does not wait on the platform.
3. Keep the degraded-board banner from covering or replacing the conversation and the ticket rail. The banner must name the failure (platform unreachable, or out of database capacity) and must not block local work.

Adjacent epic behavior that these slices must not regress: the existing write-outbox and pending-changes path records edits made while offline and replays them when the API is reachable again, then the rail refreshes.

Bound to the VSIX / extension client in `seanhogg/builderforce.ai` (base `main`). Do not redesign the hosted API or Neon.

## Functional requirements

**Connectivity**

- Treat platform API failure and Neon compute exhaustion as a degraded, non-fatal state. Detection uses the existing `apiConnectivity` signal (false means unreachable).
- Distinguish, when the client can tell, “platform unreachable” from “out of database capacity.” If the client cannot tell them apart, use one explicit degraded message that covers both, and do not invent a cause.
- Degraded state must not sign the user out, wipe local conversation state, or disable local editing.

**Ticket rail cache (slice a)**

- After every successful ticket-list load, persist the last-known chat tickets locally in the extension (enough to redraw the rail and reopen the last-viewed conversation).
- On `listTickets` failure, render that cache. Do not empty the grid and do not replace the rail with only the board-could-not-be-drawn message.
- If no cache exists yet, show an empty rail plus the degraded error. Do not fabricate tickets.
- Mark the rail as last-known / stale while serving cache, without hiding tickets or blocking selection of a cached ticket.
- Selecting a cached ticket shows its last-known conversation. Do not require a successful list or ticket fetch to paint that transcript if it was already loaded.

**Local model fallback (slice b)**

- When `apiConnectivity` is false, automatically select a usable local model: prefer Synapse when it is installed and running; otherwise an installed local runtime the extension already knows how to call.
- Do not call the platform model route while `apiConnectivity` is false.
- Chat send uses the selected local model and appends to the visible conversation.
- If no local model is available, chat input stays available but send fails with a specific non-fatal message that a local model is required while the platform is down. Do not fall through to the API.
- When `apiConnectivity` returns to true, stop forcing the local model. Restore the user’s prior platform model choice if it is still valid; do not leave them stuck on the offline fallback without a visible model indicator.

**Degraded banner (slice c)**

- Replace the blocking “board could not be drawn” presentation with a non-modal banner (or equivalent) that states the platform is unreachable or out of database capacity.
- The banner must not overlay, collapse, or unmount the conversation transcript or the ticket rail.
- Dismissing or ignoring the banner must not clear cached tickets, the transcript, or the outbox.

**Change tracking and replay**

- Every local edit made while the API is down is recorded through the existing write-outbox and pending-changes mechanism. Do not add a second queue.
- Queued writes survive extension reload and remain pending until acknowledged by the API.
- When the API is reachable again, flush the outbox in original order, then refresh the ticket rail from the server.
- A failed flush leaves remaining items queued, surfaces a non-fatal sync error, and does not drop the cached rail.
- Successful replay clears only acknowledged items and then replaces stale rail data with the server list.

## Acceptance criteria

- With the API down or Neon exhausted, a user who previously loaded tickets still sees those tickets and the open conversation, not an empty grid and not a board that hides the transcript.
- In that same state, sending a chat message uses a local model (Synapse or another installed local runtime) without a platform round-trip, and the reply appears in the conversation.
- Local edits made while offline are present in the existing outbox / pending-changes store and are not lost on reload.
- The visible error explicitly says the platform is unreachable or out of database capacity, and the user can still select cached tickets, read the conversation, and queue edits.
- The degraded banner does not cover or remove the conversation or the ticket rail.
- When the API is reachable again, the outbox flushes and the rail refreshes from the server. Acknowledged pending changes are cleared; unacknowledged ones remain queued.
- If the user has never successfully loaded tickets, failure shows the explicit error and an empty rail, not a crash and not invented tickets.
- If no local model is installed, offline chat does not call the API and explains that a local model is required. The rail cache and outbox still work.

## Out of scope

- Fixing Neon capacity, API availability, or server-side retry policy.
- New local model runtimes, installers, or Synapse product work beyond selecting a runtime the extension already supports.
- A new sync protocol, conflict-merge UI, or a second outbox. Replay uses the existing write-outbox and pending-changes path only.
- Offline account creation, billing, or auth redesign.
- Web or mobile parity.
- Creating or deleting tickets on the server while offline beyond what the current outbox already queues.
- Changing ticket schema, board layout, or model-picker design except the auto-select and stale-rail indicator required above.
