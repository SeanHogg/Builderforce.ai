# PRD: Evidence Trace Rows for `run-guards` Advisories

## Problem & Goal

Detector trips already produce progress-check trace rows that hosts understand, but advisory-only actions—B1 readiness and B4 batching nudges—leave no visible evidence. This creates an apparent gap in a run’s trace and makes advisory-driven behavior difficult to inspect.

Add a host-agnostic progress-trace mapping so every detector action produces one trace row while preserving existing trip behavior.

## Target Users / ICP

- **Runtime host engineers:** Integrate consistent progress traces without host-specific mapping logic.
- **Run operators and auditors:** Review visible evidence of both trips and advisory actions.
- **`run-guards` maintainers:** Extend detector tracing through a single package-owned abstraction.

## Scope

- Add `packages/run-guards/src/progressTrace.ts`.
- Emit one host-agnostic trace row for every detector action.
- Map detector trips to the existing `loop.progress_check` trace shape.
- Map never-a-trip advisories to `loop.progress_advisory`, including their advisory source.
- Support the current advisory sources:
  - B1 readiness
  - B4 batching nudge
- Export the progress-trace API from `packages/run-guards/src/index.ts`.
- Add coverage in `packages/run-guards/src/progressTrace.test.ts`.

## Functional Requirements

1. **Complete trace coverage**
   - Every detector action must map to exactly one progress-trace row.
   - Mapping must not depend on a specific runtime host.

2. **Trip mapping**
   - A detector trip must map to `loop.progress_check`.
   - The resulting row must retain the shape and semantics hosts already record for progress checks.

3. **Advisory mapping**
   - A never-a-trip advisory must map to `loop.progress_advisory`.
   - The row must include the advisory `source`, allowing B1 readiness and B4 batching nudges to be distinguished.
   - Advisory mapping must not convert the advisory into a trip or a progress check.

4. **Public availability**
   - The progress-trace implementation and its public types or helpers must be exported from the `run-guards` package index.

5. **Regression protection**
   - Automated tests must cover trip mapping, B1 advisory mapping, B4 advisory mapping, source preservation, and one-row-per-action behavior.

## Acceptance Criteria

- Given a detector trip, the package produces one `loop.progress_check` row compatible with existing host-recorded progress checks.
- Given a B1 readiness advisory, the package produces one `loop.progress_advisory` row whose source identifies B1 readiness.
- Given a B4 batching nudge advisory, the package produces one `loop.progress_advisory` row whose source identifies B4 batching.
- Given any supported detector action, exactly one trace row is produced; advisory-only actions no longer create an invisible trace gap.
- B1 and B4 advisories retain their existing non-tripping behavior.
- The progress-trace API is importable from `packages/run-guards/src/index.ts`.
- `packages/run-guards/src/progressTrace.test.ts` passes and protects the required mappings.
- TypeScript compilation succeeds with `tsc --noEmit`.
- The full `run-guards` Vitest suite passes with 190/190 tests.

## Out of Scope

- Changing detector thresholds, decisions, or advisory semantics.
- Converting B1 or B4 advisories into detector trips.
- Adding new detector or advisory categories.
- Host-specific trace persistence, rendering, or UI changes.
- Redesigning the existing `loop.progress_check` shape or broader runtime telemetry schema.
