## Requirements

Not a coding ticket (PRD §2 / §9). GitHub Actions cannot sign Synapse or the standalone `bfi` until signing material exists as repository secrets. Unsigned CI artifacts may ship until then; **M7 (#3776) must not claim signed installers until every acceptance item below is checked.**

## Design

### 1. Current state (verified in this repo)

| Fact | Evidence |
|---|---|
| `codesign-mac-app.sh` signs with a local keychain identity (`SIGN_IDENTITY`, or auto-selects a `Developer ID Application` cert). | `agent-runtime/scripts/codesign-mac-app.sh` |
| `notarize-mac-artifact.sh` accepts `NOTARYTOOL_PROFILE` **or** `NOTARYTOOL_KEY` + `NOTARYTOOL_KEY_ID` + `NOTARYTOOL_ISSUER`. | `agent-runtime/scripts/notarize-mac-artifact.sh` |
| `native-apps.yml` builds and unit-tests only. Its header says "it does not sign or publish". | `.github/workflows/native-apps.yml` |
| No workflow references `APPLE_*`, `notarytool`, `signtool` or Authenticode. | repo search, 0 hits |
| No workflow in this repo references `builderforce-inference` (the repo that builds standalone bfi). | repo search, 0 hits |

The scripts are already secret-friendly via env vars. **The gap is only (a) the secrets, (b) a CI step that materialises them into a temporary keychain / cert store, and (c) a non-publishing dry-run job.**

### 2. Secret contract

The same names are created in **both** `builderforce-inference` (standalone bfi) and the Synapse repo, as repository secrets (or as environment secrets on a `release-signing` environment with required reviewers; preferred, see §4).

**macOS (Apple Developer ID Application + notarization)**

| Secret | Content | Consumed by |
|---|---|---|
| `APPLE_DEVELOPER_ID_CERT_P12_BASE64` | base64 of the exported Developer ID Application `.p12` | import into temp keychain |
| `APPLE_DEVELOPER_ID_CERT_PASSWORD` | `.p12` export password | keychain import |
| `APPLE_SIGN_IDENTITY` | full identity, e.g. `Developer ID Application: <Org> (<TEAMID>)` | `SIGN_IDENTITY` for `codesign-mac-app.sh` |
| `APPLE_TEAM_ID` | 10-char Team ID | audit and logging |
| `APPLE_NOTARY_KEY_P8` | App Store Connect API key (`.p8` contents) | `NOTARYTOOL_KEY` (written to a temp file) |
| `APPLE_NOTARY_KEY_ID` | API key ID | `NOTARYTOOL_KEY_ID` |
| `APPLE_NOTARY_ISSUER_ID` | API issuer UUID | `NOTARYTOOL_ISSUER` |
| `APPLE_KEYCHAIN_PASSWORD` | arbitrary random string for the ephemeral CI keychain | `security create-keychain` |

The API-key notary path is chosen over Apple-ID + app-specific password. It is not tied to a person's account and 2FA, and it is already supported by `notarize-mac-artifact.sh`.

**Windows (Authenticode)**

| Secret | Content | Consumed by |
|---|---|---|
| `WINDOWS_CERT_PFX_BASE64` | base64 of the Authenticode `.pfx` (OV or EV code-signing cert) | `signtool sign /f` |
| `WINDOWS_CERT_PASSWORD` | `.pfx` password | `signtool sign /p` |
| `WINDOWS_TIMESTAMP_URL` (optional) | RFC 3161 server; default `http://timestamp.digicert.com` | `signtool sign /tr /td sha256` |

> **EV caveat (owner decision):** an EV cert is hardware-token bound and cannot be exported to a `.pfx`. If the owner buys EV, the Windows secret contract changes to a cloud HSM / Azure Trusted Signing service principal (`AZURE_TENANT_ID`, `AZURE_CLIENT_ID`, `AZURE_CLIENT_SECRET`, plus an endpoint and account/profile name) and the workflow step swaps `signtool` for the Trusted Signing action. The secret names above assume an exportable OV cert. This choice is recorded as an open owner decision in §6.

### 3. Workflow wiring

A reusable, **non-publishing** `workflow_call` / `workflow_dispatch` job `signing-dry-run` is added in each of `builderforce-inference` and Synapse, and documented by comments at the top of the release workflow:

1. **Secret presence check (all runners):** a step reads each secret into `env` and fails with a named list of missing secrets. It prints only `present` / `MISSING`, never values. The step is skipped with a clear notice on fork PRs, where secrets are unavailable.
2. **macOS leg (`macos-*`):**
   - decode the `.p12`, create a temporary keychain (`security create-keychain`, `set-keychain-settings`, `unlock-keychain`, `import … -T /usr/bin/codesign`, `set-key-partition-list`);
   - assert `security find-identity -p codesigning -v` lists the `Developer ID Application` identity and that its Team ID equals `APPLE_TEAM_ID`;
   - sign a tiny throwaway Mach-O (or the CI artifact, if one exists) via `SIGN_IDENTITY="$APPLE_SIGN_IDENTITY" agent-runtime/scripts/codesign-mac-app.sh`, with `codesign --verify --strict`;
   - run `xcrun notarytool history` with the API-key triple to prove the notary credentials authenticate, without submitting an artifact in dry-run;
   - `always()` cleanup: delete the temp keychain and the `.p8` file.
3. **Windows leg (`windows-latest`):** decode the `.pfx` to `$RUNNER_TEMP`, sign a throwaway `.exe` with `signtool sign /fd sha256 /tr $ts /td sha256`, run `signtool verify /pa`, then delete the `.pfx`.
4. **No publishing:** the dry-run has `permissions: contents: read`, no `NPM_TOKEN` or release-upload secrets, and no `upload-release-asset` step.

The real release jobs reuse the same decode/import steps. They additionally call `notarize-mac-artifact.sh` (submit + staple), and only run on tag or `main` pushes, so the dry-run and the release cannot drift.

### 4. Security constraints

- Secrets are scoped to a protected **`release-signing` GitHub Environment** (required reviewer = release owner; deployment branches limited to `main` and release tags). Signing jobs declare `environment: release-signing`, so PR-from-fork and arbitrary-branch runs never receive them.
- Never `echo` secrets; rely on masking, but also never `set -x` in signing steps.
- Ephemeral keychain and cert files live under `$RUNNER_TEMP` and are removed in `if: always()`.
- Cert/key rotation owner and expiry dates are recorded in the owner's secrets register (Developer ID certs: 5 years; Authenticode: 1–3 years). A calendar reminder is set 30 days before expiry.
- The `builderforce-inference` and Synapse secrets are separate copies of the same material. Rotating means updating both, so the rotation steps are listed in the release workflow header comment.

### 6. Open owner decisions / risks

1. **OV vs EV Windows cert**: EV forces the cloud-signing variant in §2. OV is simpler but starts with weaker SmartScreen reputation.
2. **Apple Developer Program enrolment** (Org vs Individual): the Org Team ID appears in the signed identity and is visible to users.
3. **Synapse repo name/location** was not resolvable from this repo (no references found). The owner confirms the target repo before secrets are created.
4. Repo secrets can only be created by a repo admin in GitHub settings or via `gh secret set`. This ticket's runner cannot do so, so the ticket stays open until the owner confirms the §5 checklist.

### 7. Scope of this PR

Design and contract only (this file). Workflow YAML is deliberately **not** added here. It lives in `builderforce-inference` and Synapse, which are not bound to this run, and adding unreferenced signing steps to this repo's `release.yml` would sit untested without the secrets present. A follow-up implementation ticket for the two workflows is recommended.
