# PRD: Frontend Typecheck, i18n Catalog Guard, and Brain Component Tests

## Problem & Goal

Frontend regressions currently slip through when TypeScript types drift, translation catalogs fall out of sync with source usage, or Brain UI components ship untested. Downstream agents need a single shared contract for a fast, deterministic quality gate that:

1. Fails the frontend if typecheck does not pass.
2. Fails the frontend if i18n catalogs are incomplete, unused, or locale-divergent.
3. Runs Vitest against Brain components when that surface exists, and skips cleanly when it does not.

**Goal:** A repeatable, CI-friendly frontend check that is the source of truth for type safety, i18n catalog integrity, and Brain component unit tests—without blocking unrelated workstreams.

## Target users / ICP roles

- Frontend engineers shipping UI and i18n strings
- CI / platform engineers wiring the gate into pipelines
- Downstream coding agents implementing or verifying this task
- Localization owners who must keep locale catalogs aligned

## Scope

In scope for this WIP:

- Project-local TypeScript typecheck for the frontend package(s) using the existing `tsconfig` graph.
- An i18n catalog guard that compares source-extracted keys against locale files and treats catalog drift as a hard failure.
- Conditional Vitest execution for Brain components: run when the Brain component tree (or equivalent test glob) is present; no-op success when it is absent.
- npm/pnpm/yarn scripts (or equivalent) and CI step wiring so the three checks can be invoked independently and as one composite gate.
- Clear, non-zero exit codes and human-readable failure output.

## Functional requirements

### Typecheck

- Invoke the frontend TypeScript compiler in no-emit mode against the frontend `tsconfig` (including project references if already configured).
- Do not generate build artifacts as part of this gate.
- Surface the first-class `tsc` diagnostics; do not swallow errors.
- Honor existing path aliases, strictness flags, and `skipLibCheck` as already defined in repo config; do not loosen compiler options for the gate.

### i18n catalog guard

- Treat the default/source locale as canonical.
- Extract or scan i18n keys from frontend source (existing extraction pipeline if present; otherwise key usage in the established i18n API).
- For every supported locale file:
  - Fail if a canonical key is missing.
  - Fail if a key exists that is not in the canonical set (unused / orphaned).
  - Fail if catalogs differ in key set, nesting, or plural/select variants required by the i18n library in use.
- Empty string values in non-source locales are a failure unless the repo already documents an explicit allowlist mechanism; if such an allowlist exists, honor it and do not invent a new one.
- The guard must be deterministic (same tree → same result) and must not mutate catalog files.
- Report failing keys grouped by locale and failure type (missing, extra, empty).

### Vitest — Brain components (conditional)

- Detect presence of Brain components via existing paths/globs (for example `**/brain/**/*.{test,spec}.{ts,tsx}` or the repo’s established Brain component directory plus colocated tests).
- If present: run Vitest in that scope only, using the frontend Vitest config already in the repo (jsdom/happy-dom, path aliases, setup files).
- If absent: skip the Vitest step, print a single explicit skip reason, and exit 0 for that step.
- Do not add new Brain components or tests unless they already exist and are broken by the gate’s invocation (fix invocation, not product surface).
- Tests must be unit/component tests only (render, props, i18n wiring, user events). No network, no live backend.

### Orchestration

- Expose three discrete scripts, e.g. `typecheck`, `i18n:guard`, `test:brain`, plus one composite `check:frontend` that runs them in that order and fails fast.
- Composite gate exit code is non-zero if typecheck or i18n guard fails, or if Brain tests ran and failed.
- Missing Brain surface does not fail the composite gate.

## Acceptance criteria

- `check:frontend` (or documented equivalent) is invocable from the frontend package root and is suitable as a CI step.
- A known type error causes typecheck and the composite gate to fail with `tsc` output.
- A missing key in any non-canonical locale causes the i18n guard and composite gate to fail, naming the locale and key.
- An extra/orphaned key in any locale causes the same class of failure.
- When Brain component tests exist, Vitest runs them and a failing assertion fails the composite gate.
- When Brain component tests do not exist, the Brain step is skipped with a visible message and the composite gate can still pass.
- The gate does not write to locale files, does not emit JS build output, and does not require network access.
- Re-running on an unchanged passing tree is green and stable.

## Out of scope

- Full frontend production build, bundling, or bundle-size budgets
- E2E / Playwright / Cypress
- Visual regression, a11y audits, or lint/format (unless already required by existing configs this gate merely invokes)
- Adding, translating, or rewriting copy; generating new locale files
- Changing i18n libraries, locale lists, or runtime fallback policy
- Implementing or redesigning Brain product behavior
- Backend, API, or shared-package typecheck outside the frontend workspace
- Coverage thresholds, mutation testing, or snapshot goldens unless already present in existing Brain tests
- Auto-fix / write-back of catalogs or types

## Requirements

This ticket is **step 4 of epic #2555** (PRD 29 verify-and-package). The product is a **frontend-package quality gate**, not new UI. Downstream implementers MUST reuse the existing frontend scripts and catalogs below; they MUST NOT invent a second i18n library, a second typechecker, or Brain product surface.

**Package root:** `frontend/` (`builderforce-frontend`). All scripts in this contract are invoked from that directory. Sibling packages (`packages/brain-ui`, `brain-embedded`, `api`, `clients/vscode`) are **out of this ticket** — they are #2557, #2556, #2558, #2560.

**Fix policy (inherited from #2555):** mechanical breakage only (imports, composing-phase exhaustive Records, catalog keys, stale test literals). Do not patch real logic defects — report them as named failures. Leave concurrent dirt (benchmarking, investor, identity, creation-canvas, ROADMAP) alone.

### R-1 — Typecheck (hard fail)

**Canonical script already in repo:** `pnpm type-check` → `node ../scripts/run-checks.mjs scripts/typecheck.manifest.mjs`.

That manifest runs **both** `tsgo --noEmit` and `tsc --noEmit` concurrently against the frontend `tsconfig` graph. `typecheck:native` (`tsgo --noEmit` only) is **not** the gate.

| ID | Requirement |
| --- | --- |
| R-1.1 | The typecheck step SHALL invoke the existing `type-check` path (both checkers, `--noEmit`). It SHALL NOT emit JS / `.next` / build artifacts. |
| R-1.2 | A first-class `tsc` / `tsgo` diagnostic SHALL be printed; errors MUST NOT be swallowed. Composite gate exit is non-zero when either checker fails. |
| R-1.3 | Existing path aliases, `strict` flags, and `skipLibCheck` SHALL be honored. The gate MUST NOT loosen compiler options. |
| R-1.4 | If the PRD-named script `typecheck` is added, it SHALL be an alias of `type-check`, not a third checker. Do not replace the concurrent runner with a serial `tsgo && tsc` chain (that hid `tsc` output). |

**Given** a TypeScript error in `frontend/src`, **when** the typecheck step (or `check:frontend`) runs, **then** it exits non-zero and prints the compiler diagnostic.

### R-2 — i18n catalog guard (hard fail, read-only)

next-intl catalogs live at `frontend/src/i18n/messages/{en,de,es,fr,zh}.json`. **`en.json` is canonical.** The four non-source locales MUST match `en` in key set (and ICU plural/select variants required by next-intl).

Two complementary guards **already exist** and MUST both be part of `i18n:guard`:

1. **Source → catalog** — `pnpm check:i18n-keys` (`scripts/check-i18n-keys.mjs`): every `t('…')` / `t.rich` / `t.raw` / `t.markup` (and static prefix of dynamic `t(\`ns.${suffix}\`)`) rendered from `frontend/src/**/*.ts(x)` (excluding `*.test.ts(x)`) resolves in `en.json`. `t.has()` is a probe and is not checked.
2. **Catalog → catalog** — Vitest `frontend/src/i18n/messages.test.ts` (and `catalog.test.ts` if it is part of the same parity contract): non-`en` locales have **exactly** the keys `en` has; every message's ICU parses.

| ID | Requirement |
| --- | --- |
| R-2.1 | `i18n:guard` SHALL run both guards. Passing only `check:i18n-keys` (en-only) is insufficient: that can go green while `messages.test.ts` is red. |
| R-2.2 | Fail if a canonical key is **missing** from any non-`en` locale. Name the locale and the key. |
| R-2.3 | Fail if a locale has an **extra / orphaned** key not in `en`. Name the locale and the key. |
| R-2.4 | Fail if catalogs diverge in nesting or in plural/select variants required by next-intl. |
| R-2.5 | Empty string values in non-source locales SHALL fail **unless** `messages.test.ts` / `catalog.test.ts` already documents an allowlist. Honor that allowlist; do **not** invent a new one. |
| R-2.6 | The guard MUST be deterministic (same tree → same result), MUST NOT mutate catalog files, and MUST NOT require network. The `scripts/i18n-patch-*.mjs` write-backs are **out of scope** for this gate. |
| R-2.7 | Failure output SHALL group failing keys by locale and failure type (`missing`, `extra`, `empty`). |

**Given** a key present in `en.json` and absent from `de.json`, **when** `i18n:guard` (or `check:frontend`) runs, **then** it exits non-zero and names `de` and the key.

**Given** an orphaned key in any locale, **when** the guard runs, **then** the same class of failure occurs.

### R-3 — Conditional Vitest for frontend Brain components

This ticket covers **frontend** Brain **component unit tests only**. `packages/brain-ui` tests (`TicketParentLine.test.tsx`, `LiveActivity.test.ts`, `pnpm test` then dist) are **#2557**, not this ticket. `brain-embedded` is **#2556**.

**Presence detection (frontend tree only), first match wins:**

- `frontend/src/**/*[Bb]rain*.test.{ts,tsx}`
- `frontend/src/**/brain/**/*.{test,spec}.{ts,tsx}`
- colocated `*.test.{ts,tsx}` next to a `Brain*.tsx` component under `frontend/src`

Known frontend Brain-adjacent sources (not tests): `src/components/BrainBackdrop.tsx`, `src/app/brainstorm/BrainstormCanvasRedirect.tsx`, `src/i18n/useBrainTimelineLabels.ts`. As of authoring, **no matching frontend Brain component test glob was found**; the skip path is therefore the expected happy path until tests appear.

| ID | Requirement |
| --- | --- |
| R-3.1 | If any detection glob matches: run Vitest **in that scope only**, using the frontend Vitest config already in the repo (jsdom/happy-dom, path aliases, setup files). `NODE_OPTIONS=--max-old-space-size=8192` matches the existing `test` script. |
| R-3.2 | If none match: skip Vitest, print **one** explicit skip reason (e.g. `skip: no frontend Brain component tests`), and exit **0** for this step. Missing Brain tests MUST NOT fail `check:frontend`. |
| R-3.3 | Do **not** add new Brain components or tests. If existing tests are broken **by the gate's invocation** (wrong glob, missing config), fix the invocation — not product behavior. |
| R-3.4 | Tests MUST be unit/component only (render, props, i18n wiring, user events). No network, no live backend. A failing assertion fails this step and the composite gate. |
| R-3.5 | Do **not** run the full frontend Vitest suite (`pnpm test` = all ratchets + all tests). That is heavier than this epic step. |

**Given** no matching Brain test files, **when** `test:brain` runs, **then** it prints a skip reason and exits 0.

**Given** at least one matching test whose assertion fails, **when** `test:brain` (or `check:frontend`) runs, **then** it exits non-zero.

### R-5 — User stories

- **As a CI / platform engineer**, I invoke `pnpm check:frontend` from `frontend/` as a single, network-free CI step so epic #2555 can fail fast on type or catalog drift without running the full frontend suite or sibling packages.
- **As a frontend engineer**, I see raw `tsc`/`tsgo` diagnostics when types drift, and I am not blocked by missing Brain tests that this package does not ship.
- **As a localization owner**, a missing, extra, or empty key in `de`/`es`/`fr`/`zh` fails the gate with locale + key + failure type, without anyone mutating catalogs as a side effect of the check.
- **As a downstream coding agent**, I have one contract: reuse `type-check` + `check:i18n-keys` + `messages.test.ts`; add only the thin `test:brain` skip wrapper and the `check:frontend` composite; do not redesign Brain UI.
