Once verified, update the marketplace row in `ROADMAP.md` from `Partial — awaits Stripe secrets` to `Available`.

## Target Users / ICP Roles

- **Marketplace buyers:** Purchase creation listings and workforce agents with real payment.
- **Sellers/creators:** Receive the seller allocation recorded after a successful purchase.
- **Platform operators/release agents:** Bind secrets, deploy the Worker, register Stripe webhooks, and verify end-to-end behavior.
- **Finance/platform operators:** Validate seller and platform ledger allocations for live transactions.

## Functional Requirements

### FR-1 — Bind and activate Stripe configuration

1. Bind `STRIPE_SECRET_KEY` and `STRIPE_WEBHOOK_SECRET` to the Worker serving production and staging.
2. Map the bindings to the actual environment names defined by the repository’s deployment configuration.
3. Ensure the production secret key is a valid live-mode key and the production webhook secret is the signing secret associated with the production webhook endpoint.
4. Deploy or roll out the Worker after binding so the active Worker version loads the secrets.
5. Verify through secret metadata and a checkout attempt that both secret names are present without retrieving or exposing their values.
6. Confirm paid checkout no longer returns `Payments are not configured on this deployment`.

If the existing seller-payout implementation depends on Stripe Connect, bind `STRIPE_CONNECT_CLIENT_ID` in each applicable environment and use a valid connected seller account for verification.

Do not set `MARKETPLACE_TAKE_RATE_BPS` or `MARKETPLACE_TAKE_RATE_THRESHOLD_CENTS` unless an approved deployment is intentionally departing from the defaults of `1500` basis points and `20000000` cents.

### FR-2 — Register the production Stripe webhook

1. Register `https://api.builderforce.ai/api/webhooks/payment` in the Stripe account used by production.
2. Configure the endpoint to receive:
   - `checkout.session.completed`
   - Every additional Stripe event type consumed by `StripeProvider.parseWebhook` in the current `main` branch.
3. Use the endpoint’s Stripe signing secret as the production `STRIPE_WEBHOOK_SECRET`.
4. Confirm Stripe can deliver a test event and that the endpoint verifies the signature and returns a successful response.
5. If staging uses a distinct public API hostname, register the equivalent staging endpoint and event set with its environment-appropriate signing secret.
6. Treat `listing.purchased` and `knowledge.purchased` as internal fulfillment outcomes unless the current parser explicitly consumes them as Stripe event types; they do not replace the required Stripe subscriptions.

### FR-3 — Complete the live creation-listing proof

Using a buyer account distinct from the seller:

1. Select or create an eligible paid creation listing through the shipped listing-commerce path.
2. Create and complete a real Stripe checkout session.
3. Confirm Stripe reports the checkout and payment as successful.
4. Verify that the purchase grants the expected persisted entitlement.
5. Verify that fulfillment creates the expected seller allocation and platform-fee allocation in the ledger.
6. Confirm the ledger amounts reconcile with the gross purchase and the effective marketplace take-rate policy.

### FR-4 — Complete the live workforce-agent proof

Repeat the end-to-end validation through `agentCommerce.ts`:

1. Complete a real Stripe checkout for a paid workforce agent.
2. Confirm successful Stripe payment state.
3. Verify the expected entitlement is persisted and usable.
4. Verify both seller and platform ledger allocations are written.
5. Confirm ledger amounts reconcile with the implemented marketplace allocation rules.

### FR-5 — Prove webhook-driven fulfillment

For both validation purchases:

1. Close or terminate the buyer’s browser tab after Stripe accepts payment but before the application’s return-page success flow can confirm fulfillment.
2. Do not invoke fulfillment manually.
3. Verify from Stripe delivery logs that the relevant webhook event was delivered and received a successful response.
4. Sign in from a new browser session after the webhook has processed.
5. Verify the entitlement and ledger rows exist without relying on the closed tab or checkout redirect.
6. Verify webhook retries do not create duplicate logical entitlements, seller allocations, or platform allocations.

### FR-6 — Handle a discovered webhook miswire

If live verification reveals that the registered Stripe event, request handling, signature verification, or event-to-fulfillment mapping is incorrect:

- Make the smallest fix that connects the existing checkout code to the correct webhook path.
- Add or update a focused regression test for the corrected event mapping.
- Deploy the fix to the affected environment.
- Repeat both live proofs before marking the roadmap item available.

No unrelated checkout, pricing, entitlement, or ledger redesign is authorized.

### FR-7 — Update the roadmap

After all live acceptance checks pass, change the relevant `ROADMAP.md` row from:

to:

Link the verification evidence to Epic #3059 or its delivery PR. If any required proof fails, leave the row unchanged and report the remaining blocker.

## Acceptance Criteria

1. **Required secrets are active**
   - Production and staging each have `STRIPE_SECRET_KEY` and `STRIPE_WEBHOOK_SECRET` bound to the Worker.
   - The active deployment loads the bindings.
   - Production uses live-mode Stripe credentials.
   - No paid path reports `Payments are not configured on this deployment`.

2. **Webhook registration is correct**
   - `https://api.builderforce.ai/api/webhooks/payment` is active in Stripe.
   - Its subscription includes `checkout.session.completed` and the complete event set handled by `StripeProvider.parseWebhook`.
   - A signed Stripe test delivery is accepted successfully.
   - The production signing secret matches the Worker binding.

3. **Creation-listing purchase passes**
   - A real paid creation-listing checkout reaches successful payment state.
   - The expected entitlement is persisted.
   - One logical seller allocation and one logical platform-fee allocation are written.
   - The allocations reconcile to the effective take-rate policy.

4. **Workforce-agent purchase passes**
   - A real paid workforce-agent checkout reaches successful payment state.
   - The expected entitlement is persisted.
   - One logical seller allocation and one logical platform-fee allocation are written.
   - The allocations reconcile to the effective take-rate policy.

5. **Fulfillment is tab-close resilient**
   - Both purchases fulfill after the buyer closes the checkout tab.
   - A fresh session can access each entitlement.
   - Stripe shows successful webhook delivery.
   - Retries do not duplicate fulfillment or ledger allocations.

6. **Evidence is sufficient**
   - The delivery record includes redacted Stripe checkout/session and webhook event identifiers, timestamps, entitlement identifiers, ledger entry identifiers and amounts, and confirmation of successful webhook delivery.
   - No secret values or payment-card data are included.

7. **Roadmap status is released**
   - `ROADMAP.md` shows `Available` for the marketplace row.
   - The change is linked to Epic #3059.

## Out of Scope

- New payment providers, checkout providers, or payment methods.
- New marketplace listing types, agent types, entitlements, or ledger models.
- Live purchase validation for knowledge products or hosted apps beyond confirming that configuration no longer blocks their paid paths.
- Redesigning checkout, redirect handling, webhook architecture, or ledger calculations.
- Changing the default 15% take rate or `$200,000` threshold without separate approval.
- Broad Stripe Connect onboarding work beyond enabling and validating the existing payout path.
- Subscriptions, usage billing, taxes, coupons, disputes, or installment payments.
- Building a new refund or reconciliation product; only approved cleanup of validation transactions is included.
- Unrelated application or roadmap changes.
