# PRD — Close CC6 Tenant-Isolation Gaps in Builderforce

## Problem & Goal

Builderforce cannot attest SOC 2 Type I Security TSC CC6 while its own tenant data-access layer allows unscoped tenant queries and segmented writes. The current baseline includes approximately:

- 271 unscoped tenant query sites tracked under `ROADMAP.md` Identity.
- 35 insert sites missing `segmentId`.
- No Postgres row-level security or equivalent database enforcement.
- No automated no-bleed test for segmented mode.
- A segmented mode that is not operationally usable.

The goal is to enforce tenant and segment isolation in the Builderforce application and database so that one tenant or segment cannot access another tenant’s or segment’s records, including when application-level filters are omitted or bypassed.

This work is a Builderforce control-design remediation. The product SOC 2 tracker may record evidence, but it is not the isolation control and must not be treated as the implementation.

## Target Users / ICP Roles

| Role | Need |
| --- | --- |
| Builderforce tenant users | Access only data belonging to their tenant and authorized segment. |
| Segment-scoped users | Read and modify only records within their active segment. |
| Tenant administrators | Perform explicitly authorized tenant-level operations without granting implicit cross-segment access. |
| Application and data engineers | Use a consistent, auditable mechanism for scoping queries and propagating tenant context. |
| Background-job and integration operators | Execute work with explicit tenant/segment context rather than shared privileged access. |
| Security and compliance reviewers | Inspect table coverage, query inventory, database policies, test evidence, and approved exceptions. |
| SOC 2 auditors | Evaluate evidence that logical access is enforced at both application and database layers. |

## Scope

### In scope

- Inventory and remediation of all tenant-bearing query sites, including reads, writes, joins, aggregates, counts, pagination, search, existence checks, raw SQL, ORM calls, and administrative paths.
- Population and validation of `tenantId` and, where applicable, `segmentId` on writes.
- Database-enforced isolation on tenant-bearing tables using Postgres RLS or an equivalently strong database mechanism.
- Tenant and segment context propagation through HTTP requests, server actions, jobs, webhooks, and other data-access paths.
- Safe enablement and validation of segmented mode, including migration or fail-closed handling of existing records.
- Automated tenant- and segment-isolation tests using a real Postgres-compatible database.
- A maintained inventory of tables, query sites, policies, and residual exceptions.
- A CC6 evidence note for Builderforce’s own tenant.

### Access-model definitions

- **Tenant:** The top-level customer or account boundary.
- **Segment:** An optional subdivision within a tenant. Segmented mode binds normal requests to one authorized segment.
- **Tenant table:** Any table or database object containing tenant-owned records.
- **Segmented table:** A tenant table whose records are additionally partitioned by `segmentId`.
- **Tenant-wide table:** A tenant table whose records are intentionally visible across segments within the same tenant, with this classification explicitly documented.
- **Global table:** Data containing no tenant-owned records and explicitly classified as non-tenant data.

## Functional Requirements

### FR-1 — Tenant and segment context

1. Every data-access operation must derive `tenantId` from authenticated server-side context.
2. In segmented mode, the server must resolve and validate the active `segmentId` against the tenant before accessing data.
3. Client-supplied tenant or segment identifiers must not override authenticated context. Cross-segment access requires a separately authorized administrative flow.
4. Tenant and segment context must propagate consistently through nested service calls, transactions, background jobs, webhooks, and batch operations.
5. Missing, malformed, or unauthorized context must fail closed for tenant data access.

### FR-2 — Scoped query enforcement

1. Every query against a tenant table must constrain `tenantId`; segmented tables must also constrain `segmentId`.
2. Filtering must cover all operation types, including `SELECT`, `INSERT`, `UPDATE`, `DELETE`, joins, subqueries, aggregates, counts, pagination, search, and raw SQL.
3. Cross-tenant and cross-segment joins must not be possible through unscoped relationship paths.
4. Query construction should use a centralized scoping mechanism where practical, with direct SQL still subject to the same requirements.
5. The approximately 271 query sites identified in the ROADMAP baseline must be reconciled against source code and either remediated or classified as non-tenant-bearing.

### FR-3 — Scoped write enforcement

1. Every insert into a tenant table must populate `tenantId` from trusted server context.
2. Every insert into a segmented table must populate `segmentId` from trusted segment context.
3. Updates and deletes must include tenant and segment predicates as applicable.
4. Writes containing a missing, mismatched, or unauthorized tenant or segment identifier must be rejected.
5. Database write policies must prevent a valid scoped session from creating or modifying another tenant’s or segment’s records.
6. The approximately 35 insert sites missing `segmentId` must be reconciled and remediated or documented as belonging to non-segmented tables.

### FR-4 — Database-enforced isolation

1. All tenant-bearing tables must be protected by Postgres RLS or an equivalent database control that cannot be bypassed by the ordinary Builderforce application role.
2. Database policies must enforce:
   - Tenant equality for tenant tables.
   - Tenant and segment equality for segmented tables.
   - Tenant-only access for explicitly classified tenant-wide tables.
3. Where RLS is used:
   - Policies must cover reads and writes.
   - Insert/update checks must prevent cross-boundary writes.
   - The application role must not own protected tables and must not have `BYPASSRLS` or equivalent privilege.
   - Transaction-scoped context must be reset safely when using connection pooling.
4. An absent tenant or segment context must produce no tenant rows or an explicit database error; it must never fall back to unrestricted access.
5. Privileged maintenance, migration, and break-glass roles must be separate from the application role and their use must be documented and auditable.
6. Any views, functions, or other database objects that expose tenant rows must inherit or preserve the same isolation guarantees.

### FR-5 — Usable segmented mode

1. Segmented mode must be selectable and operational for normal tenant workflows rather than merely configurable.
2. Standard create, read, update, delete, list, search, count, and relationship workflows must function within the active segment.
3. Existing records must be assigned an appropriate segment through migration/backfill or quarantined in a fail-closed manner before segmented mode is considered active.
4. A tenant-wide record that is intentionally shared across segments must be explicitly classified and must not weaken segment isolation for segment-owned records.
5. The existing unsegmented behavior must continue to work for tenants that do not enable segmented mode.

### FR-6 — Isolation inventory and regression prevention

1. Maintain an inventory containing each tenant table, segmented/tenant-wide/global classification, policy or equivalent control, and owning service.
2. Maintain a source-level inventory of tenant query and write sites, including their scope status and remediation reference.
3. Residual unscoped sites must contain a specific classification, rationale, owner, review date, and any compensating control. Actual tenant-bearing sites without enforced scope are not acceptable residuals.
4. CI must detect newly introduced unscoped tenant queries or missing scoped write fields, or an equivalent repeatable check must prevent regressions.
5. Inventory counts in `ROADMAP.md` must be updated to reflect the reconciled state rather than retaining stale estimates.

### FR-7 — Automated no-bleed testing

1. Add automated integration tests against a real Postgres-compatible test database; mocks alone are insufficient.
2. Tests must create at least two tenants and two segments within the same tenant and cover the read/write isolation matrix.
3. Tests must prove that Segment A cannot read Segment B records through normal application paths and through the ordinary database role with application filters omitted.
4. Tests must also cover cross-tenant isolation, missing context, mismatched context, pooled connections, and successful same-segment access.
5. The no-bleed test must run in CI and retain machine-readable output or a durable test-run artifact.

### FR-8 — CC6 evidence

1. Attach an evidence note to the relevant `soc_controls` CC6.x record for Builderforce’s own tenant.
2. The note must identify the implementation and database-migration version, covered table classes, policy mechanism, inventory location, no-bleed test, CI run, and any approved exceptions.
3. Evidence must include the commit or release identifier and the environment in which the control is enforced.
4. Evidence must not claim active database enforcement until the corresponding migration or equivalent control is applied in that environment.
5. Evidence artifacts must exclude credentials, sensitive tenant data, and personal data.

## Acceptance Criteria

- **AC-1 — Query inventory reconciled:** Every baseline query and insert site is accounted for. The committed inventory contains no unreviewed tenant-bearing site, and actual tenant queries are scoped by `tenantId` and by `segmentId` where required.
- **AC-2 — Writes scoped:** All tenant inserts populate `tenantId`; all segmented-table inserts populate a trusted `segmentId`; scoped updates and deletes cannot affect another tenant or segment.
- **AC-3 — Database enforcement present:** Every tenant-bearing table has an active RLS policy or documented equivalent database enforcement. The ordinary application role cannot bypass it, and missing context fails closed.
- **AC-4 — No segment bleed:** A passing automated test proves that Segment A cannot read Segment B records in the same tenant, including when the test uses the ordinary database role directly. The reverse direction is also covered.
- **AC-5 — Cross-tenant isolation:** Automated tests prove that one tenant cannot read or modify another tenant’s records, including through joins, aggregates, pagination, and background-processing paths included in scope.
- **AC-6 — Segmented mode usable:** Standard segmented workflows pass in CI, legacy data is safely segmented or quarantined, and unsegmented tenants retain existing behavior.
- **AC-7 — Pooling and context safety:** Tests prove that tenant/segment context does not leak between requests or transactions on reused database connections.
- **AC-8 — Regression prevention:** CI prevents introduction of an unscoped tenant query or missing scoped write field, and the existing automated test suite passes.
- **AC-9 — Evidence attached:** The relevant `soc_controls` CC6.x record contains a reviewed evidence note for Builderforce’s own tenant with links or durable references to the inventory, database controls, implementation revision, and passing no-bleed test.
- **AC-10 — Tracker is not the control:** Implementation exists in Builderforce’s application and database layers; the SOC 2 tracker only records or references the operating control.

## Out of scope

- Remediating unrelated SOC 2 controls or controls outside logical access and tenant isolation.
- Using the product SOC 2 tracker as a substitute for application or database enforcement.
- Redesigning Builderforce’s broader authentication or authorization product.
- New customer-facing cross-segment collaboration features beyond explicitly authorized administrative flows.
- Encrypting tenant data, rotating credentials, or implementing unrelated security-hardening work.
- Broad data-model cleanup unrelated to assigning, validating, or enforcing `tenantId` and `segmentId`.
- Providing unrestricted tenant-wide access to background jobs, support tooling, or administrative scripts; any elevated path must be explicit and auditable.
