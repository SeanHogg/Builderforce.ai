# WIP PRD: End-to-End QA for Synapse Discovery and Model Installation

## Problem & Goal

Builderforce’s Synapse discovery and Model-tab installation flow lack end-to-end release confidence. Regressions may surface only when connected to a live Synapse service, when authentication fails, or when installation fails after discovery succeeds.

The goal is to validate the complete user journey from endpoint discovery through model installation using deterministic mock Synapse endpoints and, where test credentials are available, a real Synapse environment. Testing must confirm successful behavior, correct error handling, absence of false-success states, and protection of credentials.

Success means the primary flow is demonstrably repeatable and release-blocking defects are identified with reproducible evidence.

## Target Users / ICP Roles

- **QA engineers:** Execute the end-to-end suite, maintain test fixtures, and report defects.
- **Frontend and backend engineers:** Use failure evidence to diagnose discovery, authentication, and installation issues.
- **Release owners:** Use the completed test matrix and defect summary to make the release decision.
- **Builderforce users:** Users who connect an authorized Synapse endpoint and install models from the Model tab are the affected end-user persona.

## Scope

### In Scope

- End-to-end Synapse discovery using:
  - A controllable mock Synapse endpoint with the supported response contract.
  - A real Synapse endpoint when valid, non-production test credentials are available.
- Validation of the Model tab after discovery:
  - Model catalog population.
  - Installable and non-installable state presentation.
  - Installation action, progress state, completion state, and persistence after refresh.
- Authentication and authorization failures:
  - Missing credentials.
  - Invalid or expired credentials.
  - Insufficient permissions.
  - Authentication expiry between discovery and installation.
- Operational failures:
  - Unreachable endpoint.
  - Timeout.
  - Invalid response payload.
  - Discovery and installation server errors.
- Duplicate-install and repeated-action behavior.
- Request verification, including method, route, model identifier, and authentication handling under the existing API contract.
- Redaction of credentials from logs, screenshots, reports, and committed test artifacts.
- Automated tests using the repository’s existing end-to-end test conventions, plus a documented real-environment smoke test.

### Test Environment

- Tests must run from the repository’s `main` baseline or an equivalent branch containing only the intended QA changes.
- Mock responses and fixtures must be deterministic and versioned with the tests.
- Real-endpoint configuration and credentials must be supplied through ignored environment variables or CI secrets.
- Real installation tests must use an approved test tenant and designated test model.
- The mock must exercise the full application path, including the backend or proxy layer when the production flow uses one.

### Deliverables

- Repeatable mock-backed end-to-end tests.
- A real-environment smoke-test procedure and result record.
- A test matrix covering success, authentication failure, and operational failure paths.
- Defect reports containing sanitized reproduction steps, expected behavior, actual behavior, and evidence.
- A concise release-readiness summary listing executed, passed, failed, blocked, and skipped checks.

## Functional Requirements

### Discovery

1. **FR-DISCOVERY-01 — Existing discovery contract is preserved.**  
   The application must use its existing endpoint configuration and discovery mechanism; QA must not introduce a parallel user flow.

2. **FR-DISCOVERY-02 — Successful mock discovery.**  
   Given a healthy mock Synapse endpoint, triggering discovery must produce a successful response and display the models defined by the supported response contract in the Model tab.

3. **FR-DISCOVERY-03 — Successful real discovery.**  
   Given a reachable real Synapse endpoint and valid credentials, discovery must return and display the available test models without exposing credentials.

4. **FR-DISCOVERY-04 — Model identity and state.**  
   Each discovered model must retain its identifier and display metadata, including its current installation state where provided by the existing contract.

5. **FR-DISCOVERY-05 — Authentication failure.**  
   A `401` or equivalent missing/invalid authentication response must produce an authentication-specific error state. The application must not present the response as a successful empty catalog and must not enable installation.

6. **FR-DISCOVERY-06 — Authorization failure.**  
   A `403` or insufficient-permission response must produce a permission-specific error state distinct from endpoint unavailability.

7. **FR-DISCOVERY-07 — Endpoint and payload failure.**  
   Unreachable endpoints, timeouts, malformed payloads, and server errors must produce a visible, actionable failure state without an uncaught client error or false success.

8. **FR-DISCOVERY-08 — Retry behavior.**  
   If the existing UI provides a retry action, it must issue a new discovery request and recover when the endpoint becomes healthy. Automatic retries must remain bounded.

### Model Installation

9. **FR-INSTALL-01 — Install eligible model.**  
   From a successfully discovered catalog, a user must be able to initiate installation of an eligible model using the existing Model-tab control.

10. **FR-INSTALL-02 — Correct installation request.**  
    The installation request must target the supported install route and include the selected model identifier and required authentication context.

11. **FR-INSTALL-03 — Progress and duplicate prevention.**  
    While installation is pending, the selected action must not be submitted repeatedly. The UI must prevent or clearly resolve a second install request for the same model.

12. **FR-INSTALL-04 — Confirmed success.**  
    Installation must be marked successful only after the server confirms completion. The Model tab must show the installed state and disable or replace the install action as required by the existing design.

13. **FR-INSTALL-05 — Persistence.**  
    A confirmed installation must remain represented as installed after page refresh or application restart.

14. **FR-INSTALL-06 — Installation failure.**  
    A server, network, timeout, or malformed-response failure during installation must leave the model in a non-installed state, display an actionable error, and never report success.

15. **FR-INSTALL-07 — Authentication expiry during installation.**  
    If credentials expire after successful discovery, installation must handle the authentication failure explicitly, clear or disable invalid authentication state, and allow the user to recover through the existing authentication flow.

16. **FR-INSTALL-08 — Error recovery.**  
    A failed installation must not corrupt the discovered catalog. Where the existing UI provides retry, selecting it must issue a fresh installation request rather than reusing stale terminal state.

### Evidence and Security

17. **FR-EVIDENCE-01 — Observable test evidence.**  
    Each automated test must assert both the user-visible state and the relevant request behavior. Relevant application logs may be collected but must be redacted.

18. **FR-EVIDENCE-02 — Secret protection.**  
    Tokens, authorization headers, credentials, and sensitive endpoint details must not appear in committed files, console output, screenshots, videos, or defect reports.

19. **FR-REPORT-01 — Actionable defects.**  
    Every failed critical-path check must have a defect or an explicitly accepted release risk, with reproducible steps and environment details.

## Acceptance Criteria

| ID | Scenario | Expected Result |
|---|---|---|
| AC-01 | Trigger discovery against a healthy mock Synapse endpoint. | Discovery succeeds, the Model tab displays expected models, and no error state appears. |
| AC-02 | Trigger discovery against a real Synapse endpoint using valid test credentials. | The available test models are discovered and rendered with no credential disclosure. |
| AC-03 | Discovery returns `401`, missing credentials, or an expired token. | A clear authentication error appears; the catalog is not treated as successfully loaded; installation is unavailable. |
| AC-04 | Discovery returns `403` or lacks the required scope. | A permission error appears and is distinguishable from authentication or endpoint failure. |
| AC-05 | The endpoint is unreachable, times out, returns malformed data, or returns `5xx`. | Discovery fails visibly and safely; there is no false success, uncaught exception, or infinite retry loop. |
| AC-06 | Install a known eligible model from the mock-discovered catalog. | One valid installation request is sent; progress is shown; confirmed completion updates the model to installed. |
| AC-07 | Reload after a confirmed installation. | The model remains installed. |
| AC-08 | Installation returns a server or network failure. | The model is not marked installed, an actionable error appears, and the catalog remains usable. |
| AC-09 | Authentication expires between discovery and installation. | Installation fails with an authentication-specific state and does not report success. |
| AC-10 | The install control is activated repeatedly or installation is requested twice concurrently. | Only the intended installation is accepted or the duplicate is safely handled. |
| AC-11 | The mock endpoint recovers after a transient failure and retry is invoked. | Discovery or installation can recover without a full restart where retry is supported. |
| AC-12 | Inspect test artifacts, logs, network evidence, and defect reports. | No credentials, authorization headers, or sensitive tokens are present. |
| AC-13 | Run the complete mock-backed suite from a clean checkout using documented commands. | The suite is deterministic, repeatable, and integrated with the repository’s existing test tooling. |
| AC-14 | Execute the real-endpoint smoke test without credentials or a reachable approved endpoint. | The check is recorded as blocked with the missing prerequisite, not silently skipped or reported as passed. |
| AC-15 | Review release-readiness results. | There are no unresolved critical or high-severity defects in discovery or installation, and remaining risks have explicit owner approval. |

## Out of Scope

- Designing or redesigning the Model tab, discovery flow, authentication flow, or installation workflow.
- Introducing new Synapse API contracts or changing endpoint routes solely for QA.
- Testing model inference quality, output accuracy, runtime performance, or model-specific behavior beyond confirming installation state.
- Load, stress, soak, or high-concurrency testing beyond duplicate-action protection.
- Exhaustive browser, device, locale, or accessibility audits unrelated to the tested flow.
- Penetration testing or a full security assessment.
- Installing models in production or shared environments without explicit approval.
- Uninstall, upgrade, version rollback, or model lifecycle management unless required to clean up an approved test installation.
- Deployment, infrastructure provisioning, or repair of external Synapse services.
- Refactoring unrelated application code; product-code fixes must be separately scoped and reviewed.
