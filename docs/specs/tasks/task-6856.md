# W3 PRD: List-only surfaces gain Card via Collection

## Problem & Goal

Many product surfaces are still one-off lists. They do not share Card|List, selection, sort, or paging with the Collection contract from PRD 47, and several entities that the bulk matrix marks Delete / Archive / Merge (or a named custom bulk op) have no server port.

Goal: migrate every W3 list-only surface onto the shared `<Collection>` through a descriptor, so each gains Card and List (table where noted), column sort, and server paging as `Page<T>`. Add the missing bulk ports in the same pass. Show selection and the bulk bar only where a port exists. All other W3 surfaces are read-only Card|List. Do not fork Collection or the W0 contract.

Depends on W0 and W1. Read `Builderforce.ai/docs/specs/47-prd-collection-view.md` (including §5 W3 and the bulk matrix) before editing. Shared `Page<T>`, `PageQuery`, and bulk request types stay in the interaction contract package under `Builderforce.ai/packages/`. UI lives under `Builderforce.ai/frontend/src/components` and `Builderforce.ai/frontend/src/app`.

## Target users / ICP roles

- Alert triagers, knowledge and fact curators, RFP owners, incident owners, and replay reviewers who need bulk Delete, Archive, Merge, or the named custom ops on the current page selection.
- Managers and PMs scanning blocked-PR and stall registers, rollups, ROI, and epic trees.
- Security and compliance reviewers of the workspace audit log, SOC2 automation, vulnerability findings, and scans.
- Finance, sales, tenant admins, builders, and kernel users who only need a consistent Card|List with sort and paging.
- Workforce and task viewers of employee metrics and accountability.

Bulk actions are tenant-scoped. A user without a port for that entity never sees selection or a bulk bar.

## Scope

In scope for this wave:

- Descriptor migration of the surfaces below onto the existing `<Collection>`.
- Server list endpoints for those surfaces accept `PageQuery` and return `Page<T>` in the same change.
- New bulk ports only where the PRD 47 matrix has D, A, and/or M, or this wave names a custom op, and no port exists yet.
- Allowlist update plus frontend type-check, lint, tests, and guards.

### Bulk ports to add

Copy D/A/M from the PRD 47 matrix. Do not invent an operation the matrix does not mark. This wave explicitly requires:

- alert, fact, rfp, ceremonySchedule: the matrix D/A/M cell, one port each, if none exists.
- knowledgeDoc: Delete, and Archive persisted as `archived_at`.
- incident: duplicates-merge only, as specified by the matrix for that entity.
- recording: Delete.
- meeting-cancel: cancel bulk op, not a generic D/A/M stand-in.
- template: custom-only bulk op. No generic Delete, Archive, or Merge.
- humanRequest: already shipped in W2. Verify the port and descriptor; do not reimplement.

## Functional requirements

1. Each in-scope list renders only through `<Collection>` and a descriptor. No parallel hand-rolled table, card grid, pager, or sort header remains on that surface.
2. Card and List both ship. EpicTreeView and the finance lists use Collection table mode for the list side. Mode switches do not drop sort, page size, or selection.
3. Header and footer stay fixed. Only rows or cards scroll. Page sizes are 50, 100, and 250, from the shared control, not a local pager.
4. Column sort is descriptor-driven and round-trips through `PageQuery` on the server. Client-only sort of a partial page is not accepted.
5. Alerts and facts keep their existing server paging and adopt the `Page<T>` response. Do not add a second pager.
6. Every backing list endpoint accepts `PageQuery` and returns `Page<T>` in this same change, including tenant scope already required by that endpoint.
7. `ManagerContent` stops owning the blocked-PR and stall lists. Those registers each have their own descriptor (`ManagerBlockedPrs`, `ManagerStallRegister`). The split is limited to those two registers. Target is removing that collection hosting from the 1,138-line component, not a rewrite of unrelated manager UI.
8. `RecordingsTable` and `RecordingsList` share one recording descriptor and one data path. Both entry points render that Collection. Delete uses the recording port.
9. Selection, select-all, and the bulk bar mount only when that descriptor has a port. Read-only surfaces have no checkbox column and no bulk bar, including audit, finance, heatmap, funnels, API-key usage, and the other rows marked read-only above.
10. Select-all applies to the current page, matching the W0 Collection contract, not an unbounded tenant-wide select.
11. Each bulk action is one server request carrying the selected ids and tenant. No client loop of single-item calls. Delete, Archive, Merge, duplicates-merge, meeting-cancel, and template custom-only are the only ops, and only on the entities listed above.
12. knowledgeDoc Archive sets `archived_at`. It does not use a parallel archive flag.
13. Register every migrated W3 surface id on the W0 collection allowlist. A surface not on the allowlist must fail the existing guard if it mounts Collection.
14. Empty, loading, and error states come from Collection. A failed bulk request leaves the list unchanged and surfaces the server error; it does not apply a partial client update.

## Acceptance criteria

- Every surface in the table, plus the §5 surfaces for incident, ceremonySchedule, meeting-cancel, and template, renders Card and List through `<Collection>` with working column sort and server paging at 50, 100, and 250.
- Alerts and facts still page on the server and now consume `Page<T>`. No duplicate paging UI.
- List endpoints used by these surfaces accept `PageQuery` and return `Page<T>`.
- `ManagerBlockedPrs` and `ManagerStallRegister` are separate descriptors. `ManagerContent` is no longer the collection host for those registers.
- Recordings have one descriptor. Delete is available there and hits the recording port once per bulk action.
- knowledgeDoc bulk Delete works, and Archive sets `archived_at`.
- incident duplicates-merge, meeting-cancel, and template custom-only exist as specified, and template has no generic D/A/M.
- alert, fact, rfp, and ceremonySchedule ports match the matrix and are wired only to their own descriptors.
- humanRequest is unchanged from W2 except for a regression check.
- Read-only surfaces have sort and paging, and no selection column or bulk bar.
- A bulk call with ids plus tenant is a single request. Cross-tenant ids are rejected by the server.
- Allowlist includes all W3 surface ids. Frontend type-check, lint, tests, and guards pass.
- No new Collection implementation and no change to page-size options or the shared bulk request shape.

## Out of scope

- W0/W1 Collection, `Page<T>`, `PageQuery`, and bulk-contract redesign.
- Reimplementing humanRequest or any W2 surface.
- Surfaces not on the PRD 47 §5 W3 list.
- Bulk operations the matrix does not mark, and client-side fan-out deletes.
- Selection or bulk bar on read-only surfaces, including audit log and finance tables.
- Rewriting `ManagerContent` beyond extracting the blocked-PR and stall registers.
- New page sizes, infinite scroll, or tenant-wide select-all.
- Visual redesign unrelated to mounting Collection.
- Backend work other than `PageQuery` on these list endpoints, the new ports, and `archived_at` for knowledgeDoc archive.
