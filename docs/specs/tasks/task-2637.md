# PRD: Remap P2 #2580 Stage Facet to P0 `start | grow | exit`

## Problem & Goal

P2 #2579 R1 binds marketplace query key `stage` to company `BUSINESS_STAGES` (`idea` · `mvp` · `early_revenue` · `growth` · `scale` in `startupListing.ts`) and explicitly rejects P0 `start/grow/exit`. That binding contradicts locked product decisions:

- P0 #2528 decision 4: stages are `start | grow | exit` on `freelancer_profiles.stages`. Do not substitute `BUSINESS_STAGES`.
- P3 epic #2583 R5: Start/Grow/Exit is the same P0 field; P3 promotes that axis to first-class chips and must not introduce `BUSINESS_STAGES`.
- P3 child #2586: query key `stage` filters `freelancer_profiles.stages` with tokens `start|grow|exit` only; selecting all three still excludes unstaged rows; match is server-side OR.

If #2580 ships `BUSINESS_STAGES` against `stages`, the facet matches nothing (P0 never stores those tokens). P3 would then collide on `stage` or ship a second stage widget.

**Goal:** Amend #2579 / #2580 so the Stage row uses P0 tokens `start|grow|exit` on `freelancer_profiles.stages`. P3 #2586 then promotes that same control to first-class multi-select chips (not a parallel axis). Expertise, language, and method rows stay unchanged.

## Target users / ICP roles

- Marketplace seekers filtering freelancer/advisor listings by company stage.
- Downstream P2 (#2579, #2580) and P3 (#2583, #2586) implementers sharing this axis.
- Product/engineering owners of `freelancer_profiles.stages` and marketplace query contracts.

## Scope

In scope for this amendment:

- Remap the marketplace Stage facet / query key `stage` from `BUSINESS_STAGES` to P0 `start | grow | exit`.
- Bind `stage` exclusively to `freelancer_profiles.stages`.
- Preserve existing Expertise, language, and method facet rows as-is.
- Keep a single `stage` axis so P3 #2586 can promote the same control to first-class chips.

## Functional requirements

1. Marketplace query key remains `stage`. It MUST filter `freelancer_profiles.stages` and MUST NOT filter company `BUSINESS_STAGES`.
2. Allowed `stage` tokens are exactly `start`, `grow`, and `exit`. Tokens `idea`, `mvp`, `early_revenue`, `growth`, and `scale` are invalid for this key and MUST NOT be emitted, stored, or matched.
3. Multi-value `stage` is an OR match on the server (`start` OR `grow` OR `exit` among selected tokens).
4. Selecting all three tokens still excludes unstaged profiles (`freelancer_profiles.stages` empty/null). All-three is not “no filter.”
5. P3 #2586 MUST reuse this same `stage` control as first-class multi-select chips. It MUST NOT introduce a second stage widget, a second query key, or `BUSINESS_STAGES`.
6. Expertise, language, and method rows are unchanged by this amendment.
7. Do not add `advisors` to `MARKETPLACE_LISTING_KINDS`. Do not add an `/advisors` route. Do not add SCORE/SBA branding.

## Acceptance criteria

- Stage facet options and query values are only `start`, `grow`, `exit`.
- A request with `stage=start` (and similarly `grow` / `exit`) returns only rows whose `freelancer_profiles.stages` contains that token.
- `stage=start,grow` (any subset) is server-side OR; a profile matching any selected token is included.
- `stage=start,grow,exit` still excludes profiles with empty/null `stages`.
- Queries using `BUSINESS_STAGES` tokens (`idea`, `mvp`, `early_revenue`, `growth`, `scale`) do not populate or satisfy this facet.
- Expertise, language, and method facets behave as before this change.
- P3 #2586 can promote the existing Stage control to chips without a second axis or query-key collision.
- No `advisors` listing kind, no `/advisors` path, and no SCORE/SBA copy or marks appear.

## Out of scope

- Adding `advisors` to `MARKETPLACE_LISTING_KINDS` or introducing `/advisors`.
- SCORE/SBA branding, copy, or visual treatment.
- Changing Expertise, language, or method facet rows.
- Introducing `BUSINESS_STAGES` as a marketplace stage axis, widget, or query key.
- A parallel/second stage control in P2 or P3.
- Changing how P0 persists `freelancer_profiles.stages` beyond using the locked `start | grow | exit` tokens.

## Requirements

This ticket is a **contract amendment**, not a new marketplace filter product. It remaps the P2 Stage facet so P2 (#2579 / #2580) and P3 (#2583 / #2586) share **one** `stage` axis bound to P0 `freelancer_profiles.stages`. It does not add a listing kind, `/advisors` route, SCORE/SBA branding, or a second stage widget.

**BA deliverable is this section.** Do not dump `specs/tasks/task-2637.md` (or any `specs/tasks/` stand-in). Do not patch product code on this BA slot. Persistence of `stages` remains P0 #2528.

### R-1 — Override #2579 R1 Stage binding

1. Epic #2579 R1’s binding of marketplace query key `stage` to company `BUSINESS_STAGES`, and its rejection of P0 `start/grow/exit`, is **withdrawn** for `?category=advisors`.
2. Implementers MUST NOT emit, store, match, or label this facet with `idea`, `mvp`, `early_revenue`, `growth`, or `scale`.
3. Implementers MUST NOT treat P0 `start/grow/exit` as “advisor journey chips only” on this listing. They **are** the marketplace Stage facet.

### R-2 — Query key and field bind

1. Query key remains **`stage`** (singular).
2. It MUST filter **`freelancer_profiles.stages`**.
3. It MUST NOT filter company `BUSINESS_STAGES`, `FUNDING_STAGES`, buyer-profile stage, or any inferred stage.
4. Gate: apply this predicate **only** when `category=advisors` on `/marketplace` (Talent family). Other categories: do not render the control; ignore leftover `stage` params (no chips, no wrong grids, do not 400).

### R-3 — Canonical tokens and labels

| Storage token (query + JSON) | Visible label (en) |
|---|---|
| `start` | Start |
| `grow` | Grow |
| `exit` | Exit |

1. Allowed tokens are **exactly** those three. No aliases (`pre-seed`, `seed`, `series-a`, `idea`, `mvp`, `early_revenue`, `growth`, `scale`, `startup`, `scale-up`, `late`).
2. P0 writes lowercase tokens. Filter matching is **case-insensitive after trim**. Unknown stored strings are ignored (they do not make a listing “staged”).
3. Unknown or empty query tokens are **ignored** (treated as unset for that token). Do not 400 the listing page. If no valid tokens remain, treat as unset (no stage constraint).
4. Codes in the URL and API; localized labels in the UI via existing marketplace / talent i18n. Do not hardcode English beyond existing talent patterns. Do not invent labels that imply `BUSINESS_STAGES` (“Series A”, “MVP”, “Scale”).

### R-4 — Match semantics (server-authoritative)

1. Multi-value `stage` is an **OR** match: a listing is included when **any** of its stored P0 `stages` tokens intersects the selected set.
2. **Unstaged listings are excluded** whenever the stage filter is active (one, two, or all three tokens).
3. Selecting **all three** (`stage=start,grow,exit` or equivalent) is “any staged advisor”: listings whose `stages` contain at least one of `start`/`grow`/`exit`. It is **not** “no filter.” Clearing the facet returns the unfiltered-by-stage set, **including unstaged**.
4. Examples (mixed inventory):
   - `stage=start` → only rows whose `stages` include `start` (may also include grow/exit). Grow-only, exit-only, and unstaged are hidden.
   - `stage=start,grow` (any subset) → rows matching any selected token. Tokens not selected, and unstaged, are hidden.
   - `stage=start,grow,exit` → staged rows only; empty/null `stages` still excluded.
   - no `stage` param → unfiltered-by-stage (unstaged included).
5. Matching runs **on the server** as part of the existing public talent list (`GET /api/public/freelancers` / equivalent), **only when** `category=advisors`. Client-side AND over the current page is insufficient (breaks counts, pagination, and shared URLs).
6. Missing P0 column / null / `[]` → that row does not match an active stage filter. **Do not error the page.**

### R-5 — `BUSINESS_STAGES` tokens are invalid for this key

1. Queries using `idea`, `mvp`, `early_revenue`, `growth`, or `scale` on `stage` **do not populate or satisfy** this facet.
2. Those tokens MUST NOT appear as options in the Stage control.
3. If present in the query string, drop them as unknown (R-3.3). Do not map `growth` → `grow` or `scale` → `exit`.
4. Do not persist `BUSINESS_STAGES` values onto `freelancer_profiles.stages`.

### R-6 — P3 promotion (same control)

1. P3 **#2586** MUST reuse this same `stage` control as first-class multi-select chips (toolbar rank, not buried in “more filters”).
2. It MUST NOT introduce a second stage widget, a second query key, or `BUSINESS_STAGES`.
3. P2 may ship Stage as a compact multi-select on the advisors filter row; P3 promotes **that** control. Replacement of a wrong `BUSINESS_STAGES` `<Select>` is in-place, not additive.
4. P2’s “single-select `<Select>`” language in epic #2579 does **not** apply to Stage after this amendment. Stage is multi-select (OR). Expertise / language / method stay as #2580 specified.

### R-7 — Sibling rows unchanged

1. **Expertise** (`expertise` → listing `expertise` / `EXPERTISE_AREAS`) — unchanged.
2. **Language** (`language` → `freelancer_profiles.languages`, #2528 ISO list) — unchanged.
3. **Method** (`method` → `freelancer_profiles.methods` = `video \| phone \| email \| in-person`) — unchanged.
4. Cross-filter logic stays **AND** across groups (including `stage`) and with `q`; **OR** within a multi-select group.
5. Do not retarget those rows at company fields.

### R-8 — URL, chrome, composition

1. Deep-link shape (order insignificant): `/marketplace?category=advisors&expertise=product,finance&language=en,es&method=video&stage=start`
2. Serialization: pick the existing marketplace convention (repeatable `stage=start&stage=exit` **or** comma-separated `stage=start,exit`) and use it everywhere. Order-independent. Duplicate tokens collapse.
3. Reload / share / back-forward restore the same selections and result set.
4. Changing stage selection **resets `page` to 1** and keeps current sort. Page/sort change does not clear `stage`.
5. Clearing the Stage facet **removes** `stage` from the URL (no `stage=` residue). Keep `category=advisors` and every other filter key.
6. Leaving advisors **drops** `expertise`, `language`, `method`, `stage`, and `category=advisors` (same as #2580 R-9).
7. Result count and empty/zero-result chrome follow the existing marketplace pattern. Controls stay visible when the intersection is empty.

### R-9 — Isolation / anti-goals

1. Do **not** add `advisors` (or `advisor`) to `MARKETPLACE_LISTING_KINDS` or `FamilyId`.
2. Do **not** add an `/advisors` route or a parallel Advisor storefront.
3. Do **not** add SCORE/SBA branding, copy, palette, or partnership marks.
4. Do **not** merge `BUSINESS_STAGES` into global marketplace facet enums.
5. Non-advisor categories: same chrome, same default results, no new required params, leftover `stage` ignored.
6. Population remains **published talent listings**. Company `SEEKING_TYPES` `'advisors'` rows are not this view.

### R-10 — Out of scope (this gap)

1. Creating, editing, or backfilling `freelancer_profiles.stages` (P0 #2528 / #2527).
2. Changing Expertise, language, or method facet rows.
3. A parallel/second stage control in P2 or P3.
4. Introducing `BUSINESS_STAGES` as a marketplace stage axis, widget, or query key.
5. Visitor chat (#2581), Resources tab (#2582), volunteer badge (#2584), location filter (#2585).
6. Ranking / sort changes based on stage.
7. Docs-only `specs/tasks/task-2637.md` as the deliverable.
8. Product-repo patch on this BA slot.
