# PRD: MCP public discovery and registry icon

## Problem & Goal

The published MCP server `io.github.SeanHogg/builderforce` scores 56/100 on the public MCP registry. Two registry recommendations are unmet:

1. Discovery methods require authentication, so unauthenticated clients cannot complete `initialize`, `ping`, or `tools/list` against `POST https://api.builderforce.ai/mcp`. That blocks public catalog discovery and costs 30 points.
2. `server.json` has no `icons` entry, costing 4 points. The live asset `https://builderforce.ai/icon-192.png` (`image/png`) is the icon to publish.

Goal: raise the registry score by those 34 points without widening what an anonymous caller can execute. Unauthenticated discovery returns only the static first-party builtin catalog. Invocation and any presented-but-rejected credential stay challenged. Republish an immutable registry version `1.1.0` that includes the icon.

## Target users / ICP roles

- Anonymous MCP clients and registry crawlers that probe `initialize`, `ping`, and `tools/list` before any OAuth or API-key flow.
- Authenticated tenant users and agents, whose connector, external-server, feature-gated, and platform-operator tool sets must not leak into the anonymous catalog.
- Platform operators publishing the registry entry and maintaining the release probe, English and zh-CN docs, and the bot-exception script comment.

## Scope

In repo `seanhogg/builderforce.ai`, base `main`:

- MCP HTTP handler for `POST https://api.builderforce.ai/mcp`: allow unauthenticated `initialize`, `ping`, and `tools/list`.
- Anonymous `tools/list` body: static first-party builtin catalog only.
- Preserve `401` plus `WWW-Authenticate` for unauthenticated `tools/call`, and for any request that presents a credential the server rejects.
- `.github` release workflow `publish-mcp-registry` probe: treat `200` on unauthenticated discovery as healthy, and treat `401` on unauthenticated `tools/call` as healthy. A discovery-only `401` is no longer the success signal.
- Docs in English and zh-CN, plus the bot-exception script comment, aligned with the new discovery vs. invocation split.
- `server.json`: add an `icons` array pointing at `https://builderforce.ai/icon-192.png`.
- Bump `SERVER_INFO.version` and `server.json` version together to `1.1.0` so the immutable registry version republishes.
- Verification: API type-check, plus the `mcpServerRoutes` and `mcpGateway` vitest suites.

## Functional requirements

1. **Unauthenticated discovery.** `POST /mcp` with JSON-RPC methods `initialize`, `ping`, or `tools/list` and no `Authorization` credential returns HTTP `200` and a valid JSON-RPC success result. `initialize` reports server info version `1.1.0`. `ping` succeeds with an empty result object per the method contract already used by authenticated pings.
2. **Static builtin catalog only.** The anonymous `tools/list` result is the static first-party builtin catalog. It must not include tenant connectors, external MCP servers, feature-gated tools, or platform-operator tools. The list must not depend on tenant resolution, session user, or remote MCP fan-out. Pagination, if the method supports a cursor, stays within that same static catalog.
3. **Invocation stays challenged.** An unauthenticated `tools/call` returns HTTP `401` and a `WWW-Authenticate` challenge. It must not execute a tool or return a tool result.
4. **Rejected credentials stay challenged.** If the caller presents a credential and the server rejects it, the response remains HTTP `401` with `WWW-Authenticate`, including on `initialize`, `ping`, and `tools/list`. Absence of a credential is what opens discovery; a bad credential is not treated as anonymous.
5. **Authenticated behavior unchanged.** A valid credential still receives the existing authenticated catalog and may call tools subject to current authorization. This change must not add anonymous execution, weaken tenant isolation, or drop the challenge header on `401`s.
6. **Registry publish probe.** The `publish-mcp-registry` job in `release.yml` currently treats a `401` as the healthy probe. Update it so unauthenticated `initialize` or `tools/list` (discovery) expecting `200`, and an unauthenticated `tools/call` expecting `401`, are both required for a healthy probe. Do not publish when discovery is not `200` or when unauthenticated `tools/call` is not `401`.
7. **Docs and bot-exception comment.** English and zh-CN docs that describe MCP auth state that discovery methods are public and that `tools/call` requires authentication. Update the bot-exception script comment so it no longer describes the MCP endpoint as `401`-only for these discovery methods.
8. **Registry icon and version.** `server.json` includes an `icons` array whose entry references `https://builderforce.ai/icon-192.png` with MIME type `image/png`. `server.json` `version` and `SERVER_INFO.version` are both `1.1.0`. No other registry identity fields change.

## Acceptance criteria

- Unauthenticated `POST https://api.builderforce.ai/mcp` (and the equivalent route under test) with `initialize`, `ping`, and `tools/list` returns `200` and a JSON-RPC success payload. `initialize` / server info version is `1.1.0`.
- Anonymous `tools/list` equals the static first-party builtin catalog and contains no tenant connector tools, external MCP server tools, feature-gated tools, or platform-operator tools.
- Unauthenticated `tools/call` returns `401` with a `WWW-Authenticate` header and does not run a tool.
- A presented credential that fails validation still returns `401` with `WWW-Authenticate` for discovery methods and for `tools/call`.
- Authenticated `tools/list` and `tools/call` behavior is unchanged relative to current authorization rules.
- `release.yml` `publish-mcp-registry` probe fails the job unless discovery returns `200` and unauthenticated `tools/call` returns `401`.
- English docs, zh-CN docs, and the bot-exception script comment describe public discovery and authenticated invocation, and do not claim discovery is `401`-only.
- `server.json` has an `icons` entry for `https://builderforce.ai/icon-192.png` (`image/png`). `server.json` version and `SERVER_INFO.version` are `1.1.0`.
- API type-check passes. `mcpServerRoutes` and `mcpGateway` vitest suites pass, including new cases for anonymous discovery `200`, anonymous catalog contents, rejected-credential `401`, and unauthenticated `tools/call` `401`.

## Out of scope

- Changing OAuth, API-key issuance, token validation, or the `WWW-Authenticate` challenge format beyond keeping it on `401` responses.
- Exposing tenant connectors, external MCP servers, feature-gated tools, or platform-operator tools without authentication.
- Allowing unauthenticated `tools/call` or any other non-discovery JSON-RPC method.
- Redesigning the builtin catalog, adding tools, or changing tool schemas except as required for the anonymous list to be the existing static first-party set.
- Replacing or re-encoding `icon-192.png`; the verified live URL is the registry icon source.
- Registry score items other than the +30 discovery recommendation and the +4 icon recommendation.
- Frontend, billing, or unrelated MCP gateway refactors.
