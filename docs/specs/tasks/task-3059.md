# PRD: Marketplace monetization (listing + transaction fee, Stripe)

**ROADMAP:** Revenue · P1 · Target Q3 2026 · Status: 🔄 Partial — awaits Stripe secrets.

## Requirements

_Owned by the business-analyst — see the ticket's BA section. This design assumes the requirement is: a creator can list a priced item, a buyer pays through Stripe, the platform takes a transaction fee, and the seller is credited the remainder._

## Design

### 1. Finding: the code path is built; the gap is deployment and one product decision

A read of the repo shows monetization is largely implemented. Nothing here needs a new payment integration. What is missing is (a) Stripe secrets bound on the deployment, (b) live verification, and (c) a decision on whether a flat **listing fee** exists at all (see §5).

| Concern | Where it lives | State |
|---|---|---|
| Hosted one-off checkout (`mode: 'payment'`) | `StripeProvider.createMarketplaceListingCheckoutSession` → `createOneTimeCheckoutSession` → `openCheckout` | Built |
| Recurring app purchase | `StripeProvider.createSubscriptionCheckoutSession` | Built |
| Seller payout accounts (Stripe Connect, `standard`) | `createConnectedAccount` / `createConnectedAccountLink` / `connectedAccountStatus` | Built |
| Start → verify → grant | `startListingCheckout` → Stripe hosted page → `completeListingCheckout` (re-reads session via `verifyPaidCheckout`) | Built |

| Transaction fee (take rate) | `resolveTakeRateBps`, `platformTakeRateBps`, `takeRateThresholdCents` | Built |
| Order / line / licence / ledger | `orders`, `order_line_items` (stamps `commissionCents`), `template_licenses`, two `ledger_entries` via `recordSaleSplit` | Built |
| Refund reversal | `stripePurchaseReversal`, `orderRefunderFor` | Built |
| Disputes | `application/marketplace/disputes.ts` | Built |

### 2. Fee model (as implemented — do not change without a product decision)

* **Transaction fee:** `MARKETPLACE_TAKE_RATE_BPS`, default **1500 bps (15%)**, clamped to 0–5000. A non-integer value (e.g. `"50%"`) falls back to the default rather than being mis-parsed.
* **Threshold:** `MARKETPLACE_TAKE_RATE_THRESHOLD_CENTS`, default **$200,000 lifetime net earnings**. Below it the seller pays 0 bps; past it the configured rate applies. Net of refunds (refunds are negative ledger entries summed with commissions).
* **Stamping invariant:** the rate in force at the instant of sale is written to `order_line_items.commissionCents`; crossing the threshold never re-prices earlier sales.
* **Not cached, by design:** the lifetime SUM is one indexed query per purchase because it prices an immutable ledger row.
* **Account kind:** sellers are `user` accounts (creations, knowledge, sites) or `tenant` accounts (marketplace agents, which have no author column). The threshold and the payout account MUST use the same kind, or a seller never crosses the threshold.

### 3. Money-safety invariants (must hold for go-live)

1. **One reference, one charge.** Ledger references derive from the order id; the unique index on `(tenant, denomination, reference)` makes retries, double-clicks and replayed webhooks collide at the database.
2. **One door for paid grants.** `acquireListing` grants free listings only; paid grants happen only in `completeListingCheckout` after Stripe confirms `payment_status: paid`, session kind, buyer ownership and captured amount. No client-supplied payment id is ever trusted.
3. **Amount check.** Captured amount must be ≥ `priceCents × quantity`, defeating "open checkout at $1, complete after the seller raises to $99".
4. **Seller tenant owns the ledger rows**, not the buyer's tenant.
5. **Single webhook endpoint.** Connect uses *destination charges* so `retrieveCheckoutSession` and the one signed webhook endpoint keep working; no second endpoint or secret.
6. **Idempotent checkout creation** via `mp-checkout:<listing>:<buyer>[:qty]`.

### 4. Go-live plan (the remaining "awaits Stripe secrets" work)

This is operations plus verification, not new code. It is tracked on the companion ticket **#3263 "Bind Stripe secrets and verify live marketplace checkout"**.

1. `wrangler secret put STRIPE_SECRET_KEY` and `STRIPE_WEBHOOK_SECRET` (test keys first). They are intentionally absent from `api/wrangler.toml`; secrets live only in Worker secrets.
2. Register the Stripe webhook at `https://api.builderforce.ai/api/webhooks/payment` for `checkout.session.completed` plus the subscription/invoice/payment-method events listed in `StripeProvider.ts`.
3. Optionally set `MARKETPLACE_TAKE_RATE_BPS` / `MARKETPLACE_TAKE_RATE_THRESHOLD_CENTS`; unset means 15% past $200k.
4. Test-mode end-to-end: seller connects a Stripe account → publishes a priced listing → buyer checks out → webhook settles → licence granted → two ledger rows → refund reverses ledger and revokes licence.
5. Failure mode check: with the secret absent, `startListingCheckout` returns a clear 400 ("Payments are not configured") and `PaymentNotConfiguredError` maps to 503 elsewhere; the Worker must still boot (the factory deliberately does not throw at boot).
6. Switch to live keys only after step 4 passes; keep the Cloudflare Containers and `AUTH_CACHE_KV` bindings untouched (unrelated, and required).

### 5. Open decision: a flat *listing fee*

The roadmap title says "listing + tx fee". The repo has **no listing-fee concept** (searches for `listingFee` / "listing fee" find nothing). The existing 0%-below-$200k threshold is a deliberate "free to try" policy modelled on monday.com / Square / Atlassian, which a per-listing charge would contradict.

**Recommendation:** treat "listing" in the roadmap as *monetizable listings* (priced listings, already built) and do **not** add a flat listing fee in Q3. If product wants one, it should be a separate ticket with this shape, so it cannot disturb the sale path:

* a one-off `createOneTimeCheckoutSession` with `purchaseKind: 'marketplace_listing_fee'`, registered in the purchase registry as its own kind (not `marketplace_listing`, whose settler grants licences);
* publish gated on a verified paid fee via `verifyPaidCheckout`, never on a client flag;
* ledger entry as platform revenue only, reference keyed on the fee session id, with a refund path through `orderRefunderFor`.

Needs a product-owner decision before any work starts.

### 6. Risks

| Risk | Mitigation |
|---|---|
| Account-kind mismatch between threshold query and payout account | Single `lifetimeSellerCents` reader with `accountKind`; covered by `takeRate.test.ts` |
| Env typo changes fee by 100× | `wholeNumberOrNull` + 0–5000 clamp, tested |
| Replayed / out-of-order webhooks | DB unique reference + re-verification at Stripe |
| Seller on non-onboarded Connect account | `connectedAccountStatus` is the only thing allowed to authorise a payout link |
| Tax / merchant-of-record | `standard` Connect accounts leave disputes, refunds and tax reporting with the seller; confirm legal wording on the listing terms |

### 7. Out of scope

New payment providers, a second webhook endpoint, direct (non-destination) charges, express Connect accounts, and any change to the fee defaults.
