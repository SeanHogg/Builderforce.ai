# PRD: Deep-link to task detail on Projects board

## Problem & Goal

**Problem.** The VSIX “view in website” action (and any shareable URL of the form `/projects?tab=tasks&project=<id>&task=<id>`) does not open the intended ticket. Opening `https://builderforce.ai/projects?tab=tasks&project=11&task=2394` lands on the Tasks tab with an empty board (“0 tasks”, all columns empty). The `project` query param is not applied, so project 11’s tasks never load, and the `task` param never opens the detail drawer/modal.

Likely causes: URL params are read before the projects list hydrates and then discarded; the board fetches tasks for a default/no project; there is no path that maps `task` to opening the detail panel.

**Goal.** Make task deep links work and stay shareable: authenticated users who open `/projects?tab=tasks&project=<id>&task=<id>` land on that project’s Tasks board with the named task selected and its detail panel open. Invalid task ids fail gracefully. Params are not stripped after load.

## Target users / ICP roles

- Engineers and PMs using the BuilderForce VSIX “view item in builderforce.ai” button (source: Brain chat #99).
- Anyone sharing or bookmarking a task URL (in-app copy link, Slack, email).
- Same behavior for all authenticated roles that can view the given project’s tasks.

## Scope

**In scope (frontend app, Projects → Tasks):**

- Parse and honor `tab`, `project`, and `task` search params on `/projects`.
- Apply `project` after (or as) the projects list loads so the selector and board fetch the correct project — no race that drops params.
- Fetch and render that project’s tasks; open the detail drawer/modal for `task=<id>` when the task exists on the board.
- Keep `tab`, `project`, and `task` in the URL after load (no redirect/replace that strips them).
- Graceful handling of missing/invalid `project` or `task`.
- Desktop and mobile viewports.

**Repro:** `https://builderforce.ai/projects?tab=tasks&project=11&task=2394` (project 11 = BuilderForce.AI, task 2394).

## Functional requirements

1. **Tab.** `tab=tasks` selects the Tasks tab on first paint (or immediately after hydration), not a default tab that later switches.
2. **Project.** `project=<id>` sets the project selector to that id and is the sole source of truth for the board’s task fetch. Application of the param must wait until the projects list is available; it must not be discarded if it arrived before load completed.
3. **Task fetch.** The board loads tasks for the URL project, not a default/empty project. Columns reflect that project’s real counts.
4. **Task detail.** After tasks for that project are available, `task=<id>` selects/highlights that task and opens its detail panel (drawer or modal, existing UI). No extra click required.
5. **URL stability.** After successful load, the address bar still contains `tab`, `project`, and `task` with the original values (query order may normalize). The link remains bookmarkable and shareable.
6. **Invalid / missing ids.**
   - Unknown or unauthorized `project`: board does not crash; show the existing empty/error/permission state; do not open a detail panel.
   - Valid project, unknown `task`: board loads that project’s tasks; no crash; no detail panel (or a brief “task not found” empty state); `task` may remain in the URL or be dropped only if product already strips unknown ids — prefer keep-and-no-open so the link is diagnosable.
   - Missing `task`: behave as a normal project Tasks deep link (board only).
   - Missing `project` with `task` present: do not open a random project’s ticket; keep current project-required empty/default behavior.
7. **Auth.** Unauthenticated users follow the existing login/redirect flow and, after login, land on the same deep-link URL with the behavior above.
8. **Responsive.** Detail open + board load work on desktop and mobile viewports (mobile may use the existing full-screen/sheet detail pattern).
9. **Idempotency.** Refreshing the same URL yields the same project, board, and open task. Client-side project/tab changes update the URL via the existing router so new shares stay correct.

## Acceptance criteria

1. Authenticated visit to `https://builderforce.ai/projects?tab=tasks&project=11&task=2394` (and any other valid `project`/`task` pair the user can access):
   - Projects page, Tasks tab.
   - Project selector = that project (e.g. 11 / BuilderForce.AI).
   - Board shows that project’s tasks (not 0 / empty columns when the project has work).
   - Task 2394 (or the given id) is highlighted/selected and its detail panel is open.
2. Invalid task id: board for the URL project loads, no crash, no blank page; detail does not open for a wrong ticket; empty/not-found treatment is sensible.
3. URL params remain after load (no strip/redirect that drops `project` or `task`); the same URL can be copied, bookmarked, and opened again with the same result.
4. Verified on desktop and mobile viewports.
5. VSIX “view item in builderforce.ai” for a task uses this URL shape and, after this fix, opens the ticket in the website.

## Out of scope

- Changing VSIX button URL shape (unless the web app requires a different canonical path; default is keep `?tab=tasks&project=&task=`).
- New task-detail UI, board redesign, or new query params.
- Deep links to other entities (docs, PRs, chats) or other Project tabs except as needed so `tab=tasks` is respected.
- Backend task/project APIs except if a frontend-only fix is impossible (then a minimal API change is a follow-up).
- SEO, unauthenticated public task pages, or permissions model changes.
- Analytics/telemetry beyond existing page views.
