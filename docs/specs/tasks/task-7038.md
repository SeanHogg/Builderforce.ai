# PRD: App manifest write gate and commit gate

## Problem & Goal

Hosts that write or commit `.builderforce/builderforce.json` do not run the shared manifest validator. Invalid manifests, including unknown resource types and other schema errors, can land on disk and be committed without the agent seeing a structured issue list.

The goal is a single validation contract used by every host gate:

- **Write gate (advisory):** `write_file` / `edit_file` of the manifest still succeeds. The tool result appends issues from `validateManifest`, described with `describeManifestIssue`.
- **Commit gate (blocking):** a commit that includes the manifest is refused when `validateManifest` reports errors. Each error is named via `describeManifestIssue`. Warnings do not block.

There is no second validator and no shared gate function. Gates live in each host and call `validateManifest` + `describeManifestIssue` from `builderforce-webcontainers/packages/core/src/manifest` (published as `@seanhogg/builderforce-webcontainers-core`).

This slice is epic #6994 and overlaps task #6997. Contract: `docs/specs/app-manifest-ai-resource.md` §9.

## Target users / ICP roles

- **Agent runtime (VSIX composer):** tools that write the manifest and `git_commit` must surface or refuse invalid manifests before the user treats the workspace as shippable.
- **API commit path:** `commitFileToRepo` / `commitAgentFile` must refuse an erroring manifest with the same issue names.
- **Platform / core owners:** the published `@seanhogg/builderforce-webcontainers-core` package is the only validator hosts may import. Gate correctness for `type: "ai"` depends on that package knowing `AiResource`.

## Scope

In scope once the published core package accepts `ai` (see hard blocker):

- Import `MANIFEST_PATH` (`.builderforce/builderforce.json`) from its owner. Do not hard-code a second path.
  - Canonical owner: `@builderforce/app-detect` (`packages/app-detect/src/manifest/manifestShape.ts`).
  - VSIX path derivation stays on `@seanhogg/builderforce-webcontainers/manifest` constants (`WORKSPACE_DIR` / `MANIFEST_FILE`) in `clients/vscode/src/composerCommands/manifestLocation.ts`.
- **VSIX write gate** in `clients/vscode/src/fileTools.ts` execute wrapper (same interception point as `publishGate`, which already handles `git_commit` / `git_push`). `write_file` / `edit_file` dispatch through `@builderforce/agent-tools` `core-tools.ts` (`writeFileTool` / `editFileTool`). Append validator issues to the JSON tool result. Do not block the write.
- **VSIX commit gate:** extend `clients/vscode/src/publishGate.ts` `commitGateRefusal` (via `publishGateFor` for `git_commit`). Read manifest content from the committed diff or working tree. Refuse on errors; name each with `describeManifestIssue`.
- **API commit gate:** `commitFileToRepo` (`api/src/application/repos/commitFileToRepo.ts`), reached via `commitAgentFile` (`commitFileAsPendingChange.ts`) and `repoBridge.ts`. Add a dependency on `@seanhogg/builderforce-webcontainers-core` pure `./manifest` export (spec §8 / §9). The API does not depend on `-core` today. `@seanhogg/builderforce-webcontainers` (browser package) `./manifest` only re-exports path constants (`MANIFEST_FILE`, `WORKSPACE_DIR`), not `validateManifest`.
- Targeted tests: one write-gate test and one commit-gate refusal test per host. Run with the package test runner (`clients/vscode` vitest; `api` vitest for `commitFileToRepo`).
- Leave changes uncommitted (`leave_uncommitted`). Owner run ships once.

### Hard blocker (must resolve before the gate is correct for `ai`)

Published `@seanhogg/builderforce-webcontainers-core@2026.11.12` (imported by hosts via `Builderforce.ai/clients/vscode/node_modules`) does not know the `ai` resource. `dist/manifest/types.d.ts` `ResourceSpec` has no `AiResource`. `dist/manifest/validate.js` emits `unknown-resource-type` for `type: "ai"` (no `ai` case).

The local checkout `builderforce-webcontainers/packages/core/src/manifest` does have `ai` (`types.ts` `AiResource`, `schema.ts`, `validate.ts`, `toApplicationSpec.ts` `HOST_DELIVERED`). The VSIX and API consume the published npm package, not local source. Only `@builderforce/*` packages are source-aliased in `clients/vscode/esbuild.mjs`.

A gate wired against the current published package would falsely reject every valid `ai` manifest. Do not treat the gate as correct for `ai` until either:

- #6996 core `ai` work is released (version bump, tag pushed, consumers bumped, lockfiles refreshed — a spec done-check), or
- hosts are pointed at the local checkout source that already implements `ai`.

Investigation only until that dependency is satisfied. No gate code in this run.

## Functional requirements

1. Hosts call `validateManifest` and format issues only with `describeManifestIssue`. No second validator. No shared gate helper that both hosts import as the policy implementation.
2. Write gate applies only when the written or edited path is the manifest path imported from the owning package (or the VSIX derivation of the same constants). Other files are unchanged.
3. Write gate is advisory: the file write lands. The JSON tool result includes the validator issues (errors and warnings). An invalid manifest is not rejected at write time.
4. Commit gate applies when the commit includes the manifest. Content is the committed diff or working-tree file, not a second on-disk copy with a hard-coded path.
5. Commit gate is blocking on errors only. Refusal text names each error via `describeManifestIssue`. Warnings do not refuse the commit. A manifest with no errors is allowed through this gate (other publish gates unchanged).
6. VSIX commit refusal stays inside `commitGateRefusal` / `publishGateFor` for `git_commit`. Write interception stays in the `fileTools.ts` execute wrapper alongside existing publish-gate interception.
7. API refusal is inside `commitFileToRepo` so both `commitAgentFile` and `repoBridge` callers get the same behavior. Validation uses `@seanhogg/builderforce-webcontainers-core` `./manifest`, not the browser package re-export.
8. Issue text and refusal behavior match for the same manifest on VSIX and API (same validator, same describer).
9. Gates must not be enabled against a core build that lacks `AiResource`. Shipping the gate for `ai` requires the released package (or an explicit local-source alias) that accepts `type: "ai"` without `unknown-resource-type`.

## Acceptance criteria

- A `write_file` or `edit_file` of the manifest with validator errors still writes the file, and the tool result appends those issues described by `describeManifestIssue`.
- A `write_file` or `edit_file` of a non-manifest path does not append manifest issues.
- VSIX `git_commit` that includes a manifest with errors is refused, and the refusal names each error via `describeManifestIssue`. Warnings alone do not refuse.
- API `commitFileToRepo` (including the `commitAgentFile` path) refuses the same erroring manifest and names each error the same way. Warnings alone do not refuse.
- A valid manifest, including `type: "ai"` once the published core (or local alias) includes `AiResource`, is not refused by the commit gate and is not reported as `unknown-resource-type`.
- Hosts import the manifest path; no second hard-coded `.builderforce/builderforce.json` string is introduced as the gate’s source of truth.
- API depends on `@seanhogg/builderforce-webcontainers-core` for `validateManifest`. It does not treat the browser package `./manifest` path-constant re-export as the validator.
- Tests: write-gate test and commit-gate refusal test per host, green under `clients/vscode` vitest and `api` vitest.
- Spec done-check: write gate appends issues; VSIX `git_commit` and the API commit path refuse errors and name them.
- Working tree left uncommitted.

## Out of scope

- Implementing or releasing core `ai` support (#6996): types, schema, `validate.ts` `ai` case, version bump, tag, consumer bumps, lockfile refresh. This PRD only records that the gate is incorrect for `ai` until that release (or a local source alias) lands.
- A second validator, a shared gate function, or duplicating `describeManifestIssue` in hosts.
- Hooking raw `git commit` inside the sandbox. `container/sandboxGit.mjs` has no commit path (clone / fetch / bundle / publish only). Per §9 that path is explicitly out of scope; do not add a hook.
- Changing publish behavior for `git_push` beyond what `publishGate` already does, except where commit refusal already runs before push.
- Blocking writes. The write gate never fails the tool because of manifest issues.
- Blocking commits on warnings.
- Rewriting or auto-fixing manifest contents.
- Aliasing `@seanhogg/builderforce-webcontainers-core` in `clients/vscode/esbuild.mjs` unless that is the chosen resolution of the hard blocker; default path is wait for the #6996 release.
