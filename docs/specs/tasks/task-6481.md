## 1. Problem & Goal

### Problem

Today, understanding a codebase through Builderforce requires sign-in and a network round-trip, and re-analysis is effectively from scratch each time. Consequences:

- **No offline path.** A developer cannot point the VSIX at a folder and get a grounded understanding without authenticating and reaching the platform.
- **Non-incremental analysis.** A one-line change re-triggers broad re-analysis. Cost and latency scale with repo size, not with change size.
- **Text diffs, not fact diffs.** Reviewers see line diffs and cannot tell whether security posture, performance, maintainability ("-ilities"), or quality moved.
- **No honest comparability.** Two runs cannot be compared reliably because inputs, tool versions, and scoring rules are not pinned or recorded.
- **No forward-looking signal.** There is no predicted measure of where a change is likely to land before it is run.

### Goal

Ship an **offline-first VSIX** that:

1. Understands a folder **with no sign-in**, deterministically and locally.
2. Computes understanding **incrementally** by diffing **facts**, not text.
3. Produces a **measured run delta** across four dimensions: **Security, Performance, -ilities, Quality**.
4. Adds **predicted measures** (Part D) layered on top of the measured baseline.

### Governing principles

| Principle | Meaning |
|---|---|
| **Deterministic first** | Same input and same pinned tool/rule versions yield the same facts and scores. LLM-derived output is additive and clearly separated from deterministic facts. |
| **Local first** | Core understanding runs on the developer's machine with no network and no account. Network features are optional enrichment. |
| **Incremental by construction** | The pipeline is designed around change sets; full recompute is the fallback, not the default. |
| **Honest comparability** | A delta is only reported between runs that are comparable. Incomparable runs are flagged, never silently compared. |
| **Registry data, not branches** | Behavior varies by data in registries (rules, metrics, language handlers), not by code branches per case. |
| **One flow** | Offline and online share a single pipeline. Sign-in adds enrichment; it does not fork the flow. |

## 2. Target Users / ICP Roles

| Role | Need |
|---|---|
| **Individual developer** | Open a folder in the VSIX and get an understanding immediately, offline, no account. |
| **Reviewer / tech lead** | See what changed in *facts* and how Security/Performance/-ilities/Quality moved between runs. |
| **Security / platform engineer** | Trust that findings are deterministic, reproducible, and comparable across runs. |
| **Builderforce agent runtime (internal consumer)** | Consume a stable fact model and run-delta contract rather than re-deriving understanding. |
| **Builderforce maintainers** | Extend rules, metrics, and languages by adding registry entries, not new code paths. |

## 4. Functional Requirements

### Part A: Offline-first foundation

- **FR-A1.** The VSIX can analyze an opened folder with **no sign-in and no network access**.
- **FR-A2.** Offline and online modes run the **same pipeline**; authentication only unlocks optional enrichment and never gates core understanding.
- **FR-A3.** All offline artifacts (facts, run records, caches) persist locally in a defined, versioned store.
- **FR-A4.** Network failure or absence degrades gracefully to offline behavior without errors in the core flow.

### Part B: Deterministic understanding

- **FR-B1.** Understanding is expressed as a **canonical, versioned fact model** (entities, relations, and attributes derived from the code and config).
- **FR-B2.** Fact extraction is **deterministic**: identical input plus identical pinned tool/rule versions produce byte-identical facts.
- **FR-B3.** Extraction is **registry-driven**: languages, extractors, and rules are registered as data; adding one does not require branching core logic.
- **FR-B4.** Deterministic facts are stored **separately** from any LLM-derived annotations, which are additive and labeled.

### Part C: Incremental understanding and the run delta

- **FR-C1.** The engine computes understanding **incrementally**: given a prior fact set and a change set, it recomputes only affected facts.
- **FR-C2.** Change detection **diffs facts, not text**. Cosmetic, whitespace-only, or comment-only edits that do not alter facts produce an empty fact delta.
- **FR-C3.** Each analysis produces a **run record** capturing inputs, tool/rule/registry versions, and resulting measures.
- **FR-C4.** A **run delta** compares two run records and reports change across **Security, Performance, -ilities, Quality**.
- **FR-C5.** **Comparability is enforced.** If two runs differ in pinned versions, scoring rules, or scope such that comparison is not valid, the delta is marked **not comparable** with the reason, and no numeric delta is fabricated.
- **FR-C6.** Each dimension's measures are **registry-defined** (metric, rule, weight, scoring), so adding or changing a metric is a data change.
- **FR-C7.** Incremental results must be **equivalent to a full recompute** for the same input (incremental is an optimization, never a different answer).

### Part D: Predicted measures

- **FR-D1.** Given a pending change and the measured baseline, produce **predicted measures** for the four dimensions.
- **FR-D2.** Predictions are **clearly labeled as predicted**, kept separate from measured values, and never merged into a measured delta.
- **FR-D3.** Predictions are **reproducible** where deterministic inputs allow, and carry provenance (model/heuristic and version) when not.
- **FR-D4.** Where measured results later exist, the system can compare **predicted vs. measured** for the same change.

### Cross-cutting

- **FR-X1.** All stores, fact schemas, and run-record schemas are **versioned** with explicit migration or invalidation behavior.
- **FR-X2.** Every workstream respects the **single-flow** and **registry-not-branches** principles; any new behavior variance is expressed as registry data.
- **FR-X3.** No telemetry or source content leaves the machine in the offline path.

## 5. Acceptance Criteria

Per-workstream done-checks live in PRD §8 and are authoritative. Program-level acceptance:

1. **Offline works end to end.** With the network disabled and no account, opening a folder in the VSIX yields a populated fact model and a run record.
2. **Determinism.** Two runs over the same folder with the same pinned versions produce identical facts and identical measures. Verified by a named repeatability test.
3. **Incrementality is correct.** For a set of representative edits, the incremental result equals the full-recompute result (FR-C7), and the work done scales with the change set, not repo size.
4. **Facts, not text.** A whitespace/comment-only edit yields an **empty fact delta** and an unchanged measure set.
5. **Run delta is produced and honest.** A comparable pair of runs yields a per-dimension delta across Security, Performance, -ilities, Quality; an incomparable pair yields an explicit **not comparable** result with a reason and no numeric delta.
6. **Registry-driven extensibility.** Adding a rule/metric/language via a registry entry changes behavior with **no change to core branching code**, demonstrated by a test that registers a new entry.
7. **Predicted measures are separated.** Predicted values are labeled, stored distinctly, and never appear inside a measured delta; predicted-vs-measured comparison works once measured data exists.
8. **One flow.** Online enrichment, when enabled, runs through the same pipeline and does not change deterministic facts or measured scores.
9. **Quality gates pass for every workstream.** Typecheck clean, repo guards pass, named tests for the workstream pass, and required review (Opus for cross-package/storage/security) is completed with fixes applied.
10. **Dependency order honored.** No workstream is marked done before its DAG prerequisites (PRD §7) are done.

## 6. Constraints & Notes for Downstream Agents

- Treat `docs/specs/41-prd-offline-understanding-and-run-delta.md` as the contract; reconcile any ambiguity against it first.

- Prefer extending registries over adding conditionals. If a change seems to need a branch, model it as registry data instead.
- Keep deterministic and LLM-derived data physically and logically separate in storage and in reported output.

## 7. Out of Scope

Full non-goals are in PRD §9. At the program level, this work does **not** include:

- Replacing or redesigning the online/cloud Builderforce experience beyond keeping it on the single shared flow.
- Introducing a second, offline-only analysis pipeline or any mode-specific forks of core logic.
- Treating LLM output as authoritative for measured results; LLM-derived content is additive only.
- Reporting numeric deltas between runs that fail the comparability check.
- Transmitting source code or understanding data off-machine from the offline path.
- Language/rule/metric expansion beyond what is required to prove the registry mechanism; broad coverage is follow-on work via registry data.
- Anything explicitly excluded in PRD §9 that is not restated here.
