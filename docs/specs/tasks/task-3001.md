# PRD: Fix Frontend Architecture Ratchet

## Problem & Goal

The frontend currently contains module dependencies that violate the repository’s configured architecture policy. These violations cause architecture checks to fail or rely on exceptions, increasing coupling and making future changes riskier.

Refactor the affected frontend modules so their dependency graph complies with the existing policy, remove obsolete workarounds, and preserve the architecture check as a guard against regressions. The change must not alter user-visible behavior.

## Target Users / ICP

- **Frontend engineers:** Receive a clear dependency structure and can make changes without introducing boundary violations.
- **Code reviewers and maintainers:** Can rely on an automated architecture check to prevent dependency debt from returning.
- **End users:** No functional or visual changes; frontend behavior remains unchanged.

## Scope

- Identify and resolve all current violations reported by the frontend architecture or dependency ratchet check.
- Refactor affected imports, exports, barrels, wrappers, and module boundaries.
- Remove obsolete indirection and architecture-rule suppressions made unnecessary by the refactor.
- Update architecture configuration only where a rule demonstrably describes an incorrect or stale dependency relationship; do not weaken checks merely to make them pass.
- Ensure the architecture check is runnable locally and enforced by CI.
- Update affected tests and type declarations for reorganized modules.

## Functional Requirements

1. **Policy compliance**
   - Frontend dependencies must follow the repository’s configured layer and module-boundary rules.
   - Refactored modules must not introduce circular dependencies.
   - Public entry points and exports must remain compatible unless an affected export is demonstrably unused and its removal is required to correct the dependency graph.

2. **Violation remediation**
   - Resolve each current frontend architecture-check violation at its source.
   - Do not hide violations through broad ignore patterns, blanket lint suppressions, path aliases, or no-op forwarding modules.
   - Configuration changes must be limited to correcting inaccurate rules and must retain equivalent or stricter enforcement.

3. **Regression protection**
   - The frontend architecture/dependency check must complete successfully on a clean checkout.
   - The check must be exposed through the repository’s normal validation workflow and run in CI.
   - A newly introduced prohibited dependency must cause the check to fail.

4. **Behavioral compatibility**
   - Preserve existing frontend features, routing, state behavior, API contracts, and rendered output.
   - Refactoring must not change authentication, authorization, data-fetching semantics, or error handling.

5. **Maintainability**
   - Consolidate or remove superseded modules and imports rather than adding another abstraction layer.
   - Keep dependency direction explicit and consistent with neighboring frontend modules.

## Acceptance Criteria

- The configured frontend architecture/dependency ratchet check exits successfully and reports zero unresolved violations.
- The checked frontend dependency graph contains no newly introduced cycles or prohibited cross-boundary imports.
- No broad suppression, exclusion, or weakened architecture rule is added to conceal existing violations.
- Frontend lint, type checking, unit tests, relevant integration tests, and production build all pass.
- CI runs the architecture check and blocks a deliberately introduced prohibited dependency.
- Existing user-facing workflows and frontend test expectations remain unchanged.
- Obsolete forwarding files, exports, and imports identified during remediation are removed.

## Out of Scope

- Backend or API architecture changes.
- UI, UX, visual-design, or product-feature changes.
- Unrelated dependency upgrades, framework migrations, or repository-wide rewrites.
- Broadening the architecture policy to accommodate the current violations.
- Suppressing architecture failures without correcting the underlying module dependencies.
- Refactoring frontend areas that already comply and are not required to resolve a reported violation.
