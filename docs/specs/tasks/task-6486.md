## Problem & Goal

The repository currently has multiple representations of the same file-level understanding: the repo-map `FileFacts` model and the `codebaseScan` result. Overlapping facts can diverge, while the VSIX directly imports the repo-map extract and is therefore coupled to an intermediate artifact and its format.

Consolidate repository understanding behind one canonical `FileFacts` contract:

`repo-map FileFacts → codebaseScan projection → API and VSIX consumers`

`codebaseScan` must become a deterministic projection of the canonical facts rather than an independently discovered view. The VSIX must consume the supported `codebaseScan` interface instead of importing the repo-map extract.

## Target Users / ICP Roles

- **Repository maintainers:** need one consistent view of files, paths, languages, and symbols.
- **VSIX users:** expect repository navigation and search to reflect the same facts as the backend.
- **Agent-runtime and API consumers:** need stable, non-divergent `codebaseScan` data.
- **WS3 and WS4 maintainers:** need their outputs converged without forking either workstream’s behavior.

## Scope

### In scope

- Converge repo-map `FileFacts` into one canonical schema and serialization path.
- Refactor `codebaseScan` into a projection of that canonical model.
- Preserve the current externally consumed `codebaseScan` contract and behavior.
- Remove all VSIX source, build, packaging, and runtime dependencies on the repo-map extract.
- Make the VSIX consume `codebaseScan` through its supported client/API contract.
- Validate canonical-to-projection parity and incremental snapshot replacement.
- Add focused WS5 coverage while leaving existing tests, fixtures, and snapshots unchanged.
- Complete Sonnet review after WS3 and WS4 are available.

### Out of scope

- Redesigning WS3 repo-map extraction or WS4 scanning behavior.
- Adding languages, symbol types, or repository-analysis capabilities.
- Redesigning the VSIX user interface or navigation experience.
- Introducing a new persistence layer or materially changing storage architecture.
- Changing unrelated APIs, agents, workflows, or public contracts.
- Performance or scalability work beyond correctness and parity for this consolidation.
- Updating existing test expectations or snapshots to accommodate divergent behavior.

## Functional Requirements

### FR-1 — Canonical `FileFacts`

- The converged repo-map `FileFacts` contract is the authoritative representation of repository file facts.
- Duplicate `FileFacts` definitions and serializers must reuse that contract rather than introduce another equivalent model.
- Canonical identity and path rules remain owned by the repo-map implementation from WS3.

### FR-2 — `codebaseScan` as a projection

- `codebaseScan` must be derivable entirely from a canonical `FileFacts` snapshot.
- The projection path must not independently traverse or parse repository files to recreate authoritative facts.
- `codebaseScan` may be materialized or cached for compatibility, but it must contain no independently owned or divergent fact data.
- The same canonical snapshot must always produce the same projection.

### FR-3 — Fact convergence

- Every canonical fact maps into the projection according to established canonical identity rules.
- Overlapping fields, including supported path, language, symbol, and source-location metadata, must agree with the canonical values.
- A canonical fact must not produce conflicting duplicate projection entries.
- When a new canonical snapshot is applied, facts absent from that snapshot must not remain in the projection.

### FR-4 — Stable consumer contract

- The external shape and semantics of `codebaseScan` remain compatible with existing consumers.
- Consumers do not need to understand the internal repo-map extract format.
- Existing `codebaseScan` behavior must not regress solely because the implementation is now projection-based.

### FR-5 — VSIX decoupling

- The VSIX must not import, copy, bundle, or directly parse the repo-map extract.
- The VSIX obtains repository facts through the supported `codebaseScan` client/API interface.
- Repository search, navigation, and file metadata continue to work against that interface.
- Any legacy extract-specific VSIX code, configuration, or build steps must be removed rather than retained as a parallel path.

### FR-6 — Validation and delivery

- WS5 begins after both WS3 and WS4 dependencies are complete.
- New tests cover canonical-to-projection parity, deterministic output, snapshot replacement, and VSIX decoupling.
- Existing tests remain unchanged and pass against the consolidated implementation.
- Sonnet reviews and approves the final change before completion.

## Acceptance Criteria

1. The implemented data flow is demonstrably `repo-map FileFacts → codebaseScan projection → consumers`.
2. `codebaseScan` contains no independent repository parsing or separately authoritative fact model.
3. For an identical canonical snapshot, repeated projection runs produce identical output.
4. Overlapping projected facts match canonical `FileFacts`; duplicate or conflicting entries are not introduced.
5. Applying a newer canonical snapshot removes facts that no longer exist.
6. The current `codebaseScan` consumer contract remains compatible without changing existing test expectations.
7. Repository inspection confirms that the VSIX has no source, build, packaging, or runtime dependency on the repo-map extract.
8. The VSIX successfully loads repository data through `codebaseScan` and retains its existing core behavior.
9. All existing tests run unchanged and pass.
10. Focused WS5 tests pass and cover the consolidation boundaries.
11. WS3 and WS4 are complete, and Sonnet review is recorded as approved.

## Out of scope

- Changes to repo-map extraction algorithms or scanner internals not required for convergence.
- New VSIX features or visual redesign.
- New `FileFacts` fields unrelated to the shared contract.
- Breaking changes to the public `codebaseScan` response.
- Broad refactors of the agent runtime, API surface, or unrelated packages.
- Test rewrites, expectation changes, or snapshot regeneration.
- Long-term performance optimization, additional language support, or new storage technologies.
