# PRD: R7 — DONE.md resolved entry and gated release notes

## Problem & Goal

Completed work is easy to lose in agent handoffs, and release notes can ship without a human check or with the wrong changelog type. R7 requires a durable resolved record plus a confirmation gate before any release notes are published.

**Goal:** When this work is resolved, write a `DONE.md` entry and ask before publishing release notes. Classify changelog items as: persona delegation = **new**, persisted diagnostics = **improvement**, 403 chain = **no note**.

## Target users / ICP roles

- Downstream implementation and docs agents sharing this PRD
- Maintainers who review `DONE.md` and approve release notes
- Release publishers who must not ship notes without an explicit ask

## Scope

- Append a resolved entry to `DONE.md` for R7
- Pre-publish confirmation before any release-notes publish step
- Changelog classification and inclusion rules for the three named items
- Wording that is accurate, concise, and user-facing where a note is required

## Functional requirements

1. **Resolved entry.** On resolution, append one `DONE.md` entry that states R7 is done, that release notes are gated on an ask, and that the three classification rules were applied.
2. **Ask before publish.** Do not publish release notes until the user is asked and confirms. Silence, implied success, or agent-only completion is not confirmation.
3. **Persona delegation → new.** If notes are approved, include persona delegation under **New**.
4. **Persisted diagnostics → improvement.** If notes are approved, include persisted diagnostics under **Improvements**.
5. **403 chain → no note.** Never include the 403 chain in release notes (no heading, bullet, or footnote).
6. **No silent publish.** If confirmation is declined or not given, keep `DONE.md` as the record of resolution and leave release notes unpublished.

## Acceptance criteria

- `DONE.md` contains a resolved R7 entry covering the gate and the three classification rules.
- No release-notes publish occurs unless the user was asked and confirmed.
- Approved notes list persona delegation as **new** and persisted diagnostics as an **improvement**.
- Approved notes omit the 403 chain entirely.
- Declined or missing confirmation results in no published notes and no partial changelog for the omitted item.

## Out of scope

- Changing persona-delegation, diagnostics persistence, or 403-chain product behavior
- Auto-publishing, scheduling, or backfilling older changelog entries
- Release tagging, version bumps, or store/marketplace listing copy
- Rewriting historical `DONE.md` entries unrelated to R7

## Requirements

R7 is a **close-out** of staffed-work / chat-diagnostics (PRD 27), not a product-behavior change. The BA-owned contract below is the only source of truth for the resolved `DONE.md` entry, the release-notes confirmation gate, and changelog classification. Downstream agents must implement this section as written; they must not invent additional changelog items, auto-publish notes, or rewrite historical `DONE.md` entries.

### R7-REQ-1 — Durable resolved record (`DONE.md`)

**Given** R7 work is resolved (persona-delegation, persisted diagnostics, and 403-chain items have reached their own done state, or this ticket is the close-out of that set).

**When** the closer records resolution.

**Then** append **exactly one** new entry to the repository root `DONE.md`. The entry MUST:

1. Use the existing house style already in `DONE.md` (newest-first):
   - Heading: `## YYYY-MM-DD — #2568 R7 close-out: DONE.md resolved entry and gated release notes`
   - Body as a bullet list with these labels, in this order: `**What:**`, `**Why:**`, `**Where:**`, `**Verify:**`.
2. State in `What:` that R7 is resolved.
3. State in `What:` or `Why:` that release notes are **gated on an explicit user ask** and are **not published** by this close-out.
4. State the three classification rules that were applied (see R7-REQ-3).
5. Point `Where:` at `DONE.md` (this entry) and, if a notes draft is kept locally, at that unpublished draft path — never at a published changelog path.
6. Be additive. Do not edit, reorder, or rewrite any historical `DONE.md` entry unrelated to R7.

The `DONE.md` entry **is** the record of resolution. It is not a substitute for published release notes, and it is not itself a publish step.

### R7-REQ-2 — Ask-before-publish gate

**Given** a closer is about to emit user-facing release notes for this R7 set.

**When** they reach any publish step (changelog file write that ships, store listing, marketplace notes, or equivalent).

**Then** they MUST stop and **ask the user** for confirmation before publishing. Confirmation rules:

| Signal | Meaning | Action |
|---|---|---|
| Explicit yes (e.g. “publish”, “yes, ship the notes”, “confirmed”) | Confirmed | Publish only the classified items in R7-REQ-3 |
| Explicit no / decline | Declined | Do not publish. Keep the `DONE.md` entry as the resolved record |
| Silence, implied success, agent-only completion, CI green, PR merge, or “the work is done” | **Not** confirmation | Do not publish |
| Partial answer that does not name publish | **Not** confirmation | Do not publish |

- Asking is a blocking human turn. The agent must not treat its own intent, a PRD checkbox, or a sibling ticket’s merge as the ask.
- If confirmation is declined or never given, leave release notes **unpublished**. Do not write a partial changelog, a “coming soon” stub, or a footnote that names the omitted 403 chain.
- This ticket’s own resolution (the `DONE.md` entry) MUST still be written even when notes are not published (see R7-REQ-6).

### R7-REQ-3 — Changelog classification (only if confirmed)

If and only if R7-REQ-2 confirmation is given, published notes MUST classify the three named items as follows. No other R7 items may be added.

| Item | Changelog category | Include? | User-facing wording (required if included) |
|---|---|---|---|
| Persona delegation (`as_agent` / run-as-teammate spawn) | **New** | Yes | Short, user-facing: operators can spawn a child agent that runs **as** a named workspace teammate (that agent’s role, bio, skills, personality), so the delegated slice is done in that teammate’s voice. |
| Persisted diagnostics (brain-chat / staffed-work diagnostic rows that survive the turn) | **Improvement** | Yes | Short, user-facing: chat/staffed-work diagnostics now persist so a later turn can read why a run failed or stalled, instead of losing the trace when the turn ends. |
| 403 chain (GitHub/API 403 handling, rate-limit, or auth-chain repair) | **no note** | **Never** | Do not mention. No heading, bullet, footnote, “also fixed”, or parenthetical. |

Category labels in the published notes MUST be the changelog’s existing heading style mapped as:

- Persona delegation → **New** (or the repo’s equivalent `### New` / `category=new`).
- Persisted diagnostics → **Improvements** (or the repo’s equivalent `### Improvements` / `category=improvement`).
- 403 chain → omitted entirely (no `### Fixes` row, even if the repo uses that heading for other work).

Wording MUST be accurate, concise, and user-facing. Do not paste internal ticket ids, file paths, or SQL migration names into published notes.

### R7-REQ-4 — 403 chain exclusion is absolute

**Given** notes are being drafted or published.

**When** any text about the 403 chain would appear (heading, bullet, “internal fix”, footnote, “see also”).

**Then** omit it. A declined or missing confirmation MUST NOT produce a partial changelog whose only remaining content is the 403 chain, and a confirmed publish MUST NOT smuggle the 403 chain under another item’s bullet.

### R7-REQ-5 — No silent or scheduled publish

- Do not auto-publish, schedule, or backfill older changelog entries as part of R7.
- Do not bump versions, cut tags, or rewrite store/marketplace listing copy.
- Do not change persona-delegation, diagnostics-persistence, or 403-chain **product** behavior under this ticket. Those behaviors are owned by their own tickets; R7 only records and (if asked) notes them.

### R7-REQ-6 — Resolution without published notes

**Given** confirmation is declined or not given.

**When** the closer finishes.

**Then:**

1. `DONE.md` still contains the R7-REQ-1 entry (gate + three classification rules recorded).
2. No release-notes file is created or updated for these three items.
3. No partial changelog exists for the omitted 403 chain.
4. The ticket is still considered **resolved** for R7 close-out. Unpublished notes are the correct outcome, not a defect.

### R7-REQ-7 — Traceability

- Ticket: **#2568**.
- Parent spec: PRD 27 “R7 — Close-out”: *When this work is resolved, write a `DONE.md` entry and ask before publishing release notes (persona delegation = `category=new`, persisted diagnostics = `improvement`, 403 chain = no note).*
