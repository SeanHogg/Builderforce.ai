# PRD: SOC 2 Type I Audit

**Status:** Planned · **Priority:** P1, Revenue · **Target:** Q4 2026 · **Repo:** seanhogg/builderforce.ai (`main`)
**Baseline:** investigation 2026-10-12 (chat 142). Re-verify every cited count before sign-off.

## Problem & Goal

Enterprise buyers treat an independent SOC 2 report as a procurement gate. Builderforce has no Type I engagement: no contracted CPA, no system description, no management assertion, no Type I report, no trust-center certification artifact. `docs/compliance` is a privacy pack (DPA, incident response, subprocessors, DPIA), not an ISMS. `agent-runtime/docs/SECURITY.md` is vulnerability reporting only.

Tenant SOC 2 tooling is largely built and must not be described as the audit. `SOC2_BASELINE` tracks 28 Common Criteria controls; the marketing FAQ says 30. `soc2Scan()` is labelled not a certification. The public `/soc2` page does not claim certification. PRD 08 Phase 7 is still Planned.

A Type I is an independent CPA examination of whether the description is fairly presented and controls are suitably designed and placed in operation at a point in time. Security is the required Trust Services Criterion. Current design claims are indefensible without remediation or narrowing:

- Logical isolation (CC6): 271 unscoped tenant queries, ~35 inserts without `segmentId`, no row-level security.
- Change and vulnerability management (CC7/CC8): esbuild GHSA in 6 packages, no CI migrate dry-run, 588 lint errors, no repo-root `CODEOWNERS`.
- Operations: Cloudflare Free and Neon Free in production, no SIEM export; Stripe secrets unset; worker `JWT_SECRET` residual open since 2026-07-24.

**Goal:** In Q4 2026 management signs a Security-only Type I assertion that matches production, an independent CPA examines that design as of a named date, and the issued report is shared under a restricted distribution policy. The product tracker may feed Builderforce's own evidence pack; it is not the attestation.

## Target users / ICP roles

Management signer; compliance owner; control owners (engineering, security, operations); external CPA firm (examines design only); customer security reviewers (consume the report, never operate the engagement, must not be handed the readiness diagnostic as a report).

## Scope

Company examination of Builderforce production as of one Q4 2026 date, Security TSC only: CPA engagement; system description; seven approved policies (ISMS, access control, change management, incident response, vendor management, SDLC, backup); one control matrix; evidence pack; design gate; management assertion and report handling; claim control; repo changes needed for a true change-management and isolation design (repo-root `CODEOWNERS`, CI migrate dry-run, dependency patching, tenant-scope enforcement on attested paths, secrets closure).

## Functional requirements

1. **Engagement** — executed letter: Type I, Security only, as-of date, boundary, locations, subservice method (carve-out vs inclusive); firm, signer, distribution terms recorded. As-of date is not scheduled before the design gate is passed or risk-accepted by the signer.
2. **System description** — services, software, infrastructure, data, people, procedures, trust boundary, CUECs, subservice orgs; states Cloudflare Free, Neon Free, no SIEM export while true; lists out-of-boundary items.
3. **Policies** — seven policies, each with owner, approver, effective date ≤ as-of date. IR covers production, not only privacy. Vendor policy covers listed subprocessors plus any other in-boundary operator.
4. **Control matrix** — one matrix owned by compliance: criterion, control statement, owner, design evidence, open exception. Reconciles the 28-control baseline and the FAQ "30"; is the source of customer-facing counts.
5. **Evidence pack** — per row: retrieval path, approved policy, config/workflow, owner, as-of snapshot. Product export only for Builderforce's own tenant; no customer data. `soc2Scan()` and the security-agent sweep labelled internal indicators.
6. **Design gate** — each blocker remediated in the boundary or removed from the description with a signed management exception (isolation, esbuild GHSA, CI migrate dry-run, lint vs control wording, `CODEOWNERS`, Stripe secrets, residual `JWT_SECRET`, monitoring wording).
7. **Assertion and report** — assertion signed after the gate; controlled fieldwork access; report stored in restricted location, never in public git; opinion, exceptions, distribution recorded.
8. **Claims** — `/soc2`, FAQ, sales stay non-certified until issuance; afterwards point at the report, not at `SOC2_AUDIT_ID`, tracker or agent.

## Acceptance criteria

- Engagement letter executed (Type I / Security / Q4 2026 as-of / boundary / subservice method).
- System description approved by signer and matches verified production facts.
- Seven policies approved, effective on or before the as-of date.
- Control matrix covers the CPA's Security set; every row has owner + evidence link; FAQ count equals the examined set.
- Design-gate recount attached for all eight blocker items; each closed or has a signed exception.
- Assertion signed; CPA report in restricted store with opinion, exceptions, recipients recorded.
- Public pages not "certified" before issuance; readiness surfaces keep the not-a-certification copy.
- Builderforce-tenant tracker export producible, with the evidence index stating it is not the attestation.

A qualified or adverse opinion does not meet the goal; if fieldwork would produce one, the as-of date moves.

## Out of scope

SOC 2 Type II; Availability/Confidentiality/Processing Integrity/Privacy criteria; buying a SIEM or leaving free tiers (unless the gate cannot otherwise pass); full Identity roadmap; PRD 08 Phase 7; rebuilding tracker/scanners/UI beyond misleading copy; auditing customer tenants; ISO 27001; offensive testing or PoC code.

### Gate rules (testable)

- **G-1 Isolation:** attested data paths show a tenant predicate or RLS, and attested inserts carry `segmentId`. Evidence is a re-run count of unscoped queries (baseline 271) and missing-`segmentId` inserts (baseline ~35) restricted to attested paths; remaining items outside the boundary are listed in the description's exclusions.
- **G-2 Vulnerability:** audit result for the esbuild GHSA across the six named packages is clean, or a compensating control plus signed risk acceptance is in the matrix.
- **G-3 Change control:** CI runs a migrate dry-run on the attested path; the control statement wording is checked against actual CI jobs. If lint-clean merge is claimed, lint errors (baseline 588) are zero and enforced; otherwise the wording is narrowed and debt ticketed.
- **G-4 CODEOWNERS:** repo-root `CODEOWNERS` exists and is cited by the change-management control (a `.github/CODEOWNERS` suffices only if the policy cites that path and branch protection requires code-owner review).
- **G-5 Secrets:** Stripe secrets present in the secret store (existence check, never values) or Stripe excluded from the description; the 2026-07-24 residual worker `JWT_SECRET` rotated/removed and the in-use worker secret is a different value (verified by rotation record, not by reading secrets).
- **G-6 Monitoring:** wording matches reality, including free-tier logging limits and weekly security sweep; no SIEM claim.
- Any gate item neither closed nor excepted by the signer fails the gate and blocks BR-2 date scheduling and BR-11 signature.

### Non-functional and compliance requirements

- **NFR-1 No secrets or customer data** in the repo, evidence pack or PRD; evidence references secret *names*, never values.
- **NFR-2 Report custody:** CPA report, workpapers and assertion are stored outside public git; the repo holds only the evidence index and a pointer.
- **NFR-3 Traceability:** every matrix row links to a policy section and a design artifact; every acceptance criterion maps to a BR/G item (table below).
- **NFR-4 No overstated claims:** wording reviewed by the compliance owner before publication; certification language only after report issuance.
- **NFR-5 Safety of remediation work:** remediation is patching, scoping, rotation and accurate description only; no exploit or PoC code.

### Assumptions and open questions

1. **Assumption:** the management signer is a named company officer; if none is designated, BR-2 cannot start (needs product decision).
2. **Assumption:** as-of date is chosen after G-1…G-6 disposition; target window November–December 2026.
3. **Open:** whether Stripe is inside the boundary (decides G-5 path); owner: signer.
4. **Open:** whether isolation remediation lands via the Identity roadmap before the as-of date or the description narrows (G-1); owner: engineering lead + signer.
5. **Open:** CPA fee/budget approval; owner: signer.
6. **Risk:** free-tier hosting and absent SIEM may draw CPA exceptions on monitoring; mitigation is accurate description (G-6), not a silent upgrade.
