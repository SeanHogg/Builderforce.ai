# PRD: App manifest schema and validate tool catalog

## Problem & Goal

Launch and composer prompts already advertise `app_manifest.schema` and `app_manifest.validate`, but neither tool exists. Agents that author or launch a Builderforce app manifest (`builderforce.json`, including an `ai` resource) have no contract-backed way to read the v1 schema or to accept or reject a manifest. An API-local validator would drift from core.

Goal: add a dedicated app-manifest tool catalog that is the launcher's only accept/reject path for manifests. Both tools call the pure manifest exports of `@seanhogg/builderforce-webcontainers-core` and are registered once, the same way as the blueprint tool catalog. Contract: `docs/specs/app-manifest-ai-resource.md` §8 (epic #6994, task #6997). Repo: `seanhogg/builderforce.ai`, base `main`. No code exists for this slice yet.

## Target users / ICP roles

- Launch and composer agents that must schema-check a manifest and accept or reject it before launch.
- Tenant project owners and app authors editing `builderforce.json`, including manifests that declare an `ai` resource.
- API and brain-embedded engineers extending the LLM tool surface without growing `builtinMcpService.ts`.

## Scope

In scope:

- New catalog file `Builderforce.ai/api/src/application/llm/appManifestToolCatalog.ts`, next to `appBlueprintToolCatalog.ts`.
- Tools `app_manifest.schema` and `app_manifest.validate`, spread once into the builtin tool list the same way `APP_BLUEPRINT_TOOLS` is spread (about line 4194 of `builtinMcpService.ts`). Implementations stay in the catalog file.
- Calls only to the pure export `@seanhogg/builderforce-webcontainers-core/manifest`: `validateManifest`, `APP_MANIFEST_SCHEMA_V1`, `RESOURCE_CAPABILITIES`, `resourceCapability`, `toApplicationSpec`, `describeManifestIssue`.
- A small alias expansion next to `findTools` in `brain-embedded/src/toolRouter.ts`.
- Tests run with the api package vitest runner, plus existing brain-embedded coverage for `findTools`. Leave the worktree uncommitted (`leave_uncommitted`; owner run ships once).

Known blocker, ticket eebdbdce, core slice #6996: published `@seanhogg/builderforce-webcontainers-core@2026.11.12` does not know the `ai` resource. Its validator emits `unknown-resource-type` for `type: 'ai'`. The API does not depend on that package today. This slice may add the dependency only so the `/manifest` import resolves. It must not mask that mis-report. Correct `ai` classification waits until the #6996 release is published and the API dependency is updated to it.

## Functional requirements

1. Catalog module
   - Own file only. Do not add tool implementations to `builtinMcpService.ts`.
   - One spread registration, matching the `APP_BLUEPRINT_TOOLS` pattern.
   - Advertised names are exactly `app_manifest.schema` and `app_manifest.validate`, the names already used by `OVERRIDE_HINT` in `api/src/application/llm/blueprintOverrideHint.ts` and by the launch/composer prompt. `check-prompt-tool-names.mjs` must pass.
   - No second validator, schema document, or capability table in the API. No dependency on the browser package. Do not fork core or special-case `type: 'ai'`.

2. `app_manifest.schema`
   - Args: optional `target` of type `ManifestTargetId`. Default target is `browser`.
   - Returns `APP_MANIFEST_SCHEMA_V1`, capabilities for that target via `RESOURCE_CAPABILITIES` / `resourceCapability`, and a short field guide. The guide covers `version`, that services require `runtime` and `command`, `roles`, `uses`, and the `ai` shape.
   - Guide text describes the core schema. It does not replace or reinterpret it.

3. `app_manifest.validate`
   - Args: optional `projectId` (number), optional `content` (string), optional `path` (string), optional `environment` (string).
   - Exactly one of `content` or `path`. If neither or both are set, return a typed argument error and do not read the repo.
   - Content-only: `projectId` is not required and there is no repo read.
   - Path: `projectId` is required. Reuse `ownedProjectId` from `appBlueprintToolCatalog.ts` (line 63). Refuse when `projectId` is missing or the project is not owned by the caller, including another tenant's project. Refusal happens before any repo read.
   - Read the project file only after `ownedProjectId` succeeds. Do not add an unscoped filesystem read.
   - Response shape follows `docs/specs/app-manifest-ai-resource.md` §8. Issues are the typed issues from `validateManifest` for that input, with text from `describeManifestIssue`. When `environment` is set, also include capability declines from `toApplicationSpec` for that environment. When `environment` is omitted, do not add capability declines.
   - That payload is the launcher accept/reject decision. Empty issues and no declines means accept; any issue or decline means reject. This slice does not add a parallel validator or launcher policy.

4. Finder aliases
   - Next to `findTools`, map exactly these phrases to both tools: `app manifest`, `builderforce.json`, `ai resource`.
   - Do not alias bare `service`, `schema`, or `launch` to either tool. Do not add other phrases.

5. Hint compatibility
   - Do not rewrite the `OVERRIDE_HINT` example into an invalid v1 manifest. `blueprintOverrideHint.test.ts` must still parse it.

## Acceptance criteria

- For the same input, `app_manifest.validate` issues equal `validateManifest` issues, plus `toApplicationSpec` capability declines when `environment` is set. A vitest locks that equality against the installed core functions, not a hand-rolled `ai`-success oracle.
- A path call with no `projectId`, or with a project the caller does not own, is refused before any repo read. A test locks the refusal and that the reader was not called.
- A content-only call validates with no `projectId` and no repo read.
- Neither or both of `content` and `path` returns an argument error and does not read the repo.
- `app_manifest.schema` with no target returns `APP_MANIFEST_SCHEMA_V1`, the field-guide topics above, and browser capabilities. A non-default `target` returns capabilities for that target.
- `findTools`, with the alias expansion, returns both tools for `app manifest`, `builderforce.json`, and `ai resource`. Bare `service`, `schema`, and `launch` do not resolve to either tool.
- Tool bodies are not added to `builtinMcpService.ts`. The catalog is spread once at the blueprint-tools registration site.
- `check-prompt-tool-names.mjs` passes. `blueprintOverrideHint.test.ts` still parses the `OVERRIDE_HINT` example as a valid v1 manifest.
- Catalog, ownership, parity, and hint-parse tests run with the api package vitest runner. findTools alias coverage runs with the existing brain-embedded test runner. No new runner.
- Changes remain uncommitted.

## Out of scope

- Implementing or correcting `ai` resource support in `@seanhogg/builderforce-webcontainers-core` (#6996), or bumping the API onto that release.
- A local validator, schema, or capability map that hides `unknown-resource-type`.
- Any dependency on the browser package.
- Tool logic inside `builtinMcpService.ts`.
- Aliases for bare `service`, `schema`, or `launch`, or any phrase other than the three named above.
- Launcher, composer, or `OVERRIDE_HINT` copy changes beyond keeping already-advertised names and the existing v1 example valid.
- Repo writes, manifest repair, or launch execution. These tools only describe the schema and validate.
- Committing or shipping.
