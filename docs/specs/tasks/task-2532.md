# PRD 26 P0 — Public visitor booking + advisory meeting join

**Status:** WIP  
**Priority:** P0  
**Spec refs:** §4.2 J1, §9

## Problem & Goal

Logged-out visitors cannot book time with an advisor from a public profile. The ATS interview booker (`/book/[token]`) already solves tokenised public scheduling, but it is interview-specific and must not be reused as a security hole.

**Goal:** Generalise the ATS `/book/[token]` pattern so a logged-out visitor can book an advisor from a profile, create an `advisory` meeting (advisor = organizer, visitor = attendee), land on a chrome-less confirm + join page, and join by token — without opening the meetings router to unauthenticated traffic, leaking availability internals, or letting a stranger book and sit in a meeting.

**Kill criterion:** A stranger cannot book and sit in a meeting.

## Target users / ICP roles

| Role | Auth | Intent |
|---|---|---|
| Public visitor | Logged out | Discover an advisor profile, pick a free slot, give name + email, receive confirm + join link |
| Advisor | Authenticated tenant member | Publish bookable availability; receive advisory meetings on-platform and on a connected calendar when present |
| Downstream agents | n/a | Implement against this PRD only; do not invent extra meeting kinds, auth bypasses, or chrome |

## Scope

1. **Public availability read** — tokenised / slug-scoped; future free slots only.
2. **Public book** — visitor name + email creates `kind=advisory`; advisor organizer, visitor attendee.
3. **Chrome-less confirm + join link** — `NO_CHROME_PREFIXES`.
4. **Visitor join-by-token** — copy the `interviewScheduling` token→tenant pattern; do **not** punch a hole in `authMiddleware` for the whole meetings router.
5. **Kind registration** — add `advisory` to `KINDS` in `meetingRoutes.ts`. Advisory does **not** default team-ceremony chat on.
6. **Calendar mirror** — when the advisor has a connected calendar, mirror the advisory meeting to it.

## Functional requirements

### FR1 — Public availability read

- Endpoint is tokenised and/or slug-scoped to a single advisor. Unscoped or cross-advisor reads are forbidden.
- Response contains **future free slots only**.
- Never return raw availability windows.
- Never return other attendees, other meetings, or any PII of existing calendar events.
- Past slots, busy slots, and slots already taken must not appear.
- Invalid, expired, or unknown token/slug → not found (no existence oracle beyond that).

### FR2 — Public book (visitor → advisory meeting)

- Logged-out visitor submits **name + email** and a slot from FR1.
- Created meeting: `kind = advisory`.
- Organizer = the advisor bound to the token/slug.
- Attendee = the visitor (name + email). No other attendees.
- Slot must still be free at write time; conflict → fail closed, no meeting.
- Do not create interview, team-ceremony, or any other kind.
- Do **not** default team-ceremony chat on for `advisory`.

### FR3 — Chrome-less confirm + join link

- Success lands on a chrome-less confirm page with a join link.
- Confirm and join URLs use `NO_CHROME_PREFIXES`.
- Join capability is token-bound to **this** meeting and **this** visitor attendee.

### FR4 — Visitor join-by-token

- Join authenticates the visitor via the booking/join token, scoped to tenant the same way `interviewScheduling` does token→tenant.
- **Do not** exempt the meetings router from `authMiddleware`.
- Token grants join (and only join) for that advisory meeting. No list, no mutate, no other meetings, no other tenants.
- Missing/invalid/expired/mismatched token → deny. No meeting payload leak.

### FR5 — Kind + routing

- Add `advisory` to `KINDS` in `meetingRoutes.ts`.
- Advisory is a first-class kind everywhere kind is validated.
- Chat / team-ceremony defaults stay off for advisory.

### FR6 — Connected calendar mirror

- If the advisor has a connected calendar, mirror the advisory meeting to it (create on book; keep times/title/attendee email consistent with the platform meeting).
- If no connected calendar, platform meeting still succeeds.
- Mirror failure must not leak calendar internals to the visitor; visitor still gets confirm + join if the platform meeting committed.

### FR7 — Abuse / stranger kill

- Booking requires a valid advisor-scoped token/slug **and** a currently free slot.
- Join requires a valid meeting-scoped visitor token issued from that booking.
- A stranger with no token, a guessed token, or another meeting’s token cannot book or sit in the meeting.

## Acceptance criteria

1. Logged-out visitor, valid advisor token/slug: sees only that advisor’s **future free slots**; payload has no raw windows and no other attendees.
2. Same visitor books with name + email: meeting exists with `kind=advisory`, advisor organizer, visitor attendee, selected slot.
3. Confirm page is chrome-less (`NO_CHROME_PREFIXES`) and shows a join link for that meeting.
4. Visitor join-by-token works; meetings router remains behind `authMiddleware`; token→tenant follows `interviewScheduling`.
5. `advisory` is in `KINDS` in `meetingRoutes.ts`; advisory meetings do not get team-ceremony chat by default.
6. Advisor with connected calendar: advisory meeting appears on that calendar. Advisor without: book still succeeds.
7. **Kill (stranger cannot book and sit in a meeting):** no/invalid token cannot list slots, create a meeting, or join; another advisor’s or meeting’s token cannot access this advisor or this meeting; busy/past slots cannot be booked.
8. Invalid token/slug and slot-conflict paths fail closed with no extra data.

## Out of scope

- Logged-in visitor identity linking, account creation, or magic-link login beyond the join token.
- Reschedule, cancel, or multi-slot holds from the public page.
- Payments, paid intro calls, or packaging.
- Punching `authMiddleware` holes on the meetings router or any other router.
- Defaulting team-ceremony chat (or any ceremony UX) on for advisory.
- Returning raw windows, busy details, or other attendees on public availability.
- New meeting kinds other than adding `advisory`.
- Advisor-side booking inbox, notifications redesign, or profile CMS.
- Changing ATS interview `/book/[token]` behaviour except where the shared token→tenant pattern is copied.
- Recurring availability editors, timezone pickers beyond what ATS book already uses, or calendar write-back other than the advisor’s connected calendar mirror.
