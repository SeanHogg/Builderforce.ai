# PRD: Corrupt local-first snapshot must fail closed

## Problem & Goal

`clients/vscode/src/localFirstStore.ts` `loadExistingSnapshot` already fails closed on a corrupt snapshot: it copies the file to `local-first-v1.json.corrupt-<timestamp>`, leaves the original in place, and throws `LocalFirstSnapshotCorruptError`. `planSnapshotLoad` returns `{ action: "preserve", ... }` on both parse failure and shape failure. The doc comment states this is deliberate: a corrupt file is not opened as an empty store, so the next open does not succeed with nothing.

An untracked test, `clients/vscode/src/localFirstStore.transaction.test.ts`, disagrees. Its case titled "recovers a corrupt snapshot to an empty store after preserving the file, and does not only throw" currently fails. That file has never been committed (`git log --all --` on that path is empty). The committed pin in `clients/vscode/src/localFirstStore.recovery.test.ts` already asserts rejection (including "throws after copying a file validSnapshot rejects, WITHOUT AN EMPTY SNAPSHOT") and covers the shape-failure plan.

Recover-to-empty is the wrong product behaviour. A file truncated mid-write would silently present zero chats, zero projects, and zero tickets, and the preserved `.corrupt-` copy is not surfaced, so the user gets no signal that data was dropped. Failing closed at least tells them.

**Goal:** Keep the shipped fail-closed behaviour. Align the one disagreeing untracked case so it asserts rejection plus the preserved `.corrupt-` file. Do not change `loadExistingSnapshot` or `planSnapshotLoad` to recover to an empty store. All 8 cases in `localFirstStore.transaction.test.ts` must pass. This conflict was verified on 2026-10-19; nothing has been changed yet.

## Target users / ICP roles

- **Local-first VS Code extension user:** has chats, projects, and tickets only in the local snapshot/journal. They must not lose that data silently after a torn or corrupt snapshot.
- **Extension maintainer / implementing agent:** must not "fix" the red test by weakening crash-safe open behaviour that `recovery.test.ts` already ships.

## Scope

- Resolve the conflict in favour of fail-closed, in `clients/vscode/src/localFirstStore.transaction.test.ts` only, unless a later explicit product decision says otherwise (see Out of scope).
- Rewrite or replace the single failing case so it expects `loadExistingSnapshot` to reject with `LocalFirstSnapshotCorruptError` (same shape as the committed recovery tests: `rejects.toMatchObject`) and expects the corrupt bytes to have been copied to a `local-first-v1.json.corrupt-<timestamp>` sibling. Do not expect an empty store, a successful open, or a thrown-and-then-recovered path.
- Leave the other 6 cases in that file as they are if they still pass. Review them before the file is committed for the first time; committing the path lands the whole file.
- Do not edit `loadExistingSnapshot`, `planSnapshotLoad`, or `localFirstStore.recovery.test.ts` to satisfy the untracked case.

Passing cases to preserve (titles as found):

- acks a chat and its sync event in one journal frame
- acks a project and a ticket
- acks an audit-run and an execution
- does not acknowledge a transaction that throws
- reads the committed frame after a torn tail
- ignores a corrupt snapshot cache when the journal already has the chat

## Functional requirements

1. A snapshot that fails parse or fails shape validation is not opened as an empty store. Open throws `LocalFirstSnapshotCorruptError`.
2. Before the throw, the corrupt file is copied to `local-first-v1.json.corrupt-<timestamp>`. The original remains in place so a later open fails closed again instead of succeeding with nothing.
3. `planSnapshotLoad` continues to return `{ action: "preserve", ... }` for both parse failure and shape failure.
4. The untracked transaction test's corrupt-snapshot case asserts (1) and (2). It must not assert recover-to-empty or "does not only throw."
5. The other six transaction cases remain green and are not rewritten to change product behaviour.
6. After the edit, all 8 cases in `localFirstStore.transaction.test.ts` pass, and the committed recovery tests still pass unchanged.

## Acceptance criteria

- `loadExistingSnapshot` and `planSnapshotLoad` are unchanged in behaviour and still match their existing doc comment and `localFirstStore.recovery.test.ts` (rejection on corrupt/shape failure; preserve copy; no empty snapshot).
- The former "recovers a corrupt snapshot to an empty store…" case is gone or rewritten. The replacement rejects with `LocalFirstSnapshotCorruptError` and checks that a `.corrupt-<timestamp>` copy exists. It does not require a successful empty open.
- `localFirstStore.transaction.test.ts` is green: 8/8. The six previously passing cases still pass without behaviour changes to production code.
- No second, contradictory expectation is left in the tree (recovery tests still reject; transaction tests no longer demand recover-to-empty).
- The file is reviewed as a first-time add before commit. This conflict is not treated as a G26 deliverable.

## Out of scope

- Changing shipped fail-closed open to recover-to-empty, adding a surfaced warning, or deleting the preserved original. That would contradict committed `recovery.test.ts` and needs an explicit product decision raised separately — do not silently change both sides.
- Gap G26 (#5860) crash-safe store work itself (VSIX slice already landed in ccb17e7ea; Rovr and Web still open). This task only settles the test/code disagreement.
- New UI for `.corrupt-` files, journal format changes, or edits outside the transaction test (and a review of that untracked file) unless required to keep the six good cases green without weakening fail-closed.
