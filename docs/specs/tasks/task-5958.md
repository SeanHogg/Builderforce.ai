## Problem & Goal

The BuilderForce chat panel (secondary sidebar) currently mounts the full CreationCanvas behind the conversation. Canvas chrome — the MAKE/RUN/MEASURE/REACH bar, surface chips, and command bar — renders as a band across the top of the Chat Panel, crowding the conversation and mixing two distinct surfaces.

Move the codebase visualization out of the Chat Panel into its own editor panel beside the chat. The Chat Panel must show the conversation only. The visualization must open in the existing dedicated VisualizationPanel via `builderforce.openVisualization`, in `ViewColumn.Beside`.

## Target users / ICP roles

- Builders using the BuilderForce VS Code extension who chat and inspect the codebase visualization in the same session.
- Downstream agents implementing and verifying the panel split in `seanhogg/builderforce.ai` (base `main`).

## Scope

- Stop mounting CreationCanvas (and its chrome) inside the Chat Panel webview.
- Open and reveal the existing VisualizationPanel editor surface beside the chat (`ViewColumn.Beside`, command `builderforce.openVisualization`).
- Add a one-click, discoverable control in the chat header that opens or reveals that panel.
- Preserve the existing editor-tab canvas (`surface: 'graph'`), the change-tree toggle, and any hostSurfaces still required by the graph surface in the editor tab.
- Preserve chat composer, ticket rail, and run bridge behavior.

## Functional requirements

1. Chat Panel content is conversation-only. CreationCanvas is not mounted behind or above the conversation. The MAKE/RUN/MEASURE/REACH bar, surface chips, and command bar do not appear in the Chat Panel.
2. Codebase visualization renders in the dedicated VisualizationPanel, opened as an editor panel beside the chat (`ViewColumn.Beside`) through `builderforce.openVisualization`. Re-invoking the command reveals the existing panel rather than stacking duplicates.
3. The chat header includes a visible control (button or equivalent) whose single click opens or focuses that visualization panel.
4. The editor-tab canvas with surface `'graph'` continues to render and receive `hostSurfaces` as it does today.
5. The change-tree toggle continues to switch the relevant canvas surface without depending on the Chat Panel mount.
6. Chat composer, ticket rail, and run bridge keep their current behavior and wiring.

## Acceptance criteria

1. The Chat Panel renders the conversation only — no canvas chrome band above it.
2. The visualization canvas opens in a separate editor panel beside the chat (`ViewColumn.Beside`), using the existing dedicated VisualizationPanel surface (`builderforce.openVisualization`).
3. A discoverable control in the chat header opens or reveals that panel in one click.
4. The existing editor-tab canvas (surface `'graph'`) and the change-tree toggle keep working.
5. No regression to the chat composer, ticket rail, run bridge, or the canvas surfaces that still need `hostSurfaces` (the graph surface in the editor tab).

## Out of scope

- Redesigning CreationCanvas chrome, surface chips, or MAKE/RUN/MEASURE/REACH behavior beyond relocating where the visualization is hosted.
- New visualization features, new surfaces, or changes to graph layout and data.
- Replacing VisualizationPanel or changing the `builderforce.openVisualization` command contract beyond using it to open or reveal the panel beside chat.
- Chat composer, ticket rail, or run-bridge feature work.
- Moving the Chat Panel itself out of the secondary sidebar.
