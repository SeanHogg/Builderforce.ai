# PRD: Phase 7 — Online Performance Learning

**Ticket:** #6744 · **Parent epic:** #6737 · **Lane:** ready
**Repo:** `seanhogg/builderforce.ai` · **Branch:** `builderforce/task-6744`
**Role of this document:** the business-analyst Requirements section of the ticket PRD. Design, implementation, review, test evidence, and acceptance sign-off belong to their owning roles and are deliberately not written here.

## Problem & Goal

### Problem

Once a run's execution and memory systems are stable, the runtime still applies a fixed strategy to every workload: the same worker count, the same scheduling, the same prefetch, the same cache policy. Nothing records which of those choices actually performed well for which kind of work, so nothing can improve them. Hand-tuning per workload does not scale, and an unbounded optimizer that silently rewrites model output or memory semantics would be worse than the fixed strategy.

### Goal

A small, CPU-only learner that, after execution and memory are stable, watches how runs actually behave and recommends a better **prevalidated** strategy for the workload it sees. Every recommendation is measurable and explainable, reversible, and cheap enough that its own cost is reported. It can be switched off entirely so deterministic tests see exactly the baseline strategy. It never changes what a model answers or what memory means.

## Target users / ICP roles

- **Runtime engineers** who own worker counts, scheduling, prefetch, and cache policy and need evidence before changing a default.
- **QA and benchmark owners** who need a deterministic mode in which learning is provably absent, so a test result is attributable to the code under test and not to a learned adjustment.
- **Operators** who need to see why a strategy changed and to roll it back without redeploying.
- **Downstream agents on this ticket** (architect, developer, reviewer, QA, validator), who need one shared contract before they design or build.

## Scope

### In scope

1. A **workload signature** — a small, stable set of observable characteristics that distinguishes one kind of run from another (for example tool-call volume, context size, cache hit rate, observed latency bands). The signature is derived only from data the run already produces.
2. **Performance observations** — per-run records of the strategy in effect, the workload signature, the outcome metrics, and the cost of collecting them.
3. **Strategy learning** — a lightweight online method (online regression first) that, given a signature, ranks the prevalidated strategies by predicted outcome and states its confidence and the observations behind the ranking.
4. **Adaptation suggestions** over exactly four levers: worker count, scheduling, prefetching, and cache policy. Each suggestion names the lever, the current value, the suggested value, and the reason.
5. **Resource-pressure awareness** — where the host already exposes thermal state or resource pressure, the learner treats pressure as a constraint that narrows the eligible strategies. Where the host does not expose it, the learner records that the signal is absent and proceeds without it. It never probes for or fabricates the signal.
6. **A kill switch** that disables learning for deterministic testing, with a defined baseline strategy that applies while it is off.
7. **Rollback** of any applied strategy change to the previously applied strategy, and ultimately to the baseline.
8. **Overhead accounting** — the time and any other cost the learner itself adds, reported separately from the run's own metrics so it cannot hide inside them.

### Out of scope

- Changing model selection, prompts, decoding, or any path that affects answer correctness.
- Changing memory semantics: what is stored, recalled, compacted, or forgotten.
- Contextual bandits. They are considered only after the regression baseline has reliable data, and that decision is a later ticket, not this one.
- Inventing new strategies at runtime. The learner chooses among strategies that were validated before they were made eligible.
- Applying a suggestion automatically inside inference, memory, prefetch, or the adaptive controller. This phase emits a suggestion; the owner of each lever decides whether and how to apply it.
- Host-level instrumentation that does not already exist. Missing thermal or pressure signals are reported as absent, not built.

## Functional requirements

1. **Suggestions are plain data.** A suggestion carries: the workload signature it was made for, the lever, the current strategy, the suggested strategy, the predicted effect with its unit, the confidence, the count of observations it rests on, and a human-readable reason. It carries no callback, no handle, and no instruction that mutates another subsystem.
2. **Prevalidated strategies only.** Each lever has an explicit allow-list of strategies. A suggestion whose strategy is not on that lever's allow-list is rejected and recorded as rejected, not silently dropped.
3. **No silent correctness changes.** Applying or withholding a suggestion must not alter model output or memory contents for the same inputs. A test that runs the same workload with learning on and learning off must produce the same answers and the same stored memory.
4. **Online regression first.** The first predictor is an online regression (or an equally lightweight method) that updates from one observation at a time and does not require a batch retraining step. Contextual bandits are not implemented in this phase.
5. **Baseline before adaptation.** No suggestion is emitted for a signature until a minimum number of observations exists for it. Below that minimum the learner reports "insufficient baseline" and the baseline strategy stays in effect.
6. **Decisions are explainable.** For any suggestion, an operator can read which observations and which signature features produced it, without reading source code.
7. **Decisions are measurable.** Every suggestion names the metric it expects to move and the direction, so a later run can confirm or refute it.
8. **Rollback.** Every applied change is recorded with the strategy it replaced. Rolling back restores that previous strategy; rolling back past the first change restores the baseline. Rollback itself is recorded.
9. **Disable for deterministic testing.** A single switch turns learning off. While off, the learner emits no suggestions, applies no changes, and adds no per-run work beyond the check of the switch. The strategy in effect is the documented baseline.
10. **Overhead is measured.** Each learning pass records its own duration. The overhead is reported as its own figure and is excluded from the outcome metrics the learner is trying to improve, so the learner cannot grade itself on work it added.
11. **No unpredictable degradation.** A suggestion is only eligible when its predicted outcome is no worse than the baseline by more than a stated bound. A suggestion that would cross that bound is withheld and the withholding is recorded with the reason.
12. **Pressure narrows, it does not invent.** When thermal or resource-pressure state is observable, strategies incompatible with that state are removed from eligibility before ranking. When it is not observable, eligibility is unchanged and the absence is noted on the suggestion.
13. **CPU-only.** The learner runs on CPU with the data it is handed. It does not call a model, does not reach the network, and does not require a GPU.
14. **Failure is non-fatal.** A learner error never fails the run. The run continues on the baseline strategy and the error is recorded.

## Acceptance criteria

- **Given** a workload with fewer than the minimum baseline observations, **when** the learner evaluates it, **then** it emits no suggestion, reports insufficient baseline, and the baseline strategy remains in effect.
- **Given** a workload with enough observations that one prevalidated strategy is predicted to beat the baseline within the degradation bound, **when** the learner evaluates it, **then** the suggestion names the lever, both strategies, the predicted metric and direction, the confidence, the observation count, and a reason a person can read.
- **Given** a suggestion, **when** an operator asks why it was made, **then** the answer cites the signature features and the observations used, without requiring source access.
- **Given** an applied strategy change, **when** the operator rolls it back, **then** the previous strategy is restored, and rolling back every change restores the documented baseline. Both the change and the rollback appear in the record.
- **Given** learning is switched off, **when** the same workload is run repeatedly, **then** no suggestion is emitted, the baseline strategy is used every time, and the only learner cost is the switch check.
- **Given** the same inputs with learning on and with learning off, **when** both runs complete, **then** model answers and stored memory are identical.
- **Given** a completed learning pass, **when** its result is read, **then** the learner's own duration is reported separately from the run's outcome metrics.
- **Given** a suggestion whose predicted outcome would cross the degradation bound, **when** the learner evaluates it, **then** the suggestion is withheld, the baseline stands, and the record states the bound and the predicted value.
- **Given** a host that exposes thermal or resource pressure, **when** the pressure excludes a strategy, **then** that strategy is not suggested. **Given** a host that exposes neither, **when** the learner runs, **then** it notes the signal is absent and does not change eligibility.
- **Given** the learner throws or returns an error, **when** the run continues, **then** the run still completes on the baseline strategy and the error is recorded rather than propagated.

## Constraints carried from prior work

- The learner stays decoupled from the other runtime phases: it emits plain-data suggestions with reasons and never mutates inference, memory, prefetch, or the adaptive controller. CPU-only operation stays unchanged, and learning can be disabled for deterministic tests. (Recorded project decision; this PRD makes it a requirement rather than an assumption.)
- A run's own delta computation must never fail the run. The same rule applies here: requirement 14.

## Open questions for the architect

These do not block the requirements, but the design must answer them:

1. Where the observation record lives, and how long it is retained.
2. The minimum observation count per signature before a suggestion is allowed.
3. The numeric degradation bound, and which metric it is measured on.
4. Which existing host signals count as "observable" thermal and resource pressure, per surface (cloud, VS Code, on-prem).
5. Who consumes a suggestion — the adaptive controller, an operator surface, or both — given this phase does not auto-apply.
