## Requirements

### R1 — Lane chaining with ONE notifier (§13)
- R1.1 On a `lifecycleManaged` board, a lane transition is decided by the Coordinator and the manifest is the single source of truth for who is owed participation in the next lane.
- R1.2 Exactly one notification is emitted per lane entry per owed role. `SwimlaneCoordinator` / `ticket_runs` must not emit a second, parallel notification for the same (ticket, lane, role).
- R1.3 Dedupe key: `(taskId, laneKey, roleKey, manifestRevision)`. Re-running the same transition is idempotent.
- R1.4 Acceptance: a test drives one lane move through both engines and asserts a single notification and a single `ticket.handoff` event.

### R2 — Per-role audit verification (§5.10)
- R2.1 Add a read model aggregating accountability gaps (from `accountabilityGaps.ts`) across incidents via the implicated-ticket links, grouped by `(laneKey, roleKey)`.
- R2.2 It answers: "which stage's sign-offs correlate with incidents?" — per role and lane: incident-linked tickets, how many had a missing, waived or unlinked sign-off, and the rate versus non-incident tickets.
- R2.3 An approval with no linked contribution counts as an audit finding (consistent with `builtin_kanban_signoff`).
- R2.4 Durable findings are written to project memory so later runs of that ticket type tighten the gate. This is advisory only and never auto-changes a gate.
- R2.5 Acceptance: unit tests with fixtures covering no incidents, an incident with all sign-offs present, and an incident with a waived or missing sign-off.

### R3 — Coordinator-routed stakeholder notifications and `kanban.handoff` (§8)
- R3.1 Stakeholder notifications (assignee, role owners, ticket watchers) are routed through the ticket's Coordinator, not sent directly by individual lane or agent code.
- R3.2 Add MCP tool `kanban.handoff` (record a hand-off: taskId, fromRole, toRole, laneKey, note). It calls the same code path as `coordinateTicket.ts` so it emits the same `ticket.handoff` event, and it is idempotent on the R1.3 key.
- R3.3 Authorization: the caller must be the Coordinator or the role being handed off from. Otherwise it is refused with a typed error.
- R3.4 Acceptance: `builtinMcpService.test.ts` covers success, idempotent repeat, and refusal. Decision fallback: if product prefers, drop the `kanban.handoff` requirement and record that in this PRD.
