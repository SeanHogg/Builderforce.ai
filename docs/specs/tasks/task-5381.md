# PRD: Semantic Recall Query Engine

## Problem & Goal

Agents currently rely on exact keyword or identifier matching to retrieve stored memories. This misses relevant information when the agent’s query uses different wording, synonyms, or paraphrases, and it often returns low-value exact matches without considering semantic relevance.

Build a semantic recall query engine that combines vector similarity and keyword search, applies permission-aware filtering and relevance ranking, and returns concise, traceable memory results to agents.

### Goals

- Retrieve relevant memories even when query wording differs from stored content.
- Preserve strong performance for exact names, identifiers, acronyms, and quoted phrases.
- Return ranked results that respect tenant, user, agent, and workspace boundaries.
- Integrate with the existing memory store and agent runtime without creating a second source of truth.
- Support measurable relevance, latency, reliability, and zero cross-tenant data leakage.

### Success measures

- At least 85% Recall@10 and 80% nDCG@10 on the approved evaluation set.
- Hybrid ranking outperforms the keyword-only baseline on semantic/paraphrase queries without degrading exact-match recall.
- p95 search latency of 500 ms or less for up to 100,000 active memories in a tenant, under the benchmark conditions.
- Zero authorization or tenant-isolation violations.

## Target Users / ICP Roles

### Agent runtime

The primary consumer. It submits the current user request or task context and receives a small ranked set of memories to include in model context.

### End users

Indirect users who benefit from agents recalling prior decisions, preferences, project context, and previously completed work.

### Platform operators and administrators

They configure retrieval weights, indexing jobs, provider settings, feature flags, and monitoring. They do not need direct access to raw search telemetry.

### Memory administrators

They rely on memory visibility, ownership, archival, and deletion rules remaining consistent between the source system and search indexes.

## Scope

### In scope

- A versioned internal search API exposed by the existing API service and consumed by the agent runtime.
- A search projection containing canonical memory content and searchable metadata.
- Incremental indexing on memory creation, update, archival, and deletion.
- Idempotent backfill for existing memories.
- Dense retrieval using semantic embeddings.
- Lexical retrieval using BM25 or an equivalent full-text ranking implementation.
- Weighted hybrid fusion, deduplication, relevance thresholds, and deterministic tie-breaking.
- Permission and scope filtering before and after retrieval.
- Structured results with ranking diagnostics.
- Graceful degradation when embedding, vector, or lexical dependencies are unavailable.
- Feature-flagged rollout, shadow evaluation, metrics, and structured operational logs.

### User flow

1. The agent runtime submits a natural-language query and retrieval scope.
2. The engine validates the request and applies authorization filters.
3. The engine retrieves vector candidates and lexical candidates independently.
4. The engine fuses, deduplicates, ranks, and truncates the candidates.
5. The runtime receives the highest-ranked memory excerpts and provenance.
6. The runtime decides how to use those memories in its prompt or response.

## Functional Requirements

### FR-1: Search contract

Expose `POST /v1/memories/search`, or the equivalent route under the repository’s established API namespace, with the following behavior:

- Required input:
  - `query`: non-empty string, up to 4,000 characters.
  - `top_k`: optional integer from 1–50; default 10.
- Optional input:
  - `agent_id`
  - `workspace_id`
  - `user_id`, when the caller is permitted to search that user’s memories.
  - `memory_types`
  - `tags`
  - `created_after` and `created_before`
  - `min_score`
- Tenant and caller identity must come from authenticated service context. Request fields may narrow scope but must never broaden it.
- The response must contain:
  - `query_id`
  - ordered `hits`
  - `total_candidates`
  - `degraded` and `degraded_mode` fields
- Each hit must contain:
  - `memory_id`
  - ranked `content` or excerpt
  - fused `score`
  - memory type and metadata
  - semantic and lexical rank/score diagnostics
  - creation and update timestamps
  - source/provenance identifier
- Fused scores must be documented as ranking scores, not probabilities or confidence values.
- An empty result must return a successful response with an empty `hits` array. Invalid input must return a client error.

### FR-2: Search projection and indexing

- The existing memory store remains authoritative.
- The searchable document must include canonical content and any existing title, summary, or tags designated as searchable.
- Each embedding record must include:
  - stable memory ID
  - embedding model and version
  - vector dimension
  - source content version or hash
  - indexed timestamp
- Lexical and vector indexes must support the same active/archived visibility rules.
- Create, update, archive, and delete operations must trigger incremental index synchronization.
- Updating content must replace the active embedding atomically; stale embeddings must not remain selectable.
- Archival or deletion must remove the document from retrieval immediately, with physical index cleanup completed within 60 seconds.
- Backfill must be resumable, idempotent, observable, and safe to rerun.
- A failed embedding operation must not prevent the underlying memory from being saved. The document must be marked for retry and remain retrievable through lexical search.

### FR-3: Hybrid candidate retrieval

- Dense retrieval must rank memories by cosine similarity using the same embedding model family and version as the active index.
- Lexical retrieval must rank memories by BM25 or an equivalent full-text score.
- Exact identifiers, acronyms, names, and phrase matches must receive additional lexical relevance.
- Default candidate depth must be configurable and no smaller than 50 candidates per retrieval path.
- Duplicate references to the same memory must collapse into one result.
- Retrieval must support semantic-only and lexical-only modes for diagnostics and fallback, while hybrid mode is the default.
- The original query must be used for both paths in the initial release; autonomous query rewriting is not required.

### FR-4: Ranking

- Default fusion must use weighted Reciprocal Rank Fusion so vector and lexical scores do not need artificial common-scale normalization.
- Default weights must be 65% semantic and 35% lexical and must be configurable within validated bounds.
- Fusion must be based on rank, with optional source-specific minimum thresholds.
- Relevance must remain the primary ranking signal. Recency and memory importance may be used only as tie-breakers unless explicitly configured by an administrator.
- Tie-breaking must be deterministic: semantic similarity first, then most recently updated.
- Results must be limited to `top_k` after fusion and deduplication.
- A degraded search must renormalize the available path’s weight and identify the degraded mode in the response.
- Advanced LLM-based or cross-encoder reranking is not required for the initial release.

### FR-5: Authorization and isolation

- Every search must be scoped to an authenticated tenant.
- User-owned, agent-owned, workspace-owned, shared, and private memories must follow the source system’s existing access rules.
- Filters must be applied before candidate retrieval whenever the backing store supports them.
- A second authoritative permission check must occur before returning content.
- Stale index entries must never expose a memory that is archived, deleted, or newly unauthorized.
- Raw memory content and query text must not be written to ordinary operational logs.
- Retrieved content must retain provenance and be treated as untrusted data rather than executable instructions.

### FR-6: Agent integration

- The agent runtime must be able to call the engine without direct access to vector or lexical indexes.
- Results must be suitable for prompt assembly, including bounded excerpts and metadata.
- The engine must return memories only; it must not generate a final answer or synthesize new memories.
- The runtime must be able to request a larger result set for agent workflows while the API enforces the maximum `top_k`.
- Existing keyword retrieval must remain available during rollout and as a failure fallback.

### FR-7: Reliability and degradation

- Search must use bounded timeouts and dependency-specific circuit breakers.
- If embedding generation fails, the engine must attempt lexical-only retrieval.
- If lexical search fails, the engine must attempt semantic-only retrieval.
- If both paths fail, the engine must return a controlled service error or use the existing keyword-search fallback.
- Provider rate limits must not block unrelated API traffic.
- The feature must support tenant-level or agent-level enablement and shadow mode.
- Shadow mode must calculate and record hybrid results without changing the runtime’s current response.

### FR-8: Observability and evaluation

- Every response and log entry must include a correlation/query ID.
- Operational telemetry must include:
  - semantic and lexical candidate counts
  - result count
  - total and per-dependency latency
  - active weights
  - degraded mode and fallback reason
  - indexing and backfill failures
- Metrics must cover latency, fallback rate, zero-result rate, indexing lag, and authorization denials.
- An offline evaluation dataset must contain at least 100 labeled queries covering:
  - semantic paraphrases
  - exact identifiers and names
  - mixed semantic and lexical queries
  - scoped and filtered searches
  - queries with no relevant memory
- The evaluation harness must support keyword-only, semantic-only, and hybrid configurations.

## Acceptance Criteria

1. **Semantic recall:** A query using meaningfully different wording returns the expected memory within the top 10 results.
2. **Exact recall:** Queries containing exact identifiers, names, acronyms, or phrases return the matching memory within the top 5 results.
3. **Hybrid quality:** On the approved evaluation set, Recall@10 is at least 85%, nDCG@10 is at least 80%, and hybrid nDCG exceeds the keyword-only baseline.
4. **Negative queries:** Queries with no relevant memory do not fill the result set with low-relevance items solely to reach `top_k`.
5. **Filtering:** Results contain only memories matching authorized agent, workspace, user, type, tag, and date constraints.
6. **Tenant isolation:** Automated tests attempting cross-tenant retrieval receive zero unauthorized content and generate no leakage through counts, snippets, diagnostics, or errors.
7. **Index freshness:** Newly committed memories become searchable within 60 seconds; updates replace prior content and versions without duplicates.
8. **Deletion safety:** Archived and deleted memories are excluded immediately, even if cleanup has not yet completed.
9. **Backfill safety:** Re-running backfill produces no duplicate index entries and reports progress, failures, and completion status.
10. **Provider degradation:** With embedding generation unavailable, lexical results are returned and the response identifies the degraded mode; with lexical search unavailable, semantic results are returned similarly.
11. **Contract behavior:** Invalid queries and invalid `top_k` values return documented errors; valid no-match queries return HTTP 200 with an empty result set.
12. **Performance:** The benchmark corpus of 100,000 active memories meets p95 latency of 500 ms or less with warmed connections and provider latency included.
13. **Observability:** Operators can identify query latency, candidate counts, ranking mode, fallback reason, and indexing failures without logging raw memory content or query text.
14. **Rollout:** Hybrid search can run in shadow mode, can be enabled selectively, and can be disabled without removing the existing retrieval path.

## Out of Scope

- A user-facing search or memory-management interface.
- Generative answers, memory summarization, or answer synthesis by the retrieval engine.
- Automatic creation, consolidation, or mutation of memories beyond the existing indexing lifecycle.
- Fine-tuning or training custom embedding models.
- LLM-based query rewriting or advanced generative reranking in the initial release.
- Knowledge-graph traversal, graph retrieval, or multi-hop reasoning.
- Image, audio, video, or other multimodal memory indexing.
- Cross-tenant, public, or organization-wide shared search.
- Replacing the existing memory datastore or introducing a competing source of truth.
- Online learning of ranking weights from user behavior.
- Cross-region search federation, offline search, or native mobile search clients.
