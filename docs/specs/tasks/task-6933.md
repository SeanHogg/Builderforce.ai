## Problem & Goal

PR open and update handling never checks whether the pull request merges cleanly against its base. Nothing in `api/src/application/runtime` reads mergeability, so an execution cannot tell a clean merge from a conflict (or from an unknown result).

**Goal:** When a PR is opened or updated, the execution records whether that PR merges cleanly against its base.

## Target users / ICP roles

- **Runtime / orchestrator:** needs a durable mergeability fact on the execution before later steps assume the PR can land.
- **Operator reviewing an execution:** needs to see, on that execution, whether the associated PR is clean against its base.

## Scope

In-repo work on `seanhogg/builderforce.ai` (`main`). On PR opened and PR updated, the application runtime must obtain mergeability of the PR against its base and persist that result on the execution that owns the PR.

Covered:

- Read path in `api/src/application/runtime` that today never consults mergeability.
- PR open and PR update as the triggers.
- Recording a clear mergeability outcome on the execution (clean vs not clean, plus unknown when the provider has not computed it yet).
- Re-recording when a later update changes the result.

## Functional requirements

1. On PR opened and on PR updated, the runtime resolves the execution for that PR and evaluates mergeability against the PR’s base ref (not against a hardcoded branch, and not against `main` unless `main` is the base).
2. The execution stores whether the PR merges cleanly: clean, not clean (conflicts or otherwise not mergeable), or unknown while the provider has not finished computing mergeability.
3. Unknown is not treated as clean. The runtime retries or refreshes until the provider returns a definitive result, then writes that result on the execution.
4. A later PR update overwrites the previous mergeability record so the execution reflects the current head against the current base.
5. The recorded fact is readable from the execution (the same record downstream steps and operators already use). Failed provider calls do not silently mark the PR clean; they leave the execution unknown or failed-to-check, distinct from a clean merge.
6. Only the bound repository’s PR events for that execution are considered. Base and head SHAs used for the check are the ones on the PR at the time of the open or update.

## Acceptance criteria

- Opening a PR whose head merges cleanly against its base causes the owning execution to record a clean merge.
- Opening a PR that does not merge cleanly against its base causes the owning execution to record not clean. It must not record clean.
- Updating the PR (new commits, base change, or other update that can change mergeability) re-evaluates and updates the execution to match the new result.
- If the provider reports mergeability as not yet known, the execution does not record clean until a definitive check completes; after that check, the execution matches the definitive result.
- A code path under `api/src/application/runtime` performs the mergeability read. A PR open or update with no such read is a failure.
- Mergeability is against the PR’s base, not a substitute ref.

## Out of scope

- Merging the PR, auto-resolving conflicts, or changing branch protection.
- UI redesign beyond exposing the fact already stored on the execution.
- Mergeability for issues, drafts-only workflows, or repositories other than the bound repo.
- Rewriting unrelated runtime stages that do not handle PR open/update.
