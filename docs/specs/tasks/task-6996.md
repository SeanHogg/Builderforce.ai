# Manifest v1 AI Resource and Host-Relay Runtime

## Problem & Goal

Manifest v1 has no accepted way to declare an AI resource that the host delivers. Without that contract, a generated app can reach a model only by placing a provider key where it must not go: in the browser process or in process environment variables.

Land only the accepted contract. Add a typed `AiResource`, validate it, publish one capability row per existing target, mark it `HOST_DELIVERED` on the application spec, let services declare `resourceUses`, and serve `AI_BASE_URL` from an in-process `HostRelay` through a callback. The page gateway uses the existing port registry. VSIX `/launch` starts that runtime. Provider keys stay out of the browser process. Connection secrets stay out of process env. `PREVIEW_DEFAULT_EGRESS` and service roles do not change. The Yardfire fixture still validates.

## Target users / ICP roles

- Manifest authors declaring resources for frontend and backend services only.
- The host and preview runtime, which delivers the AI resource and relays model calls without exposing keys to the page.
- Extension users who start an app from VSIX `/launch`.

Implementation roles for this work stay frontend and backend. Do not add a service role.

## Scope

Repository: `seanhogg/builderforce.ai`, base `main`.

In scope is the accepted contract only:

- `AiResource` in `types.ts`
- Matching arm in `schema.ts`
- Models list enforcement in `validate.ts`
- One `capabilities.ts` row per existing target
- `HOST_DELIVERED` in `toApplicationSpec`
- `resourceUses` on `ServiceSpec`
- `AI_BASE_URL` via callback, with no provider key in the browser process
- Page gateway on the port registry
- In-process `HostRelay`
- VSIX `/launch` wired to `startApplicationRuntime`
- `PREVIEW_DEFAULT_EGRESS` left unchanged
- Roles limited to frontend and backend
- Yardfire fixture still validates
- No connection secrets injected into process env

## Functional requirements

1. `types.ts` defines `AiResource` as a Manifest v1 resource. It is the only new resource type in this change.
2. `schema.ts` accepts that `AiResource` arm and rejects unknown AI fields instead of ignoring them.
3. `validate.ts` checks the resource against the accepted models list. A model not on that list fails validation. Do not widen the list.
4. `capabilities.ts` has exactly one row per existing target for this resource. AWS, Azure, and GCP are not supported. Cloudflare is not supported until both a token and a meter exist. Do not add targets that are not already in the capabilities target set.
5. `toApplicationSpec` marks the AI resource `HOST_DELIVERED`. This contract does not provision a cloud AI resource.
6. `ServiceSpec` includes `resourceUses`. A frontend or backend service that calls the host AI endpoint declares the AI resource there. No other role is valid.
7. The runtime supplies `AI_BASE_URL` through a callback. The provider key is not sent to, stored in, or readable by the browser process, including page config, the client bundle, and browser-side env.
8. The page-facing gateway is registered on the existing port registry. Do not add a second port-allocation path for this feature.
9. `HostRelay` runs in-process with the host. That process holds provider credentials and forwards model calls. It is not a separately deployed service.
10. VSIX `/launch` starts the app by calling `startApplicationRuntime`. Do not leave a launch path that skips that runtime.
11. Connection secrets are not written into process environment variables. Callback delivery of `AI_BASE_URL` is not a reason to put secrets in `process.env`.
12. `PREVIEW_DEFAULT_EGRESS` is not edited and its policy value does not change.
13. The existing Yardfire fixture validates against this contract. Do not weaken validation or edit the fixture to force a pass.

## Acceptance criteria

- A manifest with a valid `AiResource` is accepted by `types.ts`, `schema.ts`, and `validate.ts` when its model is on the accepted models list.
- An unknown AI model or unknown AI fields fail validation.
- `capabilities.ts` has one AI-resource row per existing target. AWS, Azure, and GCP are unsupported. Cloudflare is unsupported unless both a token and a meter exist.
- `toApplicationSpec` emits the AI resource as `HOST_DELIVERED`.
- A frontend or backend `ServiceSpec` can name the AI resource in `resourceUses`. No new role appears.
- VSIX `/launch` calls `startApplicationRuntime`, which runs `HostRelay` in-process and registers the page gateway on the port registry.
- The page learns `AI_BASE_URL` only through the callback. The provider key is absent from the callback payload, page config, client bundle, and browser process.
- App and browser process environments do not contain connection secrets.
- `PREVIEW_DEFAULT_EGRESS` is unchanged from `main`.
- The Yardfire fixture validates.
- No superseded contract is implemented beside this one.

## Out of scope

- Support on AWS, Azure, or GCP.
- Cloudflare support before both a token and a meter exist, including token issuance and meter implementation.
- Any change to `PREVIEW_DEFAULT_EGRESS` or preview egress behavior.
- Service roles other than frontend and backend.
- Putting connection secrets or provider keys in process env, the browser process, page source, or client bundles.
- An out-of-process relay, a new port allocator, or a `/launch` path that does not call `startApplicationRuntime`.
- Resource types other than `AiResource`, a new manifest version, or models outside the accepted `validate.ts` list.
- Changing the Yardfire fixture or relaxing validation so it passes.
- Billing work, and docs or roadmap edits not required for this contract to build and validate.
