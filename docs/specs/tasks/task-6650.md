# PRD 39 P2 — Gate Annotation Access

## Problem & Goal

Canvas annotations, including comments, pins, mentions, and resolution metadata, are not consistently protected by the platform’s object-access gate. The registry facade currently exposes annotation reads and writes without verifying the viewer’s relationship to the gated object. Comment activity may also leak through the facade’s ungated `activity` read.

Implement Push 1 of PRD 39 section 2 only: enforce access control at the registry and comment-service boundaries while preserving the existing comment write workflow through `canvasComments.ts`.

The committed schema expansion and backfill are already complete. This work must not repeat migrations, move rows, switch read paths, or remove legacy tables.

## Target Users / ICP Roles

- **Canvas collaborators:** Members with an authorized relationship to a canvas object or its gated session must continue to view permitted annotations and activity.
- **Non-members:** Must not read annotations or comment activity from private sessions.
- **API and frontend clients:** Continue using supported registry/comment APIs, now with enforced viewer authorization and immutable generic annotation writes.
- **Platform administrators and security reviewers:** Require proof that unauthorized reads and direct generic writes are refused.

## Scope

### In Scope

- Locate the actual `ObjectRegistry` implementation and its annotation methods using symbol search; do not assume the previously cited path exists.
- Gate registry annotation reads for `DOMAIN_GATED_RELATION_KINDS`.
- Require `viewerRef` on the registry facade’s `annotations` read.
- Refuse generic annotation writes for every caller.
- Permit comment creation only through `api/src/application/canvas/canvasComments.ts`.
- Gate comment activity through the registry facade’s `activity` read when comment activity is reachable through it.
- Verify or implement:
  - A 1–5000 character limit for comments, enforced in `canvasComments.ts` or by an equivalent kind-scoped database constraint.
  - Canvas-object deletion clearing the associated comment pin.
- Extend existing annotation/comment tests with access-control coverage.
- Run scoped tests, TypeScript checking, and the migration validation script if one exists.

### Out of Scope

- Re-running or modifying migrations 1298 or 1299.
- Recreating the committed `public_id`, mentions, or `resolved_by` columns or `annotation_fold_ledger`.
- Push 2 row movement or read-path switching.
- Dropping or migrating away from the legacy annotation table.
- Editing comment queries in `creationSessionRoutes.ts`.
- Expanding annotation kinds, changing the product’s comment UX, or redesigning activity feeds.
- Executing TypeScript directly with Node.
- Running commands against a production or Neon database.

## Functional Requirements

### 1. Registry Annotation Read Gate

- The facade’s `annotations` read must accept a `viewerRef`.
- For annotation kinds included in `DOMAIN_GATED_RELATION_KINDS`, authorization must use the same domain-gate semantics as `objectRelationGate.ts`.
- A viewer without the required relationship must receive the existing gate-refusal response; annotation data must not be returned.
- Authorized members must retain access to annotations permitted by the existing gate.
- The registry facade must not expose an ungated annotation read alternative.

### 2. Generic Annotation Write Refusal

- Generic registry annotation writes, including calls through `addAnnotation`, must be refused for all callers.
- The refusal must apply regardless of caller membership or privilege.
- The facade must not silently fall back to another generic write path.
- Supported comment writes must use `canvasComments.ts` exclusively.

### 3. Comment Write Boundary

- `canvasComments.ts` remains the only supported write path for comment annotations.
- The write path must validate comment content length as 1–5000 characters.
- If no equivalent kind-scoped database check exists, the service must enforce the limit before persistence.
- If an existing check is sufficient and covers comment kinds, document that verification rather than duplicating conflicting validation.

### 4. Activity Gate

- Determine whether comment annotations are returned by the registry facade’s `activity` read.
- If reachable, require a `viewerRef` and apply the same `DOMAIN_GATED_RELATION_KINDS` authorization check before returning comment activity.
- If not reachable, add or extend a regression test proving comment activity cannot bypass the annotation gate.

### 5. Comment Pin Lifecycle

- Deleting a canvas object must clear the associated comment’s pin reference.
- The behavior must not depend on the removed legacy foreign-key `ON DELETE SET NULL` behavior.
- Pin cleanup must preserve the comment record unless the established product contract requires otherwise.

### 6. Test Coverage

Use existing annotation/comment tests as the starting point and extend them to prove:

- A non-member receives a refusal when reading annotations for a private session.
- An authorized member can read annotations for an allowed session.
- Generic annotation writes are refused for both members and non-members.
- The supported `canvasComments.ts` write path remains functional.
- Comment activity is either gated or demonstrably unreachable through the ungated facade path.
- Comment content outside the 1–5000 character range is rejected.
- Deleting a canvas object clears the comment pin.

## Acceptance Criteria

- [ ] The actual registry implementation is identified; no new registry is created solely to satisfy the original path assumption.
- [ ] The registry facade’s `annotations` read requires `viewerRef`.
- [ ] `DOMAIN_GATED_RELATION_KINDS` annotation reads enforce the established object-relation gate.
- [ ] A non-member is refused when requesting annotations for a private session.
- [ ] Generic annotation writes are refused for everyone, including authorized members.
- [ ] Comments can be written only through `api/src/application/canvas/canvasComments.ts`.
- [ ] Comment activity is gated through `registry.activity`, or a regression test proves it is not reachable there.
- [ ] Comment length is constrained to 1–5000 characters at the comment service or equivalent kind-scoped constraint layer.
- [ ] Deleting a canvas object clears its associated comment pin without relying on the removed legacy FK behavior.
- [ ] Existing and newly added annotation/comment tests pass under the scoped Vitest command.
- [ ] `npx tsc --noEmit` from `Builderforce.ai/api` reports zero errors in touched files.
- [ ] If `api/package.json` defines a migration check script, that script passes without production database access.
- [ ] No changes are made to migrations 1298/1299, legacy-table removal, row movement, read switching, or `creationSessionRoutes.ts` comment queries.

## Out of Scope

- Push 2 of PRD 39 section 2.
- Row copies, backfills, ledger population, or read-source cutover.
- New annotation-table schema work beyond a narrowly required kind-scoped constraint.
- Changes to `creationSessionRoutes.ts`.
- Broad refactoring of `ObjectRegistry`, activity architecture, or authorization policy.
- Production database execution, deployment, or migration rollout.
