# PRD: Refresh Stale Blog Index

## Problem & Goal

The blog index and search dataset can drift from the repository’s published content. This may cause recently published posts to be missing while deleted, renamed, or unpublished posts remain discoverable.

Refresh the existing index/search artifacts so they accurately represent the current published blog collection, preserve established search behavior, and can be regenerated consistently.

**Repository:** `seanhogg/builderforce.ai`  
**Baseline:** `main`

## Target Users / ICP Roles

| Role | Need |
| --- | --- |
| Blog readers | Discover current articles and search for relevant content without encountering removed posts or broken links. |
| Content editors | Publish and update posts without manually reconciling a separate index when the repository supports generation. |
| Site maintainers and engineering agents | Refresh the index deterministically and verify that it matches the published content corpus. |

## Scope

- Identify the canonical blog content source and the existing index/search artifacts derived from it.
- Update all applicable repository-managed artifacts, including the browsable blog index and search dataset if they are separate.
- Add coverage for current published posts and remove records that are no longer eligible.
- Refresh post metadata, canonical links, ordering, and search data within the existing schema.
- Use established generation and validation tooling where present.
- Follow `AGENTS.md` and existing repository conventions.
- Keep changes limited to the index refresh and directly related generation or validation updates.

## Functional Requirements

1. **Canonical content corpus**
   - Determine the published-post set using repository content and existing publication rules.
   - Include every post the current site exposes as publicly published.
   - Exclude drafts, unpublished posts, and any other content hidden by existing visibility rules.

2. **Index refresh**
   - Refresh every existing index/search artifact derived from the canonical corpus.
   - Include each eligible post exactly once, with no duplicate records.
   - Prefer updating the established source or generator and regenerating its output rather than maintaining a second mechanism or manually changing generated output only.

3. **Metadata integrity**
   - Preserve the existing index schema and field contract.
   - Refresh titles, canonical URLs or slugs, publication dates, summaries or body content, and tags or categories wherever those fields already exist.
   - Derive values from the canonical post source rather than inventing or rewriting editorial content.

4. **Stale-entry removal**
   - Remove records for deleted, renamed, unpublished, or otherwise ineligible posts.
   - Remove matching stale records from both browse and search artifacts, including separate search datasets or caches maintained in the repository.

5. **Ordering and search behavior**
   - Preserve the established sort and tie-breaking behavior while placing newly published posts in the correct recency order.
   - Use publication metadata rather than filesystem modification time to determine recency.
   - Preserve existing search matching, searchable fields, filters, pagination, and result presentation.

6. **Determinism and validation**
   - Running the refresh twice against the same content must produce no additional diff.
   - Validate index coverage, metadata, duplicate entries, and post-link targets using existing checks where available.

## Acceptance Criteria

- [ ] Every currently publicly published blog post appears exactly once in each applicable index/search artifact.
- [ ] Recently published posts are indexed with correct titles, canonical links, publication dates, and existing metadata.
- [ ] Deleted, renamed, unpublished, and otherwise hidden posts are absent from both the browsable index and search results.
- [ ] Every indexed link resolves to an existing canonical post route, and no indexed record points to unpublished content.
- [ ] Newest posts appear in the correct chronological position using the repository’s established ordering rules.
- [ ] Searching for a distinctive term from a newly published post returns that post; searching for a term associated only with a removed post does not return a stale result.
- [ ] Existing search, filtering, and result-display behavior remains intact.
- [ ] Re-running the refresh process against unchanged content produces no diff.
- [ ] All applicable existing tests, lint checks, generation checks, and build checks pass.
- [ ] The final diff contains no unrelated feature, content, or formatting changes.

## Out of Scope

- Redesigning the blog listing, search interface, navigation, or visual styling.
- Replacing the current search implementation or introducing a new indexing framework.
- Changing post copy, editorial metadata, publication dates, or publication status.
- Adding new search features such as stemming, semantic ranking, facets, autocomplete, or synonyms.
- Migrating the underlying blog content model or CMS.
- Backfilling unrelated content or fixing broken links outside the index/search flow.
- Production deployment, external search-service reindexing, or CDN cache invalidation beyond the bound repository.
