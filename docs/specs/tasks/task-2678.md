# Test Harness Enhancement: Emulate Dispatch→Execution INSERT Path

## Problem & Goal

### Problem
The current CI test harness cannot emulate the full dispatch→execution INSERT path. This limitation forces waivers on tests that require end-to-end assertions for the `executions` table insertion, such as ensuring no `Postgres 22001` (`value too long for type character varying`) errors occur.

### Goal
Create a generic integration-level test fixture that can INSERT an `executions` row into a migrated test database. This will enable end-to-end testing of the dispatch→execution path and prevent future waivers on related tests.

## Target Users / ICP Roles
- **Software Engineers**: Developers who need to write and maintain tests that involve the dispatch and execution of tasks.
- **QA Engineers**: Testers who rely on the test harness to validate system behavior.

## Scope

### In Scope
- Develop a test fixture that can INSERT an `executions` row into a test database.
- Ensure the fixture handles database migrations appropriately.
- Re-instate the #2649 regression test case using the new fixture.
- Document the usage of the new fixture for future test cases.

### Out of Scope
- Modifying existing unit tests or components beyond what is necessary to integrate the new fixture.
- Addressing any other test infrastructure issues not related to the dispatch→execution path.
- Implementing additional test cases beyond the reinstated #2649 regression test.

## Functional Requirements

1. **Test Fixture for Execution Insertion**
   - The fixture should be able to connect to a test database instance.
   - It must support inserting a valid `executions` row with necessary fields.
   - The fixture should handle database migrations to ensure the `executions` table is up-to-date.

2. **Integration with Test Harness**
   - The fixture should be compatible with the existing test harness framework.
   - It should be easy to invoke from within test cases as needed.

3. **Error Handling**
   - The fixture should provide meaningful error messages if the insertion fails.
   - It should handle connection errors and database errors gracefully.

4. **Documentation**
   - Provide clear documentation on how to use the fixture in test cases.
   - Include examples of how to set up and teardown the fixture.

## Acceptance Criteria

1. **Fixture Implementation**
   - A new test fixture is implemented and can insert an `executions` row into the test database.
   - The fixture handles database migrations without manual intervention.

2. **Regression Test Re-instatement**
   - The #2649 regression test case is re-instated using the new fixture.
   - The test passes without waivers, asserting that no `Postgres 22001` errors occur.

3. **Documentation**
   - The fixture is documented in the test harness documentation.
   - Usage examples are provided for future reference.

4. **Integration**
   - The fixture integrates seamlessly with the existing test harness.
   - No existing tests are broken by the introduction of the new fixture.

## Out of Scope

- **Unit Test Modifications**: The scope does not include modifying existing unit tests or components beyond the necessary integration.
- **Additional Test Cases**: Only the reinstated #2649 regression test is included; no other test cases will be implemented as part of this ticket.
- **Other Infrastructure Issues**: Any other test infrastructure issues not related to the dispatch→execution path are excluded from this scope.
