# PRD: Add `advisory` meeting kind

## Problem & Goal

Meeting routing currently recognizes a closed set of kinds and does not include `advisory`. Advisory sessions are not team ceremonies; they should be first-class in routing without inheriting ceremony defaults.

**Goal:** Register `advisory` in `KINDS` in `meetingRoutes.ts` so advisory meetings can be created, routed, and handled like other kinds, while **not** turning team-ceremony chat on by default for advisory.

## Target users / ICP roles

- Product and engineering teams creating or joining advisory meetings
- Advisors / coaches running 1:1 or small-group advisory sessions
- Downstream agents implementing and testing meeting routing and chat defaults

## Scope

In scope:

- Add `advisory` to `KINDS` in `meetingRoutes.ts`
- Ensure advisory is a valid meeting kind for routing, validation, and any kind-based dispatch that reads `KINDS`
- Keep team-ceremony chat **off by default** for `advisory` (do not treat advisory as a team ceremony for chat defaults)
- Preserve existing kinds and their current default chat behavior

Out of scope is listed below.

## Functional requirements

1. `KINDS` in `meetingRoutes.ts` includes the string `advisory` alongside existing kinds.
2. Requests and routes that validate meeting kind against `KINDS` accept `advisory` and reject unknown kinds as before.
3. Advisory meetings do **not** get team-ceremony chat enabled by default.
4. Default chat (or equivalent ceremony-chat flag) for advisory is off unless the caller explicitly opts in.
5. Existing kinds are unchanged: membership of `KINDS`, routing, and ceremony-chat defaults for non-advisory kinds stay the same.
6. Advisory is not classified or aliased as a team ceremony for chat-default logic (no “if kind is in KINDS then enable ceremony chat”).

## Acceptance criteria

- `KINDS` contains `advisory`.
- Creating or routing a meeting with `kind: "advisory"` succeeds and does not fail kind validation.
- A newly created advisory meeting does **not** have team-ceremony chat on by default.
- Explicitly enabling chat for an advisory meeting still works if that path already exists for other kinds.
- Regression: existing kinds still route correctly; their ceremony-chat defaults are unchanged.
- No other files or product surfaces are required for this change unless they derive allowed kinds solely from `KINDS` (those should pick up `advisory` automatically).

## Out of scope

- UI, copy, or scheduling flows for advisory meetings beyond kind registration and chat default
- Changing chat defaults for any non-advisory kind
- Turning ceremony chat on for advisory by default, even as a “temporary” or “opt-out” default
- New chat features, permissions, recording, or transcription behavior
- Database migrations, new API resources, or new meeting types beyond the `advisory` kind string
- Analytics, notifications, or calendar integrations specific to advisory
- Treating advisory as a team ceremony for any other default (not only chat)

## Requirements

### As-is (main, `api/src/presentation/routes/meetingRoutes.ts`)

- `KINDS = new Set(['standup', 'planning', 'retrospective', 'adhoc', 'direct', 'interview', 'review'])` — **`advisory` is absent**.
- `TEAM_CEREMONY_KINDS = new Set(['standup', 'planning', 'retrospective', 'review'])`.
- Create path: `const kind = body.kind && KINDS.has(body.kind) ? body.kind : 'adhoc'`. Unknown kinds **silently coerce to `adhoc`** (not 400).
- Team-chat attach: `const linkChat = body.linkTeamChat ?? TEAM_CEREMONY_KINDS.has(kind)`. Default **on** only for ceremony kinds; otherwise off. Explicit `linkTeamChat: true` still opt-in.
- `defaultTitle(kind)` has cases for standup / planning / retrospective / direct / interview / review; everything else (including `adhoc`) returns `'Meeting'`.
- Persistence: `meetings.kind VARCHAR(16)` (migration `0292_meetings_and_calendar.sql`). `'advisory'` is 8 characters — **no column-width migration**. There is no DB CHECK on kind values; validation is the in-process `KINDS` set.
- Ceremony companion path (`api/src/application/ceremony/ceremonyMeeting.ts`) copies `ceremony_sessions.kind` onto `meetings.kind` and only titles standup/planning. Advisory is **not** a ceremony session kind.

Today, `POST /api/meetings` with `kind: "advisory"` stores `kind = 'adhoc'` and therefore also skips ceremony chat (because `adhoc` is not in `TEAM_CEREMONY_KINDS`). The gap is **first-class kind identity**, not the chat default of the fallback.

Parent #2532 / siblings own visitor booking, join-by-token, notetaker, and minutes. This ticket is **kind registration + ceremony-chat default only**.

### Functional requirements

**R-1. Register `advisory`.** `KINDS` in `api/src/presentation/routes/meetingRoutes.ts` MUST contain the string `'advisory'`. After the change, `KINDS.has('advisory') === true`. Do not introduce a second kind set for the same route file.

**R-2. Persist `advisory`.** `POST /api/meetings` with body `kind: "advisory"` MUST insert `meetings.kind = 'advisory'`. It MUST NOT coerce to `'adhoc'`. List (`GET /api/meetings`) and detail (`GET /api/meetings/:id`) MUST return that kind unchanged.

**R-3. Non-ceremony by default.** `'advisory'` MUST NOT be added to `TEAM_CEREMONY_KINDS`. With `linkTeamChat` omitted, `body.linkTeamChat ?? TEAM_CEREMONY_KINDS.has('advisory')` MUST be `false`. Create MUST NOT call `BrainService.getOrCreateTeamChat` and MUST leave `meetings.chatId` null for that insert.

**R-4. Explicit opt-in unchanged.** If the client sends `linkTeamChat: true` on an advisory create, existing opt-in behaviour stands (best-effort chat attach). This ticket does not add UI, org setting, or preference for that opt-in (PRD out of scope).

**R-5. Other kinds frozen.** Do not add, remove, or rename any existing member of `KINDS` or `TEAM_CEREMONY_KINDS`. Ceremony-chat default remains **on** for `standup`, `planning`, `retrospective`, `review` and **off** for `adhoc`, `direct`, `interview`.

**R-6. Unknown-kind fallback frozen.** Kinds not in `KINDS` still coerce to `'adhoc'`. Do not change that fallback to a 400 on this ticket.

**R-7. Default title is non-ceremony.** `defaultTitle('advisory')` MUST NOT return a ceremony title (`Daily Standup`, `Planning Session`, `Retrospective`, `Review`). Either add `case 'advisory': return 'Advisory'` (or `'Advisory Session'`) or keep the existing `default: return 'Meeting'`. No other UI copy, templates, or calendar surfaces.

**R-8. Not a ceremony session.** Do not add `advisory` to ceremony session kinds, to `ceremonyMeeting.ts` `TITLES`, or to any path that auto-opens a `ceremony_sessions` row. Joining an advisory meeting MUST NOT start a team ceremony. Attendance write-through (`recordCeremonyPresence`) stays gated on an **existing** linked ceremony, as today.

**R-9. No schema / data migration.** `'advisory'` fits `VARCHAR(16)`. Do not alter `meetings.kind`, do not add a CHECK constraint, and do not backfill existing rows into `advisory`.

**R-10. Composition contract (do-not-touch).** Do not add `advisor` to `MARKETPLACE_LISTING_KINDS`. Do not add `/advisors`. `category=advisors` remains a talent filter, not a listing kind (PRD 26 / epic #2522). Visitor booking, join-by-token, silent notetaker, and minutes belong to parent #2532 and siblings — not this ticket.

**R-11. No new routes.** Create / list / get / patch / join / signaling treat an `advisory` row like any other non-ceremony meeting. No new path, query param, or body field.

**R-12. Tests (developer / QA).** Prove, without changing unrelated meeting-route behaviour:
1. `KINDS` contains `'advisory'`.
2. Create with `{ kind: 'advisory' }` persists `kind === 'advisory'` (not `'adhoc'`).
3. Create with `{ kind: 'advisory' }` and no `linkTeamChat` does not set `chatId` / does not resolve team chat.
4. Create with `{ kind: 'standup' }` still default-links team chat.
5. `adhoc` / `direct` / `interview` still do **not** default-link team chat.
6. `'advisory'` is not a member of `TEAM_CEREMONY_KINDS`.

## Design

Two closed vocabularies in `api/src/presentation/routes/meetingRoutes.ts` stay **independent**. Chat default is membership of `TEAM_CEREMONY_KINDS`, never membership of `KINDS`. Adding `'advisory'` to `KINDS` is first-class kind identity only; it does not promote advisory to a team ceremony.

### As-is (main)

| Symbol | Location | Members | Role |
|---|---|---|---|
| `KINDS` | `meetingRoutes.ts` ~L61 | `standup`, `planning`, `retrospective`, `adhoc`, `direct`, `interview`, `review` | Closed set of persistable `meetings.kind` values. **`advisory` absent.** |
| `TEAM_CEREMONY_KINDS` | `meetingRoutes.ts` ~L64 | `standup`, `planning`, `retrospective`, `review` | Subset that **default-links** a team chat on create. |
| `defaultTitle(kind)` | `meetingRoutes.ts` ~L593–603 | ceremony/direct/interview/review titles; `default: 'Meeting'` | Title when `body.title` omitted. |
| `MeetingCreateBody.kind` | same file | `z.string().optional()` | Not a Zod enum. Kind validity is **only** `KINDS.has`. |
| `meetings.kind` | `api/migrations/0292_meetings_and_calendar.sql` | `VARCHAR(16) NOT NULL DEFAULT 'adhoc'` | No CHECK. `'advisory'` is 8 chars — fits. |
| Ceremony companion | `api/src/application/ceremony/ceremonyMeeting.ts` | `TITLES = { standup, planning }` | Copies `ceremony_sessions.kind` onto `meetings.kind`. Advisory is not a ceremony session kind (`0119_ceremony_sessions.sql`: `'standup' \| 'planning'`). |
| Frontend duplicate | `frontend/src/components/meetings/ScheduleMeetingPanel.tsx` | local `KINDS` / `CEREMONY_KINDS` | **Out of scope** (visitor booking / P0 create is #2534). |

Create path (the only writer of `kind`):

```
kind      = body.kind && KINDS.has(body.kind) ? body.kind : 'adhoc'   // unknown → adhoc, not 400
title     = body.title || defaultTitle(kind)
INSERT meetings (kind, title, …)                                      // chatId unset on insert
linkChat  = body.linkTeamChat ?? TEAM_CEREMONY_KINDS.has(kind)
if (linkChat) BrainService.getOrCreateTeamChat → UPDATE meetings.chatId
```

Today `POST { kind: "advisory" }` fails `KINDS.has`, stores `adhoc`, and therefore also skips ceremony chat. The product gap is **identity**, not the chat default of that fallback.

Join (`POST /:id/join`) writes ceremony presence **only** via `findActiveCeremonyForMeeting` (existing `ceremony_sessions.meetingId` + `status='active'`). Kind string never opens a ceremony.

List (`GET /`) and detail (`GET /:id`) return the stored row; they do not re-validate kind.

### Target architecture

```
KINDS                    TEAM_CEREMONY_KINDS
standup ───────────────── standup
planning ──────────────── planning
retrospective ─────────── retrospective
review ────────────────── review
adhoc
direct
interview
advisory                  ← NEW, KINDS only. Not in TEAM_CEREMONY_KINDS.
```

Invariant: `TEAM_CEREMONY_KINDS ⊆ KINDS` remains true. Do **not** derive chat default as `KINDS.has(kind)`.


Leave `TEAM_CEREMONY_KINDS` byte-identical.

**Do not:**

- Export a second kind set, merge the two sets, or switch chat default to `KINDS.has`.
- Add `'advisory'` to `TEAM_CEREMONY_KINDS`, `ceremonyMeeting.ts` `TITLES`, or ceremony session kinds.
- Change unknown-kind fallback to 400 (R-6).

- Add `advisor` to `MARKETPLACE_LISTING_KINDS`, add `/advisors`, or edit `ScheduleMeetingPanel` (R-10; #2534).
- Auto-open `ceremony_sessions` on advisory create/join (R-8).

### Runtime contract after apply

|---|---|---|---|
| `{ kind: 'advisory' }` | `'advisory'` | `false` (`TEAM_CEREMONY_KINDS.has('advisory') === false`) | left null; `getOrCreateTeamChat` **not** called |
| `{ kind: 'advisory', linkTeamChat: true }` | `'advisory'` | `true` (explicit opt-in, R-4) | best-effort attach, same as today |
| `{ kind: 'standup' }` | `'standup'` | `true` | default-link unchanged |
| `{ kind: 'adhoc' \| 'direct' \| 'interview' }` | as sent | `false` | unchanged |
| `{ kind: 'not-a-kind' }` / omitted | `'adhoc'` | `false` | unchanged |

List and detail return `kind: 'advisory'` unchanged. Patch does not accept `kind` today — leave that.

### Test design (R-12, developer / QA)

`KINDS` / `TEAM_CEREMONY_KINDS` are module-private. Prefer HTTP (or the existing route-test harness) over exporting the sets. Do not change unrelated meeting-route behaviour to make tests easier.

1. Create `{ kind: 'advisory' }` → 201, body `meeting.kind === 'advisory'` (not `'adhoc'`).
2. Same create, no `linkTeamChat` → `meeting.chatId` is null; `BrainService.getOrCreateTeamChat` is not invoked.
3. Create `{ kind: 'standup' }` still default-links team chat (existing behaviour).
4. Create `{ kind: 'adhoc' \| 'direct' \| 'interview' }` still does **not** default-link.
5. Create `{ kind: 'nope' }` still coerces to `'adhoc'` (not 400).
6. `'advisory'` is not treated as a ceremony: no `ceremony_sessions` row; join does not call `recordCeremonyPresence` unless a session was already linked.

If a unit assertion on the set is needed, export **the same** `KINDS` / `TEAM_CEREMONY_KINDS` constants — do not duplicate them.
