# PRD: M1 leftover — CubeCL GPU backends + bench-kernel (70% go/no-go)

**Origin:** epic 2916 (kernels on main, commits `06e624e`, `1f97edf`) · **Repo of record:** `SeanHogg/builderforce-inference` (`crates/bfi-core`, `crates/bfi`)

## Problem & Goal

PRD §8 M1 go/no-go is open: token throughput of the CubeCL backends versus the PrismML llama.cpp fork has never been measured. Compile-and-match tests are not a throughput decision.

**Goal:** On one M-series Mac (Metal) and one NVIDIA host (Vulkan or CUDA), run `bfi bench-kernel` and record tok/s against a paired `llama-bench` tg128 run on the same host. **Pass only if both hosts reach at least 70% of their own paired baseline.** If either misses, file PRD §9 Fallback A (hand-written Metal via `metal-rs` and CUDA via `cudarc`, hot GEMV only) as a follow-up gap. CPU-only is never accepted as the GPU result.

## Scope

In `builderforce-inference`, limited to `crates/bfi-core` and `crates/bfi` (`bench-kernel` CLI). This ticket **measures**; it does not re-implement kernels.

- CubeCL stays pinned at `=0.10.0` (`workspace.dependencies`). No bump.
- `bf-local`, VSIX, and `ollama.rs` are untouched (`ollama.rs` is not deleted).
- ROCm is selectable but is not a required measurement host.

## Design

### Where this work lives

The bound repository (`seanhogg/builderforce.ai`) holds **no** `bfi-core` / `bfi` sources and no `bench-kernel` reference (`search_code` for `bench-kernel` returns 0 matches). It only vendors the engine via `scripts/vendor-bfi-node.mjs` and `scripts/vendor-bfi-web.mjs` from the sibling checkout `../builderforce-inference` (override: `BFI_REPO`). Consequences:

1. No kernel or CLI change is made from this repo.
2. This document is the measurement protocol and the record of truth for the go/no-go decision.
3. The measurement runs must be executed on real hardware against `builderforce-inference`; they cannot be produced by an agent without a GPU host, and **no number may be filled in that was not measured**.

### Decision rule

For each device `d` in {Metal host, NVIDIA host}:

```
ratio_d = bfi_bench_kernel_toks_per_s_d / llama_bench_tg128_toks_per_s_d
GO  iff  ratio_metal >= 0.70  AND  ratio_nvidia >= 0.70
```

- The denominator is the `llama-bench` tg128 run **on the same host**, same session, same model/workload class. Published or estimated baselines are not valid.
- Both devices are required. A single-device result is a NO-DECISION, not a GO.
- A run whose reported backend is `cpu` (e.g. `BFI_BACKEND` fell through because no GPU was found) is invalid for this ticket and must be re-run or recorded as a failed attempt.

### Measurement protocol

Per host, in a clean release build (`cargo build --release -p bfi`):

1. **Preconditions** — `cargo test -p bfi-core` and `cargo test -p bfi-core --features vulkan` both 25/25 (includes `gpu_pq2/ptq1_matches_cpu_when_device_present`). Record the commit SHA of `builderforce-inference` and confirm CubeCL is `=0.10.0`.
2. **Backend pin** — set `BFI_BACKEND` explicitly (`metal` on the Mac; `cuda` or `vulkan` on NVIDIA) and confirm from the tool's own output that the selected backend is the GPU, not a probe-order fallthrough.
3. **Workload** — `bfi bench-kernel` with the synthetic Bonsai-27B shape (`hidden=5120`), or `--gguf <path>` when the real model is available. Use the same workload on both hosts where possible and record which one was used.
4. **Baseline** — on the same host, run the PrismML llama.cpp fork `llama-bench` with tg128 on the comparable workload; capture tok/s.
5. **Repeats** — run each measurement at least 3 times after a warm-up run; record the median and the spread. Close other GPU-heavy processes; on the Mac, plugged in, no thermal throttling.
6. **Record** — fill the template below verbatim from tool output.
