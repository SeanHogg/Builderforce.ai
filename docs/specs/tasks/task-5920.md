# PRD: Package-entry SyncCoordinatorHost, holder reader, and HTTP transport export

Issue: #5899 remains blocked. Lease factories already on `@builderforce/local-first` are not this gap.

## Problem & Goal

A host can obtain a `SyncCoordinatorLease` from `@builderforce/local-first`. `packages/local-first/src/index.ts` re-exports `createSyncLease` and `createDeviceStoreCoordinatorLease` plus their types (`ed482710b`, ancestor of `origin/main`; package vitest 2/2 passed). That does not unblock #5899.

Three holes remain:

- Nothing on the package entry builds a `SyncCoordinatorHost`. `clients/vscode/src/installSyncCoordinator.ts` defines the host shape; callers still cannot construct one from `@builderforce/local-first`.
- A lease may be held by another device. A restored or synced process cannot read who holds it before it decides to start or drain.
- `createHttpSyncTransport` is still not on the package entry.

Goal: close only this gap by shipping a package-entry factory that actually constructs a `SyncCoordinatorHost`, a package-entry holder reader that reports the current holder from restored or synced state without starting the host, and an entry export of `createHttpSyncTransport`. Type-only re-exports, stubs, and comments do not close it. Do not implement this in `clients/vscode/src/extension.ts`.

## Target users / ICP roles

- Client integrators of `@builderforce/local-first` who must install a sync coordinator without hand-building a host or importing deep module paths.
- Restored or synced device processes that must see a foreign holder before start or drain, so they do not steal a lease held on another device.
- The VS Code install path that already specifies `SyncCoordinatorHost` in `clients/vscode/src/installSyncCoordinator.ts` and should consume a package-built host rather than become the construction site.

## Scope

In scope, in `packages/local-first` and its package-entry tests:

- A public factory on `packages/local-first/src/index.ts` that returns a live `SyncCoordinatorHost` satisfying the shape defined in `clients/vscode/src/installSyncCoordinator.ts`.
- Export of that host type from the same entry so callers do not import the type from the VS Code client.
- A public holder reader on the same entry. It reads the current lease holder from persisted device-store or lease state after restore or sync, including when another device holds the lease.
- Re-export of the existing `createHttpSyncTransport` and its public types from that entry, matching the lease-factory export pattern. Reuse the existing implementation; do not rewrite transport behavior unless the host cannot be constructed without a small adapter.
- Package vitest coverage, alongside `syncLeaseEntry.test.ts`, that imports from the package entry, constructs a host, and reads a holder.
- Reuse internal helpers if they already exist. Add a factory or reader only where no construct-or-read path exists. Names follow `createSyncLease` / `createDeviceStoreCoordinatorLease` (`createSyncCoordinatorHost` and a clearly named holder reader if no internal name already fits).

`clients/vscode/src/installSyncCoordinator.ts` is the shape spec. It may later import the package type. It is not an acceptable substitute for package-entry construction.

## Functional requirements

1. From the package entry, a caller can construct a `SyncCoordinatorHost` in one factory call. The factory accepts the dependencies the host shape needs to start or drain, including a coordinator lease from the existing lease factories and an HTTP sync transport from `createHttpSyncTransport`. It returns a real host object, not a type and not a throw-on-use stub.
2. The constructed host matches the `SyncCoordinatorHost` contract in `clients/vscode/src/installSyncCoordinator.ts` (same required fields and callable start/drain surface that file already defines). Do not invent a second host contract.
3. The holder reader is callable without acquiring the lease and without starting or draining the host. After state is restored or synced, it returns the holding device identity already stored by the lease when another device holds it, and a distinct empty result when nobody holds it. It must not only work in the process that originally took the lease.
4. `createHttpSyncTransport` and its public types are importable from `@builderforce/local-first` / `packages/local-first/src/index.ts`. Deep-path imports are not the supported surface.
5. Existing `createSyncLease` and `createDeviceStoreCoordinatorLease` exports stay as shipped in `ed482710b`. This work composes with them; it does not replace them.
6. Tests import only the package entry. They construct a host through the new factory and read a holder in the other-device-held case and the unheld case. A missing export, a factory that does not return a host, or a reader that cannot see a foreign holder fails the tests.
7. No change to `clients/vscode/src/extension.ts`. That file has unrelated dirty hunks and is owned elsewhere.

## Acceptance criteria

- `packages/local-first/src/index.ts` exports a factory that builds a `SyncCoordinatorHost`, the host type, a holder reader, and `createHttpSyncTransport` with its public types.
- A package vitest, run with the package test script, imports those symbols from the entry, constructs a host, and asserts the holder is readable when another device holds the lease and when the lease is unheld. Reading the holder does not start the host or take the lease.
- The constructed host satisfies the shape in `clients/vscode/src/installSyncCoordinator.ts`.
- Existing lease-entry tests still pass. New tests pass. The previous 2/2 lease-entry result is not regressed.
- `clients/vscode/src/extension.ts` is unmodified by this change.
- The gap is not closed by type re-exports alone, by a factory that never returns a host, or by a reader that only works in the acquiring process.

## Out of scope

- Any edit to `clients/vscode/src/extension.ts`, including wiring install, activation, or drain there.
- Closing #5899 in the issue tracker, rebasing unrelated dirty client hunks, or treating lease-factory shipment `ed482710b` as the fix.
- Redesigning lease acquisition, device identity, sync protocol, or HTTP transport behavior beyond the export and the wiring needed to construct the host.
- New UI, auth, or a second transport.
- Building the host only inside the VS Code client, or proving the gap with a deep import that bypasses the package entry.
