# PRD: Frontend Architecture Ratchet and Blog Index Fix

**Status:** WIP

## Problem & Goal

The frontend architecture ratchet is not reliably synchronized with the current frontend structure, allowing regressions or failing on already-approved legacy violations. In addition, the blog index does not consistently reflect the repository’s canonical set of published posts, which can omit or incorrectly list articles.

Goals:

- Restore deterministic enforcement of the existing frontend architecture rules.
- Preserve approved legacy violations without permitting new architectural debt.
- Make the blog index accurately represent all published posts.
- Prevent future blog posts from requiring manual index maintenance.
- Integrate both fixes into the existing validation and CI workflows.

## Target Users / ICP Roles

- **Frontend developers:** Receive actionable architecture failures and maintain compliant module boundaries.
- **Repository maintainers:** Review intentional baseline changes without silently grandfathering new violations.
- **Content maintainers:** Publish posts without needing to update a separate index manually.
- **Site visitors:** See a complete, correctly linked list of published articles.

## Scope

- Repair the existing frontend architecture ratchet implementation and configuration.
- Align its baseline with the current approved frontend architecture.
- Ensure the ratchet runs locally and in CI.
- Reconcile the blog index with the canonical blog post metadata or content manifest.
- Add automated coverage for architecture regressions and blog-index completeness.
- Preserve existing frontend behavior, routes, URLs, and design.

## Functional Requirements

### Frontend Architecture Ratchet

1. The ratchet must enforce the repository’s existing architecture rules and boundaries.
2. It must inspect all relevant frontend source files, including newly added files.
3. Existing, explicitly approved violations may remain, but any new violation must fail validation.
4. Approved violations should be identified by a stable file-and-rule fingerprint so unrelated line-number changes do not create false failures.
5. Violations must produce deterministic, actionable output containing the affected file and violated rule.
6. The command must return a failing exit code when new violations are detected and a successful exit code when the frontend is compliant or only contains approved baseline violations.
7. Generated output, dependencies, build artifacts, and other non-source paths must be excluded according to the repository’s established configuration.
8. Baseline updates must be deliberate and reviewable; the implementation must not use broad exclusions to conceal new debt.
9. The existing CI workflow must invoke the ratchet and block merges when it fails.

### Blog Index

1. The canonical blog metadata, manifest, or content collection must be the source of truth.
2. The blog index must contain every published post exactly once.
3. Draft, scheduled, or otherwise unpublished posts must not appear in the public index.
4. Posts removed from the canonical source must also disappear from the index.
5. Each index entry must link to the post’s existing canonical route and preserve established metadata and ordering behavior.
6. Adding a published post to the canonical source must automatically update the rendered or generated blog index.
7. The fix must not introduce duplicate listings or broken links to blog posts.

## Acceptance Criteria

### Architecture Ratchet

- Given the repository’s current frontend and approved legacy baseline, when the architecture check runs, it exits successfully.
- Given a newly introduced prohibited dependency, boundary violation, or unapproved architectural pattern, when the check runs, it exits non-zero and identifies the file and rule.
- Given an approved legacy violation whose source line numbers change, when the check runs, it does not report a new violation.
- Given two check runs against the same source revision, when executed in different environments, the reported results are identical.
- The CI workflow fails when the ratchet detects a new violation.
- Any changes to the approved baseline are limited to reviewed, intentional exceptions.

### Blog Index

- An automated test confirms that the set of published canonical posts and the set of blog-index entries have no missing or extra posts.
- Every published post appears exactly once in the index and links to a valid existing post route.
- Adding or removing a published post in the canonical source updates the index without a separate manual index edit.
- Unpublished posts do not appear in the public index.
- Existing blog filters, pagination, metadata rendering, and navigation behavior remain intact.

### Regression Validation

- Existing frontend lint, type-check, test, and production-build commands pass.
- The architecture ratchet and blog-index validation are discoverable through the repository’s documented validation workflow.

## Out of Scope

- Redesigning the frontend architecture or introducing a new application framework.
- Broad frontend refactors unrelated to repairing the ratchet.
- Removing approved legacy architecture debt unless explicitly addressed as a separate task.
- Rewriting blog content or changing editorial, categorization, or publishing policies.
- Redesigning the blog listing UI.
- Changing existing post URLs, route conventions, or SEO strategy unnecessarily.
- Introducing a new CMS or content-management platform.
- Manually maintaining a second list of published posts.
