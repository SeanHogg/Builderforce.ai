# PRD 39 P1: Gateway Worker Split — RouteReplay Port + Gateway Worker + Graph Guard

## Problem & Goal

The current API composition causes the LLM replay path and tool context to depend on the full in-process application. This makes it difficult to expose the API through a dedicated Cloudflare Worker without the Worker’s module graph reaching the primary `src/index.ts` entrypoint.

Introduce a dependency-inverted `RouteReplay` port, bind it to the existing in-process implementation at the API composition root, and add an isolated gateway Worker entrypoint. A build-time graph guard must prevent future transitive imports from reconnecting the gateway Worker to `src/index.ts`.

The normative behavior is defined by [`Builderforce.ai/docs/specs/39-prd-platform-closeout.md`](Builderforce.ai/docs/specs/39-prd-platform-closeout.md) §1.

## Target Users / Roles

- **Backend engineers:** Add APIs or tool capabilities without coupling the gateway Worker to the primary API entrypoint.
- **Platform/release engineers:** Build and validate the gateway Worker independently, with automated enforcement of its import boundary.
- **Operators:** Use the Worker in a later deployment push; route movement and deployment are not part of this code push.

## Scope

### In scope

- Add `application/llm/routeReplay.ts` containing the `RouteReplay` port.
- Refactor `builtinToolContext.ts` to depend only on the `RouteReplay` port.
- Bind the port to the existing in-process app from the `builderforce-api` composition root.
- Add:
  - `api/src/gatewayWorker.ts`
  - `api/src/presentation/gatewayApp.ts`
  - `api/wrangler.gateway.toml`
  - `api/scripts/check-gateway-worker-graph.mjs`
- Add a graph check analogous to `check-sites-worker-graph.mjs`.
- Integrate the graph check into the API build or verification pipeline.
- Preserve existing in-process API and replay behavior.

### Required file responsibilities

| File | Responsibility |
|---|---|
| `application/llm/routeReplay.ts` | Defines the application-layer `RouteReplay` contract. |
| `builtinToolContext.ts` | Consumes `RouteReplay` through the port; contains no concrete app dependency. |
| `builderforce-api` composition root | Constructs the in-process implementation and injects it into the tool context. |
| `api/src/presentation/gatewayApp.ts` | Creates the Worker-facing application and request handler. |
| `api/src/gatewayWorker.ts` | Thin Worker entrypoint that exports the Worker handler. |
| `api/wrangler.gateway.toml` | Defines the gateway Worker build/runtime configuration and entrypoint. |
| `api/scripts/check-gateway-worker-graph.mjs` | Verifies the gateway module graph cannot reach `src/index.ts`. |

## Functional Requirements

1. **RouteReplay port**
   - Define a `RouteReplay` interface or equivalent port in `application/llm/routeReplay.ts`.
   - The contract must represent the route replay operation defined in Program 39 §1 without exposing transport-, runtime-, or composition-root-specific types.
   - Existing callers must be able to use the port without importing a concrete application implementation.

2. **Dependency inversion**
   - `builtinToolContext.ts` must import the `RouteReplay` type/port from `application/llm/routeReplay.ts`.
   - `builtinToolContext.ts` must not instantiate or import the in-process app, gateway app, Worker entrypoint, or other concrete `RouteReplay` adapter.

3. **In-process binding**
   - The `builderforce-api` composition root must create the existing in-process route replay implementation and inject it into `builtinToolContext`.
   - The adapter must satisfy the `RouteReplay` port at compile time.
   - Existing in-process route replay behavior must remain unchanged.

4. **Gateway application**
   - `api/src/presentation/gatewayApp.ts` must expose a Worker-compatible application/request handler.
   - It may use shared application services but must not import `api/src/index.ts`.
   - Any `RouteReplay` dependency required by the gateway app must be supplied through the port and bound in the gateway composition path.

5. **Gateway Worker entrypoint**
   - `api/src/gatewayWorker.ts` must be a minimal Worker entrypoint that delegates to `gatewayApp`.
   - `api/wrangler.gateway.toml` must point to `api/src/gatewayWorker.ts` and use the repository’s established Worker configuration conventions.
   - The Worker must bundle successfully in isolation from the primary API entrypoint.

6. **Gateway graph guard**
   - The guard must analyze the transitive static module/import graph rooted at the gateway Worker entrypoint.
   - The check must fail with a non-zero exit code if any reachable module resolves to `api/src/index.ts`.
   - Failure output must identify the import chain or offending edge sufficiently to diagnose the violation.
   - The check must follow the behavior and conventions of `check-sites-worker-graph.mjs` where applicable.
   - The check must run as part of the API build or required verification pipeline, not merely as an optional local script.

7. **Compatibility**
   - Existing API typechecking and tests must continue to pass.
   - The in-process application must continue to expose the same routes and behavior after the binding is moved to the composition root.

## Acceptance Criteria

- [ ] `application/llm/routeReplay.ts` exports the `RouteReplay` port required by Program 39 §1.
- [ ] `builtinToolContext.ts` depends on the port and has no dependency on a concrete route replay or application implementation.
- [ ] The `builderforce-api` composition root binds the existing in-process implementation to the `RouteReplay` port.
- [ ] `api/src/presentation/gatewayApp.ts` provides the gateway request handler without importing `api/src/index.ts`.
- [ ] `api/src/gatewayWorker.ts` is the entrypoint configured by `api/wrangler.gateway.toml`.
- [ ] Running `api/scripts/check-gateway-worker-graph.mjs` against the current gateway graph succeeds.
- [ ] The graph guard fails deterministically when `api/src/index.ts` is introduced into the gateway’s transitive import graph.
- [ ] The graph guard is enforced by the API build or verification pipeline.
- [ ] The gateway Worker bundles successfully using `api/wrangler.gateway.toml`.
- [ ] The generated gateway bundle contains no import or reference to `api/src/index.ts`.
- [ ] API typechecking passes.
- [ ] API tests pass.
- [ ] Existing in-process API behavior remains operational.

## Out of Scope

- Moving production traffic or DNS routes to the gateway Worker.
- Performing the push 2 deployment or route-migration steps; these are operator actions.
- Changing the public route replay behavior beyond the port refactor required by Program 39 §1.
- Refactoring unrelated API modules or other Worker entrypoints.
- Replacing the in-process app, existing deployment infrastructure, or the established Wrangler configuration model.
- Adding observability, scaling, caching, or performance behavior not required to split and validate the gateway Worker.
- Introducing a second route replay implementation solely for the gateway.
