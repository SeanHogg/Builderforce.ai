# PRD: Deflake app-runtime-stop timing tests on Windows

## Problem & Goal

`packages/browser/tests/app-runtime-stop.test.ts` in `builderforce-webcontainers` passes on Linux CI and fails intermittently on Windows. The test asserts wall-clock timing and uses fixed sleeps (`setTimeout` / `await delay`, `Date.now()` / `performance.now()` deltas), which are unstable under Windows scheduling.

Goal: make stop/drain behavior deterministic so the file passes 10 consecutive Windows runs, while preserving the meaning of the existing assertions — stop drains pending output before resolving, and `stopTimeoutMs` bounds a stuck drain.

## Target users / ICP roles

- Engineers maintaining `builderforce-webcontainers` browser runtime tests on Windows and Linux CI.
- Downstream release agents that publish only when library code and package versions change.

## Scope

- Read `packages/browser/tests/app-runtime-stop.test.ts` and the app runtime stop/drain implementation it imports under `packages/browser/src`.
- Identify every fixed sleep and wall-clock delta assertion in that test.
- Replace them with deterministic waits: await stop/drain promises or events the runtime already exposes (for example the `stop()` promise resolving after drain, or a drained/stopped event), or Vitest fake timers (`vi.useFakeTimers` + `vi.advanceTimersByTimeAsync`) where the code under test uses real timers.
- Keep both behaviors asserted and meaningful:
  - stop drains pending output before resolving;
  - `stopTimeoutMs` bounds stop (a stuck drain still resolves or rejects within the timeout; with fake timers, advance past `stopTimeoutMs` and assert the bounded outcome).
- Prefer changing only the test file. Add the smallest library seam only if no event or promise can be awaited.
- Verify on this Windows machine: run that single file 10 times in a row via `pnpm vitest run packages/browser/tests/app-runtime-stop.test.ts` from `builderforce-webcontainers`. All 10 must pass. Run the root `typecheck` script. Do not run the full suite.
- Ship from repo `builderforce-webcontainers` only:
  - Test-only change: commit that test file (`allowBaseBranch: true`) and push (`allowBaseBranch: true`). No version bump, tag, or release.
  - Library change: bump both `packages/core/package.json` and `packages/browser/package.json` to the same next unused calendar version (`2026.11.12` is taken; check `git tag --list 'v2026.11.*'` and `npm view` if available), commit library + test + version files, create and push tag `v<version>` (pre-authorized; `release.yml` publishes). Never reuse a version.
- If a CI build is `in_progress` on main, wait before pushing over it.
- Check `git_diff --cached` before committing. Commit only authored paths. No Co-Authored-By. Never reset or stash. Do not rewrite files authored by other sessions.

## Functional requirements

1. No fixed sleeps (`setTimeout`, delay helpers used as timing) and no wall-clock delta assertions remain in `app-runtime-stop.test.ts`.
2. Stop-drains-pending-output is still asserted by awaiting the real stop/drain completion (promise or event), not by sleeping.
3. `stopTimeoutMs` still bounds a stuck drain: the test advances or awaits past the timeout and asserts the bounded resolve/reject outcome. The timeout assertion is not deleted or weakened.
4. Fake timers are used only where the code under test depends on real timers, and are advanced with async timer APIs so promises flush.
5. Library edits, if any, are the smallest seam required for a deterministic wait and stay inside the stop/drain path exercised by this test.
6. If library code changes, both package versions match and are the next free `2026.11.*` calendar version not present in git tags or npm.
7. Verification is limited to 10 consecutive runs of this file plus root `typecheck`.

## Acceptance criteria

- `app-runtime-stop.test.ts` passes 10 consecutive Windows runs of `pnpm vitest run packages/browser/tests/app-runtime-stop.test.ts`.
- The file contains no fixed sleeps or wall-clock delta assertions.
- Drain-before-resolve and `stopTimeoutMs` bound assertions are still present and check the same outcomes as before.
- Root `typecheck` passes.
- Changes are committed and pushed on `builderforce-webcontainers` main (`allowBaseBranch: true`), commit limited to authored paths after reviewing the staged diff.
- Tag `v<version>` exists and is pushed only if library code changed; otherwise there is no version bump, tag, or release.
- Report states what was flaky, what the deterministic wait is, the 10-run result, commit hash, and push/tag result.

## Out of scope

- Weakening, deleting, or loosening drain or `stopTimeoutMs` assertions to force a pass.
- Other test files, unrelated library code, or the full test suite.
- `git reset`, `git stash`, checkout, or rewrite of files not authored in this task.
- Version bump, tag, or release when only the test file changed.
- Reusing `2026.11.12` or any already-published or already-tagged version.
- Co-Authored-By trailers.
- Work in `Builderforce.ai` or other workspace checkouts.
