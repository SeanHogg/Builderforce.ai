# PRD: Advisor Profile — Resources Tab (Own Marketplace Listings)

**Status:** WIP  
**Owner:** Product  
**Surface:** Advisor profile → Resources tab

## Problem & Goal

Advisor profiles currently lack a dedicated place to show what that advisor already publishes on the marketplace. Visitors cannot tell which agents, skills, courses, playbooks, or templates belong to the advisor they are viewing, and may see unrelated catalog items or a dead-end tab.

**Goal:** The Resources tab on an advisor profile shows only that advisor’s existing marketplace listings (agent, skill, course, playbook, template). If they have none, show an empty state. Do not create, import, or attribute listings that are not already theirs.

## Target users / ICP roles

- **Profile visitor** (buyer, learner, hiring manager): discovers what this advisor already offers without leaving the profile.
- **Advisor (listing owner):** expects their public profile to reflect only their published marketplace inventory.
- **Marketplace operator / support:** needs a deterministic, auditable mapping from profile → owner’s listings.

## Scope

In scope for this WIP:

- Resources tab on the advisor profile.
- Read-only surfacing of that advisor’s **existing** marketplace listings of types: **agent**, **skill**, **course**, **playbook**, **template**.
- Ownership filter: listings must belong to the profile’s advisor (same owner identity used by the marketplace).
- Empty state when the advisor has zero qualifying listings.
- Navigation from a listing card/row into the existing marketplace listing detail.
- Respect existing listing visibility (e.g. unpublished, draft, deleted, or otherwise non-public listings stay out of the public profile).

## Functional requirements

1. **Tab presence:** Advisor profile includes a Resources tab. Opening it loads that advisor’s listings only.
2. **Ownership:** Query and render listings whose owner is the advisor of the current profile. Never mix in other advisors’ listings, editorial picks, recommendations, or global catalog results.
3. **Listing types:** Include only marketplace listing types **agent**, **skill**, **course**, **playbook**, and **template**. Exclude any other entity types.
4. **Existing inventory only:** Source from current marketplace records. Do not generate placeholder listings, auto-create drafts, or backfill from non-marketplace content (bio, files, social links, etc.).
5. **Empty state:** If the advisor has no qualifying visible listings, show a clear empty state (no fake cards, no “suggested for you” substitutes). Empty is a valid success state.
6. **Item presentation:** Each listing shows enough to identify it (title, type, and other fields already used on marketplace cards) and links to the canonical listing page.
7. **Type mix:** Advisors may have zero or more of each type; the tab shows the union of their listings. Grouping or filtering by type is allowed if it does not hide owned listings or add non-owned ones.
8. **Visibility:** Public profile Resources must only include listings the visitor is already allowed to see in the marketplace. Private/draft/removed listings do not appear.
9. **Consistency:** Counts, titles, types, and availability match marketplace source of truth at load time (no stale orphan cards after unpublish/delete).
10. **Errors:** If the listings fetch fails, show a recoverable error; do not fall back to other advisors’ or global listings.

## Acceptance criteria

- Given an advisor with one or more public listings of the allowed types, Resources shows all of those listings and no others.
- Given an advisor with a mix of allowed types, each owned listing of those types appears; types they do not own simply have no items.
- Given an advisor with zero qualifying visible listings, Resources shows the empty state and zero listing cards.
- Given listings owned by other advisors, none appear on this profile’s Resources tab.
- Given a draft, unpublished, or deleted listing owned by this advisor, it does not appear on the public Resources tab.
- Clicking a listing opens that listing’s existing marketplace detail, not a new or duplicated resource.
- Removing or unpublishing a listing in the marketplace removes it from Resources on subsequent load.
- Adding a new public listing of an allowed type for that advisor causes it to appear on Resources on subsequent load.
- A failed listings request does not populate the tab with unrelated catalog content.

## Out of scope

- Creating, editing, publishing, or importing listings from the profile.
- Recommendations, related advisors, or “you might also like” modules on this tab.
- Listing types other than agent, skill, course, playbook, and template.
- Reviews, bookings, calendar, messaging, or other profile tabs.
- Search, sort, or filter UX beyond what is needed to list the advisor’s own items (nice-to-have, not required for this WIP).
- Changing marketplace ranking, pricing, entitlements, or SEO beyond linking to existing listing pages.
- Bulk admin reassignment of listing ownership.

### R-1 — Host surface and tab presence

The Resources tab SHALL appear on the **existing public talent/advisor profile** at `/talent/[id]` after that profile has loaded successfully.

- There is **no** `/advisors` route today. This ticket SHALL NOT add one, a parallel Advisor destination, or a new marketplace family (PRD 26 kill condition).
- `TalentProfileView` is currently a single stack (header, stats, about, skill **chips**, reviews, résumé) with **no tabs**. This ticket MAY introduce tab chrome so Resources is a named tab. Existing profile content SHALL remain reachable (as the default/Overview tab, or still stacked above the tab). This ticket SHALL NOT add Portfolio, Activity, or other new tabs.
- Opening Resources SHALL load **that profile’s** listings only (see R-2, R-7). Switching to another `/talent/[id]` SHALL drop the previous advisor’s cards before or as the new fetch settles (no cross-profile bleed).
- Sibling **#2581** owns visitor chat on this profile. Resources SHALL NOT add a messenger, thread, or Message CTA of its own.
- Sibling **#2580** owns marketplace `?category=advisors` filters. Resources SHALL NOT change marketplace browse filters, ranking, or category query params.

### R-2 — Ownership identity

Every item on Resources SHALL belong to the advisor of the current profile.

- Owner identity is the talent profile’s **`FreelancerProfile.userId`**.
- For canvas creation listings (`catalog_items`), that identity is **`publisherRef`**, already projected as `sellerRef` on `CreationListingView`.
- For other allowed producers (R-3), the architect SHALL map the existing owner/publisher column to the same `userId`. Do not invent a second identity or a join through display name.
- Resources SHALL NEVER mix in other advisors’ listings, editorial picks, recommendations, “you might also like”, related advisors, global catalogue pages, or talent-recommendation rows (`talentRecommendations.ts`).
- Matching by `sellerName`, headline, skill chips, or bio text is forbidden.

### R-3 — Allowed kinds and producers (closed set)

Resources SHALL include the union of this advisor’s **existing, visitor-visible marketplace listings** whose kind is one of:

| Kind | Existing producer (do not invent a new one) |
|---|---|
| `agent` | Public `catalog_items` with `kind = 'agent'`, **and/or** public `ide_agents` this user published (`published = true`, `status = 'active'`, not a demo fixture per `publicAgentScope`). Built-in seat agents (CFO/CRO/…) never qualify. |
| `skill` | Public rows in the **skill catalogue** (`marketplace_skills` / `listMarketplaceSkills`). **Not** a canvas listing kind. |
| `course` | Public `catalog_items` with `kind = 'course'`. |
| `playbook` | Public `catalog_items` with `kind = 'playbook'`. |
| `template` | Public `catalog_items` with `kind = 'template'`. |

- `skill` is **not** in `MARKETPLACE_LISTING_KINDS` / `LISTING_KIND_IDS`. This ticket SHALL NOT add `skill` or `advisor` to that registry.
- Canvas kinds that exist but are **out of scope** even when this advisor owns them: `game`, `app`, `automation`, `pack`, `dashboard`, `dataset`, `tool`, `creative`, `survey`, `book`, `room`, and any future kind not in the five.
- Talent, gig, company, knowledge-article, booking-service, LMS-enrolment, and résumé objects are **not** Resources items.
- If two producers describe the same product, show it **once** (dedupe by stable listing id / slug). Architect owns the union; BA requires no duplicates and no omissions of owned, allowed, visible listings.

### R-4 — Skill chips are not listings

`FreelancerProfile.skills: string[]` are expertise chips on the profile, **not** marketplace skill listings.

- Resources SHALL NOT render those chips as cards, SHALL NOT invent a listing per chip, and SHALL NOT treat an empty skill catalogue as “use the chips instead”.
- A skill appears on Resources only when a **marketplace skill listing** already exists for this advisor and is visitor-visible (R-6).

### R-5 — Existing inventory only

Source SHALL be current marketplace records. Resources SHALL NOT:

- generate placeholder or demo cards;
- auto-create drafts or listings;
- backfill from bio, files, social links, résumé, reviews, bookings, courses the advisor has *taken*, or any non-marketplace content;
- attribute another seller’s listing to this advisor;
- copy or duplicate a listing into a new “resource” record.

Adding inventory is the existing marketplace publish flow, out of scope for this tab.

### R-6 — Visibility (public profile = public marketplace)

Public Resources SHALL show only listings the visitor is **already allowed to see** in the marketplace.

For `catalog_items`, that is the same predicate as `browseCreationListings`: `visibility = 'public'` **and** `publishedAt IS NOT NULL`. Withdrawn / non-public rows are invisible to non-holders (`resolveListingAccess` reason `withdrawn`).

SHALL NOT appear on the public tab:

- draft, staged, unpublished, private, deleted, or withdrawn listings;
- seller-only management rows;
- licence-only access to a withdrawn listing (a buyer who holds a licence still must not see that listing on the **public profile** tab);
- demo-fixture agents excluded by `publicAgentScope`.

The **owner** viewing their own public profile still sees the **public** set only. Drafts stay on the existing seller management surface (`sellerListings`), which this tab SHALL NOT reuse (R-7).

If the talent profile itself is not publicly loadable, Resources is not offered (existing profile error/sign-in path unchanged).

### R-7 — Query shape (server-side owner filter)

The load for Resources SHALL be **scoped to this advisor on the server**.

- `GET /api/marketplace/listings` (`browseCreationListings`) today accepts `q`, `kind`, `page`, `limit` only — **no seller filter**. Resources SHALL NOT client-filter a page of the global catalogue: page size is 24 (max 48), so owned items would be dropped and foreign items would leak if the filter were wrong.
- `sellerListings` is the authenticated seller’s **management** view (all visibilities, **tenant-scoped**). It SHALL NOT back the public tab (draft leak + wrong tenant scope for a cross-tenant shop window).
- Architect SHALL add or extend a **public-by-owner** read (owner = profile `userId`, kinds = the five, visibility = public/published as in R-6). Cross-tenant public catalogue rules already used by browse (`acrossTenants` / `public_catalogue`) apply; do not require the visitor to share the advisor’s tenant.
- Unauthenticated visitors who can already see the public talent profile SHALL be able to open Resources (same as public listing browse / `/marketplace/listing/[slug]`).

### R-8 — Empty state

If the advisor has **zero** qualifying visitor-visible listings, Resources SHALL show a clear empty state and **zero** listing cards.

- Empty is a **success** state, not an error.
- SHALL NOT fill the tab with suggested listings, other advisors, editorial picks, or fake cards.
- SHALL NOT show a create/publish form on this tab (out of scope). A visitor-facing sentence that this advisor has not published marketplace resources is sufficient.
- An advisor who owns only out-of-scope kinds (e.g. only `app` / `pack`) SHALL still get the empty state.

### R-9 — Item presentation and navigation

Each card/row SHALL identify the listing with fields **already used on marketplace cards** (at minimum: title/name and kind). Other existing card fields (summary, icon, price including Free at `priceCents = 0`, rating, install count) MAY be reused; do not invent a new card design language.

- Clicking a canvas listing SHALL navigate to the **canonical** existing page `/marketplace/listing/{slug}` (`frontend/src/app/marketplace/listing/[slug]/page.tsx`). Do not add a profile-local resource detail, a duplicate listing, or an in-tab preview that replaces that page.
- Clicking a skill or registry-agent listing SHALL open **that producer’s existing public detail**, not a new URL invented for this tab.
- Primary CTA on the listing remains the marketplace CTA (Install / Run / Play / etc. on the listing page). Resources itself is a **directory**, not a checkout.

### R-10 — Type mix and optional grouping

Advisors may have zero or more of each allowed kind. The tab SHALL show the **union**.

- Grouping or in-tab filter-by-kind is allowed only if it does **not** hide owned listings and does **not** add non-owned ones.
- A kind the advisor does not own simply has no items (no empty-group obligation).
- Order MAY follow existing marketplace order (e.g. install count then published date) or kind-then-title. Do not invent a new ranking product.

### R-11 — Completeness and consistency

- Given N qualifying visible listings, Resources SHALL show all N (paginate **inside the tab** if needed). Silent truncation at the global browse page size is a defect.
- Counts, titles, kinds, prices, and availability SHALL match marketplace source of truth **at load time**.
- Publishing a new public allowed-kind listing for this advisor SHALL make it appear on the **next** Resources load.
- Unpublishing, withdrawing, or deleting a listing SHALL remove it on the **next** Resources load. No stale orphan cards.
- This ticket does not require live push/websocket refresh.

### R-12 — Errors

If the listings fetch fails, Resources SHALL show a **recoverable** error (message + retry).

- SHALL NOT fall back to the global catalogue, another advisor, cached cards from a previous profile, or recommendations.
- SHALL NOT use the global API-error toast as the only signal if the profile page already has an in-flow error pattern (follow `TalentDetailClient` / talent i18n).
- A failure is distinct from empty (R-8): retry is present on error, absent on empty.

### R-13 — Read-only

Resources is read-only for every visitor, including the owner.

Out of scope (do not build on this tab): create, edit, publish, unpublish, import, bulk reassignment, pricing, entitlements, SEO, checkout, bookings, reviews management, or messaging.

### R-14 — Accessibility and copy

- Resources SHALL be a real tab (keyboard-selectable, labelled, not a decoration).
- Kind labels SHALL use existing marketplace i18n (`marketplaceListing.kind.*` or equivalent), not hardcoded SCORE/Academy branding.
- Empty and error copy SHALL be i18n keys under the talent or marketplace namespace, not inline English-only strings if that file already uses `next-intl`.

## Design

### Architecture overview

The Resources tab unifies listings from **three independent producers** (canvas `catalog_items`, `marketplace_skills`, and `ide_agents`) under a single owner identity (`FreelancerProfile.userId`). Each producer already has its own public/visibility predicate; the tab composes them with an owner filter and deduplicates by stable listing id/slug.

**Data-flow direction:** Frontend → single new public API endpoint → three parallel DB queries (one per producer) → union in application layer → paginated response. No client-side filtering of global browse; no reuse of `sellerListings`.

### Hosting surface

- `frontend/src/app/talent/[id]/TalentDetailClient.tsx` + `frontend/src/app/talent/[id]/page.tsx`
- `TalentProfileView` (`frontend/src/components/freelance/TalentProfileView.tsx`) is currently a flat vertical stack (header → stats → about → skill chips → reviews → résumé) with **no tab chrome**. This ticket introduces tab chrome:
  - **Overview** tab (default, existing content)
  - **Resources** tab (new)
- `TalentDetailClient` already holds `profile.userId` once loaded — the Resources tab fetches after the user clicks into it (lazy load), passing `userId` as a query param.

### API: `GET /api/marketplace/listings/by-owner`

**New route** in `api/src/presentation/routes/creationListingRoutes.ts` (public router — `createPublicListingRoutes`), or a new route file if preferred. This is the public-by-owner read required by R-7.

**Route:** `GET /api/marketplace/listings/by-owner?owner=<userId>&page=1&limit=50`

- **Public, no auth required.** Same cross-tenant read model as `browseCreationListings` and the public talent profile.
- Takes `owner` (required, the `userId`), `page`, `limit` (default 50, max 100 — larger than browse because a single advisor rarely has >50 items across all five kinds).

**Response shape:**

```json
{
  "items": [
    {
      "kind": "agent" | "skill" | "course" | "playbook" | "template",
      "producer": "catalog" | "marketplace_skill" | "ide_agent",
      // Producer-specific fields — enough to render a marketplace card
      // catalog: slug, name, summary, iconUrl, priceCents, currency, installCount,
      //          rating, kind, publishedAt → link /marketplace/listing/{slug}
      // skill:  slug, name, description, category, iconUrl, priceCents, pricingModel,
      //         downloads, likes, authorUsername, authorDisplayName → link /marketplace/skills/{slug}
      // agent:  slug or id, name, summary, iconUrl → link TBD from existing producer detail
    }
  ],
  "total": 42,
  "page": 1,
  "limit": 50
}
```

**Application-layer service** (`api/src/application/marketplace/listings/byOwner.ts`, new file):

Three parallel queries, unioned in memory (a single advisor has at most low hundreds of items; in-memory sort+paginate after union is correct and simple):

#### Query 1 — Canvas listings (agent, course, playbook, template)

```sql
SELECT ... FROM catalog_items
WHERE publisherRef = :userId
  AND visibility = 'public'
  AND publishedAt IS NOT NULL
  AND kind IN ('agent', 'course', 'playbook', 'template')
  AND acrossTenants(catalogItems, 'public_catalogue', ...)
```

Uses `toView()` from `listings/model.ts` for the view shape. Each row maps to `kind` = its `catalogItems.kind`, `producer` = `"catalog"`, link = `/marketplace/listing/{slug}`.

#### Query 2 — Marketplace skills

```sql
SELECT ... FROM marketplace_skills
WHERE authorId = :userId
  AND published = true
```

No tenant scope needed — `marketplace_skills` has no `tenantId`; `authorId → users.id` is the ownership column. Creates items with `kind = "skill"`, `producer = "marketplace_skill"`, link = `/marketplace/skills/{slug}` (existing route in `marketplaceRoutes.ts`). Price fields already exist (`priceCents`, `pricingModel`, `priceUnit`).

#### Query 3 — IDE agents (registry agents)

```sql
SELECT ... FROM ide_agents
WHERE <owner column> = :userId  -- TBD: publisherRef, createdBy, or equivalent
  AND status = 'active'
  AND published = true
  AND NOT EXISTS (SELECT 1 FROM tenants t WHERE t.id = ide_agents.tenantId AND t.is_demo = true)
```

Uses `publicAgentScope` predicate (minus the `acrossTenants` wrapper — inline the conditions). Creates items with `kind = "agent"`, `producer = "ide_agent"`.

> **⚠ Column to resolve during implementation:** `ide_agents` needs an owner/publisher column that maps to `userId`. If none exists, the agent-from-ide_agents path falls back to `catalog_items.kind='agent'` only (which already has `publisherRef`). The BA requirement allows either or both producers. If `ide_agents` has no user-owner column, the `ide_agent` producer is deferred and agents are served from `catalog_items` only.

#### Union, deduplication, sort, paginate

1. Execute all three queries in parallel (`Promise.all`).
2. Map each row to the unified `item` shape.
3. Deduplicate: if a listing appears from two producers (e.g. same agent listed in both `catalog_items` and `ide_agents`), keep one by stable slug/id, preferring the catalog entry (it has the richer card fields).
4. Sort: by kind order (`agent`, `skill`, `course`, `playbook`, `template`), then by descending install count / downloads, then by published date descending.
5. Paginate in memory: `slice((page-1)*limit, page*limit)`.
6. Return `{ items, total, page, limit }`.

#### Error handling

- Any single-producer failure causes the whole endpoint to fail with a 502 (do not silently drop one producer's items).
- Response includes `error` and `retry` fields on failure; the frontend renders the in-flow error with a retry button.

### Frontend: Resources tab

**New component:** `frontend/src/components/freelance/AdvisorResources.tsx`

- Client component; receives `userId: string`.
- Fetches `GET /api/marketplace/listings/by-owner?owner={userId}` when the Resources tab is selected.
- States:
  - **Loading:** Skeleton/spinner within the tab panel.
  - **Empty:** i18n key `talent.resourcesEmpty` — a single sentence, no cards.
  - **Error:** i18n key `talent.resourcesError` + retry button. Fetches again on click.
  - **Items:** Renders a grid of cards.
- **Card rendering:** Reuses the existing marketplace card component if one exists as a shared presentational component. If no shared card exists, renders minimal cards inline (title, kind badge, icon, price, link). Minimum fields: title/name + kind label.
- **Kind labels:** via `useTranslations('marketplaceListing').kind.${kind}` (existing namespace per `listing/[slug]/page.tsx` and `ListingLaunch.tsx`).
- **Navigation:** Each card is an `<a>` or `<Link>` to the canonical detail page:
  - Canvas (agent/course/playbook/template): `/marketplace/listing/{slug}`
  - Skill: `/marketplace/skills/{slug}`
  - IDE agent: existing public agent detail route (TBD from codebase)
- **Pagination inside the tab:** If `total > items.length`, show "Load more" or page controls. No silent truncation at 24.

**Tab chrome in `TalentProfileView`:**

```tsx
// Pseudo-structure
<Tabs defaultTab="overview">
  <Tab label={t('overview')}>
    {/* existing TalentProfileView content */}
  </Tab>
  <Tab label={t('resources')}>
    <AdvisorResources userId={profile.userId} />
  </Tab>
</Tabs>
```

Alternative if no existing Tabs component: a minimal tab bar using `<button>` elements with `role="tab"` and `aria-selected`, plus a `tabpanel`. This ticket may introduce a lightweight `Tabs` component under `frontend/src/components/ui/Tabs.tsx` if none exists.

### i18n keys

Under `talent` namespace (same as `TalentDetailClient` / `TalentProfileView`):
- `talent.resources`: Tab label
- `talent.resourcesEmpty`: Empty state message
- `talent.resourcesError`: Error message
- `talent.resourcesRetry`: Retry button label

Kind labels reuse `marketplaceListing.kind.*` — verify coverage of `agent`, `skill`, `course`, `playbook`, `template`. If any are missing, add them to the `marketplaceListing` namespace (not the `talent` namespace) — those keys already serve the listing detail page.

### Caching

- **Not cached in KV** initially — a single advisor's listings change infrequently but must reflect publish/unpublish immediately (R-11). The query load is low (3 simple indexed queries per tab-open). A future optimization could wrap in `getOrSetCached` with a short TTL (30s) keyed by `userId + version`.

### Visibility & edge cases

- **Owner viewing own profile:** Same public query applies. They see the public set only. Drafts remain on the seller management surface.
- **Unpublished/withdrawn:** Filtered out by the DB predicates (`publishedAt IS NOT NULL` + `visibility = 'public'` for canvas, `published = true` for skills, `published = true AND status = 'active'` for agents).
- **Out-of-scope kinds:** If a user owns only `app`/`pack`/`game` listings, the canvas query returns zero rows for the allowed kinds → empty state (R-8, R-3).
- **Cross-tenant:** Canvas and agent queries use `acrossTenants(..., 'public_catalogue', ...)`. Skills have no tenant scope. The visitor does not need to share the advisor's tenant.

**Architect note (exec #32050) — TBD resolved on the `ide_agents` producer.**

During Design I read `api/src/infrastructure/database/schema/agents.ts` directly. `ide_agents` has **no user-owner / publisher column** that maps to `FreelancerProfile.userId` — it is tenant-scoped, not user-owned. Therefore:

- **Query 3 (ide_agents) in the Design is DEFERRED, not required for the first implementation.** R-3 permits `agent` to come from `catalog_items` "and/or" `ide_agents`; with no owner column, `ide_agents` cannot satisfy R-2's ownership identity rule ("do not invent a second identity or a join through display name").
- **`kind = 'agent'` is served from `catalog_items` only** (`publisherRef = :userId`, `visibility = 'public'`, `publishedAt IS NOT NULL`). That path already carries the correct owner identity and the richer card fields.
- If a future ticket adds a user-owner column to `ide_agents`, the union in `byOwner.ts` is the single place to add Query 3 — the response shape already carries `producer: "ide_agent"` for that case. Do NOT add such a column as part of #2582 (out of scope; it is a schema migration, not this tab).

Consequence for the developer: the union is **two** queries (canvas `catalog_items` for agent/course/playbook/template, and `marketplace_skills` for skill), not three. Deduplication across producers is therefore trivial in the first cut (the two producers cannot collide), but keep the dedupe-by-slug step so adding Query 3 later does not require reworking the union.

Also unresolved and left to implementation (low risk, both are lookups not decisions): the exact public detail route for a marketplace skill (Design assumes `/marketplace/skills/{slug}` — verify against `marketplaceRoutes.ts` / the frontend route tree before wiring the card link), and whether a shared marketplace card component already exists to reuse rather than rendering cards inline.
