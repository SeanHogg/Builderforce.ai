# PRD: Company Type I Policy Set

**Status:** WIP  
**Epic:** 3062  
**Repo:** seanhogg/builderforce.ai (base `main`)  
**Coordinator:** Security  
**Required reviewer:** Legal/compliance  
**Purpose of this PRD:** Specify the company policy set an AICPA auditor expects for SOC 2 Type I documented control design, and the publication, ownership, versioning, and control-register linkage work that makes that set evidential.

## Problem & Goal

Builderforce can show privacy artifacts and a vulnerability-reporting note, but not a company policy set. Existing material is limited to `Builderforce.ai/docs/compliance` (DPA, `privacy-incident-response.md`, subprocessors, DPIA, data export/deletion) and `agent-runtime/docs/SECURITY.md`. An auditor examining Type I control design will ask for information security, access, change, security incident response, vendor management, backup and recovery, and personnel or acceptable-use policies. Those documents are missing, unowned, unversioned, and not cited as SocEvidence.

Goal: publish a versioned Type I policy set that states how the listed controls are designed, names accountable owners, maps each policy to CC1–CC9 and Availability, and is linked from Builderforce’s own control register. Ship a customer-shareable summary that does not expose internal procedure detail. Legal/compliance reviews before publication. Do not invent operating evidence, test results, or named individuals.

## Target users / ICP roles

- **Security Lead (document owner for ISMS, access, incident response, vendor, acceptable use):** needs one consistent control-design narrative and a register an auditor can follow.
- **Engineering Lead (document owner for change management and backup/DR):** needs the written design to match the merge process already in repo and the recovery design the company actually runs.
- **Legal/compliance reviewer:** needs a reviewable set that does not contradict the DPA, privacy incident process, or public subprocessor list.
- **AICPA auditor (external reader of the internal set):** needs owners, scope, criterion mapping, version, and SocEvidence links. Type I asks whether controls are designed and in place, not whether they operated effectively over a period.
- **Customer security reviewer (reader of the summary only):** needs a short, non-sensitive description of the control design suitable to share under a normal vendor review.

## Scope

In scope:

- Seven internal policies, one customer-shareable summary, a criterion mapping matrix, `.github/CODEOWNERS` aligned to the change policy, and SocEvidence links on the existing control register.
- Cross-links to current privacy and engineering docs. Do not rewrite those docs except to add pointers where a new policy would otherwise contradict them.
- Availability (A1) is in scope because backup and tested recovery are required control design for this epic.

Policy locations:

- Internal policies: `Builderforce.ai/docs/compliance/policies/`
- Customer-shareable summary: `Builderforce.ai/docs/compliance/policies/customer-shareable-summary.md`
- Mapping matrix: `Builderforce.ai/docs/compliance/policies/tsc-mapping.md`
- Change-management code ownership: `.github/CODEOWNERS`
- Control register: the in-repo register that already uses SocEvidence. If that register is only `SOC2_TYPE1_COMPLIANCE.md`, update that file. Do not create a second register.

Each internal policy uses the same header: title, version, status, effective date, owner role, approver role, review cycle, classification, related documents, and a document history. Initial version is 1.0. Review cycle is annual or on material change. Classification of full policies is Internal. Classification of the summary is Customer-shareable.

Owner roles, not personal names:

| Policy | Owner | Approver |
| --- | --- | --- |
| Information security / ISMS | Security Lead | Legal/compliance |
| Access control | Security Lead | Legal/compliance |
| Change management / SDLC | Engineering Lead | Security Lead and Legal/compliance |
| Security incident response | Security Lead | Legal/compliance |
| Vendor / subprocessor management | Security Lead | Legal/compliance |
| Backup, disaster recovery, and recovery testing | Engineering Lead | Security Lead |
| Acceptable use and personnel security | Security Lead | Legal/compliance |

If MERGE_PROCESS, CONTRIBUTING, or GitHub org metadata names a real maintainer or team, CODEOWNERS may use that verified handle or team. Do not invent GitHub usernames. If no verified handle exists, state that gap in the change policy and do not fabricate CODEOWNERS entries.

## Functional requirements

1. **ISMS policy.** State the security program scope (product, company systems, personnel, and vendors that can affect customer data or production), roles, risk assessment cadence, policy exception path, control ownership, internal communication of policies, and management review. Map primarily to CC1–CC5. Reference, do not replace, privacy documents.
2. **Access control policy.** State least privilege, unique accounts, joiner-mover-leaver, access review design, production and admin MFA, session lifetime, and session revocation on offboarding, role change, and suspected compromise. Cover logical access to production, source, IdP, cloud, and customer-data stores. Include a short remote-work physical and endpoint statement sufficient for CC6 design. Point only at access mechanisms that already exist in the product or operating docs; do not claim an IdP, SSO, or session-revoke feature that the repo does not support.
3. **Change management policy.** State how production changes are requested, reviewed, approved, tested, and deployed, and how emergency changes are recorded after the fact. Cite `docs/MERGE_PROCESS.md` as the procedure. Require CODEOWNERS on production code and on `Builderforce.ai/docs/compliance/policies/`. Separating duties: the author is not the sole approver for production changes. Map primarily to CC8 and CC5.
4. **CODEOWNERS.** Add or update `.github/CODEOWNERS` so compliance policy paths and production code paths have owners consistent with the change policy and with verified maintainers or teams already documented in the repo. Document the uncovered-path gap rather than filling it with fictional owners.
5. **Security incident response policy.** Define SEV1–SEV4 by customer impact, data exposure, and availability. State detection, triage, severity assignment, containment roles, evidence handling, internal escalation, customer notice criteria and owner, regulator coordination handoff, and post-incident review. Security incidents that involve personal data must follow `Builderforce.ai/docs/compliance/privacy-incident-response.md` in addition to this policy. Do not restate privacy breach law as if it were a new legal opinion. Vulnerability intake remains `agent-runtime/docs/SECURITY.md`; link it. Map primarily to CC7 and CC2.
6. **Vendor and subprocessor policy.** State how vendors are classified, risk-reviewed before use, contracted, monitored, and offboarded, including access removal and data return or deletion. The public list at `/legal/subprocessors` is the customer-facing inventory; this policy is the operating design behind that list. Name the owner who updates the public list when a subprocessor changes. Map primarily to CC9.
7. **Backup and recovery policy.** State backup scope, frequency, storage separation, encryption expectation, retention, RPO, RTO, restore authority, and the recovery test design (what is tested, how often, who records the result, what failure does). Type I does not require a period of operating effectiveness. Do not write a test result that did not happen. If a completed restore test record already exists, cite it. If it does not, publish the test procedure and the owner’s obligation to run and record the first test; label the result as not yet executed.
8. **Acceptable use and personnel security.** State expected use of company and production systems, prohibition on credential sharing, confidentiality, device expectations, onboarding access grant, offboarding access removal, and the personnel-screening design the company actually uses. If a screening step is not in place, describe the designed control only if it is adopted; otherwise omit it rather than imply it operates.
9. **Customer-shareable summary.** One document covering all seven areas in plain language: what the control is designed to do, who owns it, and that Type I is a point-in-time design. Omit internal escalation contacts, infrastructure identifiers, restore commands, detection thresholds, and anything that would help an attacker. Suitable to send to a customer without further redaction.
10. **Criterion mapping.** `tsc-mapping.md` lists every CC1–CC9 point of focus the policies claim to address, plus A1 for backup and recovery. Each row cites policy path, version, and section. Unmapped criteria stay unmapped; do not force a citation.
11. **SocEvidence linkage.** On Builderforce’s control register, each control these policies support links the policy path, version, and section as SocEvidence. Links must resolve in the repo. Update `SOC2_TYPE1_COMPLIANCE.md` when that file is the register or the index to it.
12. **Consistency pass.** Policies must not contradict the DPA, DPIA, privacy incident response, data export/deletion, public subprocessor list, `SECURITY.md`, or `MERGE_PROCESS.md`. Where the operating doc is thinner than the policy, the policy states the design and points at the doc; it does not pretend the doc already contains the control.
13. **Review record.** Each policy history notes Security as author and Legal/compliance as required reviewer. Publication status stays Draft until that review is recorded. Do not mark a policy Approved without the review.

## Acceptance criteria

- All seven internal policies exist under `Builderforce.ai/docs/compliance/policies/`, each at version 1.0, with owner role, approver role, effective date, review cycle, classification, related-document links, and document history.
- The customer-shareable summary exists, covers all seven areas, and contains no internal-only operational detail.
- `tsc-mapping.md` maps the set to CC1–CC9 and A1, with path, version, and section citations, and does not claim criteria the text does not address.
- The control register cites each published policy as SocEvidence with a resolvable repo link. `SOC2_TYPE1_COMPLIANCE.md` agrees with that register.
- Access policy includes MFA for privileged and production access, session revocation triggers, and least privilege, and does not claim unimplemented product controls.
- Change policy cites `docs/MERGE_PROCESS.md`. `.github/CODEOWNERS` covers policy paths and production paths using only verified owners, or the gap is explicitly recorded.
- Security incident response defines SEV1–SEV4, customer notice owner and criteria, and a hard link to the privacy incident process for personal-data events.
- Vendor policy treats `/legal/subprocessors` as the public inventory and names who updates it.
- Backup policy states RPO, RTO, scope, and test design. It contains a restore-test result only when a real record was found.
- No policy fabricates employee names, audit evidence, pen-test results, or vendor certifications.
- Legal/compliance review is recorded before any policy status is Approved.
- Existing privacy docs and `SECURITY.md` remain authoritative for their current scope; new text only cross-links them.

## Out of scope

- SOC 2 Type II operating-effectiveness evidence, sampling, or a period-of-time narrative.
- Engaging the auditor, writing the auditor’s opinion, or representing that a report has been issued.
- Implementing new technical controls, IdP changes, backup infrastructure, SIEM content, or product features. This epic writes the design and links existing mechanisms.
- Rewriting the DPA, DPIA, privacy incident response, data export/deletion docs, or the public subprocessor list, except for cross-links required to avoid contradiction.
- Vendor contract negotiation, new DPAs, or security-questionnaire responses for a named customer.
- Penetration testing, vulnerability exploitation, or changes to vulnerability-reporting mechanics beyond a link from the incident policy.
- Physical office build-out, HR system implementation, or background-check vendor selection.
- Customer-specific policy exceptions and any policy text that embeds secrets, credentials, or customer data.
