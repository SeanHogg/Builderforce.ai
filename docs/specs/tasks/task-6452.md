# PRD: Cap section-node ref slug length in docsExtract

## Problem & Goal

Knowledge review fails at the extract phase when a section ref exceeds the API's 512-character cap. Zod rejects the entire extracted upload (`0.nodes.N.ref: Too big: expected string to have <=512 characters`), which surfaces as a KnowledgeApiError and aborts review.

Section refs are built unbounded in `extractMarkdown`'s inner `sectionNode`:

`${b.fileRef}#${n > 1 ? `${slugPath}-${n}` : slugPath}`

where `slugPath = crumbs.map(slugOf).join('/')`. Deep heading breadcrumbs push the full ref over 512 even when the file path itself is legal.

**Goal:** Bound the section slug at the producer so every section ref stays under 512 characters, remains deterministic, and stays distinct for distinct breadcrumbs. Truncate the slug; do not drop the section. The section must remain judgable.

## Target users / ICP roles

- BuilderForce for VS Code users whose knowledge review dies on deep markdown heading trees (workspaces with long paths and nested headings).
- Downstream extract/judge agents that consume section refs and content-hash digests. Output must stay stable across runs.

## Scope

Repo: `builderforce-memory` only.

File: `builderforce-memory/packages/memory/src/ingest/docsExtract.ts`, function `sectionNode` inside `extractMarkdown`.

- Export `MAX_SECTION_REF_LEN = 480` from this module or from `refs.ts`. 480 leaves headroom under the API's 512 cap for `fileRef` plus the `#` separator.
- Cap only the slug portion of section refs built in `sectionNode`.
- When the assembled ref would exceed the cap, truncate `slugPath` and append a stable short discriminator derived from the **full** (pre-truncation) `slugPath`.
- Discriminator: `hashText` from `../ingest/hash.js`, sliced to a short base36 or hex suffix. No randomness. No locale-dependent collation.
- Duplicate-heading suffix (`-${n}` when `n > 1`) must still be representable after truncation so repeated headings under the same breadcrumb do not collapse.
- Add tests in the existing docsExtract test file under `builderforce-memory/packages/memory/src` (glob `*docsExtract*test*`).

## Functional requirements

1. A section ref is `${fileRef}#${slug}` (or `#${slug}-${n}` when the heading index `n > 1`). After this change, the full string length is always `<= 512`, and the slug portion is sized so the full ref stays `<= MAX_SECTION_REF_LEN` (480) when `fileRef` itself fits in the remaining budget. If `fileRef` is already long, still keep the **section** ref `<= 512` by shrinking the slug; never truncate `fileRef`.
2. Short breadcrumbs are unchanged. If the uncapped ref is within the limit, emit the same string as today (including the `-${n}` form).
3. Over-long `slugPath`: truncate, then append a fixed-format discriminator derived from `hashText(fullSlugPath)` so two long breadcrumbs that share a prefix produce different refs.
4. The discriminator is a pure function of the full slug path (and, when `n > 1`, of `n`, so collisions between a truncated path and a numbered sibling cannot occur). Same inputs always yield the same ref.
5. Do not drop the node. A truncated section is still emitted and remains judgable.
6. `bodySection` refs (`#body`, `#body-N`, `#~preamble`) are already short. Leave that construction untouched.
7. Do not modify `srcRef`, `pathOfRef`, `fileRefOf`, or any file-ref construction. Path round-tripping must keep working. Long file paths are out of scope here (API-side sanitize is a separate task).
8. Export `MAX_SECTION_REF_LEN = 480` so tests and callers share one constant.

## Acceptance criteria

- A section built from a long heading breadcrumb produces a ref of length `<= 512` (and `<= MAX_SECTION_REF_LEN` relative to a normal `fileRef`).
- A second extract of a different long breadcrumb that shares the same prefix yields a different ref.
- Repeating the same extract yields the identical ref (deterministic; feeds content-hash digests).
- A normal (short) section ref is byte-for-byte unchanged, including the `-${n}` duplicate-heading form.
- `#body`, `#body-N`, and `#~preamble` refs are unchanged.
- `srcRef`, `pathOfRef`, and `fileRefOf` are unmodified; file-ref path round-tripping still holds.
- `pnpm -w -F @seanhogg/builderforce-memory exec vitest run src/ingest` (or the repo's equivalent scoped vitest command) passes.
- Typecheck is clean.
- No new dependency. Discriminator uses existing `hashText`.

## Out of scope

- Any change in the API repo (`Builderforce.ai`), including zod `zRef`, `putExtracted`, sanitize/drop of over-long refs, or `skippedRefs`.
- Truncating or rewriting file paths inside `srcRef` / `pathOfRef` / `fileRefOf`.
- Parallelising `judgeSections`, `compareClaims`, or the per-file loop in `review.ts`.
- Dropping over-long sections instead of truncating their slugs.
- Changing slugify rules for headings that already fit.
- Touching `judgementWithTimeout` or review-runner timeouts.
