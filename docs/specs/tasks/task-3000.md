# PRD: Frontend Architecture Ratchet and Blog Index

## Problem & Goal

The frontend architecture guard is not reliably enforcing the repository’s intended architectural boundaries. Its current baseline or comparison logic is stale, may fail on an accepted codebase, or may allow new violations to be masked by unrelated reductions in existing debt.

Separately, the blog index does not accurately represent the canonical blog content. It can omit newer posts, retain removed posts, or require manual synchronization with a second content list.

The goal is to provide a deterministic architecture ratchet that prevents regressions and a blog index that is generated from the canonical post collection.

## Target Users / ICP Roles

- **Frontend engineers:** Receive actionable feedback when code violates architectural boundaries.
- **Frontend architects and tech leads:** Maintain approved exceptions without allowing the exception baseline to grow silently.
- **Content editors and marketing teams:** See an accurate, automatically maintained list of published blog posts.
- **CI and release maintainers:** Run deterministic checks that prevent regressions from merging or shipping.

## Scope

### In Scope

- Audit and repair the existing frontend architecture-ratchet script, configuration, baseline, and CI/package-script integration.
- Preserve the repository’s established architecture rules and thresholds unless a rule is demonstrably broken or cannot be evaluated deterministically.
- Ensure the ratchet distinguishes approved existing exceptions from newly introduced violations.
- Improve diagnostics so failures identify the affected file, rule, and remediation.
- Refresh the blog index from the canonical blog-post source.
- Apply existing publication eligibility and ordering rules to index entries.
- Add or update automated tests for both the ratchet and blog-index generation.
- Update generated artifacts and relevant developer documentation when the repository tracks them.

### Functional Requirements

#### FR-1: Deterministic Architecture Evaluation

- The ratchet must evaluate the same repository state to the same result on every run.
- It must not depend on network access, machine-specific paths, or execution order.
- It must use the repository’s existing frontend source roots and rule configuration.

#### FR-2: Explicit Baseline Comparison

- The ratchet must compare current findings with a checked-in, reviewable baseline of approved exceptions.
- New violations must fail even if the total count of existing violations decreases elsewhere.
- Resolved baseline entries must be removed through an explicit baseline-update process rather than being ignored indefinitely.
- CI must not automatically rewrite or weaken the baseline.

#### FR-3: Actionable Failure Reporting

- A failing run must identify the violated rule, affected file or path, and the corresponding baseline status.
- Output must clearly distinguish new violations, accepted exceptions, and stale baseline entries.
- The implementation must not make the check pass by broadly disabling rules or excluding frontend directories.

#### FR-4: Repeatable Baseline Maintenance

- The repository must provide a documented, repeatable way to regenerate the approved baseline after an intentional architecture change.
- Baseline changes must be reviewable in source control.
- Existing approved exceptions must remain valid unless explicitly removed or superseded.

#### FR-5: Canonical Blog Index

- The blog index must derive its entries from the canonical blog-post collection or content manifest.
- The implementation must not maintain a second hand-authored list of posts.
- Posts must appear exactly once and must not reference content that has been removed or is no longer eligible for publication.
- New published posts must appear after index generation or during the existing frontend build.
- The existing site ordering rule must be preserved. If no explicit rule exists, posts should be ordered by publication date descending with a deterministic secondary sort.

#### FR-6: Build and CI Integration

- The architecture check and blog-index consistency check must run through stable package scripts and in the appropriate CI workflow.
- A committed generated index, if required by the current repository workflow, must match the output of the generator.
- Existing frontend type checking, linting, testing, and production build behavior must remain intact.

## Acceptance Criteria

1. Running the documented architecture-ratchet command against the completed repository state exits successfully with no unexplained baseline drift.
2. Introducing a representative architecture violation causes the command to fail and reports the file, rule, and that it is not an approved exception.
3. A newly introduced violation cannot be masked by resolving a different violation elsewhere.
4. Approved baseline exceptions remain explicitly visible and reproducible.
5. A stale resolved exception is detectable and can be removed through the documented baseline-update command.
6. The blog index contains every currently eligible published post exactly once, contains no removed or ineligible posts, and follows the required deterministic ordering.
7. Adding or updating a canonical blog post produces the expected index change without manually editing a duplicate post list.
8. Regenerating committed artifacts produces no uncommitted diff after the required files are updated.
9. Relevant frontend tests, linting, type checking, architecture checks, and production build all pass.
10. No broad architecture exemption, dependency upgrade, or content rewrite is required to make the checks pass.

## Out of Scope

- Redesigning the frontend architecture or changing approved architectural policy merely to simplify the ratchet.
- Resolving all pre-existing architecture debt; the work only needs to preserve accepted debt and prevent new regressions.
- Replacing the current content system, blog engine, or publishing workflow.
- Migrating content into a new CMS or changing editorial approval processes.
- Redesigning blog pages or changing the visual presentation of index cards.
- Rewriting blog copy, metadata strategy, or publication calendars.
- Broad framework, dependency, runtime, or backend upgrades unrelated to these fixes.
