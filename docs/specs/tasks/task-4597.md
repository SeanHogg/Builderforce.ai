The autonomy wiring audit must count a spec-shaped in-review ticket as a non-code deliverable, not as missing code. Production behaviour is already implemented; this ticket only pins it. Do not change production code unless a test proves a bug. Do not edit `ROADMAP.md` or `DONE.md`.

`review_has_deliverable` fails only on `missing_code` rows. Spec-shaped tickets must not fail that check.

## Design

**Architect (ticket #4597) — verified against `main`; no production change required.**

**Seam.** `classifyReviewDeliverable(row)` in `api/src/application/activity/autonomyWiringAudit.ts` is a pure function. It delegates "does this ticket expect a branch?" to `expectsCodeDeliverable(taskType, actionType, title)` in `manager/evaluateTicketReadiness.ts`. The decision order there is:
1. Non-code task type (`epic`, `product`, `design`) returns false.
2. Non-code action type (`docs`, `analysis`, `provisioning`, `decision`) returns false.
3. An action type with no producing role returns false.
4. `!isSpecShapedTitle(title)` is the final word, and it can only ever say "no".

The classifier then returns:
- `non_code` when code is not expected;
- `has_code` when a branch or PR exists;
- `missing_code` otherwise.

`review_has_deliverable` fails only on `missing_code`, so spec-shaped tickets cannot fail it.

**Why the title is the last, narrowest signal.** The classifier labels the action type from the *subject* of the work ("Write the PRD for the billing API" is labelled `backend_api`). The two failure directions are asymmetric: a bounced spec ticket is a bounded loop, but a code ticket waved through as a spec ships nothing. `isSpecShapedTitle` is therefore deliberately narrow: only a labelled title or an authoring verb with a document object counts. Any title that says "implement" is code, even when it references a spec.

**Test design.** `api/src/application/activity/autonomyWiringAudit.test.ts` already exists on `main` and pins exactly the four required cases:
- `backend_api` + "Write the PRD for the billing API" + no branch → `non_code`.
- `frontend_ui` + "Spec: onboarding wizard" + no branch → `non_code`.
- "Implement the billing API per the spec" + no branch/PR → `missing_code`.
- The same code title with a branch → `has_code`.

There is no DB fixture, because the audit's review check is a filter over this pure function. Pinning at this seam avoids an integration harness while still guarding the behaviour the ticket names.

**Decision.** No second test file and no production edit. The existing test is the deliverable. `ROADMAP.md` and `DONE.md` are untouched (parent owns them).

**Residual risk (not in scope).** The `isSpecShapedTitle` regexes have their own matcher tests under `manager/`. This test intentionally covers only the audit-level classification.
