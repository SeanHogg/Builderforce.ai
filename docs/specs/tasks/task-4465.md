## Requirements

## Problem

M1's go/no-go (parent #3762, epic #2916) shipped the CubeCL GPU backends and `bfi bench-kernel`, but the throughput gate was never measured. Until two real tok/s numbers exist, the kernel work cannot be called done, and shipping CPU-only as a substitute is explicitly forbidden.

## Goal

Decide the M1 gate with evidence: on one identical GGUF, record `bfi bench-kernel` tok/s against PrismML's llama.cpp fork `llama-bench -n 128` (tg128) on two machines, and pass only if bfi reaches at least 70% of the fork on both. If it misses, open Fallback A instead of lowering the bar.

## Who it is for

- The inference kernel owner, who needs a recorded pass/fail before M1 can close.
- The platform owner, who must not ship a CPU-only path under a GPU claim.

## In scope

1. One GGUF, identical bytes, used by both tools on both machines. Record its filename, quant, and sha256.
2. Machine A: an Apple M-series Mac, Metal backend (`BFI_BACKEND=metal`).
3. Machine B: one NVIDIA box, Vulkan or CUDA (`BFI_BACKEND=vulkan` or `cuda`). Record which.
4. On each machine, two numbers:
   - bfi: `bfi bench-kernel --gguf <file>` tok/s.
   - fork: PrismML llama.cpp `llama-bench -m <file> -n 128` tg128 tok/s.
5. Pass rule: bfi tok/s ≥ 0.70 × fork tg128 tok/s, on **both** machines. One machine passing is not a pass.
6. Record, per machine: hardware, OS, driver/runtime version, backend selected, both commands as run, both tok/s, the ratio, and the date.
7. On a miss, file Fallback A (PRD §9): hand-written Metal via metal-rs and CUDA via cudarc, covering the hot GEMV only, as its own follow-up ticket. Do not silently keep the CPU path and call the gate met.

## Out of scope

- Re-running or re-tuning the already-shipped CubeCL kernels (commits `06e624e`, `1f97edf`). CubeCL stays pinned at 0.10.0.
- `bf-local`, the VSIX, and `ollama.rs` — do not touch them.
- A synthetic stand-in. A number not produced by the two commands on the two machines is not evidence; a stubbed or estimated tok/s fails this ticket.
- Adding a `bench-kernel` implementation. It already exists in `builderforce-inference` (`crates/bfi`).

## Constraints discovered

- The commands, the GGUF loader and the backends live in **SeanHogg/builderforce-inference** (`crates/bfi-core`, `crates/bfi`), not in seanhogg/builderforce.ai. This workspace has no `bfi`, no `bench-kernel`, and no llama.cpp fork, so the measurement cannot be produced or verified from the repo currently bound.
- The run has no shell, so even with the right repo bound the benches could not be executed here.
- Both target machines (M-series Metal, NVIDIA Vulkan/CUDA) are operator hardware. Nothing in CI stands in for them.

## Acceptance criteria

- [ ] A results record names the GGUF (path, quant, sha256) and states it was identical for all four runs.
- [ ] Machine A result: hardware, `BFI_BACKEND=metal`, both commands, both tok/s, ratio.
- [ ] Machine B result: hardware, backend (`vulkan` or `cuda`), both commands, both tok/s, ratio.
- [ ] Verdict is computed, not asserted: pass only when both ratios are ≥ 0.70.
- [ ] If either ratio is below 0.70, a Fallback A ticket exists (metal-rs + cudarc hot GEMV) and this ticket is not closed as passed.
- [ ] No estimated, copied, or stubbed tok/s appears anywhere in the record.
