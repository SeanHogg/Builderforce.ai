# PRD: Export `bootVsixHost` for Denied-Network Acceptance

## Problem & Goal

The VS Code client lacks a production export named `bootVsixHost` that an end-to-end scenario can invoke without a live Builderforce platform or a fully provisioned `vscode.ExtensionContext`.

The existing `activate` path in `Builderforce.ai/clients/vscode/src/extension.ts` is not suitable as the acceptance entry point because it starts platform-dependent work, including `attention.start` and related binds. The existing `deniedNetworkAcceptance.ts` helper is not exposed through a production composition root, and `installSyncCoordinator` cannot represent denied network access because it first requires synchronize permission.

The goal is to provide a stable `bootVsixHost` export that performs a local VSIX host boot under externally enforced network denial and returns an inspectable result that does not depend on a live platform.

## Target Users / ICP Roles

- **QA/SDET engineers** creating denied-network end-to-end scenarios.
- **VS Code extension maintainers** validating isolated extension-host startup.
- **Release and security engineers** confirming that VSIX host startup does not require successful remote connectivity.

## Scope

- Add a named `bootVsixHost` export to `Builderforce.ai/clients/vscode/src/extension.ts`.
- Provide a no-required-argument call form suitable for the qa-e2e harness.
- Boot the local VSIX host without requiring:
  - A live Builderforce platform.
  - Platform credentials or endpoints.
  - A manually constructed `vscode.ExtensionContext`.
  - Synchronize permission.
- Add a new qa-e2e acceptance scenario that imports the production export directly and runs it with outbound network access denied.
- Preserve the current VS Code `activate` behavior and platform startup path.

## Functional Requirements

### FR-1: Production Export

`Builderforce.ai/clients/vscode/src/extension.ts` must expose a named `bootVsixHost` export. The qa-e2e scenario must import this production export rather than duplicating boot logic or relying only on `deniedNetworkAcceptance.ts`.

### FR-2: Isolated Host Boot

`bootVsixHost` must:

- Require no `vscode.ExtensionContext`.
- Require no live platform instance.
- Require no network-dependent setup to reach a locally ready host state.
- Be callable from the approved VS Code or VSIX qa-e2e host harness.
- Avoid module-import side effects that start platform services.

### FR-3: Denied-Network Behavior

The qa-e2e scenario must enforce network denial before invoking `bootVsixHost`.

`bootVsixHost` must:

- Complete or resolve to the documented local-host-ready outcome even though remote access is unavailable.
- Represent expected network denial as an inspectable state or result rather than an unrelated permission error.
- Not use `synchronize_not_granted` as a proxy for network denial.
- Not retry remote operations indefinitely or require successful DNS, TCP, HTTP, or platform access.
- Distinguish local host readiness from successful remote connectivity.

### FR-4: Separation from Full Activation

`bootVsixHost` must not invoke the full `activate` flow or trigger platform-only startup such as `attention.start` and related binds. It may reuse safe internal host setup, but it must remain independently callable.

### FR-5: Acceptance Coverage

A new qa-e2e file must:

1. Arrange effective outbound-network denial.
2. Call the exported `bootVsixHost`.
3. Assert that the local host reaches its ready state.
4. Assert that no live platform is required.
5. Assert that expected network denial is handled without an unrelated permission failure.
6. Complete deterministically and repeatably.

## Acceptance Criteria

- **AC-1:** A direct named import of `bootVsixHost` from `Builderforce.ai/clients/vscode/src/extension.ts` resolves successfully.
- **AC-2:** The qa-e2e scenario invokes `bootVsixHost` without creating a `vscode.ExtensionContext` or supplying live-platform credentials, endpoints, or instances.
- **AC-3:** With network denial enforced before the call, `bootVsixHost` resolves to the defined local-host-ready result.
- **AC-4:** The result makes it possible to verify local readiness separately from remote connectivity and does not report `synchronize_not_granted` as evidence of network denial.
- **AC-5:** Test instrumentation confirms that the isolated boot does not invoke `attention.start`, platform binds, or the full `activate` path.
- **AC-6:** Any attempted remote operation is subject to the enforced denial, is handled within the defined boot lifecycle, and does not cause an unbounded retry or hang.
- **AC-7:** The acceptance scenario passes when repeated without network access and does not require a live Builderforce environment.
- **AC-8:** Existing extension activation tests continue to pass, and the existing `activate` contract remains unchanged.
- **AC-9:** No `exports` field or new package-publication entry point is required for the source-level qa-e2e import.

## Out of Scope

- Redesigning or removing platform startup from the normal VS Code `activate` flow.
- Changing the synchronization-permission semantics of `installSyncCoordinator`.
- Making `deniedNetworkAcceptance.ts` a separate production composition root.
- Adding or modifying `clients/vscode/package.json` package exports.
- Providing a live Builderforce platform, mock platform server, or platform credentials for the denied-network scenario.
- Expanding the work into commands, UI, settings, telemetry, or broader offline feature behavior.
- Guaranteeing that every extension feature works offline; this PRD covers only the isolated VSIX host boot used by the acceptance scenario.
