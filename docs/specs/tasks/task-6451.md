# PRD: Tolerate oversized refs on extracted-upload

## Problem & Goal

`PUT /:projectId/knowledge/extracted/:hash` validates every node ref, edge endpoint, key ref, and `sourceRef` with `zRef` (`min(5)`, `max(512)`, prefix `src|ent|fact:`). One ref over 512 characters fails Zod for the entire body (`400`, e.g. `0.nodes.149.ref: Too big`). The VS Code extension surfaces that as a knowledge-review failure at the extract phase and aborts the whole review.

Refs can exceed 512 without being malicious: section refs are `${fileRef}#${slugPath}`, and deep paths plus a long `src:` prefix (workspace root id) push past the cap. The upload must not die because of individual over-long refs.

**Goal:** Accept the extracted body when individual refs are over-long, drop only the offending nodes, edges, keys, or whole entries, store the cleaned object, and return `200` with a skip count. Existing hash, staleness, replacement, and version semantics stay unchanged.

## Target users / ICP roles

- **End user:** BuilderForce for VS Code on large workspaces (deep paths, many files) running knowledge review through extract.
- **API owner:** engineers changing `projectKnowledgeRoutes` and `knowledgePerception`.
- **Client:** knowledge-client `putExtracted`, which already ignores unknown response fields.

## Scope

In `Builderforce.ai` only:

- `api/src/presentation/routes/projectKnowledgeRoutes.ts` — extracted-body schema and PUT handler response.
- `api/src/application/knowledge/knowledgePerception.ts` — sanitize, then existing `putExtracted` flow; return the skip count.
- Tests: `knowledgePerception.test.ts`, `projectKnowledgeRoutes.test.ts`.

Read `knowledgePrivacy.ts` and follow `clampExtracted` style. Place the sanitize step next to the existing `clampExtracted` import.

## Functional requirements

1. **Extracted schema only.** Introduce an extracted-upload ref (e.g. `zExtractedRef`) with the same prefix regex and `min(5)`, but `max(4096)`. Use it only for `ExtractedBody` (node `ref`, edge `from`/`to`, key refs, entry `sourceRef`). Over-long refs must pass route validation and reach the application layer. Do not change `zRef` `max(512)` on `WriteBody` facts, relations, or stale (the 500-row knowledge write).

2. **Sanitize before persist.** Walk each entry and count every drop:
   - Drop a node whose `ref` length is greater than 512.
   - Drop an edge whose `from` or `to` length is greater than 512.
   - Drop a key whose `ref` length is greater than 512.
   - Drop the entire entry when its `sourceRef` length is greater than 512.
   - Refs of length 512 or less are kept. Empty remaining node/edge/key lists on a kept entry are valid.

3. **`putExtracted` order.** Apply sanitize before the held-set computation and before `extracted.put`. Keep the `source_hash_mismatch` `400` when a **kept** entry’s `sourceHash` does not equal the `:hash` param. Held-set and `markRelationsStale` still apply only to **new** source refs among entries that remain. The object at a hash is still replaced whole. Version bump still runs in `finally`. Record and return the total dropped count as `skippedRefs`.

4. **Response.** PUT extracted returns `{ ok: true, hash, skippedRefs }` with `skippedRefs` a non-negative integer (0 when nothing was dropped). Adding the field is backward-compatible.

## Acceptance criteria

- Route: PUT extracted whose body has a 600-character node ref returns **200**, not 400. Body includes `ok: true`, the request `hash`, and `skippedRefs >= 1`. The object stored via the fake extracted port contains no ref longer than 512, and does not contain that node.
- Application: an entry with a 600-character node ref is stored without that node and `skippedRefs` is 1. `source_hash_mismatch` still returns 400 and does not store.
- Entries dropped solely because `sourceRef` exceeds 512 do not enter the held-set and do not mark relations stale.
- Existing `knowledgePerception` and `projectKnowledgeRoutes` tests still pass. Typecheck is clean.
- A body whose every ref is ≤512 still stores the full object, still applies new-sourceRef staleness only, still whole-replaces, still bumps version, and returns `skippedRefs: 0`.

## Out of scope

- Changing `zRef` max for `WriteBody` facts, relations, or stale.
- Changing `source_hash_mismatch`, the held / new-sourceRef staleness rule, whole-object replacement, or the version bump.
- Truncating or capping `src:` file-path refs (path parse-back must stay intact).
- Producer slug caps, parallel judgement, or any change in `builderforce-memory`.
- Knowledge-client changes (extra fields are already ignored).
