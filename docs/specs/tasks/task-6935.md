# PRD: MK-09-W9 — Repo-size ceiling before the sandbox clone

**Status:** WIP  
**Priority:** P2  
**Source:** PRD 09 §4, GAP-W9  
**Bound repo:** seanhogg/builderforce.ai (GitHub, base `main`)  
**Primary module:** `api/container/sandboxGit.mjs`

## Problem & Goal

A full-history clone of a very large Git repository can fill sandbox disk, stall the clone, and exhaust the container before any useful work starts. Refusing after the clone has already run does not protect the sandbox: the expensive transfer has already happened.

Goal: before `api/container/sandboxGit.mjs` starts a full-history clone, measure remote repository size, compare it to a single repo-size ceiling, and fail with a clear typed error when the repo is over the ceiling or the size cannot be known. The clone must not start on that path.

## Target users / ICP roles

- **Sandbox runtime owners** who need a hard guard so one oversized repo cannot take down a sandbox.
- **API callers of the sandbox Git path** who need a stable, typed failure they can surface instead of a timeout or a full disk.
- **End users connecting a GitHub repo** who should see an explicit “repo too large, clone not started” failure rather than a hung or dead sandbox.

## Scope

In `api/container/sandboxGit.mjs` only, add a pre-clone size gate on the existing full-history clone path used to bring a GitHub repo into the sandbox.

- Resolve size from GitHub repository metadata (`GET /repos/{owner}/{repo}`, field `size`) using the same credentials the clone would use. Do not transfer Git objects to learn the size.
- Treat GitHub `size` as kibibytes and compare `size * 1024` to the ceiling in bytes.
- Ceiling is one named constant in this module, `SANDBOX_REPO_SIZE_CEILING_BYTES`, default `536870912` (512 MiB). An environment variable of the same name may override it with a positive integer byte count. Invalid overrides are ignored and the default is used. There must be no second hardcoded threshold.
- If size is above the ceiling, or size cannot be read, throw a typed error and do not clone.
- On success (known size, at or under the ceiling), keep the existing full-history clone behavior unchanged.

## Functional requirements

1. The size check runs strictly before any `git clone`, full-history `git fetch`, or packfile transfer on this path. Remote metadata and ref advertisement that do not download objects are allowed. Cloning and then deleting, or cloning and then refusing, is not allowed.
2. The check applies to every full-history clone this module starts for a GitHub remote, including seanhogg/builderforce.ai on base `main`.
3. Over-ceiling failure uses a typed error named `SandboxRepoSizeError` with `code` `REPO_SIZE_CEILING_EXCEEDED`, plus `repo` (owner/name), `sizeBytes`, and `ceilingBytes`. The message states that the clone was not started and includes the observed size and the ceiling in bytes.
4. Unknown-size failure uses the same error type with `code` `REPO_SIZE_UNKNOWN`, `sizeBytes` null, and `ceilingBytes` set. The message states that size could not be confirmed and the clone was not started. This covers API failure, auth failure, missing `size`, non-numeric `size`, and a remote that is not a GitHub repo URL this module can measure.
5. A failed check must not leave a partial clone directory from this attempt.
6. Size at or under the ceiling, including equality, proceeds to the existing full-history clone. The gate must not change clone flags, depth, or destination for allowed repos.
7. Callers already catching clone failures must be able to distinguish this error by `name` and `code` without parsing prose.

## Acceptance criteria

- A repo whose GitHub `size` converts to more than `536870912` bytes causes `SandboxRepoSizeError` with `code` `REPO_SIZE_CEILING_EXCEEDED` and does not invoke the clone or fetch implementation.
- A repo whose converted size is equal to or less than the ceiling still clones with the current full-history behavior.
- When the size request fails, returns no numeric `size`, or the remote is not measurable as a GitHub repo, the module throws `SandboxRepoSizeError` with `code` `REPO_SIZE_UNKNOWN` and does not clone.
- Error text includes the repo identity, whether the clone was not started, and, for the exceeded case, both byte figures.
- Setting `SANDBOX_REPO_SIZE_CEILING_BYTES` to a positive integer changes the comparison value used by the check; a non-positive or non-integer value leaves the default in effect.
- Tests mock the metadata lookup and the clone function. They assert call order: size resolution completes, and the clone function is not called on either failure code. No test may clone an oversized fixture and then assert refusal.
- Manual check on the bound repo: a forced ceiling below that repo’s reported size fails closed with the typed error and creates no sandbox clone; a ceiling at or above the reported size allows the existing clone path.

## Out of scope

- Sparse checkout, partial clone, shallow clone, or LFS changes as a way to admit oversized repos.
- Raising sandbox disk, memory, or time quotas.
- Post-clone cleanup, quota reaping, or refusing after a clone has started.
- New UI, repo browsers, or copy beyond what callers need to display `name`, `code`, and the error message.
- Changing clone behavior for repos that pass the ceiling.
- Scanning file contents or counting working-tree bytes after checkout.
- History rewrite, GitHub-side size reduction, or user education flows.
