# G13: Durable versus best-effort outbox classification

## Problem & Goal

Gap G13 (parent epic #5747, depends on G12) is only partially done. Outbox types already distinguish durable retention, dead letters, and best-effort drop, and several queues are classified and tested. Two done-when conditions are still unmet on `origin/main`.

User-work queues `activity`, `run-outcomes`, and `host-persist` are absent from the classify table in `packages/write-outbox/src/queueClass.ts`. They inherit `durable` from outbox mode. That retention is correct today, but it is correct only by fallback, not by a classification decision. `queueClass.test.ts` pins `host-persist` as unclassified. `host-persist` mixes chat messages with host telemetry, so a fallback must not be left as the decision.

Dead-letter export and repair are not a user-visible action. `clients/vscode/src/deadLetterCommand.ts` exists only in the dirty working tree. It is not registered in HEAD `clients/vscode/src/extension.ts` and is not declared in HEAD `clients/vscode/package.json` `contributes.commands`. The person cannot export or repair a dead letter from the command palette.

Goal: every queue that carries user work is explicitly durable, telemetry-class queues are best-effort, and the person can export and repair a dead letter from the command palette. Do not close G13 until both remaining items land on `main`. Epic #5747 stays in progress.

## Target users / ICP roles

- The person using the Builderforce VS Code extension who has a dead-lettered outbox item and must export it and repair it themselves, without an engineer editing local state.
- Offline-first extension users whose user work (including chat messages carried by `host-persist`, plus `activity` and `run-outcomes`) must not be dropped when send fails.

## Scope

In scope, both required:

1. Register the existing dead-letter command so export and repair are available from the command palette on the committed tree, not only in a dirty working tree.
2. Make an explicit classify-table decision for `activity`, `run-outcomes`, and `host-persist`, preserving today's correct durable retention, and update the tests and comments that still describe them as unclassified or deliberately absent.

Already shipped on `origin/main`; do not redo:

- Dead-letter export/repair exports and telemetry stamps (`errorReporter.ts`, Chrome telemetry, frontend qa/telemetry).
- `createDurableOutbox` honoring drop-on-failure.
- `clients/vscode/src/g13QueueClassification.test.ts` (24 tests) driving `createDurableOutbox` against a refused send across 16 canonical queues, and the invariant that a queue is built only through the shared classifier.
- Confirmation that `localAuditStore`, `runRecovery`, `sessionsSnapshotStore`, and `auditExecution` have no outbox references and need no reclassification. VS Code outbox constructors are limited to `outboxStorage.ts`, `activity.ts`, `bfApi.ts`, `errorReporter.ts`, and `gateway.ts`.

## Functional requirements

1. Register `clients/vscode/src/deadLetterCommand.ts` from `clients/vscode/src/extension.ts` so the command is activated with the extension.
2. Declare that same command in `clients/vscode/package.json` under `contributes.commands`, with a title a person can find in the command palette.
3. From the command palette, the person can export a dead letter and repair it. Export and repair must use the existing dead-letter command implementation, not a second path.
4. Registration and the `package.json` contribution must be present on `origin/main`. A dirty-tree-only file does not satisfy this requirement.
5. Add `activity`, `run-outcomes`, and `host-persist` to the classify table in `packages/write-outbox/src/queueClass.ts`. Each must receive an explicit class. None may remain unclassified or inherit class only from outbox mode.
6. Classify all three as durable. That matches current correct behavior. `host-persist` stays durable because it carries chat messages (user work) mixed with host telemetry. Do not classify it best-effort to satisfy the telemetry half of the mix.
7. Keep the general rule: a queue that carries user work is durable; a telemetry-class queue is best-effort. Best-effort drop-on-failure must not apply to `activity`, `run-outcomes`, or `host-persist`.
8. Update the comments in `queueClass.ts` that currently explain why those queues are absent (including the `host-persist` mix note and the classify-table doc comment) so they describe the explicit durable decision and the reason `host-persist` is not best-effort.
9. Update `queueClass.test.ts` so it no longer pins `host-persist` as unclassified, and so it asserts the explicit durable class for `activity`, `run-outcomes`, and `host-persist`.
10. Keep queue construction on the shared classifier. Do not add an outbox constructor that bypasses `queueClass`.

## Acceptance criteria

- HEAD `extension.ts` references the dead-letter command registration. HEAD `package.json` `contributes.commands` declares it. Both are true on `origin/main`, not only in a dirty tree.
- A person can run the command from the command palette and both export a dead letter and repair it.
- `activity`, `run-outcomes`, and `host-persist` are present in the `queueClass.ts` classify table as durable. Their class does not depend on outbox-mode fallback.
- A refused send does not drop user work on those three queues. Telemetry-class queues remain best-effort.
- `queueClass.test.ts` asserts the explicit durable classification and does not pin `host-persist` as unclassified.
- `g13QueueClassification.test.ts` still passes, including the shared-classifier invariant.
- G13 is not closed, and epic #5747 is not moved out of in progress, until both the command-palette action and the explicit classifications have landed.

## Out of scope

- Closing epic #5747, or treating either remaining item as sufficient alone.
- G12 work, and any redesign of outbox modes beyond this classification and command registration.
- Reimplementing shipped export/repair internals, telemetry stamps, or `createDurableOutbox` drop-on-failure behavior.
- Splitting `host-persist` into separate chat and telemetry queues.
- Changing retention of queues that are already explicitly and correctly classified.
- Reclassifying `localAuditStore`, `runRecovery`, `sessionsSnapshotStore`, or `auditExecution`.
- New outbox constructors, new queues, or a dead-letter UI other than command-palette registration of the existing command.
