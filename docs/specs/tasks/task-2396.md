# PRD: Auto-Captured Ticket Service Improvement (Brain Chat #99)

## Problem & Goal

**Problem.** Brain chat sessions in the IDE can modify code without a user-created ticket. To keep that work visible, the platform auto-mints a ticket and links it to the originating conversation. Chat #99 produced a code change to `ChatTicketService.ts`, the service responsible for this behavior, and the ticket was itself auto-captured with no human-authored description. The intent of the change is currently undocumented beyond the label "improvement."

**Goal.** Record the scope and expected behavior of the change to `ChatTicketService` so downstream agents (review, QA, docs) share one source of truth. The change must keep auto-captured tickets accurate, traceable to the originating chat, and useful on the board, without regressing existing ticket creation flows.

**Caveat.** The exact diff is not included in the task payload. Requirements below describe the intended contract of the service and must be validated against the actual diff during review.

## Target Users / ICP Roles

- **Developers using the Brain/IDE chat**: want their chat-driven changes tracked without manual ticket overhead.
- **Engineering leads / PMs**: rely on the board to reflect all code activity, including auto-captured work.
- **Downstream agents (reviewers, QA, release-notes)**: consume auto-captured ticket metadata to understand what changed and why.

## Scope

**In scope**
- `Builderforce.ai/api/src/application/brain/ChatTicketService.ts`: logic that creates/links tickets from Brain chat deltas (title, description, type classification such as "improvement", file list, repo binding, chat link).
- Behavior of auto-captured tickets relative to the bound repo (`seanhogg/builderforce.ai`, base `main`).

**Context only (no changes expected)**
- Board/ticket persistence layer, chat storage, and the IDE chat delta capture pipeline.

## Functional Requirements

1. **Ticket auto-creation.** When a Brain chat delta modifies code and no ticket is associated with the chat, the service creates exactly one ticket for that chat.
2. **Idempotency.** Repeated deltas from the same chat (e.g., chat #99) must not create duplicate tickets. Subsequent deltas update or append to the existing ticket.
3. **Chat linkage.** Each auto-captured ticket stores a durable reference to the originating chat (chat ID and, where available, a link).
4. **Change summary.** The ticket records the list of touched files and a type classification (e.g., `improvement`, `bug`, `feature`) derived from the delta.
5. **Repo binding.** The ticket records the bound repository and base branch (`seanhogg/builderforce.ai`, `main`).
6. **Provenance labeling.** Tickets are clearly marked as auto-captured (not human-authored) in title/description or metadata, so they can be filtered and later enriched.
7. **Failure isolation.** A failure in ticket creation must not block or roll back the chat's code change; errors are logged with chat ID context.
8. **Backward compatibility.** Existing ticket creation paths and public method signatures of `ChatTicketService` remain unchanged unless explicitly documented in the diff.

## Acceptance Criteria

- [ ] A code-changing Brain chat with no linked ticket results in exactly one new ticket linked to that chat.
- [ ] A second code-changing delta in the same chat does not create a second ticket.
- [ ] The created ticket includes: chat reference, touched file list, type classification, repo + base branch, and an auto-captured indicator.
- [ ] Simulated ticket-creation failure does not prevent the code change from being saved, and an error log with chat ID is emitted.
- [ ] Existing unit/integration tests covering `ChatTicketService` pass; new or updated tests cover the changed behavior.
- [ ] Type-check and lint pass for the API package.
- [ ] No files outside `ChatTicketService.ts` (and its tests, if added) are modified.

## Out of Scope

- Redesigning the board UI or ticket schema.
- Changes to the IDE chat delta capture pipeline.
- Rich auto-generated descriptions via LLM summarization (future enhancement).
- Retroactive backfill of tickets for historical chats.
- Changes to SOC2, CI, Dockerfiles, agent-runtime, or other top-level directories.
