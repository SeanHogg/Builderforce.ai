# Product Requirements Document: Export Reports to PDF (GAP-123)

## Problem & Goal
Users currently cannot export dashboard reports into a portable, shareable format. Stakeholders need to share reports outside the platform (email, presentations, archival) without taking screenshots or copy‑pasting data. The goal is to provide a one‑click PDF export of any report view that preserves layout, charts, and tabular data exactly as seen on screen, while meeting accessibility and branding requirements.

## Target users / ICP roles
- **Analysts** who create and share performance reports.
- **Managers** who review and distribute operational summaries.
- **External partners** who receive read‑only report snapshots.

## Scope
- Add an “Export as PDF” button to all report pages.
- Generate a PDF containing:
  - The report title, date range, and applied filters.
  - All visible visualizations (charts, tables) as rendered.
  - Page‑level headers/footers with logo, page numbers, and generation timestamp.
- Support PDFs up to 50 pages of content.
- Include an option to export with or without commentary/annotations (if present).
- The exported file must pass WCAG 2.1 AA accessibility checks (tagged PDF, alt text, reading order).
- PDF generation must complete within 15 seconds for reports up to 20 pages under standard load.

## Functional requirements
1. **Export trigger**  
   - A clearly labeled “Export PDF” button appears on every report page, visible to all authenticated users with view access.
   - Button is disabled while a PDF generation is in progress; a spinner or progress indicator is shown.

2. **PDF content**  
   - The output PDF must mirror the current report view exactly (applied filters, sorting, date range, visible/hidden columns, chart zoom level).
   - All chart types (bar, line, pie, scatter) render as SVG → high‑resolution raster fallback (300 DPI) to ensure fidelity.
   - Tables render with repeating headers on each page if the table spans multiple pages.
   - Report commentary/annotations (if toggled) appear in a separated text block.

3. **Metadata & branding**  
   - PDF metadata includes report name, author (current user), creation date.
   - Header: company logo (left), report name (centre).
   - Footer: “Generated by [User Name] on [Timestamp]” (left), page X of Y (right).

4. **Performance & limits**  
   - Reports with up to 20 pages: PDF generated within 15 seconds; up to 50 pages: 40 seconds max.
   - File size must not exceed 50 MB for a 50‑page report (with images).
   - Queue concurrent requests; maximum 5 simultaneous exports per tenant.

5. **Accessibility**  
   - Output PDF must be tagged (headings, alt text on charts, table structure).
   - Follow PDF/UA‑1 guidelines.

6. **Security & permissions**  
   - User can only export reports they have view permission for.
   - PDFs are not stored server‑side after download (ephemeral generation).

## Acceptance criteria
1. A user viewing any report sees an “Export PDF” button; clicking it initiates generation with a loading indicator.
2. The downloaded PDF visually matches the on‑screen report (manual side‑by‑side comparison, cross‑browser).
3. Mandatory filters and date range are reflected in the PDF title/filter summary.
4. A 10‑page report with mixed charts and a large table exports in <15 seconds on a test environment with typical data volume.
5. The exported PDF passes an accessibility checker (e.g., PAC 2024) with no violations.
6. When a user lacks view rights to a report, the export button is hidden or disabled with a tooltip.
7. Exported PDF includes correct page numbers and branding.

## Out of scope
- Export of dashboards (multi‑report combinations).
- Scheduled batch PDF generation and email delivery.
- Export to other formats (CSV, Excel, PPTX).
- Editable PDF forms or interactive elements.
- Custom PDF templates per tenant (only company logo configurable).
- PDF archival or storage on the platform.

### Availability & Triggers

| ID | Requirement | Maps To | Rationale |
|----|-------------|---------|-----------|
| **REQ-A1** | Every authenticated user with `view` permission on a report **shall** see an "Export PDF" button rendered in the report toolbar / action bar. | FR-1, AC-1, AC-6 | Discoverability; no hidden menus or power-user-only paths. |
| **REQ-A2** | The Export PDF button **shall** be disabled (and a loading indicator displayed) while a PDF-generation request for that same report is in-flight for the current user. | FR-1, AC-1 | Prevents duplicate submissions; gives the user confidence that work is in progress. |
| **REQ-A3** | When the current user lacks `view` permission on the report, the Export PDF button **shall** be hidden **or** rendered in a disabled state with a tooltip explaining why export is unavailable. | FR-6, AC-6 | Fail-closed; no information leak about a report's existence via the export button's presence. |
| **REQ-A4** | A user **may** cancel an in-progress PDF generation; the server **shall** abort the job and release its concurrency slot within 5 seconds of receiving the cancellation signal. | FR-1, FR-4 | User control; prevents a stuck job from consuming a tenant-limited slot indefinitely. |

### Content Fidelity & Layout

| ID | Requirement | Maps To | Rationale |
|----|-------------|---------|-----------|
| **REQ-C1** | The exported PDF **must** include the report title, the active date-range, and a summary of every active filter (filter name + selected value(s)) rendered as text in the report header block. | FR-2, AC-3 | The PDF must be self-describing; a reader without access to the platform must understand what data they are looking at. |
| **REQ-C2** | Every chart visible on the report view (bar, line, pie, scatter, area, and any future chart types added to the dashboard widget registry) **must** appear in the PDF at the same dimensions, zoom level, and data state as the on-screen rendering. | FR-2, AC-2 | "Mirror the current report view exactly." |
| **REQ-C3** | Charts **shall** be embedded at 300 DPI minimum resolution. Vector (SVG) source **must** be preferred over raster; when direct SVG embedding is not feasible for a given chart type, an SVG-to-raster fallback at ≥300 DPI **shall** be used. | FR-2 | Fidelity and print-readiness. |
| **REQ-C4** | Every data table visible in the report **must** appear in the PDF with (a) header rows repeated at the top of each page when the table spans a page break, and (b) columns in the same order and visibility state as the on-screen report (hidden columns omitted). | FR-2, AC-2 | Readability of multi-page tables is a core usability concern. |
| **REQ-C5** | When the report includes commentary/annotation blocks and the user has toggled "Include commentary," those blocks **must** be rendered in a visually distinct text section (e.g., a bordered block with italic text) after the visualizations. When toggled off, commentary **shall** be omitted entirely from the PDF. | FR-2 | Respect user choice; commentary is optional per the PRD scope. |
| **REQ-C6** | Page breaks **must** be inserted before a chart or table whose full height would otherwise be split across a page boundary. If a single chart or table is taller than one page, it **may** split at a page boundary but **must** not orphan fewer than 3 rows of a table. | FR-2 | Print-layout quality; avoids "widow" rows and chopped charts. |

### Branding & Metadata

| ID | Requirement | Maps To | Rationale |
|----|-------------|---------|-----------|
| **REQ-B1** | The PDF **must** carry the following XMP/document metadata: `dc:title` (report name), `dc:creator` (current user's display name or email), `xmp:CreateDate` (UTC ISO-8601 timestamp of generation), and `dc:format` ("application/pdf"). | FR-3 | Searchable, sortable PDFs; provenance for recipients. |
| **REQ-B2** | Every page **must** render a header containing the tenant's configured company logo (left-aligned) and the report name (centre-aligned). If no logo is configured, the left slot **shall** be empty. | FR-3 | Branded output without requiring per-tenant PDF template design. |
| **REQ-B3** | Every page **must** render a footer containing "Generated by {User Name} on {Timestamp}" (left-aligned) and "Page X of Y" (right-aligned), where the timestamp uses the user's preferred timezone when available, falling back to UTC. | FR-3, AC-7 | Provenance and page navigation. |
| **REQ-B4** | The logo image **must** be embedded directly in the PDF (no external URL references) so the PDF renders correctly offline. | FR-3 | Self-contained output for email/archival use. |

### Performance & Concurrency

| ID | Requirement | Maps To | Rationale |
|----|-------------|---------|-----------|
| **REQ-P1** | For a report producing up to 20 PDF pages, generation **must** complete within 15 seconds (wall-clock, p95) under standard tenant load. For 21–50 pages, the p95 ceiling **shall** be 40 seconds. | FR-4, AC-4 | User expectation management; matches the PRD's stated limits. |
| **REQ-P2** | A tenant **must** never have more than 5 simultaneous PDF-generation jobs in-flight. Requests beyond this limit **shall** receive an HTTP 429 (Too Many Requests) with a `Retry-After` header. | FR-4 | Prevents one tenant from saturating shared compute. |
| **REQ-P3** | The generated PDF file size **must** not exceed 50 MB. If the renderer estimates the output will exceed this threshold, it **shall** abort and return an actionable error (e.g., "Report too large for PDF export — reduce date range or hide large tables"). | FR-4 | Prevents OOM / transfer failures. |
| **REQ-P4** | PDF generation **must** be asynchronous from the user's perspective: the API endpoint **shall** accept the request, enqueue the job, and return a job identifier. The frontend **shall** poll or use server-sent events / WebSocket to track progress and trigger the download when the job completes. | FR-1, FR-4 | UX: a synchronous request that takes 40 seconds blocks the UI and risks connection timeout. |
| **REQ-P5** | The server **must** impose a hard timeout of 60 seconds per generation job. If a job exceeds this timeout, it **shall** be terminated and the slot released; the user **shall** receive a clear error message. | FR-4 | Safety valve against runaway generation. |

### Accessibility (Output PDF)

| ID | Requirement | Maps To | Rationale |
|----|-------------|---------|-----------|
| **REQ-ACC1** | The output PDF **must** be tagged per PDF/UA-1 (ISO 14289-1): heading structures (`H1`–`H6`), table structures (`Table`, `TH`, `TD`), and paragraph tags **must** be present and correspond to the visual hierarchy of the report. | FR-5, AC-5 | Screen-reader navigability. |
| **REQ-ACC2** | Every chart image in the PDF **must** carry an `Alt` text entry describing what the chart shows (e.g., "Bar chart: LLM spend by month, January–June 2026"). Chart alt text **shall** be derived from the metric label + date range, not hard-coded. | FR-5, AC-5 | WCAG 2.1 AA / PDF/UA-1 image accessibility. |
| **REQ-ACC3** | The reading order of the PDF **must** follow the visual flow of the report: title → filter summary → charts (in on-screen order) → tables (in on-screen order) → commentary block (if included). | FR-5, AC-5 | Screen-reader linearization matches visual intent. |
| **REQ-ACC4** | The PDF **must** pass an automated accessibility checker (e.g., PAC 2024 or axesPDF) with zero violations prior to being marked as production-ready. | FR-5, AC-5 | Gate: do not ship inaccessible PDFs. |

### Security & Data Handling

| ID | Requirement | Maps To | Rationale |
|----|-------------|---------|-----------|
| **REQ-S1** | The server **must** verify that the requesting user holds `view` permission on the report resource before enqueuing a generation job. Authorization **must** be re-verified at generation time (not only at request time) to account for permission revocation between request and completion. | FR-6, AC-6 | Time-of-check/time-of-use protection. |
| **REQ-S2** | Generated PDFs **must** be stored ephemerally: the file **shall** be deleted from server storage (in-memory buffers, temp files, or object storage) within 60 seconds of successful download or within 5 minutes of generation if never downloaded. No PDF **shall** persist beyond the generation session. | FR-6 | Data minimization; no unintended PDF archive. |
| **REQ-S3** | The download URL for a completed PDF **must** be a single-use, time-limited, cryptographically unguessable token (≥128 bits of entropy) that expires within 10 minutes of generation. | FR-6 | Prevents unauthorized access to generated PDFs via URL guessing. |
| **REQ-S4** | All report data rendered into the PDF **must** be scoped to the tenant of the requesting user. Cross-tenant data leakage **must** be impossible by construction (tenant-id is an invariant on every data query, not a filter applied post-retrieval). | FR-6 | Multi-tenancy boundary; data isolation is already a platform invariant but must be verified in the PDF path. |

### Error Handling & Observability

| ID | Requirement | Maps To | Rationale |
|----|-------------|---------|-----------|
| **REQ-E1** | Every PDF generation failure **must** produce a user-visible error message that describes what went wrong in plain language (e.g., "PDF generation failed: the chart data could not be loaded") — not a raw stack trace or HTTP status code alone. | FR-1 | Non-technical users are the primary audience. |
| **REQ-E2** | The server **must** emit an auditable log event for every generation attempt (success or failure) containing tenant id, user id, report id, generation duration, output size, and error cause when applicable. This event **shall** feed the existing platform audit log and tenant-activity analytics. | — | Operational visibility; already aligns with the existing `audit/` and `analytics/` service patterns. |
| **REQ-E3** | The frontend **must** surface a meaningful message when the export fails due to a concurrency limit (HTTP 429), including a countdown or suggestion to retry. | REQ-P2 | User should not be left guessing why the button "did nothing." |

### Integration Points (Existing System Context)

| ID | Requirement | Maps To | Rationale |
|----|-------------|---------|-----------|
| **REQ-I1** | The PDF generator **must** reuse the existing `application/export/tabularExport.ts` module's column-resolution and value-serialisation logic for any tabular data embedded in the PDF. The CSV/HTML paths and the PDF path **shall** produce identical cell values for the same input rows. | — | Consistency; avoids divergent serialisation bugs between formats. |
| **REQ-I2** | The PDF generator **must** source metric values from the existing `application/dashboards/metricRegistry.ts` (`METRIC_REGISTRY`) so that the PDF rendering of a metric matches the on-screen widget rendering by construction. | — | Single source of truth for metric computation; the PDF is a presentation layer, not a data layer. |
| **REQ-I3** | The export button component **must** be reusable across all report surfaces (cross-project health dashboard, tenant analytics views, and any future report pages) without per-page copy-paste. It **should** accept props for `reportId`, `reportType`, and an optional `filters` snapshot. | — | Maintainability; the platform already has multiple report surfaces and this number will grow. |
