> A human starts with a need, collaborates with people and agents in one Creation Session, validates the result, and delivers it. ## Key Metrics

**North-star metric:** percentage of Creation Sessions that reach a validated, real deliverable.

**Speed:** time from first prompt to first meaningful artifact. **Delivery:** sessions reaching a real deliverable · artifact validation/pass rate · delivery success and retry rate. **Collaboration:** sessions inviting at least one human or agent · agent group-chat participation · successful synthesis rate. **Compounding value:** sessions resumed within 7 and 30 days · created outputs reused as inputs. **Efficiency:** human interventions per successful delivery · cost and latency per delivered outcome. **Measurement integrity:** percentage of meaningful actions with a correlated terminal outcome.

GitHub stars, package downloads, workflow counts, MCP connections, and active-agent counts remain operational or acquisition diagnostics. They are not evidence of customer value and do not lead roadmap prioritization.

Every metric is computed from the correlated outcome ledger and supports the same content-free aggregation dimensions: session, project, tenant, and platform. Platform aggregates must enforce minimum cohort sizes and never expose another tenant's session content. The session scorecard compares the current session with an aggregate tenant baseline; project and tenant rollups power value reviews, and privacy-safe platform rollups power the sales deck. Metric contract: **[Creation outcome metrics](./docs/design/creation-canvas/OUTCOME-METRICS.md)**.

### Autonomous lifecycle — MEASURED failure (audited 2026-07-25 via the new ticket-lifecycle ledger)

> The `GET /api/tasks/:id/lifecycle` + `GET /api/insights/autonomy` ledger (see DONE.md) was built to answer "do manager/human-created tickets actually complete their lifecycle autonomously?". Measured on tenant 1, 90-day window, 821 tickets created: **6 (0.7%) reached Done fully autonomously** (zero human lane moves), **12 (1.5%) reached Done at all**, **809 (98.5%) stalled**. The items below are the measured root causes, each still open.

- **The default board template human-gates `in_review`, which is exactly where the autonomous chain terminates.** `in_review.gate='human'` on **all 10** of tenant 1's boards (it is the template default), and the transition log shows autonomy reliably reaches it then stops: **871 system hops INTO `in_review` vs 14 into `done`**, with **315 tickets** currently piled in `in_review` and **131,431** `human_gate` skip events across **381 distinct tickets** (85% of all 154k skips). So "full autonomous lifecycle" is currently impossible by configuration, not by defect. DECISION NEEDED (product, not a mechanical fix): either ship a reviewer-agent-staffed auto-gated review lane in the default template, or stop describing the lifecycle as end-to-end autonomous. Letting agents self-advance their own work to Done without a reviewer is a governance change, so it must be chosen deliberately.
- **Lane staffing is effectively absent, so autonomy depends entirely on the owner-agent fallback.** Only **3 of 61** auto-gated lanes (and 1 of 11 human-gated) have any `swimlane_agent_assignments` row. Consequence: **466 of 821 tickets (57%) had zero runs AND zero autonomous hops** — inert from creation — and `backlog` holds **424** stalled tickets. Either seed lane staffing with the project's workforce on board creation, or make the owner-agent fallback explicit in the UI so an unstaffed lane is visibly a misconfiguration.
- **Duplicate boards per project silently orphan lane configuration.** Project 11 has **7 boards** (1 `lifecycle_managed`, 6 not), project 2 has 2, project 14 has 2. `findCanonicalBoard` picks ONE, so gates/staffing configured on the losers are dead config — and for project 11 whether the Coordinator state machine or the simple single-hop path runs depends on which board wins canonical selection. Needs a board-dedupe/merge migration + a uniqueness constraint (or an explicit primary-board FK on `projects`).
- **`auto_run_skipped` telemetry is a write amplifier: 154,312 rows in 14 days (~11k/day), 131k of them the same `human_gate` refusal re-recorded every sweep tick.** The sweep re-evaluates and re-declines permanently-gated tickets forever, writing a row each time — Neon write load for zero information gain on a sub-$5/mo budget (see [[neon-cost-under-5-dollars]]). Collapse to a state-change-only emit (record a refusal only when the reason CHANGES for a ticket+lane), and/or exclude `human_gate` tickets from the sweep until their gate or staffing changes.
- **The stall register makes the human-gate decision unavoidable rather than resolving it.** The manager's stall triage (0367) now diagnoses every non-moving ticket and escalates the ones it cannot fix — but `human_gate` and `capability_gap` are escalations BY DESIGN (the manager must not override a gate a human deliberately configured, nor conjure a capable agent). With `in_review.gate='human'` on all 10 boards and only 3 of 61 auto lanes staffed, the register will surface a large standing escalation backlog on first run. That is the honest reading of the two items above, not a new defect — but it means the template/staffing decisions are now blocking a visible queue rather than an invisible one, and should be made deliberately.
- **Ticket creation attribution is missing for the large majority of tickets: 722 of 821 (88%) have no `task.created` activity row at all**, so "who opened this — the AI Manager or a person?" is unanswerable for them and they audit as `origin: 'unknown'`. The `target_type` drift that hid the rest was fixed in this pass (103 rows were written as `'tasks'` vs 8 as `'task'`; the ledger now reads both and the MCP writer is canonicalized), but the writers that create tickets WITHOUT emitting any creation activity still need to funnel through one emitter — candidates: `QaFindingRouter`, `ValidationService`, `IncidentService`, `SecurityAuditService`, board-sync inbound, and `decomposeEpic` child fan-out.

- **Manager pass outcomes exist only as PROSE, so pass effectiveness can only be regex-parsed back out** *(found building the Manager diagnostics handover 2026-07-25)* — `finalizeManagerRunTask` (`api/src/application/manager/ManagerService.ts`) renders the full `ManagerRunSummary` into `tasks.description` ("Scored 0 · ranked 300 · assigned 0 · …") and stores nothing structured. The new `frontend/src/lib/managerDiagnostics.ts` has to `parsePassCounters()` that sentence to detect the load-bearing failure — a pass that COMPLETES and changes nothing — which means the detection silently degrades if the sentence is ever reworded, and no query can answer "how many passes actually scored anything this month?". Fix: persist the summary structurally (jsonb column on the run task, or a `manager_runs` row keyed by `run_task_id`) and read it on the overview. Unblocks exact pass-effectiveness findings, a pass-history chart, and dropping the parse.
- **A manifest sign-off slot auto-resolves an assignee nobody chose, and the ticket header never shows it** *(found fixing the "awaiting sign-off but nobody is assigned" report 2026-07-26)* — `TicketParticipantsService.resolveAssignee` falls back to the FIRST role-capable agent in the tenant when no `project_role_assignments` pin exists, so a ticket acquires up to ten required reviewers no operator ever staffed. Those slots gate completion and merge, but they appear only on the ticket's Sign-off & Accountability tab — the header/assignee column and the board card show nothing — so the ticket reads as unassigned while the manager correctly reports ten outstanding sign-offs. The manager feed and the diagnostics report now name the ownership per slot (this pass), but the SURFACE mismatch stands. Fix: show the required-role roster on the ticket header/card (count + unstaffed badge), or require an explicit pin before a required slot is created.
- **`syncStates` preserves `in_progress` forever, so a slot that later loses its assignee lies about being worked** *(same pass)* — the state recompute deliberately keeps `in_progress` (it is evidence of a run attribution it cannot re-derive), but it does so even when `assigneeRef` has since become null. Such a slot is neither dispatchable nor reported as `unstaffed` by its state column. The new `classifySignoffOwnership` classifies by `assigneeRef` rather than by state, so no gate is wrong today, but any consumer still keyed on the state column sees a slot that nobody owns and nobody is working. Fix: drop `in_progress` back to `unstaffed` when the assignee is gone, keeping the run evidence in `evidence`.
- **Coverage remediation never writes a ticket OWNER, so `unowned` cannot fall** *(same pass)* — the AUDIT+REMEDIATE stage calls `coordinateTicket`, which rewinds the lane and asks the lane gate to dispatch the missing role; it never touches `tasks.assignedUserId`/`assignedAgentRef`. On a project where the lane gate cannot dispatch (unstaffed lanes), the stage's only lasting effect is moving tickets backwards, pass after pass. The journal line no longer *claims* staffing it did not do (fixed this pass), but a flagged ticket still needs the `assign` path to actually gain an owner. Fix: have the remediation stage run `assignTicketOwner` before/alongside `coordinateTicket` when the ticket is unowned.
- **Nothing on the wire says WHY a scheduled manager sweep skipped a project** *(same pass)* — a stale `lastRunAt` can mean the KV work-gate (`cronWorkSignal.ts`, see [[neon-cost-under-5-dollars]]) decided there was no work, the token gate skipped the tenant, the cron itself failed, or every pass died before stamping. Unblocks "the cron is not reaching this project" being answered rather than inferred.

### 🤖 Missing bounded contexts for a fully agentic platform (opened 2026-07-26)

> Follow-on to the DDD review. That pass asked "are the declared domains real?"; this one asks "for a platform whose *primary actor is not a human*, which domains were never declared at all?" The 84 `application/` modules decompose the **product**; the domains below exist only because a non-human principal takes autonomous action.
>
> **Coordination, Memory governance and Rehearsal shipped 2026-07-26** (migrations 0370–0372) — moved to [DONE.md](./DONE.md). The five still open, then the residuals of the three that shipped.

- **No agent identity or credential-scoping domain — agents act with tenant-wide authority.** `rbac`/`domain/permissions` model *humans* (the 4-tier `requireRole` ladder keyed to `users`); there is no principal type for an agent, so an agent's blast radius is "whatever the tenant can do". Zero hits repo-wide for `onBehalfOf`/`scopedToken`/`credentialBroker`; third-party creds live undifferentiated in `application/integrations/credentialCrypto.ts` and are handed to a run whole (the container surface already flags this: "short-lived clone token handed to the container shell — consider a scoped git-proxy"). `containerRunToken.ts`/`previewToken.ts` are *platform* run tokens, not downstream credential scoping. Fix: an `agentIdentity` context owning a per-run principal, capability-scoped short-lived credential issuance, and delegation records. Unblocks: least-privilege runs, per-agent revocation, and an audit trail that names a principal rather than a tenant.
- **No agent-definition versioning — runs are not reproducible and agents cannot be regression-tested.** `ide_agents` is a mutable row whose prompt-shaping fields (`title`/`bio`/`skills`/`roleKeys`/`psychometric`/`baseModel`) can change at any time; `executions` stores only `agentId` + `payload`, no frozen snapshot. Editing an agent silently rewrites the history of every past run attributed to it, and there is no promote/canary/rollback of (prompt + policy pack + model + persona) as one unit. `application/eval` evaluates *models*, not agent definitions. **This now also caps rehearsal** (below). Fix: immutable `agent_versions` + a version FK on `executions`/`agent_dispatches`/`rehearsals`.
- **No untrusted-input boundary — policy gates cover tool *calls*, not the *content* that motivates them.** `evaluatePolicyGate` + `policyPackService` are a real egress control at the tool seam, but everything flowing *in* — repo files, ticket text, web-search results, CI logs, ingested knowledge — enters the same instruction channel as the operator's directives with no provenance or trust tier. `infrastructure/security/redactSecrets.ts` is log redaction, not an output filter: nothing scans agent-authored commits/PRs for exfiltrated secrets before they leave. Fix: a `trust` context tagging every context-window contribution with a source tier, plus an outbound content check on the commit/PR/message seams.
- **No containment domain — there is no stop.** Zero hits for `killSwitch`/`emergencyStop`/quarantine. What exists is per-ticket and reactive: the 3-strike `run_cap_exhausted` breaker, `staleExecutionReaper`, `pausedRunReaper`, `runRollback.ts`, `tickDispatchBudget`. No tenant-wide or global halt, no way to quarantine one misbehaving agent while its peers run, and no per-run blast-radius budget (max files, max repos, max spend) enforced before the fact. Fix: a `containment` context owning halt scopes, quarantine state, and pre-declared per-run limits checked at the tool seam.
- **No provenance/evidence domain — "the agent says it's done" is checked with string heuristics.** `assertsUnrunVerification()` and `hasNoCodeDeliverable()` in `cloudAgentTools.ts`, plus `MAX_PLACEHOLDER_FINISH_BLOCKS`, are provenance checks implemented as text matching because no model links a claim to the tool output that justifies it. `activity_log` records *that* things happened, not *what evidence supports* an assertion. Fix: a claim→evidence edge (tool-audit event ids backing each finish condition), turning the anti-stub gate from a heuristic into a structural check.

- **Coordination residuals (0370).** (1) `coordinate` is Worker-only: the container image has no handler for the four tools, so a container agent is lease-*protected* (its `write` op takes the same lease, its `finalize` op releases them) but cannot `claim_resource` ahead of time or read the blackboard — needs a `coordinate` container-op. (2) Leases key on ONE (repo, branch) per run, so multi-repo spanning must thread a per-repo context into `LeaseHolder`. (3) Nothing aggregates contention — an operator cannot see "these two agents fought over 14 files in this stage" without reading the tool-audit stream. (4) No lease view on the ticket/execution surfaces; `/agent-ops` requires typing a ticket number. (5) If the tool loop THROWS, the terminal release is skipped (it sits after the try/finally) and leases lapse via the 15-minute TTL instead of being handed back at once.
- **Memory residuals (0371).** (1) `team_memory` and `agent_knowledge_chunks` were NOT folded into the governed service — separate ingestion/host-summary stores, still with no scope/provenance/TTL contract. (2) Cloud recall is lexical (ILIKE); SSM-embedding recall is on-prem only, so isolation is now correct on both surfaces but relevance still differs. (3) A fact can still be recalled for up to the cache TTL after its EXPIRY lapses: the SQL predicate is evaluated inside the cached loader, and the passage of time bumps no version token. (Cross-surface *writes* no longer cause staleness — the key now composes both stores' tokens.) Fix: bound an entry's cache TTL by its own nearest expiry. (4) A ticket-scoped `agent_memory` row has no FK to `tasks`, so deleting a ticket orphans its ticket-scoped facts — unreachable (the scope chain never names a dead ticket) but never reclaimed.
- **Rehearsal residuals (0372).** (1) `replay` pins `frozen_ref` only when the source run's payload recorded a sha; older executions replay against the current base (the report says which) and nothing back-fills. (2) No COMPARISON view — two rehearsals of one ticket must be read side by side by eye, which is the actual product ("did this change make the agent better?"). (3) `trial` runs sequentially and picks tickets by `updated_at`, not a representative sample. (4) Blocked on agent-definition versioning above: until an agent version is immutable, a rehearsal measures "the agent as it is right now", so it and the live run it predicts can silently be different agents. (5) Prep is now read-only, so a rehearsal on a PRD-less ticket runs WITHOUT one while the live run would have drafted one — the report does not yet say so.

### Drizzle single-access-layer migration — residuals (opened 2026-07-25)
