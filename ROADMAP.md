## Platform Roadmap (umbrella — Builderforce.ai · BuilderForce Agents · Evermind/SSM)

> **Vision**: Human as the manager — developers supervise, prioritize, approve, and steer AI agents rather than writing code themselves.

### 🌟 North Star — **Idea to Real**

> The method is not a slogan on this page; it is declared as spec data in two places and ratcheted against itself by `frontend/scripts/check-methodology.mjs`. **This roadmap uses that vocabulary and no other.**
>
> **THE ARC — `Idea → Make → Run → Measure` (→ Market → Expand).** Where you are. Owned by `STAGES` in [frontend/src/lib/navGroups.ts](./frontend/src/lib/navGroups.ts).
>
> **THE LOOP — `Read → Prove → Build`.** What you do to cross from Idea into Make. Owned by [api/src/application/realization/](./api/src/application/realization/), which declares **eight proof forms** — `demo-video`, `clickable-prototype`, `smoke-test`, `wizard-of-oz`, `poc`, `pilot`, `phone-line`, `live-system` — each carrying the question it answers, a fidelity and an effort. A ninth is a registry entry, never a branch.
>
> **Read and Prove spend nothing; only Build spends run budget.** The two acts that decide whether the expensive one is worth doing must never be why somebody skips them.
>
> **Every proof carries a kill condition**, and that number is graded in Measure, which closes the loop back to Idea. A proof with no condition that could fail is not a proof, it is a launch with extra steps.
>
> A roadmap item earns its place by moving a real user through that loop. Enabling work (runtime, gateway, schema) is legitimate and is marked as such — it does not outrank a broken Idea→Real journey.

## Key Metrics

**North-star metric:** percentage of ideas that reach a **graded proof** — a Build whose kill condition was measured, not merely a deliverable that was produced.

**Read → Prove:** time from first prompt to a chosen proof form · share of ideas that Read before they Build. **Build:** proofs reaching a real, reachable artifact · validation/pass rate · delivery success and retry rate. **Measure:** share of proofs whose kill condition was actually graded — the one metric that separates this method from a launch with extra steps. **Collaboration:** sessions inviting at least one human or agent · agent group-chat participation · successful synthesis rate. **Compounding value:** sessions resumed within 7 and 30 days · created outputs reused as inputs. **Efficiency:** human interventions per successful delivery · cost and latency per delivered outcome. **Measurement integrity:** percentage of meaningful actions with a correlated terminal outcome.

GitHub stars, package downloads, workflow counts, MCP connections, and active-agent counts remain operational or acquisition diagnostics. They are not evidence of customer value and do not lead roadmap prioritization.

Every metric is computed from the correlated outcome ledger and supports the same content-free aggregation dimensions: session, project, tenant, and platform. Platform aggregates must enforce minimum cohort sizes and never expose another tenant's session content. The session scorecard compares the current session with an aggregate tenant baseline; project and tenant rollups power value reviews, and privacy-safe platform rollups power the sales deck. Metric contract: **[Creation outcome metrics](./docs/design/creation-canvas/OUTCOME-METRICS.md)**.

## Claim-to-Proof Product Program

Public copy describes evidence available today; stronger promises become roadmap requirements until their acceptance criteria are continuously verified. This is the marketing surface of the same **Prove** act — a claim with no test behind it is the marketing version of a proof with no kill condition.

**Claim policy:** **Available** means shipped, reachable, and covered by repeatable verification. **Beta** means shipped with a named limitation, environment, or incomplete coverage. **Planned** is approved direction and must not be presented as current capability. Avoid `every`, `always`, `never`, `100%`, `zero`, `entire`, and `instant` unless a test or service objective proves the stated boundary. Every public capability must declare its execution/data boundary, prerequisites, status, and last verification date.

## 🚦 Parallel Execution Plan — waves, lanes, and what each agent may touch

> **Why this section exists.** Groups 0–15 are grouped by SUBJECT, which is how you *find* an item and
> not how you *dispatch* one. This section is the dispatch view: the same register items regrouped by
> what they **edit**, so several agents run at once and never meet in a diff. Groups 0–15 remain the
> ledger of record; the **lane id** in bold on an item (e.g. **(W1B)**) is its dispatch address.
>
> **Ownership here is enforced, not advisory.** The lanes are real tracks in
> [.github/isolation-tracks.json](./.github/isolation-tracks.json) (T1–T10 plus W1A–W1E), so
> `api/scripts/check-track-scope.mjs` rejects a `track/<lane>` branch that edits a file outside its
> `owns` set or draws a migration outside its reserved band, and `check-track-manifest.mjs` fails if two
> lanes claim the same file or the same band. A lane that needs a boundary moved edits the manifest
> deliberately rather than reaching across.

### How a lane runs

1. **One lane = one agent = one `track/<laneId>` worktree and branch.** Lane ids are alphanumeric
   (`W1A` … `W1E`) because that is what the branch guard's pattern accepts.
2. **A lane edits only the files in its `owns` set**, plus files it creates inside those paths, plus the
   shared hubs. Reading and importing another lane's module is free; **editing** it is the violation.
3. **Hub files have exactly one owner per wave** (contention register below). No lane "just adds one
   line" to a hub — that one line is precisely what serialises five agents behind one file.
4. **Mounts are batched, never smuggled.** Each lane ships its surface as a self-mounting component that
   decides its own visibility (returns `null` when the project is not an app — no prop-drilled `canX`
   boolean), and files its single mount line into the wave's integration step. This is the same rule
   the DRY standard already states; here it is also what keeps the lanes disjoint.
5. **Migrations come only from the lane's reserved band.** T9 remains the steward and issues numbers
   outside every reserved band.
6. **A lane finishes its own vertical slice** — port + route + typed client + surface + all five locales
   + both themes + 360px. A lane that stops at the API is exactly what produced R15: a live
   embedded-apps API with no caller for a full pass.
7. **A lane's acceptance is its own test file(s).** A lane never edits another lane's tests; if a shared
   assertion has to change, that is an integration-step change.

### Autonomous lifecycle — MEASURED failure (audited 2026-07-25 via the new ticket-lifecycle ledger)

> The `GET /api/tasks/:id/lifecycle` + `GET /api/insights/autonomy` ledger (see DONE.md) was built to answer "do manager/human-created tickets actually complete their lifecycle autonomously?". Measured on tenant 1, 90-day window, 821 tickets created: **6 (0.7%) reached Done fully autonomously** (zero human lane moves), **12 (1.5%) reached Done at all**, **809 (98.5%) stalled**. The items below are the measured root causes, each still open.

- **Lane staffing is effectively absent, so autonomy depends entirely on the owner-agent fallback.** Only **3 of 61** auto-gated lanes (and 1 of 11 human-gated) have any `swimlane_agent_assignments` row. Consequence: **466 of 821 tickets (57%) had zero runs AND zero autonomous hops** — inert from creation — and `backlog` holds **424** stalled tickets. Either seed lane staffing with the project's workforce on board creation, or make the owner-agent fallback explicit in the UI so an unstaffed lane is visibly a misconfiguration.
- **Duplicate boards per project silently orphan lane configuration.** Project 11 has **7 boards** (1 `lifecycle_managed`, 6 not), project 2 has 2, project 14 has 2. `findCanonicalBoard` picks ONE, so gates/staffing configured on the losers are dead config — and for project 11 whether the Coordinator state machine or the simple single-hop path runs depends on which board wins canonical selection. Needs a board-dedupe/merge migration + a uniqueness constraint (or an explicit primary-board FK on `projects`).
- **The stall register makes the human-gate decision unavoidable rather than resolving it.** The manager's stall triage (0367) now diagnoses every non-moving ticket and escalates the ones it cannot fix — but `human_gate` and `capability_gap` are escalations BY DESIGN (the manager must not override a gate a human deliberately configured, nor conjure a capable agent). With `in_review.gate='human'` on all 10 boards and only 3 of 61 auto lanes staffed, the register will surface a large standing escalation backlog on first run. That is the honest reading of the two items above, not a new defect — but it means the template/staffing decisions are now blocking a visible queue rather than an invisible one, and should be made deliberately.
- **Ticket creation attribution is missing for the large majority of tickets: 722 of 821 (88%) have no `task.created` activity row at all**, so "who opened this — the AI Manager or a person?" is unanswerable for them and they audit as `origin: 'unknown'`. The `target_type` drift that hid the rest was fixed in this pass (103 rows were written as `'tasks'` vs 8 as `'task'`; the ledger now reads both and the MCP writer is canonicalized), but the writers that create tickets WITHOUT emitting any creation activity still need to funnel through one emitter — candidates: `QaFindingRouter`, `ValidationService`, `IncidentService`, `SecurityAuditService`, board-sync inbound, and `decomposeEpic` child fan-out.

- **Manager pass outcomes exist only as PROSE, so pass effectiveness can only be regex-parsed back out** *(found building the Manager diagnostics handover 2026-07-25)* — `finalizeManagerRunTask` (`api/src/application/manager/ManagerService.ts`) renders the full `ManagerRunSummary` into `tasks.description` ("Scored 0 · ranked 300 · assigned 0 · …") and stores nothing structured. The new `frontend/src/lib/managerDiagnostics.ts` has to `parsePassCounters()` that sentence to detect the load-bearing failure — a pass that COMPLETES and changes nothing — which means the detection silently degrades if the sentence is ever reworded, and no query can answer "how many passes actually scored anything this month?". Fix: persist the summary structurally (jsonb column on the run task, or a `manager_runs` row keyed by `run_task_id`) and read it on the overview. Unblocks exact pass-effectiveness findings, a pass-history chart, and dropping the parse.
- **A manifest sign-off slot auto-resolves an assignee nobody chose, and the ticket header never shows it** *(found fixing the "awaiting sign-off but nobody is assigned" report 2026-07-26)* — `TicketParticipantsService.resolveAssignee` falls back to the FIRST role-capable agent in the tenant when no `project_role_assignments` pin exists, so a ticket acquires up to ten required reviewers no operator ever staffed. Those slots gate completion and merge, but they appear only on the ticket's Sign-off & Accountability tab — the header/assignee column and the board card show nothing — so the ticket reads as unassigned while the manager correctly reports ten outstanding sign-offs. The manager feed and the diagnostics report now name the ownership per slot (this pass), but the SURFACE mismatch stands. Fix: show the required-role roster on the ticket header/card (count + unstaffed badge), or require an explicit pin before a required slot is created.
- **`syncStates` preserves `in_progress` forever, so a slot that later loses its assignee lies about being worked** *(same pass)* — the state recompute deliberately keeps `in_progress` (it is evidence of a run attribution it cannot re-derive), but it does so even when `assigneeRef` has since become null. Such a slot is neither dispatchable nor reported as `unstaffed` by its state column. The new `classifySignoffOwnership` classifies by `assigneeRef` rather than by state, so no gate is wrong today, but any consumer still keyed on the state column sees a slot that nobody owns and nobody is working. Fix: drop `in_progress` back to `unstaffed` when the assignee is gone, keeping the run evidence in `evidence`.
- **Coverage remediation never writes a ticket OWNER, so `unowned` cannot fall** *(same pass)* — the AUDIT+REMEDIATE stage calls `coordinateTicket`, which rewinds the lane and asks the lane gate to dispatch the missing role; it never touches `tasks.assignedUserId`/`assignedAgentRef`. On a project where the lane gate cannot dispatch (unstaffed lanes), the stage's only lasting effect is moving tickets backwards, pass after pass. The journal line no longer *claims* staffing it did not do (fixed this pass), but a flagged ticket still needs the `assign` path to actually gain an owner. Fix: have the remediation stage run `assignTicketOwner` before/alongside `coordinateTicket` when the ticket is unowned.
- **Nothing on the wire says WHY a scheduled manager sweep skipped a project** *(same pass)* — a stale `lastRunAt` can mean the KV work-gate (`cronWorkSignal.ts`, see [[neon-cost-under-5-dollars]]) decided there was no work, the token gate skipped the tenant, the cron itself failed, or every pass died before stamping. They are indistinguishable from the overview payload, so the diagnostics report can only name the symptom (`last_run_stale`). Fix: record the last sweep DECISION per project (ran/skipped + reason + at) and ship it on `GET /api/manager/:projectId` beside `autonomy`. Unblocks "the cron is not reaching this project" being answered rather than inferred.
- **Ceremonies.** Server-trusted presence (DO doesn't re-verify JWT per frame); server-authoritative `changed` broadcast (client-driven today); persistent session history + retro/poker integration; dnd-kit affordances (native HTML5 drag has no ghost/keyboard-a11y); auto-dispatch-on-Complete is client-driven (server-side from `POST /sessions/:id/complete`); turn timing has no pause/resume; power-meter cap falls back to a soft constant.
- **Personality** shows on `/settings` + Workforce card (human **and** agent, via the shared `PersonalitySummary`) + task-assignee hovercards. Not yet on a dedicated person profile page / brain @-mentions (drop the shared `AssigneeHovercard` / `AssigneePersonalityInline` in once those surfaces mount the `AssigneeProfilesProvider`).

### 🧑‍💼 Founder operations — the canvas can ANALYSE a company and cannot RUN one

> *Identified 2026-08-14 in one review that read the canvas through a founder's use cases (co-founder,
> CRM, pipeline, lead gen, contracts, billing, investors) and then swept the `DOMAIN_MANIFEST` domains
> for the same jobs. The founder vocabulary — the 21 kinds in `FOUNDER_OBJECT_KINDS` — is genuinely

>
> **Two of the original ten are closed** (see DONE.md): date-bearing triggers with a server sweep, and
> the `/integrations` ledger overclaim. The rest are broken out below in BUILD ORDER, because they are
> not eight independent features — six of them are downstream of two foundations.

#### Build order, and why

```
FO-A  the counterparty          ─┬─→  FO-C money  ──→  FO-D ownership
FO-B  collection & signature    ─┘    FO-E raising ──→  FO-G legal

FO-F  one pipeline — independent of all of it
```

**FO-A and FO-B are the foundations and nothing downstream is worth starting first.** Every money,
raising and legal item either needs to name a counterparty (FO-A) or needs a human outside the
workspace to agree to something (FO-B). Building any of them first means inventing a private answer to
one of those two questions that the next item then has to unpick. The two foundations are independent
of each other and can run in parallel.

**Neither foundation invents a table**, which is why they are first rather than merely urgent.
`party_roles` (kernel) already carries `role: 'customer' | 'vendor' | 'investor' | 'partner' | …` with
one row per (tenant, party kind, party ref, role) and a unique index proving it — so the counterparty
EXISTS and the canvas simply cannot see it. And `packages/creation-canvas-contract/src/people.ts`
already declares the entire form and signature contract, argued distinction by distinction, with zero
implementations. Both foundations are wiring, not modelling.

### Data-scientist canvas review — Idea → Real still has no compute and no monitor *(2026-08-13; re-validated 2026-08-18 — the model / runComparison / labelSet / prompt kinds have since shipped and were removed)*

> The canvas is strong at IDEA and DATA (`dataset`/`datasource` snapshot-vs-live, `dataContract` → `checksFromContract()`, `erd`, `metric`, `lineage` + `staleDerivatives`, and a genuinely relational client-side query engine: filter → derive → timeGrain → groupBy → aggregate → having → sort → window → limit). - **There is no cell to compute in — `code` is text with no execution.** *(DS canvas review, 2026-08-13)* `MUTABLE_FIELDS.code = ['content', 'code', 'language', 'path']` — no `stdout`, no `result`, no `figure`, no `executedAt`, and no kernel anywhere in `creation-canvas/`. The type checker cannot see this — only `.toSQL()` can. Audit every remaining `sql\`\`` fragment that interpolates a column into a subquery; interpolate the **table** (`${tbl}.col`) instead.
- **Column-level reverse schema drift is still unchecked.** `check-schema-drift.mjs` now verifies both directions at TABLE level (a migrated table with no `pgTable()` fails CI). A migrated **column** missing from an existing Drizzle table is still invisible — which is exactly how `ide_agents` hid 9 columns and `freelancer_reviews` hid 2. A column-level reverse check needs the script's rename-tracking applied to the diff (a naive version reports ~32 false positives from the `claw_*` legacy renames).
- **Cross-tenant write, `POST /api/agent-hosts/:id/file-change`.** The insert stamps `tenantId` from the agent host but never validates that `taskId` belongs to that tenant — the FK to `tasks.id` only proves the task exists, so a host key for tenant A can attach file-change rows to tenant B's task. (`githubActionsRoutes` does the equivalent check explicitly.) Pre-existing; unchanged by the refactor.
- **Silent-degradation swallows (three, all pre-existing).** `loadProviderRow` (`tenantProviderKeyService`) catches every error, so a DB outage is indistinguishable from "tenant has no BYO credential" and the gateway falls to the operator pool with **no** `unresolvedReasons` entry — the one hole in the "a BYO degrade is never silent" invariant. `resolveCloudAgent` (`cloudAgentEngine`) collapses all errors to `DEFAULT`, silently downgrading a container-surface agent to `durable` and dropping its pinned `baseModel` (surfaces later as a spurious `coding_model_degraded`). `notify()` no longer hides the in-app insert failure (now `console.error` with kind+user) but still never signals the caller.
- **Probe/credential failure details reach the UI as server-generated ENGLISH.** `probeByoProvider` builds `detail` strings (`Stored credential could not be used (<reason>).`) server-side and `probeVerdict` in `ProviderKeysSettings.tsx` prefers `result.error` over the localized `diagnostic.state.*` copy, so a zh/es/fr/de operator reads English whenever a BYO account fails to resolve. The per-reason catalog keys already exist (incl. the new `unsupported-auth`); fixing = have the API return the reason CODE only and let the client compose the sentence. Pre-existing and systemic across every probe reason — recorded here rather than fixed inside the drag-to-reorder change.
- **Marketplace / freelance correctness residuals.** `jobRoutes`: `POST /proposals/:pid/accept` does 5 writes with no transaction AND never checks the job's current `status`, so an already-`filled` job can be accepted twice and mint a second engagement; `POST /:id/proposals` never checks `visibility`, so anyone with a UUID can bid on a `private` posting; `GET /` filters discipline/skill/q **in memory after `LIMIT 200`**; `/api/notifications` computes `unread` from a 100-row page. `gigMarketplaceRoutes`: `NaN` taskId reaches the query (and mints a `…:NaN` cache entry); re-publishing a ticket whose posting is `closed`/`filled` mints a second posting and orphans the first. `freelancerMessagingRoutes`: `getOrCreateConversation`'s untargeted `ON CONFLICT DO NOTHING` can yield `undefined` cast as a row → 500; the read watermark is stamped *after* the insert so a message arriving in between is marked read unseen; `POST /:id/read` returns `{ok:true}` on zero rows matched; `readSendPayload` silently drops attachments when `UPLOADS` is unbound (the declared 415 is unreachable). `freelancerRoutes`: `POST /me/resume`'s `canAutofill` reads `resume_extract`, which was never in the projection — that term has **always** been false.
- **Dead/loose surface.** `createFreelancerMessagingRoutes(_db)` and `createGigMarketplaceRoutes(_db)` take a `Db` neither uses (both build their own per handler) — drop the param and its `src/index.ts` argument. `taskFileChanges.executionId` is nullable in schema but its only writer always supplies a number. `workforceRoutes` `DELETE /agents/:id` cascades `artifact_assignments` for `bridges[0]` only; `POST /agents/:id/feedback` always returns 201 even on the DO-UPDATE path. `getOrSetCached` returns `Date` on a miss and ISO strings on a KV hit — a cache-shape asymmetry that predates this work and interacts with the timestamp item above.
