每个在生产环境中运行 AI 的团队都会撞上同一堵墙：**token 账单。**前沿模型按 token 计费，而大多数团队一遍又一遍地为同样的工作付费，因为两个*含义*相同的提示词，在字符串层面看起来并不一样。“总结这个 PR”与“给我一份这个拉取请求的摘要”，对精确匹配缓存来说就是未命中——每次都是一次完整的、计费的模型调用。

Builderforce.ai 的答案是一个**以嵌入向量为键的语义缓存**：当新的提示词是已回答过的提示词的*同义改写*时，它会复用之前的答案，因此对于语义上重复的工作，前沿模型永远不会被调用。

## 精确匹配缓存是不够的

传统的响应缓存以字面提示词字符串为键。只有*完全相同*的文本出现两次时才有帮助——在自然语言工作负载中，这种情况很少见。换个说法重写问题、加一个文件名、调换两句话的顺序，缓存就失效了。

语义缓存以**含义**为键。每个提示词都会被转换为一个嵌入向量；当新提示词的向量与已存储的某个向量足够接近（按余弦相似度）时，就算命中。同义改写会收敛到同一个缓存答案。这就是一个几乎从不触发的缓存，与一个能吸收大量重复工作的缓存之间的区别。

## 两层：免费的设备端，加上共享的网关层

Builderforce.ai 的缓存是两层的，并且跨界面共享：

- **L1——本地且免费。**使用设备端 SSM 嵌入的进程内余弦匹配。它在浏览器 IDE 中以及每个智能体内部运行。由于嵌入是在设备端计算的（没有嵌入 API 调用），L1 是真正免费的——检查缓存没有按次查询的成本。
- **L2——共享网关。**位于网关的 `lookup`/`store` 端点之后、以租户为范围、基于 KV 的一层。在 **Web 应用**中回答过的同义改写问题，可以被**智能体**复用，反之亦然。

这种跨界面共享是关键洞察。缓存命中不会被困在一个会话或一台设备里。当开发者在 IDE 中提出一个问题，这个答案之后可供自主智能体使用——一个租户的缓存命中会变成全平台的节省。

   │                                              miss

   ├─▶ L2 (gateway KV, tenant-scoped) ──────────── hit ──▶ reuse, no model call
   │                                                │

## 一个可移植的缓存，没有浏览器/Node 分叉

两层都由 `@builderforce/memory` 包中*同一个*可移植的 `SemanticCache` 驱动。嵌入器（设备端 SSM）和 L2 后端都是**注入**的，因此不存在会渐行渐远的独立浏览器版本和 Node 版本。浏览器 IDE 和无头智能体运行完全相同的缓存逻辑——只有依赖项不同。

这对正确性和成本同样重要：单一实现意味着缓存命中在任何地方行为一致，而且调整相似度阈值只有一个地方。
