# 你的全栈应用现在就在你构建它的浏览器标签页里运行

你描述一个应用：一个页面，背后一个 API，下面一个数据库。文件没问题，蓝图也没问题。然后你开始等待——等容器被调度、启动、安装、连通——才能知道这一切能不能一起工作。

这段等待不是小事。它是 *我做出了东西* 与 *我知道它能用* 之间的鸿沟，而其中的每一分钟，本可以用来测试想法，却用在了排队上。

这道鸿沟没有了。**Run 现在会在浏览器标签页内启动你的整个应用。**

## 按下 Run 时会启动什么

你项目的应用蓝图列出了它的服务。Node、Python 和 PHP 服务——Express 或 Next.js、FastAPI、Flask、Django、Laravel、Slim——都在标签页内运行，而数据库是在页面中运行的真正的 Postgres。它们彼此相连，实时预览在看板旁边打开。

没有容器需要启动或预配，运行也不消耗云端算力。安装依然会进行——npm、pip 和 composer 在第一个页面出现之前于标签页内运行——而首次 Run 会启动标签页内的运行时。

## 无论在哪里运行，Brain 的工作方式都一样

如果助手看不到内部，换个地方运行也没有意义。它看得到。同样的运行工具——读取日志、重启服务、捕获预览——无论应用运行在你的标签页还是容器中，都能使用。问 Brain 为什么结账页面返回错误，它会读取 API 的日志、修改处理函数、重启服务，并再次捕获页面。它不需要知道应用在哪里运行。

这很重要，因为快速运行只是快速循环的一半。另一半是能查看结果并据此行动的助手。

## 它在方法中的位置

Idea to Real 是一道弧线——**Idea → Make → Run → Measure**——以及其中的一个循环：[Read、Prove、Build](/blog/read-prove-build-the-inner-loop)。阅读和验证不花钱，所以决定是否构建是一个真正的决定。构建是成本开始的地方。

Run 是你做出的东西必须经受自身检验的阶段：页面能否访问 API，API 能否访问数据，整条路径是否做到了你所描述的？方法中的验证，价值取决于多快得到答案。冒烟测试、概念验证、试点：每一个都是一个问题，趁想法还热乎时去问才最有价值。

## 今天你可以做什么

- **按下 Run，在标签页内看到你的全栈应用运行**——前端、API 和数据库一起，无需启动或预配容器。
- **趁想法还热乎时验证它。** 运行就在你所在的标签页里启动，问题与答案之间没有排队。
- **放心尝试改动。** 运行不消耗云端算力，所以为排查 bug 重启十次与重启一次花费相同。
- **把循环交给 Brain。** 它读取日志、重启服务、捕获预览，与对待容器时完全一样。
- **让容器做它们擅长的事**——执行和部署——当应用准备好离开标签页时。
