## 工程师不是设计师——他们的简历也不该长得一样

大多数标着“创意”的简历模板，都把设计师和工程师混为一谈。不该这样。产品设计师的简历本身就是一件设计作品——克制、层次和工艺就是它要传达的信息。软件工程师的简历则更接近一份写得好的 README——它要传达的是：做出了什么、用了什么、规模多大、结果如何。

Dev Graphite 模板是专门为工程师打造的。技术栈常驻侧栏，招聘人员三秒钟就能确认是否匹配。项目与工作经历并列，而不是被降到页面底部。板块标签上的等宽字体点缀，传递出你熟悉工程师真正在意的那种视觉语言（README、终端、代码），同时又不会让正文难以阅读。

## Dev Graphite：围绕技术栈打造的双栏版式

Dev Graphite 采用双栏打印版式。侧栏依次放置：技能（你的技术栈）、项目、证书和语言。主栏放置工作经历、教育经历及其他内容。

这种划分很重要。工程类招聘人员会先扫一眼技术栈。如果他们在招 Go 工程师，却在五秒内没在你的侧栏里看到 Go，这份简历就会被放进“不考虑”那一堆。把技术栈放在固定的视觉位置，意味着它永远不会被冗长的工作经历淹没。

主题以 slate-900 作为正文颜色，标题和板块标签用翡翠绿点缀——对终端美学的一次克制致敬，又不至于变成角色扮演。等宽字体、适中的密度、朴素的标题。最终效果，就像是为交付它的那个人写的一份用心的 README。

## 如何写技能侧栏

技能侧栏是工程师简历中被读得最多的部分。一定要把它写好。

**按类别分组。** “语言：Go、TypeScript、Python、Rust” / “基础设施：Kubernetes、Terraform、AWS、GCP” / “数据：Postgres、Kafka、ClickHouse、Snowflake”。分类能帮助招聘人员快速浏览；平铺的列表则会逼他们逐字阅读。

**按熟练程度排序，而不是按字母顺序。** 每个类别都以你愿意带进系统设计面试的技术打头，而不是只接触过一次的那些。

**完全不要写软技能。** 在工程师简历的技能侧栏里写“团队合作者”，读起来就是凑数。如果你有领导经验，就在工作要点里展示出来。

**不要罗列每一个工具。** 列出 40 项技术会让你显得不够专注。分成 3–4 个类别、共 12–18 项才是合适的样子。

## 如何写出不像工单的工程要点

工程师在简历上最常犯的错误，就是把要点写得像 Jira 工单——“使用 Y 库实现了 X 功能”——既没有背景，也没有规模和结果。

使用这样的结构：

**先写问题（1 行）。** “订单处理每次结账要访问 Postgres 800 次，把我们的吞吐量卡在约 40 RPS。”

**描述方案和取舍（1–2 行）。** “设计了一个基于 Redis 的直写缓存，并配有幂等的对账机制；选择最终一致性而非加锁，以把延迟控制在 50ms 以内。”

**量化结果（1 行）。** “把结账 RPS 从 40 提升到 600，把 p99 延迟从 1.4s 降到 180ms，并在假日季彻底消除了数据库这个瓶颈。”

三行，这条要点就值得在面试中展开聊了。而“实现了 Redis 缓存”则毫无存在感。

## 项目：把它们当作真正的经历

对工程师来说，业余项目往往比当前的工作更能说明问题。一位资深开发者如果发布过有分量的开源库、为热门开源项目做过贡献，或者构建并维护过一个副业产品，就是在展示日常工作可能用不到的技能。

Dev Graphite 在侧栏为项目留出了位置——这意味着它们一眼就能看到，而不是被埋在底部。每个项目写三行：它是什么、你做了什么、结果如何（下载量、Star 数、用户数，视项目而定）。

一个好的条目：“**ratelimiter-go**——实现令牌桶和滑动窗口算法的开源 Go 库。唯一维护者；3.2K GitHub Star，被 4 家有名有姓的公司用于生产环境。”

一个弱的条目：“个人项目——用 React 做了一个聊天应用。”如果你说不出任何关于规模、影响或技术决策的具体内容，就别写上去。

## 要避免的错误

**不要罗列你接触过的每一门语言。** 招聘人员看重深度。“精通 Go，熟悉 Python”胜过罗列 12 门语言。

**不要写“精通敏捷方法论”。** 每个工程师都这么写。换成一个具体的信号：“在 4 个团队中推动了季度 RFC 流程，把设计评审周期从 3 周缩短到 5 天。”

**不要漏掉 GitHub 链接。** 如果你的代码是公开的，就在简历顶部放上链接。如果不公开，就说明你在公司里交付过什么——哪怕是笼统的描述也有帮助。

**如果你有 5 年以上经验，就不要以学历开场。** 教育经历放到底部。以工作经历开场。

**不要用色彩鲜艳的主题。** 即便是“有创意”的工程团队，也期待一份克制的简历。把个性留给你的作品集网站。

## 常见问题

### 非工程类的技术岗位能用 Dev Graphite 吗？

能——这个版式同样很适合数据科学家、机器学习工程师、DevOps/SRE 和安全工程师。任何以技术栈为主要信号的人，都能从常驻侧栏中获益。对技术产品经理来说，Dev Graphite 也可以用，但 Standard 模板或 Trusted Taupe 可能更适合产品经理方向的面试。

### 我应该写上 LeetCode/算法竞赛的成绩吗？

只有当你瞄准的岗位把它当作主要信号时才写（FAANG 应届生岗位、量化交易、与算法竞赛相关的公司）。对大多数资深工程岗位来说，LeetCode 排名读起来带着初级色彩——那是面试准备，而不是职业成就。把这块空间留给已交付的项目。

### 对大公司招聘来说，等宽字体会不会太另类？

不会。Dev Graphite 只在板块标签和点缀处使用等宽字体——正文用的是可读性很高的系统等宽字体。我们在三家 FAANG 级公司的招聘 ATS 流程中测试过，简历每次都能被干净地解析。它传递的视觉信号是“这位候选人是写代码的”——这正是你想给人留下的印象。
