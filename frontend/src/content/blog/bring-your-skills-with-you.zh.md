你的团队里已经有人把"如何发布一次数据库结构变更"写了下来。它在 `.claude/skills/ship-a-schema-change/SKILL.md` 里，旁边还有一个运行守卫检查的脚本，Claude Code 每次都照着做。

直到今天，这份知识都止步于它所写入的那个工具。想把它带进 BuilderForce，你只能把说明粘贴到一个文本框里，丢掉那个脚本，然后祈祷没人只改了其中一份。原本行之有效的一套流程，变成了两套各自漂移的流程。

Skills 现在是一个**标准**，而 BuilderForce 支持它。一个 Skill 就是一个文件夹：一个说明它是什么、何时使用的 `SKILL.md`，加上它所引用的脚本和参考资料。Claude Code、Codex 以及越来越多的智能体工具读取的正是这种结构——开放的 [Agent Skills](https://agentskills.io) 格式——每个 BuilderForce 智能体在每个界面上也都读取它。

## 五十个 Skill，只花五十行的成本

这个标准最好的想法是：智能体不应随身携带它可能需要的每一套流程。它看到的是一个目录——每个 Skill 一行——只有当眼前的任务匹配时，才加载该 Skill 的说明。附带的参考资料也只在说明指向它时才加载。

## 它在方法中的位置

Skills 位于 [Read · Prove · Build](/blog/read-prove-build-the-inner-loop) 中的 **Build** 环节——花钱的那一环。Read 和 Prove 刻意保持低成本，好让"决定构建"成为一个真正的决定。一旦开始构建，智能体能做的最昂贵的事，就是重新摸索团队已经做过上百次的事：该运行哪个守卫，一个列需要哪条迁移轨道，一次发布如何进行。

Skill 就是这份知识，只写一次。把它做成标准文件夹，它才能随工作一起流动，而不是困在某一个工具里——于是你的工程师在编辑器里打磨的流程，就是云端运行在下一张工单上遵循的流程，也是看板助手在构建时遵循的流程。Build 依然是昂贵的环节；只是不再为同一个教训付两次钱。

## 今天你可以做什么

- **导入**来自 Claude Code、某个仓库的 `.agents/skills` 或同事 .zip 的技能文件夹——包括脚本和参考资料。
- 在浏览器中**编写** Skill，得到一个标准的 `SKILL.md`。
- 将任何工作区 Skill 或任何已发布的市场 Skill **下载**为可直接使用的文件夹。
- 从文件夹**发布** Skill 到市场，让列表与安装者拿到的内容永远一致。
- 在云端运行、网页/VS Code/Rovr 中的 Brain、创建画布和 Studio 中**使用**每个 Skill——在自托管智能体上也一样，分配的 Skills 现在会落到磁盘。
