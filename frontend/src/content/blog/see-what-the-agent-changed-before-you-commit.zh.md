你让它修个问题。智能体开始工作、边做边讲解、完成，然后说：*文件改动已在本地完成——你需要手动提交并推送。*

然后呢？

改动是真实的，此刻就在你的磁盘上。而在这个版本之前，BuilderForce 里没有任何地方提到这一点。聊天里显示的是一个已完成的轮次。上方的工单栏显示一个进行中的任务。侧边栏的每一个区块——会话、聊天、项目与任务、收件箱——都照常运转，仿佛什么都没碰过文件系统。这次编辑唯一的痕迹，是对话记录里一句你只能选择相信的话；而通往代码的唯一途径，是你自己留意到 VS Code 自带的源代码管理视图，再凭记忆把它和那段对话对应起来。

对于一个以“智能体所做的工作都可供你检查”为全部前提的工具来说，这实在说不过去。

**BuilderForce 侧边栏中的“更改”区块。** 每个被改动的文件占一行，标明它发生了什么变化、位于哪个仓库。点击一行，编辑器自带的 diff 查看器就会打开它——不是 diff 的渲染图，而是真正的 diff，带有它全部的导航功能，以及直接编辑右侧内容的能力。该区块带有一个数字徽标，而 VS Code 会把视图徽标汇总到活动栏图标上，所以即使面板收起，待处理的工作依然清晰可见。

**聊天中的待处理更改栏**，就在工单栏正上方。它显示数量，可展开为文件列表，并通过同一个命令打开同样的 diff。当工作树干净时，它什么都不渲染——没有空状态，也没有占位条。一个永远挂在屏幕上的信号，就算不上信号。

两者由同一次读取提供数据，这一点比听上去更重要。

## 在事件之间保持准确

智能体的文件工具直接写入磁盘。它们不经过编辑器的文档 API，所以写入完成时，VS Code 里不会触发任何事件。一个礼貌地等待通知的界面，会一直告诉你没有待处理的内容，而此时就在它底下，三个文件刚刚发生了改变。

## 它在方法论中的位置

这是**验证**，而且值得把原因说准确。

[读取、验证、构建](/blog/read-prove-build-the-inner-loop)是内循环，而验证是那个低成本的动作，用来判断构建是否正确。一个编辑了你代码的智能体，其实是提出了一个主张：*这个改动实现了你要求的事情*。对话记录里的一句话不是证据。diff 才是证据——而如果 diff 远在另一个工具里、要点三下才能看到，现实中大多数人会直接接受这个主张而不去核实，这恰恰就是一个智能体工作流不再可审查、沦为要么全盘信任、要么干脆放弃的过程。

让证据与主张只有一次点击之遥，并不是图个方便。它是让这个循环保持闭合的关键。

它还处在[构想 → 构建 → 运营 → 衡量](/blog/idea-make-run-measure-menu-as-methodology)这条弧线上一个特定的接缝处：离开**构建**的交接点。代码已经存在，但还没有被提交、运行或衡量。这次交接，是本地编辑器界面过去完全没有任何呈现的地方——看板跟踪着工单，云端通道会提交每一次写入并在运行结束时打开拉取请求，而在本地，工作一旦从对话变成文件，就彻底隐形了。现在，它看得见了。

## 今天你就能用它做什么

- **无需询问就知道某一轮改动了代码**——数量同时显示在聊天和活动栏图标上，并在工具成功的那一刻出现，而不是等到某个东西恰好触发刷新。
- **以真正的 diff 阅读每一处改动**，使用编辑器自带的查看器，从产生它的对话出发只需一次点击。
- **看清哪些内容已经暂存**，让“提交”不再有任何意外。
- **满意之后交给 Brain**——“更改”区块的标题操作会打开一个预置好的聊天，用于审阅 diff、在分支上提交、推送并打开拉取请求，并会先与你确认分支名和标题。

当时，这个版本刻意**没有**做一件事：给智能体一个属于它自己的提交或推送动作。本地智能体能对你的工作树和远程仓库做什么，是一个治理决策——用分支还是 `main`、推送是否需要审批关卡、“打开 PR 并请求评审”是否应该取代“推送”成为默认的收尾方式——在做出决策之前就发布这些动作，就等于发布一个会自作主张推送到受保护分支的智能体。评审路径被有意放在了前面。

**此后，这个决策已经做出，相应的动作也已发布**：`git_commit`（在工单分支上提交，并点名它改动的确切文件）、`git_push`（除非你批准这个具体行为，否则拒绝推送基础分支）以及 `open_pull_request`。关于这个治理问题是如何回答的，请参阅[从编辑器直接发布](/blog/ship-from-the-editor-commit-branch-pull-request)。
