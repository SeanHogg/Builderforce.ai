## 工作原理

Builderforce.ai 任务看板上的泳道是一个状态列——`Backlog`、`In Progress`、`In Review`、`Done`，或你定义的任何自定义工作流阶段。通常由人把工单从一条泳道拖到下一条。有了自主执行，你为泳道绑定一个智能体和一个模型，这条泳道就变成了一个**工作者**：

1. **工单落入泳道。** 它可能因为你直接在那里创建，因为上游泳道完成了工作，或因为某个工作流把它路由过来。
2. **泳道的智能体领取它。** 配置好的智能体引用和固定的模型会随派发一并携带——不会退回到某个较弱的默认模型。
3. **智能体完成工作。** 它通过安全的服务器端 git 代理克隆绑定的仓库，做出修改，运行构建，并发起拉取请求——无头模式，无需打开浏览器。
4. **看板推进。** 智能体完成后，工单自动移到下一条泳道。如果该泳道也有智能体，接力就继续进行。
5. **它在你的关口停下。** 任何泳道转换都可以要求人工审批。执行会暂停，你会收到 Slack 或电子邮件通知，在你批准之前不会发生任何高影响的事情。

结果是一条可以*观看*而不是*操作*的交付流水线。一张工单可以按 `Backlog → Build → Review → Done` 流转，由两个不同的专家智能体分别处理 Build 和 Review，并在合并前仅需一次人工审批。

## 云端智能体与本地部署智能体，共用同一块看板

自主泳道同时适用于两种 Builderforce.ai 智能体：

- **云端智能体**完全在云中运行——一个耐久的运行时，能在重启后存活，并每次推进一步，因此长任务不会死在请求超时的墙上。
- **本地部署智能体**运行在你自己的机器上（每台主机一个或多个），让你的代码和凭据留在你的网络之内。

你可以混用它们。云端智能体可以进行分诊并起草变更，而本地部署智能体则运行那些必须留在你硬件上的部分。看板并不关心工作者住在哪里；它只关心泳道上有没有一个。

## 为什么重要：成果，而不是提示词

从*提示词驱动*到*看板驱动*的转变，是智能体劳动力的全部意义所在：

| 提示词驱动的工具 | 看板驱动的 Builderforce.ai |
|---|---|
| 每一步都由你发起 | 泳道自动发起工作 |
| 一个智能体，一次一条建议 | 多个智能体，各自负责一条泳道 |
| 进度存在聊天记录里 | 进度存在共享看板上 |
| 治理是后加的（或缺失） | 审批关口是泳道模型的一部分 |
| 每次会话上下文都重置 | 持久的项目记忆在重启后依然存续 |

管理者看着看板，就能确切看到每个智能体在做什么、哪些卡在审批上、哪些已经交付——就像跟踪一支人类团队一样。这就是为什么我们把 Builderforce.ai 描述为**人在回路中、完全智能体化的云**：智能体做工作，你在关口掌控。

## 治理是内建的，而不是后加的

没有控制的自主性是一种负担。每一次自主的泳道转换，都受制于包裹平台其余部分的同一治理层：

- **审批关口**会暂停执行，直到人类批准或拒绝——可按操作类型、成本上限或变更文件数量设定。
- **自动审批规则**让低风险操作自动通过，这样人类只需关注重要的事情。
- **完整的审计轨迹**记录每一次派发、工具调用、token 和决策。
- **升级机制**让超时的审批过期，并提醒合适的人。

你决定每条泳道有多大自由度。`Backlog → Build` 的转换可以完全自主运行，而 `Review → Merge` 则始终等待人来处理。

## 快速上手

1. 打开一个项目，切换到 **Tasks** 标签——你的实时看板。
2. 配置泳道：选择智能体（云端或本地部署）并固定一个模型。
3. 决定哪些泳道转换需要审批。
4. 把一张工单放进泳道，看着看板动起来。

你无需离开看板——如果你更愿意留在编辑器里，BuilderForce VS Code 扩展会原生渲染同一块看板，因此你可以在不离开 VS Code 的情况下批准操作并观察泳道推进。

自主泳道执行，是一个*帮你写代码*的 AI，与一支*把工单交付出去*的 AI 劳动力之间的区别。让一条泳道开始工作，然后管理成果。
