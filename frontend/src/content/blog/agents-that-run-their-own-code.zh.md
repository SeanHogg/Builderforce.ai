会写代码的智能体和能交付代码的智能体之间，有一个不太显眼的区别。前者交给你一堆文件；后者交给你的文件能编译通过、测试能跑通、依赖真的装得上。

直到今天，画布上和 Studio 工作区里的 Brain 还属于前者。它能写后端、写页面、写测试文件，而且写得不错，却没有办法运行其中任何一个。于是检查的活就落到了你身上：打开预览，找到类型错误，把它粘回对话里，等它修好，然后再来一遍。智能体很自信，证明却要你来做。

这次补上的正是这块空白。Brain 现在会运行它自己写的代码。

## Brain 现在能做什么

让 Brain 修改一个构建，它就能对这个构建运行真正的命令：用 `npm install` 添加依赖包，用 `npm test` 运行测试，用 `npm run build` 打包，用 `tsc` 做类型检查。这些就是你会在终端里敲的那些命令。某个命令失败时，它会读取输出，修正自己刚写的代码，然后再运行一次。等它告诉你改好了的时候，这次修改已经通过了检查。

这一切都在你的浏览器里运行。Builderforce 有自己的浏览器内运行时 [BuilderForce WebContainers](/blog/builderforce-webcontainers-open-source)，实时预览本来就跑在它上面。Brain 的命令也在同一个运行时里、针对同一批文件、在同一个标签页中执行。没有任何东西被发送到构建服务器，也不需要准备任何机器。命令改动过的文件，比如更新后的 `package.json` 或生成的源文件，会保存回你的项目；安装的依赖包和构建产物则留在该在的地方，不会混进你的源代码。

## 在你自己的电脑上快速作答

同一个版本也让简单的问题回答得更快、更私密。如果你的电脑上已经有 Chrome 内置模型，那么一轮普通的对话（Brain 只是在交流、不使用工具）会直接在你的设备上作答。如果这个模型不可用或答不了，这一轮会转给 Builderforce 的云端模型，你不会察觉任何变化。

## 它在方法中的位置

在 Builderforce 上工作遵循一条弧线：**构想 → 制作 → 运行 → 衡量**，每一幕都有相同的内循环：[阅读、证明、构建](/blog/read-prove-build-the-inner-loop)。这次发布把这个循环交到了 Brain 自己手里，正好位于**制作**转向**运行**的那一刻。

- **阅读**是起点。在修改一个构建之前，Brain 会先读它的文件，现在还会读自己命令的真实输出，因此它依据的是代码实际做了什么，而不是它希望代码做什么。
- **证明**是新增的部分。一次修改写完并不算完成；能安装、能构建、通过类型检查并通过测试，才算完成。这是最小的证明，和**概念验证**是同一种直觉：先把有风险的部分单独拎出来，对照一个标准检验，再在它之上继续构建。
- **构建**建立在这份证明之上。下一次修改从一个已知可用的构建开始，所以十次修改的一轮工作，结束时不会留下十个未知数。
- **运行**留在你看得见的地方：实时预览会以真实的设备宽度运行 Brain 刚刚证明过的应用。
- **衡量**得到更好的输入。到达这里的每一次修改都已经通过了自己的检查，所以你衡量的是想法本身，而不是一个拼写错误。

## 你今天就能做的事

- **提一个功能需求，拿到一个能构建的功能。** Brain 会在告诉你完成之前先跑构建和类型检查。
- **让它补上测试，并让测试通过。** 它会编写测试、运行测试，并修改代码直到测试通过。
- **按名字添加依赖包。** Brain 会在浏览器里替你执行安装并更新 `package.json`。
- **无需账号就能试用。** 访客看板使用同一个运行时，因为它只在你的浏览器里运行，别无他处。
- **在本地获得快速回答。** 如果你的电脑上有 Chrome 内置模型，简单的对话会在本地私密作答。

打开一个看板，描述你想要的应用，看着 Brain 在把工作交给你之前先证明它。
