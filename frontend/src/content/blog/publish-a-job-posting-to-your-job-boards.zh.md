每一次招聘都始于同一个动作：把这个职位展示在人们面前。在画布上，这恰恰是职位发布卡片唯一做不到的动作。

你可以用 Brain 起草职位需求，为它在工作区里建立一条真实的记录，针对它给一叠简历排序，并统计它收到的申请数量。卡片上甚至有一个记录发布位置的字段——`distribution`，每个招聘网站一行，带有状态、日期和链接。但没有任何东西往里写。工作区早已内置了面向 Greenhouse、Lever、Ashby、Indeed、LinkedIn Jobs 和招聘站点 feed 的招聘网站连接器，每一个都能创建职位发布，可就是没有任何东西为真实的职位需求去调用它们。于是“发布这个职位”最终只落成了一份文档，而申请量为零，因为没人被告知这个职位存在。

## “已上线”意味着网站这样说了

难点不在于调用六个 API，而在于决定怎样才算已发布。

HTTP 200 并不等于发布。Ashby 对每个请求都回答 200，并把拒绝信息放在响应体内。像 Indeed 这样的 GraphQL API 也是如此。LinkedIn 的职位发布端点是一个批量调用，每个职位的失败都藏在一个成功的响应之中。一个只相信状态码的系统，会告诉招聘人员某个职位在三个网站上线了，而实际上只在一个网站上线，去找的候选人什么也找不到。

所以，只有当某个网站的回复带有它自己为该职位分配的 id 时，它才会显示为**已上线**。其他任何情况都显示为**失败**，并附上该网站给出的原因。这条规则同样由数据库强制执行：没有网站 id 的“已确认”记录无法写入。

这一决定也是所有网站都由同一份代码处理的原因。每个连接器已经以数据的形式声明了每个输入在请求中的位置。现在它还声明了职位 id 和链接在响应中返回的位置：Lever 是 `data.id` 和 `data.urls.show`，Ashby 是 `results.id`，LinkedIn 是第一个元素的 id，并以响应头作为后备。新增一个网站，只是目录中多一个条目，而不是发布器里多一个分支；无法告诉我们其 id 的网站，绝不会被作为目标提供。

## 按网站统计申请人

职位的申请量原本就已按来源拆分。现在，该职位发出的每个网站，都以自己的名称出现在这个拆分中，并带有真实的计数。这包括零，因为“Indeed：两周后为 0”恰恰就是告诉你某个网站没起作用的数字。把它省略掉，读起来会像是“从未在那里发布过”。卡片上的网站行也带有相同的计数。

匹配是精确的。一条被记录为来自某个网站的申请，带有该网站的键，而职位自身的 id 会随之传到每个网站，让网站可以把它回传回来。申请上手输入的自由文本来源（比如“LinkedIn”）会保持原样，而不会被猜测归到 LinkedIn Jobs 网站名下，因为错误归因的申请人，会对这个拆分存在的唯一目的给出错误的答案。

## 你今天就能用它做什么

- **一次把职位发布到多个招聘网站**，从职位发布卡片，或者通过询问 Brain。
- **查看它实际在哪里上线**，当网站提供链接时，附上指向各网站职位列表的链接。
- **重试失败的网站**，在修复其给出的原因之后，而不会在已经成功的地方重复发布。
- **按申请人对比各招聘网站**，包括那些至今还没带来任何人的网站。
- **触达长尾渠道**，借助招聘站点 feed，每个没有合作伙伴 API 的聚合平台都会读取它。
