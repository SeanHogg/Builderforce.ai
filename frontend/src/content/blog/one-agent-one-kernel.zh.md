在 VS Code 里和代理开始一段对话，聊到一半换到浏览器里接着聊——在那里回答你的代理拥有同样的工具、遵守同样的规则和防护，它的工作也经过同样的验证。在一个地方修好的问题，在所有地方都修好了。

前提是，回答你的东西在哪里都是同一个。很长一段时间里并不是这样：编辑器、网页应用、Rovr 和本地部署的渠道各有自己的运行循环、各有自己的工具接线，运气不好的时候，同一个问题会得到四个不同的答案。

现在，**界面会变，代理不会变。** 一个执行核心运行着每一段对话，在每一个宿主上。

## 一个循环，而不是四个

现在只有一个代理循环。旧的、按界面划分的运行循环已经没有了——是删除，不是弃用——所以不存在藏在某个开关后面、等着悄悄跑偏的第二个引擎。无论这一轮对话是从编辑器的聊天栏、网页画布、浏览器里的 Rovr，还是 Slack 这样的渠道发起，这一个循环都是它唯一能走的路径。

## 为什么这很重要

- **对话可以带着走。** 在桌面上开始，在浏览器里继续——代理的状态、记忆和工具权限都跟着你走，因为它们从来就不绑定在某个界面上。
- **修好就是修好。** 工具策略加固一次，每个宿主都会继承。“在编辑器里能用、在网页上不行”这一类缺陷已经不复存在。
- **只需验证一样东西。** 一个一致性预言机（conformance oracle）针对这一个引擎重放参考场景，所以“代理是否正确”只有一个答案，而不是四个。

## 它在方法中的位置

这是让 **Make（构建）** 阶段变得可信：负责构建的代理，在你遇见它的每个地方都是同一个。能跨界面带着走的可靠性，正是这条弧线的其余部分——Run（运行）、Measure（衡量）——得以立足的基础。

## 今天你就能用它做什么

在两个界面里打开同一段对话，看它们给出一致的结果。聊到一半，把对话从编辑器移到浏览器。内核是不变的那一个；界面就是你此刻所在的地方。
