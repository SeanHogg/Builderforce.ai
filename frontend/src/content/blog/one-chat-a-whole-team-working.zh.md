给一个代理一份包含八条工作线的规格说明，然后看看会发生什么：它一条一条地做。先做迁移，再做 API 路由，再做调度器，再做界面，最后写测试。每一步都要等上一步完成，哪怕它们彼此毫无关系。一下午的活，就要花掉整整一下午。

人不是这样工作的。负责人把工作拆开，把每一块交给专人负责，盯着所有人的进展，最后再把一切汇总起来。以前，代理只能*装作*在这样做。它可以启动一个助手，但随后就停下来等助手做完。助手有步数上限。你看不到它，也没法跟它说话。在某些云端运行环境里，它根本就不存在。

这就是缺口：**一个聊天一次只能做一件事，本可以并行的工作只能排队等候。**

## 交出去，继续干

现在，你聊天里的代理可以把部分工作交给**子代理**。它们立即启动，并排工作。启动它们的代理不会停下来。它继续规划、继续编写自己留下的那部分，或者再启动更多子代理。

看不见的团队就没法管理。每个正在工作的子代理都会出现在聊天的**代理**列表中，和受邀的代理并列，显示它的编号以及是谁启动了它。对话下方的实时栏会显示每个子代理此刻正在做什么。

## 它在方法中的位置

Builderforce 的工作沿着一条弧线前进——**想法 → 制作 → 运行 → 衡量**——每一幕都走同一个内循环：[阅读、验证、构建](/blog/read-prove-build-the-inner-loop)。

子代理属于**制作**阶段，而它改变最大的是**构建**这一步。构建是花费最大的环节，也是单线工作伤害最大的地方：每一块都要等上一块。拆分之后，构建的成本取决于最长的那一块，而不是所有块的总和。

它们也让**验证**保持诚实。子代理没有 shell，也没有 git。它们只改自己的文件，然后回报。验证仍由负责人完成：构建合并后的改动，运行测试，修复各块之间互相造成的问题，然后才提交。工作是并行的，结论只有一个。

## 你今天就能做的事

- **把一份多部分的规格说明交给一个聊天**，让它的各条工作线并行推进。
- **按名字把工作交给你自己的代理**，或者让聊天为一个没人合适的任务配备一名 Developer。
- **查看并指挥每个子代理**：用 `@名字` 或 `#工单` 重新指示它，停止一个，或者全部停止。
- **在云端以同样方式工作**，每个子代理都是一次独立的运行，有自己的记录。

将 VS Code 中的 BuilderForce 扩展更新到 2026.10.22 或更高版本即可使用以上全部功能。
