两套词汇，各自都没错，却并排摆着，中间什么都没有。

招聘掌管漏斗：发布职位、筛选、面试、发 offer。人事掌管雇佣关系：员工、生命周期、入职、绩效评估。两边的页头都用一句话描述了二者之间的过渡——*“offer 变成员工”*。可谁也没有真正去执行它。产品里有两条相隔一步之遥便戛然而止的漏斗，这道缝隙靠人把字段从一个屏幕复制到另一个屏幕来填补。

## 交接，以及它的三种拒绝

```bf-figure
{
  "kind": "flow",
  "title": "Offer → 员工，一步完成",
  "steps": [
    { "label": "已签署的 offer", "note": "触发条件。不是口头答应，也不是草稿状态的 offer——必须是已签署的。", "hue": "reach" },
    { "label": "把事实带过去", "note": "职位、地点和用工基础来自职位发布；技能和证据来自候选人；入职日期来自 offer。不凭空编造任何内容。", "hue": "run" },
    { "label": "员工 + 生命周期", "note": "雇佣记录与入职计划一并创建，并关联回它们所源自的 offer。", "hue": "measure" }
  ],
  "caption": "这次交接不属于任何一套词汇。把它放进招聘方的词汇，就等于让招聘去撰写人事记录；放进人事方的词汇，则会让人事去读取招聘方的字段。它只在两者之间声明一次。"
}
```

它会在三种情况下拒绝执行，而每一种拒绝都是有用的那种：

- **offer 尚未签署。** 以未签署的 offer 为起点的雇佣记录，记录的是一件并未发生的事。
- **没有关联到具体的人。** 背后没有候选人的员工，正是重复人员记录的诞生地。
- **没有入职日期。** 没有锚点日期的生命周期根本没有截止日期，其中每一项入职任务都会悄无声息地没有日期。

它宁可抛出错误，也不会创建一对只填了一半的记录，因为半个录用比没有录用更糟——你要等到三周后薪资部门问“这个人是谁”时才会发现。

与此同时，现在每一份打过分的简历都会关联到一位真实的候选人。给不属于任何人的文档打分，得出的数字没法据以行动；而一堆这样的分数，也拼不出一份谁都能用的候选名单。

## 读取你已经在用的人事系统

这个目录可以把职位需求向外发布，也可以把一次发薪读回来，却完全没有办法读取你**自己的**员工。于是员工、角色分配、产能，以及交付视图中显示的每一个人数，全靠手工录入——而“到底谁在这里工作”这件事，存放在这个产品够不着的系统里。
