一周前，[看清智能体改了什么](/blog/see-what-the-agent-changed-before-you-commit)补上了缺口的一半。另一半是有意留着的，那篇文章也说得很明白：没有提交动作，也没有推送动作——因为本地智能体能对你的远程仓库做什么，是一个治理决策；在做出决策之前就把这些动作放出来，等于交给你一个会自作主张推送到受保护分支的智能体。

现在，决策已经做出。下面是它最终落地的样子。

## 之前是什么样子

这里值得说得具体一点，因为问题并不是“少了一个功能”。实际情况更糟：智能体被*告知*它可以发布，而它其实做不到。

编辑器角色设定的最后一句话大意是：*用 `run_command` 执行 git——在用户想要发布时提交、推送并打开 PR。* 只有建议，背后却没有任何工具。于是，当有人让智能体提交一行 CSS 修复并推送时，事情是这样发生的：

第四步才是值得停下来细想的部分。工作树里有三个被修改的文件，智能体只动了其中一个。`git add -A` 分不清这其中的区别，一个从未被要求说明的智能体同样分不清。

## 答案的形态

三个工具，而且安全的那条路就是随手可达的那条路。

```bf-figure
{
  "kind": "flow",
  "title": "默认路径",
  "steps": [
    { "label": "git_commit", "note": "写明它改动的确切路径，以及要放到哪个工单分支——分支会替你创建", "hue": "make" },
    { "label": "git_push", "note": "推送该分支，首次推送时自动设置上游", "hue": "run" },
    { "label": "open_pull_request", "note": "针对基础分支打开 PR，并可按名字请求评审人", "hue": "prove" },
    { "label": "由人来阅读 diff", "note": "这正是重点所在", "hue": "measure" }
  ],
  "caption": "作为工作流，这里没有任何新东西。新的是：这条路现在是智能体阻力最小的路径，而不再是你只能寄望它主动选择的那条。"
}
```

**`git_commit` 要求你列出路径。** 这不是走形式。你的工作树是和你共享的——就是那个坐在屏幕前、思路正进行到一半、还开着两个改到一半的文件的你。`git add -A` 会把那些文件扫进智能体的提交、扫进智能体的拉取请求，于是你那些不相干的工作就出现在了别人的评审里。一个说不出自己改了哪些文件的智能体，根本没有资格提交，所以这个工具不允许它避而不答。

**在基础分支上提交会被拒绝。** 传入 `branch`，它就会切换到那个工单分支，不存在则自动创建。如果你正在 `main` 上却没有传这个参数，你得到的是一条指明解决办法的错误，而不是一句 git fatal。

**`open_pull_request`** 会先推送尚无上游的分支，然后通过你自己的 `gh` 登录打开 PR——无需把任何令牌传给智能体，因为这台机器本来就有一个。如果没有安装 `gh`，它会告诉你分支已经提交并推送，并把分支名交给你——这就是“工具失败了”与“工作丢失了”之间的区别。

## 推送 main 是一个明示的行为

你仍然可以这么做。只是它不会再意外发生，也不会因为智能体自作主张而发生。

```bf-figure
{
  "kind": "compare",
  "title": "“把这个推到 main”",
  "columns": [
    { "title": "之前", "hue": "bad", "items": ["没有工具——退回到原始 shell", "`git add -A` 把眼前的一切都暂存", "直接落到基础分支上", "审批提示写着：run: git add -A && git com…", "没有任何环节提议拉取请求，因为什么都做不到"] },
    { "title": "现在", "hue": "good", "items": ["智能体先提议走拉取请求，并说明理由", "只暂存它点名的路径", "除非设置了 `allowBaseBranch`，否则一律拒绝", "提示写着：推送到基础分支（main）——跳过拉取请求评审", "你批准这个具体的行为，或者不批准"] }
  ],
  "caption": "中间那一行是治理决策。第四行则让它成为真正的决策——一个你看不懂的审批，算不上审批。"
}
```

这些工具每一个都会改变状态，所以它们和 `write_file`、`delete_file` 走的是同一个审批关卡。那个关卡本来就在，它缺的是任何值得一读的内容。确认对话框里只写一个 `git_push`，对你真正需要权衡的那件事只字未提。*推送到基础分支（main）——跳过拉取请求评审*，则把一切都说清楚了。

它们还由一项新的 `git.write` 能力把关，而不是 `shell`。这听上去像是记账，其实不然：云端界面同样有 shell，而且它们早已通过一套完全不同的机制发布——在那里，一次写入**就是**一次提交，运行结束时会自行打开拉取请求。再给它们一条通往同一行为、却尚未实现的路径，只会暴露出运行时没有处理程序的工具，并在运行中途失败。一项能力，一个界面，每条通道只有一种发布方式。

## 底下那个不起眼的修复

智能体当初为什么会去找 `run_command`，这个原因值得点明，因为它代表的是一类 bug，而不是一次偶发事故。

工具目录大约有 440 个工具，每一轮大约只公布 64 个，按与你请求内容的词法相关性来挑选。`run_command` 与“commit the change and push to main”（提交改动并推送到 main）没有任何共同词干——于是恰恰在最需要它的那一轮，它被裁掉了。智能体读了自己的指令，去找指令里点名的工具，却怎么也找不到。

现在，全部九个 git 工具都与文件工具一起被无条件固定。用相关性在不同领域之间做取舍是合理的；用它来决定智能体能不能碰它身处的工作区，就不合理了。

## 它在方法论中的位置

这是[读取、验证、构建](/blog/read-prove-build-the-inner-loop)中的**构建**一步终于走到了它自己的终点，也是[构想 → 构建 → 运营 → 衡量](/blog/idea-make-run-measure-menu-as-methodology)这条弧线上**构建 → 运营**的交接。

上一个版本让这次交接变得*可见*：磁盘上已经有了代码，什么都还没提交，而你现在能看到它、读到每一处 diff。但可见不等于可通行。你能检查工作成果，却必须离开这个工具才能把它往前推——这意味着，这条弧线恰好在方法论本应无缝衔接的地方留了一道接缝，每一个本地改动都悄悄变成了某个人得记着去做的手动步骤。

真正让它闭合的，不是“智能体现在能推送了”，而是：离开构建的那条路默认通往**验证**——一个拉取请求、一份 diff、一位评审人——而不是跳过评审直接落进运营。提交到工单分支再打开 PR，比直接推到 `main` 恰好多一步，而那一步正是人去审视这次改动的那一步。让经过评审的路径成为默认，这就是全部的论点。

推送基础分支依然可用，因为有时候那样做确实是对的，而一套假装并非如此的方法论只会被人绕开。只是它现在要求你用一句话明确说出来，并给你一个清楚说明你正在批准什么的提示。

## 今天你就能用它做什么

- **先要一个改动，再要求把它发布出去**，拿回的是一个工单分支和一个拉取请求 URL——而不是一条你还得逐字审查的 shell 命令。
- **放心其中只有你的改动**，因为智能体必须点名那些文件。
- **说“推到 main”，得到的却是评审提议**——如果你确认自己就是这个意思，推送照样会执行。
- **按名字请求评审人**，就在智能体打开的拉取请求上。
- **在包含多个检出的文件夹里工作**，现在每个 git 工具都能应对：传入 `repo`，每个工具都会定位到正确的仓库。`git_sync_latest`、`git_undo` 和 `git_redo` 以前做不到这一点，会在工作区根目录直接失败，且没有任何信息说明原因。
