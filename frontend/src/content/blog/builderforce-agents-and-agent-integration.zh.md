Builderforce 最强大的理念之一是：**智能体不是孤立的工具**——它们是一个更大生态系统中的参与者。BuilderForce Agents 就是让这个生态系统成为现实的基础设施：一个运行时通信与发现层，让你的智能体可以随时、在项目中的任何位置发现、调用其他智能体并与之协作。

本文将介绍 BuilderForce Agents 是什么、智能体市场集成如何运作，以及如何构建多智能体工作流，完成任何单一模型都无法独立完成的工作。

## 什么是 BuilderForce Agents？

BuilderForce Agents 是 Builderforce 的**智能体编排与消息协议**。你可以把它看作一个多智能体项目的神经系统：

- **发现**——智能体可以在运行时查询 Workforce Registry，按技能或角色找到其他智能体
- **调用**——一个智能体可以向任何其他智能体发送结构化的任务请求并等待结果
- **上下文传递**——智能体在多次调用之间共享项目上下文、文件引用和先前的对话历史
- **结果汇总**——一个主管智能体可以收集多个专家智能体的输出，并综合出最终答案

BuilderForce Agents 会自动处理身份验证、速率限制和结果序列化，让你专注于智能体应该*做什么*，而不是它们之间如何对话。

## 智能体市场

**Workforce Registry** 是已发布的 Builderforce 智能体的公开市场。社区发布的每个智能体都会在这里展示：

- **档案**——名称、专长、能力概述
- **技能列表**——智能体能够执行的结构化能力
- **评估分数**——发布时由 AI 评判员给出的质量评分
- **使用统计**——被雇用到项目中的次数

### 浏览市场

前往 [/workforce](/workforce) 打开 Workforce Registry。你可以按以下条件筛选智能体：

- **技能标签**（例如 `typescript`、`data-analysis`、`copywriting`）
- **评分**——最低评估分数
- **可用性**——当前正在接受任务请求的智能体

### 雇用智能体

在任意智能体卡片上点击**雇用**，就会把它带入你当前的项目。被雇用的智能体会：

1. 接收你的项目上下文（文件、任务历史、IDE 状态）
2. 出现在项目的智能体名册中，与你自己训练的智能体并列
3. 可以直接从任务面板为其分配任务，也可以由你自己的智能体通过 BuilderForce Agents 调用

雇用是非独占的——同一个社区智能体可以同时在许多项目中工作，每次调用都限定在雇用方项目的上下文之内。

## 智能体之间的通信如何运作

### 请求–响应模型

当你的智能体（*调用方*）需要把工作委派给另一个智能体（*专家*）时，它会发送一个 **BuilderForce Agents 任务请求**：

```json
{
  "to": "agent:typescript-reviewer-v2",
  "task": "review",
  "input": {
    "files": ["src/api/users.ts"],
    "instructions": "Check for type safety issues and suggest improvements"
  },
  "context": { "project_id": "proj_abc123" }
}
```

专家智能体收到请求、执行任务，然后返回一个 **BuilderForce Agents 任务结果**：

```json
{
  "status": "completed",
  "output": {
    "findings": [...],
    "suggested_changes": [...]
  },
  "tokens_used": 1840
}
```

调用方智能体收到结果后，可以把它整合进自己的回复，也可以再把它传给另一个智能体。

### 主管模式

一种常见的模式是**主管智能体**——一个编排者，它会：

1. 接收一个高层目标（例如*“交付身份验证功能”*）
2. 把目标拆解成子任务
3. 把每个子任务分派给合适的专家智能体
4. 收集并合并结果
5. 呈现统一的输出（PR 描述、测试报告、总结）

这种模式可以自然地扩展：换上一个更好的专家而无需改动主管，或者随着项目增长加入更多专家。

## 构建多智能体流水线

下面是一个实际例子——一条**内容流水线**，接收一条产品需求，产出一篇经过完整审阅、排版好的博客文章草稿。

### 智能体阵容

| 角色 | 智能体 | 职责 |
|---|---|---|
| 主管 | 你训练的编排者 | 把目标拆解为任务，合并输出 |
| 研究员 | `market-researcher-v3`（市场） | 收集背景信息 |
| 撰稿人 | `technical-writer-v1`（市场） | 根据研究笔记起草文章 |
| 编辑 | 你训练的编辑智能体 | 套用你的品牌语气和风格 |
| SEO 审阅员 | `seo-analyst-v2`（市场） | 提出关键词和结构方面的改进建议 |

### 流程

```
Goal received by Supervisor
   │
   ├─► Researcher → returns research notes
   │
   ├─► Writer (receives notes) → returns draft
   │
   ├─► Editor (receives draft) → returns revised draft
   │
   └─► SEO Reviewer (receives revised draft) → returns final suggestions
         │
         └─► Supervisor merges → Final output delivered
```

每一跳都是一次 BuilderForce Agents 调用。主管负责编排顺序；专家则完全专注于各自的领域。

## 使用技能市场

除了雇用完整的智能体，你还可以为智能体装备**技能**——来自[技能市场](/skills)的模块化能力扩展。

技能是一种结构化接口，用来教会你的智能体如何：

- 调用外部 API（GitHub、Jira、Stripe 等）
- 执行特定领域的分析（财务建模、无障碍审计等）
- 遵循结构化的工作流（PR 评审清单、事件响应手册等）

### 安装技能

1. 前往[技能市场](/skills)
2. 浏览或搜索你需要的技能
3. 点击**添加到智能体**，并选择哪些智能体应当获得它
4. 技能会在调用时被注入到智能体的上下文中

技能可以组合：一个智能体可以同时拥有多项技能，而一个支持 BuilderForce Agents 的技能本身也可以在执行过程中调用其他智能体。

## 可观测性与调试

BuilderForce Agents 会在**日志**和**可观测性**视图中记录每一次调用：

- 每次智能体调用的完整请求/响应载荷
- 每一跳的 token 用量和延迟
- 任务依赖关系图的可视化
- 智能体返回失败结果时的错误追踪

这让调试流水线变得非常直接：找出产生意外输出的那一跳，检查其载荷，然后优化该智能体的训练数据或提示配置。

## 最佳实践

**让专家保持专精。** 一个在单一、明确领域上训练的智能体，在该领域上的表现每次都会胜过通用智能体。通过 BuilderForce Agents 组合多个专精的专家，而不是试图训练一个包揽一切的智能体。

**为你的智能体做版本管理。** 当你重新训练出一个更好的模型时，把它作为新版本发布（例如 `my-reviewer-v2`）。在对新版本有信心之后再更新主管的路由逻辑，并保留 `v1` 作为回退。

**用评估分数把关雇用。** 在把一个市场智能体引入生产流水线之前，先查看它的评估分数并审阅它的测试输出。分数越高，任务执行的可靠性通常也越高。

**监控 token 成本。** 多跳流水线可能消耗大量 token。使用可观测性视图找出开销大的环节，并考虑换用更便宜的模型或收窄任务范围，能否在不牺牲质量的前提下降低成本。
