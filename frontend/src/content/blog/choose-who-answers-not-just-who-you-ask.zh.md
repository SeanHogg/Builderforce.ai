与一支智能体团队对话，每一轮都有两个问题。**我在和谁说话？** 以及 **谁在回答我？**

第一个问题早就有了控件。输入框里的「发送给」或一次 @ 提及，会把消息发给受邀的智能体或队友，而不是 Brain。第二个问题只存在于网页端。在那里，「身份」可以让 Brain 以网站构建者、移动端开发者或 Evermind 教师的身份回答，或以分配给你工作区的某个智能体来回答。而在大部分构建工作发生的 VS Code 里，你每次得到的都是默认助手。

这个缺口现在补上了。

## 身份选择，来到你的编辑器

编辑器的输入框现在并排提供与网页端相同的两个控件。

「身份」提供三类回答者：

- **默认 Brain** —— 你的编程助手，以你打开的工作区为依据。
- **某个角色** —— 网站、移动端、网页 + 移动端、Evermind、微调或语音。这些正是网页构建器所用的角色：移动端角色会用 44 点的点击区域和安全区编写 React Native，Evermind 角色负责教学而不是训练。
- **分配给 Brain 的智能体** —— 任意一个。Brain 会以该智能体的角色和语气回答，并使用该智能体自己的模型，除非你在 `/` 菜单里固定了模型。

## 角色叠加在你的工作区之上

有一点在编辑器里刻意有所不同。在网页端，角色*就是* Brain 的全部指令，因为没有别的需要描述。而在编辑器里，Brain 已经知道真实的情况：打开的是哪个文件夹、你正在看哪个文件、哪些工具可以操作你的代码仓库。一个承诺「预览已上线」的网站角色，不能覆盖其中任何一点。

所以在 VS Code 里，角色是叠加上去的。

## 向整个看板提问，会显示问题发给了谁

不 @ 任何人就向画布提问，看板上的每个智能体都会回答。回答一直带着作者，问题却没有：在聊天页面打开时，它看起来像是没有发给任何特定的人。

## 它在方法中的位置

[读、证、建](/blog/read-prove-build-the-inner-loop) 这个循环关心的是*谁来做这件事*，而不只是做什么。研读市场与证明定价是不同的工作，二者又都不同于构建出售它的那个界面。此前，编辑器让你选择问谁，却不让你选择谁来回答，于是循环中的每一步都经过同一个通才。

选择谁来回答，在 **Make** 阶段最为重要——那是[弧线](/blog/idea-to-real-the-operating-methodology)中「构建」成为昂贵环节的阶段。「一个助手」和「移动端开发者」之间的差别，会在这里以返工的形式出现：从未达到 44 点的点击区域、默认存在悬停效果的布局。在写下第一行之前选好角色，比事后再改便宜得多。在弧线更早的阶段，让 Brain 以你分配给战略的智能体身份回答，就能让「读」和「证」来自你本来就会去请教的那个角色。

## 今天你就可以这样用

- **在编辑器里以专家身份运行一轮** —— 网站、移动端、网页 + 移动端、Evermind、微调或语音 —— 无需离开你的文件。
- **以你的某个智能体身份回答**，使用该智能体自己的模型，就在你平时输入的那个输入框里。
- **把消息发给队友或受邀的智能体**，网页端和 VS Code 用的是同一个「发送给」控件。
- **看到问题发给了所有哪些人**，当你一次向整个看板提问时。
