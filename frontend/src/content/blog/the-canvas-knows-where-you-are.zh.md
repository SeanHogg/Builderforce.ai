“衡量”过去会在一块什么都没上线的看板上打开。

你随时都能点它。画布会切换标签页，给出“洞察”，然后等待一个从未部署过的应用传来数据。“触达”也一样：有地方写发布帖，却没有任何可以把人带去的地址。画布顶部的阶段（构想、构建、运营、衡量、触达）只决定你能看到哪些标签页，仅此而已。它们从不查看看板上有什么。而且阶段是整个浏览器共用的一个设置：把一个画布切到“衡量”，其他所有画布也跟着切过去。

一个判断不了某个阶段是否可行的阶段选择器，只是一个菜单。它背后的方法说得更多：没有运行起来的东西无法衡量，想法还没写下来就不该动手构建。现在，画布也懂这一点了。

## 就绪状态，直接从看板读出

现在每个阶段都会读取它所在的看板。它不依赖某个设置，也不需要你填写清单，而是看工作已经留下的对象：

- **一张想法卡片**，表示“构想”已完成；
- **一个应用**，也就是一起运行的代码卡片，表示“构建”已完成；
- **一个带地址的部署**，表示“运营”已完成；
- **一个指标**，表示“衡量”已完成。

阶段条里的每个阶段会显示三种状态之一：自身产出已存在时显示对勾，需要先完成更早的阶段时显示锁，可以开始工作时什么都不显示。每个画布都有自己的阶段。如果你没有选过，画布会打开在**你还没完成的第一个阶段**，所以一块已经上线的看板不会把你送回“构想”。

## 看板把当前阶段推到前面

更大的变化在于看板本身的读法。每个阶段都有它关心的对象类型。“构想”有想法、访谈、实验、用户画像和风险；“构建”有规格、页面、原型和代码；“运营”有部署、版本和故障；“衡量”有 KPI、仪表板、图表和实验；“触达”有帖子、营销活动、受众和上架信息。这些卡片会带上阶段颜色的描边，其余的则退到后面。

画布的其他部分也跟随同一个阶段。命令栏会高亮你当前所在阶段的分组。起点会先给出这个阶段的三个建议，比如“衡量”里的“定义关键指标”、“触达”里的“起草发布帖”，然后才是完整目录。在房间里，当前阶段的工作站会亮起，并排到列表最前面。阶段未就绪时，房间里会立起一块指示牌工作站，写明缺少什么：*需要一个已上线的应用*。

## 两个新地方：运营与发布上线

有两个阶段一直没有属于自己的地方。

**运营**从“运营”阶段开始出现。它展示这个画布正在运行的一切：每个部署的环境、版本、地址和部署时间；看板上的版本发布；以及应用是否已上线。如果你构建了应用却还没部署，“运营”会直接说明，并为你打开应用的发布面板。网站一上线，它的部署及地址就会记录到看板上，“运营”阶段即告完成。

**发布上线**在“触达”阶段出现。证明想法、发布看板、上架销售、告诉大家，过去是四扇分开的门。“发布上线”把它们按这个顺序排在同一页上，因为这就是它们应该发生的顺序。

**洞察**从“衡量”开始，现在会先显示*此画布*：这块看板上定义的指标，落后于目标的排在最前，然后才是从其他地方固定过来的数字。看板上还没有指标时，它会提供让 Brain 定义一个的选项。

也有一样东西往回挪了。**应用现在从“构建”开始。** 在“构想”阶段，你是在检验有没有人想要这个东西。为此做的原型是看板上的一张实验卡片，而不是在想法还没验证之前就去构建的应用。

## 它在方法中的位置

这套方法叫 [Idea to Real](/blog/idea-to-real-the-operating-methodology)：构想、构建、运营、衡量，然后是触达。现在每个阶段都有一样东西必须先出现在看板上，下一个阶段才能开展工作；每个阶段也都会留下自己的产出。

```bf-figure
{
  "kind": "flow",
  "title": "每个阶段在看板上留下什么，下一个阶段需要什么",
  "steps": [
    { "label": "构想", "note": "解读想法，用低成本的方式证明它。留下一张想法卡片。视图：对话、看板、想法、房间。", "hue": "idea" },
    { "label": "构建", "note": "只构建证明值得构建的东西。需要一个想法，留下一个应用。新增“应用”。", "hue": "make" },
    { "label": "运营", "note": "把它放到真实的地方。需要一个应用，留下一个带地址的部署。新增“运营”。", "hue": "run" },
    { "label": "衡量", "note": "为证明里的那个数字打分。需要已上线的东西，留下一个指标。新增“洞察”。", "hue": "measure", "tag": "闭环在这里完成" },
    { "label": "触达", "note": "把它带给用户。需要已上线的东西，没有衡量时会提醒你。新增“发布上线”。", "hue": "reach" }
  ],
  "caption": "每个阶段都保留上一个阶段的全部视图，并加上自己的。后面的阶段从不会拿走任何工具。"
}
```

**构想**是[解读与证明](/blog/read-prove-build-the-inner-loop)发生的地方，两者都不花钱。画布在这里提供“想法”和“房间”，暂不提供“应用”，因为构建是代价高的一步，而方法希望它是一个经过思考的决定。

**构建**就是 Build。它需要看板上有一个想法；如果没有，路径卡片上唯一的一步就是“让 Brain 记录它”。

**运营**是草图变成一个有地址的东西的时刻。“运营”视图就是你查看它的地方。

**衡量**是闭环完成的地方。每个证明都带着一个可能让项目叫停的数字，而这个数字会[在这里打分](/blog/grade-the-proof-and-close-the-loop)。这就是“衡量”需要已上线内容的原因：一个没人能访问的应用，它的指标什么也衡量不了。

**触达**同样需要已上线的东西，并且还会*建议*你先定一个指标。没有指标它也允许你发布，但会提醒你：不衡量就去触达用户，等于闭着眼睛花钱。

这些都不会挡住你。每个阶段都能打开，每个视图都能使用。区别在于，画布现在知道看板上有什么，所以它能如实告诉你缺什么，并主动提出帮你完成下一步。

## 现在就能做的事

- **打开任何一个画布，直接落在你还没完成的下一步**，而不是上一个画布停留的地方。
- **点开一个你还没准备好的阶段**，得到最短的补齐路线，一键让 Brain 完成第一步。
- **透过阶段来读看板**：重要的卡片走到前面，其余的变淡，直到你关闭阶段聚焦。
- **在“运营”里看到正在运行的东西**：部署、版本，以及应用是否已上线，全都在你构建它的那块看板上。
- **在一个地方发布上线**：证明它、发布它、销售它、告诉大家，按这个顺序。

看板一直都是工作的记录。现在，它还会告诉你身处哪个阶段、接下来该做什么。
