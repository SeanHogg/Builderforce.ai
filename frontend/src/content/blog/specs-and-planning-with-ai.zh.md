大多数 AI 编程工具都从代码开始。它们假定你已经知道要构建什么。Builderforce 不这么认为。

最好的工程工作始于清晰的思考：问题是什么，解决方案在架构上是什么样子，以及要实现它需要哪些相互独立的工作单元。Builderforce 为每个阶段都提供了 AI 辅助工具，并用一份结构化的**规格（spec）**把你的思考一路带到执行任务的智能体手中。

![规划栈逐层收窄：从构想到 PRD，到架构规格，到 JSON 任务列表，再到可执行的智能体任务](/blog/specs-planning.svg)

---

## 规划栈

Builderforce 把规划组织成四个层级，每一层都为下一层提供输入：

```
Idea / goal (free text)
    │
    ▼
PRD (Product Requirements Document)  ◄── AI-assisted in Brainstorm
    │
    ▼
Architecture Spec                    ◄── AI-assisted in Brainstorm
    │
    ▼
Task list (JSON)                     ◄── AI-generated from spec
    │
    ▼
Executable tasks                     ──► Agent execution on BuilderForce Agents
```

规格就是把这四个层级集中存放在一处的容器。

## 从头脑风暴开始

[/brainstorm](/brainstorm) 是构思环境——一个专为产品思考（而不是编写代码）打造的 AI 辅助聊天界面。

打开头脑风暴，从一个目标开始：

> “我想构建一个功能，让用户可以把他们的项目活动导出为一份 PDF 报告。”

AI 助手会帮你：

- **打磨目标**——界定范围、挑战假设、找出边界情况
- **起草 PRD**——用户故事、验收标准、非功能性需求、不在范围内的事项
- **生成架构规格**——组件拆分、数据模型变更、API 设计、迁移注意事项

当你对结果满意时，点击**保存为规格**，即可创建一条关联到你项目的规格记录。

---

## 规格记录

规格位于 [/tasks](/tasks) → **规格**标签页。每份规格都有一个状态生命周期：

```
draft → reviewed → approved → in_progress → done
```

规格中存储：

| 字段 | 内容 |
|---|---|
| **目标** | 一句话说明这份规格要实现什么 |
| **PRD** | 完整的产品需求文档（Markdown） |
| **架构规格** | 技术设计文档（Markdown） |
| **任务列表** | 可直接放上看板的任务 JSON 数组 |
| **状态** | 在审批工作流中所处的当前阶段 |
| **关联的 agentHost** | 由哪个 BuilderForce Agents 实例来执行它 |
| **关联的项目** | 这份规格所属的项目 |

## 生成任务列表

PRD 和架构规格写好之后，Builderforce（或规格编辑器中的 AI 助手）就可以生成**任务列表**——对实现这份规格所需的每一项工作进行结构化拆分。

一条任务列表条目看起来是这样的：

```json
{
  "title": "Add PDF export endpoint to the API",
  "description": "Implement POST /api/projects/:id/export/pdf that streams a generated PDF using Puppeteer",
  "priority": "medium",
  "persona": "coder",
  "dependsOn": ["Add PDF template component"]
}
```

任务列表在规格编辑器中进行审阅。你可以添加、删除和重新排序任务，调整优先级，并分配角色（persona，即由哪个 BuilderForce Agents 智能体角色来处理每项任务）。

---

## 推送到任务看板

当规格处于 `approved` 状态时，点击**创建任务**，把任务列表推送到[任务](/tasks)看板。任务列表中的每个条目都会成为待办列表中的一条任务记录。

从这里开始，任务就走正常的任务生命周期——可以被分诊、排定优先级、分配给特定的 agentHost，并提交执行。规格始终与每项任务保持关联，因此你随时都能把任何任务追溯回最初的 PRD。

## 规格工作流

当你把一份规格提交执行（而不是把它转换成一个个单独的任务）时，Builderforce 会创建一个**规格工作流**——一个把整份规格视为一个工作单元的 BuilderForce Agents 编排。

`planning` 类型的规格工作流会依次运行：

1. **规划者**——读取规格目标和 PRD，产出一份详细的执行计划
2. **架构师**——审阅架构规格，产出实现说明
3. **编码者**——根据计划实现第一轮变更
4. **评审者**——对照规格的验收标准评审代码

每一步执行时都会出现在[工作流](/workflows)门户中。你可以实时观看智能体一步步完成这份规格。

## 围绕规格协作

规格是共享文档——任何有权访问该项目的团队成员都可以阅读、评论和编辑规格。头脑风暴的聊天记录会与规格一起保存，因此决策背后的推理始终可见。

对于会影响生产系统的规格，在批准之前先为它添加一位**评审者**。评审者会收到通知，他们的批准会把规格从 `reviewed` 推进到 `approved`。这是工作开始之前一道轻量级的人工关卡——与智能体工作过程中触发的执行级审批关卡相互独立。

## 与源代码管理集成

当一份规格的任务完成、并创建了拉取请求后，你可以把这个 PR 关联回规格：

1. 打开产出该 PR 的任务
2. 把 GitHub PR 的 URL 粘贴到 **PR URL** 字段中
3. PR 合并后，规格的状态会自动更新

如果你已经配置了 GitHub 源代码管理集成（设置 → 源代码管理），BuilderForce Agents 就能自动创建并关联 PR，省去手动这一步。

## 治理与约束

规格的架构文档也是记录**项目治理**的合适位置——即你的智能体在这个项目中工作时必须遵守的规则。治理文档会作为分配上下文的一部分同步到 agentHost 的 `.builderforce/context.yaml`，因此智能体会在启动时加载它们，并在整个执行过程中遵守。

治理示例：

- “所有数据库变更都必须包含一个迁移文件”
- “禁止直接写入 `users` 表——请使用 UserService”
- “每个 PR 都必须包含新功能的测试”
- “永远不要使用 `eval()` 或 `Function()` 构造函数”

具备相关技能的智能体会自然地理解这些约束，并在无需进一步提示的情况下加以遵守。

## 最佳实践

**先写 PRD，再写架构规格。** 人们很容易直接跳到“怎么构建”——但一份清晰的 PRD 会迫使你先回答“我们在解决什么问题”。从清晰的问题陈述出发做出的架构决策，出错的可能性要小得多。

**让任务保持小而原子化。** 一项需要熟练的人类工程师花 4 小时完成的任务，对智能体来说正好合适。更大的任务往往会产出铺得很开的实现，难以评审，也难以回滚。

**在任务列表中使用角色。** 为同一个功能同时安排一个 `coder` 任务和一个 `reviewer` 任务，可以确保实现和评审都会发生——而不是只做其中之一。规格的任务列表正是落实这条纪律的地方。

**批准之前先审阅架构规格。** 智能体非常擅长实现你所描述的东西。如果架构规格是错的，实现就会忠实地把这个错误复制出来。
