Builderforce.ai 所构建的一切，底下都是同一句话：

> **任何人提出一个需求，智能体系统就去解决它。**

这句话听起来很简单，直到你注意到“需求”可以有多少种形态。一位团队负责人希望审阅团队的 SOP，并提出一套更精简的流程。一位开发者希望用公司的专有数据训练一个智能体，并部署一个处理客服来电的定制智能体。一位工程师希望同一个智能体可以在 IDE 中、在桌面上或在云端运行——由他们来选，而不是由平台来定。一位经理希望画出一个工作流、一组流程图，并把这些步骤嵌入一个会执行它们的智能体。

四个不同的人，四种不同的需求，四种不同的*模态*——文字描述、数据集、流程图、角色设定。然而动词每一次都完全相同：**把这个需求变成一个在合适界面上运行的智能体。**

这个共同的动词，就是整个产品。我们称之为**编译原语**——而从这个版本起，它不再是一张挂在墙上的示意图，而是一条你可以直接调用、正在运行的流水线。

![编译原语：任何模态的需求都会被编译成一个 AgentSpec，并部署到任意界面](/blog/compile-primitive-spine.svg)

## 需求的形态

仔细看这四个例子，真正在变化的只有*输入模态*和*输出界面*：

| 人们说…… | 模态 | 变成…… | 界面 |
|---|---|---|---|
| “审阅我们的 SOP，提出更精简的流程。” | 诊断结论 | 一个可运行的改进流程 | 工作流 |
| “用我们的文档训练，接听客服来电。” | 数据集 / 专有数据 | 一个有依据的定制智能体 | 云端 / 桌面 |
| “就在我的编辑器里运行我的智能体。” | （已有智能体） | 同一个智能体，换个地方运行 | IDE |
| “这是流程图——执行这些步骤。” | 流程图 | 一个运行这些步骤的智能体 | 云端 / 本地部署 |

中间的一切——智能体的身份、它使用的模型、塑造其行为方式的角色设定、它调取的知识、约束它的策略、它遵循的步骤——每一次都是*同一类东西*。那就是一份智能体的规格说明。所以平台只有唯一的一种：**AgentSpec**。

## 编译原语

两个纯函数，中间是一个规范化的产物：

```
   NEED  ──▶  compile(need, modality)  ──▶  AgentSpec  ──▶  deploy(AgentSpec, surface)  ──▶  running agent
```

- **`compile`** 是一个*模态编译器*注册表——纯文字描述、数据集（加上你的专有文档）、流程图、角色设定、诊断结论和策略包各有一个。每个编译器都把自己那一类需求降级成同一个 `AgentSpec`。这是整个平台中唯一需要分辨文字、图表和数据集的地方。
- **`deploy`** 是一个*界面*注册表——IDE、桌面、云端持久化、云端容器和工作流步骤。它接收一个完成的 `AgentSpec`，通过一个共享的依赖注入注册表解析出正确的引擎，并为该界面找到正确的传输方式，然后——通过 `deployAndDispatch`——在早已存在的基础设施上真正启动运行。

两者之间是 `AgentSpec`：身份、模型、编译后的角色设定、调取的记忆、策略关卡，以及（当需求是一个流程时）有序的步骤。多种形态编译*进来*；部署到多种界面*出去*；中间只有一份规格。两个函数都是真实的代码——`compile()` 和 `deploy()` 位于 API 中，`AgentSpec` 及其唯一的规范化降级位于共享的 `agent-tools` 包中，再由一个轻薄的 HTTP 入口（`POST /api/compile`、`POST /api/compile/run`）把整条流水线暴露出来。

这个原语的威力在于，四种需求不再是四个产品。

![四个现有入口被重新安置为 compile() 适配器，合并成同一个 AgentSpec](/blog/compile-four-doors.svg)

“用我们的数据训练”和“画一张流程图”是两个 **compile** 适配器，它们合并到同一份规格中——所以你可以拥有一张流程图，*加上*一个训练好的模型，*加上*一个角色设定，*加上*一套治理策略，而它依然是一个智能体。这里的合并是字面意义上的：每个适配器输出它所了解的那一部分规格，平台再把它们折叠成一份。“在我的 IDE 里运行”和“在云端运行”是两个 **deploy** 目标——所以你训练的那个智能体，就是在你编辑器里运行的那个智能体，无需二次构建。

## 自然语言入口

平台过去缺失的模态，恰恰是最有人味的那一种：**自然语言。**“一个能分诊账单工单、并根据我们的帮助中心文档回答退款问题的智能体”——这样的需求过去无处可去。现在它在 [`/compile`](/compile) 有了入口：你用文字写下需求，一个提取器把它降级成一个 `AgentSpec`（身份、技能、自动路由的模型），`deploy()` 解析出它将在哪里运行，而——如果你按下*编译并运行*——平台会用编译好的系统提示，通过网关驱动真正的第一轮对话。提出一个需求；看着智能体作答。

当需求承载的是*步骤*而不是对话时——一张流程图，或者一次诊断提出的改进流程——`compile & run` 就不会去聊天。它会实例化一个真正的工作流：编译出的步骤会变成 `workflow_tasks`，由现有的认领与中继机制来执行。同一个 `POST /api/compile/run` 调用对任何客户端开放，所以这个入口是一个端点，而不只是一个页面。

## 为什么一根主干如此重要

当角色设定、记忆和策略存在于*规格之上*，而不是某个入口内部时，它们会自动抵达每一个界面。

![角色设定、记忆和策略存在于 AgentSpec 之上，并以完全相同的方式抵达每一个界面](/blog/compile-governance-everywhere.svg)

一个角色设定的温度参数会改变智能体的行为，无论它是作为工作流步骤运行，还是作为云端智能体运行。你用来训练的专有文档，无论智能体在哪里执行，都会在推理时被调取——甚至包括一次通过模型 ID 调用该智能体的标准 OpenAI-SDK 请求。

而治理关卡是*强制执行*的，而不只是一句建议。同一个编译好的关卡，会在每个引擎的工具接缝处被评估——持久化的云端循环、本地部署的运行器，以及编辑器内的 IDE 循环——都通过同一个共享的 `evaluatePolicyGate` 决策来完成。`block` 会拒绝调用该工具，并让智能体另寻他路；`require-approval` 会暂停运行、询问人类，并在对方答复后继续。只需在 `shell` 工具上编写一次 `block`，它在你编辑器里拦住 shell 的方式，就和它在云端某个节拍上拦住 shell 的方式完全一样——因为关卡跟着智能体走，而不是跟着它运行的地方走。这正是把策略放在规格上、而不是放在某个入口内部的全部意义：不可能出现某条规则在一个界面生效、在另一个界面失效的情况，因为只有一条规则，也只有一个检查它的地方。

这就是平台与一堆功能之间的区别。一堆功能里有一个训练工具、一个工作流构建器、一个角色设定编辑器和一个运行时，每个都对“智能体是什么”有自己私下的理解。而一个平台对“智能体是什么”只有一种理解，并允许你从任何方向抵达它，再把它送到任何界面上。

## 今天你就能做什么

这不是一张白纸上的愿景，也不再是一个只完成了一部分的愿景——这根主干已经端到端地连通了：

- **用自然语言提出需求**，得到一个正在运行的智能体——`/compile` 和 `POST /api/compile/run`。
- **把任何模态编译成一个 `AgentSpec`**——文字描述、附带你已导入专有文档的数据集、手绘的流程图、编译好的角色设定、诊断结论或策略包——并把它们**叠加**成一个智能体。
- **部署*并调度*这一份规格。** `deploy()` 为任何界面解析引擎、传输方式和运行输入；`deployAndDispatch()` 随后*启动*它——带步骤的规格变成一个实时工作流，云端规格变成一个正在运行的云端智能体，其治理关卡已随载荷一并下发。
- **把诊断变成行动**——一条成熟度诊断结论会被编译成一个有序、可运行的改进流程，而不是一份静态报告。
- **为标准 OpenAI 调用提供依据**——在标准的 `/v1/chat/completions` 端点上，用 `builderforce/workforce-<id>` 这个 ID 调用一个训练好的智能体，它就会针对该查询调取你导入的文档，与专用聊天路径获得的依据完全相同。
- **从规格出发实施治理**——一个只编写一次的 `block` 或 `require-approval` 关卡，会在云端、本地部署和 IDE 运行器的工具接缝处同样被强制执行：要么被拒绝，要么需经人工把关，而不只是一句指示。

编译原语是主干，原本已经立起来的东西，如今都立在了它之上。“提出一个需求，智能体系统就去解决它”不再是四扇各自独立的门——它是一扇门，能适配你的需求所呈现的任何形态，并通向你的工作所在的任何界面。

你用自己最自然的语言描述想要的结果，一支智能体劳动力——受治理、有依据、运行在你选择的界面上——就会去把它实现。这就是这个平台如今在做的事。
