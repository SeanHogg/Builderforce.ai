画布上有三样东西已经做好了，却无从触及。

**审批关卡。**让助手重新平衡一份预算，它会记录自己调整的每一个数字：谁动的、从什么改成什么、为什么。那些会离开系统、或日后会有人据以依赖的行为——发送营销活动、开具发票、批准预算——都被设了关卡，而且智能体无法批准自己的变更。这部分是正常工作的。不正常的是：没有一个地方能让人看到有什么在等待、并签字放行。于是记录越积越多，被设关卡的行为一直被阻塞，而“这个数字是谁批准的？”有了一个诚实的答案，却没人能据此采取行动。

**指标层。**画布上的指标是一个*定义*——数据源、过滤条件、聚合方式、目标、哪个方向算好——而不是某人手敲进图块里的一个数字，因此两个都叫“MRR”的图块不可能互相矛盾。能够一次性评估整组指标（包括派生比率）的引擎没有对应的卡片。每个定义都是正确的，但你无法把它们放在一起看。

**第三方小部件。**集成方可以通过 API 注册一个小部件、声明它的权限，并把它放到看板上。但浏览器里没有任何东西去挂载它。契约在两端都存在，中间的那块矩形却是空的。

现在这三样都落在了房间（room）里——画布唯一的空间化界面，紧挨着人和会话。

## 审批台

审批台显示有多少变更在等待，以及涉及什么。打开它，每个对象都会按审阅者需要的阅读方式列出其待处理的变动：字段、原值、新值、谁改的、何时改的，以及新值的来源。然后由你来选择。

- **批准**会以你的名义签署该对象上所有等待中的变更。签名会盖在变更所创建的同一批条目上，因此永远不会出现没有对应变更的批准。
- **批准并发送**（或*开具*、*发布*）仅在你的签名恰好满足该行为的关卡所需时才会出现。它先签署，再执行该行为，一键完成，顺序如此。
- **拒绝**记录的是有人看过并说了不。数字不会被悄悄回滚，因为那会是第二次无归属的变更。该行为保持被阻塞，直到有人做出一个他们愿意签字的变更。

## 指标看板

一旦会话定义了某个指标，房间里就会立起一块看板。看板上的每个指标一起被评估——基于数据集的普通聚合，以及像毛利率或净收入留存率这样通过其组成指标得出的派生比率——因此图块之间不会出现漂移。

它首先以洞察的形式呈现，其次才是图块。落后于目标的指标排在前面。无法计算的指标会说明原因，而绝不显示零，因为针对缺失成本项计算出的毛利率会显示为 100%，这是仪表板可能给出的最危险的错误答案。每个数字都附带它的证据：它是由多少行数据算出的，或者一个派生数字依赖于多少个指标。带时间粒度的指标附有趋势线。

## 它在方法论中的位置

这套方法是一条弧线：**Idea → Make → Run → Measure**。在其内部，[Read → Prove → Build](/blog/read-prove-build-the-inner-loop) 是你从一个想法跨向做出成品的方式。这个循环在 *Measure* 闭合，在这里你承诺的数字会与实际发生的情况核对。这三个工位位于这条弧线上原本无处落脚的两端：

- **指标看板就是 Measure**——某个证明所承诺的终止条件，读取自每个图块和报告所使用的同一套定义。
- **审批台是 Build 与 Run 之间的枢纽。**智能体所构建的东西，只有在一位具名的人签字放行之后，才会成为业务所依赖的东西。
- **小部件把你自己的工具带进 Run**，并且是受隔离的，这样运营看板就能使用你的团队已在使用的系统。

房间中的教学功能——面向班级和学员群体——也将以同样的方式到来，作为同一个房间里的工位。
