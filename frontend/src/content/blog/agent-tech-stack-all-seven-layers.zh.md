每一篇“AI 智能体技术栈”科普文都画着同一张图：七个层级，每层各司其职，每层也都是智能体可能出故障的地方。基础模型抢走了所有头条；而它下面的六层，才真正决定这套东西能否在生产环境里跑得起来。

问题在于，那张图的标准版本其实是一张*购物清单*。选一家模型厂商。接上 LangGraph。加一个记忆库。搭一个向量数据库。接入工具。买一套可观测性 SaaS。容器化，然后部署。七个层级，七家厂商，七种故障模式，外加一大堆把接缝粘在一起的胶水代码。

Builderforce.ai 同样是这七个层级——但被构建为**一个平台**。本文逐层走一遍，把每一层对应到 Builderforce.ai 实际运行的东西上，并坦白交代我们刚刚加固的两个层级：如何从“有”走到“超越”。

![七层智能体技术栈，由 Builderforce.ai 端到端实现](/blog/agent-stack-seven-layers.svg)

## 记分卡

| # | 层级 | 参考设计 | Builderforce.ai |
|---|-------|----------------------|-----------------|
| 1 | 基础模型 | 选定一家厂商 | 受支持的多厂商网关，路由 + 回退 |
| 2 | 编排 | LangGraph ReAct 循环 | 原生 ReAct 循环 + 多智能体编排器（角色、DAG、重试） |
| 3 | 记忆 | 一个提供工作记忆 + 情景记忆的库 | 全部四种记忆类型，SSM 原生，写穿式认知 |
| 4 | 向量数据库与 RAG | Pinecone/Chroma + 嵌入 | 基于 LanceDB 或 SSM 存储的**分块 + 混合检索（稠密 + BM25）+ 重排序** |
| 5 | 工具与集成 | `@tool` + MCP | 按能力管控的注册表、MCP 服务器、浏览器、10+ 渠道 |
| 6 | 可观测性与评估 | LangSmith/Langfuse | 追踪 + 成本计量 **+ 忠实度/幻觉 + 漂移** |
| 7 | 部署 | Docker + 一个队列 | Cloudflare Workers + Durable Objects + Containers + Docker |

其中五层早已超越参考设计。另外两层——RAG 和评估——*不错，但只是常规水平、偏薄*。这两层我们都补齐了。下面开始逐层导览。

## 第 1 层——基础模型

Builderforce.ai 把模型当作一种**可替换、可路由的资源**，而不是一项永久承诺。它兼容 OpenAI 的网关开放当前目录中可用的提供商，并支持配置路由、回退、自带凭据（BYO）以及推理控制。可用性因套餐、地区、凭据和运行时而异。

**结论：超越。** 你不必把产品押在某一家厂商的路线图上。

## 第 2 层——编排

单个 ReAct 循环（思考 → 行动 → 观察）只是底线。Builderforce.ai 原生运行这个循环，然后在其上叠加一个**多智能体编排器**：专家角色（创建者、评审者、测试生成者、缺陷分析者……）、任务依赖图、带自愈能力的有界重试，以及在进程重启后依然存续的持久状态。同一个循环在本地部署和云端都能运行，并内置对抗式评审环节。

**结论：超越。** 一个有治理的协同团队，胜过循环里的单个智能体。

## 第 3 层——记忆

参考技术栈通常由某个框架提供工作记忆 + 情景记忆。Builderforce.ai 提供**全部四种**——工作记忆、情景记忆、语义记忆、程序性记忆——而且它们是 *SSM 原生*的：知识通过在线蒸馏被写穿进一个模型（Evermind），而不只是追加到某个存储里，底层还有一个跨会话持久保存的事实库。

**结论：超越。** 会*学习*的记忆，而不只是会*记录*的记忆。

## 第 4 层——向量数据库与 RAG  ✦ 本次发布加固

在这一层，我们对自己很坦诚。Builderforce.ai 原本就有向量检索（LanceDB + 嵌入，外加一个零 API 的 SSM 嵌入存储）——但它*只用余弦相似度*。教科书式的 RAG 技术栈会做三件纯余弦检索做不到的事：把文档**分块**成精确的段落；运行**混合**检索（稠密向量*加上*稀疏 BM25，这样标识符、错误码、罕见名称这类精确词元就不会丢失）；以及按相关性和多样性进行**重排序**。

于是我们把这三者都构建进了标准记忆层：

![混合检索：稠密与稀疏信号经 RRF 融合、再由 MMR 重排序](/blog/hybrid-retrieval.svg)

- **分块**——带重叠的递归字符切分器，让大文档变成连贯的段落。
- **BM25**——Okapi 词法评分，与稠密向量检索并行。
- **倒数排名融合（RRF）**——基于*排名*合并两种排序结果，而不是基于无法相互比较的原始分数。
- **MMR 重排序**——在相关性与新颖性之间权衡，避免 top-k 结果变成五条近乎重复的内容。

它能优雅降级：没有可用的嵌入模型 → 只用 BM25；没有词法重叠 → 只用稠密检索。它同时接入了 SSM 记忆存储和 LanceDB 长期记忆路径，写入时即进行分块。

**结论：如今已超越。** 混合检索 + 重排序，正是大多数手搓 RAG 技术栈永远走不到的那一步。

## 第 5 层——工具与集成

工具是模型可以选择调用的一个带类型的函数。Builderforce.ai 拥有一个**按能力管控的工具注册表**（工具声明自己所需的能力；运行时按界面——云端、容器、本地部署——进行筛选，因此同一套工具在哪里都能运行）、一个向外部 IDE 开放工具的 **MCP 服务器**、Playwright 浏览器自动化、Web/搜索/git/shell 工具、10+ 个消息渠道，以及用于自定义工具的插件 SDK。

**结论：超越。** 一份工具契约，覆盖所有界面，无需逐个界面手工挑选。

## 第 6 层——可观测性与评估  ✦ 本次发布加固

LLM 会悄无声息地失败——一个幻觉出来的答案照样返回 HTTP 200。Builderforce.ai 原本已经追踪每一次 LLM 调用，计量词元与成本，并按*结果*为运行打分（PR 是否合并、CI 是否通过、用了多少步、花了多少钱）。它没有做的，是评估答案是否**有据可依、紧扣主题**——也就是如今每一款 LLM 可观测性工具都会提供的语义评估指标。

我们把它们加上了：

![评估与漂移：忠实度、相关性、幻觉——外加回归告警](/blog/evaluation-and-drift.svg)

- **忠实度**——答案是否得到其上下文的支持？
- **答案 / 上下文相关性**——它是否回应了问题；检索到的上下文是否相关？
- **幻觉率**——答案中*没有*依据的部分所占的比例。

两种后端，一个接口：**零成本的词法评分器**在每一次云端运行中内联执行（不产生额外的 LLM 调用）；而**以 LLM 为评判者（LLM-as-judge）**的升级版可通过 `/api/eval` 按需使用，与其他任何补全一样通过同一个计量网关计费。评分会持久保存在运行记录上，而**漂移监控器**——均值偏移 z 分数加上群体稳定性指数（PSI）——会按（操作类型 × 模型）比较基线窗口与近期窗口，并在质量回退时发出告警。它每天通过 cron 运行，也可以通过 `/api/eval/drift` 按需运行。

**结论：如今已超越。** 悄无声息的质量回退会变成一条告警，而不是一块全绿的仪表板。

## 第 7 层——部署

参考设计是 Docker 加一个同步 API 或异步队列。Builderforce.ai 运行在 **Cloudflare Workers + Durable Objects** 之上（一个能越过无服务器超时墙持续运转的持久智能体循环），外加用于需要 shell 的运行的 **Containers**，本地开发则使用 Docker。缓存是一等公民——读穿式缓存（L1 isolate 内 + L2 KV）、提示缓存和语义响应缓存——同时还有按租户的成本上限与步数预算。

**结论：超越。** 持久、有缓存、有成本上限，并且是托管的。

## 要点

理解完整的技术栈，并不意味着要拼装七家厂商，然后祈祷接缝别出问题。Builderforce.ai 就是这七个层级构成的单一系统——有治理、可观测——而在本次发布之后，它不只是*拥有*每一层，而是在每一层都**达到或超越**参考设计。原本只是常规水平的两层——RAG 检索和语义评估——如今分别做到了混合检索加重排序，以及忠实度评分加漂移检测。

这就是“画在图上的技术栈”和“真正交付的技术栈”之间的区别。
