产品团队很少缺反馈，缺的是一条可信的路径：从成千上万条评论走到少数几个决策，再从这些决策走到客户真正能够评估的东西。

Creation Canvas 把这条路径变成一次可见的会话。

![成千上万条客户反馈信号穿过一台晶体般的综合引擎，扇形展开为十个各不相同的高保真交互式产品概念，从每个来源到每个模型稿的证据线索都清晰可见](/blog/feedback-to-mockups-hero.webp)

## 1. 引入证据

以这样的提示词开启一次会话：

> 可视化我们的客户反馈，找出需求最多的十项功能，并为每一项创建一个交互式概念。

添加一个 Dataset 对象并导入 CSV 或 TSV 格式的反馈。你也可以把基于项目的反馈、报告、仪表盘、文档或已连接的 MCP 数据源放到画布上。对敏感数据源的访问仍然遵循底层资源的权限；添加对象并不会把这些管控复制到别处。

让 Brain 对主题、客群、频次和时效进行剖析。Chart 或 Dashboard 对象可以显示哪些诉求整体上占主导，以及哪些诉求对高价值客户群体而言格外重要。

## 2. 综合归纳，而不只是计数

原始提及次数有用，但它不是路线图。两位客户可能用不同的措辞描述同一个需求，而一个具有战略意义的诉求，其分量可能超过五十条表面化的偏好。

Brain 会创建一个 Feature Summary 对象，把语义相关的反馈归为一组，并保留对原始证据的引用。一份好的摘要会记录：

- 客户问题；
- 有代表性的原始证据；
- 频次与受影响的客群；
- 预期成果；
- 已知的约束与依赖；
- 置信度与证据的新鲜度。

由于摘要本身是一个对象，协作者可以对它发表评论、关联项目指标，或者要求换一种优先级视角，而不会丢失最初的解读。

## 3. 把十项功能展开为模型稿

把 Feature Summary 连接到一个 Mockup Set，并让 Brain 展开每一项。每项功能都会成为一个可单独评审的 Mockup 对象，而不是一张静态拼贴图。

当某个概念需要更高保真度时，使用所见即所得的 Prototype 对象。你可以在检查器中直接编辑标题、行动号召、颜色、响应式视口、导航或数据绑定。评审时还可以在概念周围添加绘图和备注，并把相关的变体归入一个可复用的 Frame。

到这一步，画布就变成了一间可视化的决策室：证据在左，综合出的机会在中，交互式概念在右。

![Product Discovery 套件保留了完整的溯源链：从 CSV、报告、仪表盘和 MCP 数据源，经过带引用的 Feature Summary，到十个可单独评审的 Mockup；随后评估客户影响、重叠情况和交付风险，最终创建一个获批的 Task 和 Agent 运行](/blog/feedback-mockup-provenance.svg)

## 4. 用现实来检验概念

添加相关的 Project 对象，并展开它的客户反馈、指标或交付视角。此时 Brain 可以把一个模型稿与当前功能、进行中的工作、产品健康度以及交付约束进行比较。

可以这样提问：

- “哪个概念解决的已验证客户问题最大？”
- “哪些功能与已规划的工作重叠？”
- “哪些依赖让这三个概念在本季度风险较高？”
- “根据获批的那一组，生成一份销售叙事和一份高管路线图。”

Brain 会添加持久的 Evaluation、Roadmap 和 Slides 对象，来源均可检查。建议的多对象变更在评审者选中并应用之前，始终只是提案。

## 5. 交付获批的工作

在探索阶段，项目是可选的，但到了交付阶段就很有价值。在获批的 Mockup 上选择 **Add to project and assign**。Builderforce 会创建或关联一个 Task，附上该工件，指派给一位人类成员或 AI Agent，并应用项目的审批策略。

任务的运行状态始终可以在会话中看到。评审者可以看到工作是就绪、运行中、等待审批、受阻还是已交付，而不必抛开促成这项工作的证据和决策。

这正是“生成十张图片”与“开发十个产品概念”之间的关键差别。每个概念都有出处，每次审批都有审计轨迹，每个交付的工件都有一条通往可问责工作的路径。

## 使用可复用的 Product Discovery 套件

Creation Canvas 模板库包含一个 Product Discovery 套件，其中 Dataset、Feature Summary、Mockup Set 和 Evaluation 对象已经排布好并相互连接。团队也可以为自己的评审流程保存自定义 Frame。

从套件开始，或者从空白画布开始，工作流程都是一样的：

**证据 → 综合 → 视觉概念 → 评估 → 审批 → 交付**
