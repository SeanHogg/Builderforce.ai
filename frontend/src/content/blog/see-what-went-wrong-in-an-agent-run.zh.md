你让编辑器代理再做几个可视化。十三分半钟后，它做了十三处修改，令牌计数器已经爬过三百万，而它最后改动的那个文件里有什么东西编译不过了。你把它停了下来。

然后你想弄清楚发生了什么，却做不到。运行没有崩溃，所以没有错误可看。模型每一轮都作答了，所以也没有超时。诊断报告把整个过程看了一遍，只给出一个词：**无法判定（Inconclusive）**。

那次运行是真实的。事后我们手工重放了它记录下来的轨迹，所有问题都在里面：第一次修改之前有 21 轮都在读；有 13 轮每轮只做了一处编辑，却每次都重新发送约十万令牌的对话；一次类型检查或测试都没有；还有一处编辑把一个对象早关了一个花括号。这些全都被记录了下来，却没有任何东西指出它们。

## Agent runs 抽屉

VS Code 中的 Visualizer 现在有了一个 **Agent runs** 抽屉。它列出你正在查看的项目最近的编辑器代理运行。选中一次运行，它就会读取这次运行的记录，告诉你其中哪里出了问题。

它不用模型来做总结。每条发现都来自对已记录轮次的一项固定检查，所以同一次运行每次都会得到同样的发现，而且每一条都会告诉你它从何而来。

- **没完没了的分析：** 第一次修改之前有大量只读轮次，以及是否需要计划预算强制交接。
- **说了准备好却没有行动：** 代理说它准备好了，然后继续读。
- **每轮只写一处：** 一连串每轮只做一处修改的轮次，以及这些轮次合计花掉的提示令牌。
- **提示膨胀：** 运行每写回一个令牌要发送多少提示，以及每处修改的成本。
- **写了却从未检查：** 被修改的文件之后没有任何类型检查、测试、lint 或诊断调用。
- **括号不平衡：** 某次编辑的新文本打开或关闭的花括号、方括号或圆括号，比它替换掉的文本多。
- **反复改写：** 同一个文件被一遍又一遍地重写。
- **建了工单，又自己做了：** 运行期间创建的工单从未交给任何人，最后由会话自己动手实现。
- **又慢又大的轮次：** 超过一分钟的轮次，以及携带数千字节重复参数的工具调用。
- **未经验证就停止：** 运行在你按下停止时结束，仍有未检查的修改悬而未决。

## 今天你就能用它做什么

- **打开任意一次最近的编辑器代理运行**，几秒钟内看清它的时间和令牌花在了哪里。
- **指出每个问题背后的轮次、工具和文件**，而不是凭记忆去描述。
- **看到一次运行改了哪些文件却从未检查**，并从任何一个文件跳到知识地图。
- **让代理发现自己弄坏的编辑**：语言服务器错误和括号警告会直接出现在编辑本身的结果里。

## 它在方法中的位置

Idea to Real 依次经过 Idea、Make、Run 和 Measure，而内循环是 [Read, Prove, Build](/blog/read-prove-build-the-inner-loop)：先理解已有的东西，再以低成本证明论断，然后才在构建上投入。我们对工作这样要求，做这份工作的代理也应达到同样的标准。

一次代理运行就是一次构建，而直到现在它都没有 Measure。你能看到它结束了，或者是你把它停了，却看不到它是不是读得太久、是不是写了不检查、是不是一路上弄坏了什么。Agent runs 抽屉就是代理的 Measure，它运行的检查是对已记录运行的证明。一条发现会说明发生了什么、在哪一轮、在哪个文件。编辑时的诊断和括号警告把这份证明的一部分移进了运行内部，放到那个原本会悄无声息失败的步骤上。
