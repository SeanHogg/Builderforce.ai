一个智能体接下一张工单，弄明白了这里的一次 schema 变更需要在某个模块里做一处声明、手写一个迁移，并按特定顺序运行两道守卫检查，然后把它合并，完成任务。

第二天，另一个智能体接下下一张 schema 工单，又把这一切重新弄明白一遍。

这就是本次发布要解决的问题。不是“智能体不够聪明”——它够聪明，而且聪明了两次。问题在于，它弄明白的一切都留在一份没人读的对话记录里，而产品中也没有任何对象可以承载“一个在这里行之有效的流程”。

## 技能就是一个流程，而现在智能体可以写一个

技能早就存在了：运行时内置了五十四个，另外还有一个市场。每一条写入路径都要经过一个人。所以智能体能遵循的流程，只有那些由人坐下来写好的。

现在，智能体可以提议一个。门槛被刻意设得很高——一个经过验证的结果，也就是已合并的工作，或一次确实产出了东西、并经过评分的运行——而邀请本身也直白地说明了这一点，因为一个在每次运行时都会触发的反思步骤，只会产出一份满是自信胡话的目录。

## 另外三扇曾经上锁的门

同一轮工作还打开了三样已经构建好、却无法触及的东西。

**接入你自己的工具服务器。** 代码库里一直躺着一个完整的 Model Context Protocol 客户端——三方 OAuth、按工具授权、加密的密钥存储，以及一个让凭据永远不经过浏览器的中继——而产品里没有任何东西调用它。租户只能手动调用 API 来注册外部服务器。现在，设置 › 集成下有了一个面板，VS Code 扩展里也有了一条命令，两者驱动的是同样的路由。

**编辑器里的治理。** 策略包在云端和自托管运行中都会被强制执行。编辑器有执行代码，却从未拿到任何关卡，所以一条在云端拦截某个工具的规则，在 VS Code 里却悄悄放行了。现在，两个编辑器界面都会在每次运行开始时解析同样的已编译关卡，而如果策略无法读取，就拒绝开始这一轮。

**引导自托管运行。** 发送给一个正在运行的本地部署执行的后续指示，会被接受、保存，然后丢弃——它被投递到了一个当前引擎早已不在其中运行的聊天会话。现在，它会抵达正在进行的运行，并作为它的下一轮被执行。

## 衡量这一切是否奏效

在查看智能体做了什么这方面，还有两件事也变了。

运行现在可以导出到你自己的 OpenTelemetry 采集器，所以智能体的工作会和你系统的其他部分放在一起，而不只在我们这里——旁边还会显示这次导出的健康状况，因为一个开始拒收 span 的采集器应该明确说出来，而不是悄悄把它们丢掉。

而智能体的质量，现在是一个时间序列，而不是一则轶事。现有的质量信号都是对到来的任何流量打分，所以一次环比变化，可能是智能体的原因，也可能只是这个月的工单不同。基准测试是一组固定的用例，每天以同样的方式打分，并把分数和预期覆盖率随时间绘制出来。

## 它在方法论中的位置

从构想到现实的弧线沿着 构想 → 构建 → 运营 → 衡量 展开，而方法的每一步都在提出一个问题：**读取**已经成立的事实，低成本地**验证**它，然后**构建**。

上面的一切，都落在这个循环的末端——也就是团队总会跳过的那一半。

**读取**有了一个真正能找到东西的记忆。云端路径上的调取，以前是关键词匹配，或者更糟：对十行由问题以外的因素选出来的记录做嵌入重排；一条落在这个窗口之外的相关记忆，是根本无法触及的。现在，它是一次真正的语义搜索，与关键词检索融合，使用的是自托管存储一直在用的同一套排序。一次能读到之前运行所学内容的运行，就是这套方法按描述运作的第一步。

**衡量**得到了其中两项。基准测试让“智能体是否在变好”成了一个有答案的问题，而导出让这个答案出现在你的团队本来就在看的地方。

而技能循环，就是这条弧线在自身上闭合。一次产出了经过评分的实证的运行，已经完整地走完了一遍 构想 → 构建 → 运营 → 衡量。把它提炼成下一次运行会遵循的流程，就是把一个循环变成一个螺旋：下一次读取，从上一次衡量所确立的东西出发，而不是从零开始。

这一直是我们的主张。现在，它是产品真正在做的事。
