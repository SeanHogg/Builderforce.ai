跨职能协作往往被切碎成一个个以工具划分的碎片。产品背景在工单里。客户证据在仪表盘里。原型在设计工具里。实现上下文在 VS Code 里。而围绕这四者的讨论，又散落在别的地方。

Builderforce 创作会话（Creation Session）为这些产物提供了一个共享的空间化家园，却不强迫每位协作者都使用同一个编辑器。

## 一个服务端会话，两个原生界面

在网页端，创作画布（Creation Canvas）是默认的可视化工作区，涵盖聊天、工作流、网站、数据、模型、人员、智能体和可选的项目。在 BuilderForce VS Code 扩展中，同一个会话会在完整的编辑器标签页中打开——不是 iframe，也不是狭窄的侧边栏。

两个界面使用同一份会话图、对象标识、权限、带版本号的命令契约、在线状态和评论。完整的活动时间线和专用检查器仍可在浏览器中使用。网页用户和编辑器用户是同一个会话里的协作者，而不是各自使用同步副本的用户。

原生 VS Code 界面可以在不离开编辑器的情况下加入开发上下文：

- 当前文件或选区；
- 仓库与分支上下文；
- 诊断信息和“问题”面板；
- 粘贴的终端输出（附带敏感信息警告）；
- 本地服务与浏览器预览；
- 原生面板中的任何共享画布对象类型。

产品经理可以在网页端连接客户证据和原型图，而开发者则在 VS Code 中连接失败的诊断信息、相关的源码选区和本地预览。

## 协作，但没有视口之争

每位成员都有自己的个人视口。移动或缩放你的画布，不会影响其他任何人。在浏览器中，在线状态会显示光标、选区、输入状态以及所使用的客户端界面。VS Code 面板则通过同一份持久的在线状态契约上报其当前选区。

当有人在演示时，协作者可以有意识地跟随这个人的视口。退出跟随模式后，控制权便回到个人手中。这让讲解演示变得有用，又不会把日常协作变成远程控制式的屏幕共享。

评论依附于对象。提及和活动会标明是谁要求 Brain 采取行动、是谁评审了提案，以及哪个规范资源发生了变化。角色区分查看者、评论者、编辑者、运行者和所有者的访问权限。底层资源的权限仍然生效——会话邀请并不是进入成员本无权访问的项目、数据集、智能体或代码仓库的捷径。

## 一次实用的设计到代码交接

设想一个团队正在评审新的引导流程：

1. 产品添加一个项目（Project）对象，并展开客户反馈和交付视图。
2. 设计把所见即所得的原型（Prototype）及其移动端变体放在证据旁边。
3. Brain 对照所需功能评估原型，并创建一个可供评审的变更集。
4. 团队批准一份设计稿（Mockup），并把它交付到分配给实现智能体（Agent）的项目任务（Task）中。
5. 开发者在 VS Code 中打开同一个会话，并添加相关的仓库、组件选区、诊断信息和本地预览。
6. 智能体按项目的审批策略执行。构建状态和输出会回到会话中显示。

没有人需要去重建这项任务为何存在。证据、决策、产物、实现上下文和执行历史始终保持关联。

## 用分支和检查点安全探索

命名检查点保留有意义的评审状态。会话分支支持更独立的实验——例如，不同的信息架构或模型流水线。分支回归时，Builderforce 会给出明确的逐对象合并评审。评审者可以对每个匹配的对象选择使用分支版本，或保留父版本。

手绘涂鸦、便签和可复用的画框（Frame）支撑着围绕正式产物的那些杂乱的空间化工作。市场包则为营销活动、产品探索、数据故事、站会、模型构建和高管评审提供更结构化的起点。

## 交接变成共享的运营全景

“交接”意味着一个团队完成后，另一个团队开始。多人创作会话支持一种更好的模式：贡献者加入各自工作所特有的上下文，共享画布保留它们之间的关系，Brain 则帮助跨越这些上下文进行推理。

浏览器仍然是收集业务背景最便捷的地方。VS Code 仍然是进行细致实现的正确场所。Builderforce 把两者连接起来，而不会把任何一方压缩成一份文字记录。
