一次评审卡在了“Judging”状态。你看得见，也能截图。可你完全不知道，四千个文件里到底是哪一个在作怪。

这就是那道鸿沟。症状出现在屏幕上，病因藏在代码库里，除了碰巧记得的那个人，没有任何东西能把两者连起来。于是人们去找图，图把每个文件都画成一个点，而这些点什么也说明不了。一张由成千上万个节点构成的图，并不是对“这个会流向哪里？”的回答。它只是换了个更好看背景的同一堵文件墙。

## 一张地图，画得像地铁线路网

知识视图现在以城市展示列车线路的方式来展示代码库：**线路**。每条线路从一个入口点出发——可能是一个路由、一个界面或一项作业——穿过它所经过的各个层，最终抵达它所触及的存储和外部服务。你读到的是一条路径，而不是一堆杂物。

你可以直接提问，而不是挑选视角。**它流向哪里？** **哪里出了问题？** **哪里没有测试？** **这里有哪些模式？** **发生了什么变化？** 每个问题都会替你设置好视图和叠加层，让答案成为屏幕上最先看到的东西。

## 粘贴截图

这正是改变你整个下午的部分。把截图拖进提问栏。一个视觉模型会读出其中可见的文字。接着由普通搜索接手：它把这些文字与你的翻译目录和源代码相匹配，找到对应文件，并再向外走一次导入。视图随之过滤，只留下你所见内容背后的代码。

  "title": "从卡住的界面到背后的文件",

这种标注才是关键。**精确**匹配，是在代码中找到了这个字符串本身。**目录**匹配，是通过翻译文件找到的——屏幕上的文字通常并不是源代码里的文字，往往就是这个原因。**导入**匹配则是一个邻居，相隔一跳。在你花上一分钟之前，就能分辨哪些匹配是确定的，哪些只是可能的。

接着，**用智能体诊断**会把路径以及地图已经掌握的一切信息传递出去。智能体不必从一张白纸和一个搜索框开始。

叠加层把一个指标变成视觉通道，而且任何指标都可以驱动任何通道。

地图周围是你接下来会用到的面板：

- **同步**显示你机器上的内容与服务器上的内容对比，以及哪些文件被跳过及原因，因此地图上的缺口绝不会成为谜团。
- **覆盖率**显示哪里没有测试。
- **模式**列出代码中的反模式及其聚集之处。
- **API** 把你的路由转换为 OpenAPI 骨架或 Postman 导出文件。
- **修复队列**对未使用的代码应用确定性修复，其余情况则为智能体写出提示词。
- **模拟**让智能体编写并运行一个测试，用你选定的值驱动一条路径，让“这里真的会流向那里吗？”得到真实的答案。

## 它在方法论中的位置

[Idea to Real](/blog/idea-to-real-the-operating-methodology) 贯穿从 Idea 到 Make、Run 和 Measure 的全过程。这项能力关乎那些决定是否投入的行动，以及真正花钱的那个行动。

**它让“读取”在你已有的代码上真正奏效。** [读取](/blog/read-prove-build-the-inner-loop)问的是实际有什么，而且它本应是免费的。对于一个运行中的系统，“实际有什么”过去意味着在文件里耗上数小时。地图和提问栏把它缩短为几分钟，而且在你选择之前不会产生任何智能体开销。

**它通过缩小范围让“构建”更便宜。** 构建是花钱的行动，而瞄准错误文件的构建是最昂贵的一种。一张截图能让智能体落在正确的路径上，并附带所有发现，这意味着钱花在改动上，而不是花在寻找改动该落在哪里上。

**它同样有助于“运行”和“度量”。** 在“运行”中，实时界面上的一个症状会变成一条路径。在“度量”中，同样的叠加层会显示什么发生了变化、什么没有测试，让你看到系统在哪里发生了变动，而不只是知道它变动了。

## 你今天就能用它做什么

- **粘贴一张 bug 截图**，看到背后的文件，每个文件都标注了是如何被找到的。
- **询问一个请求流向哪里**，从入口点穿过各层，直到末端的存储和服务。
- **询问哪里出了问题、哪里没有测试、什么发生了变化**，并得到能回答它的视图。
- **在同一个代码库的八种视图之间切换**，而不会丢失你的位置。
- **导出你的 API**，基于已发现的路由生成 OpenAPI 骨架或 Postman 集合。
- **清理未使用的代码**，采用确定性修复，并把其余一切作为现成的提示词交给智能体。
- **模拟一条路径**，用你自己的值，在信任它之前先验证一遍。
