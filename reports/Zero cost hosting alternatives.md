# Split Builderforce across free edge and free VM

No $0 combination keeps every current Builderforce.ai capability at current scale. The closest is a hybrid with four parts: **Cloudflare's Free plan as the edge** (thin Worker router, all 11 SQLite Durable Objects, R2 with wildcard sites, inbound email, Workers AI), **Neon Free** restructured so that no single project exceeds 100 CU-hours a month, **one Oracle Always Free Ampere A1 VM** behind Cloudflare Tunnel for the container workloads and the CPU-heavy API routes, and the **tenant's own GitHub Actions** as the overflow path for coding-agent runs. The runtime already supports that last path. Three capabilities have no $0 home at current scale: **25 concurrent budgeted coding-agent containers**, **three always-available Chromium runners plus live preview dev servers next to them**, and **heavy Worker routes and crons that need more than 10 ms of CPU or more than 50 external subrequests**. Oracle's A1 allowance was halved to **2 OCPU / 12 GB** on 2026-06-15, which caps realistic concurrency at roughly 2–4 agents *or* about 3 browsers, not both. The cheapest escape hatches are Workers Paid at $5/month, which brings back Containers, 5-minute CPU and unlimited daily requests, and Modal's recurring $30/month Starter credit, which allows 100 concurrent containers. Several 2025–2026 changes cut both ways. Cloudflare removed the compressed bundle limit, so the 4.58 MiB-gzip API now deploys on Free. In the other direction, Oracle halved A1, Neon moved to per-project quotas, CockroachDB, Hugging Face Docker Spaces and Koyeb ended free compute or database tiers for new users, AWS replaced its 12-month free tier with credits, and Vercel Hobby still bans commercial use. All of this sits on free plans with no SLA, broad unilateral termination rights, and a documented record in 2026 of unannounced cuts. A $0 Builderforce is therefore a deliberate reliability downgrade, not a lateral move.

The brief says the operator "refuses to pay for either Neon or Cloudflare." This report reads that as "stay on their *free* plans". Architecture C below covers the stricter reading: leave both vendors entirely.

## Cloudflare Free keeps the edge; 10 ms of CPU decides what has to leave

Removing the compressed size limit changes the central question. The question is no longer whether the API fits on Workers Free, but which of its code paths can run inside **10 ms CPU per request, 50 external subrequests per invocation and 100,000 requests/day** ([CF Workers limits](https://developers.cloudflare.com/workers/platform/limits/)). Cloudflare says the average Worker uses about 2.2 ms. It also says each isolate has "some built-in flexibility" for occasional overruns, but publishes no figure for how much. Routes that verify JWTs, reshape large JSON or parse LLM responses on every call should be expected to fail intermittently. Crons get the same 10 ms on Free, against 30 s on Paid for sub-hourly schedules. The startup limit is still 1 second, so a 20.6 MiB bundle can deploy and still fail to start. Run a dry-run deploy before anything else. Going over the daily request limit returns Error 1027 until 00:00 UTC.

Durable Objects are the strongest reason to keep Cloudflare. **Free allows only SQLite-backed DOs, which is what Builderforce already uses.** The daily limits are 100,000 requests, 13,000 GB-s, 5M rows read, 100,000 rows written and 5 GB stored, and "exceeding any limit causes further operations to fail" ([CF DO pricing](https://developers.cloudflare.com/durable-objects/platform/pricing/)). WebSocket messages are billed at 20:1 under Hibernation, and every `setAlarm()` counts as one row written. At 128 MB per object, 13,000 GB-s works out to roughly 28 DO-hours of wall-clock activity a day across all objects (this is my arithmetic). That makes Hibernation mandatory for the WebSocket rooms and the agent-host relay. The **100,000 rows written/day** limit is the one Yjs persistence and alarm-driven step runners will hit first. No managed alternative comes close at $0. Liveblocks Free caps rooms at 10 simultaneous connections and requires a watermark, while Ably Free and Supabase Realtime top out around 200 concurrent connections ([Liveblocks](https://liveblocks.io/pricing), [Ably](https://ably.com/pricing)).

## Postgres stays on Neon Free only if the cron stops keeping it awake

The storage numbers are not the problem. **437 MB, 261 MB and 8 MB all fit under 1 GB per project**, against a 20 GB org total. Compute is the problem. Neon counts **100 CU-hours per project per month**, and its FAQ confirms each project gets "its own 100 CU-hour bucket" ([Neon FAQ](https://neon.com/faqs/free-plan-limits-and-quotas)). The ~235 CU-hours a month in the brief is under the 300-hour combined ceiling only if no single project goes over 100, and the 750-table core database probably carries most of that load. Autosuspend after 5 minutes cannot be disabled. A cron every 5 minutes therefore keeps a compute permanently awake: about 182 CU-h/month at 0.25 CU, or about 730 at 1 CU (research-note arithmetic). That alone exceeds the cap ([Neon plans](https://neon.com/docs/introduction/plans)). **The first database task is to gate the 5-minute cron through the KV/DO work gate so it touches Postgres only when there is work.** The second is to read per-project CU-h in the Neon console. Storage overruns block writes, and the 6-hour restore window with one manual snapshot is not a backup. A nightly `pg_dump` to R2 (10 GB free) is the mitigation.

The managed alternatives are weaker. **Supabase Free caps databases at 500 MB, goes read-only above that, includes no backups, and pauses projects after a week of inactivity** ([Supabase pricing](https://supabase.com/pricing), [size docs](https://supabase.com/docs/guides/platform/database-size)). That rules out the 437 MB core once it grows. Prisma Postgres Free has 500 MB and 200,000 operations a month ([Prisma](https://www.prisma.io/pricing)), and the 8,640 cron runs a month alone would use a large share of that. Aiven Free gives 1 GB on 1 CPU / 1 GB RAM with no connection pooling, and Aiven reserves the right to shut down services "unused for an extended period of time" ([Aiven](https://aiven.io/pricing?product=pg)). Nile Free offers 1 GB and 50M "query tokens", but its pg_trgm/pgcrypto support is unverified ([Nile](https://www.thenile.dev/pricing)). None of these offers the pgvector + pg_trgm + pgcrypto trio *and* 1 GB *and* backups for free. Neon already does, which is why staying on Neon Free beats migrating.

The only $0 option with no compute cap is **self-hosted Postgres on the Oracle VM**. It has 200 GB of disk, any extension, and the 10 TB/month egress is far above Neon's 5 GB per project. Workers reach it through Hyperdrive, which is free up to 100,000 queries/day ([Hyperdrive](https://developers.cloudflare.com/hyperdrive/platform/pricing/)). The costs are that the database shares a single VM, and its 12 GB of RAM, with untrusted agent workloads, and that the operator takes on patching, WAL archiving and failover. Append-only telemetry (261 MB) could also move to D1 (5 GB, 100k rows written/day, now enforced) or Turso Free (5 GB, 10M rows written/month) ([Turso](https://turso.tech/pricing)). Either move takes write pressure and compute off the core. The tradeoff is a SQL-dialect split, and whether telemetry's daily write rate fits under 100k is unknown.

The practical answer has three layers. The Oracle VM is the always-on floor, running two or three agents, one QA runner, one stage sandbox and a few previews under a hard concurrency budget. Burst load goes to the tenant's own GitHub Actions, which is $0 to Builderforce but moves a quota and a GitHub dependency onto tenants. The DO runner handles shell-free steps. Live previews and Playwright QA lose the most: about three concurrent browsers sharing 2 cores with builds, and Cloudflare Browser Run's 10 minutes a day covers roughly 20–60 short renders. The cheapest non-zero option that restores the original 25-concurrent shape is **Workers Paid at $5/month**. The research did not establish the included Container allowance or the per-instance rates above it, so the full cost at 25 concurrent is unverified. Modal's $30 credit is a functional alternative for burst agent runs.

Two Oracle details shape the deployment. First, Chrome's branded channel fails to install on Linux arm64, so use Playwright's own Chromium builds or the multi-arch `mcr.microsoft.com/playwright` image ([zenn.dev](https://zenn.dev/saneatsu/articles/f1f2141b6d464a), [Playwright Docker](https://playwright.dev/docs/docker)). The multi-arch tagging was not confirmed from Playwright's docs. Arbitrary tenant repos with x86-only native dependencies will break. Second, running untrusted tenant code in plain Docker on the same host as the API and the database is a real security regression from Cloudflare Containers' VM isolation. Splitting the A1 allowance into two 1-OCPU / 6 GB instances, one for the control plane and one for untrusted workloads, keeps that separation within the free limit. Coolify supports ARM64, documents setup on Oracle's free server, and routes per-app subdomains through a single Cloudflare Tunnel ([Coolify](https://coolify.io/docs/get-started/installation)). Cloudflare Tunnel's own Free-plan limits were not verified.

## Three $0 architectures, and what each surrenders

**Architecture A: Cloudflare Free plus Neon Free, no VM.** The Worker, DOs, R2 sites, KV, inbound email, crons and Workers AI stay where they are. Neon stays, reached through Hyperdrive. Agent work falls back entirely to tenant GitHub Actions and the DO runner. *It keeps* realtime collaboration, published sites, email intake and the data layer. *It loses* every platform-hosted container: interactive previews, platform-run Playwright QA, and the stage sandbox (Browser Run's 10 minutes a day is a token substitute). It also loses any route or cron that needs more than 10 ms of CPU or more than 50 subrequests. This is viable only as a deliberately reduced product.

**Architecture B: Cloudflare Free edge, an Oracle A1 origin via Tunnel, and Neon Free (recommended).** The Worker becomes a thin router and auth check. It keeps DOs, R2 and wildcard routing, email intake and small Workers AI calls, and its crons only enqueue. Heavy Hono routes run as a Node process on the VM with no CPU limit, and each proxied request costs one subrequest. The VM also hosts the agent, QA, sandbox and preview containers under Coolify, with tenant GitHub Actions as overflow. Neon Free stays on three projects with the cron gated, plus nightly dumps to R2. Variant B′ moves Postgres onto the VM, which removes the CU-hour and egress caps but makes one VM a single point of failure for both compute and data. *It keeps* nearly every feature at reduced concurrency. *It loses* 25-way agent concurrency, generous browser capacity and VM-grade tenant isolation. *It adds* two runtimes to maintain, an Oracle reclamation and termination risk, and Neon's per-project suspension risk.

**Architecture C: leave Cloudflare and Neon entirely.** Everything runs on the Oracle VM: Node API, a `ws` server, Hocuspocus for Yjs, Redis, Postgres and containers. The frontend goes on Netlify Free, objects on Backblaze B2 with Oracle Object Storage for cold blobs, scheduling on QStash or system cron, outbound email on Resend, and LLM calls on Groq. *It loses* the global edge, Durable Object semantics (step runners need a DB-backed job table and a poller), and a free inbound-email-to-webhook path; ImprovMX webhooks are paid, and Resend's inbound limits on Free are unverified. Wildcard routing moves to Traefik on the VM. Netlify's 300-credit cap pauses *every* project when hit. Oracle Object Storage allows only 50,000 API requests a month ([Oracle](https://docs.oracle.com/en-us/iaas/Content/FreeTier/freetier_topic-Always_Free_Resources.htm)). The whole platform also becomes one 2-core VM in one region. This is the strictly vendor-free reading, and the weakest of the three.

Terms of service add risks no architecture avoids. Cloudflare's agreement does not ban commercial use. It does forbid processing or collecting "credit card information on any web property that is receiving Free Services", lets Cloudflare terminate "at any time, with or without notice", and bans scripted creation of multiple accounts ([Cloudflare Terms](https://www.cloudflare.com/terms/)). **Billing must redirect to a Stripe-hosted page**, which is this report's reading rather than legal advice, and the 100k/day limits cannot be multiplied across accounts. Neon's ToS has no free-plan commercial or multi-project restriction, and its FAQ describes per-project buckets as intended ([Neon ToS](https://neon.com/terms-of-service)). Neon's Acceptable Use Policy was not read. Oracle has documented anecdotes of free accounts terminated without explanation ([LowEndSpirit](https://lowendspirit.com/discussion/10956/oracle-free-tier-changing-be-careful-confirmed); community reports, not official). Oracle also showed in 2026 that it will cut allowances without announcement. Vercel Hobby is excluded outright, and Deno Deploy Free describes itself as for "personal projects" ([Deno](https://deno.com/deploy/pricing)).

### Recommended migration sequence

The order matters. Containers stop working the moment the account drops to Workers Free, so the VM must be serving before the downgrade. The steps below follow that order and assume Architecture B.

| # | Step | Gate before proceeding |
|---|---|---|
| 1 | Measure: per-route CPU with Workers Logs (200,000 events/day free), daily Worker and DO requests, DO rows written, KV writes, per-project Neon CU-h | List of routes and crons that exceed 10 ms or 50 subrequests; confirm Neon is 1 GB, not 0.5 GB, per project in the console |
| 2 | Gate the 5-minute cron so it wakes Neon only when work exists. Add a nightly `pg_dump` to R2. | Every Neon project projected under 100 CU-h/month |
| 3 | Provision Oracle A1 in the home region, preferably as two 1-OCPU / 6 GB instances. Install Docker and Coolify, and connect `cloudflared`. | Instances survive a week above the 20% reclamation thresholds |
| 4 | Rebuild agent, QA and sandbox images for arm64 on Playwright's Chromium. Run them on the VM with a hard concurrency budget. Set the runtime fallback order to VM, then tenant GitHub Actions, then DO runner. | Agent run, QA run and preview all pass end-to-end through the Tunnel |
| 5 | Move the step-1 heavy routes and the bodies of over-limit crons to the Node process on the VM. Leave the Worker as router and auth, with crons that only enqueue. | No `Exceeded CPU` or subrequest errors in a dry-run on Free limits |
| 6 | Move auth and L2 caches from KV to DO SQLite or Redis on the VM. Keep KV for the cron gate. Make sure every WebSocket DO uses Hibernation. | Projected KV writes under 1,000/day and DO writes under 100,000/day |
| 7 | Serve Next.js from Workers static assets (check the 20,000-file limit), move card collection to Stripe-hosted Checkout, and move outbound mail to Resend | No card fields on any Cloudflare-proxied page |
| 8 | Downgrade Cloudflare to Free. Confirm R2, wildcard routes and Email Workers still bind (card-on-file and wildcard-route behaviour is unverified). | Error 1027 and DO-limit alerting in place |
| 9 | Optional: move Postgres to the VM (B′) or move telemetry to D1/Turso if Neon compute stays tight | Restore drill from R2 dump succeeds |

## Conclusion

Paying the vendors was mostly buying headroom, not features. Every Builderforce feature except container concurrency has a free home, but each one now sits behind a hard daily limit that fails closed: 100k Worker requests, 100k DO row writes, 1,000 KV writes, 10,000 Neurons, and 100 CU-hours per Neon project. The operational job therefore shifts from paying bills to **budgeting quotas per subsystem and alerting before 00:00 UTC resets**. That discipline does not exist yet. The coding agent is a different case. The existing fallback to the tenant's own GitHub Actions turns a capacity problem into a product decision: at $0, scaling depends on tenants bringing their own compute.

The economics are lopsided. Workers Paid at $5/month removes the 10 ms limit, the daily caps and the Container ban in one step. Neon's pay-as-you-go rate is $0.106 per CU-hour, so today's ~235 CU-hours would cost about $25/month if the free per-project buckets ever fail ([Neon pricing](https://neon.com/pricing); this report's arithmetic). Neon is the component worth fighting to keep free. Cloudflare's $5 is the component where refusing to pay buys the most engineering work and the most fragility. If the refusal is firm, Architecture B is the right target. Treat Oracle's 2 OCPU as the free tier most likely to change again, and keep every container image multi-arch and every database dump portable, so that leaving it takes days rather than a rewrite.
